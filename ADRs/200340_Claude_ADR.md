📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: OCF 표준 기반 스마트팜 IoT 플랫폼 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 온도·습도·CO₂·토양 수분 등 다양한 센서와 액추에이터가 혼재하며, 제조사별 프로토콜 파편화로 인해 상호운용성 확보가 핵심 과제다. Wi-Fi, Zigbee, Bluetooth 등 이기종 전송 계층 위에서 단일 데이터 모델로 장치를 통합 관리해야 하며, Industrial 프로파일 적용이 요구된다.                                                                         |
| **결정(Decision)**       | OCF(Open Connectivity Foundation) 표준을 핵심 프레임워크로 채택하고, Core Framework의 Resource Model & RESTful Interactions를 통해 모든 센서/액추에이터를 추상화한다. 전송 계층은 Wi-Fi(실내 광역), Zigbee(저전력 메시), Bluetooth(근거리 점검)를 병용하며, oneIoTa 데이터 모델로 시맨틱 통일성을 확보한다. 프로파일은 Industrial을 주축으로 한다. |
| **근거(Rationale)**      | OCF는 ISO/IEC 30118 국제 표준으로 농업·산업 IoT에서 검증된 상호운용성을 제공한다. RESTful 인터페이스는 클라우드 플랫폼 연동 및 UI 서비스 개발 공수를 최소화한다. oneIoTa는 농업 특화 리소스 타입(온습도, 관개 밸브 등)을 표준 스키마로 지원하여 데이터 모델 재사용성이 높다. Security, Identity & Permissions 레이어가 프레임워크에 내장되어 있어 별도 보안 미들웨어 개발 부담이 낮다.     |
| **결과(Consequences)**   | ✅ 벤더 종속성 탈피 및 다중 공급사 센서 통합 가능 / ✅ Discovery·Provisioning·Comms 표준화로 신규 장치 온보딩 자동화 / ✅ RESTful API 기반 UI 서비스 개발 속도 향상 / ❌ OCF 인증 비용 및 펌웨어 포팅 공수 발생 / ❌ 저사양 MCU(예: 8-bit AVR) 계열 센서 노드에서 OCF 스택 탑재 제약                                                         |
| **트레이드오프(Trade-offs)** | **얻는 것:** 표준 준수를 통한 장기 유지보수성, 멀티벤더 생태계 확장성, 내장 보안 레이어 / **감수할 것:** 초기 구축 복잡도 증가, 경량 엣지 노드에서의 스택 오버헤드, OCF 표준 업데이트 주기에 따른 버전 관리 부담                                                                                                                           |

### ADR-002: 다중 전송 계층(Multi-Transport) 병용 전략

| 항목                     | 내용                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜은 온실 내부(수십 m)부터 노지 광역(수백 m)까지 커버리지 요구사항이 상이하고, 배터리 구동 토양 센서와 유선 전원 카메라가 공존한다. 단일 전송 기술로는 전력·거리·대역폭 요구를 동시에 충족할 수 없다.                               |
| **결정(Decision)**       | Zigbee(저전력 메시, 토양/환경 센서), Wi-Fi(고대역폭 카메라·게이트웨이), Wi-Fi Direct(P2P 현장 점검), Bluetooth(근거리 설정·유지보수)를 역할 분리하여 병용하고, OCF Core Framework의 Comms 레이어에서 추상화한다. |
| **근거(Rationale)**      | 역할 기반 전송 계층 분리는 전력 최적화와 커버리지 확장을 동시에 달성한다. OCF의 전송 계층 독립적 설계(Transport Agnostic)가 이를 아키텍처적으로 지원한다.                                                     |
| **결과(Consequences)**   | ✅ 배터리 수명 연장 및 운영비 절감 / ✅ 농장 규모 확장 시 Zigbee 메시 노드 추가만으로 커버리지 확대 / ❌ 다중 무선 프로토콜 관리를 위한 게이트웨이 복잡도 증가 / ❌ 전파 간섭(2.4GHz 대역 혼용) 리스크                          |
| **트레이드오프(Trade-offs)** | **얻는 것:** 최적화된 전력·커버리지·대역폭 조합 / **감수할 것:** 게이트웨이 단일 장애점(SPOF) 위험 증가, 무선 채널 플래닝 필요                                                                      |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 게이트웨이 단일 장애점(Single Point of Failure)

* **설명:** Wi-Fi, Zigbee, Bluetooth 등 다중 전송 계층을 OCF Core Framework로 집약하는 게이트웨이 장비가 물리적 장애(전원 차단, 하드웨어 결함) 또는 소프트웨어 크래시 발생 시, 온실 내 전체 센서 데이터 수집과 액추에이터 제어가 동시에 중단된다. 특히 고온 경보·관개 자동화 등 실시간 제어가 필요한 스마트팜 환경에서는 작물 피해로 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 게이트웨이 이중화(Active-Standby 구성) 및 엣지 노드 자체 로컬 Failsafe 로직 탑재(네트워크 단절 시 최후 수신 명령 유지). 게이트웨이 상태를 주기적으로 Watchdog 모니터링하고 자동 재시작 정책 적용.

### 2. 2.4GHz 대역 무선 전파 간섭

* **설명:** Zigbee(IEEE 802.15.4), Wi-Fi(802.11b/g/n), Bluetooth가 모두 2.4GHz 대역을 공유하는 환경에서, 온실 내 다수 센서 노드가 동시 통신 시 채널 충돌이 발생한다. 특히 관개 펌프 제어 신호 지연이나 화재·이상온도 경보 패킷 손실이 발생할 경우 안전사고로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** Zigbee 채널을 15·20·25번(Wi-Fi 비중첩 채널과 최대 이격)으로 고정 할당. Wi-Fi는 5GHz 듀얼밴드 AP 도입. Bluetooth는 저에너지(BLE) 주파수 호핑 활용. 채널 플래닝 도구로 현장 RF 스펙트럼 사전 측정 필수.

### 3. OCF Security 레이어 미적용 또는 설정 오류로 인한 인증·인가 취약점

* **설명:** OCF Core Framework는 Security, Identity & Permissions 레이어를 내장하지만, 현장 배포 시 개발 편의를 위해 ACL(Access Control List)을 과도하게 개방하거나 기본 자격증명을 변경하지 않는 경우가 빈번하다. 외부 공격자가 Discovery 프로토콜을 통해 네트워크에 노출된 디바이스를 탐색하고 무단으로 액추에이터(관개 밸브, 환기팬)를 조작할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 배포 파이프라인에 OCF 보안 설정 검증 단계 의무화(Provisioning 단계 자동화). 디바이스 온보딩 시 DTLS 1.2 이상 및 상호 인증(Mutual TLS) 강제 적용. 정기적인 펜테스트 및 OCF 보안 컴플라이언스 감사 수행.

### 4. oneIoTa 데이터 모델 버전 불일치로 인한 상호운용성 파괴

* **설명:** 다수의 벤더가 공급하는 스마트팜 센서들이 서로 다른 버전의 oneIoTa 리소스 타입을 구현하는 경우, Resource Model 레이어에서 속성 키 불일치 또는 단위 체계 차이(예: 온도 °C vs °F, 토양수분 % vs kPa)로 인해 플랫폼 UI에서 데이터 오독이 발생한다. 잘못된 센서값 해석은 과관개 또는 환기 오작동을 유발한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 플랫폼 진입 시 리소스 타입 버전 검증 게이트웨이 레이어 구성. oneIoTa 버전별 변환 어댑터(Adapter Pattern) 구현. 신규 센서 벤더 온보딩 시 데이터 모델 적합성 테스트를 인수 조건으로 명문화.

### 5. 저전력 엣지 노드의 OCF 스택 리소스 부족

* **설명:** Zigbee 기반 토양 센서 등 저사양 MCU(예: ARM Cortex-M0, 32KB Flash)에 OCF 경량 스택(IoTivity-Lite)을 탑재할 경우, 메모리 부족으로 인한 스택 오버플로우 또는 주기적 재시작이 발생한다. 센서 노드가 간헐적으로 오프라인 상태가 되면 농장 모니터링에 데이터 공백이 생긴다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 저사양 노드는 OCF 전체 스택 대신 경량 프록시 패턴 적용(게이트웨이에서 OCF 변환 처리). 하드웨어 선정 단계에서 IoTivity-Lite 최소 요구사항(64KB Flash, 32KB RAM 권장)을 조달 기준으로 명시. 펌웨어 OTA(Over-The-Air) 업데이트 메커니즘을 통해 메모리 최적화 패치 배포 체계 구축.

### 6. Industrial 프로파일 적용 범위 모호성으로 인한 설계 일관성 부재

* **설명:** OCF Profiles 계층에서 Industrial 프로파일이 선택되었으나, 스마트팜은 Consumer(사용자 앱)와 Industrial(자동화 제어) 프로파일이 혼용되어야 하는 경계 도메인이다. 프로파일 정의 없이 구현을 진행할 경우, UI 서비스 팀과 펌웨어 팀 간 API 계약 불일치가 발생하고 통합 테스트 단계에서 대규모 재작업이 필요해진다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 프로젝트 착수 단계에서 도메인별 프로파일 매핑 문서(Profile Mapping Document) 작성 및 전 팀 공유. Consumer 프로파일(농장주 모바일 앱)과 Industrial 프로파일(자동화 제어 시스템)의 리소스 접근 권한을 ACL로 명확히 분리. 인터페이스 계약을 OpenAPI 스펙으로 문서화하여 팀 간 공유.
