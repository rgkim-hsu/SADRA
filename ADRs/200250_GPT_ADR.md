📋 ADR (Architecture Decision Record)

### ADR-001: 상태 기반(State Machine) 작업 제어 아키텍처 도입

| 항목                     | 내용                                                                                                                                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 이미지 상 시스템은 작업 흐름이 `NEW → WAITING → SENT → WORKING → 종료 상태`로 이어지는 명확한 상태 전이 구조를 가지고 있으며, 센서 이벤트 및 외부 명령에 따라 다양한 종료 조건(정상 종료, 센서 종료, 강제 종료 등)이 존재합니다. 이는 스마트팜 내 자동화 장치(급수, 급이, 환경 제어 등)의 제어 로직으로 해석됩니다. 핵심 과제는 다양한 이벤트 조건에서도 일관된 제어 흐름과 안정성을 유지하는 것입니다. |
| **결정(Decision)**       | 작업 제어를 위해 **Finite State Machine(FSM) 기반 상태 관리 아키텍처**를 도입하고, 모든 작업은 명확한 상태 전이 규칙과 이벤트 트리거(센서, 사용자 명령)에 따라 관리되도록 설계합니다.                                                                                                                                |
| **근거(Rationale)**      | IoT 기반 제어 시스템은 비동기 이벤트가 빈번하며, 상태 기반 설계는 복잡한 흐름을 명확하게 관리할 수 있습니다. FSM은 예측 가능성과 디버깅 용이성을 제공합니다.                                                                                                                                                         |
| **결과(Consequences)**   | 시스템 동작이 명확해지고 오류 추적이 쉬워집니다. 하지만 상태 정의 및 전이 관리가 복잡해질 수 있습니다.                                                                                                                                                                                           |
| **트레이드오프(Trade-offs)** | 안정성과 명확성을 확보하는 대신, 상태 수 증가에 따른 설계 복잡성과 유지보수 비용이 증가합니다.                                                                                                                                                                                                |

### ADR-002: 이벤트 기반 제어 및 인터럽트 처리 구조

| 항목                     | 내용                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | WORKING 상태에서 센서 이벤트(A-Sensor) 또는 사용자 명령(Stop Command)에 따라 작업이 중단되거나 종료됩니다. 또한 특정 조건에서는 명령이 무시되는 로직(IGNORED)이 존재합니다. |
| **결정(Decision)**       | 시스템을 **이벤트 드리븐(Event-Driven) 아키텍처**로 설계하고, 각 상태에서 처리 가능한 이벤트와 무시해야 할 이벤트를 명확히 정의합니다.    |
| **근거(Rationale)**      | 실시간 제어 환경에서는 센서 및 사용자 입력이 비동기적으로 발생하며, 이벤트 기반 구조는 이러한 상황에 유연하게 대응할 수 있습니다.                                          |
| **결과(Consequences)**   | 시스템 반응성이 향상되고 확장성이 증가합니다. 하지만 이벤트 처리 순서 및 충돌 관리가 중요해집니다.                                                            |
| **트레이드오프(Trade-offs)** | 유연성과 실시간성을 확보하는 대신, 이벤트 관리 복잡성과 디버깅 난이도가 증가합니다.                                                                     |

* * *

### ADR-003: 예외 및 무시(IGNORE) 처리 정책 명시화

| 항목                     | 내용                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------- |
| **상황(Context)**        | 일부 상태에서는 자동 제어나 신규 명령이 무시되는 정책이 존재합니다. 이는 시스템 안정성과 충돌 방지를 위한 설계입니다.                    |
| **결정(Decision)**       | 모든 상태에 대해 **허용/차단 이벤트 정책(Allow/Deny Matrix)**을 정의하고, 무시되는 이벤트는 명시적으로 로깅 및 추적하도록 설계합니다. |
| **근거(Rationale)**      | 제어 시스템에서 잘못된 명령 처리나 중복 실행은 치명적인 오류를 유발할 수 있으므로, 명확한 정책이 필요합니다.                         |
| **결과(Consequences)**   | 예외 상황에서도 시스템 안정성이 확보됩니다. 그러나 정책 관리가 복잡해질 수 있습니다.                                       |
| **트레이드오프(Trade-offs)** | 안정성과 예측 가능성을 확보하는 대신, 정책 정의 및 유지관리 비용이 증가합니다.                                          |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 상태 전이 오류로 인한 제어 실패

* **설명:** 잘못된 상태 전이 정의 또는 예외 처리 누락으로 인해 시스템이 비정상 상태에 머무를 가능성

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 상태 전이 다이어그램 검증, 상태 기반 테스트(State Transition Testing) 수행

* * *

### 2. 이벤트 충돌 및 우선순위 문제

* **설명:** 센서 이벤트와 사용자 명령이 동시에 발생할 경우 충돌로 인해 잘못된 동작 수행 가능

* **심각도:** 🔴 High

* **발생 가능성:** 🔴 High

* **대응 방안:** 이벤트 우선순위 정책 정의, 큐 기반 처리, 동기화 메커니즘 적용

* * *

### 3. 무시(IGNORE) 처리로 인한 사용자 혼란

* **설명:** 사용자가 입력한 명령이 무시되었으나 피드백이 없을 경우 시스템 신뢰도 저하

* **심각도:** 🟡 Medium

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 명령 무시 시 사용자 알림 및 로그 제공, UI 피드백 강화

* * *

### 4. 센서 오작동에 따른 비정상 종료

* **설명:** 센서 오류로 인해 정상 작업이 중단되거나 잘못된 종료 상태로 전이됨

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 센서 이중화, 필터링 및 검증 로직 추가

* * *

### 5. 장기 실행 작업의 상태 불일치

* **설명:** 네트워크 장애 또는 시스템 재시작 시 상태 정보가 유실되어 실제 상태와 불일치 발생

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 상태 저장소(Checkpointing), 트랜잭션 기반 상태 관리, 복구 로직 구현

* * *

### 6. 확장 시 상태 관리 복잡도 증가

* **설명:** 새로운 기능 추가 시 상태 수와 전이 규칙이 증가하여 유지보수 어려움 발생

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 상태 머신 모듈화, 상태 그룹화, 상태 관리 프레임워크 도입
