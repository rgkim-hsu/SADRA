## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈별 데이터 처리 및 통합 아키텍처 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **이미지 기반 생육 정보 추출**과 **기본 정보 데이터베이스와의 통합**을 통해 농업 데이터 분석을 수행해야 함. 각 모듈은 독립적으로 기능하면서도 상호 연계되어야 하며, 최종적으로 사용자에게 맞춤형 영농 정보를 제공해야 함. |
| **결정(Decision)** | 1. **이미지 처리 모듈(100)**은 촬영부(110)와 전송부(120)로 분할하여 이미지 수집과 전송을 분리 처리
2. **생육정보 산출부(200)**는 입력부(210), 기반 기반 기반부(220), 보정부(230), 기상/환경 데이터 통합부(240, 250), 영농정보 매칭부(270), 정보전송부(280)로 구성하여 **모듈별 책임을 명확히 분리**
3. **기본 정보 데이터베이스(300)**와 **영농 정보 데이터베이스(400)**는 별도 관리하며, **생육정보 산출부**를 통해 데이터 통합 및 변환 처리 |
| **근거(Rationale)** | - **모듈 분리**는 유지보수성과 확장성을 높임 (ISO/IEC 30141:2024의 재사용성 원칙 준수)
- **기상/환경 데이터 통합부(240, 250)**는 **oneM2M 표준**과 **ETSI EN 303 645** 보안 요구사항을 준수하여 외부 데이터 소스와의 상호운용성을 보장
- **영농정보 매칭부(270)**는 **Matter/OCF 표준**과 유사한 맞춤형 데이터 처리 로직을 적용하여 스마트팜 시스템과의 호환성을 높임 |
| **결과(Consequences)** | - ✅ **장점**: 모듈별 독립적 개발/테스트 가능, 표준 준수 통해 글로벌 상호운용성 확보
- ❌ **단점**: 모듈 간 데이터 동기화 지연 가능성, 보안 취약점 발생 가능성 |
| **트레이드오프(Trade-offs)** | - **모듈 분리**로 인한 복잡성 vs. **통합 처리**로 인한 성능 저하
- **외부 데이터 의존성**으로 인한 신뢰성 vs. **내부 데이터 통제**로 인한 유연성 |

### **ADR-002: 데이터 보안 및 접근 제어 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **사용자 데이터(500)**와 **영농 정보 데이터베이스(400)**를 보호해야 하며, **ITU-T X.1352**와 **ISO/IEC 27030:2020** 보안 표준을 준수해야 함. |
| **결정(Decision)** | 1. **생육정보 산출부(200)**의 **기반 정보 보정부(230)**에서 **암호화된 데이터 전송**을 적용 (TLS 1.3 사용)
2. **사용자 데이터(500)** 접근은 **OAuth 2.0** 기반 인증/인가 시스템 도입
3. **기본 정보 데이터베이스(300)**는 **KISA 보안 기준**에 따라 접근 로그 관리 및 정기 감사 수행 |
| **근거(Rationale)** | - **ITU-T X.1352** 표준 준수 통해 글로벌 보안 인증 제품 호환성 확보
- **OAuth 2.0**은 **ETSI EN 303 645**와 일치하는 접근 제어 메커니즘 제공
- **암호화 및 감사 로그**는 **ISO/IEC 27030:2020** 요구사항 충족 |
| **결과(Consequences)** | - ✅ **장점**: 글로벌 보안 표준 준수, 데이터 유출 위험 최소화
- ❌ **단점**: 암호화 처리로 인한 성능 오버헤드, 복잡한 인증 시스템 관리 비용 |
| **트레이드오프(Trade-offs)** | - **강화된 보안** vs. **시스템 성능 저하**
- **중앙 집중식 접근 제어** vs. **분산형 시스템 유연성** |

### **ADR-003: 데이터 통합 및 실시간 처리 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **이미지 데이터(100)**와 **기상/환경 데이터(240, 250)**를 실시간으로 통합하여 분석해야 함. |
| **결정(Decision)** | 1. **생육정보 산출부(200)**의 **기반 정보 통합부(220)**에서 **Kafka** 기반 이벤트 스트리밍 사용
2. **영농정보 매칭부(270)**는 **MQTT 프로토콜**을 통해 실시간 데이터 전송 처리
3. **기본 정보 데이터베이스(300)**는 **NoSQL(MongoDB)**를 사용하여 유연성 확보 |
| **근거(Rationale)** | - **Kafka**는 **IETF CoAP/MQTT**와 호환 가능한 실시간 데이터 처리 제공
- **NoSQL**은 **ISO/IEC 30141:2024**의 유연성 요구사항 충족
- **MQTT**는 **IoT 환경**에서 저용량 통신에 최적화된 프로토콜 |
| **결과(Consequences)** | - ✅ **장점**: 실시간 데이터 처리 가능, 확장성 높은 아키텍처
- ❌ **단점**: Kafka/MQTT 운영 복잡성, NoSQL 데이터 일관성 관리 어려움 |
| **트레이드오프(Trade-offs)** | - **실시간 처리** vs. **데이터 일관성 관리**
- **확장성** vs. **운영 복잡성** |

## ⚠️ 잠재적 위험 분석

### **1. 모듈 간 데이터 동기화 지연**
- **설명**: **생육정보 산출부(200)**와 **기본 정보 데이터베이스(300)** 간 데이터 동기화 지연으로 실시간 분석 실패 가능성 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Kafka**의 **ACK 메커니즘** 강화 (ACK=all 설정)
  - **데드레터 큐(Dead Letter Queue)** 도입하여 실패 메시지 재처리

### **2. 보안 취약점 (외부 데이터 의존성)**
- **설명**: **기상/환경 데이터 통합부(240, 250)**가 외부 API에 의존하는 경우, **MITM 공격**이나 **데이터 변조** 위험 발생.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3** 강제 적용 및 **공인 인증서** 사용
  - **데이터 무결성 검사** (HMAC-SHA256) 추가

### **3. 시스템 확장성 한계 (NoSQL 사용)**
- **설명**: **NoSQL 데이터베이스(300)**의 스케일링 한계로 인해 대용량 데이터 처리 시 성능 저하 발생 가능성.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (초기 단계)
- **대응 방안**:
  - **샤딩(Sharding)** 전략 도입
  - **Read Replica**를 통해 읽기 성능 최적화

### **4. 모듈별 오류 누적 (분산 시스템)**
- **설명**: **이미지 처리 모듈(100)**과 **생육정보 산출부(200)** 간 오류가 누적되어 시스템 전체 장애로 확산 가능성.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **서킷 브레이커 패턴** (Hystrix/Resilience4j) 적용
  - **모니터링 도구(Prometheus + Grafana)** 도입

### **5. 표준 준수 미비 (국내외 호환성)**
- **설명**: **TTA 표준**과 **국제 표준(ISO/IEC 30141, oneM2M)** 간 호환성 문제로 글로벌 시장에서 배제될 가능성.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (초기 설계 단계)
- **대응 방안**:
  - **oneM2M 표준 API**를 기반으로 **어댑터層** 구축
  - **정기적 표준 리뷰** 및 업데이트 프로세스 도입
