## 📋 ADR (Architecture Decision Record)

### **ADR-001: 중앙 집중식 데이터 모델링 및 코드 기반 엔티티 관계 구축**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 작업자, 작업계획, 장비, 이벤트, 태그 등 **비즈니스 프로세스 중심의 데이터**를 관리해야 하며, 각 엔티티 간의 **논리적 종속성**을 명확히 정의하여 데이터 일관성과 재사용성을 확보해야 함. 특히, 작업계획(`sf_workplan`)은 작업자(`sf_worker`)와 장비(`sf_machine`)의 코드 기반 참조로 운영되어야 하며, 이벤트(`sf_msevent`)와 태그(`sf_tag`)는 유연하고 확장 가능한 구조로 설계되어야 함. |
| **결정(Decision)** | 1. **코드 기반 참조 시스템** 도입: 모든 엔티티 간 관계는 코드(`WKCODE`, `WTCODE`, `TAG CODE`, `MCCODE`)로 매핑하여 관리
2. **정규화된 데이터 모델**: 엔티티별로 독립적인 테이블을 생성하고, 외래키를 통해 관계 정의
3. **태그 및 이벤트 확장성**: 태그(`sf_tag`)와 이벤트(`sf_msevent`)는 **다대다 관계**로 설계하여 유연성 확보
4. **작업유형 분류**: 작업유형(`sf_wtype`)은 별도 테이블로 관리하여 작업계획(`sf_workplan`)의 재사용성 높임 |
| **근거(Rationale)** | - **코드 기반 참조**: 데이터 중복 방지와 일관성 유지 (예: `WKCODE`로 작업자 식별)
- **정규화**: 데이터 무결성 강화 및 쿼리 성능 최적화
- **다대다 관계**: 태그와 이벤트의 유연한 할당을 위한 표준화된 구조 (예: 한 작업계획에 다중 태그 할당)
- **ISO/IEC 30141:2024** 및 **oneM2M** 표준과 일치하는 **모듈식 아키텍처** 설계 원칙 적용 |
| **결과(Consequences)** | ✅ **장점**:
- 데이터 일관성 및 무결성 강화
- 새로운 작업유형/태그 추가 시 최소한의 스키마 변경으로 대응 가능
- 시스템 확장성 및 유지보수성 향상
❌ **단점**:
- 초기에 코드 매핑 로직 구현에 추가 노력 필요
- 복잡한 조인 쿼리가 발생할 수 있음 (대응: 캐싱 및 인덱스 최적화) |
| **트레이드오프(Trade-offs)** | - **정규화 vs 성능**: 정규화로 인한 조인 오버헤드 → 인덱스 및 캐싱으로 보완
- **유연성 vs 복잡성**: 다대다 관계로 유연성 확보 → ORM 도구 및 API 레이어로 복잡성 숨김 |

### **ADR-002: 이벤트 및 태그 기반 확장성 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **실시간 모니터링**과 **사후 분석**을 위한 이벤트(`sf_msevent`)와 태그(`sf_tag`)를 지원해야 하며, 이러한 데이터는 **동적으로 확장**되어야 함. 예를 들어, 새로운 센서 데이터나 작업 이벤트가 추가될 경우 시스템이 최소한의 변경으로 대응할 수 있어야 함. |
| **결정(Decision)** | 1. **이벤트 테이블(`sf_msevent`)**: `MCCODE`(모듈 코드)와 `TAG CODE`로 조회 가능하도록 설계
2. **태그 테이블(`sf_tag`)**: 독립적 관리 및 다중 할당 지원
3. **이벤트-태그 링크 테이블**: 다대다 관계 처리 (예: `sf_msevent_tag` 테이블 추가 고려)
4. **이벤트 유형 확장성**: `MCCODE`를 통해 새로운 이벤트 유형 추가 지원 |
| **근거(Rationale)** | - **oneM2M 표준**과 유사한 **모듈식 이벤트 처리** 구조 적용
- **ETSI EN 303 645** 보안 표준과의 호환성을 위해 태그 및 이벤트 데이터 암호화 및 접근 제어 구현 예정
- **ISO/IEC 27030:2020** 가이드라인에 따라 데이터 무결성 검증 로직 추가 |
| **결과(Consequences)** | ✅ **장점**:
- 새로운 센서/이벤트 유형 추가 시 코드만 수정하면 됨
- 태그 기반 검색 및 필터링 기능 강화
❌ **단점**:
- 다대다 관계로 인한 쿼리 복잡성 → 그래프 데이터베이스 또는 materialized view로 최적화 |
| **트레이드오프(Trade-offs)** | - **SQL vs NoSQL**: 관계형 데이터베이스 사용으로 일관성 보장 → 필요한 경우 NoSQL 보조 사용 |

### **ADR-003: 보안 및 접근 제어 모델**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **작업자(`sf_worker`)별 접근 제어**와 **데이터 무결성**을 보장해야 하며, **ITU-T X.1352** 및 **KISA 기준**에 준한 보안 요구사항을 충족해야 함. 특히, 작업계획(`sf_workplan`)과 장비(`sf_machine`) 데이터는 민감한 정보로 처리되어야 함. |
| **결정(Decision)** | 1. **역할 기반 접근 제어(RBAC)**: 작업자별 역할(`WORKER_ROLE`) 정의 및 권한 할당
2. **데이터 암호화**: `sf_workplan` 및 `sf_msevent`의 민감 데이터 필드 암호화 (AES-256)
3. **로그 감사**: 모든 데이터 수정/조회 이벤트 로깅 및 KISA 기준에 따른 보관
4. **API 레벨 보안**: JWT 토큰 기반 인증 및 OAuth 2.0 지원 |
| **근거(Rationale)** | - **ITU-T X.1352** 및 **ISO/IEC 27030:2020** 준수
- **KISA 보안 인증 기준**에 따른 암호화 및 접근 제어 구현
- **Matter/OCF 표준**과 호환되는 보안 프로토콜 사용 |
| **결과(Consequences)** | ✅ **장점**:
- 민감 데이터 보호 및 규제 준수
- 세분화된 접근 제어로 데이터 유출 방지
❌ **단점**:
- 암호화/복호화로 인한 성능 오버헤드 → 하드웨어 보안 모듈(HSM) 도입 고려 |
| **트레이드오프(Trade-offs)** | - **중앙 집중식 vs 분산 보안**: 중앙 집중식 RBAC로 관리 용이성 확보 → 분산 시스템 확장 시 추가 레이어 필요 |

## ⚠️ 잠재적 위험 분석

### **1. 데이터 일관성 위반**
- **설명**: 코드 기반 참조(`WKCODE`, `TAG CODE`)의 오류 또는 중복으로 인해 데이터 불일치 발생 (예: 작업계획에 유효하지 않은 작업자 코드 참조).
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **데이터베이스 트랜잭션**을 통해 코드 참조 무결성 검증
  - **이중 체크** 로직 구현 (예: 작업자 코드 조회 후 작업계획 생성)
  - **KISA 기준**에 따른 데이터 검증 API 제공

### **2. 성능 저하 (조인 오버헤드)**
- **설명**: 정규화된 모델로 인한 다중 조인 쿼리가 시스템 성능 저하를 유발할 수 있음 (예: 작업계획 + 작업자 + 장비 + 태그 조회).
- **심각도**: 🟡 Medium | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **인덱스 최적화**: 코드 필드(`WKCODE`, `WTCODE`)에 복합 인덱스 생성
  - **캐싱 레이어** 도입 (Redis 등) - 자주 조회되는 데이터 캐싱
  - **Materialized View**를 통해 사전 조회 결과 저장

### **3. 확장성 제한 (태그/이벤트 다대다 관계)**
- **설명**: 태그 및 이벤트의 다대다 관계로 인해 시스템 확장 시 쿼리 복잡성이 증가하고, 성능 저하 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **그래프 데이터베이스** (Neo4j) 도입 고려
  - **이벤트-태그 링크 테이블**에 인덱스 및 파티셔닝 적용
  - **비동기 처리**를 통한 대량 데이터 처리 지원

### **4. 보안 취약점 (API 및 데이터베이스 레벨)**
- **설명**: JWT 토큰 탈취 또는 데이터베이스 주입 공격으로 인해 민감 데이터 유출 위험.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **OAuth 2.0 + PKCE**를 통한 토큰 보안 강화
  - **데이터베이스 레벨 암호화** (TDE: Transparent Data Encryption)
  - **정기적 보안 감사** 및 KISA 기준에 따른 취약점 스캔

### **5. 표준 준수 미비 (국제/국내 표준)**
- **설명**: 시스템이 **ISO/IEC 30141:2024**나 **oneM2M** 표준과 호환되지 않아 글로벌/국내 시장에서 배제될 가능성.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **oneM2M CSE(Common Service Entity) 레이어** 추가
  - **Matter/OCF 프로토콜** 지원을 위한 게이트웨이 개발
  - **TTA 표준**에 따른 인터페이스 정의서 작성 및 인증 획득
