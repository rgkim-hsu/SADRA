## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 모듈화된 서비스 레이어와 에지-클라우드 하이브리드 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트 livestock farming 시스템은 실시간 모니터링(동물 건강, 사료 관리 등)과 대규모 데이터 처리(생산 추적성, 로지스틱스)를 요구하며, 농장 현장(에지)과 중앙 서버(클라우드) 간 지연 시간과 네트워크 의존성을 최소화해야 함. 또한, 각 서비스(사료 관리, 질병 모니터링 등)가 독립적으로 확장 가능해야 함. |
| **결정(Decision)** | 1) **서비스 레이어 모듈화**: Feed Management, Animal Health Monitoring, Grassland Management 등 각 기능별로 독립된 마이크로서비스 아키텍처를 채택하여 재사용성과 유지보수성을 높임.<br>2) **에지-클라우드 하이브리드 아키텍처**: 현장 데이터 처리(에지 게이트웨이)를 통해 로컬 분석을 수행하고, 클라우드에서 백업/분석/지능형 서비스(예: 인공지능 기반 질병 예측)를 제공함. |
| **근거(Rationale)** | - **모듈화**: TTA 표준에서 정의한 "스마트 축사환경 데이터 모니터링 시스템" 요구사항(2022.05.30)과 ISO/IEC 30141:2024의 "재사용 가능한 설계" 원칙에 부합.<br>- **에지-클라우드**: ITU-T X.1352(보안 요구사항)와 oneM2M 아키텍처가 에지 컴퓨팅을 권장하며, 네트워크 지연 문제를 해결.<br>- **실시간성**: 현장 데이터(예: 동물 체온, 사료 섭취량)는 에지에서 처리하여 클라우드 전송 부하를 줄임. |
| **결과(Consequences)** | ✅ **장점**:<br> - 각 서비스 독립적 배포/업데이트 가능.<br> - 네트워크 의존성 감소 및 로컬 처리 속도 향상.<br> - 보안 강화(현장 데이터 암호화 및 에지 게이트웨이 필터링).<br>❌ **단점**:<br> - 초기 구축 비용 증가(에지 장비 및 모듈화 인프라).<br> - 서비스 간 동기화 복잡성(이벤트 드리븐 아키텍처 필요). |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 통합**: 모듈화로 유연성을 얻지만, 서비스 간 통신 오버헤드가 발생할 수 있음.<br>- **에지 처리 vs. 클라우드**: 에지 처리로 지연 시간을 줄이지만, 클라우드 리소스가 필요한 고급 분석 기능이 제한될 수 있음.<br>- **보안 vs. 성능**: 에지 게이트웨이에서 데이터 필터링으로 보안을 강화하면, 현장 장비의 성능 요구가 증가함. |

### **ADR-002: 표준화된 데이터 모델과 인터페이스 프로토콜 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 공급업체(Suppliers), 농부(Farmers), 가공업체(Processors) 등 다수의 스테이크홀더가 참여하며, 데이터 상호운용성이 필수적임. 또한, TTA와 국제 표준(ISO/IEC 30141, oneM2M) 요구사항을 준수해야 함. |
| **결정(Decision)** | 1) **공통 데이터 모델**: ISO/IEC 30141:2024의 "IoT 참조 아키텍처"를 기반으로, livestock 데이터(동물 건강, 사료 기록, 생산 추적성)를 표준화된 JSON Schema로 정의.<br>2) **프로토콜**: 에지-클라우드 통신에 MQTT(경량, 실시간), 서비스 간 통신에 RESTful API, 장비 간 통신에 CoAP 채택. |
| **근거(Rationale)** | - **표준 준수**: TTA의 "스마트팜 데이터 상호운용 프레임워크"(2022.07.13) 및 ISO/IEC 30141의 "공통 언어" 원칙에 부합.<br>- **프로토콜 선택**:<br>  - MQTT: ITU-T X.1352가 권장하는 "IoT 기기 통신" 프로토콜.<br>  - CoAP: ETSI EN 303 645의 "IoT 기기 사이버보안" 요구사항에 적합.<br>  - RESTful API: oneM2M 아키텍처가 권장하는 "서비스 간 통신" 방식. |
| **결과(Consequences)** | ✅ **장점**:<br> - 스테이크홀더 간 데이터 공유 용이.<br> - 국제 표준 준수로 글로벌 상호운용성 확보.<br> - 보안 강화(CoAP의 DTLS, MQTT의 TLS 지원).<br>❌ **단점**:<br> - 초기 데이터 모델 설계 비용 증가.<br> - 레거시 시스템과의 호환성 문제 가능성. |
| **트레이드오프(Trade-offs)** | - **표준화 vs. 유연성**: 표준화로 상호운용성을 얻지만, 미래 기술 변화에 대한 유연성이 제한될 수 있음.<br>- **프로토콜 선택**: MQTT는 경량적이지만, RESTful API보다 복잡한 상태 관리 필요. |

### **ADR-003: 보안 아키텍처 - 제로 트러스트 모델 및 데이터 암호화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | livestock 데이터(예: 동물 질병 기록)는 민감하며, ITU-T X.1352와 ETSI EN 303 645의 보안 요구사항을 준수해야 함. 또한, 에지 장비와 클라우드 간 데이터 유출 위험이 존재함. |
| **결정(Decision)** | 1) **제로 트러스트 모델**: 모든 접근 요청에 대해 인증/인가(예: JWT + OAuth 2.0) 및 장치 인증(예: X.509 인증서) 요구.<br>2) **데이터 암호화**:<br>  - 에지-클라우드 통신: TLS 1.3.<br>  - 현장 데이터 저장: AES-256.<br>  - 개인정보(예: 농부 데이터): GDPR 준수 및 KISA 기준에 따른 암호화. |
| **근거(Rationale)** | - **제로 트러스트**: ITU-T X.1352의 "IoT 기기 보안 요구사항"과 ISO/IEC 27030:2020의 "안전한 설계" 가이드라인에 부합.<br>- **암호화**: ETSI EN 303 645의 "사이버보안" 요구사항과 KISA의 "IoT 보안 인증" 기준에 준함. |
| **결과(Consequences)** | ✅ **장점**:<br> - 데이터 유출 위험 최소화.<br> - 국제 표준 및 법적 요구사항 준수.<br>❌ **단점**:<br> - 성능 오버헤드(암호화/복호화 지연).<br> - 복잡한 키 관리 인프라 필요. |
| **트레이드오프(Trade-offs)** | - **보안 vs. 성능**: 암호화로 보안을 강화하면, 에지 장비의 처리 능력이 요구됨.<br>- **중앙화 vs. 분산화**: 제로 트러스트 모델로 중앙 인증 서버를 사용하면, 단일 장애 지점이 발생할 수 있음. |

## ⚠️ **잠재적 위험 분석**

### **1. 네트워크 의존성 및 에지-클라우드 동기화 실패**
- **설명**: 농장 현장(에지)에서 네트워크가 단절되면, 실시간 데이터 수집이 중단되고, 클라우드와 에지 간 데이터 불일치가 발생할 수 있음. 예: 동물 건강 데이터가 로컬에 저장되지 않으면, 질병 조기 감지가 실패함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **오프라인 처리 기능**: 에지 게이트웨이에 로컬 데이터베이스(예: SQLite) 구축 및 네트워크 복구 시 자동 동기화 기능 구현.
  - **이벤트 드리븐 아키텍처**: Kafka 또는 RabbitMQ를 사용하여 비동기 데이터 처리 및 재시도 메커니즘 도입.
  - **모니터링**: 네트워크 상태를 실시간으로 모니터링하고, 농부에게 알림 시스템 구축.

### **2. 모듈화 서비스 간 결합도 증가**
- **설명**: 마이크로서비스 아키텍처로 인해 서비스 간 통신이 증가하면, 분산 트랜잭션 관리(예: 사료 주문 → 동물 건강 데이터 업데이트)가 복잡해질 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **사고적 모니터링**: OpenTelemetry를 사용하여 서비스 간 의존성 및 성능 모니터링.
  - **이벤트 소싱 패턴**: 서비스 간 상태 변화를 이벤트로 처리하여 일관성 유지.
  - **API 게이트웨이**: Kong 또는 Apigee를 사용하여 서비스 간 통신 중앙 관리 및 로깅.

### **3. 에지 장비의 보안 취약성**
- **설명**: 에지 게이트웨이 및 센서 장비가 보안 패치 적용이 지연되면, 악의적인 접근이나 데이터 조작 위험이 발생할 수 있음. 예: 사료 관리 시스템이 해킹되어 오염된 사료가 공급됨.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **자동 업데이트**: 에지 장비에 자동 패치 관리 시스템 구축(예: AWS IoT Greengrass).
  - **장치 인증**: 모든 에지 장비에 X.509 인증서 발급 및 주기적 재인증.
  - **네트워크 세그먼테이션**: 에지 장비를 VLAN 또는 SDN을 통해 격리하여 공격 면적 최소화.

### **4. 데이터 표준화 지연 및 호환성 문제**
- **설명**: 공급업체나 가공업체가 표준화된 데이터 모델을 채택하지 않으면, 시스템 간 데이터 교환이 실패할 수 있음. 예: 새로운 농장 시스템이 기존 JSON Schema와 호환되지 않음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **백워드 호환성**: 데이터 모델 버전 관리 및 마이그레이션 가이드라인 제공.
  - **스테이크홀더 협업**: TTA 표준화 위원회와 협력하여 데이터 모델을 주기적으로 업데이트.
  - **어댑터 패턴**: 레거시 시스템용 데이터 어댑터 개발 및 제공.

### **5. 클라우드 서비스 의존성 및 가용성 위험**
- **설명**: 클라우드 제공업체의 서비스 중단(예: AWS 아웃েজ)이 발생하면, 분석 및 백업 기능이 마비될 수 있음. 예: 동물 질병 예측 모델이 사용할 수 없게 됨.
- **심각도**: 🔴 High | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **멀티 클라우드 지원**: 분석 서비스를 AWS + Azure로 분산 배포.
  - **로컬 백업**: 클라우드 데이터의 로컬 복사본 유지 및 주기적 동기화.
  - **고가용성 아키텍처**: Kubernetes를 사용하여 컨테이너화된 서비스의 자동 복구 기능 구현.

### **6. 규제 준수 실패 위험**
- **설명**: GDPR(유럽) 또는 개인정보 보호법(한국) 등 규제가 변경되면, 시스템이 준수하지 못할 수 있음. 예: 동물 소유자 동의 절차가 변경되면, 데이터 수집이 불법화될 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **규제 모니터링**: 법률 팀과 협력하여 주기적 규제 감사 실시.
  - **가변성 설계**: 데이터 처리 로직을 모듈화하여 규제 변경에 신속하게 대응 가능하게 함.
  - **오디트 로그**: 모든 데이터 접근 및 처리를 로깅하여 규제 요구사항에 대응.

### **7. 초기 구축 비용 과다**
- **설명**: 에지-클라우드 하이브리드 아키텍처 및 모듈화 서비스는 초기 투자 비용이 높음. 예: 중소규모 농장이 경제적으로 부담될 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **파이ilot 프로그램**: 정부 또는 협회와 협력하여 중소규모 농장에 무상/저비용 솔루션 제공.
  - **모듈별 배포**: 우선순위 높은 서비스(예: 동물 건강 모니터링)부터 구축하여 비용 분산.
  - **공유 인프라**: 다수의 농장이 동일한 에지 게이트웨이를 공유하여 비용 절감.
