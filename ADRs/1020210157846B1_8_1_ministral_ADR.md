## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈별 기능 분할 및 데이터 흐름 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜/축사 환경 모니터링 및 제어 시스템은 실시간 환경 데이터 수집, 처리, 제어, 출력까지의 통합된 아키텍처가 요구됩니다. 현 시스템은 **환경 정보 입력부(110)**, **환경 정보 데이터베이스(120)**, **제어부(130)**, **출력부(140)**로 분할되어 있으며, 추가적으로 **일별/주간 데이터 처리 모듈(150, 160)**이 필요합니다. |
| **결정(Decision)** | 1. **기능적 모듈 분할**: 입력/처리/제어/출력 4대 블록으로 기본 구조를 정의하고, **데이터베이스 중심 아키텍처**를 채택하여 모듈 간 결합도를 낮춥니다.<br>2. **데이터 처리 모듈 분리**: 디폴트/화장 모듈(150, 160)에서 **일별/주간 계산부(152, 162)**와 **데이터베이스 인터페이스부(154, 164)**를 분리하여 재사용성을 높입니다.<br>3. **표준 프로토콜 채택**: IoT 표준인 **MQTT/CoAP**를 기반으로 모듈 간 통신을 표준화합니다. |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준에 따라 재사용 가능한 설계 원칙을 적용하여 확장성을 확보합니다.<br>- **oneM2M** 및 **ETSI EN 303 645** 표준을 준수하여 보안 및 상호운용성을 보장합니다.<br>- **TTA 단체표준**에서 정의한 스마트팜 데이터 관리 요구사항에 맞춰 모듈별 인터페이스를 설계합니다. |
| **결과(Consequences)** | ✅ **장점**: 모듈별 독립적 개발/유지보수 가능, 표준 프로토콜로 상호운용성 확보, 데이터 일관성 향상.<br>❌ **단점**: 초기 구축 비용 증가, 표준 프로토콜 적용 시 추가 보안 인증 필요. |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 성능**: 모듈 간 통신 오버헤드 발생 가능 → **에지 컴퓨팅**을 도입하여 로컬 처리 속도 향상.<br>- **표준 준수 vs. 유연성**: 표준 프로토콜로 유연성이 제한될 수 있음 → **API 게이트웨이**를 통해 확장성 확보. |

### **ADR-002: 실시간 데이터 처리 및 저장 전략**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 환경 데이터(온도, 습도 등)는 **실시간 수집**과 **일별/주간 집계**가 동시에 요구됩니다. 현 시스템에서 **환경 정보 데이터베이스(120)**는 실시간 데이터 저장과 **일별/주간 계산부(152, 162)**의 입력으로 사용됩니다. |
| **결정(Decision)** | 1. **실시간 데이터베이스**: **InfluxDB** 또는 **TimescaleDB**를 채택하여 시간 시리즈 데이터 효율적으로 저장합니다.<br>2. **배치 처리**: **Apache Spark**를 사용하여 일별/주간 집계 작업을 비동기 처리합니다.<br>3. **데이터베이스 분리**: 실시간 데이터와 집계 데이터베이스를 물리적으로 분리하여 성능 최적화합니다. |
| **근거(Rationale)** | - **IoT 데이터 특성**에 맞춰 시간 시리즈 DB를 사용합니다.<br>- **TTA 스마트팜 표준**에서 정의한 데이터 관리 요구사항에 따라 배치 처리 시스템을 도입합니다.<br>- **ISO/IEC 27030:2020** 보안 가이드라인에 따라 데이터베이스 접근 제어를 강화합니다. |
| **결과(Consequences)** | ✅ **장점**: 실시간 처리 지연 최소화, 대용량 데이터 효율적 저장, 보안 강화.<br>❌ **단점**: 초기 데이터 마이그레이션 비용 발생, 배치 처리 시스템 운영 복잡성 증가. |
| **트레이드오프(Trade-offs)** | - **실시간 vs. 배치 처리**: 실시간 처리 우선순위 설정 시 배치 작업 지연 발생 가능 → **우선순위 큐**를 도입하여 처리 순서 조절.<br>- **데이터베이스 비용 vs. 성능**: 고성능 DB 사용 시 비용 증가 → **클라우드 기반 하이브리드 아키텍처**로 비용 최적화. |

### **ADR-003: 보안 및 접근 제어 정책**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 시스템은 **사이버 공격**과 **데이터 유출** 위험에 노출되어 있으며, **ITU-T X.1352** 및 **ETSI EN 303 645** 표준을 준수해야 합니다. |
| **결정(Decision)** | 1. **데이터 암호화**: **TLS 1.3**을 사용하여 모듈 간 통신 암호화, **AES-256**으로 데이터베이스 데이터 암호화합니다.<br>2. **접근 제어**: **OAuth 2.0** 기반 토큰 인증 시스템 도입, **RBAC(역할 기반 접근 제어)** 적용합니다.<br>3. **네트워크 분리**: IoT 디바이스와 서버를 **VLAN**으로 분리하여 네트워크 공격 방지합니다. |
| **근거(Rationale)** | - **KISA IoT 보안 기준** 및 **ISO/IEC 27030:2020** 준수.<br>- **oneM2M** 표준에서 정의한 보안 요구사항 적용.<br>- **Matter 표준**과 호환 가능한 보안 프로토콜 사용. |
| **결과(Consequences)** | ✅ **장점**: 데이터 유출 위험 최소화, 표준 준수성 확보, 네트워크 안정성 향상.<br>❌ **단점**: 암호화 처리 오버헤드 발생, 접근 제어 시스템 운영 복잡성 증가. |
| **트레이드오프(Trade-offs)** | - **보안 vs. 성능**: 암호화로 성능 저하 발생 가능 → **하드웨어 가속기(HWSEC)** 도입.<br>- **중앙화 vs. 분산화**: 중앙 집중식 접근 제어로 관리 용이성 향상 → **블록체인 기반 로깅**으로 감사 가능성 강화. |

## ⚠️ 잠재적 위험 분석

### **1. 데이터 일관성 문제**
- **설명**: 모듈 간 동기화 지연으로 인해 **환경 정보 데이터베이스(120)**와 **일별 계산부(152)** 간 데이터 불일치 발생 가능.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 소싱 패턴** 도입하여 모든 데이터 변경 이벤트를 로그로 기록.
  - **데이터베이스 트랜잭션**을 사용하여 ACID 성질 보장.
  - **주기적 크롤링 스크립트**로 데이터 일관성 검증.

### **2. 모듈 간 결합도 증가**
- **설명**: **제어부(130)**와 **출력부(140)**가 tightly coupled되어 변경 시 리스크 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **미들웨어(Apache Kafka)**를 도입하여 비동기 통신 구현.
  - **API 게이트웨이**를 통해 모듈 간 인터페이스 표준화.
  - **마이크로서비스 아키텍처**로 모듈 독립성 강화.

### **3. 실시간 처리 지연**
- **설명**: 대량의 환경 데이터 수집 시 **실시간 처리 지연**으로 제어부(130) 응답 속도 저하.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **에지 컴퓨팅**을 도입하여 로컬 처리 속도 향상.
  - **스트리밍 처리 프레임워크(Flink)**를 사용하여 실시간 분석 최적화.
  - **데이터 샘플링**을 통해 처리량 조절.

### **4. 보안 취약점 노출**
- **설명**: **IoT 디바이스**의 보안 취약점으로 인해 **데이터베이스(120, 154, 164)**가 공격받을 위험.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **디바이스 인증(Device Authentication)**을 필수화.
  - **정기적 보안 패치** 및 **취약점 스캔** 자동화.
  - **네트워크 세그멘테이션**을 통해 공격 면적 최소화.

### **5. 표준 변경에 따른 재작업 위험**
- **설명**: **ISO/IEC 30141:2024** 또는 **oneM2M** 표준이 변경될 경우 시스템 재작업 필요.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **표준 모니터링 팀**을 구성하여 변경 사항 추적.
  - **추상화 계층** 도입으로 표준 변경에 대한 영향 최소화.
  - **백워드 호환성**을 고려한 설계 원칙 적용.
