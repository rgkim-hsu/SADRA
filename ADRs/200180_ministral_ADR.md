## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈화된 IoT 환경 제어 시스템 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜/축사 환경에서 실시간 모니터링과 원격 제어가 필요한 시스템을 구축해야 함. 센서 데이터 수집, 웹/스마트폰 기반 제어, 그리고 환경 제어 시스템 간의 상호운용성이 필수적임. 또한, **국내외 IoT 표준(ISO/IEC 30141:2024, oneM2M, ITU-T X.1352)** 준수와 보안 요구사항을 충족해야 함. |
| **결정(Decision)** | 1. **모듈화 아키텍처** 채택: 입력 모듈(센서), 출력 모듈(액추에이터), 웹/스마트폰 제어 시스템, 그리고 **내부 사육환경 제어 시스템**으로 분리하여 개발 및 유지보수 용이성 확보
2. **oneM2M 기반 API 게이트웨이** 도입: 웹/스마트폰 제어 시스템과 내부 시스템 간의 통신을 표준화된 프로토콜(MQTT/CoAP)으로 처리
3. **센서 데이터 표준화**: TTA 단체표준(KTA.KO-10.1170)에 따라 온도/습도/CO₂ 센서 데이터 포맷을 통일
4. **보안 계층 추가**: ITU-T X.1352 준수하여 센서-제어 시스템 간 통신 암호화 및 인증 메커니즘 구현 |
| **근거(Rationale)** | - 모듈화 아키텍처는 **ISO/IEC 30141:2024**의 재사용 가능한 설계 원칙과 일치
- oneM2M 표준은 **ETSI/ITU-T**에서 승인된 글로벌 상호운용성 프레임워크임
- 센서 데이터 표준화는 **TTA 단체표준**과 **스마트팜 가이드북** 요구사항을 충족
- 보안 계층은 **ETSI EN 303 645**와 **ISO/IEC 27030:2020** 가이드라인에 따라 구현됨 |
| **결과(Consequences)** | ✅ **장점**: 모듈별 독립적 개발/배포 가능, 표준 준수로 글로벌 시장에서의 상호운용성 확보, 보안 취약점 최소화
❌ **단점**: 초기 구축 비용 증가, 모듈 간 통신 오버헤드 발생 가능 |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 통합 아키텍처**: 모듈화로 유연성 확보하지만, 통신 오버헤드 발생
- **표준 준수 vs. 성능**: oneM2M/MQTT 프로토콜로 상호운용성 확보하지만, 실시간 처리 지연 가능성 존재
- **보안 강화 vs. 복잡성**: 암호화/인증 메커니즘 추가로 보안 강화지만, 시스템 복잡성 증가 |

### **ADR-002: 실시간 데이터 처리 및 피드백 루프 구현**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 센서 데이터는 **실시간으로 수집**되어야 하며, 제어 시스템은 즉각적인 피드백을 통해 환경 조절을 수행해야 함. 또한, **사용자 제어 요청과 시스템 자동 제어 간의 우선순위 관리**가 필요함. |
| **결정(Decision)** | 1. **에지 컴퓨팅 기반 데이터 처리**: 센서 데이터는 **로컬 게이트웨이(NuE 사육용 환경제어 시스템)**에서 전처리 후 클라우드에 전송
2. **우선순위 기반 스케줄러**: 사용자 제어 요청 > 시스템 자동 제어 > 예방적 유지보수 순으로 처리
3. **MQTT QoS Level 1** 채택: 실시간성 보장과 네트워크 오버헤드 균형 유지 |
| **근거(Rationale)** | - 에지 컴퓨팅은 **네트워크 지연 최소화** 및 **오프라인 운용 가능성**을 제공
- 우선순위 스케줄러는 **안전성 및 사용자 경험**을 최우선으로 함
- MQTT QoS Level 1은 **실시간성**과 **리소스 효율성**을 균형 있게 처리 |
| **결과(Consequences)** | ✅ **장점**: 저지연 데이터 처리, 네트워크 효율성 향상, 사용자 제어 우선 처리
❌ **단점**: 에지 장비에 대한 추가 유지보수 비용 발생 |
| **트레이드오프(Trade-offs)** | - **에지 vs. 클라우드 처리**: 에지로 실시간성 확보하지만, 클라우드 처리보다 높은 초기 비용
- **QoS Level 1 vs. Level 2**: Level 2로 신뢰성 향상 가능하지만, 네트워크 오버헤드 증가 |

### **ADR-003: 보안 및 접근 통제 정책**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 시스템은 **사이버 공격**과 **데이터 유출** 위험에 노출되어 있으며, **다중 사용자 접근 통제**가 필요함. |
| **결정(Decision)** | 1. **TLS 1.3**을 기반으로 센서-게이트웨이 및 게이트웨이-클라우드 통신 암호화
2. **OAuth 2.0**을 사용하여 웹/스마트폰 앱 인증 및 접근 통제
3. **KISA 보안 기준**에 따라 센서 데이터 무결성 검사(HMAC-SHA256) 적용
4. **로그 관리 시스템** 구축: 모든 제어 요청 및 시스템 이벤트를 30일 이상 보관 |
| **근거(Rationale)** | - TLS 1.3과 OAuth 2.0은 **ETSI EN 303 645** 및 **ISO/IEC 27030:2020**에서 권장하는 보안 프로토콜임
- KISA 기준은 **국내 IoT 보안 인증**을 위한 필수 요구사항임 |
| **결과(Consequences)** | ✅ **장점**: 데이터 암호화 및 접근 통제로 보안 강화, 규제 준수성 확보
❌ **단점**: 인증/암호화 프로세스로 처리 지연 발생 가능 |
| **트레이드오프(Trade-offs)** | - **보안 강화 vs. 성능**: 암호화로 보안성 향상하지만, 처리 속도 저하 가능
- **로그 관리 vs. 스토리지 비용**: 로그 보관으로 감사 가능성 확보하지만, 스토리지 비용 증가 |

## ⚠️ 잠재적 위험 분석

### **1. 네트워크 지연 및 통신 실패**
- **설명**: 센서-게이트웨이 또는 게이트웨이-클라우드 간 네트워크 장애로 실시간 데이터 수집 실패 또는 제어 지연 발생. 특히 **농촌 지역과 같은 저망원역**에서 문제 심각성 높음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **MQTT QoS Level 1 + 오프라인 큐 메커니즘** 도입: 네트워크 복구 시 누락된 데이터 재전송
  - **로컬 에지 백업 시스템** 구축: 클라우드 연결 실패 시 로컬에서 데이터 처리 및 제어 유지
  - **모바일 네트워크(4G/5G) + LoRaWAN** 하이브리드 네트워크 지원

### **2. 센서 데이터 오류 및 노이즈**
- **설명**: 센서 하드웨어故障 또는 환경적 노이즈로 **오류 데이터 수집** 발생. 예: 온도 센서의 이상치로 인해 과도한 제어 동작 유발.
- **심각도**: 🟡 Medium | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **다중 센서 크로스 체크**: 동일한 환경 변수를 측정하는 복수 센서의 데이터 비교를 통해 이상치 검출
  - **기계 학습 기반 이상치 탐지**: 로컬 에지에서 LSTM 모델을 사용하여 이상치 필터링
  - **주기적 센서 캘리브레이션**: TTA 단체표준(KTA.KO-10.1170)에 따라 3개월마다 센서 정밀도 검증

### **3. 보안 취약점 및 불법 접근**
- **설명**: ** weak credentials** 또는 **미사용 보안 패치**로 인해 시스템에 불법 접근 또는 데이터 탈취 위험. 특히 **IoT 기기 보안**은 전통적 IT 시스템보다 취약함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **자동 패치 관리 시스템**: 센서/게이트웨이에 대한 보안 패치 자동 배포 (월 1회 최소)
  - **MFA(Multi-Factor Authentication)** 강제 적용: 웹/스마트폰 앱 로그인 시 SMS/TOTP 기반 2단계 인증
  - **정기 보안 감사**: KISA 기준에 따라 6개월마다 침투 테스트 및 취약점 스캔 수행

### **4. 시스템 확장성 제한**
- **설명**: 모듈화 아키텍처로 개발 용이성을 확보했지만, **대규모 센서 네트워크** 또는 **다중 사용자 동시 접속** 시 시스템 과부하 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **마이크로 서비스 아키텍처**: 각 모듈(센서 처리, 제어 로직, UI)을 독립적 컨테이너로 배포하여 수평 확장 지원
  - **클라우드 기반 로드 밸런싱**: AWS ALB 또는 Kubernetes HPA를 사용하여 트래픽 분산
  - **에지 캐싱**: 자주 접근하는 제어 로직 및 센서 데이터를 로컬 캐시에 저장

### **5. 표준 준수 및 상호운용성 문제**
- **설명**: **다양한 제조사의 센서/액추에이터**를 통합해야 하는 경우, 표준 미준수로 인해 **통신 실패** 또는 **데이터 포맷 불일치** 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **oneM2M 표준 기반 어댑터**: 비표준 장비를 표준화된 포맷으로 변환하는 어댑터 개발
  - **TTA 단체표준 준수 테스트Bed**: 모든 새로운 장비에 대해 표준 준수성을 사전 검증
  - **API 버전 관리**: 백워드/포워드 호환성을 위한 API 버전 정책 수립 (예: v1.0, v2.0)

### **6. 사용자 오류 및 운영 미숙**
- **설명**: **비전문 사용자**가 시스템을 오용하여 예기치 않은 제어 동작을 유발. 예: 온도 설정값을 임의로 변경하여 작물/가축에 피해 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **권한별 UI 커스터마이징**: 관리자/일반 사용자별로 접근 가능한 기능 제한
  - **제어 동작 로그**: 모든 수동 제어 동작을 로그로 기록하고, 전문가 검토를 위한 알림 발송
  - **사용자 교육 프로그램**: TTA가 개발한 **스마트팜 운영 가이드**를 기반으로 정기 교육 실시

### **7. 규제 및 준수 변경 위험**
- **설명**: **국내외 IoT 규제**가 변경되면 시스템이 준수하지 못할 위험. 예: **EU의 사이버 보안법(ENISA)** 또는 **미국의 IoT 보안 법안** 도입 시 대응 지연 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기)
- **대응 방안**:
  - **정기 규제 모니터링**: KISA 및 ISO/IEC 업데이트를 주기적으로 확인 (월 1회)
  - **모듈화된 준수 레이어**: 보안/규제 관련 로직을 독립적 모듈로 분리하여 빠른 업데이트 가능
  - **국제 표준 참여**: TTA를 통해 **ISO/IEC JTC1 SC41** 및 **ITU-T SG17** 활동에 참여하여 규제 동향 사전 파악

---
**참고 사항**:
- 모든 위험 대응 방안은 **TTA 단체표준** 및 **KISA 보안 가이드라인**과 연계하여 구현됨.
- **에지 컴퓨팅**과 **모듈화 아키텍처**는 **ISO/IEC 30141:2024**의 "재사용 가능한 설계" 원칙을 충족함.
- **oneM2M** 및 **MQTT** 표준은 **ETSI/ITU-T**에서 승인된 글로벌 표준으로, 글로벌 시장에서의 상호운용성을 보장함.
