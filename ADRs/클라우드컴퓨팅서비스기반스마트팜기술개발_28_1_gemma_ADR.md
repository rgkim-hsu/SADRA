# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 표준화 기반의 서비스 지향 데이터 계층 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 여러 개별 농장 및 생산자로부터 습득되는 비정형적(Non-standard)이고 이질적인(Heterogeneous) 데이터를 통합하여, 소비자에게 일관성 있고 신뢰할 수 있는 사용자 경험(UX)을 제공해야 합니다. 데이터의 출처가 다양하고(센서, 기록, 스토리), 산업 분야(농업)의 전문 용어와 요구사항이 복잡하여, 단순히 기능을 나열하는 방식의 단일 백엔드 아키텍처로는 상호운용성(Interoperability)을 보장할 수 없습니다. |
| **결정(Decision)** | 데이터 중심의 아키텍처(Data-Centric Architecture)를 채택하며, 모든 입력 데이터는 전용 **데이터 게이트웨이/메시징 계층**을 거쳐 **표준화된 토픽(Topic)**을 발행해야 합니다. 이를 위해 메시지 브로커(Message Broker, 예: Kafka)를 핵심 컴포넌트로 두고, 각 데이터를 마이크로서비스(Microservices) 단위로 처리 및 저장하여 **서비스 지향 아키텍처(SOA)**를 구현합니다. |
| **근거(Rationale)** | 1. **상호운용성 확보:** 컨텍스트 자료에서 강조된 ISO/IEC 30141과 같은 참조 아키텍처의 목표는 공통 용어 및 재사용 가능한 설계를 제공하는 것입니다. 메시지 브로커와 마이크로서비스는 비즈니스 도메인(생산 데이터, 물류 데이터, 스토리 데이터 등)별로 독립적인 개발 및 업데이트를 가능하게 하여, 산업 표준 변화에 민첩하게 대응할 수 있게 합니다. 2. **데이터 품질 및 확장성:** 게이트웨이 계층에서 데이터 검증(Validation) 및 표준화(Normalization) 프로세스를 강제함으로써, 공급되는 데이터의 품질을 일괄적으로 관리하고 대규모 트래픽 증가에 유연하게 확장할 수 있습니다. |
| **결과(Consequences)** | **긍정적:** 농업 데이터를 포맷/규격 레벨에서 강제 표준화할 수 있어, 시스템의 장기적인 확장성과 신뢰성이 극대화됩니다. 각 서비스의 독립성이 보장되어 기능 개선 속도가 빠릅니다. **부정적:** 초기 시스템 구축 단계에서 메시지 브로커, 데이터 파이프라인, 그리고 다수의 마이크로서비스를 설계하고 통합하는 데 상당한 시간과 전문 인력이 필요합니다. |
| **트레이드오프(Trade-offs)** | **[Trade-off]** 복잡성 증가 vs. 유연성 및 확장성 확보. 복잡한 분산 시스템 구조를 감수함으로써, 단일 실패 지점을 제거하고 미래의 다양한 스마트팜(축사, 온실, 양식장 등) 종류와 데이터를 무제한으로 흡수할 수 있는 아키텍처적 근간을 마련합니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 표준화 불일치로 인한 서비스 마비 (Data Schema Inconsistency)
- **설명:** 다양한 생산자가 각자의 방식과 규격(Schema)으로 데이터를 입력하거나 API를 호출할 경우, 시스템의 표준 데이터 게이트웨이에서 데이터를 정상적으로 파싱하거나 의미를 부여하지 못하여, 소비자에게 부정확하거나 누락된 정보를 제공하게 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:**
    *   **기술적:** 필수 필드에 대한 스키마 유효성 검사(Schema Validation)를 게이트웨이 계층에서 1차적으로 강제하고, 검증 실패 데이터는 즉시 대시보드를 통해 생산자에게 피드백하여 수정하도록 의무화합니다.
    *   **운영적:** 온보딩(Onboarding) 단계에 표준 데이터 입력 교육 및 가이드라인을 필수로 제공합니다.

### 2. 초당 데이터 처리 용량 한계 초과 (Ingestion Rate Bottleneck)
- **설명:** 대규모의 스마트팜 기기(센서, IoT 디바이스)가 짧은 시간에 대량의 환경 및 생체 데이터를 중앙 서버로 동시 전송할 경우, 메시지 브로커 또는 데이터베이스의 쓰기(Write) 용량을 초과하여 데이터 병목 현상이 발생하고 서비스가 지연/중단될 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **아키텍처:** 데이터 수집 계층에 엣지 컴퓨팅(Edge Computing) 노드를 도입하여, 센서 데이터를 로컬에서 1차 필터링(Aggregation)하고 필요한 메타데이터만 중앙 서버로 전송하도록 설계를 변경합니다.
    *   **확장성:** 클라우드 기반의 수평적 확장(Horizontal Scaling)이 가능한 클러스터 환경을 구축합니다.

### 3. 생산자 측 데이터 입력/유지 비용 증가 (Producer Onboarding Resistance)
- **설명:** 시스템이 요구하는 데이터 표준화 및 기록 의무가 너무 복잡하거나, 생산자 입장에서 추가적인 시간 및 비용 투입(센서 추가, 기록 작업 등)이 발생한다고 느낄 경우, 시스템 활용도가 낮아지고 데이터 공급 자체가 원활하지 않게 됩니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:**
    *   **비즈니스 모델:** 초기에는 데이터 제공에 대한 경제적 인센티브(예: 프리미엄 판매 채널 연결, 마케팅 지원)를 제공하여 참여 동기를 부여해야 합니다.
    *   **UX/UI:** 데이터 입력 프로세스를 최소화하고, 사물인터넷(IoT) 장비와 연동하여 사람이 개입할 필요 없이 데이터를 자동 수집하는 기능을 최우선으로 구현합니다.

### 4. 사이버 보안 위협 (API 및 디바이스 해킹 공격)
- **설명:** 시스템의 민감 정보(생산자의 경영 정보, 작물 데이터)가 API 게이트웨이나 백엔드 마이크로서비스를 통해 노출되거나, 연결된 엣지 디바이스 자체가 해킹되어 위변조된 데이터를 주입할 위험이 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **보안:** 전송되는 모든 API 호출에 대해 OAuth 2.0 또는 JWT 기반의 강력한 접근 제어(Access Control)를 적용합니다.
    *   **디바이스:** 엣지 디바이스에 물리적 및 소프트웨어적 무결성 검증(Integrity Check) 메커니즘을 의무화하고, 데이터 암호화(Encryption)는 전송(TLS) 및 저장(AES-256) 단계 모두에서 적용합니다.

### 5. 법규 및 표준 변화 미반영 위험 (Regulatory Compliance Drift)
- **설명:** 농업/식품 관련 법규(예: 식품 안전 기준, 환경 규제)나 IT 표준(예: 데이터 주권 관련 규정, 국내 IoT 표준 등)이 변화할 때, 시스템의 핵심 로직이 이를 즉각적으로 반영하지 못하여 법적 리스크나 시장 경쟁력 저하를 초래할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **거버넌스:** 아키텍처 설계 단계부터 '규제 변경에 대한 영향 분석'을 주기적인 프로세스로 포함합니다.
    *   **모듈화:** 규제나 표준 변화가 예상되는 비즈니스 로직(예: 생산 인증, 환경 기준치)을 독립적인 마이크로서비스로 분리하여, 규정 변경 시 해당 서비스만 업데이트하면 되도록 설계합니다.
