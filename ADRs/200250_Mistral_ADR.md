📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **상태 기반 작업 관리 시스템 도입**

| 항목                     | 내용                                                                                                                                                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템에서 장비/센서의 작업 상태를 실시간으로 추적하고, 외부 명령(자동 제어, 새로운 명령, 정지 명령) 또는 센서 이벤트(A-센서)에 따라 작업의 시작, 중지, 종료를 관리해야 하는 필요성. 현재 시스템은 **NEW → WAITING → SENT → WORKING**의 상태 전환을 통해 작업을 진행하며, **A-센서**, **정지 명령**, **자동 제어/새로운 명령에 의한 무시** 등 다양한 종료 조건을 처리해야 함. |
| **결정(Decision)**       | **유한 상태 머신(Finite State Machine, FSM) 기반 아키텍처**를 도입하여 작업 상태를 명시적으로 정의하고, 상태 전환 로직을 중앙 집중화. 각 상태(NEW, WAITING, SENT, WORKING)는明確한 역할과 전환 조건을 가짐.                                                                                                     |
| **근거(Rationale)**      | FSM은 상태 전환의 복잡성을 줄이고, 시스템의 예측 가능성을 높임. 스마트팜에서 실시간으로 발생하는 이벤트(A-센서 트리거, 정지 명령 등)를 일관성 있게 처리할 수 있으며, 상태별로 다른 동작을 정의하여 오류를 최소화. 또한, 상태 로그를 통해 추적성이 향상됨.                                                                                                |
| **결과(Consequences)**   | ✅ **장점**: 상태 관리 로직의 단순화, 이벤트 처리의 일관성, 시스템 디버깅 용이성. ❌ **부정적 결과**: 새로운 상태 또는 전환 조건이 추가될 경우, FSM의 확장성이 제한적일 수 있음.                                                                                                                                      |
| **트레이드오프(Trade-offs)** | **장점**: 명확한 상태 정의로 인한 유지보수성 향상, 실시간 이벤트 처리 최적화. **단점**: 복잡한 비즈니스 로직이 추가될 경우, FSM의 상태 explosive growth(상태 폭발) 가능성.                                                                                                                                   |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. **A-센서 오작동으로 인한 잘못된 상태 전환**

* **설명:** A-센서가 오류로 인해 작업이 완료되지 않았음에도 "FINISHED BY A-SENSOR" 상태로 전환되는 경우, 실제 작업은 진행 중이지만 시스템은 종료된 상태로 인식하여 후속 명령이 무시됨.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** A-센서의 데이터 검증 로직 추가(예: 다중 센서 교차 검증, 시간 기반 타임아웃). 상태 전환 시 로그 기록 및 알림 시스템 구축.

* * *

### 2. **정지 명령과 A-센서 이벤트의 충돌**

* **설명:** WORKING 상태에서 동시에 **STOP COMMAND**와 **A-SENSOR** 이벤트가 발생할 경우, 시스템이 어떤 이벤트를 우선 처리할지 정의되지 않아 작업 상태가 불일치할 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 이벤트 우선순위 규칙 정의(예: 정지 명령 > A-센서). 이벤트 처리 큐를 도입하여 순차 처리 보장.

* * *

### 3. **NEW/WAITING 상태에서 명령 손실**

* **설명:** NEW 또는 WAITING 상태에서 **IGNORED BY AUTO CONTROL** 또는 **IGNORED BY NEW COMMAND**로 인해 명령이 무시될 경우, 사용자는 명령이 처리되었다고 오인할 수 있으며, 실제 작업이 시작되지 않음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 무시된 명령에 대한 로그 기록 및 사용자 알림(예: "새로운 명령이 기존 명령을 대체했습니다"). 명령 큐를 통해 명령 이력을 추적.

* * *

### 4. **네트워크 지연으로 인한 상태 동기화 실패**

* **설명:** 분산된 스마트팜 시스템에서 상태가 중앙 서버와 로컬 장비 간에 동기화되지 않아, **WORKING** 상태로 표시되지만 실제 장비는 정지된 상태.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:** 상태 동기화를 위한 **Heartbeat 메커니즘** 도입(주기적인 상태 확인). Offline 상태에서 로컬 캐시 사용 및 동기화 시점 재처리.

* * *

### 5. **보안 취약점으로 인한 명령 주입 공격**

* **설명:** 외부에서 **STOP COMMAND** 또는 **NEW COMMAND**를 악의적으로 주입하여 시스템을 비정상적으로 종료시키거나, 작업 흐름을 교란시킴.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:** 명령 전송 시 **인증 및 권한 검증** 적용. TLS/SSL을 통한 암호화 통신. 명령 로그에 IP/사용자 정보 기록.

* * *

### 6. **SENT 상태에서 작업 지연**

* **설명:** **SENT** 상태로 전환된 후, 장비 또는 네트워크 지연으로 인해 **WORKING** 상태로 전환되지 않아, 작업이 시작되지 않은 상태로 오래 머무는 경우.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** SENT 상태에 **타임아웃 메커니즘** 도입(예: 30초 이내에 WORKING으로 전환되지 않으면 NEW 상태로 롤백). 지연 발생 시 알림 전송.
