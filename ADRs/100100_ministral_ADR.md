## 📋 ADR (Architecture Decision Record)

### **ADR-001: 근적외선(FT-NIR) 분석 시스템의 파장 범위 및 분석 방법론 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 농업/축산 분야의 생체 데이터 분석을 위해 근적외선(0.8 µm ~ 2.5 µm) 스펙트럼을 활용해야 함. 분석 대상은 농산물, 축산물, 토양 등 다양한 생체 물질로, FT-NIR(간섭계 기반 근적외선 분광법)을 기본 분석 방법으로 채택함. |
| **결정(Decision)** | 1. **파장 범위**: 0.8 µm (12,500 cm⁻¹) ~ 2.5 µm (4,000 cm⁻¹) 범위를 표준 분석 범위로 채택 <br> 2. **분석 방법**: FT-NIR를 기본 분석 기술로 채택하고, **정량 분석(Quantitative)**, **중첩(Overtone)**, **조합(Combination) 밴드** 분석을 지원 <br> 3. **표준 준수**: ISO/IEC 30141:2024의 IoT 데이터 상호운용성 원칙과 KISA 보안 기준을 준수하여 시스템 구축 |
| **근거(Rationale)** | - **과학적 타당성**: 생체 물질의 분자 진동 모드(12,500–4,000 cm⁻¹)는 이 범위에서 최적의 신호 강도를 제공 <br> - **기술적 성숙도**: FT-NIR는 농업/축산 분야에서 표준으로 사용되며, 하드웨어 및 소프트웨어 모두 상용화되어 있음 <br> - **표준화 동향**: TTA의 스마트팜 데이터 상호운용 프레임워크(2022.07.13)와 연계하여 데이터 표준화 가능 |
| **결과(Consequences)** | ✅ **장점**: <br> - 생체 데이터 분석의 정확도 향상 <br> - 기존 농업 IoT 플랫폼과의 상호운용성 보장 <br> - 국제 표준(ISO/IEC 30141) 준수로 글로벌 시장에서의 신뢰성 강화 <br> ❌ **단점**: <br> - FT-NIR 센서의 초기 구축 비용이 높음 <br> - 중적외선(IR) 및 원적외선 범위와 비교하여 분석 범위가 제한적임 |
| **트레이드오프(Trade-offs)** | - **비용 vs. 정확도**: FT-NIR의 높은 정확도를 위해 초기 투자 비용을 감수 <br> - **범위 확장성**: 현재 2.5 µm까지의 범위만 지원하므로, 향후 중적외선 분석을 위한 확장 계획 필요 |

### **ADR-002: 시스템 아키텍처의 계층화 및 프로토콜 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 기반 스마트팜 시스템은 **센서 계층 → 에지 게이트웨이 → 클라우드 플랫폼**의 3계층 구조를 필요로 함. 각 계층 간 통신은 보안 및 실시간 처리를 지원해야 함. |
| **결정(Decision)** | 1. **계층 구조**: <br> - **센서 계층**: FT-NIR 센서 + IoT 센서(온도, 습도, 영상) <br> - **에지 계층**: MQTT 프로토콜을 기반으로 데이터 전송 및 전처리 <br> - **클라우드 계층**: CoAP 프로토콜 + Kubernetes 기반 플랫폼 <br> 2. **보안 표준**: ITU-T X.1352와 ETSI EN 303 645 준수 <br> 3. **데이터 포맷**: JSON/Protobuf를 표준화하여 oneM2M 프레임워크와 연계 |
| **근거(Rationale)** | - **MQTT/CoAP**: 경량 프로토콜로 에지-클라우드 간 실시간 통신을 지원 <br> - **Kubernetes**: 클라우드 플랫폼의 확장성과 가용성을 보장 <br> - **보안 준수**: KISA 인증 기준과 국제 표준을 동시 준수하여 글로벌 시장에서의 인증을 용이하게 함 |
| **결과(Consequences)** | ✅ **장점**: <br> - 저지연 통신 및 실시간 데이터 처리 가능 <br> - 보안 인증 프로세스 간소화 <br> ❌ **단점**: <br> - MQTT의 암호화 오버헤드 증가 <br> - Kubernetes 운영 복잡성 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 보안**: MQTT의 암호화로 인한 지연을 감수하여 보안을 강화 <br> - **운영 복잡성**: Kubernetes의 이점을 위해 DevOps 전문 인력 확보 필요 |

### **ADR-003: 데이터 상호운용성 프레임워크 구축**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 **다양한 제조사의 센서 및 플랫폼**과 상호운용성을 요구함. TTA의 "스마트팜 데이터 상호운용 프레임워크"(2022.07.13)를 기반으로 표준화된 API 및 데이터 모델을 구축해야 함. |
| **결정(Decision)** | 1. **데이터 모델**: ISO/IEC 30141:2024의 공통 용어를 기반으로 JSON Schema 정의 <br> 2. **API 표준**: RESTful API + WebSocket을 지원하여 실시간 스트리밍 가능 <br> 3. **인터페이스**: OCF(Open Connectivity Foundation) 프레임워크와 연계하여 스마트홈/스마트팜 통합 지원 |
| **근거(Rationale)** | - **TTA 표준**: 국내 스마트팜 시장에서의 호환성을 보장 <br> - **OCF 연계**: 스마트홈(Matter) 및 스마트팜의 통합을 용이하게 함 <br> - **JSON Schema**: 유연성 및 가독성을 높임 |
| **결과(Consequences)** | ✅ **장점**: <br> - 제조사 간 데이터 호환성 향상 <br> - 스마트홈/스마트팜의 통합 서비스 제공 가능 <br> ❌ **단점**: <br> - 초기 데이터 모델 설계 비용 증가 <br> - 기존 시스템과의 역호환성 이슈 가능성 |
| **트레이드오프(Trade-offs)** | - **유연성 vs. 복잡성**: JSON Schema의 유연성을 위해 초기 설계 복잡성을 감수 |

## ⚠️ 잠재적 위험 분석

### **1. 센서 데이터의 정확도 저하**
- **설명**: FT-NIR 센서의 노화 또는 환경 변수(온도, 습도)에 의한 신호 왜곡으로 분석 데이터의 정확도가 저하될 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **정기 캘리브레이션**: 3개월마다 표준 물질을 사용하여 센서 재조정
  - **환경 보정 알고리즘**: 온도/습도 데이터를 기반으로 신호 보정 수행
  - **중복 센서 배치**: 주요 분석 지점에 2개 이상의 센서를 설치하여 교차 검증

### **2. 네트워크 지연 및 패킷 손실**
- **설명**: 에지-클라우드 간 MQTT 통신에서 네트워크 혼잡 또는 장비故障로 인해 실시간 데이터 전송이 지연되거나 손실될 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **QoS 레벨 설정**: MQTT QoS Level 2를 사용하여 패킷 손실 방지
  - **로컬 캐싱**: 에지 게이트웨이에 5분 분량의 데이터 버퍼를 구축
  - **대안 프로토콜**: CoAP를 보조 프로토콜로 사용하여 네트워크 오버헤드 분산

### **3. 보안 취약점 및 데이터 유출**
- **설명**: IoT 장비의 약한 인증 또는 MQTT/CoAP 프로토콜의 암호화 미준수로 인해 데이터 유출 또는 악의적인 접근이 발생할 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3 강제 적용**: 모든 통신에 TLS 1.3을 의무화
  - **장치 인증**: ITU-T X.1352 기준의 디바이스 인증서를 의무화
  - **네트워크 분할**: 센서 네트워크와 클라우드 플랫폼을 VLAN으로 분리

### **4. 시스템 확장성 한계**
- **설명**: Kubernetes 기반 클라우드 플랫폼의 자원 할당 미관리로 인해 시스템 확장성이 저하되어 분석 요청이 지연될 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **오토스케일링 설정**: CPU 사용률 70% 이상 시 자동으로 노드 추가
  - **마이크로서비스 아키텍처**: 분석 모듈을 독립적으로 배포하여 자원 격리
  - **모니터링 도구**: Prometheus + Grafana를 사용하여 자원 사용량 실시간 모니터링

### **5. 표준화 미준수로 인한 상호운용성 실패**
- **설명**: TTA 또는 ISO/IEC 30141 표준을 미준수하여 다른 제조사의 센서/플랫폼과 데이터 호환이 실패할 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **표준 준수 테스트**: 모든 소프트웨어 릴리스에 대해 TTA 표준 테스트 케이스 실행
  - **백워드 호환성 설계**: 기존 시스템과의 호환성을 위한 어댑터層 구축
  - **공동 개발**: 주요 제조사와의 협업으로 표준화된 API 사양 공동 개발

- **에지 컴퓨팅 최적화**: 분석 작업을 에지에서 수행하여 클라우드 부하를 분산

| **결과(Consequences)** | ✅ **장점**: <br> - 제조사 간 데이터 호환성 향상 <br> - 스마트홈/스마트팜의 통합 서비스 제공 가능 <br> ❌ **단점**: <br> - 초기 데이터 모델 설계 비용 증가 <br> - 기존 시스템과의 역호환성 이슈 가능성 |
| **트레이드오프(Trade-offs)** | - **유연성 vs. 복잡성**: JSON Schema의 유연성을 위해 초기 설계 복잡성을 감수 |

## ⚠️ 잠재적 위험 분석

### **1. 센서 데이터의 정확도 저하**
- **설명**: FT-NIR 센서의 노화 또는 환경 변수(온도, 습도)에 의한 신호 왜곡으로 분석 데이터의 정확도가 저하될 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **정기 캘리브레이션**: 3개월마다 표준 물질을 사용하여 센서 재조정
  - **환경 보정 알고리즘**: 온도/습도 데이터를 기반으로 신호 보정 수행
  - **중복 센서 배치**: 주요 분석 지점에 2개 이상의 센서를 설치하여 교차 검증

### **2. 네트워크 지연 및 패킷 손실**
- **설명**: 에지-클라우드 간 MQTT 통신에서 네트워크 혼잡 또는 장비故障로 인해 실시간 데이터 전송이 지연되거나 손실될 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **QoS 레벨 설정**: MQTT QoS Level 2를 사용하여 패킷 손실 방지
  - **로컬 캐싱**: 에지 게이트웨이에 5분 분량의 데이터 버퍼를 구축
  - **대안 프로토콜**: CoAP를 보조 프로토콜로 사용하여 네트워크 오버헤드 분산

### **3. 보안 취약점 및 데이터 유출**
- **설명**: IoT 장비의 약한 인증 또는 MQTT/CoAP 프로토콜의 암호화 미준수로 인해 데이터 유출 또는 악의적인 접근이 발생할 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3 강제 적용**: 모든 통신에 TLS 1.3을 의무화
  - **장치 인증**: ITU-T X.1352 기준의 디바이스 인증서를 의무화
  - **네트워크 분할**: 센서 네트워크와 클라우드 플랫폼을 VLAN으로 분리

### **4. 시스템 확장성 한계**
- **설명**: Kubernetes 기반 클라우드 플랫폼의 자원 할당 미관리로 인해 시스템 확장성이 저하되어 분석 요청이 지연될 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **오토스케일링 설정**: CPU 사용률 70% 이상 시 자동으로 노드 추가
  - **마이크로서비스 아키텍처**: 분석 모듈을 독립적으로 배포하여 자원 격리
  - **모니터링 도구**: Prometheus + Grafana를 사용하여 자원 사용량 실시간 모니터링

### **5. 표준화 미준수로 인한 상호운용성 실패**
- **설명**: TTA 또는 ISO/IEC 30141 표준을 미준수하여 다른 제조사의 센서/플랫폼과 데이터 호환이 실패할 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **표준 준수 테스트**: 모든 소프트웨어 릴리스에 대해 TTA 표준 테스트 케이스 실행
  - **백워드 호환성 설계**: 기존 시스템과의 호환성을 위한 어댑터層 구축
  - **공동 개발**: 주요 제조사와의 협업으로 표준화된 API 사양 공동 개발
