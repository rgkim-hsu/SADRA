# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: IoT/M2M 환경을 위한 표준 기반 계층형 아키텍처 채택 (Adoption of Standard-based Layered Architecture for IoT/M2M Environments)

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 x1 (데이터 수집/엣지), x2 (플랫폼/처리), x3 (서비스/애플리케이션)의 3단계 흐름을 가짐. 핵심 과제는 이처럼 이질적이고 분산된(Heterogeneous) 다수의 디바이스 및 프로토콜에서 발생하는 데이터를 통합하고, 미래의 확장성과 상호운용성(Interoperability)을 보장하는 것이며, 이는 최신 글로벌 표준화 요구(ISO/IEC 30141, oneM2M)를 충족해야 함. |
| **결정(Decision)** | 아키텍처는 데이터를 최소 3개의 논리적 계층(Layered Architecture)으로 분리하고, 모든 컴포넌트 간의 통신 규약 및 데이터 모델링을 국제 표준화된 API Gateway 및 메시지 브로커 패턴(예: MQTT/Kafka 기반의 메시지 큐)을 중심으로 구현한다. 데이터 표준화 및 보안 게이트웨이를 전용 계층으로 분리한다. |
| **근거(Rationale)** | 1. **상호운용성 확보:** 표준 프로토콜 기반의 분리는 특정 제조사나 기술에 종속되는 것을 방지한다. 2. **확장성 및 유지보수성:** 계층 분리를 통해 특정 계층(예: 엣지 디바이스)의 변화가 전체 시스템에 미치는 영향을 최소화한다 (Decoupling). 3. **표준 준수:** 이 접근 방식은 ISO/IEC 30141과 같은 참조 아키텍처 가이드를 따름으로써, 산업의 모범 사례와 글로벌 요구사항을 충족시킨다. |
| **결과(Consequences)** | **긍정적:** 높은 수준의 표준 준수성, 높은 확장성, 모듈 교체 용이성. **부정적:** 초기 설계 복잡도 및 아키텍처 구현 난이도가 상승함. |
| **트레이드오프(Trade-offs)** | **획득 장점:** 전 세계 표준에 맞는 유연하고 신뢰성 높은 시스템 구축 가능. **감수 단점:** 표준화된 게이트웨이 및 메시지 브로커를 추가 구축해야 하므로 초기 인프라 비용 및 개발 시간이 증가함. |

## ⚠️ 잠재적 위험 분석

### 1. 엣지 디바이스 보안 취약점 (Edge Device Security Vulnerability)
- **설명:** x1 계층에 연결되는 수많은 이종(Heterogeneous) 디바이스들은 개별적인 보안 패치, 운영체제(OS) 업데이트 관리가 어렵고, 물리적 공격에 노출되기 쉽다. 이로 인해 한 디바이스가 해킹당할 경우, 전체 시스템으로의 진입점(Attack Vector)이 될 위험이 매우 높다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 모든 엣지 디바이스에 대한 최소한의 물리적 보안(Tamper-proof)을 적용하고, 디바이스가 전송하는 데이터를 최소 권한 원칙(Principle of Least Privilege)에 따라 검증(Validation)하는 보안 펌웨어 레벨의 게이트웨이를 의무화한다.

### 2. 데이터 모델링 및 의미론적 상호운용성 문제 (Semantic Interoperability Issues)
- **설명:** 각기 다른 산업군(스마트팜, 스마트시티 등)의 장비들이 데이터를 전송할 때, '온도'나 '습도' 같은 핵심 개념을 다르게 정의하거나(예: 단위, 측정 시점 등), 데이터 필드가 누락되는 경우가 발생하여 상위 계층(x2, x3)에서 의미를 오해하거나 데이터를 조합할 수 없다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 입력을 위한 중앙 집중식 데이터 카탈로그(Data Catalog)를 구축하고, 모든 데이터 흐름에 대해 국제 표준(예: JSON Schema, FHIR 같은 의료 데이터 모델 참조)에 기반한 **강제 스키마 검증(Schema Validation)** 계층을 필수로 삽입한다.

### 3. 트래픽 폭증 및 확장성 한계 (Data Burst and Scalability Bottleneck)
- **설명:** 스마트팜이나 도시 환경처럼 다수의 센서가 동시에 데이터를 전송하거나, 시스템이 갑작스럽게 트래픽이 몰리는 이벤트(예: 재난 상황의 집중 모니터링) 발생 시, x2 플랫폼 레이어의 데이터 처리 용량(CPU, 메모리, I/O)이 한계를 초과하여 시스템 전체가 지연되거나 다운될 수 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 플랫폼 레이어(x2)는 **분산 메시지 큐(Distributed Message Queue)** 시스템(예: Kafka)을 핵심적으로 사용하여 데이터 수집과 처리를 비동기적으로 분리한다. 또한, 데이터 저장소는 샤딩(Sharding)을 염두에 둔 클라우드 네이티브 아키텍처를 채택해야 한다.

### 4. 데이터 프라이버시 및 거버넌스 부재 (Data Privacy and Governance Failure)
- **설명:** 수집되는 데이터 중에는 사물인터넷(IoT) 기기 위치 데이터, 사람의 생체 데이터(Biometric Data) 등 민감한 개인 식별 정보(PII)가 포함될 수 있다. 이러한 데이터를 적절히 익명화, 가명화하거나 접근 권한을 관리하지 못할 경우, 법적 규제 위반 및 심각한 신뢰성 손실을 초래한다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터가 x2 플랫폼으로 유입되는 단계(Ingestion Layer)에서 **개인정보 비식별화(De-identification)** 모듈을 의무적으로 삽입하고, 데이터 사용 목적과 접근 주체에 따른 **접근 제어 목록(ACL) 및 감사 추적(Audit Trail)** 시스템을 구현한다.

### 5. 시스템 종속성 및 장애 전파 (System Dependency and Failure Propagation)
- **설명:** 시스템이 특정 핵심 서비스(예: 인증서 관리 서비스, 통신 게이트웨이)에 지나치게 의존하게 되면, 해당 단일 컴포넌트가 장애를 일으켰을 때 전체 시스템이 마비되는 단일 실패 지점(Single Point of Failure, SPoF)이 발생한다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 핵심 서비스 컴포넌트(인증서 관리, 플랫폼 API 등)는 반드시 **고가용성(High Availability, HA)** 클러스터 환경을 구축하고, 모든 중요한 기능에 대해 지연 허용 시간(Latency Tolerance)을 정의한 후, 장애 발생 시 자동 우회(Failover) 로직을 구현해야 한다.
