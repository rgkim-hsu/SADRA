===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 사료 잔량 모니터링을 위한 IoT 기반 이벤트 드리븐 분산 아키텍처

| 항목                     | 내용                                                                                                                                                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 시스템은 사료 잔량 감시 장치(10), 사료 공급기(30), 사료 잔량 모니터링 서버(20), 관리자 단말(40)로 구성된다. 원격 센서부(120)와 제어부(140)는 사료 잔량 및 빈 급이기 상태를 측정하고, 측정 결과는 서버로 전송되어 저장·분석 후 관리자에게 전달된다. 전체 프로세스는 장치 등록(S200~S204), 관리지점 등록(S210~S214), 데이터 측정(S220~S260), 결과 처리 및 전송(S270~S290) 단계로 구성된다. 핵심 과제는 실시간 데이터 수집, 정확한 잔량 측정, 그리고 이벤트 기반 알림 및 관리 자동화이다. |
| **결정(Decision)**       | IoT 센서 기반 이벤트 드리븐(Event-driven) 아키텍처를 채택하고, 측정 이벤트 발생 시마다 데이터가 서버로 비동기 전송되는 구조를 적용한다. 센서 → 엣지 제어부 → 중앙 서버 → 관리자 단말로 이어지는 계층 구조를 유지하며, 상태 변화(빈 급이기, 잔량 부족 등)에 따라 알림 트리거를 발생시키는 방식으로 설계한다.                                                                                                                            |
| **근거(Rationale)**      | 사료 잔량은 실시간 또는 준실시간으로 변하는 데이터이므로 폴링 방식보다 이벤트 기반 방식이 효율적이다. 또한 IoT 환경에서는 네트워크 효율성과 전력 소비를 고려해야 하므로 필요 시에만 데이터를 전송하는 구조가 적합하다.                                                                                                                                                                                         |
| **결과(Consequences)**   | 네트워크 사용량 감소 및 실시간 대응성 향상 효과를 얻을 수 있다. 그러나 이벤트 폭주 또는 네트워크 불안정 시 데이터 누락 가능성이 존재한다.                                                                                                                                                                                                                                    |
| **트레이드오프(Trade-offs)** | 효율적인 데이터 전송(장점) vs 이벤트 관리 복잡성 증가(단점), 실시간성 확보(장점) vs 데이터 유실 가능성(단점)                                                                                                                                                                                                                                                 |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 센서 측정 오류

* **설명:** 원격 센서부(120)가 사료 잔량 또는 빈 급이기 상태를 잘못 측정하는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 센서 보정, 이중 센서 적용, 데이터 필터링

### 2. 이벤트 누락 또는 중복 처리

* **설명:** 이벤트 기반 전송 과정에서 데이터가 누락되거나 중복 수신되는 문제

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 메시지 큐(QoS 보장), 이벤트 ID 기반 중복 제거

### 3. 네트워크 장애

* **설명:** 장치와 서버 간 통신 장애로 데이터 전송 실패

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 로컬 버퍼링 및 재전송, 오프라인 모드 지원

### 4. 서버 과부하

* **설명:** 다수 장치에서 동시에 이벤트 발생 시 모니터링 서버(20) 과부하

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 메시지 브로커(Kafka, MQTT) 도입, 오토스케일링

### 5. 알림 지연 또는 미전송

* **설명:** 관리자 단말(40)로의 알림 전달 실패로 대응 지연

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 다중 알림 채널(SMS, 앱 푸시), 재전송 메커니즘

### 6. 보안 취약점 (IoT 디바이스)

* **설명:** IoT 장치가 해킹되어 잘못된 데이터 전송 또는 시스템 침입 발생

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 디바이스 인증, 펌웨어 보안 업데이트, 암호화 통신 적용
