## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 중앙 집중형 ERP + 에지 컴퓨팅 기반 스마트팜 제어 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 실시간 센서 데이터 수집, 머신러닝 기반 재배 컨설팅, 원격 모니터링 및 제어 기능을 요구한다. 중앙 서버만 의존한 아키텍처는 네트워크 지연과 확장성 한계로 인해 현장 장비 제어가 불능화될 위험이 있으며, 분산형 아키텍처는 데이터 일관성 및 보안 관리가 복잡하다. |
| **결정(Decision)** | **1) 중앙 ERP 서버 + 에지 컨트롤러 하이브리드 아키텍처** 채택: <br> - **식물생산 ERP (100)**: 중앙 서버로 비즈니스 로직(생산 계획, 재고 관리, 영업 관리) 처리 <br> - **에지 컨트롤러 (200/300)**: 현장 센서 데이터 전처리, 실시간 제어, 로컬 머신러닝 모델 실행 <br> - **데이터 동기화**: 에지에서 중앙 ERP로 주기적 배치 업데이트 및 이벤트 기반 실시간 알림 |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 참조 아키텍처에서 권장하는 "Edge-to-Cloud" 모델을 따름 <br> - **ETSI EN 303 645** 보안 요구사항에 따라 에지 장비에 로컬 인증/암호화 적용 가능 <br> - **TTA 스마트팜 표준**에서 에지 기반 데이터 관리 요구사항을 충족 (예: "에지 기반 스마트 온실 서비스의 데이터 관리용 웹 인터페이스") <br> - **실시간 제어 필요성**: 센서 데이터의 평균 지연 시간 요구사항 (예: 온도/습도 제어: <100ms, 영상 분석: <2s) |
| **결과(Consequences)** | ✅ **장점**: <br> - 네트워크 단절 시 에지 컨트롤러가 로컬 제어 유지 가능 <br> - 중앙 ERP는 대용량 데이터 처리 및 분석에 특화 <br> - 보안 강화: 민감 데이터는 에지에서 암호화 후 전송 <br> ❌ **단점**: <br> - 에지-클라우드 동기화 복잡성 증가 <br> - 초기 구축 비용 상승 (에지 장비 추가) <br> - 데이터 일관성 관리 필요성 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 복잡성**: 에지 처리로 성능 향상但 동기화 로직 추가 <br> - **비용 vs. 확장성**: 에지 장비 비용 증가但 클라우드 스케일링 유연성 유지 <br> - **보안 vs. 사용성**: 로컬 암호화로 보안 강화但 키 관리 복잡성 |

### **ADR-002: 모듈식 머신러닝 모델 통합 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 재배 컨설팅 모듈은 다양한 머신러닝 모델(예: 작물 병해 진단, 영상 기반 성장 예측)을 통합해야 하며, 모델 업데이트 주기가 짧고 모델별 요구사항(입력 데이터, 출력 포맷)이 다름. |
| **결정(Decision)** | **1) 마이크로서비스 기반 모델 통합**: <br> - **모델별 컨테이너화**: Docker/Kubernetes로 각 모델을 독립적 마이크로서비스로 배포 <br> - **통일된 API 게이트웨이**: 모델 입력/출력 포맷 변환 및 에지-클라우드 간 호출 중계 <br> - **모델 버전 관리**: GitOps 방식으로 에지/클라우드 모델 동기화 |
| **근거(Rationale)** | - **oneM2M 표준**에서 권장하는 "모듈식 서비스 아키텍처" 적용 <br> - **TTA "재배 컨설팅 모듈" 표준**에서 "모델 독립성" 요구사항 반영 <br> - **IEEE 2413** IoT 아키텍처 프레임워크의 "플러그인 모델" 개념 활용 |
| **결과(Consequences)** | ✅ **장점**: <br> - 모델 독립적 업데이트 가능 <br> - 에지/클라우드 간 모델 A/B 테스트 지원 <br> ❌ **단점**: <br> - API 게이트웨이 복잡성 증가 <br> - 컨테이너 오케스트레이션 필요성 |
| **트레이드오프(Trade-offs)** | - **유연성 vs. 운영 복잡성**: 마이크로서비스로 유연성 향상但 Kubernetes 운영 필요 <br> - **성능 vs. 표준화**: 통일된 API로 표준화但 변환 오버헤드 발생 |

### **ADR-003: 데이터 표준화 및 상호운용성 프레임워크 적용**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 센서/카메라/컨트롤러 등 다종다양한 장비에서 수집된 데이터는 포맷과 단위가 일치하지 않으며, **TTA 스마트팜 데이터 상호운용 프레임워크** 표준을 준수해야 함. |
| **결정(Decision)** | **1) oneM2M 기반 데이터 모델 표준화**: <br> - **공통 데이터 스키마**: ISO/IEC 30141:2024의 "IoT Common Data Model" 적용 <br> - **변환 레이어**: 에지에서 장비별 포맷 → 표준 포맷 변환 (예: 온도: °C → 표준 JSON) <br> - **메타데이터 관리**: 센서별 단위, 범위, 시간 동기화 정보 저장 |
| **근거(Rationale)** | - **oneM2M 표준**에서 정의한 "Information Model" 적용 <br> - **TTA "스마트팜 데이터 상호운용 프레임워크"** 표준과 일치 <br> - **ETSI EN 303 645** 보안 요구사항과 호환 (예: 데이터 무결성 검사) |
| **결과(Consequences)** | ✅ **장점**: <br> - 장비 간 데이터 공유 가능 <br> - 미래 확장성 확보 <br> ❌ **단점**: <br> - 초기 데이터 마이그레이션 비용 발생 <br> - 변환 로직 유지보수 필요 |
| **트레이드오프(Trade-offs)** | - **표준화 vs. 구현 복잡성**: 표준 준수로 상호운용성 향상但 변환 로직 추가 |

## ⚠️ **잠재적 위험 분석**

### **1. 네트워크 단절 시 에지-클라우드 동기화 실패**
- **설명**: 네트워크 장애 시 에지 컨트롤러의 로컬 데이터와 중앙 ERP의 데이터 불일치 발생. 예: 에지에서 수정된 재배 계획이 클라우드로 반영되지 않음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **오프라인 모드 지원**: 에지에서 로컬 DB에 변경 사항 누적 후 네트워크 복구 시 일괄 동기화 (예: Conflict-Free Replicated Data Types, CRDT 사용).
  - **주기적 스냅샷**: 5분마다 에지-클라우드 간 데이터 스냅샷 동기화.
  - **네트워크 모니터링**: Prometheus + AlertManager로 네트워크 상태 실시간 모니터링.

### **2. 에지 장비 보안 취약성**
- **설명**: 에지 컨트롤러가 IoT 기기 보안 표준(예: ITU-T X.1352)을 준수하지 않으면, 악의적인 접근 또는 데이터 변조 위험 발생.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **하드웨어 보안 모듈(HSM)**: 에지 장비에 TPM 2.0 통합하여 키 관리.
  - **네트워크 세그멘테이션**: 에지 장비와 센서 간 dedicated VLAN 구성.
  - **주기적 펌웨어 업데이트**: OTA 업데이트 지원 및 자동 패치 관리.

### **3. 머신러닝 모델 성능 저하**
- **설명**: 에지에서 실행되는 머신러닝 모델(예: 영상 분석)이 하드웨어 제약으로 인해 성능 저하 발생. 예: 카메라 해상도 감소 또는 처리 지연.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **모델 최적화**: TensorFlow Lite 또는 ONNX 런타임으로 에지 모델 최적화.
  - **하드웨어 가속**: NVIDIA Jetson 또는 Google Coral TPU 사용.
  - **모델 A/B 테스트**: 클라우드에서 테스트 후 에지로 배포.

### **4. 데이터 일관성 문제**
- **설명**: 에지-클라우드 간 동기화 지연으로 인해 중앙 ERP와 현장 데이터 불일치 발생. 예: 센서 데이터가 클라우드에 반영되지 않아 재배 컨설팅 오류 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 소싱 패턴**: 모든 데이터 변경 사항을 이벤트로 로깅하고 재생성 가능성 확보.
  - **체크섬 검증**: 데이터 전송 시 SHA-256 체크섬으로 무결성 검사.
  - **데드레터큐**: 실패한 동기화 요청을 별도 큐에 저장 후 재시도.

### **5. 스케일링 제한**
- **설명**: 에지 장비 수 증가에 따라 중앙 ERP의 데이터 처리 부하가 증가하여 성능 저하 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기적)
- **대응 방안**:
  - **미리 읽기 캐시**: Redis를 사용하여 빈번히 접근하는 센서 데이터 캐시.
  - **수평 확장**: Kubernetes로 ERP 마이크로서비스 수평 스케일링.
  - **에지 캐시**: 자주 사용되는 모델/데이터를 에지에서 캐시 (예: 재배 컨설팅 결과).

### **6. 표준 준수 미비로 인한 상호운용성 실패**
- **설명**: 신규 장비 추가 시 기존 데이터 표준과 호환되지 않아 시스템 통합 실패.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기적)
- **대응 방안**:
  - **표준 준수 테스트**: 신규 장비 추가 시 TTA/oneM2M 표준 준수 테스트 강제.
  - **어댑터 패턴**: 장비별 어댑터 모듈 제공 (예: legacy 센서용 변환기).
  - **백워드 호환성**: 기존 데이터 포맷을 유지하면서 신규 표준 지원.

### **7. 운영 복잡성 증가**
- **설명**: 에지-클라우드 하이브리드 아키텍처로 인해 운영 및 유지보수 복잡성 증가.
- **심각도**: 🟢 Low | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **자동화 도구**: Terraform/Ansible로 인프라 프로비저닝 자동화.
  - **중앙화된 로깅**: ELK 스택(Elasticsearch, Logstash, Kibana)으로 로그 중앙 관리.
  - **운영 팀 교육**: 에지-클라우드 통합 운영 프로세스 교육.
