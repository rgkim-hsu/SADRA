## 📋 ADR (Architecture Decision Record)

### ADR-001: 중앙 집중식 제어 로직 및 모듈화 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 외부 환경 데이터 수집 (제1 통신부, 401) 과 내부 제어 명령 전송 (제2 통신부, 402) 을 수행하면서도, 시스템 내부 상태 (메모리, 전원, 에너지 하드웨어) 를 통합적으로 관리할 시스템이 필요함. 기존 시스템은 각 기능이 분리되어 있어 제어 로직 복잡성 증가 및 상태 일관성 유지 어려움 |
| **결정 (Decision)** | **제어부 (403)**를 시스템의 핵심 로직 중심 (Hub) 으로 설정하고, **메모리 (404)**, **제1 통신부 (401)**, **제2 통신부 (402)**, **전원부 (405)**, **에너지 하드웨어 (406)**를 모두 제어부에 하청 형태로 연결하는 **중앙 집중식 스타 구조** 아키텍처를採用함. |
| **근거 (Rationale)** | 1. **일관된 상태 관리**: 제어부가 모든 하위 모듈의 상태를 독점적으로 관리하므로, 전원 오작동이나 메모리 오버플로우 시 전체 시스템을 안전하게 Shutdown/Reset 할 수 있음.<br>2. **유연한 확충**: 통신 부가 (401, 402) 는 상이한 프로토콜 (예: Wi-Fi, Zigbee 등) 을 지원할 수 있도록 물리적으로 분리되어 있어 제어 로직 변경 없이 하드웨어만 교체 가능함.<br>3. **스마트팜 표준 준수**: TTA 표준 (스마트 축사 제어 인터페이스 등) 에서 요구하는 통합 제어 인터페이스 구현을 용이하게 함. |
| **결과 (Consequences)** | **긍정적**: 시스템 로직의 일관성 향상, 유지보수성 증가, 외부 통신 프로토콜 변경 시 제어 로직 수정 최소화.<br>**부정적**: 제어부 (403) 단일 장애점 (Single Point of Failure) 위험 발생. 제어부 고장 시 전체 시스템 마비 가능성. |
| **트레이드오프 (Trade-offs)** | **장점**: 아키텍처 단순화, 상태 제어의 명확성 확보.<br>**단점**: 제어부 부하 증가, 고장 시 복구 비용 증가. |

### ADR-002: 독립형 전원 및 에너지 관리 모듈 분리

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | IoT 디바이스는 배터리 또는 외부 전원 변동에 민감하며, 에너지 효율이 중요한 시스템임. 에너지 하드웨어 (406) 와 전원부 (405) 가 결합되어 있으면 전원 공급 오작동 시 에너지 모니터링 기능도 동시에 중단될 위험이 있음. |
| **결정 (Decision)** | **전원부 (405)**와 **에너지 하드웨어 (406)**를 별도의 모듈로 구분하고, 모두 제어부 (403) 에 연결하도록 아키텍처 설계함. 전원 공급 경로와 에너지 모니터링 경로를 논리적으로 분리. |
| **근거 (Rationale)** | 1. **내구성**: 에너지 효율 최적화를 위한 알고리즘 (406) 과 단순 전원 공급 (405) 을 분리하면, 전력 관리 소프트웨어 업데이트 시 전원 회로 영향 방지.<br>2. **안전성**: 전원 과부하 발생 시 에너지 하드웨어 (406) 가 제어부를 보호하며 독립적으로 동작하도록 설계 가능.<br>3. **에너지 효율**: IoT 디바이스의 핵심 과제인 배터리 수명 연장을 위해 에너지 관리를 별도의 로직으로 독립화함. |
| **결과 (Consequences)** | **긍정적**: 전력 관리 로직의 독립적 업데이트 가능, 전원 고장 시 에너지 모니터링 기능 지속 가능.<br>**부정적**: 하드웨어 설계 및 레이아웃이 다소 복잡해질 수 있음. |
| **트레이드오프 (Trade-offs)** | **장점**: 전력 관리 안정성 및 에너지 효율성 향상.<br>**단점**: PCB 레이아웃 복잡도 증가, BOM(Bill of Materials) 비용 소폭 상승. |

### ADR-003: 이방성 통신 인터페이스 (제1/제2 통신부) 채택

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 스마트팜/스마트축사 환경에서는 외부 네트워크 (네트워크 클라우드) 로 데이터 전송 (제1 통신부) 과 내부 센서/구동기 제어 (제2 통신부) 를 동시에 수행해야 하는 경우가 많음. |
| **결정 (Decision)** | **제1 통신부 (401)**와 **제2 통신부 (402)**를 독립적인 인터페이스 모듈로 설계하여, 상향 (Data In/Cloud Sync) 과 하향 (Command Out/Device Control) 데이터 흐름을 분리 처리함. |
| **근거 (Rationale)** | 1. **상호운용성**: oneM2M 또는 ISO/IEC 30141 표준에 따라 외부와의 인터페이스 (제1) 와 내부 기기 인터페이스 (제2) 를 분리하면 프로토콜 (MQTT vs CAN/RS485 등) 충돌 방지.<br>2. **대역폭 최적화**: 외부 전송 대역폭 (제1) 과 내부 제어 대역폭 (제2) 을 별도의 채널로 확보하여 병목 현상 방지.<br>3. **보안**: 외부 네트워크 (제1) 와 내부 네트워크 (제2) 의 보안 정책 (예: 암호화 강도) 을 별도로 적용 가능. |
| **결과 (Consequences)** | **긍정적**: 외부 공격으로부터 내부 네트워크 보호, 데이터 전송 속도 향상.<br>**부정적**: 인터페이스 하드웨어 비용 증가 (통신 모듈 2 개 필요). |
| **트레이드오프 (Trade-offs)** | **장점**: 프로토콜 간 충돌 방지, 보안 격리 효과.<br>**단점**: 하드웨어 부가 비용 증가, 시스템 복잡도 증가. |

## ⚠️ 잠재적 위험 분석

### 1. [중앙 집중식 제어부 장애 위험]
- **설명:** 시스템의 모든 로직이 **제어부 (403)**에 집중되어 있어, 이 모듈에 하드웨어 오류나 소프트웨어 버그가 발생하면 **메모리 (404)**, **통신부 (401/402)**, **전원부 (405)**를 포함한 전체 시스템이 즉시 마비될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (하드웨어 수명, 소프트웨어 복잡도에 의존)
- **대응 방안:**
    1. 제어부 (403) 로직을 이중화하거나, 단순한 상태 관리 기능 (예: 전원 차단 명령) 은 펌웨어 레벨에서 하드웨어적으로 제어하도록 설계.
    2. 제어부 오작동 감지 시 **에너지 하드웨어 (406)**를 통해 외부 전원을 자동으로 차단하거나 시스템 리셋 신호를 발동하는 Fail-safe 메커니즘 구현.

### 2. [통신 부가 간섭 및 대역폭 부족 위험]
- **설명:** **제1 통신부 (401)**와 **제2 통신부 (402)**가 동일한 주파수 대역이나 동일한 프로토콜을 사용하는 경우, 서로 간섭을 일으키거나 대역폭이 부족해 데이터 전송 지연이 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High (다중 통신 모듈 사용 시 빈번한 현상)
- **대응 방안:**
    1. 제1 통신부는 외부 네트워크 (5G, LoRa 등) 용으로, 제2 통신부는 내부 센서/구동기 (Zigbee, Z-Wave 등) 용으로 물리적으로 분리된 모듈을 채택.
    2. 제어부 (403) 내에서 통신 스케줄링 알고리즘 적용하여 제1/2 통신부가 동시에 점유하는 대역폭 제한.

### 3. [전원 불안정에 따른 데이터 손실 위험]
- **설명:** **전원부 (405)**와 **에너지 하드웨어 (406)** 간의 연결이 불안정하거나, 에너지 모니터링 오류로 인해 전원이 갑자기 차단될 경우, **메모리 (404)**에 저장되지 않은 임시 데이터가 손실되고 **제어부 (403)**가 오작동할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (전원 품질, 배터리 수명에 영향)
- **대응 방안:**
    1. **에너지 하드웨어 (406)**에 커패시터 등 에너지 저장 장치 (ESCAP, 배터리 백업) 를 탑재하여 전원 차단 시에도 최소 1~2 초 유지 전력 공급 확보.
    2. **메모리 (404)**를 비휘발성 메모리 (Flash 등) 로 설계하여 전원 손실 시 데이터 무손실 보장.

### 4. [외부 통신 부가를 통한 보안 침투 위험]
- **설명:** **제1 통신부 (401)**가 외부 네트워크와 연결되므로, 제1 통신부에 취약점 (예: OTA 업데이트 취약점) 이 있다면 공격자가 이를 통해 **제어부 (403)**로 침투하여 **제2 통신부 (402)**를 조작하거나 시스템 제어권을 탈취할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low (단순 설계 단계) / 🔴 High (실무 적용 시, 공격 벡터 증가)
- **대응 방안:**
    1. **제1 통신부 (401)**에 보안 게이트웨이 기능 추가하여, 외부에서 들어오는 모든 트래픽은 **제어부 (403)**가 검증한 후만 처리하도록 필터링.
    2. TTA 보안 표준 및 ETSI EN 303 645 요구사항 준수하여, 외부 통신 프로토콜 암호화 (TLS/SSL 등) 강제 적용.

### 5. [메모리 포화로 인한 시스템 성능 저하 위험]
- **설명:** **메모리 (404)** 크기가 제한되어 있으며, 스마트팜 환경에서는 센서 데이터 (온도, 습도, 영상 등) 가 실시간으로 축적될 경우 메모리가 빠르게 소진되어 **제어부 (403)** 처리 속도 저하 및 시스템 응답 지연이 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (데이터 수집 주기와 양에 따라 변동)
- **대응 방안:**
    1. **제어부 (403)**에 데이터 압축 알고리즘 적용 또는 **제1 통신부 (401)**에서 전송 시 실시간 데이터만 필터링하여 유효 데이터만 **메모리 (404)**에 저장.
    2. **메모리 (404)** 용량을 동적으로 확장 가능한 구조 (eMMC 등) 로 설계, 혹은 데이터 저장 주기는 상황 (날씨, 생체 데이터 등) 에 따라 조절하도록 **제어부 (403)** 로직 구현.
