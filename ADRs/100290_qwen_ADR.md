## 📋 ADR (Architecture Decision Record)

### ADR-001: 모듈화된 기능 분리 및 독립적 모듈 구성

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 환경 정보 수집, 분석, 제어, 결과 관리 등 다양한 복잡한 기능을 수행해야 하며, 향후 확장성을 고려할 때 기능별 모듈화를 통해 유지보수성과 독립성을 확보해야 하는 상황임. 특히 스마트팜이나 사물인터넷(IoT) 환경과 같은 실시간 데이터 처리가 필요한 환경에서 특정 기능의 고장이나 업데이트가 전체 시스템 마비를 야기하지 않아야 함. |
| **결정(Decision)** | 시스템을 크게 `모니터링모듈`, `제어모듈`, `결과관리모듈`로 분할하고, 각 모듈은 독립적인 인터페이스 (예: DB 연동, 내부 API) 를 통해 연결되도록 아키텍처를 설계함. 각 모듈 내부 하위 기능부 (예: 환경정보수집부, 병충해판단부 등) 를 기능 단위 블록으로 캡슐화하여 관리함. |
| **근거(Rationale)** | - **유지보수성**: 한 기능 (예: 병충해 판단 알고리즘 업데이트) 이 변경될 때 다른 기능 (예: 스케줄링) 에 영향이 없도록 분리.<br>- **확장성**: `모니터링모듈`의 분석 기능이 복잡해지면 독립된 모듈로 분리하여 병렬 처리 가능.<br>- **명확성**: 아키텍처 도표가 시스템을 구성하는 주요 블록 (2, 4, 5) 과 그 내부 기능부 (21~25, 41~44 등) 를 명확히 정의함. |
| **결과(Consequences)** | **긍정**: 시스템의 복잡도가 관리하기 쉬워지고, 각 블록의 역할이 명확해짐.<br>**부정**: 모듈 간 통신 오버헤드가 발생할 수 있으며, 초기 구현 비용이 증가할 수 있음. |
| **트레이드오프(Trade-offs)** | 기능의 통합성을 희생하여 모듈화, 독립성을 얻음. 대신 모듈 간 통신 프로토콜 (API, Message Queue 등) 을 표준화해야 하므로 추가적인 설계 노력이 필요함. |

## ⚠️ 잠재적 위험 분석

### 1. 실시간 데이터 처리 지연 및 시스템 반응성 저하
- **설명:** `모니터링모듈`에서 수집한 데이터가 `데이터베이스`를 경유하여 `제어모듈`의 알고리즘 (병충해 판단 등) 을 거쳐 제어 명령으로 이어지는 과정에서 네트워크 지연이나 컴퓨팅 부하로 인해 실시간 제어가 실패할 경우.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 에지 컴퓨팅 (Edge Computing) 기술을 도입하여 데이터 수집과 기본 분석을 로컬에서 처리하고, 중앙 서버에는 aggregated data 만 전송하도록 아키텍처 수정. 실시간성을 위해 데이터베이스의 샤arding 또는 인메모리 캐시 (Redis 등) 적용 고려.

### 2. 보안 취약점으로 인한 데이터 조작 및 시스템 공격
- **설명:** IoT 디바이스들이 네트워크에 연결되어 있어 외부 공격자가 `환경정보수집부`의 센서 데이터를 위조하거나 `작업추천부`를 조작하여 잘못된 제어 명령을 발생시킬 경우. (문서에서 강조된 `ITU-T X.1352`, `ETSI EN 303 645` 등 보안 표준 준수 필요성 언급됨)
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 전송 중인 데이터 암호화 (TLS/SSL) 와 무결성 검증 서명 적용. 인증된 디바이스만 데이터베이스와 통신하도록 할 수 있는 인증 토큰 (JWT 등) 기반 보안 프로토콜 (OAuth2, mTLS) 구현.

### 3. 데이터베이스 병목 현상 및 저장 용량 부족
- **설명:** 수많은 IoT 센서 (`환경정보수집부`) 에서 발생하는 방대한 양의 데이터가 `데이터베이스`와 `데이터페이징` 모듈로 급증할 때, 저장 공간 부족이나 읽기/쓰기 성능 저하가 발생할 경우.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 라이프사이클 관리 정책을 수립하여 오래된 데이터는 자동 보관 또는 압축. 시계열 데이터베이스 (InfluxDB 등) 도입으로 효율적인 저장 및 쿼리 성능 확보.

### 4. 알고리즘 오류로 인한 잘못된 제어 결정 (False Positive/Negative)
- **설명:** `병충해판단부`나 `음영분석부`에서 잘못된 판단을 내릴 경우 (가짜 질병 탐지 또는 누락), `작업추천부`가 오작동하여 불필요한 비용 발생이나 실제 위험 놓칠 경우.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** AI/ML 모델의 정기적인 재교육 및 모니터링 (Model Drift 감지). 인간의 개입을 위한 `작업접수부`의 수동 승인 프로세스를 중요한 결정 시 적용 (Human-in-the-loop).

### 5. 모듈 간 상호 운용성 및 표준화 미비
- **설명:** 다양한 벤더의 IoT 장비와 통신할 때, 문서에서 언급된 표준 (ISO/IEC 30141, oneM2M 등) 을 완벽히 따르지 않아 호환성 문제가 발생하거나, 커스텀 인터페이스만 사용되어 시스템이 고립될 경우.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
