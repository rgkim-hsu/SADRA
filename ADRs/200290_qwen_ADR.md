## 📋 ADR (Architecture Decision Record)

### ADR-001: **AI-In-One 플랫폼을 통한 모듈화된 기능 분리 및 통합 설계**

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트 재배환경 시스템은 온도, 습도, CO2, 광 등 다양한 물리량을 수집해야 하며, 이를 분석하고 사용자에게 서비스를 제공해야 합니다. 또한 향후 새로운 센서나 AI 알고리즘 추가가 빈번히 발생합니다. 기존 아키텍처가 이러한 다변화에 유연하게 대응할 수 있어야 합니다. |
| **결정(Decision)** | 중앙 'AI-In-One 플랫폼'을 핵심으로 설정하되, 내부 기능을 `데이터 수집 (MW)`, `분석 모듈`, `UI/UX 모듈`, `데이터 관리 (DBMS)`, `외부정보 수신` 등 명확한 하위 모듈로 분리하여 설계합니다. (이미지 상단 중앙의 `AI-In-One 플랫폼` 블록 참조) |
| **근거(Rationale)** | 1. **확장성**: 새로운 데이터 수집기 (MW) 나 분석 알고리즘을 추가할 때 전체 시스템을 재설계하지 않고 특정 모듈만 변경 가능.<br>2. **유지보수**: `DATA 분석 MODULE`이 문제가 있어도 `MW`나 `UI` 모듈은 정상 작동하며 고장 격리 가능.<br>3. **복용성**: 표준화된 `DATA 수집 기능`은 다양한 디바이스 환경에 재사용 가능. |
| **결과(Consequences)** | **긍정적**: 시스템 개발 속도가 빨라지고, 특정 기능의 업데이트가 용이함.<br>**부정적**: 모듈 간 통신 (API 등) 에 대한 오버헤드가 발생할 수 있음. |
| **트레이드오프(Trade-offs)** | 모듈 간 인터페이스 표준화 (예: RESTful API) 에 대한 추가 개발 노력 vs 유지보수 비용 절감 |

### ADR-002: **상호운용성 및 표준화 기반의 개방형 인터페이스 (OpenAPI) 채택**

| 항목 | 내용 |
|------|------|
| **상황(Context)** | TTA, ISO/IEC 등 문서에 언급된 표준에 따라 다양한 농장 환경 데이터와 외부 사물인터넷 (IoT) 기기를 연동해야 합니다. 특히 `Cloud 플랫폼` (이미지 하단) 과 외부 시스템, 모바일 서비스와의 데이터 교환이 필수적입니다. |
| **결정(Decision)** | 시스템의 핵심 데이터 흐름을 `OpenAPI & Service API` (이미지 중앙 하단) 를 통해 외부로 개방합니다. 이트 (ETSI) 나 oneM2M 표준을 참조하여 메시지 프로토콜과 데이터 형식을 표준화합니다. |
| **근거(Rationale)** | 1. **상호운용성**: 다른 제조사의 IoT 기기나 외부 S/W 와도 데이터 연동이 쉬워짐.<br>2. **생태계 성장**: 외부 개발자나 파트너사들이 시스템에 쉽게 접근하여 새로운 애플리케이션 개발 가능.<br>3. **표준 준수**: 국제/국내 표준 (ISO/IEC 30141 등) 을 준수하여 글로벌 시장 진출 및 인증 획득 용이. |
| **결과(Consequences)** | **긍정적**: 다양한 생태계 파트너십 가능, 시장 확장성 확보.<br>**부정적**: 보안 정책 (Authentication, Authorization) 이 엄격하게 적용되어야 할 부담 증가. |
| **트레이드오프(Trade-offs)** | 오픈된 API 공격 표면 (Attack Surface) 확대 vs 파트너십 통한 비즈니스 기회 증가 |

### ADR-003: **분산형 DBMS 구조 및 하이브리드 클라우드 전략**

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 이미지 하단 `Cloud 플랫폼` 및 중앙 `수집 DBMS` 블록에서 데이터를 다중으로 관리하고 있으며, 다양한 센서 (`수집 장비`) 에서 방대한 양의 데이터 (`온도, 습도, pH` 등) 가 생성됩니다. 또한 실시간 모니터링과 분석을 동시에 수행해야 합니다. |
| **결정(Decision)** | 단일 거대한 데이터베이스가 아닌 `수집 DBMS` 및 분석용 저장소를 분리하는 전략을 취합니다. 필요 시 온프레미스 데이터베이스와 클라우드 스토리지를 혼용하는 하이브리드 아키텍처를 고려합니다. |
| **근거(Rationale)** | 1. **데이터 분리**: 수집용 (Raw Data) 과 분석용 (Analytics Data) 의 목적에 따라 저장 엔진을 다르게 사용하여 성능 최적화 (예: 시계열 DB vs 관계형 DB).<br>2. **내구성**: 수집 데이터의 무결성을 위해 분산된 DBMS 구성 (이미지에 3 개의 원형 아이콘 시각화).<br>3. **비용 효율**: `Cloud 플랫폼` 을 기반으로 핵심 처리만 집중하고, 대용량 로우데이터는 저비용 스토리지로 격리. |
| **결과(Consequences)** | **긍정적**: 데이터 처리 지연 시간 최소화, 비용 최적화.<br>**부정적**: 여러 DBMS 환경 간의 동기화 및 데이터 통합 관리 복잡도 증가. |
| **트레이드오프(Trade-offs)** | DB 연동 및 마이그레이션 비용 증가 vs 높은 성능 및 가용성 확보 |

## ⚠️ 잠재적 위험 분석

### 1. [IoT 디바이스 보안 및 인증 취약점]
- **설명:** 시스템은 `관측 환경 데이터` (이미지 왼쪽) 를 다양한 IoT 센서 (온도, 습도, 기체 센서 등) 에서 수집합니다. 이러한 각 기기마다 고유한 보안 정책과 인증 키가 필요하지만, 저가의 농장용 센서는 보안 기능이 부족하거나 표준화된 인증 프로토콜을 준수하지 않을 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 
    - **TTA 또는 KISA 보안 인증 기준 (ITU-T X.1352 등)** 을 준수하도록 디바이스 호환성을 검토합니다.
    - **Mutual Authentication (서로 인증)** 기반의 통신 프로토콜 (MQTT over TLS 등) 을 강제 적용합니다.
    - **Edge Gateway** 를 사용하여 센서 데이터를 수집한 후, 외부 네트워크로 직접 연결되기 전에 보안 필터링 및 인트라넷망으로 유도합니다.

### 2. [단일 장애점 (Single Point of Failure): AI-In-One 플랫폼 고장]
- **설명:** 시스템의 모든 데이터 처리가 중앙 `AI-In-One 플랫폼` (이미지 중앙 상단) 을 거쳐갑니다. 플랫폼의 핵심 엔진 (예: 데이터 수집 MW 모듈 중 하나) 에 중대한 장애가 발생하면 전체 `Cloud 플랫폼` 및 서비스 제공이 정지될 위험이 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **Active-Active 클러스터링**: 핵심 모듈을 2 개 이상 복제하여 이중화 구성합니다.
    - **Graceful Degradation**: 한 모듈 (예: `분석 모듈`) 이 멈추더라도 `수집 MW` 및 기본 모니터링 서비스는 최소한의 기능으로만 유지되도록 설계합니다.

### 3. [데이터 무결성 및 동기화 문제]
- **설명:** `수입 DBMS` (이미지 중앙 하단) 및 다양한 데이터 수집 (`MW`) 에서 들어오는 데이터가 실시간성 없이 저장되거나, 네트워크 분할로 인해 `Cloud 플랫폼` 과 `수집 장비` 간의 데이터 동기화가 지연될 수 있습니다. 이는 실시간 모니터링 (`Application`, `WEB S/W`) 에 오류를 발생시킬 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **Change Data Capture (CDC)** 를 사용한 실시간 데이터 복제 방식을 적용합니다.
    - **최소 데이터 무결성 규칙** (예: 온도 범위 검증) 을 적용하여 오동작 데이터를 자동으로 필터링합니다.

### 4. [API 남용 및 외부 공격]
- **설명:** 시스템은 `OpenAPI & Service API` (이미지 중앙 하단) 를 통해 외부와 연동됩니다. 이 API 를 통해 권한 없는 접근을 시도하거나, 대용량 데이터를 추출하는 공격 (DDoS 또는 데이터 스캐빈징) 을 감지하지 못할 경우 문제가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **API Gateway** 를 도입하여 rate limiting (요구 빈도 제한) 과 사용자 인증 (OAuth2.0 등) 을 집중 관리합니다.
    - **방화벽 (WAF)** 을 통해 Malicious Traffic 을 실시간으로 차단합니다.

### 5. [클라우드 비용 및 성능 최적화 실패]
- **설명:** `Cloud 플랫폼` 기반 시스템은 트래픽 증가에 따라 자동으로 스케일링 (Auto Scaling) 됩니다. 그러나 예측 불가능한 농업 계절성 피크 트래픽 (예: 수확기 집중 모니터링) 이 발생했을 때, 비용 과부하나 클라우드 리소스 부족으로 성능이 저하될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **스케일링 정책 최적화**: 트래픽 예측을 기반으로 사전 리소스 할당이나 반응형 스케일링을 조정합니다.
    - **비용 관리 도구**를 사용하여 사용하지 않는 리소스 (Idle Resources) 를 자동으로 종료하도록 설정합니다.
