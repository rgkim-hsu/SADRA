📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **모듈형 마이크로서비스 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜 시스템은 기상 DB, 예보기상 DB, 예보 DB 등 이기종 데이터 소스를 통합하여 실시간으로 작물 생육 상태를 예측하고, 수량 예측 및 조치 사항을 출력해야 함. 각 데이터 소스(기상, 품종, 재배)는 독립적인 특성을 가지고 있으며, 시스템은 유연하고 확장 가능한 구조가 필요함.                                                                                                                                      |
| **결정(Decision)**       | **마이크로서비스 아키텍처**를 채택하여 기상 입력자료, 품종자료, 재배자료를 독립적인 서비스로 분리하고, 작업모형(생육 상태 예측)을 중앙에서 관리하며, 예측수량과 출력을 위한 API 게이트웨이를 통해 통합함.                                                                                                                                                                                 |
| **근거(Rationale)**      | 1) **독립적 확장성**: 각 데이터 소스(기상, 품종, 재배)는 사용량 패턴이 다를 수 있으므로, 독립적으로 스케일링 가능. 2) **유연성**: 개별 컴포넌트(예: 기상 DB) 업데이트 시 전체 시스템 중단을 방지. 3) **기술 다형성**: 각 마이크로서비스는 최적의 기술 스택(예: 기상 DB는 시계열 DB, 품종 DB는 문서형 DB)을 사용할 수 있음. 4) **스마트팜 트렌드**: 최신 스마트팜 시스템은 IoT 센서 데이터(기상, 토양 등)와 클라우드 기반 분석을 결합하는 추세이며, 모듈형 아키텍처가 표준화됨. |
| **결과(Consequences)**   | **긍정적**: 시스템 유지보수성 향상, 장애 격리(한 서비스 장애가 전체 시스템에 영향을 미치지 않음), 개별 컴포넌트의 독립적 배포 가능. **부정적**: 네트워크 오버헤드 증가, 분산 시스템의 복잡성(트랜잭션 관리, 데이터 일관성 등) 증가.                                                                                                                                                             |
| **트레이드오프(Trade-offs)** | **장점**: 유연성, 확장성, 장애 복구력. **단점**: 아키텍처 복잡성, 네트워크 latency, 데이터 일관성 관리 어려움.                                                                                                                                                                                                                              |

### ADR-002: **실시간 데이터 스트리밍 처리 파이프라인 구축**

| 항목                     | 내용                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 기상 DB, 예보기상 DB, 예보 DB에서 실시간으로 데이터가 유입되며, 작업모형은 이 데이터를 기반으로 실시간으로 생육 상태를 예측해야 함. 기존 배치 처리 방식은 스마트팜의 실시간 요구사항을 충족하지 못함.                                                                                        |
| **결정(Decision)**       | **Apache Kafka** 또는 **AWS Kinesis**를 사용하여 실시간 데이터 스트리밍 파이프라인을 구축. 입력 인터페이스에서 데이터가 유입되면 즉시 작업모형으로 전달되며, 생육 상태 및 예측수량이 실시간으로 갱신됨.                                                                              |
| **근거(Rationale)**      | 1) **실시간성**: 스마트팜은 환경 변화(기상, 토양 등)에 즉각적으로 반응해야 하며, 스트리밍 처리는 1초 미만의 지연으로 데이터를 처리할 수 있음. 2) **데이터 손실 방지**: Kafka의 영속성 보장 메커니즘으로 데이터 손실을 최소화. 3) **확장성**: 스트리밍 시스템은 수평적으로 확장 가능하여 대용량 데이터(예: 다수의 IoT 센서) 처리 가능. |
| **결과(Consequences)**   | **긍정적**: 실시간 모니터링 및 조치 가능, 데이터 처리 지연 최소화. **부정적**: 스트리밍 시스템의 구축 및 유지보수 비용 증가, 복잡한 이벤트 처리 로직 필요.                                                                                                              |
| **트레이드오프(Trade-offs)** | **장점**: 실시간 데이터 처리, 확장성, 신뢰성. **단점**: 인프라 비용, 복잡한 오류 처리 로직.                                                                                                                                                  |

### ADR-003: **중앙 집중형 작업모형(생육 상태 예측) 엔진**

| 항목                     | 내용                                                                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 작업모형은 기상, 품종, 재배 데이터를 종합하여 생육 상태를 예측하는 핵심 로직임. 이 로직은 모든 데이터 소스의 의존성이 높으며, 예측 정확도가 시스템 성능을 좌우함.                                                                                                                                                               |
| **결정(Decision)**       | **중앙 집중형 예측 엔진**을 구축하여, 모든 입력 데이터를 통합 처리하고, 생육 상태 및 예측수량을 산출. 엔진은 **기계 학습 모델**(예: XGBoost, Random Forest) 또는 **농업 시뮬레이션 알고리즘**을 사용함.                                                                                                                         |
| **근거(Rationale)**      | 1) **데이터 통합**: 기상, 품종, 재배 데이터는 서로 연관성이 높으며, 중앙에서 통합 처리해야 예측 정확도가 높음. 2) **모델 관리**: 예측 모델은 주기적으로 재훈련해야 하며, 중앙 집중형으로 관리하면 버전 컨트롤이 용이함. 3) **스마트팜 표준**: 농업 분야에서 **FAO(UN Food and Agriculture Organization)**와 **ISO 11783(ISOBUS)** 표준은 중앙화된 데이터 처리 및 분석을 권장함. |
| **결과(Consequences)**   | **긍정적**: 높은 예측 정확도, 모델 관리 용이성. **부정적**: 단일 장애점(single point of failure) 위험, 높은 컴퓨팅 자원 요구.                                                                                                                                                                    |
| **트레이드오프(Trade-offs)** | **장점**: 예측 정확도 향상, 중앙화된 관리. **단점**: 장애 시 전체 시스템 영향을 미침, 고성능 서버 필요.                                                                                                                                                                                           |

⚠️ 잠재적 위험 분석
------------

### 1. **데이터 일관성 문제**

* **설명:** 마이크로서비스 아키텍처에서 기상 DB, 예보기상 DB, 예보 DB 간 데이터 동기화 지연으로 인해 작업모형이 오류 있는 데이터를 처리할 수 있음. 예를 들어, 기상 DB의 최신 데이터와 예보 DB의 데이터가 일치하지 않아 생육 상태 예측이 부정확해질 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **이벤트 소싱(Event Sourcing)** 패턴을 도입하여 모든 데이터 변화를 이벤트 로그로 기록하고, 필요 시 재처리 가능하도록 함.
  * **Saga 패턴**을 사용하여 분산 트랜잭션을 관리하고, 데이터 일관성을 유지함.
  * **CDN(Content Delivery Network)**을 활용하여 자주 접근하는 데이터(예: 품종 정보)를 캐싱하여 지연을 줄임.

* * *

### 2. **실시간 처리 지연**

* **설명:** 스트리밍 파이프라인에서 데이터 유입 속도가 시스템 처리 속도를 초과할 경우, 예측수량 및 생육 상태 갱신이 지연되어 실시간성이 떨어질 수 있음. 특히, IoT 센서에서 대량의 데이터가 동시에 유입될 때 발생 가능.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **오토스케일링(Auto-scaling)**을 통해 스트리밍 처리 노드를 동적으로 확장함.
  * **데이터 샘플링** 또는 **에지 컴퓨팅**을 통해 센서 데이터의 일부를 사전 처리하여 중앙 시스템의 부담을 줄임.
  * **우선순위 큐**를 도입하여 중요 데이터(예: 기상 이상 현상)를 우선 처리함.

* * *

### 3. **예측 모델 정확도 저하**

* **설명:** 작업모형에서 사용하는 예측 모델이 새로운 품종 또는 예기치 않은 기상 조건(예: 극한 기상 현상)에 대해 정확도가 떨어질 수 있음. 특히, 스마트팜에서 새로운 작물이 도입될 때 발생 가능.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **지속적 학습(Continuous Learning)** 메커니즘을 도입하여 모델을 주기적으로 재훈련하고, 새로운 데이터에 적응하도록 함.
  * **A/B 테스팅**을 통해 새로운 모델과 기존 모델의 성능을 비교하여 점진적으로 업데이트함.
  * **도메인 전문가(농업 과학자)**와 협업하여 모델의 예측 결과를 검증하고, 피드백을 반영함.

* * *

### 4. **보안 취약점(데이터 유출)**

* **설명:** 기상 DB, 예보 DB 등 민감한 농업 데이터가 해커에 의해 유출될 경우, 경쟁사 또는 악의적인 사용자에 의해 악용될 수 있음. 특히, 클라우드 기반 시스템에서 발생 가능.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **데이터 암호화**: 저장 시(AES-256) 및 전송 시(TLS 1.3) 데이터를 암호화함.
  * **Zero Trust Architecture**를 도입하여 모든 접근을 인증하고, 최소 권한 원칙을 적용함.
  * **정기적인 보안 감사** 및 **침해 시뮬레이션**을 통해 취약점을 사전 발견함.

* * *

### 5. **시스템 장애로 인한 영농 정보 손실**

* **설명:** 중앙 집중형 작업모형 또는 출력 인터페이스(출력사양) 장애 시, 영농정보(수량예측, 조치사항, 생육상태)가 손실될 수 있으며, 농업 결정에 지장을 초래할 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **다중화(Replication)**를 통해 작업모형 및 출력 인터페이스를 이중화하여 장애 시 자동으로 Failover되도록 함.
  * **지속적 백업**을 통해 영농정보를 주기적으로 백업하고, 장애 시 빠르게 복구할 수 있도록 함.
  * **오프라인 모드**를 지원하여, 네트워크 장애 시에도 로컬에서 기본적인 예측을 수행할 수 있도록 함.

* * *

### 6. **IoT 센서 오류로 인한 데이터 오염**

* **설명:** 기상 DB 또는 예보 DB에 공급되는 IoT 센서(예: 온도, 습도, 토양 수분 센서)가 오작동하여 잘못된 데이터를 전달할 경우, 작업모형의 예측 결과가 왜곡될 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **데이터 검증 로직**을 도입하여, 센서 데이터의 유효 범위를 체크하고, 이상치를 필터링함.
  * **다중 센서 fusion**을 통해 여러 센서의 데이터를 교차 검증하여 오류를 감지함.
  * **센서 상태 모니터링**을 통해 오작동 센서를 자동으로 감지하고, 관리자에게 알림을 보냄.

* * *

### 7. **API 게이트웨이 병목 현상**

* **설명:** 출력을 위한 API 게이트웨이가 다수의 클라이언트(예: 모바일 앱, 웹 대시보드) 요청을 처리하지 못하여 시스템 전체가 느려질 수 있음. 특히, 수확 시즌에 많은 사용자가 동시에 접근할 때 발생 가능.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **API 게이트웨이의 수평 확장**을 통해 처리 용량을 늘림.
  * **캐싱(Caching)**을 도입하여 자주 요청하는 데이터(예: 일일 수량 예측)를 캐싱하여 응답 시간을 단축함.
  * **Rate Limiting**을 통해 과도한 요청을 제한하고, 우선순위를 부여함.
