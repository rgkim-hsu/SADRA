📋 ADR (Architecture Decision Record)

### ADR-001: 중앙 집중형 농업 정보 레포지터리 기반 데이터 통합 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 환경 모니터링(Environment Monitoring), 데이터 누적(Data Accumulation), 노하우 베이스 관리(KnowHow Base Mgmt.) 등 이질적인 세 가지 기능 엔티티로부터 Measured Data, Log Data, Expertise Data가 동시에 생성된다. 이를 분산 저장할 경우 예측·계산 분석 엔티티가 일관성 없는 데이터를 참조하게 되어 재배 계획 컨설팅의 신뢰성이 저하된다.   |
| **결정(Decision)**       | 모든 데이터 수집 기능 엔티티의 출력을 단일 Agricultural Information Repository로 집선(Aggregation)하고, 예측(Prediction) 및 계산(Calculation) 기능 엔티티는 반드시 이 레포지터리만을 유일한 데이터 소스(Single Source of Truth)로 참조하도록 아키텍처를 결정한다. Plan Consulting Function 역시 동 레포지터리를 통해서만 분석 결과를 수신한다. |
| **근거(Rationale)**      | ① 농업 도메인 특성상 환경 센서 데이터(Measured)·운영 로그(Log)·전문가 지식(Expertise)의 교차 참조가 정밀 예측에 필수적이다. ② 중앙 레포지터리 패턴은 데이터 버전 관리, 감사 추적(Audit Trail), 일관된 스키마 적용을 단일 지점에서 보장한다. ③ ITU-T Y.4000 계열 및 ISO 11783(ISOBUS) 스마트팜 ICT 표준이 요구하는 상호운용성 확보에 유리하다.                  |
| **결과(Consequences)**   | (+) 분석 엔티티 간 데이터 일관성 보장, 재배 컨설팅 품질 향상, 단일 보안 정책 적용 용이. (+) 서비스 사용자(Service Users)에게 제공되는 의사결정(Decisions) 및 재배 계획 정보의 신뢰도 제고. (−) 레포지터리가 단일 장애점(SPOF)이 되어 장애 시 전체 서비스 중단 위험 존재. (−) 대용량 시계열 센서 데이터 수용을 위한 스토리지·I/O 설계 복잡도 증가.                         |
| **트레이드오프(Trade-offs)** | **얻는 것:** 데이터 일관성, 단순한 분석 파이프라인, 표준 준수 용이성. **감수해야 할 것:** 레포지터리 가용성에 대한 전체 시스템 의존, 수평 확장(Scale-out) 시 분산 트랜잭션 복잡성, 초기 스키마 설계 실패 시 전면 재구조화 비용.                                                                                                        |

### ADR-002: 네트워크 계층을 통한 외부 연계 및 서비스 사용자 인터페이스 분리

| 항목                     | 내용                                                                                                                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | Service Users는 네트워크를 통해 Request/Inquiry를 직접 서비스 제공자(Service Provider)에 전달하고, 반대로 Plan Consulting Function도 네트워크를 통해 재배 계획 컨설팅 정보를 사용자에게 반환한다. 현재 다이어그램상 네트워크 구간의 보안 및 프로토콜 정의가 명시되지 않아 외부 접점 관리 정책이 불분명하다.                         |
| **결정(Decision)**       | 서비스 사용자와 서비스 제공자 사이의 네트워크 구간에 API Gateway / ESB(Enterprise Service Bus) 계층을 명시적으로 배치하고, 외부 요청은 반드시 이 게이트웨이를 통해서만 Plan Consulting Function에 도달하도록 한다. 내부 Data Collection Function과 분석 엔티티 간 통신은 내부 메시지 브로커(예: MQTT, AMQP)로 분리 운영한다. |
| **근거(Rationale)**      | ① 농업 IoT 환경에서는 저대역폭·고지연 네트워크 조건이 빈번하므로 외부/내부 통신 프로토콜을 분리해야 한다. ② API Gateway는 인증, 속도 제한(Rate Limiting), 로깅을 단일 지점에서 처리하여 내부 컴포넌트 보호에 유리하다. ③ 국내 스마트팜 ICT 기기 표준(농식품부 고시)에서 요구하는 데이터 연동 규격 준수를 게이트웨이 레벨에서 일괄 적용 가능하다.                |
| **결과(Consequences)**   | (+) 외부 공격 표면 최소화, 프로토콜 변환 중앙화, 서비스 버전 관리 용이. (−) 게이트웨이 자체가 추가적인 레이턴시 및 SPOF 요소가 되며, 운영 복잡도 증가.                                                                                                                                     |
| **트레이드오프(Trade-offs)** | **얻는 것:** 보안 강화, 외부·내부 프로토콜 독립성, 정책 일관성. **감수해야 할 것:** 게이트웨이 고가용성 구성 비용, 추가 홉(Hop)으로 인한 응답 지연 가능성.                                                                                                                                 |

⚠️ 잠재적 위험 분석
------------

### 1. Agricultural Information Repository 단일 장애점(SPOF) 위험

* **설명:** 현재 아키텍처에서 Prediction, Calculation, Plan Consulting 등 모든 상위 기능이 단일 레포지터리에 의존한다. 레포지터리 장애(HW 오류, DB 프로세스 다운, 네트워크 파티션) 발생 시 데이터 수집은 지속되나 분석·컨설팅 기능이 전면 중단되어 농작물 생육 위기 대응이 불가능해진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Active 또는 Active-Standby 이중화 구성(예: PostgreSQL Streaming Replication, TimescaleDB HA) 적용. 장애 전환(Failover) 시간을 RTO 기준으로 정의하고 자동화된 Health Check 및 Failover 스크립트를 운영한다. 수집 엔티티에는 로컬 버퍼링(Edge Buffering) 기능을 추가하여 레포지터리 장애 시에도 데이터 유실을 방지한다.

### 2. 실시간 센서 데이터 처리 지연(Latency) 및 처리량 병목 위험

* **설명:** Environment Monitoring Functional Entity는 온도·습도·CO₂·조도 등 다수의 IoT 센서로부터 고빈도 Measured Data를 수집한다. 단일 레포지터리 경유 구조에서 데이터 유입 속도가 쓰기 처리량을 초과하면 큐 백프레셔(Backpressure)가 발생하고, 이는 Prediction Entity의 입력 데이터 지연으로 이어져 재배 환경 이상 감지가 늦어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 시계열 데이터 전용 TSDB(InfluxDB, TimescaleDB) 도입 및 핫/콜드 티어 분리 저장 전략 채택. MQTT 브로커(예: EMQX, Mosquitto)를 Data Collection 전단에 배치하여 비동기 버퍼링을 수행하고, 레포지터리 쓰기 부하를 평탄화(Smoothing)한다. 수평 샤딩(Sharding) 전략을 초기 설계에 반영한다.

### 3. KnowHow Base(전문가 지식) 데이터 품질 저하 및 편향 위험

* **설명:** KnowHow Base Mgmt. Functional Entity가 수집하는 Expertise Data는 특정 전문가 또는 제한된 작물·지역에 편향된 경험 데이터일 수 있다. 이 데이터가 Prediction Entity의 학습 입력으로 활용될 경우, 모델이 특정 환경 조건에 과적합(Overfitting)되어 다양한 스마트팜 환경에서 잘못된 재배 계획을 Service Users에게 제공할 위험이 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Expertise Data 입력 시 출처·지역·작물종·측정 조건을 필수 메타데이터로 태깅하는 데이터 거버넌스 정책 수립. 신규 지식 데이터에 대한 전문가 검토(Peer Review) 워크플로 구현. Prediction 모델의 성능 지표(정확도, F1-Score 등)를 주기적으로 모니터링하고 드리프트(Data Drift) 감지 시 재학습 파이프라인을 자동 트리거한다.

### 4. 네트워크 구간 보안 취약점 및 데이터 위변조 위험

* **설명:** 다이어그램의 'Network' 계층은 공중망(인터넷) 또는 농업용 무선망을 포함할 수 있다. Service Users의 Request/Inquiry 및 서비스 응답이 암호화되지 않은 채 전송될 경우, 중간자 공격(MITM)을 통해 재배 계획 데이터가 탈취되거나, 악의적으로 위변조된 센서 데이터가 레포지터리에 주입되어 Prediction 결과를 오염시킬 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 네트워크 구간에 TLS 1.3 이상 적용 의무화. IoT 디바이스(센서 노드) 수준에서 디바이스 인증서 기반 상호 TLS(mTLS) 인증 도입. 데이터 수집 엔티티 → 레포지터리 경로에 데이터 무결성 서명(HMAC 또는 디지털 서명) 적용. 국내 망분리 및 개인정보보호법, 농업 데이터 보안 가이드라인 준수 여부를 정기 감사한다.

### 5. Prediction/Calculation 모델 설명 불가능성(Explainability) 및 의사결정 신뢰성 위험

* **설명:** Prediction Functional Entity가 머신러닝/딥러닝 기반 블랙박스 모델을 사용할 경우, Plan Consulting Function이 Service Users에게 전달하는 '재배 계획 컨설팅' 결과의 근거를 설명할 수 없다. 농업 현장의 사용자는 이유를 알 수 없는 추천을 신뢰하지 않거나, 반대로 맹목적으로 따라 작물 피해가 발생할 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** XAI(Explainable AI) 기법(SHAP, LIME 등)을 Prediction Entity 출력 파이프라인에 통합하여 예측 결과와 함께 주요 기여 변수 및 신뢰 구간을 Plan Consulting Function에 전달한다. 사용자 인터페이스에는 "이 추천의 주요 근거: 최근 7일간 야간 온도 평균 2.3°C 하락"과 같은 자연어 설명을 함께 제공하는 UX를 설계한다. 모델 성능 임계값 미달 시 전문가 검토 플래그를 자동 발행하는 Human-in-the-loop 프로세스를 운영한다.

### 6. 멀티테넌트 서비스 사용자 간 데이터 격리 실패 위험

* **설명:** 다수의 Service Users(복수의 농장 운영자)가 동일한 Service Provider 플랫폼을 공유할 경우, Agricultural Information Repository 내 데이터 격리가 불충분하면 A농장의 재배 노하우·환경 데이터가 B농장에 노출될 수 있다. 특히 Expertise Data는 농장 고유의 영업 비밀에 해당할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 레포지터리 설계 단계부터 테넌트 ID를 모든 데이터 레코드의 파티션 키로 적용하는 Row-Level Security(RLS) 정책 구현. Plan Consulting Function의 API 계층에서 JWT 토큰 내 테넌트 클레임을 검증하여 교차 접근을 원천 차단한다. 연간 단위 멀티테넌트 격리 침투 테스트(Penetration Test)를 수행하고 결과를 보안 감사 기록으로 보존한다.

### ADR-002: 네트워크 계층을 통한 외부 연계 및 서비스 사용자 인터페이스 분리

⚠️ 잠재적 위험 분석
------------

### 1. Agricultural Information Repository 단일 장애점(SPOF) 위험

* **설명:** 현재 아키텍처에서 Prediction, Calculation, Plan Consulting 등 모든 상위 기능이 단일 레포지터리에 의존한다. 레포지터리 장애(HW 오류, DB 프로세스 다운, 네트워크 파티션) 발생 시 데이터 수집은 지속되나 분석·컨설팅 기능이 전면 중단되어 농작물 생육 위기 대응이 불가능해진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Active 또는 Active-Standby 이중화 구성(예: PostgreSQL Streaming Replication, TimescaleDB HA) 적용. 장애 전환(Failover) 시간을 RTO 기준으로 정의하고 자동화된 Health Check 및 Failover 스크립트를 운영한다. 수집 엔티티에는 로컬 버퍼링(Edge Buffering) 기능을 추가하여 레포지터리 장애 시에도 데이터 유실을 방지한다.

### 2. 실시간 센서 데이터 처리 지연(Latency) 및 처리량 병목 위험

* **설명:** Environment Monitoring Functional Entity는 온도·습도·CO₂·조도 등 다수의 IoT 센서로부터 고빈도 Measured Data를 수집한다. 단일 레포지터리 경유 구조에서 데이터 유입 속도가 쓰기 처리량을 초과하면 큐 백프레셔(Backpressure)가 발생하고, 이는 Prediction Entity의 입력 데이터 지연으로 이어져 재배 환경 이상 감지가 늦어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 시계열 데이터 전용 TSDB(InfluxDB, TimescaleDB) 도입 및 핫/콜드 티어 분리 저장 전략 채택. MQTT 브로커(예: EMQX, Mosquitto)를 Data Collection 전단에 배치하여 비동기 버퍼링을 수행하고, 레포지터리 쓰기 부하를 평탄화(Smoothing)한다. 수평 샤딩(Sharding) 전략을 초기 설계에 반영한다.

### 3. KnowHow Base(전문가 지식) 데이터 품질 저하 및 편향 위험

* **설명:** KnowHow Base Mgmt. Functional Entity가 수집하는 Expertise Data는 특정 전문가 또는 제한된 작물·지역에 편향된 경험 데이터일 수 있다. 이 데이터가 Prediction Entity의 학습 입력으로 활용될 경우, 모델이 특정 환경 조건에 과적합(Overfitting)되어 다양한 스마트팜 환경에서 잘못된 재배 계획을 Service Users에게 제공할 위험이 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Expertise Data 입력 시 출처·지역·작물종·측정 조건을 필수 메타데이터로 태깅하는 데이터 거버넌스 정책 수립. 신규 지식 데이터에 대한 전문가 검토(Peer Review) 워크플로 구현. Prediction 모델의 성능 지표(정확도, F1-Score 등)를 주기적으로 모니터링하고 드리프트(Data Drift) 감지 시 재학습 파이프라인을 자동 트리거한다.

### 4. 네트워크 구간 보안 취약점 및 데이터 위변조 위험

* **설명:** 다이어그램의 'Network' 계층은 공중망(인터넷) 또는 농업용 무선망을 포함할 수 있다. Service Users의 Request/Inquiry 및 서비스 응답이 암호화되지 않은 채 전송될 경우, 중간자 공격(MITM)을 통해 재배 계획 데이터가 탈취되거나, 악의적으로 위변조된 센서 데이터가 레포지터리에 주입되어 Prediction 결과를 오염시킬 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 네트워크 구간에 TLS 1.3 이상 적용 의무화. IoT 디바이스(센서 노드) 수준에서 디바이스 인증서 기반 상호 TLS(mTLS) 인증 도입. 데이터 수집 엔티티 → 레포지터리 경로에 데이터 무결성 서명(HMAC 또는 디지털 서명) 적용. 국내 망분리 및 개인정보보호법, 농업 데이터 보안 가이드라인 준수 여부를 정기 감사한다.

### 5. Prediction/Calculation 모델 설명 불가능성(Explainability) 및 의사결정 신뢰성 위험

* **설명:** Prediction Functional Entity가 머신러닝/딥러닝 기반 블랙박스 모델을 사용할 경우, Plan Consulting Function이 Service Users에게 전달하는 '재배 계획 컨설팅' 결과의 근거를 설명할 수 없다. 농업 현장의 사용자는 이유를 알 수 없는 추천을 신뢰하지 않거나, 반대로 맹목적으로 따라 작물 피해가 발생할 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** XAI(Explainable AI) 기법(SHAP, LIME 등)을 Prediction Entity 출력 파이프라인에 통합하여 예측 결과와 함께 주요 기여 변수 및 신뢰 구간을 Plan Consulting Function에 전달한다. 사용자 인터페이스에는 "이 추천의 주요 근거: 최근 7일간 야간 온도 평균 2.3°C 하락"과 같은 자연어 설명을 함께 제공하는 UX를 설계한다. 모델 성능 임계값 미달 시 전문가 검토 플래그를 자동 발행하는 Human-in-the-loop 프로세스를 운영한다.

### 6. 멀티테넌트 서비스 사용자 간 데이터 격리 실패 위험

* **설명:** 다수의 Service Users(복수의 농장 운영자)가 동일한 Service Provider 플랫폼을 공유할 경우, Agricultural Information Repository 내 데이터 격리가 불충분하면 A농장의 재배 노하우·환경 데이터가 B농장에 노출될 수 있다. 특히 Expertise Data는 농장 고유의 영업 비밀에 해당할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 레포지터리 설계 단계부터 테넌트 ID를 모든 데이터 레코드의 파티션 키로 적용하는 Row-Level Security(RLS) 정책 구현. Plan Consulting Function의 API 계층에서 JWT 토큰 내 테넌트 클레임을 검증하여 교차 접근을 원천 차단한다. 연간 단위 멀티테넌트 격리 침투 테스트(Penetration Test)를 수행하고 결과를 보안 감사 기록으로 보존한다.
