# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 데이터 상호운용성 확보를 위한 Event-Driven, 메시징 기반 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 User 1부터 User n까지 매우 이질적이고 다양한 출처(센서, 장비, 서비스)의 데이터를 실시간으로 수집(Monitoring Function)해야 합니다. 또한, 수집된 데이터를 학습하고 분석한 정보(Learning Screening)를 다시 표준화된 형태로 외부에 제공(Learning Information Connection)해야 하므로, 데이터의 이질성(Heterogeneity)과 높은 결합도를 해결하는 것이 가장 큰 아키텍처적 과제입니다. |
| **결정(Decision)** | **서비스 지향 아키텍처(SOA)와 이벤트를 중심으로 하는 메시징 버스(Message Bus) 패턴**을 핵심 데이터 통신 계층으로 채택한다. 모든 시스템 컴포넌트는 데이터의 발행자(Publisher)와 구독자(Subscriber) 역할을 수행하며, 표준화된 메시지 포맷(Schema)을 기반으로 데이터를 교환해야 한다. |
| **근거(Rationale)** | 1. **느슨한 결합(Loose Coupling):** 데이터가 중앙의 단일 서비스에 의존하지 않고 메시징 버스를 통해 흐르므로, 개별 컴포넌트(User 1 장비, Learning 모듈 등)의 변경이 전체 시스템에 미치는 영향을 최소화하여 시스템 유지보수성과 확장성을 극대화할 수 있습니다. 2. **확장성(Scalability):** 실시간으로 증가하는 다양한 소스(n개 사용자)의 데이터를 버스가 효율적으로 분산 처리하고 대용량 스트리밍을 지원합니다. 3. **표준 준수:** oneM2M 또는 ISO/IEC 30141에서 요구하는 표준화된 데이터 객체 모델(Canonical Data Model)을 메시지 스키마로 정의하여 글로벌 상호운용성 기반을 마련합니다. |
| **결과(Consequences)** | **긍정적:** 매우 높은 탄력성(Resilience)과 독립적인 서비스 배포가 가능해지며, 새로운 데이터 소스(User n+1)를 추가할 때 기존 아키텍처의 수정 범위를 최소화할 수 있습니다. **부정적:** 메시지 흐름을 추적하기가 복잡하고(Observability), 최초의 통합 메시지 포맷 정의 및 거버넌스(Data Governance)를 수립하는 데 많은 시간과 노력이 필요합니다. |
| **트레이드오프(Trade-offs)** | **[복잡도 증가 vs. 결합도 최적화]** 초기 설계 단계에서 복잡도가 급격히 증가하고, 메시지 스키마 관리(Schema Registry)를 위한 별도의 오버헤드가 발생합니다. 그러나 이로 인해 개별 컴포넌트 간의 의존성이 제거되어, 장기적으로 시스템의 변경 비용이 현저하게 낮아지는 이점을 얻습니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 모델 비일관성 및 스키마 드리프트 (Schema Drift)
- **설명:** 각 사용자(User 1, User 2 등)가 제공하는 데이터 포맷이나 의미 정의가 시간이 지나면서 무분별하게 변경되거나, 시스템이 학습에 필요한 필수 데이터 필드를 누락시키는 경우입니다. 이는 Learning Screening Function의 학습 모델 오작동 및 신뢰도 저하로 이어집니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 모든 데이터 입구(Ingestion Point)에 데이터 유효성 검사(Data Validation) 게이트웨이를 필수로 구축하고, 엄격한 스키마 레지스트리(Schema Registry, 예: Confluent Schema Registry)를 도입하여 모든 데이터 모델 변경은 사전에 중앙에서 승인하고 버전 관리를 수행해야 합니다.

### 2. 실시간 데이터 폭주 및 메시징 버스 병목 현상 (Data Spike & Bottleneck)
- **설명:** 스마트팜의 모든 장비가 특정 이벤트(예: 갑작스러운 온도 변화, 대규모 장비 작동)를 한순간에 보고할 경우, Message Bus가 예상치 못한 대용량의 데이터 부하를 처리하지 못해 메시지 손실, 지연(Latency) 증가, 또는 서비스 장애가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 메시징 버스를 수평적으로 확장 가능한 분산 스트리밍 플랫폼(예: Apache Kafka)을 사용하고, Monitoring Function 레벨에서 데이터 펌핑(Throttling) 로직 및 버스트 케이스(Burst Case)에 대한 백프레셔(Backpressure) 처리 메커니즘을 구현해야 합니다.

### 3. 전방위적 보안 취약점 및 인증 범위 누락 (Attack Surface Expansion)
- **설명:** 시스템이 User 1부터 User n까지 다양한 외부 시스템과 연결되면서 공격 표면적(Attack Surface)이 기하급수적으로 증가합니다. 특히, 경량 통신 프로토콜(CoAP, MQTT 등)을 사용하는 Edge 디바이스에서 인증 부재, 암호화 취약점, 혹은 물리적 접근을 통한 데이터 탈취 위험이 높습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 최소 권한 원칙(Principle of Least Privilege)을 모든 서비스에 적용하고, 모든 통신 채널에 대해 강력한 엔드-투-엔드 암호화(End-to-End Encryption)를 의무화하며, 모든 데이터 요청/응답에 대해 OAuth 2.0 기반의 토큰 기반 인증(Token-based Authentication)을 적용해야 합니다.

### 4. 기술 표준 종속성 및 레거시 시스템 통합 문제 (Vendor/Tech Lock-in)
- **설명:** Monitoring Function을 구현하는 과정에서 특정 하드웨어 벤더나 독점적인 통신 규격(Proprietary Protocol)에 깊이 종속될 경우, 향후 표준 변경(예: TTA 표준 개정)이나 하드웨어 교체가 어려워져 아키텍처 변경 비용(Migration Cost)이 폭증합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 커넥터 레이어(Adaptor Layer)를 경계 짓고, 표준화된 API Gateway를 통해 통신을 통제해야 합니다. 이물 격리(Isolation) 원칙에 따라 독점 프로토콜이 들어오더라도, 내부에서는 반드시 표준화된 canonical data model로 변환하는 게이트웨이를 통해 처리하여 외부 의존성을 차단해야 합니다.

### 5. 학습 데이터의 편향성 및 설명 가능성 부재 (Model Bias & Explainability)
- **설명:** Learning Screening Function이 특정 사용자 그룹(예: 시설이 잘 갖춰진 User 1)의 데이터만 주로 학습에 활용하게 되면, 다른 사용자 그룹(예: 재정적 제약이 있는 User n)의 데이터 특성이 모델에 반영되지 않아, 시스템의 추천이나 진단 결과에 편향성(Bias)이 발생할 수 있습니다. 또한, 시스템이 왜 특정 결론을 도출했는지 설명(Explainability)할 수 없어 현장에서의 신뢰를 잃을 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 다양한 데이터 소스의 가중치(Weight)를 동적으로 조정하는 다중 모델 앙상블(Ensemble Model)을 구축하고, XAI(Explainable AI) 기법을 적용하여 AI가 내린 모든 판단에 대해 *'이러한 데이터 A와 B의 추세 변화가 주요 원인입니다'* 와 같은 근거 기반 설명을 필수로 출력하도록 로직을 설계해야 합니다.
