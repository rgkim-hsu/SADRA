📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: OSPH 기반 오픈소스 하드웨어 플랫폼 채택

| 항목                     | 내용                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템에서 다양한 환경 센서(온도, 습도, CO₂, 조도 등)와 구동기(환기 팬, 히팅 시스템, 조명 등)를 통합해야 하는 필요성. 각 장치별로 상이한 프로토콜과 인터페이스를 사용해 통합 복잡도가 높음. 또한, 실시간 데이터 수집·처리·제어가 필수적이며, KC 인증 등 표준화된 환경에서 운영되어야 함.   |
| **결정(Decision)**       | OSPH(Open Source Plant Hardware) 표준을 기반으로 **서버 디바이스 개발** 및 **환경 제어 서버 개발**을 진행. 모든 센서/구동기 데이터는 OSPH 기반 서버에서 통일적으로 관리되며, 사용자 UI/UX는 웹/앱을 통해 제공.                                   |
| **근거(Rationale)**      | OSPH는 농업용 오픈소스 하드웨어 표준으로, 다양한 센서/구동기와 호환성을 보장하며, 커뮤니티 지원을 받을 수 있음. 또한, 표준화된 인터페이스를 통해 개발 효율성과 유지보수성을 높일 수 있음. 온실 내/외부 환경 감지 및 최적 조건 비교 로직을 OSPH 서버에서 중앙집중식으로 관리함으로써 데이터 일관성을 확보. |
| **결과(Consequences)**   | **장점**: 표준화된 하드웨어 인터페이스로 다양한 장치 통합 용이, 개발 및 유지보수 비용 감소, KC 인증 준수를 위한 표준화된 환경 구축 가능. **단점**: OSPH 표준을 준수하지 않는 커스텀 장치와의 통합 시 어댑터 개발 필요, OSPH 표준의 버전 변화에 따른 시스템 업데이트 요구.            |
| **트레이드오프(Trade-offs)** | 얻는 장점: 호환성 향상, 개발 속도 가속화, 표준 준수 용이성. 감수해야 할 단점: OSPH 의존도로 인한 유연성 제한, 특정 벤더의 독자적 장치 통합 시 추가 비용 발생.                                                                                |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 센서 데이터 신뢰성 저하

* **설명:** 센서 오류 또는 노이즈로 인해 잘못된 환경 데이터(예: 온도, 습도)가 수집되어, 구동기가 비정상적인 제어 신호를 받게 됨. 예를 들어, 온도 센서 오류로 인해 과도한 냉방이 가동되어 작물 손실 발생.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 다중 센서 **크로스 밸리데이션** 구현, 이상 감지 알고리즘(예: Z-score, IQR) 적용, **정기적인 센서 교정** 및 예비 센서 배치.

* * *

### 2. OSPH 호환성 문제

* **설명:** OSPH 표준을 준수하지 않는 커스텀 장치(예: 특정 벤더의 고유 센서)와 통합 시, 프로토콜 또는 데이터 포맷 mismatch로 인해 시스템 오류 발생.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **어댑터 패턴**을 활용한 중간 계층 개발, 호환성 테스트 자동화, OSPH 커뮤니티와 협업을 통한 표준 준수 유도.

* * *

### 3. 실시간 데이터 처리 지연

* **설명:** 대용량 센서 데이터 스트림 처리 시, 시스템 지연으로 인해 실시간 환경 제어가 실패하여 온실 내 환경이 최적 조건에서 벗어남. 예를 들어, 급격한 온도 변화 시 제어 신호가 지연되어 작물 손상.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **엣지 컴퓨팅** 도입을 통한 로컬 데이터 처리, 데이터 스트림 최적화(예: Apache Kafka), **실시간 OS** 사용, 우선순위 기반 큐잉 시스템 구축.

* * *

### 4. 보안 취약점 노출

* **설명:** 웹/앱 인터페이스 또는 서버 디바이스에서 보안 취약점(예: SQL 인젝션, API 미인증 접근)이 노출되어, 외부 공격으로 인한 시스템 제어 권한 탈취 또는 데이터 유출 발생.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** TLS 1.3 암호화 적용, **다중 인증(MFA)** 도입, 정기적인 보안 패치 및 취약점 스캔 수행, **제로 트러스트 아키텍처** 적용.

* * *

### 5. KC 인증 미준수

* **설명:** 시스템이 KC 인증 기준(예: 전기 안전, EMI/EMC, 방수/방진)을 충족하지 못하여, 상품화 단계에서 법적 문제 발생. 예를 들어, 서버 디바이스에 사용된 부품이 KC 인증을 받지 못한 경우.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:** 인증 요구사항을 **초기 설계 단계**부터 반영, 인증 테스트 자동화, 외부 인증 기관(예: KTC)과 사전 협의 및 테스트 수행.

* * *

### 6. 시스템 확장성 제한

* **설명:** 온실 규모가 확대되거나, 새로운 작물 재배 요구사항(예: 수직 농법, 수경 재배)이 추가될 때, 기존 시스템 아키텍처가 유연하게 확장되지 못하여 성능 저하 또는 재개발 필요.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **마이크로서비스 아키텍처** 도입, 컨테이너화(예: Docker) 및 오케스트레이션(예: Kubernetes), 모듈러 디자인 적용.
