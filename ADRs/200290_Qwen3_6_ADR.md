## 📋 ADR (Architecture Decision Record)

### ADR-001: All-In-One 통합 플랫폼 및 계층형 데이터 관리 아키처 적용

| 항목                     | 내용                                                                                                                                                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트 팜 환경은 공기 환경(온습도, CO2), 근권부 환경(EC, pH, 토양수분), 외부 기상 데이터 등 이기종(Heterogeneous) 데이터 소스가 매우 다양합니다. 또한, 단순 데이터 수집뿐만 아니라 실시간 모니터링, 심층 분석, 예측, 그리고 다양한 클라이언트(Web, Mobile, S/W)로의 서비스 제공이 동시에 요구됩니다.                                                                                       |
| **결정(Decision)**       | **All-In-One 플랫폼** 아키텍처를 채택하여 데이터 수집(MW1~MW6), 처리(UI/UX, Signal Module), 저장(Collect DBMS), 분석(Analyze DBMS) 기능을 단일 플랫폼 내에서 통합합니다. 특히, **수집 DBMS**와 **근권환경 분석 DBMS**를 물리적으로 분리하여 실시간 데이터 수집 성능과 복잡한 분석 리 성능을 모두 최적화하는 계층형 데이터 관리 전략을 도입합니다.                                            |
| **근거(Rationale)**      | 이미지에서 볼 수 있듯이, 다양한 환경 데이터가 MW 시리즈 모듈을 통해 수집되고, 중앙의 'All-In-One 플랫폼'에서 통합 처리됩니다. '데이터 수집 기능', '데이터 보기 기능', '데이터 분석 기능'이 명확히 구분되어 있으며, 특히 하단에 '수집 DBMS'와 '근권환경 분석 DBMS'가 별도로 구성된 것은 시계열 데이터의 고속 수집과 분석용 데이터의 정합성을 동시에 확보하기 위한 설계로 판단됩니다. 또한 OpenAPI를 통해 외부 서비스와 연계하는 구조는 확장성을 고려한 것입니다. |
| **결과(Consequences)**   | **긍정적:** 다양한 데이터 소스를 통합 관리할 수 있으며, 실시간 모니터링과 심층 분석을 동시에 제공할 수 있습니다. API 기반 서비스 제공으로 Web, Mobile, 전문 S/W 등 다양한 채널로의 서비스 확장이 용이합니다.<br>**부정적:** 플랫폼 내부 모듈 간 결합도가 높아질 수 있으며, 수집 DBMS와 분석 DBMS 간의 데이터 동기화 또는 ETL(추출, 변환, 적재) 과정에서 지연이 발생할 수 있습니다.                                         |
| **트레이드오프(Trade-offs)** | **장점:** 데이터 통합성(Data Integration) 확보 및 다채널 서비스 제공 용이.<br>**단점:** 시스템 복잡도 증가 및 DBMS 간 데이터 이동 오버헤드 발생 가능성.                                                                                                                                                                              |

## ⚠️ 잠재적 위험 분석

### 1. 대용량 시계열 데이터 수집 병목 (Data Ingestion Bottleneck)

- **설명:** MW1부터 MW6까지 다수의 모듈을 통해 실시간으로 들어오는 센서 데이터(온도, 습도, EC, pH 등)의 양이 급증할 경우, '데이터 수집 기능' 및 '수집 DBMS'가 병목 현상을 일으켜 데이터 유실이 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 수집 계층에 **메시지 큐(Message Queue, 예: Kafka, RabbitMQ)**를 도입하여 데이터 유입을 버퍼링하고, '수집 DBMS'에는 시계열 데이터에 특화된 DB(InfluxDB, TimescaleDB 등)를 사용하여 쓰기 성능을 극대화해야 합니다.

### 2. 수집 DBMS와 분석 DBMS 간 데이터 동기화 지연 (Data Synchronization Latency)

- **설명:** '수집 DBMS'에 쌓인 원천 데이터가 '근권환경 분석 DBMS'로 이동하여 '데이터 분석 기능'(예: 수확량 분석, 이력관리)에 사용될 때, ETL 과정의 지연으로 인해 분석 결과가 실시간 모니터링 화면과 불일치할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 두 DBMS 간의 데이터 이동 파이프라인을 **스트리밍 처리(Stream Processing)** 방식으로 구축하여 지연 시간(Latency)을 최소화하고, 데이터 정합성을 검증하는 모니터링 프로세스를 상시 가동해야 합니다.

### 3. OpenAPI 노출에 따른 보안 취약점 (OpenAPI Security Risks)

- **설명:** 'OpenAPI & Service API'를 통해 외부의 Application(Web S/W, Mobile) 및 Service(농업 컨설턴트 등)에 데이터가 개방됩니다. 인증 및 권한 관리가 미흡할 경우, 악의적인 사용자가 농장 내부의 민감한 환경 데이터나 제어 신호에 접근할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 API 호출에 대해 **OAuth 2.0** 또는 **JWT(Json Web Token)** 기반의 강력한 인증(Authentication) 및 인가(Authorization) 메커니즘을 적용하고, API 게이트웨이를 통해 트래픽 제어 및 모니터링을 수행해야 합니다.

### 4. 외부 기상 데이터 의존성 및 가용성 (External Data Dependency)

- **설명:** '외부정보 수집 기능'을 통해 기상청 데이터 등을 수집하는데, 외부 API 장애나 네트워크 문제로 인해 데이터 수집이 중단될 경우, '데이터 분석 기능' 중 기상 데이터와 연계된 예측/진단 로직이 오작동할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:** 외부 데이터 수집 실패 시를 대비한 **Fallback 로직(예: 최근 유효 데이터 사용 또는 기본값 적용)**을 구현하고, 다중 외부 데이터 소스를 중복으로 구성하여 가용성을 높여야 합니다.

### 5. 모듈 간 높은 결합도로 인한 유지보수 어려움 (High Coupling Risk)

- **설명:** 'All-In-One 플랫폼'이라는 이름에서 알 수 있듯이, 데이터 수집, 처리, 분석, DB 관리 기능이 단일 시스템 내에 밀집되어 있을 경우, 특정 모듈(예: UI/UX Data Module)의 수정이 다른 모듈(예: Database Management Program)에 영향을 미쳐 전체 시스템 장애로 이어질 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 플랫폼 내부 아키텍처를 **마이크로서비스(Microservices)** 또는 **모듈러 모놀리스(Modular Monolith)** 형태로 설계하여 모듈 간 인터페이스를 명확히 분리하고, 독립적인 배포 및 테스트가 가능하도록 해야 합니다.
