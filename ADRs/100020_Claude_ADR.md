📋 ADR (Architecture Decision Record)

### ADR-001: 스마트팜 AI 기반 양방향 데이터 파이프라인 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜 환경에서는 센서·장비로부터 수집되는 대규모 실시간 데이터(온도, 습도, 토양, 영상 등)를 처리하여 작물 생육 예측, 이상 감지, 자율 제어까지 수행해야 한다. 이를 위해 빅데이터 수집(310), 공급자/제공부(320)로부터의 외부 데이터 연동, 확인부(330)·진행관리부(340)를 통한 상태 검증, 예측부(350)·분석학습부(360)를 통한 AI 추론, 연동학습부(370)·미러링부(380)를 통한 모델 동기화까지 8개 컴포넌트가 유기적으로 협력하는 아키텍처가 필요하다. |
| **결정(Decision)**       | 중앙 양방향 데이터 버스(이중 화살표 수직 축)를 중심으로 좌측(내부 처리 레이어: 빅데이터부→확인부→예측부→연동학습부)과 우측(외부 연동 레이어: 제공부→진행관리부→분석학습부→미러링부)을 대칭 구조로 배치하는 **듀얼 레이어 스트리밍 파이프라인** 아키텍처를 채택한다. 각 레이어 간 통신은 양방향 메시지 브로커(Kafka/MQTT) 기반으로 구성하며, AI 추론(예측부 350)과 학습(분석학습부 360)은 분리된 서비스로 운영한다.                           |
| **근거(Rationale)**      | ① 스마트팜의 실시간성 요구(작물 이상 감지 < 수 분 이내)를 충족하려면 배치가 아닌 스트리밍 처리가 필수적이다. ② 내부/외부 데이터 레이어 분리를 통해 외부 제공자(320) 장애가 내부 예측·제어 루프에 전파되는 것을 격리할 수 있다. ③ 연동학습부(370)·미러링부(380)의 대칭 배치는 에지-클라우드 간 모델 동기화(Federated Learning 또는 Model Mirroring) 패턴을 지원한다.                                        |
| **결과(Consequences)**   | 긍정: 컴포넌트 간 느슨한 결합으로 개별 서비스의 독립적 스케일링 가능, AI 모델 업데이트 시 전체 시스템 중단 불필요. 부정: 중앙 데이터 버스가 단일 장애점(SPOF)이 될 수 있으며, 8개 컴포넌트의 분산 트랜잭션 일관성 보장이 복잡해진다.                                                                                                                                     |
| **트레이드오프(Trade-offs)** | 얻는 것: 높은 확장성, 장애 격리, AI 추론·학습의 독립 운영. 감수할 것: 운영 복잡도 증가(분산 모니터링 필수), 네트워크 레이턴시로 인한 실시간 제어 응답 지연 가능성, 메시지 브로커 유지관리 비용 발생.                                                                                                                                                        |

### ADR-002: 예측부(350)·분석학습부(360) AI 추론-학습 분리 운영 결정

| 항목                     | 내용                                                                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 AI 모델은 실시간 작물 상태 예측(추론)과 누적 데이터 기반 모델 재학습(학습)이 동시에 요구된다. 하나의 서비스에서 이 두 역할을 처리할 경우 학습 워크로드가 추론 응답시간에 영향을 미쳐 실시간 제어 루프가 불안정해질 위험이 있다.                      |
| **결정(Decision)**       | 예측부(350)는 경량 추론 전용 서비스(온라인 서빙)로, 분석학습부(360)는 배치/스트림 재학습 전용 서비스로 완전히 분리하여 운영한다. 두 컴포넌트는 모델 레지스트리를 통해 모델 버전을 교환하며, 연동학습부(370)·미러링부(380)가 에지-클라우드 간 모델 배포를 담당한다. |
| **근거(Rationale)**      | GPU/CPU 자원 경합 방지, 추론 SLA(응답시간 < 1초) 보장, 학습 실패가 서비스 장애로 전파되는 것을 차단. MLOps 관점에서 Blue/Green 모델 배포 및 A/B 테스트 운영이 가능해진다.                                           |
| **결과(Consequences)**   | 긍정: 추론 안정성 확보, 모델 롤백 용이. 부정: 모델 레지스트리·버전 관리 인프라 추가 필요, 학습-서빙 간 모델 staleness(지연 반영) 발생 가능.                                                                     |
| **트레이드오프(Trade-offs)** | 얻는 것: 추론 안정성, 독립 스케일링, CI/CD 파이프라인 적용 가능. 감수할 것: 인프라 복잡도 증가, 최신 학습 결과가 즉시 추론에 반영되지 않는 지연 윈도우 존재.                                                              |

⚠️ 잠재적 위험 분석
------------

### 1. 중앙 데이터 버스 단일 장애점(SPOF) 위험

* **설명:** 시스템 개념도의 수직 양방향 버스는 8개 컴포넌트 전체의 통신 경로다. 메시지 브로커(Kafka 등) 클러스터 장애 발생 시, 빅데이터부(310)의 데이터 수집부터 예측부(350)의 AI 추론까지 전체 파이프라인이 동시에 중단될 수 있다. 스마트팜에서는 온실 환경 제어 중단으로 작물 피해가 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 메시지 브로커를 다중 브로커 클러스터(Kafka 3-노드 이상)로 구성하고, 에지 게이트웨이에 로컬 버퍼(로컬 큐)를 두어 브로커 장애 시에도 최소 제어 명령이 유지되도록 한다. Circuit Breaker 패턴 적용 및 헬스체크 기반 자동 페일오버를 구성한다.

### 2. 농업 환경 특성에 따른 데이터 품질 저하 위험

* **설명:** 스마트팜의 IoT 센서는 고온·고습·분진 환경에 노출되어 오작동, 드리프트, 단절이 빈번하다. 빅데이터부(310)로 유입되는 데이터에 결측치·이상값이 누적될 경우, 확인부(330)의 검증을 통과하더라도 분석학습부(360)의 모델이 오염된 데이터로 학습되어 예측부(350)의 출력 정확도가 시간이 갈수록 저하(Model Drift)된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 확인부(330)에 통계적 이상값 탐지(Z-score, IQR), 센서 간 교차 검증, 타임스탬프 기반 결측 감지 로직을 구현한다. 데이터 품질 지표(DQ Score)를 실시간 대시보드로 모니터링하고, 품질 임계치 미달 시 해당 데이터를 학습 파이프라인에서 자동 격리한다.

### 3. AI 모델 미러링(380) 과정의 보안 취약점

* **설명:** 미러링부(380)는 에지(농장 현장)와 클라우드 간 AI 모델을 동기화한다. 이 과정에서 모델 파일이 암호화 없이 전송될 경우, 중간자 공격(MITM)을 통한 모델 탈취 또는 악의적으로 조작된 모델 주입(Model Poisoning)이 가능하다. 조작된 모델이 예측부(350)에 배포되면 잘못된 농장 제어 명령이 실행될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모델 전송 시 TLS 1.3 암호화 및 모델 파일 서명(SHA-256 해시 + PKI 인증서) 검증을 의무화한다. 모델 레지스트리에 불변(immutable) 버전 관리를 적용하고, 배포 전 무결성 검증 단계를 파이프라인에 삽입한다. 제로 트러스트 네트워크 원칙에 따라 에지-클라우드 간 상호 인증(mTLS)을 적용한다.

### 4. 연동학습부(370) 연합학습 과정의 데이터 프라이버시 위험

* **설명:** 연동학습부(370)가 여러 농장의 데이터를 연합학습(Federated Learning) 방식으로 집계할 경우, 모델 그래디언트나 중간 집계 값을 분석한 역공격(Gradient Inversion Attack)을 통해 개별 농장의 민감한 생육 데이터·경영 정보가 복원될 수 있다. 특히 소규모 농가 데이터는 익명성이 낮아 재식별 위험이 크다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 연동학습부(370)에 차분 프라이버시(Differential Privacy) 노이즈 추가 및 Secure Aggregation 프로토콜을 적용한다. 참여 농장별 데이터 기여량을 최소화하는 로컬 에포크 제한을 설정하고, 개인정보 보호법(PIPA) 및 농업 데이터 거버넌스 정책 준수 여부를 정기 감사한다.

### 5. 진행관리부(340)·제공부(320) 외부 연동 장애에 따른 서비스 연속성 위험

* **설명:** 제공부(320)는 기상청 API, 농산물 시세, 외부 전문가 처방 데이터 등 외부 서비스와 연동될 가능성이 높다. 외부 API 장애·버전 변경·SLA 위반 발생 시, 진행관리부(340)가 정상 스케줄을 수립하지 못하고, 이 오류가 분석학습부(360)로 전파되어 모델 학습 입력 피처가 결손되는 cascading failure가 발생할 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 외부 연동 구간에 Bulkhead 패턴과 Timeout/Retry 정책을 적용하고, 외부 데이터 부재 시 최근 캐시값 또는 기본값(Fallback)으로 동작하는 Graceful Degradation 모드를 구현한다. 제공부(320)와의 계약에 SLA 명시 및 대체 데이터 소스(Secondary Provider)를 사전 확보한다.

### 6. 빅데이터부(310) 데이터 폭증(Data Surge)에 따른 시스템 과부하 위험

* **설명:** 수확기·기상 이변 등 특정 시점에 수천 개의 스마트팜 센서 데이터가 동시에 급증할 경우, 빅데이터부(310)의 수집·저장 처리량을 초과하여 데이터 유실이 발생할 수 있다. 이는 확인부(330) 이하 전체 파이프라인의 처리 지연을 야기하며, 예측부(350)의 실시간 추론 결과가 수 분~수십 분 지연되어 작물 제어 타이밍을 놓칠 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 빅데이터부(310)에 수평 자동 스케일링(HPA) 및 백프레셔(Backpressure) 메커니즘을 구현하고, 데이터 중요도 기반 우선순위 큐(Priority Queue)를 도입하여 긴급 제어 데이터가 먼저 처리되도록 한다. 평상시 부하의 3배 이상을 처리할 수 있는 용량 계획(Capacity Planning)을 수립하고 정기 부하 테스트를 실시한다.
