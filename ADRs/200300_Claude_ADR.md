📋 ADR (Architecture Decision Record)

### ADR-001: OSHP 기반 클라우드 관제 서버와 엣지 디바이스 간 하이브리드 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 중소형 스마트팜은 온실 내 온도·습도·CO₂·광량 등 복합환경 데이터를 실시간으로 수집·제어해야 한다. 농가별 네트워크 인프라가 불균일하고, 농업 현장 특성상 간헐적 통신 단절이 빈번하다. 단일 클라우드 의존 구조는 네트워크 장애 시 환경 제어 불능 상태를 초래하므로, 엣지-클라우드 이중 구조가 필수적이다.                   |
| **결정(Decision)**       | OSHP(Open Smart Home Protocol 또는 유사 개방형 표준 프로토콜)를 기반으로 현장 디바이스(엣지 레이어)가 자율적 환경 제어 로직을 수행하고, 클라우드 관제 서버는 데이터 집계·시각화·원격 파라미터 조정을 담당하는 하이브리드 2-Tier 아키텍처를 채택한다. 센서 데이터 수집·저장·처리·변환 로직은 엣지에 내재화한다. |
| **근거(Rationale)**      | ① 농촌 환경의 WAN 불안정성 대응을 위한 오프라인 자율제어 필수 ② OSHP 표준 채택으로 다양한 센서·액추에이터 벤더 간 상호운용성 확보 ③ 엣지에서 1차 전처리 후 요약 데이터만 업링크하여 클라우드 전송 비용 절감 ④ 재배 환경 조건(작물별 온습도 프로파일)은 로컬 실행으로 응답 지연(latency) 최소화               |
| **결과(Consequences)**   | (+) 통신 장애 시에도 온실 환경 제어 연속성 보장 / (+) 클라우드에서 영농 관리 서버·웹앱을 통한 다중 농가 통합 관제 가능 / (+) KC 인증 등 제품화 경로에서 디바이스 단위 검증 가능 / (-) 엣지 디바이스와 클라우드 간 상태 동기화 복잡도 증가 / (-) 펌웨어 및 제어 로직의 이중 유지보수 부담               |
| **트레이드오프(Trade-offs)** | **얻는 것:** 고가용성·저지연 제어·벤더 독립성 / **감수할 것:** 엣지-클라우드 데이터 정합성 관리 복잡도, 디바이스 현장 배포·업데이트(OTA) 운영 비용 증가                                                                                                |

### ADR-002: 데이터 파이프라인 — 센서 수집·저장·처리·변환의 레이어드 로직 분리 설계

| 항목                     | 내용                                                                                                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 온실 내 다종 센서(온도·습도·CO₂·EC·pH·광량 등)에서 발생하는 고빈도 시계열 데이터를 수집하여 재배 환경 판단에 활용해야 한다. 원시 데이터를 그대로 클라우드로 전송하면 대역폭 낭비와 스토리지 비용이 급증한다.                                                              |
| **결정(Decision)**       | 데이터 처리를 수집(Ingestion) → 저장(Storage) → 처리(Processing) → 변환(Transformation) 4단계로 레이어 분리한다. 엣지에서 이상값 필터링·집계(aggregation)를 수행한 후, 클라우드 영농 관리 서버에서 분석·시각화용 데이터로 변환한다. 사용자 웹/앱은 변환된 결과만 소비한다. |
| **근거(Rationale)**      | ① 관심사 분리(Separation of Concerns)로 각 레이어 독립 교체 가능 ② 샘플 추출 및 생육 상태 비교 검증 단계에서 정제된 데이터 품질 보장 ③ 환경제어 시스템 성능평가 시 계층별 병목 구간 식별 용이                                                             |
| **결과(Consequences)**   | (+) 클라우드 전송량 감소로 운영 비용 절감 / (+) 데이터 품질 관리 포인트 명확화 / (-) 엣지 디바이스에 처리 로직 탑재로 하드웨어 사양 요건 상승                                                                                                |
| **트레이드오프(Trade-offs)** | **얻는 것:** 확장성·비용 효율·데이터 품질 / **감수할 것:** 엣지 디바이스 단가 상승, 전처리 로직 버전 관리 필요                                                                                                                  |

### ADR-003: 사용자 인터페이스 — 웹/앱 통합 UI/UX 단일 코드베이스 전략

| 항목                     | 내용                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 농업인(비IT 전문가)이 PC·모바일 환경 모두에서 온실 환경 모니터링 및 제어 명령을 내릴 수 있어야 한다. 별도 네이티브 앱과 웹을 이중 개발하면 유지보수 비용이 배증된다.                     |
| **결정(Decision)**       | 반응형 웹 기반 단일 코드베이스로 사용자 웹/앱을 통합 개발하고, UI/UX 설계 단계에서 농업인 맥락(저조도 환경, 장갑 착용 등)을 반영한 대형 터치 타겟·고대비 디자인을 적용한다.                |
| **근거(Rationale)**      | ① 중소형 스마트팜 보급형 시스템이므로 개발·운영 비용 최소화 필수 ② PWA(Progressive Web App) 구조로 오프라인 캐싱 지원 가능 ③ 영농 관리 서버의 데이터 시각화와 UI를 동일 스택으로 통합 |
| **결과(Consequences)**   | (+) 단일 배포 파이프라인으로 유지보수 단순화 / (+) KC 인증 시 소프트웨어 검증 범위 축소 / (-) 네이티브 앱 대비 기기 센서·푸시 알림 접근 제약 가능성                          |
| **트레이드오프(Trade-offs)** | **얻는 것:** 개발 효율·배포 단순성 / **감수할 것:** 일부 플랫폼 고유 기능(백그라운드 알림 등) 구현 복잡도                                                    |

⚠️ 잠재적 위험 분석
------------

### 1. 엣지-클라우드 데이터 불일치(State Divergence)로 인한 오제어 위험

* **설명:** 네트워크 단절 구간 동안 엣지 디바이스가 로컬 제어 로직으로 환경을 변경한 후 재연결 시, 클라우드 관제 서버의 상태값과 충돌하여 이중 제어 명령이 발생할 수 있다. 예를 들어 온실 가습기가 엣지에 의해 이미 작동 중인데 클라우드가 동일 명령을 재발송하여 과습 피해가 발생하는 시나리오.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Last-Write-Wins 또는 엣지 우선(Edge-First) 충돌 해소 정책을 OSHP 프로토콜 레벨에서 명세화한다. 재연결 시 엣지가 현재 액추에이터 상태를 클라우드로 먼저 동기화(State Reconciliation)한 후 명령을 수신하는 핸드셰이크 절차를 의무화한다. 상태 변경 이력은 타임스탬프 기반 이벤트 로그로 영속 저장한다.

### 2. 엣지 디바이스 펌웨어 OTA 업데이트 실패로 인한 제어 불능

* **설명:** 보급형 중소형 스마트팜 특성상 농가에 수십~수백 대의 엣지 디바이스가 분산 배포된다. OTA 업데이트 도중 전원 차단·통신 오류가 발생하면 펌웨어가 벽돌(brick) 상태가 되어 온실 환경 제어가 완전 중단될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** A/B 파티션 이중화 펌웨어 구조를 채택하여 업데이트 실패 시 자동 롤백을 보장한다. 업데이트는 농번기 외 야간 시간대에 단계적 배포(Canary Release) 방식으로 진행하고, 업데이트 전 현재 제어 파라미터를 NVRAM에 스냅샷 저장한다. 현장 물리 복구를 위한 시리얼 콘솔 접근 방법을 매뉴얼화한다.

### 3. 단일 클라우드 영농 관리 서버의 가용성 장애(SPoF)

* **설명:** 영농 관리 서버가 단일 인스턴스로 운영될 경우, 서버 장애·클라우드 리전 이슈 발생 시 다수 농가의 모니터링·원격 제어·알림이 동시에 불가능해진다. 특히 병해충 긴급 방제나 이상기후 대응이 필요한 임계 시점에 관리 공백이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 영농 관리 서버를 멀티 AZ(Availability Zone) 구성으로 이중화하고, 헬스체크 기반 자동 장애 조치(Auto Failover)를 적용한다. 엣지 디바이스는 클라우드 장애 시에도 로컬 알림(부저·LED)을 통해 농업인에게 이상 상태를 통보할 수 있는 독립 경보 로직을 탑재한다.

### 4. OSHP 프로토콜 표준 미성숙 또는 벤더 Lock-in 위험

* **설명:** OSHP가 스마트팜 분야에서 충분히 성숙하지 않았거나 국내 농업 환경에 특화된 표준 지원이 부족할 경우, 특정 센서·액추에이터 벤더의 독점 프로토콜 의존이 발생한다. 이후 해당 벤더 단종·가격 인상 시 전체 시스템 교체 비용이 급증한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** OSHP 드라이버 레이어를 추상화 인터페이스(HAL: Hardware Abstraction Layer)로 격리 설계하여, 프로토콜 교체 시 상위 제어 로직 변경을 최소화한다. MQTT·Modbus·BACnet 등 복수 프로토콜 어댑터를 플러그인 구조로 지원하고, 국가 스마트팜 표준(농림축산식품부 스마트팜 다부처 패키지 사업 표준 규격)과의 정합성을 사전 검토한다.

### 5. 센서 데이터 위변조 및 무인가 제어 명령 주입(사이버보안 위협)

* **설명:** 클라우드-엣지 간 통신 구간 또는 사용자 웹/앱 API가 적절히 암호화·인증되지 않을 경우, 공격자가 허위 센서값을 주입하거나 무단 제어 명령(히터 강제 작동, 환기 차단 등)을 발송하여 작물 피해를 야기할 수 있다. 보급형 IoT 디바이스는 일반적으로 보안 리소스가 제한적이다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 디바이스-클라우드 간 상호 인증을 X.509 인증서 기반 mTLS로 구현하고, 디바이스별 고유 식별자(Device Identity)를 하드웨어 보안 모듈(TPM/SE)에 저장한다. API 게이트웨이에서 JWT 기반 인가 및 요청 속도 제한(Rate Limiting)을 적용한다. 제어 명령에는 서명(HMAC)을 의무화하여 명령 무결성을 검증하고, KC 인증 과정에서 IEC 62443 산업 사이버보안 요건을 준용한다.

### 6. 생육 단계별 환경 제어 파라미터의 부정확성으로 인한 수확량 손실

* **설명:** 샘플 추출 및 생육 상태 비교 검증 단계에서 수집된 데이터가 통계적으로 불충분하거나 작물 품종별 특성이 제어 로직에 반영되지 않으면, 환경 제어 시스템이 최적 조건이 아닌 표준 조건으로 운영되어 생산성 저하가 발생한다. 특히 작물 재배 환경 조건이 작물 재배 주기 내에 동적으로 변해야 하나, 정적 파라미터로 고정 운영될 위험이 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 환경 제어 로직에 생육 단계(발아→육묘→정식→수확) 상태 머신(State Machine)을 도입하고, 각 단계별 환경 프로파일을 클라우드에서 동적으로 내려받아 엣지에 적용하는 파라미터 프로비저닝 체계를 구축한다. 온실 환경제어 시스템 성능평가 결과를 피드백 루프로 연결하여 파라미터를 점진적으로 최적화하는 데이터 기반 개선 프로세스를 제도화한다.
