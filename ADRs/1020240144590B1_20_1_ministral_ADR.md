## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈화된 프로세스 제어 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **알밥기 공정 → 재리 투입 공정 → 톱밥 공급/교체 공정 → 질식 공정 → 출하**의 순차적 프로세스를 요구하며, 각 공정은 독립적 제어와 데이터 통합이 필요함. 또한 IoT 표준 준수와 확장성, 보안이 필수적임. |
| **결정(Decision)** | 1) **모듈화된 마이크로 서비스 아키텍처**를 채택하여 각 공정을 독립적 서비스 단위로 분리
2) **IoT 플랫폼 기반 통합 제어**를 도입하여 프로세스 간 데이터 공유와 원격 모니터링 지원
3) **MQTT 프로토콜**을 사용하여 실시간 데이터 통신 구현
4) **ISO/IEC 30141:2024** 및 **ITU-T X.1352** 표준을 준수하여 보안과 상호운용성 확보 |
| **근거(Rationale)** | - **모듈화**는 개별 공정의 독립적 업데이트와 확장성을 가능하게 함
- **MQTT**는 IoT 환경의 경량 통신 요구에 적합하며, **IoT 플랫폼**은 프로세스 간 데이터 통합을 효율적으로 지원
- **표준 준수**는 글로벌 시장에서의 상호운용성과 보안 인증을 보장함 |
| **결과(Consequences)** | ✅ **장점**: 확장성, 유지보수 용이성, 표준 준수, 실시간 모니터링 가능
❌ **단점**: 초기 구축 비용 증가, 서비스 간 동기화 복잡성 |
| **트레이드오프(Trade-offs)** | - **초기 비용 vs. 장기적 확장성**: 모듈화 아키텍처는 초기 구축 비용이 높지만 장기적으로 시스템 확장과 유지보수 비용을 절감
- **실시간성 vs. 보안**: MQTT는 실시간성을 제공하지만, **TLS 인증**을 통해 보안 위험을 완화 |

### **ADR-002: 에지 컴퓨팅 기반 로컬 제어 노드 구현**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 각 공정(알밥기, 재리 투입 등)은 **고신뢰성**과 **저지연** 제어가 요구되며, 클라우드 전송 지연으로 인한 문제 발생 가능성 존재 |
| **결정(Decision)** | 1) **에지 컴퓨팅 노드**를 각 공정에 배포하여 로컬 제어 및 데이터 전처리 수행
2) **OPC UA 프로토콜**을 사용하여 공정 데이터 표준화 및 안전한 통신 지원
3) **로컬 데이터 캐싱**을 통해 네트워크 장애 시에도 운영 가능성 확보 |
| **근거(Rationale)** | - **에지 컴퓨팅**은 실시간 제어 요구에 적합하며, 네트워크 지연 문제를 해결
- **OPC UA**는 산업용 IoT 환경의 표준 프로토콜로 보안과 상호운용성을 제공
- **로컬 캐싱**은 고가용성을 보장함 |
| **결과(Consequences)** | ✅ **장점**: 저지연 제어, 네트워크 독립성, 고신뢰성
❌ **단점**: 에지 노드 관리 복잡성 증가, 초기 하드웨어 비용 |
| **트레이드오프(Trade-offs)** | - **중앙 집중형 vs. 분산형 제어**: 에지 컴퓨팅은 분산 제어를 통해 신뢰성을 높지만, 중앙 관리 시스템이 필요함
- **하드웨어 비용 vs. 성능**: 에지 노드는 성능을 높일 수 있지만, 추가 하드웨어 투자가 필요 |

### **ADR-003: 보안 및 접근 제어 정책 구현**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **공정 데이터의 기밀성**, **무결성**, **가용성**이 필수적이며, **ETSI EN 303 645** 및 **ISO/IEC 27030:2020** 표준 준수가 요구됨 |
| **결정(Decision)** | 1) **역할 기반 접근 제어 (RBAC)**를 도입하여 사용자/시스템 권한 관리
2) **블록체인 기반 로그 감사**를 통해 데이터 무결성 검증
3) **하드웨어 보안 모듈 (HSM)**을 사용하여 암호화 키 관리
4) **네트워크 세그먼테이션**을 통해 공정 간 격리 |
| **근거(Rationale)** | - **RBAC**는 접근 제어를 세밀하게 관리할 수 있음
- **블록체인 로그**는 변경 불가능한 감사 기록을 제공
- **HSM**은 암호화 키를 물리적으로 보호함
- **네트워크 세그먼테이션**은 보안 위협 범위를 최소화 |
| **결과(Consequences)** | ✅ **장점**: 고도의 보안, 규정 준수, 데이터 무결성
❌ **단점**: 복잡한 보안 관리, 성능 오버헤드 |
| **트레이드오프(Trade-offs)** | - **보안 vs. 성능**: HSM과 블록체인은 보안을 강화하지만, 시스템 성능에 영향을 줄 수 있음
- **중앙 관리 vs. 분산 보안**: RBAC는 중앙에서 관리하기 용이하지만, 에지 노드 보안도 중요함 |

## ⚠️ 잠재적 위험 분석

### **1. 시스템 통합 실패 위험**
- **설명**: 모듈화된 서비스 간 데이터 동기화 실패로 인해 프로세스 중단 발생 (예: 톱밥 공급 공정과 질식 공정 간 데이터 불일치)
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 드리븐 아키텍처** 도입 (예: Kafka를 사용하여 서비스 간 이벤트 기반 통신)
  - **자동화된 데이터 검증 메커니즘** 구현 (예: 체크섬, 디지털 서명)

### **2. 에지 노드 장애로 인한 공정 중단**
- **설명**: 에지 컴퓨팅 노드 하드웨어故障로 로컬 제어 실패 → 공정 정지
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **고가용성 클러스터링** (예: 에지 노드 중복 배포)
  - **폴백 메커니즘** 구현 (예: 클라우드 제어로의 자동 전환)

### **3. 보안 취약점 공격**
- **설명**: IoT 디바이스 취약점 (예: MQTT/TLS 구현 오류)으로 인해 데이터 도난 또는 공정 조작
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **정기적 보안 패치** 및 취약점 스캔 자동화
  - **네트워크 인트루전 감지 시스템 (IDS)** 배포
  - **공정 로그 암호화** 강화

### **4. 표준 준수 미비로 인한 상호운용성 문제**
- **설명**: 새로운 디바이스/시스템 통합 시 **ISO/IEC 30141** 또는 **oneM2M** 표준 미준수로 인해 호환성 실패
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **표준 준수 테스트 자동화** (예: CI/CD 파이프라인에 표준 검증 스텝 추가)
  - **API 게이트웨이**를 통해 표준화된 인터페이스 제공

### **5. 데이터 일관성 문제**
- **설명**: 분산 시스템에서 발생하는 **경합 조건**으로 인해 공정 데이터 불일치 (예: 톱밥 공급량 오류)
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **분산 트랜잭션 관리** (예: Saga 패턴 또는 2PC 프로토콜)
  - **데이터 버전 관리** 시스템 도입

### **6. 운영 복잡성 증가**
- **설명**: 모듈화 및 에지 컴퓨팅 도입으로 인한 **운영 및 유지보수 복잡성** 상승
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **자동화된 모니터링 및 로깅** (예: Prometheus + Grafana)
  - **운영 가이드라인 문서화** 및 팀 교육 강화
