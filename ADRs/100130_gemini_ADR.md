# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 디폴트 및 확장 모듈 분리를 통한 환경 영향도 분석 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 온습도와 같은 기본 환경 변수 외에도, 다양한 외부 요인(미세먼지, 강수 등)이 환경 지수에 미치는 영향을 유연하게 반영해야 함. 모든 로직이 제어부(130)에 집중될 경우 시스템 복잡도가 증가하고 유지보수가 어려워짐. |
| **결정(Decision)** | 표준화된 환경 지수를 처리하는 '디폴트 모듈(150)'과 가변적인 추가 요인을 처리하는 '확장 모듈(160)'을 물리적/논리적으로 분리하고, 제어부(130)가 이를 통합 관리하는 모듈형 아키텍처를 설계함. |
| **근거(Rationale)** | 기본 온습도 지수(152)는 변동성이 적으나 추가 영향 지수(162)는 산업군이나 지역에 따라 요구사항이 수시로 변경됨. 모듈 분리를 통해 개별 컴포넌트의 독립적인 업데이트와 확장이 가능해짐. |
| **결과(Consequences)** | 시스템의 확장성(Scalability)과 유연성이 크게 향상됨. 새로운 분석 모델 추가 시 기존 디폴트 로직을 수정하지 않고도 확장 모듈 및 전용 데이터베이스(164)만 추가/수정하여 신속한 대응이 가능함. |
| **트레이드오프(Trade-offs)** | 모듈 간 데이터 동기화 및 제어부(130)의 오케스트레이션 부하가 발생할 수 있으며, 전체적인 시스템 인터페이스 설계의 복잡도는 단일 모듈 방식보다 높음. |

---

## ⚠️ 잠재적 위험 분석

### 1. 데이터 정합성 불일치 위험
- **설명:** 환경 정보 데이터베이스(120), 온습도 영향도 DB(154), 추가 영향도 DB(164) 간의 기준 정보(Master Data)가 일치하지 않아 분석 결과에 오류가 발생하는 시나리오
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 중앙 집중식 마스터 데이터 관리(MDM) 체계를 구축하고, 각 DB 업데이트 시 트랜잭션 일관성을 보장하는 검증 로직 도입

### 2. 제어부(130)의 단일 장애점(SPOF) 위험
- **설명:** 모든 입력(110), 출력(140) 및 모듈(150, 160) 연산이 제어부를 통과하므로, 제어부 장애 시 전체 시스템이 마비되는 현상
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** 제어부의 이중화(Active-Standby 또는 Active-Active) 구성을 통해 가용성을 확보하고 부하 분산 처리

### 3. 확장 모듈 연산 지연에 따른 실시간성 저하
- **설명:** 확장 모듈(160)에서 복잡한 추가 영향 지수를 계산하는 과정에서 지연이 발생하여 출력부(140)의 정보 갱신 속도가 늦어지는 시나리오
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 비동기 메시지 큐(Message Queue)를 도입하여 연산을 분리하고, 계산된 지수를 캐싱(Caching)하여 응답 속도 최적화

### 4. 입력 데이터 오염 및 무결성 훼손
- **설명:** 환경 정보 입력부(110)를 통해 잘못된 센서 데이터나 비정상적인 값이 유입되어 분석 결과 전체의 신뢰성이 하락하는 시나리오
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 입력 단계에서 이상치 탐지(Outlier Detection) 알고리즘 및 데이터 유효성 검증 필터를 적용

### 5. 모듈 간 인터페이스 호환성 문제
- **설명:** 디폴트 모듈이나 확장 모듈의 인터페이스 사양이 변경되었을 때, 이를 참조하는 제어부와의 프로토콜 불일치로 시스템이 오동작하는 시나리오
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
