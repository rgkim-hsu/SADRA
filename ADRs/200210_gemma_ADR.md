# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 계층형 산업 IoT 플랫폼 및 데이터 페더(Data Fabric) 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 농업 생산자(다양한 레거시 장비/센서), 서비스 제공자(다양한 분석 모델), 유통 경로(물리적 이동)를 포괄하는 복합적인 산업 생태계입니다. 이로 인해 각 단계별 데이터를 처리하는 프로토콜, 데이터 모델, 운영 표준이 극도로 파편화되어 있어(Data Silo), 단일하고 상호 운용 가능한 데이터 레이어 구축이 가장 큰 아키텍처적 난제입니다. |
| **결정(Decision)** | 시스템의 중앙 코어에 개방형 표준 기반의 '계층형 IoT 플랫폼 아키텍처'를 구축하고, 이를 기반으로 모든 데이터 소스를 연결하는 '데이터 페더(Data Fabric)' 패턴을 채택합니다. 이 플랫폼은 클라우드-엣지-서비스 계층으로 분리하며, 모든 통신은 API 게이트웨이를 통해 엄격하게 관리됩니다. |
| **근거(Rationale)** | **1. 상호운용성 확보:** ISO/IEC 30141과 oneM2M과 같은 국제 표준 아키텍처 프레임워크를 준수하여, 장비의 제조사나 시스템의 종류에 관계없이 데이터를 수집하고 표준화할 수 있습니다. **2. 확장성 및 탄력성:** 마이크로 서비스(Microservices) 아키텍처를 채택하여, 수요 예측, 물류, 트레이서빌리티 등 특정 기능의 변화나 확장이 전체 시스템에 영향을 주지 않도록 모듈화합니다. **3. 보안 강화:** 엣지 단(Edge)에서 데이터 처리 및 게이트웨이를 통한 인증/인가를 필수화하여, 물리적 환경에서 발생할 수 있는 보안 취약점을 최소화합니다. |
| **결과(Consequences)** | **[긍정적]:** 모든 계층에서 데이터 표준화가 가능해지며, 새로운 산업 요구사항(예: 기후 변화 모델링)이 발생해도 플랫폼을 통해 유연하게 통합할 수 있습니다. **[부정적]:** 초기 구축 단계에서 모든 컴포넌트와 인터페이스의 표준화 및 게이트웨이 개발에 막대한 시간과 비용이 소요됩니다. |
| **트레이드오프(Trade-offs)** | **[장점]:** 최고 수준의 **상호운용성(Interoperability)**과 **미래 확장성(Future-Proofing)**을 확보하여 시장 선도적 지위를 구축합니다. **[감수할 단점]:** 시스템 아키텍처의 복잡도가 매우 높아져, 초기 설계 및 통합 관리가 어려우며, 숙련된 전문 인력(DevOps, Cloud Native 전문가)이 필수적입니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 사일로 및 프로토콜 불일치 위험 (Technical Risk)
- **설명:** 생산자 현장에는 수많은 레거시 센서, 장비(PLC, 아날로그 센서 등)가 사용되며, 이들은 서로 다른 프로토콜(Modbus, CAN, LoRaWAN, ZigBee 등)을 사용합니다. 이로 인해 데이터가 통일된 형식으로 통합되지 못하고 시스템 내에 '사일로'로 남아 분석가들이 종합적인 의사 결정을 내리기 어렵게 만듭니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:**
    *   **게이트웨이 표준화:** 모든 엣지 레벨에 '산업 IoT 게이트웨이'를 의무적으로 도입하고, 이 게이트웨이를 통해 모든 데이터를 표준화된 데이터 포맷(예: JSON 또는 Avro)과 표준화된 메시징 프로토콜(예: MQTT)로 변환하는 데이터 변환 레이어(ETL/ELT)를 구축해야 합니다.
    *   **데이터 모델링:** 시스템 초기 단계에서부터 온톨로지(Ontology) 기반의 통합 데이터 모델을 정의하여, 모든 데이터 요소가 공통의 의미 체계를 따르도록 합니다.

### 2. 엣지 디바이스 보안 취약성 위험 (Security Risk)
- **설명:** 농장 현장의 센서 및 제어 장치(Actuator)는 네트워크 접근성이 낮거나 물리적으로 보호하기 어렵습니다. 해커가 물리적 접근을 통해 장치에 악성 코드를 주입하거나 통신 채널을 가로채는 경우(Man-in-the-Middle), 수확량 데이터 조작, 환경 제어 시스템(온습도, 관개)의 오작동을 유발하여 막대한 피해를 줄 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **하드웨어 보안:** 신뢰할 수 있는 하드웨어 모듈(TPM, Secure Element)을 모든 게이트웨이에 탑재하여 부팅 과정부터 무결성을 검증합니다.
    *   **통신 암호화:** 엣지 레벨부터 클라우드까지 모든 통신 구간을 TLS/DTLS 프로토콜을 이용하여 종단 간 암호화(End-to-End Encryption)합니다.
    *   **분산 인증:** 모든 엣지 디바이스에 고유의 디지털 인증서(Certificates)를 부여하고, 중앙 인증서 관리 시스템(PKI)을 통해 주기적으로 검증합니다.

### 3. 데이터 주권 및 소유권 불명확성 위험 (Operational/Legal Risk)
- **설명:** 공급망의 여러 주체(농가, 서비스 제공업체, 유통업체, 플랫폼 운영자)가 데이터를 생산, 공유, 이용하는 과정에서, 특정 데이터(예: 특정 농가의 생산량 패턴, 특정 유통업체의 판매 경로 데이터)의 소유권과 이용 범위를 명확히 합의하지 못할 경우, 법적 분쟁이나 데이터 활용의 제약이 발생하여 시스템의 신뢰도를 저해합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **데이터 거버넌스 체계 구축:** 프로젝트 초기 단계에 모든 이해관계자(Stakeholder)가 참여하는 데이터 거버넌스 위원회를 구성합니다.
    *   **계약 기반 정의:** 데이터의 유형별(Source, Owner, Use-case) 이용 목적, 이용 범위, 수익 분배 기준을 계약서에 명확히 명시하고, 이를 시스템 접근 제어(Access Control) 로직에 반영합니다.

### 4. 시스템 복잡성에 따른 운영 및 유지보수 실패 위험 (Operational Risk)
- **설명:** 20년 경력의 수석 아키텍트가 설계한 것처럼 매우 크고 복잡한 마이크로 서비스 기반의 플랫폼은, 실제 운영 단계에서 특정 모듈의 장애가 전체 시스템의 연쇄 장애를 유발할 수 있습니다. 또한, 다양한 기술 스택(AI/ML, IoT, 클라우드, 백엔드)을 가진 전문 인력이 필요하기 때문에, 유지보수 인력의 이탈 시 운영 공백이 발생할 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    *   **관제 시스템 도입:** 전체 플랫폼 상태를 한눈에 모니터링하고 이상 징후를 자동으로 탐지하는 통합 관제 시스템(Monitoring Dashboard)을 구축하여 운영 가시성을 극대화합니다.
    *   **문서화 및 지식 공유:** 모든 컴포넌트와 인터페이스에 대해 상세한 API 명세 및 운영 매뉴얼을 작성하고, 표준화된 CI/CD 파이프라인을 통해 지식 축적을 체계화합니다.

### 5. 표준화 실패로 인한 글로벌 진출 제한 위험 (Business Risk)
- **설명:** 시스템 아키텍처가 국내의 특정 표준이나 비표준 방식으로만 구현될 경우, 글로벌 시장 진출 시 필수적으로 요구되는 국제 표준(예: ISO/IEC 30141, oneM2M, Matter 등)과 상호운용성을 인정받지 못하여 시장 확장에 제약을 받을 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:**
    *   **최초 설계 표준 준수:** 아키텍처 설계 초기 단계부터 국제 표준 아키텍처 프레임워크(Reference Architecture)를 최우선으로 적용하여, 특정 기술이나 지역에 종속되지 않도록 합니다.
    *   **표준 인증 선점:** 시스템의 핵심 모듈(특히 데이터 인터페이스 및 보안 모듈)에 대해 관련 국제 표준 인증(예: TTA/KISA 인증, Matter 인증 등) 획득 로드맵을 수립하고 예산에 반영합니다.
