📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 멀티 프로토콜 하이브리드 디바이스 디스커버리 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 Bluetooth, Wi-Fi, Data Matrix(바코드) 등 다양한 통신 방식을 사용하는 IoT 디바이스가 혼재한다. 단일 프로토콜로는 농장 내 다양한 센서·액추에이터(온습도 센서, 관개 제어기, 환경 모니터링 장비 등)를 통합 탐색하는 것이 불가능하며, 특히 글로벌 농식품 비즈니스 에코시스템(IoF2020 표준 기반)에서는 다국적 장비 호환성이 필수적이다.                                                                |
| **결정(Decision)**       | 모바일 앱 단계 ②에서 Bluetooth Scan(②-1), Data Matrix Scan(②-2), Wi-Fi Scan(②-3)을 병렬적으로 수행하는 멀티 프로토콜 하이브리드 디스커버리 레이어를 채택한다. 탐색된 디바이스는 단계 ③의 Service 리스트로 통합 출력되며, 단계 ④에서 WebView 기반 서비스 연결로 최종 처리된다. 언어·국가 설정(단계 ①)을 선행하여 글로벌 다국어 환경을 지원한다.                                                    |
| **근거(Rationale)**      | IoF2020 표준은 이기종 IoT 디바이스 간 상호운용성(Interoperability)을 핵심 요건으로 규정한다. Bluetooth는 근거리 저전력 센서 노드에, Wi-Fi는 데이터 처리량이 높은 게이트웨이 장비에, Data Matrix는 물리적 장비 식별(자산 추적, GS1 표준 연계)에 각각 최적화되어 있어 세 프로토콜의 병렬 운용이 커버리지와 신뢰성을 극대화한다. WebView 기반 최종 연결은 네이티브 앱 업데이트 없이 서비스 UI를 갱신 가능하게 하여 다국적 배포 비용을 절감한다. |
| **결과(Consequences)**   | **긍정적:** 단일 앱으로 Bluetooth·Wi-Fi·바코드 기반 스마트팜 장비를 모두 온보딩 가능. 글로벌 농식품 공급망(한국·유럽 등)에서 동일한 앱으로 현지 언어 및 장비 표준 대응. **부정적:** 세 가지 스캔 모듈의 동시 동작으로 모바일 기기의 배터리 및 CPU 부하 증가. WebView 의존도가 높아 오프라인 환경(농장 음영 지역)에서 서비스 연결 단절 위험 상존.                                                                 |
| **트레이드오프(Trade-offs)** | **얻는 것:** 디바이스 호환성 극대화, 글로벌 표준(IoF2020·GS1) 준수, 서비스 레이어 유연성. **감수해야 할 것:** 앱 복잡도 증가로 인한 유지보수 비용 상승, 멀티 스캔 동시 실행 시 UX 응답 지연, WebView 보안 취약점 노출 가능성.                                                                                                                                     |

### ADR-002: WebView 기반 서비스 연결 및 URL 값 처리 분기 설계

| 항목                     | 내용                                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 단계 ③에서 출력된 Service 리스트의 항목 값이 URL인 경우와 비-URL인 경우가 존재하며, URL일 때는 WebView로 직접 렌더링하는 분기 처리가 필요하다. 스마트팜 서비스는 클라우드 대시보드, 로컬 게이트웨이 웹 UI 등 다양한 엔드포인트를 가질 수 있다. |
| **결정(Decision)**       | Service 리스트 항목의 값이 URL인 경우 WebView로 바로 라우팅하는 조건 분기를 앱 내 네비게이션 레이어에 구현한다. 비-URL 값의 경우 별도 네이티브 핸들러로 처리한다(개념도 상 "값이 url 일 경우" 분기선 참조).                     |
| **근거(Rationale)**      | IoT 서비스의 엔드포인트는 클라우드 SaaS URL, 로컬 IP 기반 게이트웨이 주소 등 다양하게 존재한다. WebView 분기는 서비스 제공자가 앱 업데이트 없이 UI를 독립적으로 배포할 수 있게 하여 글로벌 에코시스템의 빠른 서비스 변경에 대응한다.          |
| **결과(Consequences)**   | **긍정적:** 서비스 엔드포인트 변경 시 앱 재배포 불필요, 다양한 파트너사 서비스 통합 용이. **부정적:** WebView 내 외부 URL 로드로 인한 피싱·악성 페이지 노출 위험.                                                |
| **트레이드오프(Trade-offs)** | **얻는 것:** 서비스 민첩성, 파트너 생태계 확장성. **감수해야 할 것:** URL 유효성 검증 및 화이트리스트 관리 부담, WebView 보안 정책 강화 필요.                                                           |

⚠️ 잠재적 위험 분석
------------

### 1. Bluetooth/Wi-Fi 동시 스캔으로 인한 전파 간섭 및 디스커버리 실패

* **설명:** 스마트팜 시설 내에서 Bluetooth와 Wi-Fi가 동일한 2.4GHz 대역을 공유하는 경우, 두 스캔 모듈이 동시에 동작하면 상호 간섭이 발생하여 디바이스 탐색 실패율이 높아진다. 특히 대형 유리온실이나 금속 구조물이 많은 환경에서는 신호 감쇄가 심화된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** Bluetooth 5.0 이상(2.4GHz/1M PHY)과 Wi-Fi 6(6GHz 대역) 조합으로 대역 분리 설계. 스캔 스케줄링 알고리즘을 도입하여 시간 분할(TDMA 방식) 스캔 수행. 재시도(Retry) 로직과 스캔 타임아웃 값을 환경별로 튜닝 가능하도록 설정 파라미터화.

### 2. WebView 기반 서비스 연결의 보안 취약점 (XSS·피싱·오픈 리다이렉트)

* **설명:** 단계 ④에서 Service 리스트의 URL 값을 검증 없이 WebView에 로드할 경우, 악의적인 URL이 Service 리스트에 삽입되거나 중간자 공격(MITM)으로 URL이 변조되어 농장 운영자가 피싱 페이지에 노출될 수 있다. 스마트팜 제어 인터페이스가 탈취되면 관개·환경 제어 시스템의 오작동을 유발할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** URL 화이트리스트 정책 적용 및 정규식 기반 URL 유효성 검증 로직 구현. WebView에 `setAllowFileAccess(false)`, `setJavaScriptEnabled` 최소 권한 원칙 적용. 서비스 연결 시 TLS 1.3 강제 및 인증서 피닝(Certificate Pinning) 적용. Service 리스트 서버와의 통신에 HMAC 서명 검증 도입.

### 3. Data Matrix(바코드) 스캔 데이터의 위변조 및 스푸핑

* **설명:** 스마트팜 현장에서 장비에 부착된 Data Matrix 코드가 물리적으로 교체되거나 복사 출력된 위조 코드로 대체될 경우, 앱이 비인가 디바이스를 정상 디바이스로 인식하여 서비스 리스트에 등록할 수 있다. 이는 공급망 위변조 시나리오와 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Data Matrix 내 디바이스 고유 서명값(PKI 기반 디지털 서명) 포함 및 서버 측 검증 프로세스 구축. GS1 표준의 SGTIN(Serialised Global Trade Item Number) 체계와 연계하여 공급망 무결성 확보. 물리적 보안을 위해 홀로그램 씰 또는 탬퍼-에비던트 라벨 병행 적용.

### 4. 오프라인·네트워크 음영 환경에서의 서비스 연결 불가

* **설명:** 스마트팜 시설은 산간·농촌 지역에 위치하는 경우가 많아 LTE/5G 커버리지가 불안정하다. WebView 기반 서비스 연결(단계 ④)은 인터넷 연결을 전제로 하므로, 네트워크 단절 시 서비스 리스트 로딩 실패 및 원격 모니터링 중단이 발생한다. 관개 자동화 등 실시간 제어가 필요한 상황에서 치명적일 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 로컬 게이트웨이(Edge Gateway) 도입으로 로컬 IP 기반 오프라인 서비스 운영 구조 설계. Service 리스트 및 마지막 정상 상태 데이터를 앱 로컬 캐시(SQLite/Room DB)에 저장하는 오프라인 퍼스트(Offline-First) 전략 적용. MQTT·CoAP 등 경량 메시징 프로토콜을 로컬 Fallback 통신 채널로 병행 구성.

### 5. 다국어·다국가 설정 오류로 인한 디바이스 식별 실패

* **설명:** 단계 ①에서 언어·국가 설정이 잘못 선택되거나, 설정 값이 이후 Bluetooth/Wi-Fi 스캔의 디바이스명 인코딩 처리에 영향을 미칠 경우 비ASCII 문자(한국어, 유럽 특수문자 등)로 구성된 디바이스 이름이 깨지거나 누락될 수 있다. 글로벌 에코시스템에서 다국가 장비가 혼재하는 환경에서 발생 빈도가 높다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 디바이스명 및 서비스 리스트 데이터를 UTF-8로 표준화 처리하고, 언어 설정과 독립적으로 동작하도록 인코딩 레이어 분리. 국가별 로케일(Locale) 설정과 디바이스 스캔 로직을 디커플링 설계. IoF2020 표준의 다국어 메타데이터 스키마(JSON-LD 또는 ISO 11179 기반)를 디바이스 식별자 체계에 적용.

### 6. Service 리스트 서버 단일 장애점(SPOF) 및 가용성 문제

* **설명:** 단계 ③의 Service 리스트 출력이 중앙 서버에 의존하는 구조일 경우, 서버 장애 시 탐색된 모든 디바이스의 서비스 연결이 일괄 차단된다. 스마트팜의 24시간 무중단 운영 요건을 충족하지 못하며, 수확기·파종기 등 농업 크리티컬 타임에 장애 발생 시 경제적 피해가 크다.

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** Service 리스트 서버를 멀티-AZ(가용 영역) 또는 엣지 CDN 기반으로 이중화 구성. 앱 내 Service 리스트 로컬 캐싱(TTL 기반 갱신) 및 mDNS(Multicast DNS)를 활용한 로컬 서비스 자동 탐색 Fallback 구현. RTO(복구 목표 시간) 15분 이내의 DR(재해복구) 계획 수립 및 정기 훈련 시행.
