### ADR-001: 이기종 산업 데이터 소스 통합을 위한 중앙화된 데이터 허브 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜 환경에서는 MES(생산실행시스템), ERP(전사자원관리), LIMS(품질관리), Data Historian(OSIsoft PI, Honeywell, Siemens, ABB 등), MDE/Shift Logs, Excel/WIS 등 다양한 이기종 시스템이 병존한다. 각 시스템은 SQL, OPC, REST API 등 서로 다른 인터페이스를 사용하며, 데이터 포맷과 갱신 주기도 상이하다. 스마트팜 도메인에서는 여기에 더해 센서(온·습도, CO₂, 조도, 토양수분), 기상 API, 자동화 제어기(PLC/DCS)가 추가되어 통합 복잡도가 극도로 높아진다. |
| **결정(Decision)**       | dataPARC를 중심으로 하는 **단일 데이터 허브(Hub-and-Spoke) 아키텍처**를 채택한다. 모든 외부 시스템은 dataPARC의 표준 커넥터(SQL Interface, OPC Interface, API Interface)를 통해 연결되며, 하위 레이어의 Data Historian이 실시간 시계열 데이터를 수집·버퍼링하는 역할을 담당한다. 스마트팜 적용 시에는 MQTT/OPC-UA 기반 IoT 게이트웨이를 Historian 레이어에 추가 편입한다.                                                      |
| **근거(Rationale)**      | ① 각 소스 시스템의 변경이 다른 시스템에 영향을 주지 않는 **느슨한 결합(Loose Coupling)** 확보. ② OPC 인터페이스를 통한 DCS/QCS/PLC 연동은 IEC 62541(OPC-UA) 표준을 준수하여 스마트팜 제어기와의 호환성 확보. ③ 중앙 허브에서 데이터 품질 검증, 단위 변환, 태그 정규화를 일괄 처리하여 하위 분석 레이어의 부담 최소화.                                                                                                            |
| **결과(Consequences)**   | (+) 신규 데이터 소스 추가 시 허브 커넥터만 개발하면 되므로 확장성 향상. (+) 데이터 계보(Data Lineage) 추적이 단일 지점에서 가능. (-) dataPARC가 **단일 장애점(Single Point of Failure)** 이 될 위험 존재. (-) 허브 처리 용량이 병목이 될 경우 전체 데이터 파이프라인 지연 발생.                                                                                                                             |
| **트레이드오프(Trade-offs)** | **얻는 것:** 통합 관리 단순화, 표준 인터페이스 통일, 중앙 집중식 모니터링. **감수하는 것:** 허브 가용성에 대한 전체 시스템 종속, 초기 커넥터 개발 비용 증가, 허브 벤더(dataPARC) 종속성(Vendor Lock-in) 위험.                                                                                                                                                                                |

### ADR-002: OPC-UA 기반 실시간 제어 데이터와 SQL 기반 비즈니스 데이터의 계층적 분리

| 항목                     | 내용                                                                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜에서 PLC/DCS로부터 수집되는 초단위 센서 데이터(실시간성 필수)와 ERP/LIMS의 일·월 단위 경영 데이터는 데이터 특성, 갱신 주기, 보존 요건이 근본적으로 다르다. 이를 동일한 파이프라인으로 처리하면 실시간 제어 지연 및 스토리지 낭비가 발생한다.                                                                             |
| **결정(Decision)**       | **OT(Operational Technology) 레이어**와 **IT(Information Technology) 레이어**를 명확히 분리한다. Data Historian(OSIsoft PI 등)은 OT 데이터를 시계열 DB로 처리하고, ERP/MES/LIMS는 관계형 DB(SQL)로 처리한다. dataPARC는 두 레이어 간의 **컨텍스트 브리지(Context Bridge)** 역할을 수행한다. |
| **근거(Rationale)**      | IEC 62443(산업 제어 시스템 보안) 및 ISA-95(엔터프라이즈-제어 시스템 통합) 표준에 따른 계층 분리 원칙을 준수한다. 스마트팜의 환경 제어(냉난방, 관개)는 ms~초 단위 응답이 필요하므로 비즈니스 시스템의 지연이 제어 루프에 영향을 주어서는 안 된다.                                                                            |
| **결과(Consequences)**   | (+) 제어 시스템 안정성 보장. (+) 보안 경계 명확화로 OT 네트워크 격리 가능. (-) 두 레이어 간 데이터 동기화 로직 추가 필요. (-) 운영 조직이 OT/IT로 분리될 경우 협업 복잡도 증가.                                                                                                               |
| **트레이드오프(Trade-offs)** | **얻는 것:** 실시간 제어 안정성, 보안 격리, 표준 준수. **감수하는 것:** 아키텍처 복잡도 증가, 레이어 간 데이터 정합성 관리 부담.                                                                                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. dataPARC 단일 장애점(Single Point of Failure) 위험

* **설명:** dataPARC 허브 서버 장애 시 MES, ERP, LIMS, Historian 등 모든 연결 시스템과의 데이터 교환이 동시에 중단된다. 스마트팜 환경에서는 온실 환경 제어 데이터 수집이 중단되어 작물 피해로 직결될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Passive 이중화 구성(Hot Standby) 적용, Kubernetes 기반 컨테이너 오케스트레이션으로 자동 재시작 구현. 각 엣지 게이트웨이에 로컬 버퍼(SQLite/InfluxDB)를 두어 허브 장애 시에도 데이터 유실 방지(Store-and-Forward 패턴).

### 2. OPC 인터페이스 경유 사이버 보안 침해 위험

* **설명:** DCS/QCS/PLC와 dataPARC 간 OPC 인터페이스는 OT 네트워크와 IT 네트워크를 연결하는 경계에 위치한다. 이 인터페이스가 침해될 경우 공격자가 스마트팜의 관개 펌프, 환기 시스템 등 물리적 제어 장치에 무단 명령을 전송할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** IEC 62443 기반 OT/IT DMZ 구간 설치 및 단방향 데이터 다이오드(Data Diode) 적용. OPC-UA 통신에 X.509 인증서 기반 상호 인증 및 TLS 암호화 필수 적용. 이상 명령 패턴 탐지를 위한 OT 특화 IDS(Industrial Intrusion Detection System) 도입.

### 3. MDE(수동 데이터 입력) 기인 데이터 품질 오염 위험

* **설명:** Shift Logs 및 MDE를 통해 수작업으로 입력된 데이터가 오기입, 단위 오류, 누락 등으로 오염될 경우 dataPARC를 거쳐 ERP 및 분석 시스템 전체에 오염 데이터가 전파된다. 스마트팜에서는 수확량, 투입 비용 오류로 인한 잘못된 경영 의사결정으로 이어질 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** dataPARC 인입 레이어에 데이터 유효성 검증 규칙(범위 체크, 이상치 탐지, 필수값 검증) 구현. MDE 입력 UI에 자동완성 및 센서 데이터와의 교차 검증 기능 추가. 수동 입력 데이터에 별도 출처 태그(provenance tag) 부여하여 분석 시 신뢰도 가중치 차등 적용.

### 4. 벤더 종속성(Vendor Lock-in) 및 라이선스 위험

* **설명:** dataPARC, OSIsoft PI(AVEVA), Honeywell, Siemens 등 특정 벤더 솔루션에 핵심 인프라가 종속된 상태에서 라이선스 정책 변경, 가격 인상, 서비스 종료가 발생할 경우 전체 아키텍처 재구성이 불가피하다. 스마트팜 스타트업이나 중소 농가에서는 라이선스 비용이 도입 장벽이 될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 핵심 데이터 모델과 인터페이스를 오픈 표준(OPC-UA, MQTT, REST)으로 정의하여 솔루션 교체 가능성 확보. TimescaleDB, Apache Kafka 등 오픈소스 대안을 병행 검토한 이중화 전략 수립. 데이터 추출·이관 절차(Data Exit Strategy)를 계약 초기부터 명문화.

### 5. 이기종 시스템 간 데이터 시간 동기화(Timestamp Synchronization) 오류 위험

* **설명:** MES, ERP, Historian, PLC 등 각 시스템이 서로 다른 타임존, NTP 동기화 주기, 내부 클럭을 사용할 경우 dataPARC에서 데이터를 병합할 때 시간 불일치가 발생한다. 스마트팜에서 환경 이벤트(일조량 변화)와 제어 응답(차광막 작동) 간 인과관계 분석이 왜곡될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 전체 시스템에 계층적 NTP(Network Time Protocol) 서버 구성 및 PTP(IEEE 1588 Precision Time Protocol) 적용으로 ms 수준 시간 동기화 확보. dataPARC 수집 레이어에서 타임스탬프 정규화 파이프라인 구현. 시간 불일치 탐지 알람 및 이상 데이터 격리 정책 수립.

### 6. 네트워크 대역폭 부족으로 인한 실시간 데이터 지연 위험

* **설명:** 스마트팜 확장 시 수백~수천 개의 IoT 센서가 추가되면 Data Historian으로 유입되는 데이터량이 급증하여 dataPARC와의 연결 구간에서 병목이 발생한다. 특히 농촌 지역 스마트팜은 네트워크 인프라가 취약하여 클라우드 기반 ERP/MES 연동 시 지연이 심화될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 엣지 컴퓨팅(Edge Computing) 레이어를 Historian 앞단에 배치하여 로컬에서 1차 집계·필터링 수행 후 dataPARC로 전송(Edge-to-Hub 패턴). 데이터 우선순위 큐(QoS) 설정으로 제어 임계 데이터를 일반 로그 데이터보다 우선 전송. 5G/LTE 백업 회선 이중화 적용.

| **결과(Consequences)**   | (+) 제어 시스템 안정성 보장. (+) 보안 경계 명확화로 OT 네트워크 격리 가능. (-) 두 레이어 간 데이터 동기화 로직 추가 필요. (-) 운영 조직이 OT/IT로 분리될 경우 협업 복잡도 증가.                                                                                                               |
| **트레이드오프(Trade-offs)** | **얻는 것:** 실시간 제어 안정성, 보안 격리, 표준 준수. **감수하는 것:** 아키텍처 복잡도 증가, 레이어 간 데이터 정합성 관리 부담.                                                                                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. dataPARC 단일 장애점(Single Point of Failure) 위험

* **설명:** dataPARC 허브 서버 장애 시 MES, ERP, LIMS, Historian 등 모든 연결 시스템과의 데이터 교환이 동시에 중단된다. 스마트팜 환경에서는 온실 환경 제어 데이터 수집이 중단되어 작물 피해로 직결될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Passive 이중화 구성(Hot Standby) 적용, Kubernetes 기반 컨테이너 오케스트레이션으로 자동 재시작 구현. 각 엣지 게이트웨이에 로컬 버퍼(SQLite/InfluxDB)를 두어 허브 장애 시에도 데이터 유실 방지(Store-and-Forward 패턴).

### 2. OPC 인터페이스 경유 사이버 보안 침해 위험

* **설명:** DCS/QCS/PLC와 dataPARC 간 OPC 인터페이스는 OT 네트워크와 IT 네트워크를 연결하는 경계에 위치한다. 이 인터페이스가 침해될 경우 공격자가 스마트팜의 관개 펌프, 환기 시스템 등 물리적 제어 장치에 무단 명령을 전송할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** IEC 62443 기반 OT/IT DMZ 구간 설치 및 단방향 데이터 다이오드(Data Diode) 적용. OPC-UA 통신에 X.509 인증서 기반 상호 인증 및 TLS 암호화 필수 적용. 이상 명령 패턴 탐지를 위한 OT 특화 IDS(Industrial Intrusion Detection System) 도입.

### 3. MDE(수동 데이터 입력) 기인 데이터 품질 오염 위험

* **설명:** Shift Logs 및 MDE를 통해 수작업으로 입력된 데이터가 오기입, 단위 오류, 누락 등으로 오염될 경우 dataPARC를 거쳐 ERP 및 분석 시스템 전체에 오염 데이터가 전파된다. 스마트팜에서는 수확량, 투입 비용 오류로 인한 잘못된 경영 의사결정으로 이어질 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** dataPARC 인입 레이어에 데이터 유효성 검증 규칙(범위 체크, 이상치 탐지, 필수값 검증) 구현. MDE 입력 UI에 자동완성 및 센서 데이터와의 교차 검증 기능 추가. 수동 입력 데이터에 별도 출처 태그(provenance tag) 부여하여 분석 시 신뢰도 가중치 차등 적용.

### 4. 벤더 종속성(Vendor Lock-in) 및 라이선스 위험

* **설명:** dataPARC, OSIsoft PI(AVEVA), Honeywell, Siemens 등 특정 벤더 솔루션에 핵심 인프라가 종속된 상태에서 라이선스 정책 변경, 가격 인상, 서비스 종료가 발생할 경우 전체 아키텍처 재구성이 불가피하다. 스마트팜 스타트업이나 중소 농가에서는 라이선스 비용이 도입 장벽이 될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 핵심 데이터 모델과 인터페이스를 오픈 표준(OPC-UA, MQTT, REST)으로 정의하여 솔루션 교체 가능성 확보. TimescaleDB, Apache Kafka 등 오픈소스 대안을 병행 검토한 이중화 전략 수립. 데이터 추출·이관 절차(Data Exit Strategy)를 계약 초기부터 명문화.

### 5. 이기종 시스템 간 데이터 시간 동기화(Timestamp Synchronization) 오류 위험

* **설명:** MES, ERP, Historian, PLC 등 각 시스템이 서로 다른 타임존, NTP 동기화 주기, 내부 클럭을 사용할 경우 dataPARC에서 데이터를 병합할 때 시간 불일치가 발생한다. 스마트팜에서 환경 이벤트(일조량 변화)와 제어 응답(차광막 작동) 간 인과관계 분석이 왜곡될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 전체 시스템에 계층적 NTP(Network Time Protocol) 서버 구성 및 PTP(IEEE 1588 Precision Time Protocol) 적용으로 ms 수준 시간 동기화 확보. dataPARC 수집 레이어에서 타임스탬프 정규화 파이프라인 구현. 시간 불일치 탐지 알람 및 이상 데이터 격리 정책 수립.

### 6. 네트워크 대역폭 부족으로 인한 실시간 데이터 지연 위험

* **설명:** 스마트팜 확장 시 수백~수천 개의 IoT 센서가 추가되면 Data Historian으로 유입되는 데이터량이 급증하여 dataPARC와의 연결 구간에서 병목이 발생한다. 특히 농촌 지역 스마트팜은 네트워크 인프라가 취약하여 클라우드 기반 ERP/MES 연동 시 지연이 심화될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 엣지 컴퓨팅(Edge Computing) 레이어를 Historian 앞단에 배치하여 로컬에서 1차 집계·필터링 수행 후 dataPARC로 전송(Edge-to-Hub 패턴). 데이터 우선순위 큐(QoS) 설정으로 제어 임계 데이터를 일반 로그 데이터보다 우선 전송. 5G/LTE 백업 회선 이중화 적용.
