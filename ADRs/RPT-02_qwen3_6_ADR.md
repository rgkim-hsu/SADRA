# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 고정밀 부동소수점 연산 및 오차 보상(Epsilon Compensation) 패턴 적용

| 항목                    | 내용                                                                                                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**       | 시스템은 `9.999`와 같이 정밀도가 높은 소수점 데이터를 처리해야 하며, 여러 처리 단계(블록)를 거치면서 발생하는 부동소수점(Floating-point) 반올림 오차나 데이터 드리프트(Data Drift)를 해결해야 합니다. 단순 산술 연산만으로는 데이터의 무결성이 깨질 수 있는 상황입니다.                                |
| **결정(Decision)**      | 각 처리 단계(블록)마다 미세 조정 계수(Micro-adjustment factor, 예: `-0.001`, `0.002`)를 적용하여 오차를 보정하는 **Epsilon Compensation 패턴**을 아키텍처에 도입합니다.                                                                        |
| **근거(Rationale)**     | 이미지에서 `x1 (9.999)`가 처리되어 `x2 (8.999)`로 변환되고, 각 블록 내에 `-0.001`이나 `0.002`와 같은 미세한 보정값이 명시된 것을 볼 때, 이 시스템은 계산 과정에서의 오차 누적을 방지하기 위해 의도적으로 보정 로직을 삽입해야 함을 알 수 있습니다. 이는 금융 정산이나 정밀 계측 데이터 처리에 필수적인 아키텍처입니다. |
| **결과(Consequences)**  | **긍정적:** 다단계 처리 파이프라인에서도 데이터 값의 정밀도가 유지되며, 최종 출력(`x6`) 시 데이터 불일치로 인한 치명적 오류를 방지할 수 있습니다.<br>**부정적:** 단순 연산에 비해 로직이 복잡해지며, 보정 계수를 관리하기 위한 추가적인 메타데이터 관리가 필요합니다.                                        |
| **트레이드프(Trade-offs)** | **장점:** 데이터 신뢰성(Data Integrity) 및 정밀도 극대화.<br>**단점:** 시스템 복잡도 증가 및 미세 조정 로직으로 인한 처리 지연(Latency) 발생 가능성.                                                                                               |

---

## ⚠️ 잠재적 위험 분석

### 1. 부동소수점 정밀도 손실 (Floating-Point Precision Loss)

- **설명:** 내부적으로 `float32`나 `float64`를 사용할 경우, `9.999`와 같은 값을 정확히 표현하지 못하고 `9.9990000001` 등으로 저장되어 보정 계수(`-0.001`) 적용 시 미세한 오차가 여전히 남을 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:**  High
- **대응 방안:** 핵심 연산 구간에는 `Decimal` 타입(임의 정밀도 산술)을 사용하거나, 보정 로직에 Epsilon 허용 범위(`1e-9`) 비교 로직을 명시적으로 포함해야 합니다.

### 2. 매직 넘버(Magic Number)로 인한 유지보수성 저하

- **설명:** 이미지 내 블록에 `-0.001`, `0.002`와 같은 값이 하드코딩된 형태로 존재할 경우, 데이터 특성 변경 시 코드 수정이 빈번해지고 시스템 전반의 정합성이 깨질 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 보정 계수(Compensation Factors)는 코드 내부가 아닌 외부 설정 파일(Configuration Server)이나 데이터베이스 테이블로 분리하여 관리해야 합니다.

### 3. 오차의 누적 (Error Accumulation)

- **설명:** 다단계 블록(Chain of Blocks)을 거치면서 각 단계의 보정 오차가 쌓여, 최종 출력(`x6`) 시 허용 범위를 벗어나는 오버플로우(Overshoot) 현상이 발생할 수 있습니다.
- **심각도:**  Medium
- **발생 가능성:**  Medium
- **대응 방안:** 각 블록의 출력 지점에서 `Sanity Check`(유효성 검사)를 수행하여 값의 범위를 검증하고, 비정상적인 누적 오차가 감지되면 즉시 알림(Alert)을 발생시켜야 합니다.

### 4. 동시성 제어 실패 (Concurrency Control Failure)

- **설명:** 데이터 스트림(`x1` ~ `x6`)이 비동기적으로 처리될 때, 보정 로직 적용 전후의 값이 다른 스레드에서 참조되어 데이터 불일치가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low (싱글 스트림 처리 시)
- **대응 방안:** 블록 간 데이터 전달 시 Immutability(불변성) 원칙을 적용하거나, 트랜잭션 범위를 명확히 하여 원자성(Atomicity)을 보장해야 합니다.

### 5. 데이터 타입 불일치 (Data Type Mismatch)

- **설명:** 입력값 `9.999`와 보정값 `-0.001`이 서로 다른 데이터 타입(예: Double vs Float)으로 처리될 경우, 의도하지 않은 자동 형 변환으로 인해 미세한 정밀도 손실이 발생할 수 있습니다.
- **심각도:**  Medium
- **발산 가능성:**  Medium
- **대응 방안:** 아키텍처 전반에 걸쳐 동일한 데이터 타입(예: `Decimal128`)을 사용하도록 강제하는 Strict Type Checking 정책을 도입해야 합니다.
