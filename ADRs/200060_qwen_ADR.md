## 📋 ADR (Architecture Decision Record)

### ADR-001: 중앙 집중식 통합 서버 기반의 데이터 허브 아키텍처 도입

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 매설관로 네트워크는 지리적으로 분산된 IoT 센서, NFC 태그, 모바일 애플리케이션, 그리고 외부 기관(국가기관, 119 등) 등 이질적인 시스템과 연동되어야 합니다. 데이터 일관성을 보장하고 실시간 상황판(디스패치) 기능을 제공하기 위해 단일 진실 공급원(Single Source of Truth)이 필요합니다. |
| **결정(Decision)** | **매설관로 통합서버**를 중앙 허브로 설정하여 모든 데이터(센서 입력, 위치정보, 태그 정보)를 수렴하고, 이를 기반으로 웹 정보 조회 및 전용 앱 정보 조회, 그리고 외부 기관(시설표관리기관, 국가기관, 119, 재난현장)으로 라우팅하는 중추 역할을 부여합니다. |
| **근거(Rationale)** | 문서에 언급된 **ISO/IEC 30141:2024** (IoT 참조 아키텍처) 표준의 요구사항을 충족하기 위해 상호 운용성을 핵심으로 설계해야 합니다. 또한, **oneM2M** 아키텍처 방식과 유사하게 계층적 접근을 취하여 데이터 수집, 처리, 서비스 계층을 명확히 분리하여 확장성을 확보합니다. |
| **결과(Consequences)** | *긍정적:* 시스템 유지보수가 단일화되고, 다양한 사용자 (소요자, 소방관, 관리자) 의 접근이 용이해짐.<br>*부정적:* 서버 부하나 단일 장애점(SPOF) 리스크가 존재하므로, 클라우드 기반의 확장성 있는 인프라(Scalability) 도입 필요성 대두. |
| **트레이드오프(Trade-offs)** | *장점:* 데이터 일관성과 관리 용이성 확보.<br>*단점:* 높은 통합 비용 및 외부 시스템과의 API 표준화 (M2M, IETF CoAP 등) 노력 필요. |

### ADR-002: 하이브리드 상호작용 및 오프라인 대응 전략 (Tagging 및 NFC)

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 관로 작업 현장에서는 네트워크 연결이 불안정하거나 급박한 상황에서도 신속한 정보 조회가 필요합니다. 스마트폰 앱만으로는 모든 상황 (예: 네트워크 끊김) 에서의 접근이 제한될 수 있습니다. |
| **결정(Decision)** | **Tagging 정보조회** 및 **NFC 기반 정보 입력/저장** 기능을 유지합니다. 모바일 앱은 네트워크 의존도가 높은 '전용 APP 정보조회'를 담당하고, NFC 태그와 QR 코드는 오프라인 상태나 급격한 상황 발생 시의 데이터 저역 (Tagging 정보 조회) 및 식별을 위한 핵심 수단으로 활용합니다. |
| **근거(Rationale)** | **ETSI EN 303 645** (IoT 기기 사이버보안) 및 **ITU-T X.1352** 표준에서 강조하는 보안 및 가용성을 고려합니다. 네트워크 환경이 제한된 현장 (터널, 지하) 에서 물리적 매체 (Tag/NFC) 를 통해 시스템 진입을 보장하여 가용성을 높이는 전략입니다. |
| **결과(Consequences)** | *긍정적:* 현장의 네트워크 상황에 유연하게 대응하며, 재난 상황에서도 최소한의 정보 접근이 가능함.<br>*부정적:* NFC 및 태그 데이터 동기화 로직이 복잡해지고, 하드웨어 비용 (NFC 리더 등) 이 증가함. |
| **트레이드오프(Trade-offs)** | *장점:* 네트워크 부재 상황에서의 시스템 접근성 확보.<br>*단점:* 오프라인 데이터 동기화 (Reconciliation) 로직의 복잡성 증가 및 보안 정책 (로컬 데이터 암호화) 적용 필요. |

## ⚠️ 잠재적 위험 분석

### 1. [위험명] IoT 기기 및 센서 데이터의 무결성 위협
- **설명:** 매설관로의 다양한 센서 (압력, 유량 등) 에서 수집된 데이터가 악의적으로 조작되거나, 노후화된 센서로 인해 오동작이 발생하여 잘못된 정보 (False Positive/Negative) 가 통합 서버로 전송될 경우, 관로 파손이나 누수 사고 대응 지연을 초래할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (하드웨어 노후화 및 네트워크 공격)
- **대응 방안:** **ISO/IEC 27030:2020** (안전한 설계 가이드라인) 을 준수하여 에지 게이트웨이에서 데이터 암호화 및 서명 방식을 적용하고, 이상 데이터 발생 시 통계 기반의 Anomaly Detection 알고리즘을 도입하여 악성 데이터를 필터링합니다.

### 2. [위험명] 중앙 서버 단일 장애점 (SPOF) 및 가용성 저하
- **설명:** 모든 데이터 흐름이 '매설관로 통합서버'로 집중되어 있어, 해당 서버가 가동 중단되거나 DDOS 공격을 받으면 웹 정보조회, 앱 정보조회, 그리고 중요한 외부 기관 (119, 국가기관) 으로도 정보가 전달되지 않을 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (하드웨어 고장 및 대량 트래픽)
- **대응 방안:** 클러스터링 방식을 통한 서버군 구성으로 고가용성 (HA) 을 구축하며, 핵심 API 는 **oneM2M** 스펙에 부합하는 중복된 경로를 통해 복제 (Replication) 되도록 설계합니다.

### 3. [위험명] 네트워크 분실 및 위치정보 오차 (Positioning Risk)
- **설명:** 위성 신호 (그림 상의 위성 아이콘) 에 의존하고 있는데, 고층 건물, 지하 관로, 또는 간섭 환경에서 GPS 신호가 약화되면 위치정보 결합이 부정확해질 수 있습니다. 이는 재난 현장 (119, 지진/재난현장) 에의 신속한 접근을 방해합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High (환경적 요인)
- **대응 방안:** 오차 보정 알고리즘 (GNSS 보정 기술 등) 을 적용하고, 위치정보 결합 시 모바일 기기의 WiFi/블루투스 비콘과 같은 근거리 식별자 정보를 보조 정보로 활용하여 정확도를 높입니다.

### 4. [위험명] 프라이버시 및 정보 유출 (Data Breach)
- **설명:** 관로 정보 입력 시 사용자의 위치 및 작업 기록 데이터가 저장되고, 다양한 플랫폼 (웹, 전용 앱) 을 통해 조회됩니다. 이 과정에서 민감한 인프라 정보가 유출되거나, 개인 식별 정보 (PII) 가 탈취될 경우 법적 및 윤리적 리스크가 발생합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (소프트웨어 취약점, 해킹)
- **대응 방안:** **ETSI EN 303 645** 표준에 따라 최소 권한 원칙 (Least Privilege) 을 적용하고, 모든 데이터 전송 시 TLS 1.3 을 사용하며, 민감한 저장 데이터는 암호화 (Encryption at Rest/Transit) 를 적용합니다.

### 5. [위험명] 이질 시스템 간의 상호 운용성 실패
- **설명:** 시스템이 기존 관로 데이터나 다른 IoT 프로토콜 (MQTT, CoAP 등) 을 사용하는 다른 시스템 (시설물관리기관 등) 과 연동해야 하는데, 표준화되지 않은 프로토콜을 사용하면 데이터 포맷 변환 실패로 인해 시스템 간 통신이 단절될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟠 High (외부 파트너 시스템과의 연동)
- **대응 방안:** **oneM2M** 및 **ISO/IEC 30141** 정의된 표준 API 및 데이터 모델을 강제 적용하여 이기종 환경 간의 인터페이스를 표준화합니다. 또한, 메시지 브로커를 통해 프로토콜 변환 계층을 명확히 분리합니다.
