===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트 양봉 플랫폼의 중앙집중식 통합관리서버 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 위탁소비자·양봉가·일반소비자 등 다양한 이해관계자가 존재하며, 양봉 계약 관리, IoT 기반 원격 모니터링(이상검출부·원격제어부), 시뮬레이션, 통계분석, 생산관리(발물·택배), 쇼핑몰 운영 등 이질적인 도메인을 단일 플랫폼에서 통합 운영해야 하는 과제가 존재한다. 분산 배치 시 데이터 일관성 유지와 실시간 제어 지연이 핵심 아키텍처 과제다.                 |
| **결정(Decision)**       | 모든 기능 모듈(회원관리부·양봉계약부·모니터링부·시뮬레이션부·통계분석부·생산관리부·쇼핑몰관리부)을 단일 통합관리서버 하위에 배치하는 **중앙집중식 모놀리식 서버 아키텍처**를 채택하고, 서버통신부(701)가 외부 인터페이스 단일 창구 역할을 담당하도록 설계한다.                                                               |
| **근거(Rationale)**      | ① 양봉 도메인 특성상 계약→모니터링→생산→판매의 데이터 연계가 강결합 구조이므로 서비스 간 트랜잭션 복잡도를 최소화할 수 있다. ② 지역별 환경조건 시뮬레이션(707)과 통계분석(708)이 동일한 현황정보 DB를 실시간으로 참조해야 하므로 데이터 복제 지연을 허용하기 어렵다. ③ 초기 사용자 규모와 운영 조직의 기술 역량을 고려할 때 단일 서버가 운영 복잡도를 낮춘다. |
| **결과(Consequences)**   | (+) 모든 모듈이 동일한 DB 컨텍스트를 공유하여 데이터 정합성이 보장된다. (+) 서버통신부 단일 진입점으로 인해 보안 정책 적용이 일관된다. (-) 특정 모듈(예: 쇼핑몰관리부 트래픽 급증) 부하가 전체 시스템 성능에 영향을 미친다. (-) 개별 모듈의 독립적 배포·확장이 불가능하다.                                               |
| **트레이드오프(Trade-offs)** | **얻는 장점:** 데이터 일관성, 낮은 초기 개발 복잡도, 통합 운영 편의성. **감수해야 할 단점:** 수평적 스케일아웃 한계, 모듈 간 장애 전파 위험, 기술 스택 다양성 제한, 장기적 유지보수 비용 증가.                                                                                           |

### ADR-002: 도메인별 전용 DB 분리 설계 (논리적 데이터 분리)

| 항목                     | 내용                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 위탁소비자 DB·양봉가 DB·일반소비자 DB(702), 양봉위수탁계약정보(703), 현황정보·통계분석정보(708), 발물생산이력·택배발송이력(709), 위탁소비자판매정보·양봉가판매정보(710) 등 도메인별로 성격이 상이한 데이터가 혼재한다. 단일 스키마 통합 시 쿼리 복잡도와 접근 제어가 어려워진다. |
| **결정(Decision)**       | 각 기능 모듈별로 **논리적으로 분리된 전용 DB(데이터 저장소)**를 부여하되, 물리적으로는 통합관리서버 내에서 관리하는 **논리 분리 / 물리 통합** 구조를 채택한다.                                                                         |
| **근거(Rationale)**      | 도메인 경계를 명확히 하여 향후 마이크로서비스 전환 시 데이터 이전 비용을 최소화하고, 현재 단계에서는 물리 통합으로 운영 인프라를 단순화한다. 각 DB는 소유 모듈만 직접 접근하도록 캡슐화하여 데이터 무결성을 보호한다.                                              |
| **결과(Consequences)**   | (+) 모듈별 데이터 책임 경계가 명확해져 유지보수성 향상. (+) 특정 DB 스키마 변경이 타 모듈에 미치는 영향 최소화. (-) 크로스 도메인 조회(예: 계약정보 + 생산이력 통합 리포트) 시 조인 복잡도 증가. (-) 물리 통합이므로 DB 서버 단일 장애점(SPOF) 위험 공유.          |
| **트레이드오프(Trade-offs)** | **얻는 장점:** 도메인 응집도, 확장성 기반 마련. **감수해야 할 단점:** 크로스 도메인 쿼리 성능 저하, 물리 SPOF 공유.                                                                                              |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 통합관리서버 단일 장애점(SPOF) 위험

* **설명:** 서버통신부(701)를 포함한 모든 기능 모듈이 단일 서버에 집중되어 있어, 하드웨어 장애·OS 패닉·네트워크 단절 발생 시 양봉 모니터링 실시간 제어(705·706), 계약 처리, 쇼핑몰 전체 서비스가 동시에 중단된다. 특히 양봉 이상 상황(과열, 여왕벌 이상 등) 발생 시 원격제어부(706)가 응답 불능 상태가 되어 생물학적 피해로 직결될 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Standby 이중화 구성(HA Cluster) 적용, 모니터링부(704)만이라도 엣지 서버로 분리 배치하여 독립 생존성 확보. 자동 Failover 구성 및 RTO/RPO 목표치 명문화.

### 2. IoT 모니터링 데이터 실시간성 저하 위험

* **설명:** 이상검출부(705)와 원격제어부(706)는 양봉 현장의 온도·습도·소리 등 IoT 센서 데이터를 밀리초~초 단위로 처리해야 한다. 그러나 동일 서버에서 통계분석(708)의 대용량 배치 쿼리나 시뮬레이션부(707)의 연산 집약적 작업이 실행될 경우, CPU·I/O 경합으로 인해 실시간 제어 응답이 지연되어 이상 상황 대응 골든타임을 놓칠 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 모니터링부에 최고 우선순위 QoS 설정 및 전용 스레드풀 격리. 시뮬레이션·통계 배치 작업은 업무 시간 외 스케줄링. 중장기적으로 모니터링부를 엣지/MEC(Mobile Edge Computing) 환경으로 분리 배치.

### 3. 회원 및 계약 데이터 보안 침해 위험

* **설명:** 위탁소비자·양봉가·일반소비자 개인정보 DB(702)와 양봉위수탁계약정보(703), 판매정보(710)가 동일 서버에 공존한다. 쇼핑몰관리부(710) API를 통한 외부 노출면이 넓어, SQL Injection 또는 API 인증 우회 공격 성공 시 계약 정보와 개인정보가 동시에 유출될 수 있다. 개인정보보호법 위반으로 인한 법적 제재와 플랫폼 신뢰도 손상이 동반된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** DB 접근 계층에 역할 기반 접근 제어(RBAC) 및 컬럼 단위 암호화 적용. 서버통신부(701)에 WAF(Web Application Firewall) 및 API Gateway 도입. 정기적 침투 테스트 및 개인정보 영향평가(PIA) 수행.

### 4. 시뮬레이션·통계 분석 데이터 품질 저하 위험

* **설명:** 시뮬레이션부(707)는 지역별 지역조건 데이터를, 통계분석부(708)는 현황정보를 기반으로 작동한다. 모니터링부(704)에서 IoT 장애 또는 통신 단절로 인해 현황정보 DB에 결측값·이상값이 누적될 경우, 시뮬레이션 결과와 통계 분석이 왜곡되어 양봉가에게 잘못된 의사결정 정보를 제공하게 된다. 이는 생산량 손실 및 계약 분쟁으로 이어질 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** IoT 데이터 수집 파이프라인에 이상값 탐지 및 결측값 보정 로직(데이터 품질 게이트) 적용. 시뮬레이션 실행 전 입력 데이터 완전성 검증 단계 필수화. 데이터 계보(Data Lineage) 추적 및 품질 대시보드 운영.

### 5. 생산관리부 추적성(Traceability) 데이터 무결성 위험

* **설명:** 발물생산이력과 택배발송이력(709)은 식품 안전 관점에서 법적 추적 의무 대상 데이터다. 시스템 장애 또는 SW 버그로 인해 생산 이력이 누락되거나 배송 상태가 잘못 기록될 경우, 식품위생법·농수산물 원산지 표시법 위반 리스크가 발생하며 위탁소비자(702) 및 쇼핑몰 구매자(710) 간 계약 분쟁의 증거 자료로 활용이 불가능해진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 생산·배송 이력 DB에 Append-Only(불변) 로그 구조 적용 및 변경 불가 감사 로그(Audit Trail) 별도 저장. 블록체인 기반 이력 공증 연계 검토. 데이터 변경 시 이중 검증(Two-phase commit) 트랜잭션 보장.

### 6. 쇼핑몰 트래픽 급증으로 인한 전체 시스템 성능 저하 위험

* **설명:** 쇼핑몰관리부(710)는 계절성(꿀 수확기, 명절 등) 트래픽 피크가 극심한 도메인이다. 단일 서버 구조에서 쇼핑몰 트래픽 폭증 시 DB 커넥션 풀 고갈 및 CPU 포화가 발생하여, 양봉 계약 처리(703), 모니터링 실시간 제어(704), 통계 분석(708) 등 무관한 핵심 기능까지 연쇄적으로 응답 지연 또는 서비스 불가 상태에 빠질 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 쇼핑몰관리부를 우선적으로 별도 서비스로 분리하여 독립 스케일아웃 가능하도록 설계. 모듈별 DB 커넥션 풀 상한 제한(Connection Pool Capping) 적용. CDN 및 정적 리소스 캐싱으로 원서버 부하 감소. 트래픽 피크 시즌 대비 사전 부하 테스트 의무화.
