# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 계층 분리 및 표준화된 데이터 모델을 이용한 상호운용성 확보 (Standardized Interoperability Layer)

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 센서, 액추에이터, 제어기 등 매우 이질적(Heterogeneous)이고 다양한 프로토콜(Modbus, MQTT, Zigbee 등)을 사용하는 다수의 물리적 장비들로 구성되어 있다. 이로 인해 각 장비가 생성하는 데이터의 형식, 시점, 의미론적 모델(Semantic Model)이 표준화되지 않아, 중앙의 핵심 비즈니스 로직(Core Logic)으로 데이터를 통합하고 처리하는 데 큰 장벽이 존재한다. |
| **결정(Decision)** | **IoT 데이터 게이트웨이/추상화 계층(Abstraction Layer)**을 명확히 분리하고, 이 계층 내에서 모든 물리적 데이터를 수집하여 **통일된 개념 모델(Common Ontology)**과 **이벤트 기반 스트리밍 프로토콜(Event-Driven Streaming)**로 변환하는 전용 모듈을 구현한다. 모든 서비스는 이 표준화된 인터페이스를 통해서만 데이터를 주고받도록 강제한다. |
| **근거(Rationale)** | 1. **상호운용성(Interoperability):** 국내외 표준(ISO/IEC 30141, oneM2M)은 공통 용어와 재사용 가능한 설계를 강조한다. 데이터 모델을 표준화하는 것이 상호운용성의 핵심 전제 조건이다. 2. **유지보수성(Maintainability):** 물리 계층과 비즈니스 로직을 분리함으로써, 새로운 센서나 장비가 추가되더라도 핵심 로직 수정 없이 게이트웨이 전용 개발만으로 대응할 수 있다. 3. **확장성(Scalability):** 이벤트 스트리밍 패턴(예: Kafka 기반)을 채택하면, 데이터 처리 부하가 증가해도 수평적 확장이 용이하며 실시간 데이터 처리가 가능하다. |
| **결과(Consequences)** | 🟢 **긍정적:** 시스템의 아키텍처적 안정성, 확장성, 표준 준수성이 극대화된다. 새로운 장비 통합 시간이 획기적으로 단축된다. 🟡 **부정적:** 아키텍처 복잡도가 증가하며, 게이트웨이/데이터 변환 계층 설계 및 구현에 높은 전문 지식과 시간이 요구된다. |
| **트레이드오프(Trade-offs)** | **[Gain]** 높은 상호운용성 및 미래 확장성을 확보하여, 다양한 표준 프로토콜과 장비 변화에 능동적으로 대응할 수 있다. **[Cost]** 초기 개발 단계에서 통합 게이트웨이 및 데이터 변환(Normalization) 모듈 설계에 막대한 공수가 투입되며, 이는 초기 시스템 구축 비용 증가로 이어진다. |

## ⚠️ 잠재적 위험 분석

### 1. 물리 계층 프로토콜 이질성 및 연동 실패 위험 (Protocol Heterogeneity & Integration Failure)
- **설명:** 스마트팜 현장에는 수십 가지가 넘는 제조사별, 노후된 프로토콜(RS-485, 아날로그 신호 등)의 장비들이 혼재되어 있다. 게이트웨이/추상화 계층이 모든 장비의 비표준 프로토콜을 완벽하게 해석하고 통합하는 것이 기술적 난제이다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 1. **표준 프로토콜 게이트웨이(Protocol Gateway)** 모듈을 분리하여, 각 프로토콜에 맞는 어댑터를 개발하고 중앙 플랫폼에 노출시킨다. 2. 핵심 로직에 도달하기 전, **데이터 밸리데이션(Validation)** 및 **프로토콜 변환 계층**을 의무화하여 이질성을 격리하고 표준 데이터 모델로 변환하는 과정을 거친다.

### 2. 사이버 보안 취약점 및 제어 시스템 오용 위험 (Cybersecurity & Control Misuse)
- **설명:** 시스템이 작물 생육을 직접 제어하는 액추에이터(스마트팜 기자재 제어기)를 포함하고 있어, 해킹이나 전송 데이터의 변조가 발생할 경우 작물에 치명적인 피해를 입힐 수 있다 (예: 과도한 급수, 난방 중단).
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 1. **OT/IT 네트워크 분리:** 제어 시스템(OT, Operational Technology)과 정보 시스템(IT)의 물리적/논리적 네트워크를 분리(Air Gap 또는 DMZ 사용)하고, 필수 통신만 게이트웨이를 통해 제어한다. 2. **End-to-End 암호화 및 무결성 검증:** 모든 통신 경로(센서-게이트웨이-클라우드)에서 암호화(TLS/DTLS)를 적용하고, 전송 데이터에 대한 위변조 방지 메커니즘(HMAC)을 적용한다.

### 3. 실시간 데이터 처리 지연 및 서비스 가용성 위험 (Real-Time Latency & Availability)
- **설명:** 작물 재배는 시간 민감형 프로세스이다. 만약 데이터 수집, 전송, 핵심 로직 처리 과정 중 어느 한 단계라도 지연(Latency)이 발생하면, 최적의 제어 결정이 늦어지거나 오동작을 초래할 수 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 1. **엣지 컴퓨팅 도입:** 센서와 제어기에 근접한 게이트웨이 레벨에서 기본적인 필터링, 로컬 제어 로직(예: 온도 임계치 초과 시 경고)을 수행하여 클라우드 의존도를 낮춘다. 2. **메시지 브로커 최적화:** Kafka와 같은 고가용성 메시지 브로커를 사용하여 높은 처리량(Throughput)을 보장하고, 데이터 처리 백엔드에 대한 백업 시스템을 구축한다.

### 4. 데이터 수명 주기 관리 및 규격 미준수 위험 (Data Lifecycle & Standardization Gap)
- **설명:** 시스템 운영 과정에서 발생하는 방대한 양의 데이터를 어떻게 장기적으로 저장, 분석, 활용할 것인지에 대한 정책이 없다. 또한, 산업 표준(ISO 30141)에서 정의한 공통 데이터 모델을 제대로 따르지 못할 경우, 데이터의 재활용성 및 상호운용성이 급격히 떨어진다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:** 1. **데이터 거버넌스 프레임워크 수립:** 데이터 수집부터 폐기까지의 전체 라이프사이클을 정의하고, 메타데이터 관리 시스템을 구축한다. 2. **표준화된 온톨로지(Ontology) 강제 적용:** 모든 데이터 수집 및 분석 시, 관련 국제표준(ISO 30141)에서 제정한 공통 어휘와 데이터 타입을 필수로 사용하도록 아키텍처 정책을 수립한다.

### 5. 클라이언트와 백엔드 간 API 통신 복잡성 및 버전 관리 위험 (API Complexity & Versioning)
- **설명:** 여러 이해관계자(농업 전문가, 연구원, 관리자)를 위한 다양한 기능을 제공하므로, API가 복잡해지고 기능이 추가될 때마다 API 명세가 꼬이거나 버전 관리가 실패할 위험이 있다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 1. **API Gateway 패턴 적용:** 모든 외부 호출은 API Gateway를 통해 통제한다. 이를 통해 인증, 권한 부여, 로드 밸런싱 등을 중앙에서 관리하고, 클라이언트 요청과 백엔드 서비스의 분리를 명확히 한다. 2. **버전 명세 강제:** API 설계 시 Swagger/OpenAPI 표준을 사용하고, 새로운 기능 추가 시 반드시 **하위 호환성을 유지하는 방식(Non-breaking changes)**으로 버전을 관리하고 마이그레이션 계획을 수립한다.
