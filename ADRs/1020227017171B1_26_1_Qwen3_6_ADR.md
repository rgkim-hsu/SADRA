# 🏗️ 아키텍처 분석 보고서

## ADR (Architecture Decision Record)

### ADR-001: 다중 3PL 통합을 위한 메시지 게이트웨이 기반 허브-앤-스포크 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 물류 운영 환경에서 내부 창고 관리(119), 운송(107), 판매(109) 등의 기능과 함께, 다수의 제3자 풀필먼트(121A, 121B, 121C)를 활용하여 주문을 처리해야 함. 각 3PL은 상이한 API와 통신 프로토콜을 사용할 가능성이 높으며, 주문 최적화(113) 및 공급체인 관리(117) 시스템이 모든 3PL과 직접 연결될 경우 유지보수 비용이 기하급수적으로 증가하는 아키텍처적 과제가 발생함.                            |
| **결정(Decision)**       | 내부의 **배송 기반기술 시스템(101)**을 허브(Hub)로 설정하고, 외부의 다수 3PL(121A/B/C)과의 통신을 전담하는 **풀필먼트 메시지 게이트웨이(115)**를 도입하는 **허브-앤-스포크(Hub-and-Spoke) 아키텍처**를 채택함. 모든 3PL 관련 요청은 게이트웨이를 통해 라우팅 및 프로토콜 변환이 이루어지도록 설계함.                                                                |
| **근거(Rationale)**      | 1. **결합도 최소화:** 풀필먼트 최적화 시스템(113)은 게이트웨이(115)에만 의존하면 되므로, 3PL 변경 시 코어 시스템 수정이 불필요함.<br>2. **표준화:** 게이트웨이가 이기종 3PL의 응답을 표준화하여 배송 및 주문 트래킹 시스템(111)이 일관된 데이터를 처리할 수 있도록 함.<br>3. **보안 강화:** 3PL과의 직접적인 내부 시스템 노출을 차단하고, 게이트웨이를 단일 진입점으로 통제함으로써 보안 경계를 명확히 할 수 있음. |
| **결과(Consequences)**   | 신규 3PL 추가가 용이해지며 시스템 확장성이 크게 향상됨. 내부 로직과 외부 통신이 분리되어 장애 격리(Fault Isolation)가 가능해짐. 반면, 게이트웨이(115)가 단일 장애점(SPOF)이 될 수 있으며, 메시지 변환 과정에서 미세한 지연(Latency)이 발생할 수 있음.                                                                                                |
| **트레이드오프(Trade-offs)** | 높은 확장성, 표준화된 인터페이스, 보안 경계 명확화 vs. 게이트웨이 복잡도 증가, 단일 장애점(SPOF) 리스크, 메시지 처리 지연 가능성.                                                                                                                                                                                |

## ⚠️ 잠재적 위험 분석

### 1. 풀필먼트 메시지 게이트웨이(115) 장애로 인한 3PL 통신 두절

- **설명:** 게이트웨이(115)는 모든 3PL(121A, 121B, 121C)로 나가는 트래픽의 관문임. 이 모듈에 장애가 발생할 경우, 최적화된 주문이 외부 창고로 전달되지 못하고 배송 트래킹 정보가 갱신되지 않아 전체 물류 운영이 마비됨.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 게이트웨이 모듈의 클러스터링(Clustering) 및 로드 밸런싱(Load Balancing) 구성, 비동기 메시지 큐(Message Queue)를 활용한 트래픽 버퍼링, 게이트웨이 장애 시 기본 라우팅으로의 자동 페일오버(Failover) 로직 구현.

### 2. 이기종 3PL 데이터 형식 불일치 및 변환 오류

- **설명:** 각 제3자 풀필먼트(121A/B/C)가 반환하는 배송 상태나 재고 데이터 형식이 다를 경우, 게이트웨이(115)에서의 데이터 변환 과정에서 오류가 발생하여 배송 및 주문 트래킹 시스템(111)에 잘못된 정보가 입력될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 게이트웨이 내부에 강력한 데이터 검증(Validation) 및 스키마 매핑 로직 도입, 각 3PL별 어댑터(Adapter) 패턴 적용을 통한 변환 로직 모듈화, 데이터 변환 실패 시 재시도(Retry) 및 관리자 알림 시스템 구축.

### 3. 풀필먼트 최적화 시스템(113)의 알고리즘 비효율성

- **설명:** 최적화 시스템(113)이 실시간 재고, 운송 비용, 3PL 처리 능력 등을 종합하여 최적의 배송 경로를 계산해야 함. 알고리즘이 복잡하거나 데이터 처리 지연이 발생하면, 주문 처리(109)에서 지연이 발생하거나 비효율적인 3PL 배정이 이루어져 비용이 증가함.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 최적화 알고리즘의 캐싱(Caching) 메커니즘 도입, 근사 알고리즘(Approximation Algorithm)을 활용한 계산 속도 향상, 피크 타임(Traffic Spike) 대비 자동 스케일링(Auto-scaling) 인프라 구축.

### 4. 풀필먼트 센터 인증 시스템(123)의 보안 취약점

- **설명:** 인증 시스템(123)은 외부 사용자(200) 및 내부 시스템 간의 인증을 담당함. 만약 인증 로직이 우회되거나 토큰이 탈취될 경우, 제3자 풀필먼트(121A/B/C)에 대한 권한 없는 접근이나 위변조된 주문 데이터 주입이 가능해짐.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** OAuth 2.0 / JWT 기반의 강력한 토큰 관리 정책 적용, 다중 인증(MFA) 지원, API 호출 시 IP 화이트리스트 및 Rate Limiting 적용, 정기적인 보안 감사(Penetration Test) 수행.

### 5. 배송 및 주문 트래킹 시스템(111)과 창고 관리 시스템(119) 간 데이터 불일치

- **설명:** 트래킹 시스템(111)이 3PL로부터 받은 배송 완료 정보를 창고 관리 시스템(119)에 반영하는 과정에서 네트워크 지연이나 트랜잭션 오류가 발생하면, 재고 수량과 실제 배송 상태가 일치하지 않는 데이터 불일치(Data Inconsistency)가 발생함.
- **심각도:**  Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 이벤트 소싱(Event Sourcing) 패턴을 도입하여 상태 변경 이력을 모두 기록, 최종 일관성(Eventual Consistency) 보장을 위한 보상 트랜잭션(Compensating Transaction) 로직 구현, 정기적인 데이터 정합성 검사 배치(Job) 실행.
