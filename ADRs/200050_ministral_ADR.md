## 📋 ADR (Architecture Decision Record)

### **ADR-001: 데이터 수집 및 정제 프로세스의 중앙 집중형 vs 분산형 아키텍처 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **스마트팜/축산 IoT 데이터**를 수집하여 AI 모델 학습 및 활용까지 처리하는 **엔드투엔드 데이터 라이프사이클**을 지원해야 함. 데이터 원천은 다수(원시데이터, 완전데이터, 라벨링데이터)로 분산되어 있으며, **실시간 처리 요구**와 **보안/규제 준수**가 필수적임. 또한, **국내외 IoT 표준(ISO/IEC 30141, oneM2M, ITU-T X.1352)**과의 상호운용성이 요구됨. |
| **결정(Decision)** | **중앙 집중형 데이터 플랫폼**을 채택하며, **데이터 수집 → 정제 → 라벨링 → 모델 학습** 프로세스를 단일 **데이터 플랫폼**에서 통합 관리함. 그러나 **외주관리**를 통해 일부 프로세스를 분산 처리할 수 있도록 유연성을 확보함. |
| **근거(Rationale)** | 1. **데이터 일관성 보장**: 중앙 플랫폼을 통해 데이터 정제/라벨링 규칙을 일원화하여 AI 모델의 학습 품질을 높임.
2. **표준 준수**: ISO/IEC 30141의 **"데이터 관리 계층"**과 oneM2M의 **"통합 데이터 접근"** 원칙에 부합함.
3. **보안 강화**: KISA의 **ITU-T X.1352** 기준에 따라 중앙 플랫폼에 **접근 통제(ACL)**와 **데이터 암호화**를 적용함.
4. **유연성**: 외주관리를 통해 **라벨링 데이터** 생성과 같은 비용 집약적 작업은 분산 처리 가능함. |
| **결과(Consequences)** | ✅ **장점**:
- 데이터 품질과 일관성이 향상되어 AI 모델의 예측 정확도 향상.
- 표준화된 데이터 스키마로 **국내외 상호운용성** 강화.
- 중앙 모니터링으로 **실시간 오류 탐지** 및 대응 가능.
❌ **단점**:
- **단일 장애점(SPOF)**: 중앙 플랫폼 장애 시 전체 시스템 영향 발생 가능.
- **초기 구축 비용**: 중앙 플랫폼과 네트워크 인프라에 높은 투자가 필요함. |
| **트레이드오프(Trade-offs)** | - **중앙 집중형**의 장점(일관성, 보안)은 **분산형**의 장점(확장성, 장애 격리)과 트레이드오프 관계.
- **대응책**: 중앙 플랫폼에 **고가용성(HA) 클러스터링**과 **지리적 중복(DR)**을 적용하여 SPOF를 완화함. |

### **ADR-002: 데이터 라벨링 프로세스의 자동화 vs 수동 라벨링 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | AI 모델 학습을 위한 **데이터 라벨링**은 **농업 전문가**의 도움 없이 자동화할 수 있는가? 현재 시스템은 **원시데이터 → 완전데이터 → 라벨링데이터**로 변환되는 프로세스를 포함함. |
| **결정(Decision)** | **반자동 라벨링 시스템** 채택:
- **자동 라벨링**: 규칙 기반(예: 온도/습도 임계값) 또는 **ML 기반 사전 라벨링**을 적용.
- **수동 검수**: 전문가가 자동 라벨링 결과를 검수하여 **오류율 5% 이하**로 보장함.
- **외주관리**: 전문가 라벨링을 외주로 처리하여 **비용 효율성** 확보. |
| **근거(Rationale)** | 1. **정확성 요구**: 농업 데이터는 **고정밀 라벨링**이 필수적임(예: 질병 진단 데이터).
2. **비용 vs 정확성**: 완전 자동 라벨링은 **오류율이 높음**(예: 15% 이상), 수동 라벨링은 **비용과 시간**이 소요됨.
3. **국내 표준 준수**: TTA의 **"스마트팜 데이터 상호운용 프레임워크"**는 **"인간 검수 필수"**를 규정함. |
| **결과(Consequences)** | ✅ **장점**:
- **라벨링 오류율**을 5% 이하로 낮춤.
- **반자동화**로 인력 비용을 30% 절감 가능.
❌ **단점**:
- **초기 구축**: 규칙 엔진과 검수 워크플로우 구축에 시간 소요.
- **의존성**: 전문가 검수 과정이 **병목**으로 작용할 수 있음. |
| **트레이드오프(Trade-offs)** | - **완전 자동화**의 장점(속도, 비용)은 **정확성 저하**와 트레이드오프.
- **대응책**: **주기적 모델 업데이트**로 자동 라벨링 정확도를 개선하고, **다중 검수자**를 도입하여 병목 완화함. |

### **ADR-003: AI 모델 개발 및 활용의 온프레미스 vs 클라우드 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | AI 모델 학습 및 추론은 **온프레미스**로 처리할지, **클라우드**로 처리할지 결정해야 함. **데이터 민감성**(예: 축산 데이터), **실시간 처리 요구**, **비용** 등이 고려 변수임. |
| **결정(Decision)** | **하이브리드 아키텍처** 채택:
- **데이터 저장/정제**: **온프레미스**에서 처리(데이터 보안 및 규제 준수).
- **모델 학습**: **클라우드**(예: AWS SageMaker, Azure ML)에서 분산 학습 처리.
- **추론**: **에지 디바이스** 또는 **온프레미스**에서 실시간 처리. |
| **근거(Rationale)** | 1. **데이터 보안**: KISA의 **개인정보 보호법**과 **ITU-T X.1352**에 따라 민감 데이터는 **온프레미스**에 저장함.
2. **컴퓨팅 리소스**: 클라우드의 **GPU 클러스터**를 활용하여 **대용량 모델 학습** 효율성 향상.
3. **실시간 요구**: 에지 디바이스에서 **저지연 추론**을 지원함(예: 스마트 온실 제어). |
| **결과(Consequences)** | ✅ **장점**:
- **보안 강화**: 민감 데이터가 클라우드로 노출되지 않음.
- **확장성**: 클라우드 리소스를 동적으로 할당하여 **대규모 학습** 가능.
❌ **단점**:
- **네트워크 latency**: 온프레미스 ↔ 클라우드 데이터 전송 지연 발생 가능.
- **복잡성**: 하이브리드 시스템 관리가 어려움. |
| **트레이드오프(Trade-offs)** | - **온프레미스 전용**의 장점(보안)은 **클라우드**의 장점(확장성, 비용 효율성)과 트레이드오프.
- **대응책**: **에지 캐싱**과 **데이터 압축**을 통해 네트워크 지연 완화함. |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 플랫폼의 단일 장애점(SPOF)**
- **설명**: 중앙 데이터 플랫폼이 장애를 발생하면 **전체 데이터 수집/정제 프로세스**가 중단됨. 특히 **실시간 모니터링 시스템**(예: 스마트 온실)은 **10분 이내 복구**가 요구됨.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **고가용성 클러스터링**: 중앙 플랫폼에 **Active-Active** 구조를 적용(예: Kubernetes + etcd).
  - **자동 장애 복구**: **Kubernetes Operator**를 사용하여 장애 노드 자동 교체.
  - **백업 플랫폼**: **지리적 중복(DR)**을 통해 2차 플랫폼을 운영함.

### **2. 데이터 라벨링 오류 누적**
- **설명**: 자동 라벨링 시스템의 **오류**가 검수 과정에서 발견되지 않으면, AI 모델에 **편향된 데이터**가 학습되어 **정확도 저하**를 초래함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **다중 검수자 시스템**: 최소 **2명의 전문가**가 검수를 수행하고, **다수결 원칙**으로 라벨링 결정.
  - **오류 피드백 루프**: 검수 과정에서 발견된 오류를 **자동 라벨링 규칙**에 반영함.
  - **통계적 검증**: 라벨링 데이터의 **일관성 분석**을 통해 이상치 탐지(예: 표준 편차 분석).

### **3. 클라우드 의존성 및 네트워크 지연**
- **설명**: 하이브리드 아키텍처에서 **온프레미스 ↔ 클라우드** 데이터 전송 지연이 발생하면, **실시간 처리 시스템**(예: 무인 농기계 제어)에 영향을 미침.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **에지 캐싱**: 자주 사용되는 데이터는 **온프레미스 캐시**(예: Redis)에 저장함.
  - **데이터 압축**: **Protocol Buffers** 또는 **Parquet** 형식으로 데이터 크기 줄임.
  - **로컬 학습 옵션**: **Lightweight 모델**(예: TinyML)을 에지 디바이스에 배포하여 **오프라인 추론** 지원.

### **4. 표준 준수 미비로 인한 상호운용성 문제**
- **설명**: 시스템이 **국내외 IoT 표준**(예: ISO/IEC 30141, oneM2M)을 준수하지 않으면, **기존 IoT 디바이스**와의 통합이 어려워짐.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (초기 설계 시 고려)
- **대응 방안**:
  - **표준화된 API 게이트웨이**: **oneM2M Base Protocol**과 **OData**를 지원하여 표준화된 데이터 접근 제공.
  - **스키마 레지스트리**: **Apache Atlas**를 사용하여 데이터 스키마를 표준화함.
  - **인증된 인프라**: **ETSI EN 303 645** 준수 인증 취득을 통해 보안 표준 보장.

### **5. 보안 위협 및 데이터 유출**
- **설명**: 중앙 플랫폼이 **사이버 공격**(예: DDoS, 데이터 탈취)에 노출되면, **민감한 농업 데이터**가 유출될 위험이 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **접근 통제(ACL)**: **RBAC**와 **ABAC**를 결합하여 데이터 접근 제한.
  - **데이터 암호화**: **AES-256**으로 데이터 전송 및 저장 암호화.
  - **침입 탐지 시스템(IDS)**: **KISA의 보안 기준**에 따라 **SIEM**(예: Splunk) 통합.
  - **정기 감사**: **ISO 27001** 준수에 따른 **보안 감사** 주기적으로 수행.

**※ 추가 고려사항**:
- **규제 준수**: **농업데이터 보호법**과 **개인정보 보호법**을 준수하여 **데이터 처리 기록**을 5년 이상 보관함.
- **확장성**: **Kubernetes**와 **Serverless** 아키텍처를 통해 **수평 확장**을 지원함.
- **모니터링**: **Prometheus + Grafana**를 사용하여 **실시간 성능 모니터링**을 수행함.
