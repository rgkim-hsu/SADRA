# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 센서 데이터 수집 및 중앙 제어 아키텍처 설계

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 다양한 종류의 센서(날씨, 줄기 온도, 토수)에서 데이터가 수집되어 ARSP 서버로 전송되고, 이를 기반으로 정밀 처방 지도를 생성한 후 VRI-Center Pivot 으로 제어 명령이 전송되는 시스템이 필요합니다. 이 과정에서 이기종 센서 데이터의 통합 처리와 일괄적인 처방 로직 실행이 핵심 과제로 대두됩니다. |
| **결정(Decision)** | 센서 데이터 수집층(Sensing Systems)과 제어 명령 실행층(VRI-Center Pivot) 사이에 ARSP 서버와 클라이언트(클라우드/로컬) 기반의 중앙 집중식 데이터 처리 및 의사결정 아키텍처를 채택함. |
| **근거(Rationale)** | 복잡한 데이터 융합(Weather, Soil, Temp) 및 처방 알고리즘 실행은 높은 계산 자원이 필요하여 중앙 서버에서 처리하는 것이 효율적입니다. 또한, ARSP 서버와 클라이언트의 양방향 통신을 통해 사용자는 실시간 모니터링과 개입이 가능합니다. |
| **결과(Consequences)** | **긍정적:** 데이터 분석의 일관성을 높이고, 복잡한 의사결정 로직을 단일화할 수 있습니다. <br> **부정적:** 중앙 서버 장애 시 전체 시스템 정지 위험이 존재합니다. |
| **트레이드오프(Trade-offs)** | 중앙 처리의 효율성 vs. 네트워크 지연 시의 시스템 가용성 (가용성을 높이기 위해 엣지 컴퓨팅 고려 필요). |

### ADR-002: IoT 표준 기반 상호운용성 보장

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템 구축 시 센서 통신 프로토콜 및 데이터 교환 형식이 표준화되어 있지 않을 경우, 다양한 기기들이 서로 통신하지 못하거나 데이터 해석이 어렵습니다. 특히 국제 표준 (ISO/IEC 30141) 및 국내 표준 (TTA 등) 에 맞춘 것이 필요합니다. |
| **결정(Decision)** | IoT 시스템 아키텍처 표준인 **ISO/IEC 30141:2024** 또는 **oneM2M** 규격에 따라 API 와 데이터 모델링을 정의함. 보안 요구사항은 **ITU-T X.1352** 를 준수함. |
| **근거(Rationale)** | 이 표준들은 재사용 가능한 설계와 업계 모범 사례를 제공하여, 시스템 확장성과 유지보수성을 보장합니다. 또한 글로벌 시장 진출 시 신뢰성을 높여줍니다. |
| **결과(Consequences)** | **긍정적:** 향후 센서 기기 업그레이드 시 호환성 유지가 용이해지고, 국제 인증 획득 가능. <br> **부정적:** 초기 표준 준수 비용 및 기술 전환 시간이 소요됨. |
| **트레이드오프(Trade-offs)** | 초기 개발 비용 증가 vs. 장기적인 유지보수 비용 절감 및 확장성 확보. |

### ADR-003: 보안 아키텍처 및 데이터 보호 전략

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 농업 IoT 환경에서는 외부 공격, 물리적 손실, 그리고 민감한 농업 데이터 (생산량, 작물 정보) 유출 등 보안 리스크가 존재합니다. 특히 ETSI EN 303 645 와 같은 사이버보안 요구사항을 충족해야 합니다. |
| **결정(Decision)** | **End-to-End Encryption** (IoT 기기와 서버 간 통신 암호화) 및 **Identity Management** (기기 인증) 를 필수 프로토콜로 도입. **ETSI EN 303 645** 표준에 따라 사이버보안 위험 평가를 수행함. |
| **근거(Rationale)** | 네트워크를 통한 제어 명령 조작이나 가짜 데이터 주입을 방지하여 물리적 안전 (작물 피해) 을 보호해야 합니다. |
| **결과(Consequences)** | **긍정적:** 신뢰성 높은 시스템 구축 및 보안 사고 예방. <br> **부정적:** 암호화 및 인증 관리로 인한 시스템 오버헤드 증가. |
| **트레이드오프(Trade-offs)** | 처리 속도의 소폭 감소 vs. 데이터 무결성과 보안성 강화. |

## ⚠️ 잠재적 위험 분석

### 1. [중앙 서버 단일 장애점 (SPOF)]
- **설명:** 'ARSP's Server'가 핵심 중개자로서 모든 데이터 처리 및 처방 명령 생성을 담당합니다. 이 서버가 네트워크 차단이나 장애를 겪을 경우, 사용자 인터페이스는 작동하지만 VRI-Center Pivot 으로 명령이 전달되지 않을 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **에지 컴퓨팅 도입:** 로컬 네트워크 내에 서버의 캐피어본 또는 엣지 디바이스를 설치하여 인터넷 연결이 끊겨도 로컬 센서 데이터를 임시 저장하고, 오프라인 모드에서 기본 처방 수행 가능하도록 설계.
  - **고가용성 (HA) 구조:** Active-Standby 서버 구성으로 하나의 서버가 다운되어도 즉시 백업 서버가 역할을 대체.

### 2. [통신 지연 및 실시간성 문제]
- **설명:** 센서 데이터가 서버로 오가고, 서버에서 처방 맵을 만들어서 다시 피벗으로 가려면 네트워크가 필요합니다. 농경지 등 네트워크 환경이 불안정하면 처방 로직이 지연되어 최적의 관개 시기를 놓칠 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:**
  - **QoS (Quality of Service) 설정:** IoT 통신 프로토콜 (예: MQTT over TLS) 을 사용하여 최소한의 데이터만 주고받고 지연 시간을 최소화.
  - **지역 네트워크 최적화:** 농장 내부에 LoRaWAN 또는 NB-IoT 게이트웨이 구축하여 외부 인터넷 의존도 줄이기.

### 3. [다양한 센서 데이터 불일치 및 정확도]
- **설명:** 'Weather Station', 'Canopy Temp. Sensors', 'Soil Water Sensors' 가 서로 다른 원리와 위치에서 데이터를 수집합니다. 이 데이터 간에 불일치가 발생할 경우 (예: 날씨 센서는 맑다고 하지만 토수 센서는 가뭄을 감지), 서버가 잘못된 처방을 내릴 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:**
  - **데이터 융합 알고리즘:** 서버에서 여러 센서 데이터의 평균값이나 신뢰도 가중치를 적용하여 최종 의사결정 데이터로 사용하는 로직 구현.
  - **센서 보정 프로세스:** 정기적인 센서 교정 지침 (표준화된 센서 설치 규격) 적용 및 소프트웨어 보정 옵션 제공.

### 4. [보안 취약점 및 악성 제어 명령]
- **설명:** 표준 (ISO/IEC 30141, ITU-T X.1352 등) 에 따라 보안이 강화되더라도, VRI-Center Pivot 등 현장 디바이스 또는 센서의 인증 키가 유출될 경우 외부자가 관개 시스템을 조작하거나 가짜 데이터를 주입하여 작물을 피해를 줄 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **로컬 네트워크 격리 (VLAN):** 농업 IoT 네트워크를 공개 인터넷망과 격리하고, 오직 관리용 네트워크만 허용.
  - **역방향 추적성:** 모든 제어 명령에 대한 로그와 디지털 서명을 사용하여 명령을 조작한 경우 원인을 규명 가능하도록 기록 유지.
  - **보안 인증서 사용:** 각 IoT 기기에 고유한 디지털 인증서 (X.509) 를 할당하여 기기 인증 강화.

### 5. [기존 장비와의 호환성 (Legacy System Integration)]
- **설명:** 이미 도입된 'VRI-Center Pivot' 이나 기존 센서들이 최신 IoT 표준 프로토콜 (MQTT, CoAP 등) 을 따르지 않을 경우, ARSP 시스템과 연동되지 않을 수 있습니다. 표준화 (oneM2M 등) 를 따르지 않는 경우 통합이 어려울 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:**
  - **가게웨어 게이트웨이:** 비표준 프로토콜을 사용하는 기존 장비에 게이트웨이를 설치하여 표준 프로토콜로 변환 (Adapter Pattern 적용).
  - **단계적 마이그레이션:** 신규 장비 도입 시 즉시 표준 호환 디바이스만 구매하고, 기존 장비는 게이트웨이를 통해 연결하는 정책 수립.
