# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 다원화된 프로토콜을 위한 통합 데이터 수집 아키텍처

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 데이터PARC 중앙 플랫폼은 MES(제조), ERP(기업), LIMS(품질), MDE(수동 입력), Data Historian(기록), 기타 소스(Excel 등) 등 이질적인 외부 시스템과 연동해야 합니다. 각 소스는 서로 다른 통신 기술 (SQL, API, OPC 등) 과 데이터를 생성하며, 이를 하나의 시계열 또는 관계형 데이터 모델로 통합하는 것이 핵심 과제입니다. 특히 기존 OT 환경(PLC, DCS) 과 IT 환경(ERP, MES) 이 공존하는 환경에서 상호 운용성을 확보해야 합니다. |
| **결정(Decision)** | `dataPARC` 를 중앙 허브 (Central Hub) 로 설계하며, 외부 시스템 유형에 따라 **하이브리드 인터페이스 패턴**을 적용합니다.<br>1. **SQL 기반 소스 (MES/ERP/LIMS/MDE):** JDBC 드라이버 및 표준 SQL 인터페이스를 통해 실시간 및 배치 처리를 지원.<br>2. **OPC 기반 소스 (Data Historian):** OPC Client 서버를 활용하여 OPC 태그를 표준화된 내부 데이터 모델로 매핑합니다.<br>3. **플랫 파일 소스 (Excel/WIS 등):** 커스텀 파서를 통한 주기적 ETL 처리를 제공합니다.<br>4. 내부 데이터는 관계형 DB 와 시계열 DB 를 혼용하는 하이브리드 스토리지 전략을 채택하여 분석 효율성을 극대화합니다. |
| **근거(Rationale)** | <br>- **상호 운용성 (Interoperability):** ISO/IEC 30141:2024 와 같은 IoT 아키텍처 표준에서 강조하는 공통 인터페이스 및 표준화 요구사항을 충족하기 위해 다양한 프로토콜 (SQL/OPC) 을 지원해야 합니다.<br>- **유연성:** ERP/MES 벤더 변경 시에도 데이터PARC 가 중재자 역할을 하여 핵심 비즈니스 로직을 보호할 수 있습니다.<br>- **데이터 일관성:** 다수의 소스에서 들어오는 데이터를 중앙 표준화하여 보고서 및 분석의 신뢰성을 높입니다. |
| **결과(Consequences)** | <br>**긍정:** 다양한 시스템과 통합이 쉬워지며, 기존 레거시 시스템 (Honeywell, Siemens 등) 과의 연결이 가능해집니다.<br>**부정:** 인터페이스 관리자가 복잡해지며, 각 소스별로 특화 드라이버를 관리해야 하는 오버헤드가 발생할 수 있습니다. |
| **트레이드오프(Trade-offs)** | 복잡한 통합 로직 (드라이버 관리) 과 높은 유연성/확장성 사이의 절충입니다. 통합 비용을 감수하더라도 시스템 전체의 가용성과 데이터 통합 능력을 확보하는 것이 우선입니다. |

## ⚠️ 잠재적 위험 분석

### 1. [데이터 일관성 및 동기화 문제]
- **설명:** MES, ERP, Data Historian 등 분산된 소스 시스템들은 각각 다른 시계 (Clock) 를 가지거나, 데이터 갱신 주기가 다릅니다 (예: MES는 실시간, ERP는 배치). 이로 인해 `dataPARC` 에 저장된 데이터가 시간 순서대로 정렬되지 않거나, 중복/누락이 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터PARC 내부에 타임스탬프를 통일하고, 외부 시스템 시계 동기화 (NTP) 를 강제합니다. 배치 처리 시 버전 관리 (Versioning) 를 적용하여 데이터 변경 이력을 추적합니다.

### 2. [단일 장애점 (SPOF) 위험]
- **설명:** 이미지에서 `dataPARC` 는 모든 외부 시스템 (MES, ERP, LIMS 등) 의 데이터를 모으는 중앙 노드로 묘사됩니다. 이 중앙 서버나 데이터베이스가 중단되면, 모든 외부 시스템의 데이터 수집과 분석이 멈추게 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** `dataPARC`를 클러스터링 (HA/Cluster) 으로 구성하여 고가용성을 확보합니다. 외부 소스와 별도의 데이터 수집 (Edge Collector) 을 두고, 장애 발생 시 백업 서버로 자동 장애 이관을 합니다.

### 3. [보안 및 네트워크 공격 벡터 증가]
- **설명:** 데이터PARC 는 ERP(기업 시스템), MES(제어 시스템) 등 민감한 정보를 포함하는 모든 시스템과 통신합니다. 특히 OPC를 통한 Historian 연동은 보안이 취약한 OT 구간과 IT 구간을 연결하므로, 해커가 이 경로를 통해 내부망으로 침투할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** OT 구간 (Historian, PLC) 과 IT 구간 (ERP, MES) 을 네트워크 구간화 (Segmentation) 합니다. OPC 연결 시 암호화 (TLS/SSL) 를 적용하고, API 및 SQL 인터페이스는 인증 (OAuth2, LDAP) 을强制执行합니다.

### 4. [성능 병목 현상 (Performance Bottleneck)]
- **설명:** `dataPARC` 는 다수의 시스템에서 대량의 데이터를 받습니다. 특히 Data Historian은 초 단위로 밀리세컨드 단위 데이터 (시계열) 를 보내는데, ERP/MES는 비교적 느린 트랜잭션을 보냅니다. 이 둘이 섞여서 `dataPARC` 의 성능 저하가 발생할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:** 시계열 데이터는 전용 시계열 DB (TSDB) 에, 관계형 데이터는 RDBMS 에 분리 저장하거나 (Sharding/Polyglot Persistence), 인메모리 캐싱을 활용하여 읽기 속도를 최적화합니다.

### 5. [벤더 종속성 및 호환성 이슈]
- **설명:** 이미지는 Honeywell, Siemens, ABB, OSIsoft 등 다양한 벤더 로고를 보여줍니다. 이들 벤더가 OPC 사양을 변경하거나, DB 구조를 업데이트하면 `dataPARC` 의 인터페이스 드라이버가 즉시 중단될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
