### ADR-001: **중앙집중식 데이터 처리 아키텍처 채택**

| 항목                | 내용                                                                                                                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**   | 스마트팜 시스템은 실시간으로 다양한 센서(온도, 습도, 조도 등)로부터 대용량 데이터를 수집하고, 이를 기반으로 환경 제어 장비(예: 환기시스템, 조명, 관개 시스템)를 자동으로 제어해야 함. 또한, 사용자 인터페이스와 모니터링 서비스를 통해 관리자가 시스템 상태를 모니터링하고 수동으로 제어할 수 있어야 함. 시스템 개념도에서 **서버(140)**가 모든 데이터의 중앙 허브 역할(예: S200, S214, S216 등)을 담당하며, 센서, 제어기기, 사용자 인터페이스 간의 데이터 흐름을 중개함. |
| **결정(Decision)**  | **중앙집중식 아키텍처**를 채택하여 모든 센서 데이터와 제어 명령이 서버를 통해 처리되도록 설계. 서버는 데이터 수집(S200), 사용자 정의/조회(S214), 관리자 설정(S216), 환경 제어(S220, S230, S255 등) 등을 통합 관리.                                                                                                                                            |
| **근거(Rationale)** | 1. **데이터 일관성**: 중앙 서버에서 모든 데이터를 통합 관리하여 데이터 중복 및 충돌을 방지.                                                                                                                                                                                                                                |

2. **실시간 제어**: 서버를 통해 센서 데이터와 제어 명령의 동기화로 실시간 환경 제어가 가능.
3. **확장성**: 새로운 센서나 제어기기 추가 시 서버에 연결만 하면 되므로 시스템 확장이 용이.
4. **관리 효율성**: 중앙에서 로그, 상태, 오류를 모니터링하여 유지보수 효율성 증가. || **결과(Consequences)** | **장점**: 데이터 통합 관리, 실시간 처리 가능, 시스템 확장 용이. **단점**: 서버에 단일 장애점(Single Point of Failure) 발생 가능성, 서버 과부하 시 시스템 전체 성능 저하. || **트레이드오프(Trade-offs)** | **장점**: 통일된 데이터 관리, 실시간성 보장, 유지보수 용이성. **단점**: 서버 의존도 높음, 서버 장애 시 시스템 마비 위험, 서버 성능이 시스템 전체 성능의 병목 현상 발생 가능. |

### ADR-002: **이벤트 기반 비동기 통신 프로토콜 채택**

| 항목                | 내용                                                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**   | 시스템은 센서에서 서버로 데이터 전송(S200), 서버에서 제어기기로 명령 전송(S220, S230 등), 사용자 인터페이스와 상호작용(S210, S212 등) 등 다수의 비동기적 데이터 흐름이 존재. 실시간성과 신뢰성이 요구됨. |
| **결정(Decision)**  | **MQTT(MQ Telemetry Transport) 프로토콜**을 사용하여 센서-서버-제어기기 간에 lightweight한 비동기 통신을 구현.                                               |
| **근거(Rationale)** | 1. **저전력/저대역폭**: 스마트팜 환경에서 센서가 저전력으로 동작해야 하며, 네트워크 대역폭이 제한적일 수 있음.                                                               |

2. **실시간성**: MQTT는 publish-subscribe 모델로 실시간 데이터 전송에 최적화.
3. **신뢰성**: QoS(Quality of Service) 레벨을 통해 메시지 전달 보장. || **결과(Consequences)** | **장점**: 네트워크 리소스 효율적 사용, 실시간 데이터 처리 가능, 메시지 손실 최소화. **단점**: MQTT 브로커가 단일 장애점이 될 수 있음, 복잡한 메시지 라우팅 시 구현 난이도 증가. || **트레이드오프(Trade-offs)** | **장점**: 실시간성, 저전력/저대역폭 최적화, 신뢰성 있는 메시지 전달. **단점**: 브로커 의존성, 메시지 순서 보장 어려움, 보안 구현(예: TLS) 필요. |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 서버 단일 장애점(Single Point of Failure)

* **설명:** 중앙 서버(140)에 장애가 발생할 경우, 전체 시스템의 데이터 수집, 제어, 모니터링 기능이 마비됨. 예를 들어, 서버 다운 시 센서 데이터(S200)가 처리되지 않고, 제어기기(S220, S230 등)가 명령을 받지 못해 환경 제어가 중단됨.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **이중화(Redundancy)**: 서버를 활성-대기(Active-Standby) 또는 활성-활성(Active-Active) 구성으로 이중화.
  * **자동 장애 조치(Failover)**: 장애 감지 시 자동으로 예비 서버로 전환.
  * **로드 밸런싱**: 트래픽을 분산하여 서버 과부하 방지.

* * *

### 2. 센서 데이터 오염 또는 손실

* **설명:** 외부 센서(120)에서 잘못된 데이터(예: 오류 값, 노이즈)가 수집되거나, 네트워크 문제로 데이터가 손실될 경우, 시스템이 잘못된 환경 제어 명령을 내릴 수 있음(예: 온도가 실제보다 높게 측정되어 냉방 시스템이 과도하게 가동).
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **데이터 검증**: 서버에서 수집된 데이터에 대해 범위(예: 온도 -10°C ~ 50°C) 및 통계적 검증(예: Z-score)을 수행.
  * **중복 센서**: 중요한 환경 변수(예: 온도, 습도)에 대해 다중 센서를 설치하여 교차 검증.
  * **데이터 재전송 메커니즘**: MQTT QoS 1 또는 2를 사용하여 메시지 손실 시 재전송.

* * *

### 3. 네트워크 지연 또는 단절

* **설명:** 센서-서버(S200) 또는 서버-제어기기(S220, S230) 간의 네트워크 지연 또는 단절로 인해 실시간 제어가 불가능해짐. 예를 들어, 온도 급등 시 서버가 제어 명령을 제시간에 전달하지 못해 작물이 손실될 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **로컬 캐시**: 제어기기에서 마지막 명령 캐시하여 네트워크 단절 시 일정 시간 동안 마지막 명령으로 동작.
  * **에지 컴퓨팅**: 서버의 일부 기능을 에지 디바이스(예: 게이트웨이)에서 처리하여 지연 시간 단축.
  * **네트워크 모니터링**: 지연 시간 및 패킷 손실률을 실시간 모니터링하고, 임계치 초과 시 알림.

* * *

### 4. 보안 취약점(무단 접근 및 데이터 변조)

* **설명:** 외부 공격자가 서버(140) 또는 사용자 인터페이스(40)에 무단 접근하여 데이터를 변조하거나, 제어기기를 조작할 경우(예: S210, S212를 통해 관리자 권한 획득), 시스템이 악의적으로 조작될 수 있음. 예를 들어, 관개 시스템을 과도하게 가동하여 토양을 손상시킬 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **인증 및 권한 관리**: 모든 접속에 대해 다단계 인증(MFA) 및 역할 기반 접근 제어(RBAC) 적용.
  * **데이터 암호화**: MQTT 메시지를 TLS로 암호화하고, 서버-데이터베이스 간에도 암호화된 채널 사용.
  * **로그 감사**: 모든 제어 명령 및 데이터 접근에 대해 로그를 기록하고, 이상 패턴 감지 시 알림.

* * *

### 5. 시스템 호환성 및 확장성 제한

* **설명:** 새로운 센서 또는 제어기기를 추가할 때(S255, S260 등), 기존 시스템과 프로토콜(예: MQTT) 또는 데이터 포맷이 호환되지 않을 경우, 통합에 많은 시간과 비용이 소요됨. 예를 들어, 특정 제조사의 센서가 MQTT를 지원하지 않을 경우, 추가 개발이 필요.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **표준 프로토콜 강제**: 모든 디바이스가 MQTT 또는 OPC UA와 같은 표준 프로토콜을 사용하도록 요구.
  * **Adapter 패턴**: 호환되지 않는 디바이스에 대해 어댑터(프록시) 서버를 통해 데이터 포맷 변환.
  * **API 게이트웨이**: 외부 시스템과 통합 시 API 게이트웨이를 통해 데이터 변환 및 라우팅.

* * *

### 6. 사용자 인터페이스(UI) 응답 지연

* **설명:** 사용자 인터페이스(40)에서 관리자가 실시간으로 시스템 상태를 모니터링(S210, S212)하거나 제어 명령을 내릴 때(S216), 서버의 과부하 또는 네트워크 지연으로 인해 UI 응답이 지연될 경우, 관리자가 제시간에 조치를 취하지 못할 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **UI 최적화**: 클라이언트 측 캐시 및 lazy loading을 통해 서버 부하 감소.
  * **WebSocket 사용**: 실시간 업데이트를 위해 WebSocket 프로토콜 사용.
  * **우선순위 처리**: 중요한 제어 명령은 우회 로직을 통해 우선 처리.
