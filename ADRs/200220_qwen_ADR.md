# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 이종 센서 데이터 통합 및 가시화 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 다양한 종류와 통신 프로토콜을 가진 센서 (기상관측, 온도/습도, CCTV)들이 이질적인 데이터를 생성하고 있으며, 이를 하나의 체계적인 시스템으로 통합하여 효율적으로 관리해야 하는 상황 |
| **결정(Decision)** | **통합제어기 (Integrated Controller)**를 핵심 허브 (Hub) 로 선정하여, 모든 센서 데이터를 수집하고 표준화된 형식으로 통합 관리 |
| **근거(Rationale)** | 이미지 상 센서 영역과 제어 영역이 명확하게 분리되어 있으며, 센서들이 통합제어기로 데이터를 전송함. 이를 통해 다중 센서 데이터를 중앙에서 일관성 있게 처리하고 로그화할 수 있음 |
| **결과(Consequences)** | 다양한 센서를 추가하거나 교체할 때 통신 인터페이스만 변경하면 통합 시스템에 쉽게 연결 가능 (확장성 유지) |
| **트레이드오프(Trade-offs)** | 통합제어기에 과도한 부하가 발생할 수 있어 고성능 처리능력이 필요하며, 중앙 집중화 모델의 단일 장애점 (Single Point of Failure) 리스크 존재 |

### ADR-002: 지능형 자동 제어 루프 (Smart Control Loop) 아키텍처 구축

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 수집된 센서 데이터를 기반으로 현장에서 즉시 밸브나 컨베이어 벨트 등을 제어해야 하며, 사용자의 원격 지시도 실시간으로 처리되어야 하는 실시간성 요구 |
| **결정(Decision)** | **통합제어기**에서 센서 데이터를 분석한 후, 현장에 위치한 **전자 밸브**와 **컨베이어 벨트** 등 구동기를 직접 제어하는 클로스트 루프 제어 아키텍처 설계 |
| **근거(Rationale)** | 이미지에서 통합제어기가 통합된 상태이며, 이는 현장의 밸브와 컨베이어를 직접 제어한다는 것을 시사함. 지연이 허용되지 않는 환경 (예: 홍수 방류, 물 순환) 에 적합함 |
| **결과(Consequences)** | 사용자가 스마트폰을 통해 상황을 모니터링하지만, 시스템이 자동으로 최적의 작동을 하거나 위험 상황에서 즉시 대응 가능 (자동화 수준 높음) |
| **트레이드오프(Trade-offs)** | 자동 제어 로직이 잘못 설계될 경우 시스템 오작동으로 인한 물리적 피해 (염전, 농작물 손상) 가 발생 가능 |

### ADR-003: 모바일 중심의 원격 관제 아키텍처 도입

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 현장 기술자는 물론 관리자들도 스마트폰을 통해 시스템 상태를 실시간으로 파악하고 지시해야 함 |
| **결정(Decision)** | **인터넷**을 통해 통합제어기와 **스마트폰**을 연결하여 양방향 통신 (상태 모니터링 및 명령 발령) 가능하도록 아키텍처 설계 |
| **근거(Rationale)** | 이미지 중간에 '인터넷' 아이콘이 중앙에 위치하고, 그 아래 스마트폰으로 연결됨. 이는 클라우드/네트워크 기반의 접근성을 의미 |
| **결과(Consequences)** | 현장에 없어도 상황을 관리 가능 (원격 관리) 및 비상 상황 시 즉각적인 대응 (긴급 제어) |
| **트레이드오프(Trade-offs)** | 네트워크 연결 상태에 따라 서비스 품질이 제한될 수 있으며, 통신 대역폭 확보가 필수적 |

## ⚠️ 잠재적 위험 분석

### 1. [네트워크 장애 및 통신 단절]
- **설명:** 외부 환경 (바다, 습한 환경) 이나 통신사 문제를 포함한 네트워크 연결이 불안정할 경우, 원격 제어 기능이 마비되고 센서 데이터가 수집되지 않을 수 있음
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (해안 지역 특성상 통신 불안정 요소 존재)
- **대응 방안:** 통합제어기에 오프라인 모드가 작동하거나 로컬 자동 제어 기능이 활성화되도록 아키텍처 설계 (Network Isolation & Fallback Mode)

### 2. [센서 오작동 및 데이터 신뢰성 저하]
- **설명:** 염분 침식, 습기, 먼지 등으로 인해 센서 (기상, 온도/습도) 가 오작동하거나 정확한 데이터를 측정하지 못하여 잘못된 제어 명령이 발령될 수 있음
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 센서 다중화 및 교차 검증 (Redundancy) 구현, 센서 보호 케이스 설치 및 정기적 교정 절차 마련

### 3. [외부 사이버 보안 공격]
- **설명:** 이미지와 문서를 보면 IoT 보안 기준 (ITU-T X.1352, ETSI 등) 이 언급되어 있음. 시스템이 연결되어 있으므로 해커에 의해 센서 데이터 조작, 원격 제어 도난 (예: 밸브 폭격) 에 취약함
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 강력한 인증/암호화 프로토콜 (TLS/DTLS) 사용, 네트워크 분리 (Segmentation) 및 IDS/IPS 등 보안 장비 도입

### 4. [실시간 제어 지연으로 인한 제어 실패]
- **설명:** 통합제어기에서 현장 밸브 등으로 명령을 전달할 때 네트워크 지연 (Latency) 이 발생할 경우, 급변하는 기상 조건에 대응하지 못해 피해 발생 가능
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 제어 명령은 로컬 네트워크 (LAN) 를 통해 처리하며, 인터넷을 통한 데이터만 수집하는 등 제어/관리 트래픽 분리 아키텍처 적용

### 5. [통합제어기의 단일 장애점 (SPOF)]
- **설명:** 시스템의 핵심인 통합제어기 하나에 장애가 발생하면 데이터 수집과 제어 기능 전체가 마비될 수 있음 (이미지의 중앙부에 위치한 핵심 요소)
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** 핫스탠바이 (Hot Standby) 시스템을 구축하거나, 주요 기능 (데이터 수집) 을 엣지 디바이스에서 분산 처리하도록 아키텍처 변경
