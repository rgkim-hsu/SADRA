# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: [중앙 집중형 데이터 통합 및 처리 모듈 (Hub-And-Spoke) 아키텍처 채택]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **분산된 데이터 소스의 통합 처리 필요성:** 시스템은 사용자의 요청, 이미지 제공모듈 (100), 기준정보 DB (300), 영농정보 DB (400) 등 서로 다른 소스의 데이터를 모두 수집하고 처리해야 함. 기존 아키텍처는 각 기능이 독립적으로 존재할 경우 데이터 일관성이 떨어질 수 있음.<br>**주요 과제:** 다양한 원천 데이터를 신뢰성 있고 일관된 형태로 처리하여 '생육정보 산출모듈'을 통해 정확한 결과물을 제공하는 것. |
| **결정(Decision)** | **생육정보 산출모듈 (200) 을 중앙 허브 (Hub) 로 기능화:** 모든 데이터 흐름 (이미지 입력, 기준 DB 조회/수정, 영농 DB 조회/수정, 사용자와의 상호작용) 이 이 모듈을 경유하도록 설계. 이를 통해 데이터 변환, 필터링, 집계 로직을 한곳에 캡슐화하고,<br>**양방향 데이터 동기화 전략 도입:** 기준정보 DB 와 영농정보 DB 는 생육정보 산출모듈을 통해 양방향으로 연동되도록 설계하여, 실시간 업데이트와 데이터 무결성을 확보.<br>**인터페이스 표준화:** TTA 표준 과제 (예: '스마트 온실 서비스를 위한 데이터 관리 요구 사항 및 기능 구조') 및 ISO/IEC 30141 등 국제 표준을 참고하여 모듈 간 API 및 데이터 형식을 정의. |
| **근거(Rationale)** | **기능적 효율성:** DFD 분석 결과, 모든 외부 입력/출력이 '생육정보 산출모듈'에 집중되어 있어, 여기서 처리 로직을 관리하는 것이 가장 효율적임.<br>**상호 운용성:** TTA 등 국내 표준 (TTAK.KO-10.1170 등) 이나 ISO/IEC 30141:2024 등을 따르는 것은 시스템의 확장성과 다른 시스템과의 연동 가능성을 높임.<br>**유지보수성:** 비즈니스 로직을 중앙 모듈에 모으면 특정 소스 데이터의 변화에 대한 로직 수정이 집중적으로 이루어져 유지보수가 용이함. |
| **결과(Consequences)** | **긍정적:** 시스템 로직의 일관성 유지, 데이터 흐름의 가시성 확보, 개발 및 운영 비용 절감.<br>**부정적:** 중앙 모듈의 부하 증가, 모듈 장애 시 전체 시스템 마비 가능성 (단일 고장점 이슈는 ADR-002 를 통해 보완 필요). |
| **트레이드오프(Trade-offs)** | **장점:** 데이터 일관성 유지, 로직 재사용성 높음.<br>**단점:** 중앙 모듈 성능 한계에 따른 확장성 저하 가능. |

## ⚠️ 잠재적 위험 분석

### 1. [단일 고장점 (Single Point of Failure) 위험]
- **설명:** 모든 데이터 흐름이 중앙의 '생육정보 산출모듈 (200)'을 경유하도록 설계되어 있으므로, 이 모듈에 장애가 발생하거나 성능 병목이 생기면 전체 시스템 (이미지 수집, DB 연동, 사용자 응답) 이 마비될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (하루 중 정점이 없거나 피크타임에 발생 시)
- **대응 방안:** 
  - **클러스터링/리플리케이션:** 핵심 모듈 로직을 여러 인스턴스로 분산하여 처리 (Stateless 디자인).
  - **회복 시나리오:** 모듈 장애 시 기본값으로 동작하거나 로컬 캐시 (Redis 등) 에서 임시 데이터를 제공하는 임시 모드 활성화.
  - **재부팅 자동화:** 건강 상태 모니터링 (Health Check) 을 통해 장애 시 자동 재시작 (Auto-recovery) 시스템 구축.

### 2. [네트워크 대역폭 병목 (Bandwidth Bottleneck) 위험]
- **설명:** '이미지 제공모듈 (100)'에서 '생육정보 산출모듈 (200)'로 대용량 이미지 데이터를 지속적으로 전송할 경우, 네트워크 대역폭이 차고 모듈의 처리 성능이 저하될 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (이미지 데이터가 많거나 고해상도가 많은 환경에서)
- **대응 방안:** 
  - **이미지 최적화:** 전송 전 이미지 압축 또는 축소 (Thumbnail) 처리.
  - **배치 (Batching) 전송:** 이미지를 단건이 아닌 일정 간격 또는 일정 개수 기준으로 묶어서 전송 (Batch Processing).
  - **CDN 및 캐싱:** 이미지 데이터를 캐싱하여 반복 전송 시 대역폭 감소.

### 3. [외부 DB 연결 장애 (External Dependency Failure) 위험]
- **설명:** '기준정보 데이터베이스 (300)' 및 '영농정보 데이터베이스 (400)'가 외부에 존재하므로, 네트워크 분단, 서버 장애, DB 엔진 버전 호환성 문제 등으로 인해 정상적인 데이터 조회 및 수정이 불가능해짐.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (외부 서비스 불안정성)
- **대응 방안:** 
  - **로컬 캐시 전략:** 외부 DB 가 응답하지 않을 때, 마지막 정상 데이터를 기반으로 로컬 캐시를 활용하여 임시로 서비스 운영 (Offline Mode).
  - **재시도 로직 (Retry Logic):** DB 연결 오류 시 일정한 간격으로 자동 재시도.
  - **서버리스 아키텍처 활용:** DB 연동 기능을 별도의 마이크로서비스로 분리하여 고립화.

### 4. [데이터 무결성 및 동기화 오류 (Data Integrity & Sync Issues) 위험]
- **설명:** '기준정보 데이터베이스 (300)'와 '생육정보 산출모듈 (200)' 간에 양방향 데이터가 오가지만, 네트워크 지연이나 트랜잭션 처리 오류로 인해 양쪽 데이터가 불일치 (Data Divergence) 될 수 있음. 특히 동시성 문제가 발생할 경우.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low (올바른 트랜잭션 처리 시)
- **대응 방안:** 
  - **트랜잭션 관리:** DB 연동 시 ACID 특성이 보장되는 트랜잭션 사용.
  - **버전 관리 (Versioning):** 데이터 변경 시 버전 관리 (Optimistic Concurrency Control) 를 적용하여 충돌 방지.
  - **대응 및 감사:** 데이터 불일치 감지 시 자동 경고 및 로그 남기기, 주기적 데이터 감사 스케줄링.

### 5. [보안 취약점 (API Exposure & Unauthorized Access) 위험]
- **설명:** '사용자단말 (400)'과 '생육정보 산출모듈 (200)' 간 통신은 API 를 통해 이루어지므로, 인증/인가 (Authentication/Authorization) 가 취약하거나, DDoS 공격 시 모듈이 다운될 수 있음. 특히 ISO/IEC 30141 등 보안 표준을 준수하지 않을 경우.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (성실한 보안 관리를 하더라도)
- **대응 방안:** 
  - **보안 프로토콜:** HTTPS, OAuth 2.0, JWT 등을 활용하여 안전한 통신 보장.
  - **방화벽 및 WAF:** 외부 공격 차단 및 필터링 시스템 도입.
  - **접근 제어:** 역할 기반 접근 제어 (RBAC) 를 통해 모듈 접근 권한 엄격히 제한 (ETSI EN 303 645 준수).
