# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 이벤트 기반의 모듈형 (Event-Driven, Modular) 플랫폼 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 '센싱 $\rightarrow$ 관리 $\rightarrow$ 분석 $\rightarrow$ 제어'의 연속적인 데이터 파이프라인을 갖추고 있으며, 데이터 소스(센서)의 다양성, 실시간 처리 요구사항, 그리고 지능적인 의사 결정(Planning)이 핵심입니다. 기존의 모놀리식(Monolithic) 아키텍처로는 수많은 이기종 데이터 흐름과 모듈 간의 결합도를 효과적으로 관리할 수 없습니다. |
| **결정(Decision)** | 시스템의 핵심 백본(Backbone)을 **이벤트 스트리밍(Event Streaming)** 기반의 **마이크로 서비스 아키텍처(MSA)**로 구성합니다. 데이터 수집/저장/처리 계층을 명확히 분리하고, 국제 표준(ISO/IEC 30141, oneM2M)에 부합하는 메시징 프로토콜(MQTT, Kafka 등)을 표준으로 채택합니다. |
| **근거(Rationale)** | 1. **확장성(Scalability):** 각 기능(예: 온도 분석 모듈, 제어 명령 모듈)을 독립적인 서비스로 분리하여, 특정 기능의 부하 증가 시 전체 시스템에 영향을 주지 않고 독립적인 스케일 아웃이 가능합니다. 2. **상호운용성(Interoperability):** 이벤트 메시지 표준을 사용함으로써, 센서, 클라우드, 분석 모듈 간의 물리적 연결에 관계없이 논리적 결합도를 최소화하여 이기종 기기 및 소프트웨어의 통합을 용이하게 합니다. 3. **실시간 대응:** 이벤트 기반 구조는 데이터가 발생하는 순간(Event)에 즉시 알림 및 처리가 가능하여, 제어(Control)와 같은 실시간성이 중요한 기능 구현에 필수적입니다. |
| **결과(Consequences)** | **긍정적:** 시스템의 탄력성(Resilience)과 확장성이 극대화됩니다. 새로운 기능(예: 예측 유지보수) 추가가 빠르고, 개별 컴포넌트 업데이트가 용이합니다. **부정적:** 서비스 간의 통신이 많아지므로, 시스템 설계 및 초기 배포가 매우 복잡해지며, 트랜잭션 추적(Distributed Transaction Management)이 어려워질 수 있습니다. |
| **트레이드오프(Trade-offs)** | **[복잡성 증가]** 초기 설계 및 운영 복잡성이 매우 높습니다. 이는 전문적인 플랫폼 엔지니어링 지식을 요구합니다. **VS** **[최고의 유연성과 확장성]** 시장 변화나 기능 추가에 대한 대응 속도가 빠르며, 예측 불가능한 대규모 데이터 증가(Data Sprawl)에도 구조적으로 안정합니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 무결성 및 위변조 위험 (Data Integrity & Tampering Risk)
- **설명:** 센싱 및 모니터링 단계에서 데이터 수집 게이트웨이 또는 통신 경로가 해킹당하거나, 데이터 전송 과정에서 물리적/논리적 조작이 발생하여 오염된 데이터가 분석 엔진으로 유입되는 시나리오입니다. (Ex: 센서 값 위변조)
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 모든 센서와 게이트웨이에 신뢰할 수 있는 하드웨어 보안 모듈(HSM)을 적용하고, 데이터 전송 시마다 **상호 인증(Mutual Authentication)**을 수행하며, 페이로드에 대한 **디지털 서명(Digital Signature)** 및 **HMAC**을 적용하여 무결성 체크를 필수로 수행해야 합니다.

### 2. 엔드-투-엔드 지연 위험 (E2E Latency Risk)
- **설명:** 실시간 제어가 요구되는 환경(예: 축사 온도 급변 시 자동 환기)에서, 센싱-클라우드 전송-분석-제어 신호 명령 전파의 전체 과정(End-to-End)에서 지연(Latency)이 발생하여 적절한 조치가 취해지지 못하는 위험입니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 중요도가 높은 제어 루프(Critical Control Loop)는 **엣지 컴퓨팅(Edge Computing)**을 통해 데이터 전처리 및 즉각적인 제어 결정을 클라우드 의존 없이 현장 게이트웨이 레벨에서 수행하도록 아키텍처를 설계해야 합니다. (분산 처리 방식 채택)

### 3. 표준 부재로 인한 상호운용성 위험 (Lack of Interoperability Risk)
- **설명:** 시스템을 구성하는 하드웨어 및 소프트웨어 모듈들이 서로 다른 제조사의 독자 규격이나 버전의 API를 사용함에 따라, 데이터 포맷이나 인터페이스 정의가 불일치하여 데이터 연동이 불가능해지는 상황입니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **모델 기반 시스템 엔지니어링(MBSE)** 접근법을 채택하고, **데이터 모델링 언어(예: OWL)**를 활용하여 시스템 전체의 공통 데이터 모델(Common Data Model)을 정의해야 합니다. 모든 API는 반드시 정의된 이 공통 모델을 기준으로 게이트웨이 계층에서 변환(Adaptation Layer)하는 구조를 강제합니다.

### 4. 데이터 폭증 및 스토리지 병목 위험 (Data Sprawl & Storage Bottleneck Risk)
- **설명:** 센싱 데이터의 종류와 양이 지속적으로 증가(데이터 폭증)하여, 데이터 레이크나 시계열 데이터베이스(Time-Series DB)의 수용 능력(Ingestion Rate)을 초과하거나, 검색 및 분석에 필요한 스토리지 접근 시간이 길어지는 병목 현상이 발생할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 모든 데이터를 원본 그대로 저장하기보다, **데이터 라이프사이클 관리(Data Lifecycle Management)** 정책을 수립해야 합니다. 실시간 분석에 필요한 데이터는 핫 스토리지에, 장기 분석에 필요한 데이터는 콜드 스토리지에 적절히 분산하고, 정기적인 데이터 정제 및 요약(Aggregation) 파이프라인을 구축합니다.

### 5. 제어 논리의 복잡성 및 충돌 위험 (Control Logic Complexity & Conflict Risk)
- **설명:** 여러 개의 독립적인 분석 모델(예: 습도 예측 모델, 에너지 효율화 모델)이 동시에 작동하여 서로 다른 제어 명령(Actuation Command)을 내리고, 이 명령들이 충돌하거나 비논리적인 제어 루프를 형성하여 실제 시스템에 악영향을 미치는 경우입니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 제어 명령은 반드시 **최상위 제어 모듈(Orchestration Layer)**을 거치도록 합니다. 이 모듈은 개별 분석 결과가 제어 명령으로 변환될 때, **상위 우선순위 로직(Priority Logic)**과 **안전 범위 검증(Safety Constraint Check)**을 거쳐야 하며, 명시적인 충돌 감지 및 경고 시스템(Conflict Detection System)을 구현해야 합니다.
