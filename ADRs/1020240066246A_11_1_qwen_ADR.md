## 📋 ADR (Architecture Decision Record)

### ADR-001: 기능 모듈화 및 제어부 중심 아키텍처 도입

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 다양한 센서 데이터 수집, 실시간 분석, 제어 신호 생성, 알람 처리, 리포트 생성 등 복잡한 기능을 단일 시스템으로 통합해야 함. 시스템은 입출력부 (110) 를 통해 외부와 상호작용하며, 제어부 (120) 를 통해 로직 처리가 이루어짐. |
| **결정(Decision)** | 제어부 (120) 를 중심으로 실시간 제어 (120a), 제어량 분석 (120b), 알람 (120c), 노이즈 모니터링 (120d), 원격 제어 (120e), 리포트 (120f) 기능을 독립 모듈로 분리하여 설계. |
| **근거(Rationale)** | **유지보수성:** 각 모듈 (120a~f) 이 독립적이므로, 특정 기능 (예: 노이즈 필터링) 이 변경될 때 전체 시스템에 미치는 영향 최소화.<br>**확장성:** 표준화 가이드 (TTA, ISO/IEC 30141:2024) 에 따라 기능 추가 시 기존 구조에 쉽게 통합 가능.<br>**보안:** 각 기능 모듈이 분리되어 있어 권한 관리 및 보안 정책 적용이 용이함. |
| **결과(Consequences)** | ✅ **장점:** 시스템의 가독성 향상, 병렬 처리로 인한 처리 속도 개선, 특정 기능 오류 시 시스템 전체 다운 위험 감소.<br>❌ **단점:** 모듈 간 통신 (예: 120a 에서 120b 로의 데이터 전달) 을 위한 내부 통신 프로토콜 정의 필요 (추가 오버헤드 발생 가능). |
| **트레이드오프(Trade-offs)** | 모듈화 (유지보수성 +) vs 내부 통신 복잡도 (성능 -). |

### ADR-002: 다중 인터페이스 중재 아키텍처 (Multimodal Interface Management)

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 제어용 I/O IF (130), 송수신부 (140), 데이터베이스 (150), 음성입출력장치 (160) 등 다양한 외부 인터페이스와 상호작용해야 함. |
| **결정(Decision)** | 모든 외부 인터페이스 (130, 140, 150, 160) 는 제어부 (120) 에 집중되어 관리됨 (Centralized Mediation). 제어부 (120) 가 외부 요청을 모듈 (120a~f) 로 라우팅하고 처리 결과를 인터페이스로 전달. |
| **근거(Rationale)** | **상호운용성:** OCF, Matter 등 표준과 호환되도록 제어부 내부에서 표준 인터페이스 (API) 를 제공.<br>**일관성:** 음성 (160), 디스플레이, DB (150) 등 다양한 출력 장치에서 동일한 제어 논리 (120) 를 기반으로 정보를 제공하여 오류 방지.<br>**보안:** 네트워크 트래픽 (140) 과 I/O (130) 를 제어부 (120) 에서 필터링하여 외부 공격 차단. |
| **결과(Consequences)** | ✅ **장점:** 하드웨어/소프트웨어 추상화 (Abstraction) 로 디바이스 교체 시 시스템 로직 변경 최소화.<br>❌ **단점:** 제어부 (120) 가 병목 (Bottleneck) 지점 역할 가능성. (대규모 트래픽 시 성능 저하 위험). |
| **트레이드오프(Trade-offs)** | 중앙 집중식 관리 (보안성 +, 일관성 +) vs 단일 실패 지점 (SPOF 위험). |

### ADR-003: 보안 및 표준 준수 아키텍처

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜/사물인터넷 기기로서 ETSI EN 303 645, ISO/IEC 27030, ITU-T X.1352 등의 보안 표준을 준수해야 함. |
| **결정(Decision)** | 제어부 (120) 내부의 모든 모듈 (특히 원격 통신 제어 120e, 데이터베이스 150 관련) 에 보안 계층 (Encryption, Authentication) 을 적용. |
| **근거(Rationale)** | **규정 준수:** 국제 표준 (ISO/IEC, ITU-T) 과 국내 표준 (TTA) 을 반드시 준수해야 시장 진입 가능.<br>**데이터 무결성:** 센서 데이터 (110) 와 제어 신호가 유출되거나 변조되지 않도록 암호화. |
| **결과(Consequences)** | ✅ **장점:** 글로벌 시장 진출 시 인증 획득 용이성 증가, 사용자 신뢰도 확보.<br>❌ **단점:** 암호화 오버헤드로 인한 처리 속도 감소, 보안 키 관리 복잡도 증가. |
| **트레이드오프(Trade-offs)** | 보안 강화 (위험 감소 -) vs 성능 및 비용 증가. |

## ⚠️ 잠재적 위험 분석

### 1. 실시간 제어 지연으로 인한 시스템 불안정

- **설명:** 입출력부 (110) 를 통해 들어오는 센서 데이터가 실시간 설비 제어 모니터링 모듈 (120a) 로 전달되는 과정에서, 데이터베이스 (150) 저장이나 음성입출력 (160) 같은 비핵심 작업이 병행 처리될 경우 실시간 제어가 지연될 수 있음. 특히 스마트팜 환경에서 온도/습도 제어가 늦어지면 작물 피해나 설비 고장으로 이어질 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **비동기 처리:** 비핵심 기능 (리포트 120f, 알람 기록 120c) 은 무거운 동기 처리가 아닌 비동기 방식 (Queue 등) 으로 분리.
  - **레벨링 (Leveling):** 제어부 (120) 내부에 실시간 우선순위 큐를 구현하여 120a/120e(원격 제어) 신호의 우선순위를 최상위, 리포트/저장은 최하위로 설정.

### 2. 노이즈에 의한 오작동 및 제어 오동작

- **설명:** 노이즈 모니터링 분석 모듈 (120d) 이 외부 간섭이나 센서 오작동에 의해 발생하는 노이즈를 정확히 필터링하지 못하면, 실제 제어 신호를 방해하거나 가짜 알람 (120c) 을 발생시킬 수 있음. 이는 시스템 신뢰도를 크게 떨어뜨림.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **다중 센서 퓨전:** 단일 센서 신호 대신 여러 센서 데이터를 융합하여 노이즈 식별 정확도 향상.
  - **가정성 검증:** 120d 에서 받은 데이터를 물리학적 모델 (예: 온도 상승 속도 한계) 과 비교하여 비현실적인 데이터는 노이즈로 간주하고 배제.

### 3. 보안 취약점으로 인한 해킹 및 데이터 유출

- **설명:** 제어용 I/O IF (130) 또는 송수신부 (140) 를 통한 외부 공격 시, 데이터베이스 (150) 의 민감한 데이터 유출이나, 음성입출력장치 (160) 를 통한 물리적 제어 장악 (IoT 봇넷 등) 위험이 있음. ETSI EN 303 645 등 보안 표준 준수를 이행했더라도 새로운 취약점 (Zero-day) 발생 가능.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (IoT 환경 특성상)
- **대응 방안:**
  - **방화벽 및 침입 탐지:** 140(송수신부)入口处에 방화벽 (Firewall) 및 IPS(침입 방지 시스템) 배치.
  - **네트워크 분할 (Segmentation):** 제어 네트워크와 관리 네트워크를 물리/논리적으로 분리.
  - **정기 보안 감사:** ISO/IEC 27030 가이드라인에 따라 정기적인 보안 취약점 테스트 수행.

### 4. 데이터베이스 및 저장소 부하

- **설명:** 시스템이 장시간 운전되며 대량의 센서 데이터를 생성하면, 데이터베이스 (150) 와 리포트 제공 모듈 (120f) 이 데이터 저장 및 조회 요청에 부하를 받아 시스템 응답성이 떨어질 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **인메모리 캐싱:** DB 대신 Redis 등 인메모리 데이터베이스를 임시 캐싱으로 활용.
  - **데이터 아카이빙:** 구 데이터는 차분 저장 (Compressed/Archived) 이나 클라우드 객체 스토리지 (S3 등) 로 이동하여 메인 DB 용량 감소.
  - **인덱싱 최적화:** 쿼리 성능을 위해 데이터베이스 인덱싱 전략 최적화.

### 5. 모듈 간 상호작용 복잡도 증가로 인한 버그

- **설명:** 제어부 (120) 내부에 6 개 모듈 (120a~f) 이 존재하며, 각 모듈이 서로 데이터를 교환하면 (예: 120a->120b->120f), 데이터 형식 불일치, 경쟁 조건 (Race Condition), 데드락 등 소프트웨어 복잡도가 급증하여 예상치 못한 버그가 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
  - **명확한 인터페이스 정의:** 모듈 간 데이터 주고받는 API 명세를 TTA 표준 (예: TTAK.KO-10.1170) 이나 OpenAPI(Swagger) 형식으로 명확히 정의하고 문서화.
  - **유닛 테스트 자동화:** 각 모듈별 유닛 테스트 (Unit Test) 와 모듈 간 통합 테스트 (Integration Test) 를 CI/CD 파이프라인에 자동 포함하여 버그 조기 발견.
