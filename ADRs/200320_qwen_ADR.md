# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 동적 상태 기반 환경 제어 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 및 축사 환경을 위한 자동화 제어 시스템이 요구됨. 고정된 제어 로직이 아닌, 온도, 습도, 가스 농도 등 실시간 환경 변수에 민감하게 반응하여 시스템 상태를 동적으로 관리할 필요가 있음. 특히, 극단적인 상태 (고온/저온/오염) 에서는 즉시 조치하고, 정상 상태에서는 에너지를 절약하는 적응형 시스템이 요구됨. |
| **결정(Decision)** | 시스템은 단일 정적 제어 로직 대신 **상태 머신 (State Machine) 기반의 계층적 제어 아키텍처**를 채택함. 상위 단계에서는 온도 (Temperature) 를 기반으로 전체 시스템을 '고온/저온/정상'으로 구분하고, 하위 단계에서는 습도 (Relative Humidity) 및 가스 (CO2, NH3) 를 세분화된 상태로 관리하는 이중 제어 레이어를 구현함. |
| **근거(Rationale)** | - **적응성:** 외부 환경 변화 (날씨, 축사 내 열화) 에 유연하게 대처할 수 있음.<br>- **효율성:** 불필요한 제어 동작을 줄이고, 오작동을 최소화하여 자원 (에너지를) 절약할 수 있음.<br>- **확장성:** 새로운 가스 센서나 습도 센서를 추가할 때 상태 전이 조건을 단순히 수정하면 되므로 유연함.<br>- **문서 근거:** ISO/IEC 30141:2024 (IoT 참조 아키텍처) 이 요구하는 재사용 가능한 설계 및 업계 모범 사례와 일치함. |
| **결과(Consequences)** | - **긍정:** 시스템 안정성 및 신뢰도 증가, 에너지 효율 향상, 다양한 환경 변수 통합 용이.<br>- **부정:** 상태 전이 로직이 복잡해져 유지보수 비용 증가 가능성, 초기 개발 시간 소요 (State Machine 설계 및 검증 필요). |
| **트레이드오프(Trade-offs)** | 복잡한 상태 로직 vs 단순화된 정적 제어 로직 사이에서 적응성과 구현 난이도를 균형 있게 선택함. |

## ⚠️ 잠재적 위험 분석

### 1. 센서 데이터 편향 (Sensor Data Bias)

- **설명:** 온도, 습도, CO2, NH3 센서의 오차나 고장, 혹은 외부 간섭 (예: 태양광 직접 조사) 으로 인해 시스템이 잘못된 상태 (예: 고온 상태) 로 오인정식하여 불필요한 냉각 장비를 가동하거나, 실제 위험 상황에 반응하지 않는 사례가 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
  - 다중 센서 사용 (Redundancy) 및 데이터 평균화 필터링 적용
  - 이상치 탐지 알고리즘 (Outlier Detection) 구현하여 특정 패턴의 데이터를 실시간으로 필터링
  - 정기적인 센서 교정 프로세스 수립

### 2. 상태 전이 지연 (State Transition Latency)

- **설명:** 환경 변수 (온도 등) 가 '전이 범위' (@) 를 벗어났음에도, 제어 시스템이 이를 감지하고 'Normal State'로 다시 전환하거나 다른 상태로 이동하는 데 시간 차이가 발생하면, 해당 상태가 유지되는 동안의 손상 (예: 고온 상태가 유지될 때 가축 스트레스) 이 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 
  - 실시간 모니터링 및 상태 전이 지연 시간 모니터링
  - 소프트웨어 업데이트 시 실시간 성능 최적화 (Latency Reduction)
  - 시스템 오버로드 시 우선순위 조정 (Priority Scheduling)

### 3. 제어 알고리즘의 복잡성 증가 (Control Logic Complexity)

- **설명:** '온도 기반 제어'와 '습도 및 가스 기반 제어'가 분리되어 있으나, 실제 구현 시 두 단계 간의 상호작용 (Interference) 이 고려되지 않아 시스템이 충돌하거나 예측 불가능한 동작을 보일 수 있음. 또한, 상태 전이 조건 (T-indoor > T-high + @ 등) 이 너무 복잡해지면 버그 발생 확률 증가.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
  - 상태 머신 (State Machine) 모델의 단순화 및 모듈화
  - 자동화된 단위 테스트 (Unit Test) 및 상태 전이 검증 툴 사용
  - 아키텍처 검토 (Architecture Review) 주기적 수행

### 4. 보안 취약점 (Security Vulnerability)

- **설명:** IoT 표준 (예: ETSI EN 303 645) 에 맞지 않는 보안 조치가 적용되어, 제어 신호 (온도/습도 조절 명령) 가 해커에 의해 조작될 경우, 악의적인 온도/습도 조종으로 농작물이나 가축에 치명적인 피해가 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
  - 암호화 통신 (End-to-End Encryption) 적용
  - 인증 및 권한 부여 강화 (ETSI EN 303 645 준수)
  - IoT 보안 시험·인증 기준 (KISA 기준) 적용 및 정기적인 취약점 점검

### 5. 상호운용성 저하 (Interoperability Degradation)

- **설명:** 다양한 센서 및 제어장비를 도입할 때, 시스템이 표준 프로토콜 (MQTT, CoAP 등) 을 준수하지 않거나, 데이터 형식이 다르면서 상태 전이 조건에 문제가 발생하여 다른 장비와 연동 시 오동작할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
  - 표준 프로토콜 (ISO/IEC 30141, oneM2M 등) 준수 확인
  - 오픈 소스 API 및 표준 데이터 모델 (JSON/Schemas) 사용
  - 다양한 벤더의 장비와 호환성을 위한 통합 테스트 수행
