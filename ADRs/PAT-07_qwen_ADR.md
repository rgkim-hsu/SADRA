## 📋 ADR (Architecture Decision Record)

### ADR-001: 분산형 블록체인 아키텍처 채택 및 노드 네트워크 구성

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 기존의 중앙 집중식 서버 기반 아키텍처는 단일 장애점 (SPOF) 과 데이터 조작 위험에 취약할 수 있습니다. 제공된 이미지 (그림 5-1) 는 사용자 (거래 내역 93) 의 요청이 블록체인 네트워크 (300) 로 전달되고, 노드들이 이를 처리하여 블록 (310) 을 생성하는 분산 구조를 보여줍니다. 시스템은 다양한 IoT 기기 및 사용자와의 상호작용을 지원하며, 데이터 무결성과 투명성이 필수적인 환경입니다. |
| **결정 (Decision)** | 중앙 서버 대신 **블록체인 네트워크 (300) 기반의 분산 아키텍처**를 채택합니다. 네트워크는 다수의 노드로 구성되어 있으며, 각 노드는 거래 (93) 를 검증하고 블록 (310) 에 포함시킵니다. 이 구조는 단일 실패 포인트를 제거하고 시스템의 내고용성과 신뢰성을 높입니다. |
| **근거 (Rationale)** | **분산성:** 다수의 노드 (이미지 상 원형 아이콘) 가 네트워크에 참여함으로써 리스크를 분산합니다.<br>**투명성:** 거래 내역 (93) 이 공개되어 모든 참여자가 검증할 수 있어 데이터 조작을 방지합니다.<br>**보안:** 분산원장 기술은 데이터 무결성을 보호하며, 공격자가 전체 네트워크를 장악해야 할 경우를 대비합니다. |
| **결과 (Consequences)** | **긍정적:** 데이터 위변조 방지, 시스템 고장 시 백업 노드 기능 유지, 감사 용이성 향상.<br>**부정적:** 네트워크 동기화 지연 가능성, 초기 구축 및 운영 복잡성 증가, 트랜잭션 처리 속도 제한. |
| **트레이드오프 (Trade-offs)** | **단점:** 트랜잭션 처리 속도 감소 (Consensus 과정 필요).<br>**장점:** 고가용성 및 데이터 신뢰성 확보.<br>**해결책:** 경량 프로토콜 사용 또는 최적화된 Consensus 알고리즘 적용으로 속도 문제 완화. |

## ⚠️ 잠재적 위험 분석

### 1. [분산 노드 간 동기화 지연 및 Consensus 실패]
- **설명:** 블록 (310) 이 생성되거나 거래 (93) 가 처리될 때, 노드들 간의 네트워크 연결이 불안정하여 데이터 동기화가 지연될 경우, 네트워크 분기 (Fork) 가 발생하거나 거래 처리가 마비될 수 있습니다. 특히 IoT 기기와의 실시간 연동 시 지연은 치명적일 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 네트워크 토폴로지 최적화 (Mesh 네트워크 등), Consensus 알고리즘의 안정성 강화, 핵심 노드 (Validator) 수를 적절히 조절하여 결정 속도 향상.

### 2. [블록체인 공격 및 네트워크 해킹]
- **설명:** 외부 공격자가 다수의 노드를 장악하여 51% 공격을 수행하거나, 특정 노드에 악성코드를 주입하여 거래 내역 (93) 을 조작할 경우 시스템 전체의 신뢰성이 붕괴될 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 노드 키 관리 강화 (MFA), 해시 알고리즘 사용, 이상 징후 감지 모니터링 시스템 구축, 다중 서명 (Multi-signature) 기능 도입.

### 3. [거래 내역 (93) 의 프라이버시 침해 위험]
- **설명:** 블록체인은 기본적으로 공개 원장 기술로 운영되므로, 특정 사용자의 거래 내역 (93) 이 투명하게 공개될 경우 개인 정보 유출이나 민감한 거래 데이터가 노출될 수 있습니다. (예: 스마트팜 데이터 등 민감 정보)
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 제로지식증명 (Zero-Knowledge Proof), 암호화된 원장, 프라이빗 채널 (Private Channel) 사용으로 데이터 최소화 전략 적용.

### 4. [확장성 한계 및 성능 병목]
- **설명:** 네트워크에 참여하는 노드가 증가하거나 트랜잭션 (거래 내역 93) 이 폭주할 경우, 블록 (310) 생성 주기나 Consensus 과정으로 인해 처리 속도가 느려져 시스템 응답 시간이 길어질 수 있습니다. 이는 사용자 경험에 악영향을 줍니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 레이어 2 솔루션 (Lightning Network 등) 적용, 샤딩 (Sharding) 기술 도입, 노드 수를 동적으로 조절하여 부하 분산.

### 5. [사용자 키 관리 및 인증 취약점]
- **설명:** 거래 내역 (93) 을 실행하기 위해 사용자는 디지털 지갑과 키를 필요로 합니다. 사용자의 키가 유출될 경우, 모든 거래가 악용될 수 있으며, 특히 노우키 (No-key) 시스템과 달리 키 관리가 필수적인 아키텍처입니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 하드웨어 지갑 (HSM) 활용, 생체 인증 기반 인증, 키 분산 저장 시스템 (Sharded Key Storage) 도입, 지속적인 보안 교육.
