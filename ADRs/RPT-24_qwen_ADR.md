## 📋 ADR (Architecture Decision Record)

### ADR-001: 관계형 데이터 모델 (RDBMS) 기반의 정규화된 엔티티 설계 채택

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 스마트팜 환경은 농작업(수확, 방제 등), 장비(MCCODE), 작업자(WKCODE) 등 이산적이고 구조화된 데이터가 생성됩니다. 컨텍스트 문서에 언급된 TTA 표준 및 ISO/IEC 아키텍처 프레임워크는 엄격한 데이터 관리와 상호운용성을 요구합니다. |
| **결정 (Decision)** | 비정형 데이터 (예: 이미지 로그) 보다 구조화된 작업 및 장비 정보를 위해 정규화된 RDBMS 스키마 (`sf_worker`, `sf_machine`, `sf_workplan` 등) 를 사용합니다. 외래키 (Foreign Keys) 를 통해 엔티티 간의 관계를 명확히 정의합니다. |
| **근거 (Rationale)** | 1. **데이터 무결성:** 작업자 정보와 작업 결과 간의 연관성을 추적해야 하므로 참조 무결성이 필수적입니다. <br> 2. **표준 준수:** TTA 단체표준 (예: 스마트 축사환경 데이터 모니터링 시스템) 에서 요구하는 구조화된 데이터 수집 지침을 충족시키기 위해 적합합니다. <br> 3. **분석 용이성:** 작업 유형 (`sf_wtype`) 같은 마스터 데이터를 이용해 다양한 농업 활동 (수확, 방제 등) 을 분류하여 보고서 작성이 용이합니다. |
| **결과 (Consequences)** | **+** 복잡한 쿼리 (JOIN) 가 필요할 수 있음. <br> **+** 데이터 모델 변경 시 기존 데이터 영향 분석 필요.<br> **-** 비정형 IoT 센서 로그를 저장할 경우 별도의 로그 관리 아키텍처 필요. |
| **트레이드오프 (Trade-offs)** | **장점:** 데이터의 일관성과 검색 속도가 보장됨. <br> **단점:** 대용량 IoT 이벤트 로그 (`sf_msevent`) 처리 시 성능 최적화 (분할 등) 가 추가로 필요함. |

### ADR-002: 마스터 데이터 중심의 작업 유형 분류 체계 (`sf_wtype`) 구현

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 시스템은 단순한 작업을 넘어 '수확', '작업', '방제', '식량 공급 (coffee 등)' 등 특정 농업 용도 (`sf_wtype`) 를 관리합니다. 이 분류는 컨텍스트 문서에 언급된 '스마트 온실 서비스'나 '축산 데이터'와 같은 구체적인 도메인에 따라 확장될 수 있습니다. |
| **결정 (Decision)** | 모든 작업은 `sf_wtype` 테이블을 통해 표준화된 코드 (`WTCODE`) 로 매핑되도록 강제합니다. 이를 통해 비즈니스 로직과 데이터 스키마가 분리되고, 향후 새로운 작업 유형을 추가할 때 데이터 정합성을 유지합니다. |
| **근거 (Rationale)** | 1. **상호운용성:** 다양한 IoT 기기 (Matter, oneM2M 표준 등) 와 연동 시, 동일한 작업 (예: 방제) 을 다른 기기에서 인식하기 위해 공통 코드가 필요합니다. <br> 2. **리포트 단순화:** "총 방제 횟수"나 "작업자별 수확량"과 같은 리포트를 생성할 때, 모든 레코드가 동일한 카테고리를 가지므로 집계 (AGGREGATION) 가 매우 쉽습니다. |
| **결과 (Consequences)** | **+** 새로운 작업이 도입될 때마다 `sf_wtype` 테이블을 업데이트해야 함.<br> **+** 레거시 시스템과의 통합 시, 기존에 존재하던 비표준 작업명을 변환 (MAPPING) 작업이 필요함. |

### ADR-003: 작업자-기계 할당 관계의 다대다 (Many-to-Many) 관계 모델링

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | `sf_worker` (작업자) 와 `sf_machine` (작업기) 간 관계는 직접적인 연결보다는 `WKCODE` 등을 통해 간접적으로 관리되는 것으로 보입니다. 현실적으로 한 기계는 여러 작업자가 교체하여 운용하고, 한 작업자도 여러 대의 기기를 사용하는 경우가 많습니다. |
| **결정 (Decision)** | `sf_worker` 와 `sf_machine` 간에 명시적인 할당 이력 테이블 (또는 작업 계획 `sf_workplan` 내에서의 간접 연결) 을 도입하여, 시계열 기반의 할당 관계를 기록합니다. 즉, 정적인 관계가 아닌 동적인 "작업 계획 -> 실행"을 통해 관계를 정의합니다. |
| **근거 (Rationale)** | 1. **유연성:** 농기계의 수선, 파손, 또는 계절적 농작업 변화에 따라 작업자와 기계를 실시간으로 재할당할 수 있어야 합니다.<br> 2. **책임 추적:** `sf_msevent`에서 `MCCODE` 와 `TAG_INFO`가 발생하므로, 정확히 누가 (어떤 작업자) 언제 어떤 기계 (어떤 TAG) 를 사용했는지 `sf_msevent`와 `sf_msevent` 테이블을 통해 연결해야 합니다. |
| **결과 (Consequences)** | **+** 복잡한 데이터 정합성 (ACID) 유지 필요.<br> **+** 작업 로그 (`sf_msevent`) 가 방대해짐. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 일관성 및 무결성 위험 (Data Integrity Risk)
- **설명:** `sf_workplan`에서 작업 계획이 수립되었으나, 실제 실행 (`sf_msevent`) 단계에서 `WKCODE`와 `MCCODE` 매핑이 실패하거나 누락될 경우, 작업 기록이 불완전하거나 잘못된 인원을 추적할 수 있습니다. 특히 작업자 (`sf_worker`) 가 퇴사하거나 계정이 정지되었을 때, 과거 작업 기록에서 해당 정보를 참조하여 오류가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:**
    1. **사oft Delete 적용:** `sf_worker` 테이블에 `is_deleted` 또는 `end_date` 컬럼을 추가하여 로그 기록 시점에 해당 정보가 유효했음을 보장합니다.
    2. **Transaction 검증:** 작업 계획 수립 (`sf_workplan`) 시, 작업자의 현재 상태 (활성 여부) 를 DB 레코드에 스냅샷으로 저장합니다.

### 2. 작업 유형 분류의 경직성 (Rigidity of Taxonomy)
- **설명:** `sf_wtype` 테이블 (작업종류) 에는 수확, 작업, 방제, 식이 등 고정된 분류가 정의되어 있습니다. 하지만 스마트팜 기술이 발전하거나 새로운 작목 (예: 수직농장용 LED 조명 유지 관리 등) 이 추가되면, 이 고정된 분류를 빠르게 확장해야 하는 부담이 있습니다. 컨텍스트 문서의 표준 (TTA) 이 느리게 갱신될 경우, 새로운 기능을 구현하는 데 제동이 걸릴 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    1. **동적 분류 메타데이터:** `sf_wtype`에 `category` (예: '기술지원', '수확', '관리') 와 `sub_code` 를 분리하여, 표준 분류를 유지하되 세부 태그는 자유롭게 확장할 수 있도록 설계합니다.

### 3. 대규모 이벤트 로그 처리 성능 병목 (Performance Bottleneck in Event Logging)
- **설명:** `sf_msevent`는 `MCCODE` 와 `TAG_INFO` 정보를 포함하며, IoT 기기 (`sf_machine`) 에서 매 순간 발생하는 이벤트 (온도, 상태 등) 를 저장합니다. 이는 초당 수만 건의 로그가 발생할 수 있어, 단순한 관계형 테이블 스키마 (`sf_msevent`) 만으로는 쿼리 속도 저하나 저장 공간 부족 문제가 발생할 수 있습니다.
- **심각도:** 🟠 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:**
    1. **Time-Series Database (TSDB) 고려:** 이벤트 데이터 (`sf_msevent`) 에는 TSDB (InfluxDB 등) 를, 관계형 데이터 (`sf_worker`) 에는 RDBMS 를 하이브리드 방식으로 분리하여 저장하거나, `sf_msevent` 를 별도 파티션으로 관리합니다.

### 4. 보안 및 개인정보 유출 (Security & PII Exposure)
- **설명:** `sf_worker` 테이블에 저장된 작업자 정보는 개인식별정보 (PII) 에 해당합니다. 이 정보가 `sf_msevent`와 같이 민감한 장비 로그와 연동되어 노출될 경우, 특정 작업자가 어떤 기기를 어떻게 조종했는지 상세한 행동 분석이 가능해져 해킹 시점 (Attack Surface) 이 커집니다. 컨텍스트 문서에 언급된 `ITU-T X.1352`(보안요구) 를 충족해야 합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    1. **역할 기반 접근 제어 (RBAC):** 작업자 정보를 조회할 권한은 최소 권한 원칙으로 제한합니다.
    2. **마스크링 및 암호화:** `sf_worker` 테이블 내 성명, 사번 등은 암호화하거나, 로그 조회 시 마스킹 처리합니다.

### 5. 태그 (Tag) 시스템의 복잡도 및 확장성 문제
- **설명:** `sf_machine` 과 `sf_tag` 사이의 연결 (`TAG CODE`) 이 단순 연결인지, 아니면 복잡한 계층 구조인지 명확하지 않습니다. 만약 기기별 설정 (`TAG_INFO`) 이 매우 다양하게 변한다면, `sf_machine` 테이블을 과다하게 확장하거나 노치 (No-SQL) 방식의 유연한 스키마가 필요할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:**
    1. **JSON 타입 활용:** `sf_machine` 또는 `sf_tag` 관련 열에 JSON 타입을 허용하여, 표준화된 필드 외의 비정형 태그 데이터를 유연하게 저장합니다.
    2. **외부 서비스 연동:** 태그 관리는 별도의 MDM (Master Data Management) 서비스나 설정 서버를 통해 연동하여 DB 내 복잡도를 줄입니다.
