## 📋 ADR (Architecture Decision Record)

### ADR-001: [모듈 기반의 확장 가능한 로직 분리 설계 채택]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 환경 정보를 기반으로 '온습도 영향도'라는 핵심 지수를 계산해야 하지만, 향후 추가적인 환경 인자를 반영하거나 알고리즘을 변경해야 하는 유연성이 요구된다. 단일 로직 블록을 사용하는 경우, 새로운 요소를 도입 시 전체 코드를 수정해야 하는 리스크가 존재함. |
| **결정(Decision)** | **제어부 (130)**를 중심으로 '디폴트 모듈 (150)'과 '확장 모듈 (160)'로 기능과 데이터베이스를 물리적으로 분산한다.<br>1. **디폴트 모듈 (150)**: 핵심 비즈니스 로직인 '일별 온습도지수 계산부 (152)'와 기본 데이터를 보유.<br>2. **확장 모듈 (160)**: 추가 로직 (162) 및 데이터 (164) 를 독립적으로 관리하며, 제어부 (130) 가 이를 호출하는 방식. |
| **근거(Rationale)** | **유지보수성**: 핵심 로직 변경 시 확장 모듈에 영향을 주지 않음.<br>**상호운용성**: 추가 기능이 필요할 때 제어부 변경 없이 모듈만 교체 가능 (Open Architecture).<br>**표준 준수**: TTA 표준 (스마트팜 데이터 상호운용 프레임워크) 에서 요구하는 모듈화 요구 사항 반영. |
| **결과(Consequences)** | **긍정적**: 시스템의 수명 주기 연장 및 기능 추가 용이.<br>**부정적**: 초기 아키텍처 설계 및 통신 오버헤드 증가. |
| **트레이드오프(Trade-offs)** | **장점**: 유연성 확보.<br>**단점**: 모듈 간 통신 오버헤드 및 네트워크 복잡도 증가. |

### ADR-002: [중앙 집중식 제어부 (Hub) 아키텍처 채택]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 환경 입력부 (110) 에서 온습도 데이터 (120) 로 넘어가면, 이를 처리하고 계산 (152, 162) 을 거쳐 최종 결과 (140) 로 보내는 복잡한 데이터 흐름이 존재함. 분산 처리 시 데이터 일관성 유지가 어려울 수 있음. |
| **결정(Decision)** | 모든 데이터 흐름의 진입점이자 핵심 로직 처리가 되는 **제어부 (130)**를 설계하며, 이 부가 데이터베이스부 (120, 154 등) 와 직접적으로 통신한다. |
| **근거(Rationale)** | **단일 진입점 (SPOI) 관리**: 복잡한 로직 흐름을 한곳에서 통제하여 디버깅 및 트래픽 모니터링 용이.<br>**트랜잭션 관리**: 여러 데이터베이스 (기본 DB, 영향도 DB) 를 건드릴 때 ACID 성질 만족을 위해 단일 제어부에서 처리 로직을 집중화함. |
| **결과(Consequences)** | **긍정적**: 시스템 오작동 시 원인 파악 및 수정이 용이함.<br>**부정적**: 제어부 단일 장애점 (SPOF) 이 될 위험이 존재 (백업 노드 필요 시 고려). |
| **트레이드오프(Trade-offs)** | **장점**: 제어 및 관리가 수월함.<br>**단점**: 제어부 성능 저하 시 전체 시스템 마비 위험. |

## ⚠️ 잠재적 위험 분석

### 1. [단일 장애점 (SPOF) 위험]
- **설명:** `제어부 (130)`가 모든 데이터 (입력, 출력, 계산 요청) 의 유일한 처리 중심이기 때문에, 이 노드가 다운될 경우 전체 시스템이 마비될 수 있음. `환경 정보 데이터베이스부 (120)` 역시 단일 연결점 역할을 함.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (하드웨어/소프트웨어 오류 발생 시)
- **대응 방안:** 제어부 (130) 와 데이터베이스 (120, 150, 160) 에 대해 Active-Passive 또는 Active-Active 클러스터링 구조를 도입하거나, 데이터베이스를 복제 (Replica) 형태로 분산시켜고가용성을 확보함.

### 2. [데이터 무결성 부재 위험]
- **설명:** `디폴트 모듈 (150)`과 `확장 모듈 (160)`이 독립된 데이터베이스 (154, 164) 를 보유하고 있되, `제어부 (130)`가 이를 동시에 참조할 때, 기본값 업데이트 시 확장 모듈 데이터베이스가 동기화되지 않아 계산된 지수가 불일치할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (소프트웨어 업데이트 또는 수동 수정 시)
- **대응 방안:** 모듈 간 데이터 갱신 시的事务(Transaction) 관리가 필요한지 고려하거나, 제어부 (130) 가 모든 데이터의 최종 원천(Source of Truth) 이 되도록 DB 구조를 재설계함.

### 3. [보안 공격 취약점 (입력부)]
- **설명:** `환경 정보 입력부 (110)`를 통해 외부에서 환경 데이터가 유입되는데, 이 데이터에 악성 코드나 이상 값이 포함되면 `제어부 (130)`와 `환경 정보 데이터베이스부 (120)`가 이를 그대로 처리하거나 저장할 경우 데이터 누출 또는 조작 위험이 존재함.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (악성 행위자 발생 시)
- **대응 방안:** `환경 정보 입력부 (110)`에 대한 Strict Input Validation (입력 유효성 검사) 를 의무화하고, ITU-T X.1352 와 같은 IoT 보안 표준을 적용하여 데이터 암호화 및 인증을 수행함.

### 4. [확장성 한계 (Performance Bottleneck)]
- **설명:** `확장 모듈 (160)`이 여러 개의 추가 인자 (일별 추가영향 지수 등) 를 계산하게 되며, 이러한 모듈의 기능이 증가할수록 `제어부 (130)`의 처리 속도가 느려져 `출력부 (140)`를 지연시킬 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (사용량 증가 시)
- **대응 방안:** 계산 로직 (162) 과 데이터 (164) 를 별도 서버로 분리하거나, 비동기 처리 방식을 적용하여 병렬처리가 가능하도록 아키텍처를 변경함.

### 5. [복잡한 유지보수 비용 증가]
- **설명:** `제어부 (130)`가 디폴트 모듈 (150) 과 확장 모듈 (160) 로 나뉘어 있으며, 각 모듈 내부에 DB 와 계산기가 존재하므로, 시스템이 복잡해져 개발 비용과 유지보수 인력이 증가함. 특히 표준 (ISO/IEC 30141 등) 에 맞춘 변경이 필요할 경우 이 구조에 비효율적으로 적용될 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low (시간에 따라 증가)
- **대응 방안:** 모듈 간 인터페이스 (API) 를 명확히 정의하고 표준화된 프레임워크 (예: oneM2M API 등) 를 사용하여 개발 및 통합 비용을 절감함.
