## 200010

# 🏗️ 아키텍처 분석 보고서

## ADR (Architecture Decision Record)

### ADR-001: 중앙 집중식 데이터 허브(Centralized Data Hub) 아키텍처 및 다중 프로토콜 통합 패턴 적용

| 항목                     | 내용                                                                                                                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 제조 현장의 데이터는 MES(생산), ERP(경영), LIMS(품질), DCS/PLC(제어) 등 이기종 시스템에 분산(Silo)되어 있어, 전사적인 데이터 분석과 실시간 모니터링이 어렵습니다. 다양한 데이터 소스(SQL, API, OPC, 수동 입력, Excel 등)를 단일 플랫폼으로 통합해야 하는 과제가 있습니다.                                                                         |
| **결정(Decision)**       | **dataPARC**를 중앙 데이터 허브(Central Data Hub)로 선정하고, 각 외부 시스템의 특성에 맞는 최적의 인터페이스(SQL, API, OPC UA/DA 등)를 사용하여 데이터를 수집·통합하는 **Hub-and-Spoke 아키텍처**를 채택합니다.                                                                                                      |
| **근거(Rationale)**      | 이미지에서 볼 수 있듯이 dataPARC는 MES, ERP, LIMS와의 SQL/API 연동뿐만 아니라 하단의 DCS/PLC 장비군(AspenTech, Honeywell, Siemens 등)과는 OPC 인터페이스를 통해 연결됩니다. 이는 실시간 제어 데이터와 트랜잭션 데이터를 하나의 타임라인에서 통합 분석하기 위한 최적의 패턴이며, 데이터 사일로(Data Silo)를 제거하고 'Single Source of Truth'를 확보할 수 있습니다. |
| **결과(Consequences)**   | **긍정적:** 생산, 품질, 설비 데이터를 통합한 종합적인 대시보드 구축이 가능하며, 의사결정 속도가 향상됩니다.<br>**부정적:** 중앙 허브에 대한 의존도가 높아지며, 모든 데이터 소스의 인터페이스 표준화 및 매핑 작업에 초기 구축 비용과 시간이 소요됩니다.                                                                                                      |
| **트레이드오프(Trade-offs)** | **장점:** 데이터 통합성(Data Integrity) 확보 및 cross-domain 분석(예: 품질 불량 원인 추적) 가능.<br>**단점:** 시스템 복잡도 증가 및 중앙 허브 장애 시 데이터 수집 전체가 마비될 수 있는 단일 장애점(SPOF) 리스크 존재.                                                                                                      |

---

## ️ 잠재적 위험 분석

### 1. 이기종 데이터 소스 통합 복잡성 (Heterogeneous Data Integration Complexity)

- **설명:** SQL(MES, ERP, LIMS), OPC(DCS, PLC), 수동 입력(MDE), 파일(Excel) 등 서로 다른 주기와 포맷을 가진 데이터를 하나의 dataPARC 모델로 통합할 때 데이터 매핑 오류나 변환 실패가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 수집 파이프라인 단계에서 강력한 **ETL/ELT 검증 로직**을 도입하고, 각 소스별 데이터 사전(Data Dictionary)을 표준화하여 매핑 오류를 최소화해야 합니다.

### 2. 실시간 데이터와 배치 데이터의 타임스탬프 불일치 (Timestamp Misalignment)

- **설명:** OPC를 통한 실시간 제어 데이터는 밀리초(ms) 단위이지만, MES나 ERP의 SQL 데이터는 배치(Batch) 단위로 전송됩니다. 이 두 데이터의 시간 동기화가 실패하면 원인 분석 시 잘못된 상관관계가 도출될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** dataPARC 내부에서 **타임스탬프 정규화(Time Alignment)** 기능을 활성화하고, 배치 데이터의 경우 '거래 발생 시간'과 '시스템 기록 시간'을 명확히 구분하여 저장해야 합니다.

### 3. 중앙 허브 단일 장애점 (Single Point of Failure - SPOF)

- **설명:** 모든 데이터가 중앙의 dataPARC로 집중되는 아키텍처이므로, dataPARC 서버에 장애가 발생할 경우 공장 전체의 데이터 가시성(Visibility)이 즉시 상실됩니다.
- **심각도:** 🔴 High
- **발생 가능성:**  Low (HA 구성 시)
- **대응 방안:** dataPARC 서버를 **Active-Passive 또는 Active-Active 클러스터(High Availability)** 구성으로 운영하여 장애 발생 시 즉시 페일오버(Failover) 되도록 해야 합니다. 또한 엣지 단계에서 데이터 버퍼링 기능을 활성화해야 합니다.

### 4. 수동 데이터 입력(MDE)으로 인한 데이터 품질 저하 (Data Quality Degradation)

- **설명:** 'MDE, Shift Logs' 항목에서 볼 수 있듯이, 운영자가 수동으로 입력하는 데이터는 오타나 지연 입력으로 인해 시스템의 자동 수집 데이터와 불일치를 일으킬 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 수동 입력 인터페이스에 **입력값 검증(Input Validation)** 및 필수값 체크 기능을 강화하고, 가능하다면 IoT 센서를 활용하여 수동 입력 의존도를 낮추는 자동화 전환 계획을 수립해야 합니다.

### 5. 다중 인터페이스 개방에 따른 보안 취약점 (Expanded Attack Surface)

- **설명:** SQL, API, OPC 등 다양한 포트로 외부 시스템과 연결되므로, 인증이 취약한 인터페이스를 통해 악성 코드가 유입되거나 데이터가 변조될 위험이 있습니다.
- **심각도:**  High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 인터페이스(SQL, API, OPC)에 대해 **최소 권한 원칙(Least Privilege)** 기반의 접근 제어(IAM)를 적용하고, 네트워크 구간을 VLAN으로 분리하여 제어망(Control Network)과 정보망(IT Network)을 격리해야 합니다.
