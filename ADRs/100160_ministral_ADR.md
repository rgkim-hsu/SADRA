## 📋 ADR (Architecture Decision Record)

### **ADR-001: 중앙 집중형 IoT 플랫폼 아키텍처 채택 및 이벤트 기반 데이터 처리**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 제공된 개념도는 **IoT 플랫폼의 중앙 집중형 아키텍처**를 반영하고 있으며, **스마트팜/축산 분야**에서 발생하는 센서 데이터 수집, 처리, 저장 및 서비스 제공을 위한 시스템을 설계해야 함. 주요 컴포넌트는 **데이터 수집 계층(405, 406)**, **중앙 처리 계층(403)**, **서비스 제공 계층(401, 402)**, **보조 저장/제어 계층(404)**로 구성되어 있으며, **실시간 데이터 처리**와 **상호운용성**이 핵심 요구사항임. |
| **결정(Decision)** | 1. **이벤트 기반 데이터 처리 아키텍처** 채택: MQTT/CoAP 프로토콜을 활용한 **Pub/Sub 모델**로 센서 데이터 수집 및 전송
2. **중앙 처리 계층(403)**에서 **Edge Computing**과 **Cloud Hybrid** 방식을 병행하여 실시간 처리 및 분석 수행
3. **데이터 저장 계층**은 **NoSQL(InfluxDB, MongoDB)**과 **관계형 DB(MySQL)**를 병행하여 구조화/비구조화 데이터 모두 지원
4. **API 게이트웨이(401, 402)**를 통해 **RESTful API**와 **GraphQL**을 제공하여 서비스 상호운용성 보장
5. **보안 계층(404)**에서 **TLS 1.3**과 **OAuth 2.0**을 적용한 인증/인가 시스템 구축 |
| **근거(Rationale)** | - **IoT 표준 준수**: ISO/IEC 30141:2024의 **"참조 아키텍처"**와 **oneM2M**의 **"이벤트 처리 모델"**을 따름
- **실시간 처리 요구사항**: 스마트팜/축산 분야에서 **지연 시간 100ms 이하**의 데이터 처리 필요성으로 Edge Computing 도입
- **상호운용성**: **Matter/OCF 표준**과 **ETSI EN 303 645**의 **"보안 요구사항"**을 충족하기 위한 API 표준화
- **확장성**: NoSQL/관계형 DB 병행으로 **대용량 데이터**와 **고도화된 분석** 지원 |
| **결과(Consequences)** | ✅ **장점**:
- 실시간 모니터링 및 조치 가능 (예: 가축 질병 조기 감지)
- 글로벌 표준 준수로 **보안 및 상호운용성** 강화
- Edge-Computing으로 **네트워크 비용 절감** 및 **오프라인 처리** 지원
❌ **단점**:
- 중앙 처리 계층의 **단일 장애점(SPOF)** 위험
- 다중 DB 관리로 **운영 복잡성** 증가
- 초기 구축 비용이 높음 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 비용**: Edge-Computing 도입으로 성능 향상但 초기 하드웨어 비용 증가
- **보안 vs. 사용성**: OAuth 2.0 및 TLS 적용으로 보안 강화但 추가 인증 프로세스로 사용자 경험 영향
- **확장성 vs. 복잡성**: NoSQL/관계형 DB 병행으로 확장성 향상但 운영 복잡성 증가 |

### **ADR-002: 데이터 상호운용성 프레임워크 구축**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | TTA 표준에서 정의한 **"스마트팜 데이터 상호운용 프레임워크"** 요구사항에 따라, **다양한 센서/장비 간 데이터 형식을 통일**하고 **API 표준화**를 통해 시스템 간 상호운용성을 보장해야 함. |
| **결정(Decision)** | 1. **JSON Schema**를 기반으로 **공통 데이터 모델** 정의
2. **oneM2M Common Service Layer**를 참조하여 **API 표준화** (RESTful + WebSocket)
3. **Kafka**를 활용한 **이벤트 스트리밍**으로 실시간 데이터 동기화

| **근거(Rationale)** | - **국내 표준 준수**: TTA의 **"스마트팜 데이터 상호운용 프레임워크"**와 **"에지 기반 데이터 관리"** 표준을 따름
- **국제 표준 연계**: ISO/IEC 30141의 **"공통 언어"**와 **oneM2M**의 **"API 명세"**를 참조

- **실시간 모니터링 및 조치** 지원
- **국내외 표준 호환성** 확보
❌ **단점**:
- **데이터 변환 오버헤드** 발생 가능
- **Kafka 클러스터 관리 복잡성** 증가 |
| **트레이드오프(Trade-offs)** | - **표준화 vs. 유연성**: 공통 데이터 모델 도입으로 유연성 감소但 상호운용성 강화
- **실시간성 vs. 안정성**: Kafka를 통한 스트리밍으로 실시간성 향상但 클러스터 장애 시 데이터 손실 위험 |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 처리 계층의 단일 장애점(SPOF)**
- **설명**: 중앙 처리 계층(403)이 **단일 서버/클러스터**로 구성될 경우, 장애 시 **전체 시스템 마비** 위험 발생. 특히 스마트팜/축산 분야에서 **실시간 모니터링**이 critical path임.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Active-Active 클러스터** 구성 (예: Kubernetes + HAProxy)
  - **지리적 중복(DR Site)** 구축 (예: 서울 + 부산 데이터 센터)
  - **자동 장애 복구(Chaos Engineering)**를 통한 테스트 수행

### **2. 데이터 일관성 문제 (NoSQL + 관계형 DB 병행)**
- **설명**: **NoSQL(InfluxDB)**과 **관계형 DB(MySQL)**를 병행할 경우, **트랜잭션 일관성**과 **데이터 동기화 지연**으로 인해 **분석 오류** 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Change Data Capture(CDC)** 도구 (예: Debezium) 활용하여 실시간 동기화
  - **이벤트 소싱 패턴** 도입으로 데이터 일관성 강화
  - **DB별 역할 명확화** (예: NoSQL은 시간계열 데이터, 관계형 DB는 메타데이터 관리)

### **3. 보안 취약성 (IoT 기기 간 통신)**
- **설명**: **MQTT/CoAP 프로토콜**을 사용한 IoT 기기 간 통신은 **기본 보안 기능이 약**하며, **미사용 디바이스**나 **약한 인증**으로 인해 **DDoS 공격**이나 **데이터 도청** 위험 발생.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3 강제 적용** 및 **기기 인증(Device Certificate)**
  - **KISA의 IoT 보안 기준(ITU-T X.1352)** 준수한 **보안 모듈** 도입
  - **네트워크 세그멘테이션** (예: VLAN, Zero Trust Architecture)

### **4. 운영 복잡성 증가 (다중 기술 스택)**
- **설명**: **Edge-Computing**, **Kafka**, **다중 DB**, **API 게이트웨이** 등 **다양한 기술 스택**으로 인해 **운영 및 유지보수 비용** 증가 및 **전문 인력 부족**으로 시스템 관리 어려움.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (장기적 위험)
- **대응 방안**:
  - **Terraform/IaC**를 통한 **인프라 자동화**
  - **내부 기술 문서화** 및 **운영 체크리스트** 작성
  - **PaaS(Platform-as-a-Service)** 활용 (예: AWS IoT Core, Azure IoT Hub)

### **5. 표준 변화에 따른 재작업 위험**
- **설명**: **ISO/IEC 30141**이나 **oneM2M** 등 **국제 표준**이 주기적으로 업데이트될 경우, 시스템이 **비호환성**으로 인해 **재설계**가 필요할 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (장기적 위험)
- **대응 방안**:
  - **표준 모니터링 팀** 구성하여 **변화 사항 추적**
  - **모듈화 설계**로 **표준 변경에 대한 영향 최소화**
  - **백워드 호환성**을 고려한 **API 버전 관리**

---
**※ 추가 고려사항**:
- **에지 컴퓨팅**의 **오프라인 처리** 기능은 **네트워크 장애 시**에도 **지역별 조치** 가능하지만, **데이터 동기화 지연**으로 인해 **전체 시스템 분석에 영향** 발생 가능 → **오프라인 모드 및 동기화 정책** 명확히 정의 필요.

## ⚠️ 잠재적 위험 분석

### **1. 중앙 처리 계층의 단일 장애점(SPOF)**
- **설명**: 중앙 처리 계층(403)이 **단일 서버/클러스터**로 구성될 경우, 장애 시 **전체 시스템 마비** 위험 발생. 특히 스마트팜/축산 분야에서 **실시간 모니터링**이 critical path임.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Active-Active 클러스터** 구성 (예: Kubernetes + HAProxy)
  - **지리적 중복(DR Site)** 구축 (예: 서울 + 부산 데이터 센터)
  - **자동 장애 복구(Chaos Engineering)**를 통한 테스트 수행

### **2. 데이터 일관성 문제 (NoSQL + 관계형 DB 병행)**
- **설명**: **NoSQL(InfluxDB)**과 **관계형 DB(MySQL)**를 병행할 경우, **트랜잭션 일관성**과 **데이터 동기화 지연**으로 인해 **분석 오류** 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Change Data Capture(CDC)** 도구 (예: Debezium) 활용하여 실시간 동기화
  - **이벤트 소싱 패턴** 도입으로 데이터 일관성 강화
  - **DB별 역할 명확화** (예: NoSQL은 시간계열 데이터, 관계형 DB는 메타데이터 관리)

### **3. 보안 취약성 (IoT 기기 간 통신)**
- **설명**: **MQTT/CoAP 프로토콜**을 사용한 IoT 기기 간 통신은 **기본 보안 기능이 약**하며, **미사용 디바이스**나 **약한 인증**으로 인해 **DDoS 공격**이나 **데이터 도청** 위험 발생.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3 강제 적용** 및 **기기 인증(Device Certificate)**
  - **KISA의 IoT 보안 기준(ITU-T X.1352)** 준수한 **보안 모듈** 도입
  - **네트워크 세그멘테이션** (예: VLAN, Zero Trust Architecture)

### **4. 운영 복잡성 증가 (다중 기술 스택)**
- **설명**: **Edge-Computing**, **Kafka**, **다중 DB**, **API 게이트웨이** 등 **다양한 기술 스택**으로 인해 **운영 및 유지보수 비용** 증가 및 **전문 인력 부족**으로 시스템 관리 어려움.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (장기적 위험)
- **대응 방안**:
  - **Terraform/IaC**를 통한 **인프라 자동화**
  - **내부 기술 문서화** 및 **운영 체크리스트** 작성
  - **PaaS(Platform-as-a-Service)** 활용 (예: AWS IoT Core, Azure IoT Hub)

### **5. 표준 변화에 따른 재작업 위험**
- **설명**: **ISO/IEC 30141**이나 **oneM2M** 등 **국제 표준**이 주기적으로 업데이트될 경우, 시스템이 **비호환성**으로 인해 **재설계**가 필요할 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (장기적 위험)
- **대응 방안**:
  - **표준 모니터링 팀** 구성하여 **변화 사항 추적**
  - **모듈화 설계**로 **표준 변경에 대한 영향 최소화**
  - **백워드 호환성**을 고려한 **API 버전 관리**
