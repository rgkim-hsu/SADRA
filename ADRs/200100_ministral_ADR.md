## 📋 ADR (Architecture Decision Record)

### **ADR-001: 센서 데이터 통합 및 실시간 처리를 위한 중앙 서버 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **Weather Station, Canopy Temp Sensors, Soil Water Sensors** 등 다수 분산형 센서로부터 실시간 데이터를 수집하여 농업 생산성을 최적화해야 함. 센서 데이터는 **고주기성(예: 기상 데이터)**과 **고빈도성(예: 토양 수분)**이 혼재하며, 지연 없이 처리가 필요함. 또한, **사용자 정의 처방 지도(Prescription Map)** 생성 및 **VRI-Center Pivot** 제어 로직을 지원해야 함. |
| **결정(Decision)** | 1. **ARSP’s Server**를 **중앙 집중형 데이터 처리 플랫폼**으로 설계하여 모든 센서 데이터를 수신, 저장, 가공
2. **MQTT 프로토콜**을 기반으로 센서-서버 통신을 구현하여 **저지연, 고신뢰성**을 보장
3. **Prescription Map** 생성 로직을 서버 측에서 처리하여 클라이언트 부담을 줄임
4. **Edge Computing**을 보조적으로 도입하여 지역적 데이터 전처리를 지원 (예: 현장 센서 노드에서 이상치 필터링) |
| **근거(Rationale)** | - **MQTT 프로토콜**: IoT 표준 프로토콜로, **저대역폭, 고효율** 통신을 지원하며, **ISO/IEC 27030:2020** 및 **oneM2M** 표준과 호환됨.
- **중앙 서버**: 데이터 일관성 및 통합 분석을 용이하게 하며, **ISO/IEC 30141:2024**의 참조 아키텍처와 일치.
- **Edge Computing 보조**: 네트워크 지연을 줄이고, **ETSI EN 303 645**의 보안 요구사항을 지역 단위로 적용 가능. |
| **결과(Consequences)** | ✅ **장점**:
- 센서 데이터의 **실시간 통합** 및 **고신뢰성** 보장
- **스케일러빌리티**가 높아 새로운 센서 추가 시 최소한의 변경으로 확장 가능
- **보안 강화**: 서버 측에서 **TLS 1.3** 및 **KISA 인증 기준**을 적용하여 데이터 암호화 및 접근 통제 가능
❌ **단점**:
- **단일 장애점(SPOF)**: 중앙 서버 장애 시 전체 시스템 영향 발생 가능
- **네트워크 의존성**: 원격 농장 환경에서 네트워크 불안정성으로 데이터 손실 위험 존재 |
| **트레이드오프(Trade-offs)** | - **중앙 집중형 vs 분산 처리**:
  - 중앙 서버는 **관리 용이성** 높으나 **고가용성** 구현이 필요
  - 분산 처리(예: 블록체인)는 **신뢰성** 높으나 **복잡성** 증가
- **MQTT vs CoAP**:
  - MQTT: **IoT 표준**으로 적합하나, **CoAP**보다 **메모리 사용량** 높음
  - 선택: **MQTT**로 표준화 및 확장성을 우선시 |

### **ADR-002: 보안 및 데이터 무결성 강화策略**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **토양/작물 데이터** 및 **제어 명령어**를 처리하므로, **사이버 공격** 및 **데이터 변조**에 취약함. **ITU-T X.1352** 및 **ETSI EN 303 645** 표준 준수 필요. |
| **결정(Decision)** | 1. **센서-서버 통신**: **TLS 1.3** + **MQTT over WebSocket**로 암호화
2. **데이터 무결성**: **SHA-256** 해시 및 **블록체인 기반 로그**를 도입
3. **접근 통제**: **OAuth 2.0** + **JWT**를 사용하여 사용자 인증 및 권한 관리
4. **서버 보안**: **KISA 인증 기준** 준수하여 **DDoS 방화벽** 및 **실시간 침입 탐지(IDS)** 구현 |
| **근거(Rationale)** | - **TLS 1.3**: **NIST SP 800-52** 및 **ISO/IEC 27030:2020** 권장 프로토콜
- **블록체인 로그**: 데이터 변조 방지를 위해 **하이퍼레저 파브릭**을 활용
- **OAuth 2.0**: **Matter 표준**과 호환되며, **스마트홈/IoT 보안**에 널리 사용됨 |
| **결과(Consequences)** | ✅ **장점**:
- **국제 표준 준수** 및 **보안 인증** 가능 (KISA, ISO/IEC)
- **데이터 무결성** 강화로 **사기 방지** 효과
❌ **단점**:
- **성능 오버헤드**: 암호화 및 해시 처리로 **10-15% 지연** 발생 가능
- **복잡성 증가**: 보안 미들웨어 구현으로 **개발 비용** 상승 |
| **트레이드오프(Trade-offs)** | - **블록체인 vs 전통적 로그**:
  - 블록체인: **무결성** 높으나 **처리 속도** 저하
  - 선택: **중요 데이터만** 블록체인 적용, 일반 로그는 **SQL 데이터베이스** 사용 |

### **ADR-003: 클라우드 기반 확장성 vs 온프레미스 고가용성**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **대규모 농장**에서 운영되므로, **고가용성**과 **저비용 확장성**이 필요함. 클라우드 vs 온프레미스 중 선택 필요. |
| **결정(Decision)** | 1. **하이브리드 아키텍처** 채택:
   - **센서 데이터 수집**: **온프레미스 에지 서버** (현장 네트워크 지연 최소화)
   - **중앙 처리**: **AWS IoT Core** + **Kubernetes**를 활용한 **클라우드 기반 서버**
2. **백업**: **Multi-Region 복제**를 통해 **99.99% 가용성** 보장 |
| **근거(Rationale)** | - **AWS IoT Core**: **MQTT/HTTPS 지원** 및 **IoT 표준** 준수
- **Kubernetes**: **자동 스케일링** 및 **고가용성** 제공
- **온프레미스 에지**: **네트워크 지연** 최소화 (현장 센서 데이터 처리 속도 향상) |
| **결과(Consequences)** | ✅ **장점**:
- **클라우드 확장성**: **수천 개의 센서** 동시 처리 가능
- **온프레미스 안정성**: **네트워크 불안정성**에 대한 내성 향상
❌ **단점**:
- **비용**: 클라우드 사용료 및 **Multi-Region 복제** 비용 발생
- **운영 복잡성**: 하이브리드 시스템 관리 어려움 |
| **트레이드오프(Trade-offs)** | - **전체 클라우드 vs 하이브리드**:
  - 클라우드: **유연성** 높으나 **네트워크 의존성** 증가
  - 하이브리드: **안정성** 높으나 **운영 복잡성** 증가
- 선택: **현장 중요성**에 따라 **하이브리드**로 결정 |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 서버 단일 장애점(SPOF)**
- **설명**: 중앙 서버 장애 시 **전체 시스템 마비** 발생. 센서 데이터 누적 및 제어 명령어 실패로 **작물 손실** 위험.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Active-Active 복제**를 통해 **2개 이상의 서버 클러스터** 구축
  - **자동 failover** 메커니즘 도입 (예: **Kubernetes HPA + AWS Auto Scaling**)
  - **현장 에지 서버**에서 **로컬 백업 처리** 로직 구현

### **2. 네트워크 불안정성으로 인한 데이터 손실**
- **설명**: 원격 농장 환경에서 **네트워크 끊김**으로 센서 데이터 손실 발생. 특히 **실시간 제어 명령어**가 실패 시 **작물 피해** 발생 가능.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **MQTT QoS Level 2**를 적용하여 **최소 1회 이상 전달** 보장
  - **오프라인 큐 시스템** (예: **AWS IoT Greengrass**)을 통해 **네트워크 복구 시 재전송**
  - **현장 모뎀 백업**을 통해 **셀룰러 네트워크**를 보조적으로 활용

### **3. 보안 취약성 및 사이버 공격**
- **설명**: **센서 스푸핑 공격** 또는 **서버 해킹**으로 **데이터 변조** 또는 **제어 명령어 조작** 가능. 예: **토양 수분 데이터 조작**으로 **과수분 관개** 발생.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **센서 인증**: **X.509 인증서**를 통해 센서 식별
  - **실시간 침입 탐지(IDS)**: **AWS GuardDuty** 또는 **Snort**를 활용
  - **정기 보안 감사**: **KISA 기준**에 따라 **quarterly penetration test** 수행

### **4. 데이터 일관성 문제**
- **설명**: **분산된 센서**와 **클라우드 서버** 간의 **시간 동기화 오차**로 데이터 불일치 발생. 예: **Prescription Map** 생성 시 **오류된 토양 데이터** 사용.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **NTP 프로토콜**을 통해 **미리세컨드 단위 동기화**
  - **이벤트 소싱 패턴**을 도입하여 **데이터 변경 로그** 추적
  - **데이터 유효성 검사**: **현장 센서**에서 **범위 검증** (예: 토양 수분 0-100% 범위 강제)

### **5. 표준 호환성 문제**
- **설명**: **다양한 센서 브랜드**가 **표준 미준수**로 통신 실패 발생. 예: **Canopy Temp Sensors**가 **MQTT 비호환** 프로토콜 사용 시.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기) / 🟡 Medium (장기)
- **대응 방안**:
  - **프로토콜 게이트웨이** 구축 (예: **MQTT ↔ Modbus/CoAP**)
  - **TTA 표준** 준수 센서만 **공식 지원** 목록에 포함
  - **오픈 소스 드라이버** 개발 및 공유 (예: **GitHub 리포지토리**)

### **6. 운영 비용 과다**
- **설명**: **클라우드 사용료** 및 **고가용성 인프라** 유지 비용으로 **장기적으로 경제성 저하** 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기) / 🟡 Medium (장기)
- **대응 방안**:
  - **코스트 모니터링 도구** (예: **AWS Cost Explorer**)를 통해 **자동 최적화**
  - **현장 에지 서버**를 통해 **클라우드 데이터 전송량 최소화**
  - **정부 보조금** 활용 (예: **농업 IoT 지원 프로그램**)
