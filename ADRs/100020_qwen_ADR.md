## 📋 ADR (Architecture Decision Record)

### ADR-001: 데이터 처리 파이프라인 및 학습 피드백 루프 통합

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 또는 IoT 환경에서 방대한 센서 데이터를 수집 (빅데이터부) 하고, 이를 기반으로 분석, 예측, 제어 지시사항을 제공해야 하는 복잡한 데이터 흐름이 존재함. 단순 데이터 저장과 처리뿐만 아니라, 예측 정확도를 높이기 위해 지속적인 학습 (Analysis Learning) 과 연동 (Joint Learning) 이 필수적임. |
| **결정(Decision)** | 데이터 수집 (310), 데이터 확인 (330), 모델 학습/분석 (360), 예측 (350), 제어 지시사항 제공 (320) 의 선형 프로세스와 동시에, 모델 성능 개선을 위한 '연동학습부' (370) 와 '미리닝부' (380) 의 피드백 루프를 포함한 분산 아키텍처를 채택함. |
| **근거(Rationale)** | - **데이터 흐름:** 센서 데이터 수집부터 최종 서비스 제공 (제공부 320) 까지 이어지는 명확한 파이프라인 필요. <br>- **지능화:** 단순 처리가 아닌 '분석학습부 (360)'를 통해 AI 모델을 지속적으로 업데이트하고, 이를 '예측부 (350)'에 반영하여 정확도 향상. <br>- **적응성:** '연동학습부 (370)'를 통해 외부 환경 변화나 시스템 오류에 대해 모델이 자동으로 적응하도록 피드백 메커니즘을 구축함. |
| **결과(Consequences)** | - **긍정적:** 시스템의 자동화 수준 향상, 예측 정확도 개선, 유지보수성 증대. <br>- **부정적:** 시스템 초기 설계 및 설정 시간 증가, 학습 과정에 따른 리소스 소모 증가. |
| **트레이드오프(Trade-offs)** | **장점:** 높은 정확도의 자동 제어 및 예측, 시스템의 자체 학습 능력 확보.<br>**단점:** 복잡한 시스템 구조로 인한 개발 및 운영 난이도 증가, 실시간 데이터 처리를 위한 고성능 인프라 필요. |

### ADR-002: 표준 기반의 상호운용성 및 확장성 확보

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 다양한 제조사의 IoT 디바이스 및 서비스 (제공부 320 등) 가 시스템을 구성해야 하며, 국제 표준 (ISO, ITU 등) 과 국내 표준 (TTA 등) 에의 호환이 필수적임. 확장성과 호환성을 고려해야 함. |
| **결정(Decision)** | 시스템 인터페이스 및 데이터 포맷을 IEEE, ISO, TTA 표준에 부합하도록 설계. '제공부 (320)'와 '진행관리부 (340)' 등 외부와의 통신을 표준 프로토콜 (MQTT, CoAP 등) 을 통해 수행. |
| **근거(Rationale)** | - **호환성:** 다양한 이종 시스템 간의 연동을 위해 표준화된 데이터 모델 (ISO/IEC 30141 등) 필수. <br>- **유지보수:** 표준 기반 설계 시 새로운 장비나 서비스 추가 시 기존 시스템 영향 최소화. <br>- **보안:** 국제 보안 표준 (ITU-T X.1352 등) 준수를 통해 글로벌 시진 요구 충족. |
| **결과(Consequences)** | - **긍정적:** 생태계 확장 용이, 시스템 통합 비용 절감, 글로벌 진출 가능성 확대.<br>- **부정적:** proprietary 기능 구현 시 제약 가능, 표준 프로토콜의 유연성 부족. |
| **트레이드오프(Trade-offs)** | **장점:** 개방성 확보, 기술적 장벽 해소.<br>**단점:** 특정 최적화된 비표준 프로토콜보다 통신 오버헤드 증가 가능. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 보안 취약성 및 침해 위험

- **설명:** '빅데이터부 (310)'와 '제공부 (320)'를 통해 수집 및 외부로 출력되는 데이터가 해킹되거나 유출될 경우, 사생활 침해나 시스템 조작으로 이어질 수 있음. 특히 IoT 기기 연결성 (oneM2M 등) 이 증가함에 따라 취약점이 확대될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (IoT 환경의 보편적 위험)
- **대응 방안:** 
  - ISO/IEC 27030 및 ETSI EN 303 645와 같은 IoT 보안 표준을 준수한 암호화 (TLS, MQTT over TLS) 적용.
  - '진행관리부 (340)'에서 인증/인가 (AuthN/AuthZ) 프로세스를 강화하여 무단 접근 차단.
  - 정기적인 보안 패치 및 침투 테스트 수행.

### 2. 실시간 데이터 처리 지연 및 제어 오류

- **설명:** '빅데이터부 (310)'에서 '제공부 (320)'로 데이터가 이동하고 '분석학습부 (360)'에서 학습되는 과정에서 네트워크 지연이나 시스템 부하가 발생하면, 스마트팜의 환경 제어 (온습도, 급수 등) 에서 실시간 대응이 안 될 수 있음. 이는 작물 손실로 직결될 수 있음.
- **심각도:** 🔴 High (운영적 치명적 오류)
- **발생 가능성:** 🟡 Medium (시스템 부하 시 발생)
- **대응 방안:** 
  - Edge Computing 도입을 고려하여 '미리닝부 (380)'에서 기본 분석 로직 실행하여 지연 시간 최소화.
  - 메시지 브로커 (MQTT Broker 등) 의 스케일링 전략 수립.
  - '확인부 (330)' 및 '연동학습부 (370)'를 통해 시스템 상태 모니터링 및 자동 장애 복구 로직 구현.

### 3. AI 모델 편향성 및 예측 오작동

- **설명:** '분석학습부 (360)'와 '예측부 (350)'가 사용하는 학습 데이터가 불균형하거나 편향되어 있으면, 특정 기상 조건이나 질병 패턴에서만 작동하거나 잘못된 예측 (예: 과다/과소 급수) 을 할 수 있음. 이는 '연동학습부 (370)'를 통한 재학습 기간이 길어지거나 시스템 고장으로 이어짐.
- **심각도:** 🟡 Medium (간접적 손실)
- **발생 가능성:** 🟡 Medium (데이터 품질에 의존)
- **대응 방안:** 
  - 학습 데이터 품질 관리 및 다양성 확보 (FAIR 데이터 원칙 등).
  - 예측 결과에 대해 '확인부 (330)'와 같은 인적 모니터링이나 검증 계층을 마련.
  - '연동학습부 (370)'를 통해 모델 버전 관리 및 롤백 (Rollback) 전략 준비.

### 4. 시스템 구성 요소 간 통신 단절 및 고가용성 부재

- **설명:** '진행관리부 (340)'나 '제공부 (320)'와 같은 핵심 모듈 중 하나가 네트워크 문제나 서버 장애로 인해 다운될 경우, 전체 시스템 기능이 마비될 수 있음. 아키텍처상 모듈 간의 상호작용 (↔) 이 많아 연결성 신뢰도가 중요함.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium (외부 환경에 의존)
- **대응 방안:** 
  - Active-Active 또는 Active-Passive 백업 구성 (High Availability) 검토.
  - 서비스 메시 (Service Mesh) 기술을 도입하여 모듈 간 연결성 자동 복구 및 트래픽 분산.
  - '확인부 (330)'에서 시스템 건전성 (Health Check)을 실시간으로 모니터링하여 장애 시점 조기 발견.

### 5. 표준 변경 및 규정 대응 비용

- **설명:** TTA 나 ISO 가 IoT 표준 (예: TTAK.KO-10.1170 등) 을 주기적으로 개정하거나 새로운 보안 요구사항 (예: EU의 IoT Cybersecurity Act 대응) 을 내릴 경우, 기존 아키텍처 ('빅데이터부' 등) 를 대폭 변경해야 하는 비용 발생.
- **심각도:** 🟢 Low (중장기적 부담)
- **발생 가능성:** 🟡 Medium (규제 환경 변화에 따라)
- **대응 방안:** 
  - 아키텍처 설계 시 플러그인 가능 모듈 설계 (예: '미리닝부'에 알고리즘 교체 기능 분리).
  - 표준 변경 모니터링 시스템을 구축하여 규정 준수 여부를 지속적 체크.
  - 기술적 진화와 표준화를 분리된 개발 전략 수립.
