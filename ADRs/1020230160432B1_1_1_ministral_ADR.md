## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 모듈화된 진단 로직 및 확장성 지원 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **장비 진단 및 에러 처리**를 핵심 기능으로 하며, **장비 모델별 진단 로직**, **에러 카운트 기반 재진단**, **부품별 확장적 요인 분석**을 요구한다. 또한 사용자 단말과 연동하여 최종 진단 결과를 제공해야 한다. 현재 시스템은 **고장 여부 재확인부**와 **확장적 요인**을 분리하여 처리해야 하며, **장비 모델별 데이터**와 **사용자 피드백**을 통합하여 확장성을 확보해야 한다. |
| **결정(Decision)** | 1. **모듈화된 진단 엔진** 구축: 기초 진단 결과와 확장적 요인을 분리하여 처리
2. **장비 모델별 진단 로직** 동적 로딩: 장비 모델(120) 데이터베이스와 연동하여 모델별 진단 알고리즘을 동적으로 적용
3. **에러 카운트 기반 재진단** 메커니즘: 에러 카운트(200)가 임계값을 초과할 경우 자동으로 재진단 프로세스 실행
4. **부품별 확장적 요인 분석** 모듈: 부수의 부품(112)의 특정 관련 요인을 별도 모듈로 처리하여 진단 결과에 반영
5. **사용자 단말(300) 연동 API**: 최종 진단 결과를 RESTful API 또는 MQTT 프로토콜을 통해 사용자 단말에 실시간으로 전송 |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준에 따라 **모듈화된 아키텍처**를 적용하여 재사용성과 확장성을 확보
- **oneM2M** 표준의 **기계 간 통신(M2M)** 원칙을 따라 장비 모델별 데이터 동적 로딩을 지원
- **ETSI EN 303 645** 보안 표준 준수를 위해 사용자 단말과 통신 시 **인증된 API**를 사용
- **IEEE 2413** 프레임워크에 따라 **진단 로직을 모듈화**하여 유지보수성을 높임 |
| **결과(Consequences)** | ✅ **장점**: 모듈화로 인해 새로운 장비 모델 추가 시 최소한의 코드 변경으로 대응 가능
✅ **장점**: 에러 카운트 기반 재진단으로 **진단 정확도 향상**
✅ **장점**: 부품별 확장적 요인 분석으로 **정밀한 진단 결과 제공**
❌ **단점**: 모듈 간 통신 오버헤드 발생 가능 (MQTT/REST API 사용으로 완화)
❌ **단점**: 초기 구축 비용 증가 (모듈화 및 표준 준수에 따른 개발 노력) |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 성능**: 모듈화로 인한 통신 오버헤드 vs. 유연성 및 확장성
- **표준 준수 vs. 개발 복잡성**: 국제 표준 준수로 인한 개발 복잡성 vs. 글로벌 상호운용성 |

### **ADR-002: 실시간 데이터 처리 및 사용자 피드백 통합**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **실시간 진단 결과**를 사용자 단말에 제공해야 하며, **사용자 피드백**을 기반으로 진단 로직을 개선해야 한다. 현재 구조에서는 **기초 진단 결과**와 **확장적 요인**이 별도로 처리되므로, 사용자 피드백을 통합하여 **최종 진단 결과**를 동적으로 업데이트해야 한다. |
| **결정(Decision)** | 1. **이벤트 드리븐 아키텍처** 도입: 진단 결과가 발생할 때마다 사용자 단말에 실시간으로 푸시 알림 전송 (MQTT 프로토콜 사용)
2. **피드백 루프 메커니즘**: 사용자 단말로부터 수신된 피드백을 **기초 진단 결과**에 반영하여 머신러닝 모델을 통해 진단 로직 자동 개선
3. **데이터 버스 패턴**: 장비 모델(120), 에러 카운트(200), 사용자 단말(300) 간의 데이터 흐름을 **이벤트 버스**로 통합하여 실시간 처리 |
| **근거(Rationale)** | - **IETF CoAP/MQTT** 표준을 따라 **실시간 통신**을 지원
- **ISO/IEC 27030:2020** 보안 가이드라인을 준수하여 사용자 피드백 데이터를 암호화 처리
- **oneM2M**의 **이벤트 기반 아키텍처** 원칙을 적용하여 확장성 확보 |
| **결과(Consequences)** | ✅ **장점**: 실시간 피드백으로 **진단 로직의 지속적 개선** 가능
✅ **장점**: 사용자 만족도 향상 (즉시 피드백 및 알림 제공)
❌ **단점**: 이벤트 처리 오버헤드 발생 가능 (MQTT 브로커 최적화로 완화)
❌ **단점**: 보안 취약점 위험 (TLS 인증 및 데이터 암호화로 완화) |
| **트레이드오프(Trade-offs)** | - **실시간성 vs. 시스템 복잡성**: 이벤트 드리븐 아키텍처로 인한 복잡성 vs. 실시간 처리 요구사항 |

## ⚠️ **잠재적 위험 분석**

### **1. 모듈 간 통신 지연 및 오버헤드**
- **설명**: 모듈화된 진단 엔진과 장비 모델 데이터베이스 간의 통신 지연으로 **실시간 진단 처리 속도 저하** 발생 가능. 특히, **에러 카운트 기반 재진단** 프로세스에서 병목 현상 발생.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **MQTT 프로토콜**을 사용하여 경량 통신 지원
  - **캐시 메커니즘** 도입: 자주 사용되는 장비 모델 진단 로직을 메모리에 캐시
  - **비동기 처리**를 통해 블로킹 방지

### **2. 보안 취약점 (사용자 단말 및 API)**
- **설명**: 사용자 단말과 연동하는 **RESTful API/MQTT**가 **미인증 접근**이나 **데이터 탈취** 위험에 노출될 수 있다. 특히, **최종 진단 결과**가 암호화되지 않은 채 전송될 경우 보안 사고 발생 가능성 높음.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3**을 사용하여 모든 통신 채널 암호화
  - **OAuth 2.0** 인증 방식을 도입하여 API 접근 통제
  - **KISA 보안 기준(ITU-T X.1352)** 준수하여 기기 인증 강화

### **3. 확장성 제한 (장비 모델 추가 시)**
- **설명**: 새로운 **장비 모델(120)**이 추가될 경우, **동적 로딩 메커니즘**이 제대로 작동하지 않으면 시스템 다운 또는 성능 저하 발생 가능. 특히, **부품별 확장적 요인** 분석 모듈이 기존 로직과 호환되지 않을 경우 오류 발생.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **마이크로 서비스 아키텍처** 도입: 각 장비 모델별로 독립적인 서비스 제공
  - **API 게이트웨이**를 통해 모델별 진단 로직 동적 로딩 지원
  - **테스트 자동화**를 통해 새로운 모델 추가 시 호환성 검증

### **4. 데이터 일관성 문제 (재진단 및 피드백 루프)**
- **설명**: **에러 카운트 기반 재진단**과 **사용자 피드백 루프**가 동시에 발생할 경우, **데이터競合(race condition)**으로 인해 일관성 없는 진단 결과 발생 가능. 예를 들어, 재진단 중 사용자 피드백이 반영되지 않으면 오류진단 발생.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **트랜잭션 메커니즘** 도입: 재진단 및 피드백 처리 시 데이터베이스 트랜잭션 사용
  - **이벤트 소싱 패턴**을 통해 상태 변경 이력을 추적
  - **데드락 방지 알고리즘** 적용

### **5. 운영 및 유지보수 복잡성**
- **설명**: **모듈화된 아키텍처**와 **이벤트 드리븐 시스템**으로 인해 **운영 및 디버깅 복잡성** 증가. 특히, **확장적 요인**과 **기초 진단 결과**가 분리되어 처리되므로 오류 추적이 어려울 수 있다.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🔴 High
- **대응 방안**:
  - **중앙 로그 관리 시스템** 도입 (ELK 스택 사용)
  - **모니터링 도구** (Prometheus + Grafana)를 통해 시스템 상태 실시간 모니터링
  - **문서화 자동화**: Swagger/OpenAPI를 통해 API 및 모듈 인터페이스 자동 문서화
