# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 통합 서비스 레이어 기반의 API-First 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 매설 관로라는 물리적 자산에 대한 데이터(관로정보, 위치정보)를 수집하고, 이를 다양한 사용자(현장 작업자, 설계 엔지니어, 국가 재난 대응 기관)와 여러 플랫폼(Web GIS, Mobile App, IoT 기기)에 제공해야 하는 복합적인 환경에 놓여 있습니다. 핵심 과제는 이처럼 이종적이고 비동기적인 데이터 소스(NFC, GPS, 수동 입력, 센서)를 실시간으로 통합하고, 각 소비자의 요구사항(Stakeholder Concerns)에 맞춰 최적화된 서비스를 제공하는 것입니다. |
| **결정(Decision)** | 데이터의 입력, 처리, 그리고 외부 노출(Exposition)의 모든 계층에 걸쳐 **API 게이트웨이(API Gateway) 중심의 서비스 지향 아키텍처(SOA) 및 마이크로 서비스 아키텍처(MSA)**를 채택합니다. 모든 기능적 로직은 비즈니스 도메인별 독립적인 마이크로 서비스로 분리하고, 이들을 단일 게이트웨이를 통해 통합적으로 관리합니다. |
| **근거(Rationale)** | 1. **확장성 및 이종성 대응:** MSA는 각 서비스(예: 관로 데이터 관리, 위치 정보 결합, 재난 예측 모듈)를 독립적으로 개발, 배포, 확장할 수 있게 합니다. 이는 국제표준 (ISO/IEC 30141)이 요구하는 재사용 가능하고 유연한 아키텍처 설계에 부합합니다. 2. **사용자별 분리:** API 게이트웨이는 복잡한 내부 아키텍처를 외부에 숨기고, 클라이언트(Web, App, IoT)별로 맞춤형 API를 제공함으로써, 각 사용자가 필요한 정보만 받아볼 수 있도록 하여 보안과 효율성을 극대화합니다. 3. **진화 대응:** 새로운 센서나 표준(oneM2M, Matter)이 추가되어도 기존 핵심 시스템을 건드리지 않고 새로운 마이크로 서비스를 통합할 수 있어 시스템의 수명 주기를 연장합니다. |
| **결과(Consequences)** | **긍정적:** 극도의 유연성과 확장성을 확보하며, 새로운 기능을 점진적(Incremental)으로 추가할 수 있습니다. 중앙 집중식 API 관리로 데이터 거버넌스를 강화할 수 있습니다. **부정적:** 아키텍처 초기 설계 복잡도가 매우 높고, 서비스 간 통신(Inter-Service Communication) 관리를 위한 운영 오버헤드가 증가합니다. |
| **트레이드오프(Trade-offs)** | **얻는 장점:** 압도적인 유연성, 높은 복원력(Fault Isolation), 독립적 배포(Independent Deployment). **감수해야 할 단점:** 초기 개발 비용 및 복잡도 급증, 트랜잭션 관리를 위한 분산 트랜잭션(Distributed Transaction) 복잡성 처리 필요. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 무결성 및 출처 신뢰성 문제 (Data Integrity & Source Trust)
- **설명:** 시스템은 NFC, GPS(위치정보), 수동 입력(관로정보), 센서 등 매우 이질적인 출처의 데이터를 결합합니다. 만약 현장 작업자가 잘못된 데이터를 입력하거나, 센서가 오염된 데이터를 전송할 경우, 통합 서버에 부정확한 '진실'이 저장되어 재난 대응과 같은 치명적인 의사결정 오류를 초래할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **데이터 거버넌스 및 검증 계층(Validation Layer) 필수 도입.** 1. **입력 계층 통제:** 입력 데이터에 대한 필드 검증(Field Validation) 규칙을 엄격히 적용하고, 2. **교차 검증:** GPS 데이터와 NFC를 통한 물리적 위치 기반의 상호 교차 검증(Cross-Validation) 메커니즘을 구현하여 데이터 이상치를 감지하고 플래그를 지정해야 합니다.

### 2. 사이버 보안 및 물리적 접근 위험 (Cybersecurity & Physical Access)
- **설명:** 이 시스템은 국가 핵심 인프라(상하수도, 가스, 전력)에 관한 민감한 정보를 다룹니다. API Gateway를 통해 외부에 노출되는 각 서비스(Web, App)가 해킹당하거나, 내부 서버가 제어권을 탈취당할 경우, 핵심 인프라에 대한 가짜 정보가 유포되거나 원격 제어 공격이 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **Defense-in-Depth(깊이 방어) 원칙 적용.** 1. **접근 제어:** OAuth 2.0 및 JWT 기반의 엄격한 접근 제어 및 사용자 역할 기반 접근 통제(RBAC)를 구현해야 합니다. 2. **네트워크 분리:** 핵심 운영 데이터베이스와 외부 인터페이스/API Gateway는 물리적/논리적으로 분리하고, 모든 통신은 암호화(TLS/SSL)되어야 합니다. 3. **보안 감사:** 국제 표준 (ITU-T X.1352, ETSI EN 303 645)에 맞춰 정기적인 침투 테스트와 보안 감사를 의무화합니다.

### 3. 시스템 상호운용성 및 표준 준수 문제 (Interoperability & Standardization)
- **설명:** 시스템은 NFC(근거리), GPS(위치), 네트워크 센서(IoT), 레거시 장비 인터페이스 등 너무 많은 이종 기술 표준을 다룹니다. 표준화된 API가 아닌 프로토콜 기반으로 연결될 경우, 특정 제조사나 기술 스택에 종속되거나(Vendor Lock-in), 표준 업데이트가 발생했을 때 전체 시스템을 재설계해야 하는 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **오픈 표준 API 및 메시지 포맷 강제 적용.** 1. **표준화:** 모든 데이터 교환은 JSON/XML 등 개방형 형식으로 통일하고, 메시징 버스(e.g., Kafka)를 활용하여 느슨한 결합(Loose Coupling)을 유지해야 합니다. 2. **참조 아키텍처:** ISO/IEC 30141과 같이 공통된 용어와 모델을 정의하는 참조 아키텍처 모델을 도입하여 표준 준수 여부를 강제해야 합니다.

### 4. 실시간 성능 및 대용량 데이터 부하 문제 (Real-time Performance & Scalability)
- **설명:** 재난 현장이나 대규모 점검 시, 수십만 건에 달하는 관로, 지질, 장비 데이터를 지연 없이 실시간으로 조회하고 결합하는 것은 엄청난 부하를 발생시킵니다. 특히 지리정보 시스템(GIS) 레이어와 실시간 센서 데이터의 결합 쿼리는 고도의 성능을 요구합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **데이터 캐싱 및 분산 검색 엔진 도입.** 1. **지리공간 인덱싱:** PostGIS와 같은 전용 지리공간 데이터베이스를 사용하여 쿼리 속도를 최적화합니다. 2. **캐싱 레이어:** 자주 조회되는 마스터 데이터(관로 경로, 시설물 ID 등)는 Redis와 같은 인메모리 캐시를 사용하여 DB 부하를 최소화하고 응답 속도를 확보해야 합니다.

### 5. 운용 환경의 비정형성 및 가용성 확보 문제 (Operation Environment Variability & Availability)
- **설명:** 현장(지진/재난/매설물)은 전력 공급이나 네트워크 연결이 불안정하거나 완전히 두절되는 비정형적 상황이 빈번합니다. 시스템의 핵심 기능을 이 같은 극한 환경에서도 지속적으로 수행할 수 있는 가용성(Availability) 확보가 어렵습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** **오프라인 최우선 아키텍처 설계 (Offline-First Design).** 1. **현장 장치:** 현장 단말기(태블릿, NFC 리더기)는 핵심 데이터를 로컬에 임시 저장하고, 네트워크가 복구되면 자동으로 서버와 동기화(Sync)하는 기능을 갖춰야 합니다. 2. **백업:** 필수 기능은 최소한 2개 이상의 다른 물리적/논리적 백업 채널(예: 위성 통신 백업, 로컬 서버)을 확보하여, 단일 실패 지점(Single Point of Failure)을 원천 제거해야 합니다.
