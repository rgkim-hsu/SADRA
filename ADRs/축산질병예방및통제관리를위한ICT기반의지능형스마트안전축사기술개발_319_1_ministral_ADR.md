## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 이중 계층 제어 로직 구현 (Temperature & Humidity/Gas Control Stage 분리)**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 온도, 습도, 가스 농도(CO₂, NH₃) 등 환경 조건을 실시간으로 감지하여 제어 상태를 결정해야 함. 단일 제어 로직으로 통합 시 복잡성과 유지보수성이 증가하며, 각 환경 변수가 독립적으로 최적화되어야 함. |
| **결정(Decision)** | 1) **온도 기반 제어 계층**: `High/Low/Normal State`로 분류된 온도 상태에 따라 제어 로직을 분리하여 구현. <br> 2) **습도 및 가스 기반 제어 계층**: `Relative Humidity`, `CO₂`, `NH₃`의 임계값을 독립적으로 모니터링하여 제어 로직을 실행. <br> 3) **상태 전이 로직**: 온도와 습도/가스 제어 계층 간 상호작용을 최소화하고, `Normal State`를 중앙 집중식으로 관리하여 일관된 제어 정책을 적용. |
| **근거(Rationale)** | - **모듈성 강화**: 각 환경 변수별로 독립적인 제어 로직을 구현하여 시스템 확장성과 재사용성을 높임. <br> - **실시간 대응성**: 온도와 가스/습도 제어 로직이 병렬 처리되어 지연 시간을 최소화. <br> - **표준 준수**: ISO/IEC 30141:2024의 "재사용 가능한 설계" 원칙과 oneM2M의 "모듈화 아키텍처" 요구사항에 부합. <br> - **안전성**: ETSI EN 303 645의 "임계값 기반 제어" 요구사항을 충족하여 위험한 환경 조건을 사전에 방지. |
| **결과(Consequences)** | - **장점**: 유지보수성 향상, 독립적 테스트 및 배포 가능, 표준 준수성 강화. <br> - **단점**: 계층 간 통신 오버헤드 발생 가능, 초기 구현 복잡성 증가. |
| **트레이드오프(Trade-offs)** | - **모듈성 vs. 복잡성**: 독립적 제어 로직으로 인한 초기 복잡성 증가로 인해 단기적으로 개발 비용이 상승하지만, 장기적으로 시스템 유연성과 확장성을 확보. <br> - **통신 오버헤드**: 계층 간 상태 동기화를 위한 추가 통신 프로토콜(예: MQTT) 필요. |

### **ADR-002: 상태 전이 로직의 임계값 관리 방식**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템의 상태 전이 로직(예: `T_indoor > T_high + δ`)은 환경 조건의 변동에 따라 동적으로 조정되어야 함. 고정 임계값은 시스템의 적응성을 저하시키고, 사용자 요구사항에 맞지 않을 수 있음. |
| **결정(Decision)** | 1) **동적 임계값 조정**: 사용자 또는 외부 시스템(예: 스마트팜 관리 플랫폼)에서 임계값(`δ`, `α`, `β`)을 실시간으로 업데이트할 수 있도록 API를 제공. <br> 2) **기본값 설정**: 초기 임계값은 ISO/IEC 27030:2020의 "안전한 환경 범위" 가이드라인에 따라 설정. <br> 3) **로그 기록**: 모든 상태 전이 이벤트와 임계값 변경 이력을 로그로 기록하여 오류 분석에 활용. |
| **근거(Rationale)** | - **유연성**: TTA의 "스마트팜 데이터 상호운용 프레임워크" 표준에 따라 사용자 정의 임계값을 지원. <br> - **안전성**: ITU-T X.1352의 "보안 요구사항"을 준수하여 임계값 변경 시 인증된 접근만 허용. <br> - **디버깅 지원**: 상태 전이 로그를 통해 시스템 이상을 사후 분석 가능. |
| **결과(Consequences)** | - **장점**: 사용자 맞춤형 제어 가능, 시스템 적응성 강화. <br> - **단점**: 임계값 관리 시스템 추가로 인한 복잡성 증가, 보안 취약점 risks. |
| **트레이드오프(Trade-offs)** | - **유연성 vs. 보안**: 동적 임계값 조정을 위한 API 노출로 인해 보안 취약점이 발생할 수 있으나, KISA의 "IoT 보안 인증 기준"을 적용하여 완화. |

### **ADR-003: 데이터 통합 및 상호운용성 프레임워크**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 온도, 습도, 가스 데이터는 서로 다른 센서 및 시스템에서 수집되며, 통합된 분석과 제어가 필요함. 현재 시스템은 데이터 포맷 및 통신 프로토콜의 다변화로 인해 상호운용성이 저하됨. |
| **결정(Decision)** | 1) **통합 데이터 모델**: oneM2M의 "공통 정보 모델"을 기반으로 모든 환경 데이터를 표준화된 포맷(예: JSON/CoAP)으로 변환. <br> 2) **통신 프로토콜**: MQTT를 주 프로토콜로 채택하여 경량 통신과 실시간 데이터 전송을 지원. <br> 3) **API 게이트웨이**: 모든 센서 데이터가 통합 API를 통해 접근 가능하도록 게이트웨이를 구현. |
| **근거(Rationale)** | - **표준 준수**: oneM2M과 Matter 표준의 "데이터 상호운용성" 요구사항을 충족. <br> - **효율성**: MQTT 프로토콜은 IETF 표준으로 채택되어 IoT 환경에서 광범위하게 지원됨. <br> - **확장성**: TTA의 "스마트팜 데이터 프레임워크"와 호환성을 확보하여 미래 확장 가능성 확보. |
| **결과(Consequences)** | - **장점**: 데이터 통합 및 분석 용이성 향상, 프로토콜 호환성 강화. <br> - **단점**: 초기 프로토콜 변환 로직 구현 비용 발생. |
| **트레이드오프(Trade-offs)** | - **호환성 vs. 성능**: MQTT의 경량 특성으로 인해 통신 오버헤드가 최소화되지만, 초기 데이터 변환 로직 구현이 필요. |

## ⚠️ **잠재적 위험 분석**

### **1. 센서 데이터 오류 및 이상치 발생**
- **설명**: 센서의 노이즈, 고장, 또는 오염으로 인해 잘못된 환경 데이터가 수집되어 제어 상태가 오류로 전이될 수 있음. 예: 온도 센서 고장으로 `High Temperature State`로 오인식.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **중복 센서 배치**: critical한 환경 변수(온도, CO₂)에는 중복 센서를 설치하여 데이터 교차 검증.
  - **이상치 탐지 알고리즘**: 통계적 방법(예: Z-score, IQR)을 사용하여 이상치 필터링.
  - **자동 재구성**: 센서 오류 감지 시 시스템이 자동으로 백업 센서로 전환.

### **2. 상태 전이 로직의 경쟁 조건(Race Condition)**
- **설명**: 실시간으로 발생하는 상태 전이 이벤트(예: 온도와 습도 동시 변동)가 경쟁 조건을 유발하여 일관되지 않은 제어 상태가 발생할 수 있음.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **동기화 메커니즘**: 상태 전이 로직에 뮤텍스(lock) 또는 분산 트랜잭션(예: Saga 패턴)을 적용.
  - **이벤트 큐**: 상태 변경을 이벤트 기반 큐(예: Kafka)로 처리하여 순차적 처리 보장.
  - **상태 머신 모델**: 상태 전이를 유한 상태 머신(FSM)으로 모델링하여 일관성 검증.

### **3. 보안 취약점: 임계값 조작 공격**
- **설명**: 악의적인 사용자가 임계값(`δ`, `α`, `β`)을 조작하여 시스템을 비정상 상태로 유도할 수 있음. 예: 온도 임계값을 낮추어 과도한 냉방/난방 발생.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **인증된 API 접근**: 임계값 수정 API에 OAuth 2.0 또는 JWT 인증을 적용.
  - **로그 감사**: 모든 임계값 변경 이력을 불변성 저장소(예: Blockchain-based 로그)에 기록.
  - **역량 제한**: 임계값 변경 주기에 대한 속도 제한(예: 1시간에 1회만 수정 가능) 적용.

### **4. 시스템 오버헤드: 계층 간 통신 지연**
- **설명**: 온도/습도/가스 제어 계층 간 상태 동기화를 위한 통신이 지연을 유발하여 실시간 제어가 저하될 수 있음.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **경량 프로토콜**: 상태 동기화를 위한 통신에 gRPC-streaming 또는 WebSocket을 활용.
  - **캐시 메커니즘**: 자주 접근하는 상태 데이터를 Redis와 같은 인메모리 캐시에 저장.
  - **지역적 처리**: 가능한 한 각 제어 계층을 에지 디바이스에서 처리하여 클라우드 통신 줄임.

### **5. 표준 변경에 따른 호환성 문제**
- **설명**: IoT 표준(예: ISO/IEC 30141:2024, oneM2M)이 업데이트되면 시스템이 기존 표준과 호환되지 않을 수 있음.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟢 Low (단기적으로)
- **대응 방안**:
  - **버전 관리**: 시스템 코드에 표준 버전 정보를 포함하고, 업데이트 시 자동 호환성 체크 스크립트 실행.
  - **추상화 계층**: 표준 종속성을 추상화 계층(예: Adapter 패턴)으로 분리하여 변경에 대한 영향을 최소화.
  - **모니터링 시스템**: 표준 업데이트를 모니터링하고, 필요한 경우 시스템을 사전 테스트 환경에서 검증.

### **6. 유지보수성 저하: 복잡한 상태 전이 로직**
- **설명**: 다수의 상태 전이 조건(예: `T_indoor > T_low - α`)과 임계값이 복잡하게 얽혀 있어 유지보수가 어려워질 수 있음.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **시각화 도구**: 상태 전이 로직을 PlantUML 또는 Mermaid로 문서화하여 가시성 향상.
  - **단위 테스트**: 모든 상태 전이 조건에 대한 단위 테스트 자동화(예: JUnit, pytest).
  - **모듈화**: 상태 전이 로직을 독립적 서비스(예: State Transition Service)로 분리하여 개별 테스트 가능.
