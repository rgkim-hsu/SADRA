## 📋 ADR (Architecture Decision Record)

### **ADR-001: IoT 기반 스마트팜 시스템의 모듈별 분산 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 빅데이터 처리, 실시간 모니터링, 예측 분석, 그리고 외부 서비스 제공 등 다중 기능이 요구됩니다. 중앙 집중식 아키텍처는 확장성, 유연성, 그리고 실시간 처리에 제약이 존재하며, IoT 표준(ISO/IEC 30141:2024, oneM2M)에서는 분산 아키텍처를 권장합니다. |
| **결정(Decision)** | **모듈별 분산 아키텍처** 채택: 각 기능(빅데이터, 확인, 예측, 제공)을 독립된 모듈로 분리하고, 이벤트 기반 메시지 큐(예: Kafka, RabbitMQ)를 통해 상호작용합니다. |
| **근거(Rationale)** | 1. **확장성**: 모듈별 배포로 수평적 확장 가능 (ex: 빅데이터부만 스케일링 가능).
2. **유연성**: 각 모듈의 기술 스택 독립적 선택 가능 (ex: 예측부: TensorFlow/PyTorch, 제공부: REST/gRPC).
3. **실시간 처리**: 이벤트 기반 통신으로 지연 시간 최소화.
4. **표준 준수**: ISO/IEC 30141의 "재사용 가능한 설계" 원칙과 oneM2M의 "모듈화 아키텍처" 권장사항에 부합.
5. **故障 격리**: 하나의 모듈 장애가 전체 시스템에 영향을 미치지 않음. |
| **결과(Consequences)** | ✅ **장점**:
- 모듈별 CI/CD 파이프라인 구축 가능.
- 보안 정책을 모듈별로 세분화 가능 (ex: 예측부 데이터 암호화 강화).
- TTA 스마트팜 표준(예: "스마트팜 데이터 상호운용 프레임워크")와의 호환성 높음.
❌ **단점**:
- 모듈 간 통신 오버헤드 발생 (대응: Protobuf/MessagePack 사용).
- 운영 복잡성 증가 (대응: Terraform/Ansible으로 IaC 적용). |
| **트레이드오프(Trade-offs)** | - **성능 vs. 복잡성**: 분산 시스템의 통신 오버헤드 vs. 중앙 시스템의 단순성.
- **비용 vs. 확장성**: 초기 설정 비용 증가 vs. 장기적 확장성 이점. |

### **ADR-002: 데이터 처리 플로우의 이벤트 소싱 패턴 적용**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 센서 데이터(온도, 습도, 질병 감지 등)가 실시간으로 생성되며, 이 데이터는 **불변성**과 **추적 가능성**이 요구됩니다. 전통적 CRUD 방식은 데이터 변천사 추적이 어렵습니다. |
| **결정(Decision)** | **이벤트 소싱 패턴** 채택: 모든 상태 변화를 이벤트로 기록하고, 각 모듈(예: 예측부, 제공부)은 이벤트 스트림을 구독하여 상태를 재구축합니다. |
| **근거(Rationale)** | 1. **데이터 무결성**: 이벤트 로그를 통해 모든 상태 변화 추적 가능 (forensics, 오류 복구).
2. **표준 준수**: ISO/IEC 27030(보안 가이드라인)의 "데이터 무결성" 요구사항 충족.
3. **유연성**: 새로운 분석 모듈 추가 시 기존 데이터 재처리 가능 (ex: 과거 질병 데이터로 새로운 모델 학습).
4. **복원력**: 시스템 장애 시 마지막 이벤트부터 재구축 가능. |
| **결과(Consequences)** | ✅ **장점**:
- KISA 보안 기준(ITU-T X.1352)의 "데이터 추적성" 요구사항 만족.
- TTA "스마트팜 데이터 상호운용 프레임워크"와의 호환성 높음.
❌ **단점**:
- 초기 저장소 용량 증가 (대응: 로그 압축 및 TTL 설정).
- 복잡한 이벤트 처리 로직 필요 (대응: Kafka Streams/Spark Streaming 사용). |
| **트레이드오프(Trade-offs)** | - **저장소 비용 vs. 데이터 가용성**: 로그 저장 비용 증가 vs. 데이터 복원력 향상.
- **처리 복잡성 vs. 유연성**: 이벤트 처리 로직 복잡성 vs. 시스템 유연성. |

### **ADR-003: 보안 아키텍처의 제로 트러스트 모델 적용**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 IoT 기기, 에지 서버, 클라우드 모듈 등 다중 계층으로 구성되며, **ETSI EN 303 645**와 **ISO/IEC 27030**은 엄격한 보안 요구사항을 규정합니다. 전통적 방화벽은 내부 공격에 취약합니다. |
| **결정(Decision)** | **제로 트러스트 모델** 적용:
- 모든 모듈(빅데이터부, 예측부 등)은 **인증/인가**를 통해 접근 통제.
- 모듈 간 통신은 **mTLS**로 암호화.
- 데이터는 **필드 레벨 암호화** 적용. |
| **근거(Rationale)** | 1. **표준 준수**: ETSI EN 303 645의 "사이버보안 요구사항" 충족.
2. **공격 방어**: 내부/외부 공격 모두 방지 (ex: 예측부에서 빅데이터부로의 접근 통제).
3. **규제 준수**: KISA "IoT 보안 시험 기준"에 따른 인증 가능성 높음.
4. **데이터 보호**: 필드 레벨 암호화로 PII(개인 식별 정보) 보호. |
| **결과(Consequences)** | ✅ **장점**:
- 보안 인증(ISO/IEC 27030) 가능성 향상.
- TTA "스마트팜 보안 가이드라인"과의 호환성 높음.
❌ **단점**:
- 인증/암호화 오버헤드 (대응: 하드웨어 보안 모듈(HSM) 사용).
- 운영 복잡성 증가 (대응: 자동화된 보안 모니터링 도구 사용). |
| **트레이드오프(Trade-offs)** | - **성능 오버헤드 vs. 보안**: 암호화/인증 지연 vs. 데이터 보호.
- **비용 vs. 보안**: HSM/보안 도구 비용 vs. 데이터 유출 위험. |

## ⚠️ 잠재적 위험 분석

### **1. 모듈 간 통신 지연**
- **설명**: 분산 아키텍처에서 모듈 간 메시지 큐(예: Kafka) 또는 API 호출 지연으로 실시간 처리 성능 저하 발생. 특히 예측부(ML 모델)가 빅데이터부로부터 데이터를 받아야 하는 경우, 지연이 예측 정확도에 영향을 미침.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 배치 처리**: Kafka의 배치 크기 및 주기 조절 (ex: 100ms마다 배치 전송).
  - **에지 캐싱**: 예측부에서 빈번히 접근하는 빅데이터를 로컬 캐시(Redis) 저장.
  - **모니터링**: Prometheus + Grafana으로 통신 지연 모니터링 및 경고 설정.

### **2. 데이터 일관성 문제**
- **설명**: 이벤트 소싱 패턴에서 모듈별로 상태를 재구축하는 과정에서 일관성 오류 발생 가능 (ex: 예측부와 제공부가 다른 이벤트 버전을 참조).
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 버전 관리**: 모든 이벤트에 버전 스탬프 추가 및 모듈별 버전 동기화.
  - **트랜잭션 로그**: Saga 패턴을 통해 분산 트랜잭션 관리 (ex: 예측부와 제공부 업데이트를 하나의 Saga로 묶음).
  - **체크섬 검증**: 모듈 간 데이터 교환 시 체크섬으로 무결성 검사.

### **3. 보안 취약점 노출**
- **설명**: 제로 트러스트 모델 적용에도 불구하고, 모듈 간 인증/암호화 설정 오류로 보안 취약점 발생 가능 (ex: mTLS 설정 미비, 필드 레벨 암호화 미적용).
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **자동화된 보안 스캔**: Terraform + OpenPolicyAgent를 통해 인프라 코드 보안 검사.
  - **정기 오디트**: KISA "IoT 보안 인증 기준"에 따른 3개월마다 보안 오디트 실시.
  - **강제 접근 제어**: 모듈 간 API 게이트웨이(OAuth2 + JWT)를 통해 접근 통제 강화.

### **4. 확장성瓶頸**
- **설명**: 특정 모듈(예: 빅데이터부)의 수평적 확장에도 불구하고, 의존 모듈(예: 예측부)의 처리 능력이 병목 현상 발생. 특히 ML 모델의 추론 속도가 데이터 처리 속도를 따라가지 못할 경우.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **모듈별 스케일링**: Kubernetes HPA(Horizontal Pod Autoscaler)를 통해 동적 스케일링.
  - **로드 테스팅**: Locust를 사용하여 모듈별 부하 테스트 및 병목 분석.
  - **미리 캐싱**: 예측부에서 빈번히 사용되는 빅데이터를 CDN(Cloudflare) 캐싱.

### **5. 운영 복잡성 증가**
- **설명**: 분산 아키텍처와 이벤트 소싱 패턴으로 인해 운영 복잡성이 증가하여 DevOps 팀의 유지보수 부담 증가. 특히 로그 추적 및 장애 진단이 어려워짐.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🔴 High
- **대응 방안**:
  - **중앙화된 로깅**: ELK 스택(Elasticsearch, Logstash, Kibana)을 통해 모듈별 로그 통합 관리.
  - **자동화된 배포**: ArgoCD를 통해 GitOps 기반 CI/CD 파이프라인 구축.
  - **문서화**: 각 모듈의 API 스펙과 이벤트 스키마를 Swagger/OpenAPI로 문서화.

2. **표준 준수**: ISO/IEC 27030(보안 가이드라인)의 "데이터 무결성" 요구사항 충족.
3. **유연성**: 새로운 분석 모듈 추가 시 기존 데이터 재처리 가능 (ex: 과거 질병 데이터로 새로운 모델 학습).
4. **복원력**: 시스템 장애 시 마지막 이벤트부터 재구축 가능. |
| **결과(Consequences)** | ✅ **장점**:
- KISA 보안 기준(ITU-T X.1352)의 "데이터 추적성" 요구사항 만족.
- TTA "스마트팜 데이터 상호운용 프레임워크"와의 호환성 높음.
❌ **단점**:
- 초기 저장소 용량 증가 (대응: 로그 압축 및 TTL 설정).
- 복잡한 이벤트 처리 로직 필요 (대응: Kafka Streams/Spark Streaming 사용). |
| **트레이드오프(Trade-offs)** | - **저장소 비용 vs. 데이터 가용성**: 로그 저장 비용 증가 vs. 데이터 복원력 향상.
- **처리 복잡성 vs. 유연성**: 이벤트 처리 로직 복잡성 vs. 시스템 유연성. |

### **ADR-003: 보안 아키텍처의 제로 트러스트 모델 적용**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 IoT 기기, 에지 서버, 클라우드 모듈 등 다중 계층으로 구성되며, **ETSI EN 303 645**와 **ISO/IEC 27030**은 엄격한 보안 요구사항을 규정합니다. 전통적 방화벽은 내부 공격에 취약합니다. |
| **결정(Decision)** | **제로 트러스트 모델** 적용:
- 모든 모듈(빅데이터부, 예측부 등)은 **인증/인가**를 통해 접근 통제.
- 모듈 간 통신은 **mTLS**로 암호화.
- 데이터는 **필드 레벨 암호화** 적용. |
| **근거(Rationale)** | 1. **표준 준수**: ETSI EN 303 645의 "사이버보안 요구사항" 충족.
2. **공격 방어**: 내부/외부 공격 모두 방지 (ex: 예측부에서 빅데이터부로의 접근 통제).
3. **규제 준수**: KISA "IoT 보안 시험 기준"에 따른 인증 가능성 높음.
4. **데이터 보호**: 필드 레벨 암호화로 PII(개인 식별 정보) 보호. |
| **결과(Consequences)** | ✅ **장점**:
- 보안 인증(ISO/IEC 27030) 가능성 향상.
- TTA "스마트팜 보안 가이드라인"과의 호환성 높음.
❌ **단점**:
- 인증/암호화 오버헤드 (대응: 하드웨어 보안 모듈(HSM) 사용).
- 운영 복잡성 증가 (대응: 자동화된 보안 모니터링 도구 사용). |
| **트레이드오프(Trade-offs)** | - **성능 오버헤드 vs. 보안**: 암호화/인증 지연 vs. 데이터 보호.
- **비용 vs. 보안**: HSM/보안 도구 비용 vs. 데이터 유출 위험. |

## ⚠️ 잠재적 위험 분석

### **1. 모듈 간 통신 지연**
- **설명**: 분산 아키텍처에서 모듈 간 메시지 큐(예: Kafka) 또는 API 호출 지연으로 실시간 처리 성능 저하 발생. 특히 예측부(ML 모델)가 빅데이터부로부터 데이터를 받아야 하는 경우, 지연이 예측 정확도에 영향을 미침.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 배치 처리**: Kafka의 배치 크기 및 주기 조절 (ex: 100ms마다 배치 전송).
  - **에지 캐싱**: 예측부에서 빈번히 접근하는 빅데이터를 로컬 캐시(Redis) 저장.
  - **모니터링**: Prometheus + Grafana으로 통신 지연 모니터링 및 경고 설정.

### **2. 데이터 일관성 문제**
- **설명**: 이벤트 소싱 패턴에서 모듈별로 상태를 재구축하는 과정에서 일관성 오류 발생 가능 (ex: 예측부와 제공부가 다른 이벤트 버전을 참조).
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 버전 관리**: 모든 이벤트에 버전 스탬프 추가 및 모듈별 버전 동기화.
  - **트랜잭션 로그**: Saga 패턴을 통해 분산 트랜잭션 관리 (ex: 예측부와 제공부 업데이트를 하나의 Saga로 묶음).
  - **체크섬 검증**: 모듈 간 데이터 교환 시 체크섬으로 무결성 검사.

### **3. 보안 취약점 노출**
- **설명**: 제로 트러스트 모델 적용에도 불구하고, 모듈 간 인증/암호화 설정 오류로 보안 취약점 발생 가능 (ex: mTLS 설정 미비, 필드 레벨 암호화 미적용).
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **자동화된 보안 스캔**: Terraform + OpenPolicyAgent를 통해 인프라 코드 보안 검사.
  - **정기 오디트**: KISA "IoT 보안 인증 기준"에 따른 3개월마다 보안 오디트 실시.
  - **강제 접근 제어**: 모듈 간 API 게이트웨이(OAuth2 + JWT)를 통해 접근 통제 강화.

### **4. 확장성瓶頸**
- **설명**: 특정 모듈(예: 빅데이터부)의 수평적 확장에도 불구하고, 의존 모듈(예: 예측부)의 처리 능력이 병목 현상 발생. 특히 ML 모델의 추론 속도가 데이터 처리 속도를 따라가지 못할 경우.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **모듈별 스케일링**: Kubernetes HPA(Horizontal Pod Autoscaler)를 통해 동적 스케일링.
  - **로드 테스팅**: Locust를 사용하여 모듈별 부하 테스트 및 병목 분석.
  - **미리 캐싱**: 예측부에서 빈번히 사용되는 빅데이터를 CDN(Cloudflare) 캐싱.

### **5. 운영 복잡성 증가**
- **설명**: 분산 아키텍처와 이벤트 소싱 패턴으로 인해 운영 복잡성이 증가하여 DevOps 팀의 유지보수 부담 증가. 특히 로그 추적 및 장애 진단이 어려워짐.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🔴 High
- **대응 방안**:
  - **중앙화된 로깅**: ELK 스택(Elasticsearch, Logstash, Kibana)을 통해 모듈별 로그 통합 관리.
  - **자동화된 배포**: ArgoCD를 통해 GitOps 기반 CI/CD 파이프라인 구축.
  - **문서화**: 각 모듈의 API 스펙과 이벤트 스키마를 Swagger/OpenAPI로 문서화.
