# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 실시간 비동기 스트림 처리 아키텍처 도입

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 이 시스템은 스마트 농장/사육 환경과 같이, 온도, 습도, 생체 신호, 환경 변화 등 이질적이고(Heterogeneous), 높은 빈도(High Velocity)로 발생하는 센서 데이터를 통합적으로 수집하고, 이를 기반으로 즉각적인 의사결정(작업 추천/제어)을 내려야 합니다. 기존의 배치(Batch) 처리 방식으로는 실시간 요구사항(Low Latency)을 충족할 수 없으며, 데이터 손실 없이 빠른 반응 속도가 핵심 과제입니다. |
| **결정(Decision)** | **스트림 프로세싱 기반의 하이브리드 아키텍처(Edge-to-Cloud Stream Processing)를 채택합니다.** 데이터를 수집하는 단계(모니터링)에서 경량 프로토콜(MQTT/CoAP)과 에지 컴퓨팅을 활용하여 전처리/필터링을 수행하고, 중앙 시스템은 Apache Kafka 또는 유사한 메시지 브로커를 핵심 메시징 계층으로 사용하며, Flink/Spark Streaming 등 스트림 처리 엔진을 이용해 실시간 상태 관리 및 이상 감지를 수행합니다. |
| **근거(Rationale)** | 1. **저지연성 확보:** 에지 컴퓨팅은 네트워크 병목 현상을 줄이고 실시간 제어에 필수적인 낮은 지연 시간(Low Latency)을 보장합니다. 2. **처리 능력:** Kafka는 대규모 데이터 스트림을 안정적으로 처리할 수 있는 분산 메시징 시스템의 표준을 제시합니다. 3. **탄력성:** 스트림 처리는 데이터의 흐름(Stream) 자체를 처리 대상으로 삼기 때문에, 시스템 부하 변동에 유연하게 대응할 수 있습니다. |
| **결과(Consequences)** | **긍정적:** 환경 데이터 변화에 즉각적으로 반응하는 고도화된 제어 및 추천 시스템 구현이 가능하며, 데이터 무결성과 처리 성능이 획기적으로 향상됩니다. **부정적:** 시스템의 복잡도가 급격히 증가하며, 에지 장치와 스트림 엔진에 대한 전문 인력 및 지속적인 관리가 필수적입니다. |
| **트레이드오프(Trade-offs)** | **[획득 장점]** 실시간성(Real-time responsiveness)과 대규모 데이터 처리 능력(Scalability)을 동시에 확보합니다. **[감수 단점]** 시스템 설계 및 운영 복잡성(Complexity)이 가장 큰 리스크입니다. 따라서 표준화된 컨테이너 오케스트레이션(Kubernetes)을 통해 복잡도를 관리해야 합니다. |

## ⚠️ 잠재적 위험 분석

### 1. **데이터 무결성 및 센서 신뢰도 저하**
- **설명:** 환경정보수집부(21)에서 오는 센서 데이터가 물리적 환경 변화, 센서 오염(Drift), 또는 통신 오류로 인해 잘못되거나 누락될 경우, 객체식분류(22) 및 작업추천부(42)가 오작동하여 잘못된 제어 명령을 내릴 수 있습니다. (예: 실제 온도가 정상인데 시스템이 고장으로 인식하여 냉각을 과도하게 실행)
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 다중 센서 융합(Sensor Fusion) 및 이력 기반의 이상 탐지 로직(Anomaly Detection)을 구현합니다. 각 센서 데이터에 대한 신뢰 지수(Confidence Score)를 부여하고, 특정 임계값 이하의 데이터는 경고 처리 후 제어 모듈에서 제외하도록 설계해야 합니다.

### 2. **운영 환경의 보안 취약점 (Edge-to-Cloud)**
- **설명:** 시스템은 수많은 물리적 센서와 에지 게이트웨이(Edge Gateway)를 통해 데이터를 수집합니다. 이 중 단 하나의 취약한 센서 노드나 통신 게이트웨이가 해킹될 경우, 전체 제어 모듈이 위변조된 데이터를 기반으로 오작동할 위험이 있습니다. (특히, 스마트팜의 경우 생명과 직결되는 시스템에 대한 공격 위험이 존재함)
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **최소 권한 원칙(Principle of Least Privilege)**을 적용하고, 모든 통신 구간(Edge $\leftrightarrow$ Cloud)에 대해 **암호화 및 상호 인증(Mutual TLS)**을 의무화해야 합니다. 게이트웨이 레벨에서 물리적 접근 통제 및 펌웨어 무결성 검증(Root of Trust)을 적용해야 합니다.

### 3. **시스템 확장성 병목 현상 (데이터 수집/처리 용량)**
- **설명:** 현재는 소규모 환경에서 운영될 수 있으나, 시스템이 점차 커지고 (예: 축사 수 증가, 센서 밀도 증가), 데이터 수집 속도가 기하급수적으로 증가할 경우, 데이터페이지(DB)나 핵심 스트림 프로세서가 처리 용량의 병목(Bottleneck)에 걸려 시스템 지연 시간이 급증할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터베이스는 NoSQL 또는 시계열 데이터베이스(Time-Series DB, 예: InfluxDB)를 메인 저장소로 채택하여 트랜잭션 처리를 최적화해야 합니다. 또한, 스트림 프로세서 계층은 컨테이너 기반의 수평 확장(Horizontal Scaling)이 용이하도록 설계해야 합니다.

### 4. **표준화 및 상호운용성 부재**
- **설명:** 시스템에 사용되는 수많은 주변 기기(센서, 구동기, 액추에이터)가 다양한 제조사 및 독자적인 통신 프로토콜을 사용할 경우, 하나의 표준화된 API나 인터페이스로 통합하기가 어려워 시스템 유지보수 비용이 급증하고, 새로운 기기 추가가 사실상 불가능해집니다. (TTA나 oneM2M 같은 거대 표준화 체계와의 연계 실패)
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **오픈 표준 프로토콜(MQTT, OPC UA, CoAP)만을 사용하도록 인터페이스를 강제 정의**해야 합니다. 특히, 데이터 페이지와 제어 모듈 사이의 모든 인터페이스는 표준화된 메시지 포맷(JSON/Protobuf)과 API Gateway를 통해 통제되어야 합니다.

### 5. **의사결정의 책임 소재 불분명**
- **설명:** 작업추천부(42)가 AI/ML 모델 기반으로 "A라는 행동을 취해야 한다"고 추천했지만, 해당 행동이 환경이나 생물학적 특성을 고려하지 못한 경우, 시스템의 실패 원인을 사용자, 모델 제공자, 또는 시스템 아키텍처 중 어디에 귀속시켜야 할지 모호해져 운영상 혼란과 책임 문제가 발생할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 추천/제어 로직 실행 전, 반드시 '인간의 검토(Human-in-the-Loop)' 과정을 의무화합니다. 모든 제어 명령은 단순 실행이 아니라, **제어 모듈 $\rightarrow$ 운영 대시보드 $\rightarrow$ 최종 승인자(Operator)**를 거치는 승인 플로우(Approval Flow)를 통해 처리해야 합니다.
