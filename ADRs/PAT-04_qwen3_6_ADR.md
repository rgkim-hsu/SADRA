## PAT-04

# 🏗️ 아키텍처 분석 보고서

## ADR (Architecture Decision Record)

### ADR-001: 중앙 집중식 생육 정보 산출 및 양방향 데이터 연동 아키처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 작물의 생육 상태를 분석하기 위해 `이미지 제공모듈(100)`로부터 시각 데이터를 수집하고, `기준정보 데이터베이스(300)`의 농작물 표준 데이터를 참조하여 `생육정보 산출모듈(200)`에서 분석을 수행해야 함. 분석 결과는 `영농정보 데이터베이스(400)`에 저장되고, `사용자단말(400)`을 통해 실시간으로 조회 및 제어되어야 하는 통합 관리 요구사항이 존재함.                                                   |
| **결정(Decision)**       | `생육정보 산출모듈(200)`을 시스템의 허브(Hub)로 설정하고, 이미지 입력, 기준 데이터 참조, 결과 저장, 사용자 인터페이스 제공 등 모든 기능을 중앙에서 orchestration하는 중앙 집중식 아텍처를 채택함. 모든 외부 모듈 및 데이터베이스와의 통신은 양방향(Bidirectional)으로 설계하여 실시간 데이터 교환 및 상태 동기화를 가능하게 함.                                                       |
| **근거(Rationale)**      | 생육 정보 산출은 이미지 분석 알고리즘의 실행뿐만 아니라, 작물별 성장 표준(300)과의 즉각적인 비교, 그리고 분석 결과의 영농 이력(400-DB) 저장이 동시에 요구되는 복합적인 프로세스임. 중앙 집중식 구조는 데이터 흐름의 추적성을 높이고, 산출 로직과 데이터 접근 로직을 단일 모듈 내에서 tightly-coupling하여 처리 지연을 최소화할 수 있음. 또한 사용자 단말과의 양방향 통신을 통해 분석 요청 및 결과 확인을 실시간으로 지원할 수 있음. |
| **결과(Consequences)**   | 시스템의 데이터 일관성과 실시간 응답성이 향상되며, 중앙 모듈을 통해 전체 프로세스를 통합적으로 모니터링 및 제어하기 용이해짐. 반면, `생육정보 산출모듈(200)`에 부하가 집중될 경우 단일 장애점(SPOF)이 될 수 있으며, 이미지 처리와 DB I/O가 동시에 발생할 경우 성능 저하가 발생할 수 있음.                                                                                      |
| **트레이드오프(Trade-offs)** | 데이터 흐름의 단순화 및 실시간 통합 제어 용이성 확보 vs. 중앙 모듈의 확장성 제한 및 과부하 시 전체 시스템 지연 가능성.                                                                                                                                                                                          |

---

## ️ 잠재적 위험 분석

### 1. 중앙 산출 모듈의 과부하 및 병목 현상

- **설명:** `생육정보 산출모듈(200)`이 이미지 처리(Compute-intensive), DB读写(I/O-intensive), 사용자 요청 처리(Network-intensive)를 모두 담당하므로, 고해상도 이미지 다량 입력 시 CPU/메모리 리소스 고갈로 인해 `사용자단말(400)`의 응답이 지연되거나 `영농정보 데이터베이스(400)` 기록이 패할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 이미지 처리 파이프라인과 사용자 요청 처리 스레드 분리, 비동기 메시지 큐(Message Queue) 도입을 통한 작업 큐잉, 산출 모듈의 수평적 확장(Horizontal Scaling) 고려.
  
  ### 2. 데이터베이스 식별자(ID) 중복으로 인한 설계 혼선
- **설명:** 다이어그램 상 `사용자단말`과 `영농정보 데이터베이스`가 모두 `(400)`으로 표기되어 있음. 이는 시스템 설계 문서나 구현 시 참조 무결성 오류, 엔드포인트 충돌, 또는 개발자 간의 의사소통 오류를 유발할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 설계 다이어그램의 ID를 명확히 구분(예: 사용자단말 400, 영농DB 500)하고, 시스템 구현 시 각 컴포넌트에 고유한 식별자(UUID 또는 명확한 Naming Convention)를 부여하여 혼동을 방지.
  
  ### 3. 기준정보 데이터베이스(300) 의존성 장애
- **설명:** `생육정보 산출모듈(200)`이 분석을 위해 `기준정보 데이터베이스(300)`에 실시간으로 의존하는 구조이므로, 기준 DB의 네트워크 단절 또는 성능 저하 시 생육 분석 프로세스 자체가 중단되거나 잘못된 기준을 적용하여 부정확한 결과를 산출할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:**  Medium
- **대응 방안:** 산출 모듈 내부에 기준정보 캐싱(Caching) 메커니즘 도입하여 DB 장애 시에도 최근 기준 데이터로 분석 지속 가능하도록 구현, Circuit Breaker 패턴 적용.
  
  ### 4. 양방향 통신 보안 및 무단 접근 위험
- **설명:** 모든 모듈이 `생육정보 산출모듈(200)`과 양방향으로 통신하므로, 외부에서 `사용자단말(400)`을 통해 악의적인 데이터 주입이나 `기준정보 데이터베이스(300)` 변조 시도 시 시스템 전체의 신뢰성이 훼손될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** 모든 통신 채널에 TLS/SSL 암호화 적용, API Gateway를 통한 인증/인가(Authentication/Authorization) 강제, 입력 데이터 유효성 검증(Input Validation) 로직 강화.
  
  ### 5. 영농정보 데이터베이스(400) 쓰기 병목
- **설명:** `생육정보 산출모듈(200)`에서 분석된 대량의 데이터가 실시간으로 `영농정보 데이터베이스(400)`에 기록되려 할 때, DB의 쓰기 성능 한계로 인해 트랜잭션 대기 시간이 길어지고 결국 산출 모듈의 처리 속도가 저하될 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 영농정보 저장 프로세스를 비동기 배치 처리로 전환, DB 쓰기 최적화(Indexing, Partitioning), 또는 시계열 데이터베이스(TSDB) 도입 검토.
