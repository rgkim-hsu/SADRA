# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### **ADR-001: 중앙 집중형 IoT 플랫폼 아키텍처 채택 및 MQTT 프로토콜 기반 통신 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜/스마트축산 시스템은 다수의 센서 노드(100~120개)와 모바일/웹 클라이언트(200)가 실시간 데이터 수집 및 제어를 요구함. 기존 REST API 방식은 latency와 스케일링 한계로 부적합하며, 보안 및 상호운용성도 표준화되지 않은 상태임. |
| **결정(Decision)** | 1) **중앙 집중형 IoT 플랫폼(400)**을 도입하여 모든 센서 데이터(500)를 집계/처리 <br> 2) **MQTT 프로토콜**을 기반으로 센서-플랫폼 통신 표준화 <br> 3) **API 게이트웨이(600)**를 통해 모바일 앱(200)과의 통신 중계 <br> 4) **ISO/IEC 30141:2024** 준수 아키텍처로 상호운용성 보장 |
| **근거(Rationale)** | - **MQTT**: IoT 환경의 lightweight 통신 요구사항 충족 (IETF 표준, pub/sub 모델) <br> - **중앙 플랫폼**: 데이터 일관성 및 고급 분석(예: 예보 모델 110/120) 지원 가능 <br> - **ISO/IEC 30141**: 글로벌 상호운용성 요구사항 대응 (TTA 표준과 연계) <br> - **API 게이트웨이**: 보안(인증/인가) 및 로드 밸런싱 기능 제공 |
| **결과(Consequences)** | ✅ **장점**: <br> - 실시간 데이터 처리 latency 90% 감소 <br> - 플랫폼 확장성 확보 (수천 노드 지원 가능) <br> - 글로벌 표준 준수로 보안 인증 강화 <br> ❌ **단점**: <br> - 중앙 플랫폼 단일 장애점(SPOF) 위험 <br> - 초기 구축 비용 증가 (하드웨어/소프트웨어) |
| **트레이드오프(Trade-offs)** | - **중앙화 vs 분산화**: 중앙 플랫폼으로 데이터 일관성 확보 vs 에지 컴퓨팅 비용 절감 <br> - **MQTT vs CoAP**: pub/sub 모델의 실시간성 vs CoAP의 REST 통합 용이성 <br> - **표준 준수 vs 커스텀 개발**: 글로벌 상호운용성 vs 빠른 개발 속도 |

### **ADR-002: 데이터 저장 및 처리 아키텍처 (OLTP + OLAP 하이브리드)**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 실시간 센서 데이터(500) 저장과 동시에 고급 분석(예보 모델 110/120)을 요구함. 단일 DB 시스템으로는 성능과 유연성이 부족함. |
| **결정(Decision)** | 1) **OLTP DB(300)**: MySQL/PostgreSQL로 실시간 트랜잭션 처리 <br> 2) **OLAP DB(400 내장)**: TimescaleDB로 시간 시리즈 데이터 분석 <br> 3) **데이터 파이프라인**: Kafka를 통해 OLTP→OLAP 데이터 동기화 |
| **근거(Rationale)** | - **OLTP**: ACID 특성으로 센서 데이터 신뢰성 보장 <br> - **OLAP**: 시간 시리즈 분석 최적화 (예: 온도/습도 패턴 검출) <br> - **Kafka**: 실시간 데이터 스트리밍으로 latency 최소화 |
| **결과(Consequences)** | ✅ **장점**: <br> - 실시간 처리 + 고급 분석 동시 지원 <br> - 데이터 중복 최소화 <br> ❌ **단점**: <br> - 시스템 복잡성 증가 <br> - 데이터 일관성 관리 필요 |
| **트레이드오프(Trade-offs)** | - **단일 DB vs 하이브리드**: 구현 단순성 vs 성능 최적화 <br> - **SQL vs NoSQL**: 트랜잭션 일관성 vs 스케일 아웃 용이성 |

### **ADR-003: 보안 아키텍처 (Zero Trust 모델 적용)**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 시스템은 분산된 센서 노드와 네트워크 공격에 취약함. 기존 방화벽만으로는 불충분함. |
| **결정(Decision)** | 1) **센서 인증**: X.509 인증서 기반 MQTT TLS 1.3 <br> 2) **API 게이트웨이(600)**: JWT 토큰 기반 인증/인가 <br> 3) **네트워크**: VPC 내 통신 제한 (센서→플랫폼→앱) <br> 4) **표준 준수**: ITU-T X.1352 및 ETSI EN 303 645 준수 |
| **근거(Rationale)** | - **TLS 1.3**: 암호화 통신 보장 <br> - **JWT**: 세션 관리 및 권한 세분화 <br> - **VPC**: 네트워크 격리 강화 <br> - **표준 준수**: 글로벌 보안 인증 지원 |
| **결과(Consequences)** | ✅ **장점**: <br> - 엔드투엔드 암호화 통신 <br> - 글로벌 보안 인증 가능 <br> ❌ **단점**: <br> - 인증 처리 latency 증가 <br> - 복잡한 키 관리 요구 |
| **트레이드오프(Trade-offs)** | - **강화된 보안 vs 성능**: 암호화 overhead vs 공격 방어 <br> - **커스텀 보안 vs 표준 준수**: 유연성 vs 글로벌 인증 |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 플랫폼 단일 장애점 (SPOF)**
- **설명**: 플랫폼(400) 장애 시 모든 센서 데이터 수집 및 제어 실패. 특히 스마트팜에서는 실시간 모니터링이 critical함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **주/백업 플랫폼** 구축 (Active-Passive)
  - **에지 컴퓨팅** 도입 (장애 시 지역 데이터 처리)
  - **자동 복구 스크립트** 개발 (Kubernetes 기반 오케스트레이션)

### **2. MQTT 프로토콜의 보안 취약성**
- **설명**: MQTT는 lightweight 특성으로 인해 보안 기능이 제한적. 브로커(400) 공격 시 데이터 유출 위험.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3 강제 적용** + 인증서 회전 정책
  - **MQTT 브로커 격리** (DDoS 공격 방지용 WAF 적용)
  - **정기 보안 패치** 및 취약성 스캐닝 (OWASP ZAP 사용)

### **3. 데이터 일관성 문제 (OLTP/OLAP 동기화 지연)**
- **설명**: Kafka 파이프라인 지연으로 OLAP DB(400) 데이터가 실시간 분석에 사용되지 못할 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Change Data Capture(CDC)** 도구 (Debezium) 적용
  - **동기 복제** 옵션 제공 (성능 저하 감수)
  - **모니터링 대시보드** 구축 (지연 시간 실시간 모니터링)

### **4. 모바일 앱(200) 스케일링 한계**
- **설명**: 사용자 증가 시 API 게이트웨이(600) 과부하로 latency 증가 및 장애 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Horizontal Scaling** 지원 (Kubernetes 기반)
  - **캐시 레이어** 추가 (Redis для 빈번한 쿼리)
  - **지역별 CDN** 배포 (전 세계 사용자 지원)

### **5. 표준 준수 복잡성 및 유지보수 비용**
- **설명**: ISO/IEC 30141 및 ITU-T X.1352 준수를 위해 커스텀 개발이 필요하며, 표준 업데이트 시 재작업 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **표준화된 SDK** 제공 (센서/앱 개발자용)
  - **자동화 테스트** (Conformity Assessment Toolkit 사용)
  - **표준 업데이트 모니터링 팀** 구성 (ETSI/ISO 참여)

### **6. 센서 노드(100~120) 네트워크 latency**
- **설명**: 원격 농장 환경에서 센서-플랫폼 통신 지연으로 실시간 제어 실패 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **에지 컴퓨팅** 도입 (지역 처리 후 중앙 동기화)
  - **LoRaWAN/5G** 혼합 네트워크 지원
  - **QoS 레벨 조정** (MQTT QoS 1 또는 2 사용)

### **7. 사용자 인증/인가 복잡성**
- **설명**: 다수 사용자(사용자 정보 200) 및 역할(관리자/사용자/관리자) 관리가 복잡해질 수 있음.
- **심각도**: 🟢 Low | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **RBAC(Role-Based Access Control)** 구현
  - **SSO 통합** (OAuth 2.0/OIDC)
  - **자동화된 권한 관리 도구** 개발
