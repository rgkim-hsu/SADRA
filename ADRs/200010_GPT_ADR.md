📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 제조/운영 데이터 통합 플랫폼(dataPARC) 기반 통합 데이터 허브 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 시스템은 MES, ERP, LIMS, Data Historian, MDE(수기 입력), 기타 데이터 소스(Excel 등)와 같은 다양한 산업 시스템에서 데이터를 수집해야 한다. 각 시스템은 서로 다른 인터페이스(SQL, API, OPC 등)를 사용하며 데이터가 분산되어 있다. 핵심 과제는 “이질적인 산업 데이터를 통합하여 분석 및 운영 효율을 향상시키는 것”이다. |
| **결정(Decision)**       | dataPARC와 같은 중앙 데이터 통합 플랫폼을 도입하여 다양한 시스템(MES, ERP, LIMS, Historian 등)과 인터페이스(SQL/API/OPC)를 통해 데이터를 수집·통합하는 허브형 아키텍처를 채택한다.                                                                                   |
| **근거(Rationale)**      | 산업 환경에서는 데이터 사일로가 문제이므로 중앙 통합 플랫폼이 필요하다. dataPARC는 다양한 인터페이스를 지원하여 이기종 시스템 간 데이터 통합을 가능하게 하며, 실시간 분석 및 시각화를 지원한다.                                                                                            |
| **결과(Consequences)**   | **긍정적:** 데이터 통합, 운영 가시성 향상, 의사결정 지원, 분석 기반 생산 최적화**부정적:** 초기 구축 비용, 시스템 의존성 증가                                                                                                                               |
| **트레이드오프(Trade-offs)** | 데이터 통합과 분석 역량을 확보하는 대신, 특정 플랫폼 의존성과 구축 비용을 감수해야 한다.                                                                                                                                                          |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 데이터 통합 복잡성

* **설명:** 서로 다른 데이터 포맷 및 인터페이스로 인해 통합 과정 복잡

* **심각도:** 🔴 High

* **발생 가능성:** 🔴 High

* **대응 방안:** 표준 데이터 모델 정의, ETL 프로세스 정립

### 2. 실시간 데이터 지연

* **설명:** 다양한 시스템 연결로 인해 데이터 수집 지연 발생 가능

* **심각도:** 🟡 Medium

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 스트리밍 처리, 캐싱 구조 도입

### 3. 시스템 의존성 (Vendor Lock-in)

* **설명:** 특정 플랫폼(dataPARC)에 대한 의존성 증가

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 표준 인터페이스 활용, 데이터 이식성 확보

### 4. 데이터 품질 문제

* **설명:** 각 소스 시스템의 데이터 품질이 다를 경우 분석 결과 왜곡

* **심각도:** 🔴 High

* **발생 가능성:** 🔴 High

* **대응 방안:** 데이터 검증 및 정제 프로세스 적용

### 5. 보안 및 접근 제어

* **설명:** 다양한 시스템 데이터 통합으로 보안 취약점 증가

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 권한 관리, 암호화, 접근 제어 정책 적용

### 6. 인터페이스 장애

* **설명:** OPC, API, SQL 연결 오류 시 데이터 수집 중단

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 인터페이스 모니터링, 장애 대응 자동화

### 7. 확장성 및 성능 문제

* **설명:** 데이터 증가 시 플랫폼 성능 저하 가능

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 분산 아키텍처, 스케일 아웃 구조 적용
