📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 모듈형 이중 계층 지수 산출 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                            |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서 작물 생육에 영향을 미치는 온습도 등 환경 변수는 표준화된 기본 지수(디폴트)만으로는 농장별 특수 조건(토양 종류, 작물 품종, 지역 기후 편차 등)을 반영하기 어렵다. 환경 정보 입력부(110)로부터 수집된 데이터를 단일 연산 경로로만 처리할 경우, 확장성과 유연성이 심각하게 제한된다.                   |
| **결정(Decision)**       | 제어부(130)를 중심으로 디폴트 모듈(150)과 확장 모듈(160)을 병렬로 운용하는 이중 계층 구조를 채택한다. 디폴트 모듈은 일별 온습도지수 계산부(152)와 온습도 영향도 데이터베이스(154)로 표준 연산을 담당하고, 확장 모듈은 일별 추가영향 지수 계산부(162)와 추가 영향도 데이터베이스(164)로 농장 특화 변수를 처리한다. |
| **근거(Rationale)**      | 환경 정보 데이터베이스부(120)에서 수집·저장된 데이터를 제어부(130)가 중앙 조율하여 두 모듈에 선택적으로 분배함으로써, 표준 산출 로직의 안정성을 유지하면서도 추가 환경 변수를 독립적으로 확장할 수 있다. 출력부(140)는 두 모듈의 결과를 통합하여 최종 의사결정 정보를 제공한다.                             |
| **결과(Consequences)**   | 긍정적: 기본 온습도 지수 연산의 안정성 보장, 농장별 커스터마이징 가능, 모듈 단위 독립 업데이트 가능. 부정적: 두 모듈 간 연산 결과 정합성 관리 필요, 제어부(130)에 대한 단일 장애점(SPOF) 위험 증가.                                                                     |
| **트레이드오프(Trade-offs)** | 얻는 장점: 확장 모듈 추가 시 디폴트 로직 무중단 유지, 농업 환경 다양성 대응력 향상. 감수할 단점: 제어부의 복잡도 증가로 인한 유지보수 부담 상승, 두 DB 간 데이터 동기화 오버헤드 발생 가능.                                                                             |

### ADR-002: 환경 정보 데이터베이스부의 중앙 집중식 데이터 허브 역할 부여

| 항목                     | 내용                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜에서는 온도, 습도, CO₂, 광량 등 다양한 센서 데이터가 실시간으로 생성된다. 환경 정보 입력부(110)가 이를 수집하지만, 각 모듈이 개별적으로 원시 데이터에 직접 접근하면 데이터 일관성 훼손 및 중복 수집 문제가 발생한다. |
| **결정(Decision)**       | 환경 정보 데이터베이스부(120)를 단순 저장소가 아닌 데이터 정규화·버전 관리·이력 보관의 중앙 허브로 설계하고, 제어부(130)만이 이 DB에 접근하여 각 모듈에 정제된 데이터를 공급하는 단방향 흐름을 강제한다.             |
| **근거(Rationale)**      | 데이터 거버넌스 일원화를 통해 디폴트 모듈(150)과 확장 모듈(160)이 항상 동일한 기준 데이터를 기반으로 지수를 산출하게 되어, 두 모듈 간 연산 결과의 비교 및 통합 신뢰성이 보장된다.                          |
| **결과(Consequences)**   | 긍정적: 데이터 일관성 확보, 이력 추적 및 재연산 가능, 감사(audit) 용이. 부정적: DB 부하 집중, DB 장애 시 전체 시스템 마비 위험.                                                  |
| **트레이드오프(Trade-offs)** | 얻는 장점: 단일 진실 공급원(Single Source of Truth) 확보. 감수할 단점: DB 가용성이 전체 시스템 가용성과 직결되어 이중화 구성 필수.                                             |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 제어부(130) 단일 장애점(Single Point of Failure)

* **설명:** 제어부(130)는 환경 정보 DB(120), 디폴트 모듈(150), 확장 모듈(160), 출력부(140) 등 모든 컴포넌트의 중앙 조율자 역할을 수행한다. 제어부에 소프트웨어 버그, 메모리 누수, 하드웨어 장애가 발생할 경우 온습도 지수 산출이 전면 중단되어 스마트팜의 자동 환경 제어 기능 전체가 마비된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Standby 이중화 구성(HA) 적용, 헬스체크 기반 자동 페일오버 구현, 제어부 프로세스 독립 컨테이너(Docker/K8s) 배포로 빠른 재시작 보장, Circuit Breaker 패턴 적용.

* * *

### 2. 디폴트 모듈과 확장 모듈 간 지수 불일치(Data Inconsistency)

* **설명:** 일별 온습도지수 계산부(152)와 일별 추가영향 지수 계산부(162)가 각각 다른 DB(154, 164)를 참조하여 산출한 결과를 출력부(140)에서 통합할 때, 기준 시점·단위·가중치 불일치로 인해 최종 출력값이 실제 농장 환경과 괴리된 오류 데이터를 생성할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 두 모듈의 계산 기준 시점(타임스탬프) 동기화 프로토콜 강제 적용, 출력부에 결과 유효성 검증 로직(Range Check, Cross-Validation) 추가, 정기적인 두 DB 간 스키마 정합성 검사 자동화.

* * *

### 3. 환경 정보 데이터베이스부(120) 데이터 적재 지연 및 누락

* **설명:** 스마트팜 현장의 네트워크 불안정(IoT 센서 통신 끊김, Wi-Fi 간섭 등)으로 환경 정보 입력부(110)에서 DB(120)로의 데이터 전송이 지연되거나 누락될 경우, 제어부(130)가 오래된 데이터 또는 결측값을 기반으로 지수를 산출하여 잘못된 환경 제어 명령이 출력부(140)를 통해 실행된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 입력부(110)에 로컬 버퍼링 및 재전송 큐(Queue) 구현, DB 적재 시 타임스탬프 기반 데이터 신선도(Freshness) 검증 로직 추가, 결측값 발생 시 마지막 유효값 또는 보간(Interpolation) 처리 정책 수립, 알림 임계값 설정으로 운영자에게 즉시 경보 발송.

* * *

### 4. 온습도 영향도 DB(154) 및 추가 영향도 DB(164) 모델 노후화(Model Drift)

* **설명:** 두 데이터베이스에 저장된 온습도 영향도 파라미터와 추가 영향도 기준값은 초기 구축 시점의 실험·통계 데이터를 기반으로 한다. 기후변화, 작물 품종 변화, 재배 방식 변경 등으로 시간이 지남에 따라 저장된 모델 파라미터가 현실과 괴리되는 모델 드리프트(Model Drift)가 발생하여 지수 산출 정확도가 점진적으로 저하된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 실제 수확량·생육 데이터와 예측 지수 간 정기적 상관관계 분석 파이프라인 구축, DB 파라미터 버전 관리 및 롤백 기능 구현, 연 1회 이상 현장 실증 데이터 기반 모델 재보정(Recalibration) 프로세스 의무화.

* * *

### 5. 출력부(140)를 통한 비인가 제어 명령 실행(보안 위협)

* **설명:** 출력부(140)는 산출된 지수를 기반으로 관개 펌프, 환풍기, 난방기 등 물리적 액추에이터에 제어 명령을 전달한다. 제어부(130) 또는 네트워크 구간에 대한 외부 침입(Injection Attack, Man-in-the-Middle) 또는 내부자 위협으로 비인가 명령이 출력부를 통해 실행될 경우, 작물 고사, 설비 과부하, 화재 등 실물 피해로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 출력부 명령 실행 전 제어부 디지털 서명 검증(Command Signing) 적용, 물리적 액추에이터 연동 구간에 OT/IT 분리 네트워크(DMZ) 구성, 비정상 명령값(범위 초과) 자동 차단 하드웨어 인터록(Interlock) 설치, 제어 명령 전체 감사 로그(Audit Log) 기록 및 이상 탐지(SIEM) 연계.

* * *

### 6. 확장 모듈(160) 신규 지수 추가 시 디폴트 모듈(150) 연산 성능 저하

* **설명:** 농장 운영 고도화에 따라 확장 모듈(160)에 CO₂ 농도, 토양 EC, 일조량 등 추가 환경 지수가 누적 등록될수록, 제어부(130)가 동기적으로 두 모듈의 결과를 취합하는 과정에서 처리 지연이 발생한다. 이로 인해 실시간성이 요구되는 온습도 기반 디폴트 지수 산출까지 지연되어 환경 제어 골든 타임을 놓칠 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 디폴트 모듈과 확장 모듈의 연산 파이프라인을 비동기(Async) 처리로 분리하여 디폴트 지수는 즉시 출력부에 반영, 확장 지수는 보조 채널로 후속 반영하는 2-Phase Output 설계 적용. 확장 모듈 지수 추가 시 성능 기준선(Baseline) 테스트 의무화.
