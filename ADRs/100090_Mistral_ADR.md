📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **마이크로서비스 기반 통합 관리 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 실시간 환경 모니터링, 수확 예측, 시뮬레이션, 생산 관리 등 다양한 기능이 필요하며, 각 기능은 독립적으로 확장 가능하고 유지보수 용이해야 함. 기존 모노리식 아키텍처는 기능 추가/수정 시 시스템 전체에 영향을 미치며, 데이터 흐름의 복잡성으로 인해 유지보수가 어려움.                                                           |
| **결정(Decision)**       | **마이크로서비스 아키텍처**를 채택하여 각 기능(서버통신부, 시뮬레이션서비스부, 통계분석부, 생산관리부, 쇼핑몰관리부)을 독립적인 서비스로 분리하고, **통합관리서버**를 통해 중앙 집중식 관리. 각 서비스는 자체 DB(예: 위탁소지자 DB, 양봉가 DB, 환경정보 DB 등)를 가지며, RESTful API 또는 메시지 큐를 통해 통신.                              |
| **근거(Rationale)**      | 1. **모듈성**: 각 서비스(701~710)는 독립적으로 개발, 배포, 확장 가능. 2. **유연성**: 특정 서비스(예: 양봉예측부)만 업데이트해도 시스템 전체에 영향 없음. 3. **장애 격리**: 한 서비스 장애가 전체 시스템에 영향을 미치지 않음. 4. **기술 스택 최적화**: 각 서비스에 적합한 DB(예: 시계열 데이터는 Time Series DB 사용) 및 기술 선택 가능. |
| **결과(Consequences)**   | **장점**: 개발 속도 향상, 장애 복구 시간 단축, 독립적 스케일링 가능. **부정적 결과**: 분산 시스템의 복잡성 증가(트랜잭션 관리, 데이터 일관성), 네트워크 오버헤드, 모니터링 및 로깅 복잡성.                                                                                                         |
| **트레이드오프(Trade-offs)** | **获得**: 유연성, 확장성, 장애 격리. **희생**: 아키텍처 복잡성, 운영 오버헤드(예: Kubernetes 같은 오케스트레이션 도구 필요), 데이터 일관성 관리 어려움.                                                                                                                         |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. **분산 시스템에서의 데이터 일관성 문제**

* **설명:** 마이크로서비스 간 데이터 동기화 지연으로 인해 실시간 환경 데이터(예: 온도, 습도)와 시뮬레이션 결과(707, 708) 간 불일치가 발생할 수 있음. 예: 양봉예측부(703)에서 사용되는 환경 데이터가 최신 상태가 아닐 경우, 예측 정확도 저하.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **이벤트 소싱(Event Sourcing)** 및 **CQRS 패턴** 도입. 실시간 데이터는 Kafka 같은 메시지 큐를 통해 스트리밍하고, eventual consistency 모델 적용. 중요 데이터는 2PC(2-phase commit) 또는 Saga 패턴으로 트랜잭션 관리.

* * *

### 2. **실시간 모니터링 시스템의 지연 및 장애**

* **설명:** 모니터링부(704)에서 수집된 센서 데이터(705: 이상감지부, 706: 원격제어부)가 통합관리서버로 전송되는 과정에서 네트워크 지연 또는 장애 발생 시, 환경 제어(예: 온도 조절) 지연으로 작물 손실 발생 가능.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **에지 컴퓨팅** 도입. 센서 노드에 로컬 처리 로직 구현하여 실시간 제어(예: 온도 조절)은 로컬에서 수행하고, 데이터는 주기적으로 서버로 동기화. 또한, **Redundant 네트워크 경로** 및 **UPS(무정전 전원 공급 장치)** 설치.

* * *

### 3. **시뮬레이션 및 예측 모델의 정확도 저하**

* **설명:** 시뮬레이션서비스부(707, 708)에서 사용되는 모델(예: 환경 시뮬레이션, 통계 분석)이 실제 데이터와 차이가 나는 경우, 생산관리부(709)에서 내리는 결정(예: 수확 시기, 자원 배분)의 오류로 이어질 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **MLOps 파이프라인** 구축. 모델은 정기적으로 실제 데이터로 재학습하고, **A/B 테스팅**을 통해 새로운 모델과 기존 모델의 성능을 비교. 또한, **feature store**를 통해 데이터 품질 관리.

* * *

### 4. **보안 취약점: API 및 DB 접근 제어**

* **설명:** 각 마이크로서비스(701~710)가 독립적인 API를 노출하고, DB(예: 위탁소지자 DB, 양봉가 DB)에 직접 접근할 경우, 인증/권한 관리 미비로 인한 데이터 유출 또는 조작 위험(예: 쇼핑몰관리부(710)에서 주문 정보 조작).
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** **Zero Trust 아키텍처** 적용. 모든 API 호출에 **JWT 토큰** 및 **OAuth 2.0** 기반 인증, **RBAC(Role-Based Access Control)**으로 권한 관리. DB는 **암호화(At-Rest, In-Transit)** 및 **VPC 내 частный 네트워크**에서만 접근 가능하도록 설정.

* * *

### 5. **시스템 확장 시 인프라 비용 급증**

* **설명:** 스마트팜 사용자가 증가하거나, 데이터 수집 주기가 짧아질 경우(예: 센서 데이터 1초 단위 수집), 클라우드 인프라 비용(예: 서버, DB, 네트워크)이 비선형적으로 증가할 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟢 Low
* **대응 방안:** **오토스케일링(Auto-Scaling)** 및 **서버리스 아키텍처** 도입. 예: AWS Lambda를 사용한 이벤트 기반 처리, **Cold Storage**를 활용한 과거 데이터 아카이빙. 또한, **비용 모니터링 도구**를 통해 리소스 사용량 추적 및 최적화.
