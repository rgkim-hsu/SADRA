# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 비동기 상태 관리 및 이벤트를 통한 프로세스 워크플로우 구현

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 초기 상태(NEW)부터 대기(WAITING)를 거쳐 실행(WORKING)하는 복잡한 라이프사이클을 가집니다. 특히, 시스템의 종료 또는 중단(STOPPING/FINISHED)가 단일한 경로가 아닌, 외부 센서 입력(A-SENSOR), 제어 명령(A-CONTROL), 또는 자동 시스템(AUTO/COMMAND) 등 다양한 이벤트를 통해 비동기적으로 발생합니다. 기존의 동기적, 순차적 아키텍처로는 이러한 다중 경로의 상태 전이(State Transition)와 최종 결과(IGNORED, STOPPING, FINISHED)의 신뢰성을 보장하기 어렵습니다. |
| **결정(Decision)** | 시스템의 상태 전이와 비즈니스 로직 실행을 **이벤트 기반 아키텍처(Event-Driven Architecture, EDA)**로 설계하고, 상태 저장소로 **이벤트 소싱(Event Sourcing)** 패턴을 채택하여 시스템의 상태 변화를 불변의 이벤트 시퀀스(Sequence of Immutable Events)로 기록합니다. 프로세스 워크플로우 관리에는 **사가 패턴(Saga Pattern)**을 적용하여 분산 트랜잭션의 일관성을 보장합니다. |
| **근거(Rationale)** | 1. **신뢰성 및 감사 추적(Auditability):** 이벤트 소싱은 모든 상태 변화를 시간 순서대로 기록하므로, 어떤 외부 트리거(센서, 명령)가 어떤 상태를 변경했는지 완벽하게 추적할 수 있습니다 (디버깅 및 규제 준수 측면에서 필수). 2. **느슨한 결합(Loose Coupling):** 각 상태 전이 로직을 독립적인 이벤트 리스너(Consumer)로 분리하여, 새로운 종류의 트리거(예: 새로운 센서)가 추가되어도 시스템 핵심 로직을 변경하지 않고 확장할 수 있습니다. 3. **비동기 처리:** IoT 환경은 네트워크 지연이나 센서의 불규칙한 데이터 전송이 흔하므로, 메시지 브로커를 통한 비동기 처리가 필수적입니다. |
| **결과(Consequences)** | **긍정적:** 시스템의 확장성, 내결함성, 추적 가능성이 극대화됩니다. 다양한 외부 요인에 대한 로직 분리가 용이합니다. **부정적:** 초기 구현 복잡도가 높고, 트랜잭션의 완전한 검증(CQRS 패턴 도입 필요)을 위해 복잡한 데이터 모델링과 관리가 요구됩니다. |
| **트레이드오프(Trade-offs)** | **[얻는 장점]:** 극도의 높은 가용성(High Availability)과 비즈니스 로직의 명확한 격리(Isolation). 전역 상태 관리의 어려움을 이벤트 로그를 통한 재구축(Reconstruction)으로 해결합니다. **[감수해야 할 단점]:** 구현 복잡성 증대 및 오케스트레이션(Orchestration) 관점의 트랜잭션 관리 어려움 (Saga 패턴 적용 필요). |

## ⚠️ 잠재적 위험 분석

### 1. 이벤트 중복 처리 및 상태 불일치 (Idempotency Failure)
- **설명:** 메시지 브로커(예: Kafka)의 At-Least-Once Delivery 특성상, 동일한 이벤트가 네트워크 오류나 리트라이 메커니즘 때문에 두 번 이상 처리될 수 있습니다. WORKING 상태의 로직이 동일한 이벤트를 두 번 처리할 경우, 실제 시스템 상태가 이중으로 변경되거나 아키텍처의 상태 모델이 불일치할 위험이 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 비즈니스 로직 엔드포인트는 반드시 **멱등성(Idempotency)**을 보장하도록 설계되어야 합니다. 이벤트 메시지에 고유한 트랜잭션 ID(Transaction ID)를 포함시키고, 이 ID를 기반으로 이미 처리된 이벤트인지 확인하는 메커니즘을 도입해야 합니다.

### 2. 실시간 보안 및 권한 상승 공격 (Insecure Communication & Command Injection)
- **설명:** 시스템이 여러 종류의 외부 트랜지션(A-SENSOR, A-CONTROL, COMMAND)에 의존하고 있으므로, 이들 입력 채널 중 하나가 해킹되거나 위변조된 데이터(예: 비정상적인 센서 데이터 또는 권한이 없는 명령)가 주입될 경우, 시스템 전체가 오작동하거나 제어권을 빼앗길 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** **Defense in Depth** 전략을 적용합니다. 모든 외부 입력(센서, API, 명령)은 경계 서비스(Gateway)에서 **인증(Authentication)** 및 **인가(Authorization)** 과정을 거쳐야 합니다. 또한, 입력 데이터의 범위를 벗어나는 비정상 데이터를 탐지하는 **데이터 유효성 검사(Data Validation)** 레이어를 필수로 추가해야 합니다.

### 3. 상태 전이 지연 및 병목 현상 (State Transition Deadlock/Latency)
- **설명:** WORKING 상태에서 너무 많은 종류의 외부 이벤트(A-SENSOR, A-CONTROL, COMMAND)가 동시에 발생하거나, 이벤트 처리 로직 자체의 복잡도가 높아질 경우, 시스템의 상태 전이가 지연되거나 특정 상태에서 장기적으로 멈추는(Deadlock) 병목 현상이 발생할 수 있습니다. 이는 실시간성이 중요한 IoT 제어 시스템에서 치명적입니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 핵심 제어 로직은 최대한 가볍고 빠르게 동작하도록 최적화해야 하며, 복잡한 계산이나 외부 시스템 호출은 별도의 비동기 Worker Queue로 분리합니다. 또한, 모든 상태 전이 과정에 **Timeout 메커니즘**을 강제하고, 타임아웃 시 대체 경로(Fallback State)를 지정해야 합니다.

### 4. 표준화 및 상호운용성 실패 (Interoperability Failure)
- **설명:** 시스템이 다양한 종류의 센서(A-SENSOR) 및 외부 장치와 연동되어야 하므로, 장비 제조사별 통신 프로토콜, 데이터 형식, API 규격이 다를 경우, 통합 계층(Adaptation Layer)에서 데이터 매핑 실패가 발생하여 시스템이 데이터를 무시(IGNORED) 처리하게 될 위험이 있습니다. (문서 컨텍스트에서 강조된 상호운용성 문제입니다.)
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **표준화 프레임워크(예: ISO/IEC 30141, OCF)** 준수를 최우선 목표로 삼고, 물리적 장치와 제어 시스템 사이에 추상화 계층(Abstraction Layer)을 필수로 도입합니다. 이 계층은 모든 게이트웨이 장치에서 공통의 Canonical Data Model을 사용하도록 강제해야 합니다.

### 5. 장애 상황의 모니터링 사각지대 (Lack of Observability in Event Flow)
- **설명:** EDA는 이벤트가 다양한 서비스(Consumer)를 거쳐 비동기적으로 처리되므로, 어떤 이벤트를 보냈고, 어느 서비스에서 처리되었으며, 어떤 로직에서 실패했는지 한눈에 파악하기 어렵습니다. 이는 시스템 장애 발생 시 원인 분석(Root Cause Analysis)을 지연시키거나 불가능하게 만들 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **분산 추적(Distributed Tracing)** 시스템(예: Jaeger, Zipkin)과 중앙 집중식 로깅 및 메트릭 수집 시스템(ELK Stack 또는 Prometheus/Grafana)을 구축합니다. 모든 이벤트 메시지와 트랜잭션은 고유의 Correlation ID를 공유하여, 장애 발생 시 처음부터 끝까지의 전파 경로를 시각적으로 재구성할 수 있어야 합니다.
