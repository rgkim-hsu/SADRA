## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈별 기능 분할 및 데이터 흐름 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 스마트팜/축산 환경 모니터링, 제어, 결과 관리 기능을 통합하여 운영해야 하며, 각 모듈 간의 데이터 흐름과 인터페이스 표준화가 필수적이다. 특히 IoT 장비와 애플리케이션 간의 상호운용성 및 실시간 데이터 처리 요구가 높다. |
| **결정(Decision)** | 1) **모듈별 기능 분할**: 모니터링(21-25), 제어(41-44), 결과관리(51-52) 모듈로 세분화하여 각 모듈의 책임을 명확히 정의한다.<br>2) **데이터 표준화**: 모든 모듈은 DB를 통해 데이터페이스를 공유하며, 데이터 포맷과 프로토콜(예: MQTT, CoAP)을 표준화한다.<br>3) **모니터링 모듈**: 환경정보 수집(21), 객체식 분류(22), 병충해 판단(23), 음영 분석(24), 객체 매칭(25)을 처리한다.<br>4) **제어 모듈**: 스케줄 관리(41), 작업 추천(42), 작업 점수부(43), 작업 관리(44)를 처리한다. |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준에 따라 모듈별 기능 분할 및 데이터 표준화가 필수적이다.<br>- **oneM2M** 및 **ETSI EN 303 645** 표준에 따라 IoT 장비와 애플리케이션 간의 상호운용성을 보장하기 위해 데이터 포맷과 프로토콜을 표준화한다.<br>- **TTA 단체표준**에 따라 스마트팜/축산 시스템의 모니터링 및 제어 기능이 모듈화되어야 한다. |
| **결과(Consequences)** | - **장점**: 모듈별 기능 분할로 유지보수 및 확장성이 향상된다.<br>- **단점**: 모듈 간 데이터 표준화로 초기 개발 비용이 증가할 수 있다.<br>- **장점**: 표준화된 데이터 흐름으로 시스템 신뢰성이 향상된다. |
| **트레이드오프(Trade-offs)** | - **유연성 vs. 표준화**: 모듈별 표준화로 유연성이 slightly 감소할 수 있으나, 장기적으로 시스템 안정성이 향상된다.<br>- **초기 비용 vs. 유지보수 비용**: 초기 개발 비용이 증가하지만, 유지보수 및 확장 비용이 크게 감소한다. |

### **ADR-002: 실시간 데이터 처리 및 저장소 구조**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 실시간으로 모니터링 데이터를 수집하고 처리해야 하며, 대용량 데이터의 저장 및 분석이 요구된다. 또한, 데이터의 일관성과 접근 속도가 중요하다. |
| **결정(Decision)** | 1) **데이터베이스 구조**: 관계형 DB(예: PostgreSQL)와 NoSQL DB(예: MongoDB)를 혼합하여 사용한다.<br>2) **실시간 처리**: 모니터링 모듈(21-25)에서 수집된 데이터는 데이터페이스를 통해 실시간으로 처리되며, 제어 모듈(41-44)은 이를 기반으로 스케줄 및 작업 관리를 수행한다.<br>3) **결과 관리 모듈**: 저장부(51)와 강신부(52)는 분석 결과와 로그 데이터를 관리한다. |
| **근거(Rationale)** | - **ISO/IEC 27030:2020** 표준에 따라 데이터의 안전한 저장 및 처리 방식을 적용한다.<br>- **IEEE 2413** 표준에 따라 실시간 데이터 처리 및 저장소 구조를 설계한다.<br>- **TTA 단체표준**에 따라 스마트팜/축산 시스템의 데이터 관리 요구사항을 충족한다. |
| **결과(Consequences)** | - **장점**: 관계형 DB로 데이터 일관성을 보장하고, NoSQL DB로 실시간 처리 성능을 향상시킨다.<br>- **단점**: 혼합 DB 구조로 복잡성이 slightly 증가할 수 있다.<br>- **장점**: 실시간 데이터 처리로 시스템 반응성이 향상된다. |
| **트레이드오프(Trade-offs)** | - **성능 vs. 복잡성**: 혼합 DB 구조로 성능이 향상되지만, 시스템 복잡성이 slightly 증가한다.<br>- **데이터 일관성 vs. 처리 속도**: 관계형 DB로 일관성을 보장하고, NoSQL DB로 처리 속도를 최적화한다. |

### **ADR-003: 보안 및 접근 제어**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 IoT 장비 및 데이터의 보안을 강화해야 하며, 권한별 접근 제어가 필수적이다. 특히, ITU-T X.1352 및 ETSI EN 303 645 표준에 따라 보안 요구사항을 충족해야 한다. |
| **결정(Decision)** | 1) **데이터 암호화**: 모든 모듈 간 통신 및 데이터 저장 시 AES-256 암호화를 적용한다.<br>2) **접근 제어**: RBAC(Role-Based Access Control) 방식을 적용하여 사용자 권한을 관리한다.<br>3) **보안 모니터링**: 데이터페이스 및 DB에 보안 로그를 기록하고, 이상 행위를 실시간으로 감지한다. |
| **근거(Rationale)** | - **ITU-T X.1352** 표준에 따라 IoT 장비 및 데이터의 보안을 강화한다.<br>- **ETSI EN 303 645** 표준에 따라 사이버보안 요구사항을 충족한다.<br>- **KISA 보안 기준**에 따라 시스템의 보안성을 강화한다. |
| **결과(Consequences)** | - **장점**: 데이터 암호화 및 접근 제어로 시스템 보안성이 크게 향상된다.<br>- **단점**: 암호화 및 접근 제어로 시스템 처리 속도가 slightly 감소할 수 있다.<br>- **장점**: 보안 모니터링으로 이상 행위를 실시간으로 감지할 수 있다. |
| **트레이드오프(Trade-offs)** | - **보안성 vs. 성능**: 암호화 및 접근 제어로 보안성이 향상되지만, 처리 속도가 slightly 감소한다.<br>- **복잡성 vs. 보안성**: 보안 모듈 추가로 시스템 복잡성이 증가하지만, 보안성이 크게 향상된다. |

## ⚠️ 잠재적 위험 분석

### **1. 데이터 일관성 문제**
- **설명**: 모듈 간 데이터 표준화 부족으로 인해 데이터 일관성 문제가 발생할 수 있다. 예를 들어, 모니터링 모듈과 제어 모듈 간 데이터 포맷 불일치로 시스템 오류가 발생할 수 있다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - 데이터 표준화 프로토콜(예: MQTT, CoAP)을 강제 적용한다.
  - 데이터베이스 스키마를 정기적으로 검증하고, 자동화된 데이터 검증 도구를 도입한다.
  - 모듈 간 데이터 인터페이스 테스트를 강화한다.

---

### **2. 실시간 처리 지연**
- **설명**: 대용량 데이터 처리 시 실시간 처리 지연이 발생하여 시스템 반응성이 저하될 수 있다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - NoSQL DB를 사용하여 실시간 데이터 처리 성능을 최적화한다.
  - 데이터 캐싱 메커니즘을 도입하여 처리 속도를 향상시킨다.
  - 로드 테스트를 통해 시스템 성능을 모니터링하고, 필요한 경우 하드웨어를 업그레이드한다.

---

### **3. 보안 취약점**
- **설명**: 암호화 및 접근 제어 구현 부족으로 인해 시스템이 사이버 공격에 취약할 수 있다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - 정기적인 보안 감사 및 취약점 스캔을 수행한다.
  - KISA 및 ITU-T X.1352 표준에 따라 보안 정책을 업데이트한다.
  - 보안 모니터링 시스템을 강화하여 이상 행위를 실시간으로 감지한다.

---

### **4. 모듈 간 결합도 증가**
- **설명**: 모듈 간 데이터 표준화 및 통합으로 인해 결합도가 증가하여 시스템 유연성이 저하될 수 있다.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - 모듈 간 인터페이스를 API 게이트웨이를 통해 추상화한다.
  - 마이크로서비스 아키텍처를 도입하여 모듈 간 결합도를 최소화한다.
  - 정기적인 아키텍처 리뷰를 통해 결합도를 모니터링한다.

---

### **5. 유지보수 및 확장성 문제**
- **설명**: 시스템이 확장되거나 유지보수가 필요한 경우, 모듈 간 의존성으로 인해 복잡성이 증가하여 유지보수 및 확장성이 저하될 수 있다.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟢 Low
- **대응 방안**:
  - 모듈별 문서화 및 코드 리뷰 프로세스를 강화한다.
  - CI/CD 파이프라인을 도입하여 자동화된 테스트 및 배포를 지원한다.
  - 시스템 아키텍처를 모니터링하고, 필요한 경우 리팩토링을 수행한다.
