📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 실시간 스마트팜 설비 통합 제어 및 모니터링 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 시스템은 스마트팜 환경에서 다양한 설비(센서, 액추에이터)의 데이터를 실시간으로 수집하고, 이를 기반으로 제어 및 모니터링을 수행해야 한다. 이미지 상의 제어부(120)는 실시간 설비 제어(120a), 노이즈 분석(120d), 원격 통신 제어(120e), 데이터 분석/표시(120b), 알람 관리(120c), 리포트(120f) 등 복합 기능을 수행하며, 외부 입출력부(110), 제어용 I/O IF(130), 송수신부(140), DB(150), 음성 출력(160)과 연동된다. 주요 과제는 실시간성, 신뢰성, 확장성, 데이터 일관성을 동시에 확보하는 것이다. |
| **결정(Decision)**       | 중앙 집중형 제어부(120)를 중심으로 모듈화된 마이크로서비스형 논리 구조를 채택하되, 물리적으로는 엣지 컴퓨팅 기반 분산 처리 구조를 적용한다. 실시간 제어 모듈(120a)과 노이즈 분석 모듈(120d)은 엣지에서 처리하고, 데이터 저장 및 리포팅(150, 120f)은 중앙 또는 클라우드에서 처리하는 하이브리드 아키텍처를 구성한다.                                                                                                                              |
| **근거(Rationale)**      | 스마트팜은 네트워크 지연이나 장애 상황에서도 안정적으로 동작해야 하므로, 실시간 제어 기능을 엣지에 배치하는 것이 필수적이다. 동시에 데이터 분석, 리포팅, 장기 저장은 확장성과 비용 효율성을 위해 중앙화가 유리하다. 모듈화 구조는 기능 확장 및 유지보수성을 높인다.                                                                                                                                                                    |
| **결과(Consequences)**   | 실시간 제어 안정성과 확장성을 동시에 확보할 수 있으며, 기능별 독립적 확장이 가능해진다. 그러나 시스템 복잡도가 증가하고, 엣지-중앙 간 데이터 동기화 문제가 발생할 수 있다.                                                                                                                                                                                                                      |
| **트레이드오프(Trade-offs)** | 저지연 제어 성능 확보(장점) vs 아키텍처 복잡성 증가(단점), 데이터 일관성 관리 비용 증가(단점) vs 시스템 확장성 및 유연성 확보(장점)                                                                                                                                                                                                                                        |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 실시간 제어 지연 위험

* **설명:** 네트워크 장애 또는 송수신부(140) 지연으로 인해 제어 명령이 설비에 늦게 전달되는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 엣지 기반 로컬 제어 로직 강화, 네트워크 장애 시 fallback 제어 정책 적용

### 2. 데이터 불일치 및 동기화 문제

* **설명:** 엣지(제어부)와 중앙 DB(150) 간 데이터 동기화 실패로 인해 분석 결과와 실제 상태 불일치 발생

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 이벤트 기반 데이터 동기화(예: 메시지 큐), eventual consistency 모델 적용, 충돌 해결 정책 정의

### 3. 노이즈 분석 오류로 인한 오제어

* **설명:** 노이즈 모니터링 분석 모듈(120d)이 잘못된 데이터를 정상으로 판단하거나 반대로 오탐지하는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** AI/ML 기반 이상 탐지 모델 고도화, 다중 센서 검증, 임계값 동적 조정

### 4. 보안 취약점 (원격 제어 공격)

* **설명:** 원격 통신 제어 모듈(120e)을 통해 외부에서 악의적인 제어 명령이 유입되는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** TLS 기반 통신 암호화, 인증/인가 체계 강화(OAuth, PKI), 제어 명령 화이트리스트 적용

### 5. 시스템 단일 장애점(SPOF)

* **설명:** 중앙 제어부(120) 또는 DB(150) 장애 시 전체 시스템 기능 중단

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 이중화(HA) 구성, 클러스터링, 장애 자동 복구(Failover) 시스템 구축

### 6. 알람 과다 발생으로 인한 운영 피로도 증가

* **설명:** 알람 표시 및 기록 모듈(120c)에서 불필요한 알람이 과다 발생하여 운영자가 중요한 이벤트를 놓치는 경우

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 알람 필터링 및 우선순위 정책 적용, 사용자 맞춤 알람 설정, AI 기반 이벤트 중요도 분류
