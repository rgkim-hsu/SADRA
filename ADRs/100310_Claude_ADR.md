### ADR-001: 스마트팜 클라우드-엣지 하이브리드 제어 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 재배 환경(100)에는 다수의 식물 재배 구획과 LED 조명(110, 120)이 설치되어 있으며, 양액 공급 장치(400)와 제어기(600), 전원 공급기(500)가 연동된다. 사용자(200, 모바일)는 원격에서 재배 관리를 수행하고, 서버(300)는 서대 양액 정보 및 적물 관련 정보를 수집·처리한다. 실시간 제어와 원격 모니터링이 동시에 요구되며, 네트워크 단절 시에도 현장 제어가 유지되어야 한다. |
| **결정(Decision)**       | 제어기(600)를 엣지 노드로 위치시켜 로컬 자율 제어(조명 ON/OFF, 양액 펌프 제어)를 담당하게 하고, 서버(300)를 중앙 클라우드/온프레미스 브레인으로 구성하여 데이터 수집·분석·양액 처방을 수행한다. 사용자 앱(200)은 서버(300)를 통해 간접 제어하는 3-tier 하이브리드 구조를 채택한다.                                                      |
| **근거(Rationale)**      | 농업 환경은 네트워크 불안정성이 높아 클라우드 단독 제어는 단일 장애점(SPOF)이 된다. 제어기(600)에 로컬 인텔리전스를 부여함으로써 서버 장애 시에도 기본 재배 루틴이 유지된다. 또한 조명(110/120) 및 양액(400)의 실시간 제어는 수ms 단위 응답이 요구되므로 엣지 처리가 필수적이다.                                                           |
| **결과(Consequences)**   | ✅ 네트워크 단절 시에도 현장 자율 제어 가능 / ✅ 실시간 센싱-액추에이터 루프 지연 최소화 / ✅ 서버는 분석·처방·이력 관리에 집중 가능 / ❌ 엣지-클라우드 간 상태 동기화 로직 복잡도 증가 / ❌ 제어기(600) 펌웨어 관리 및 OTA 업데이트 운영 부담 발생                                                                             |
| **트레이드오프(Trade-offs)** | **얻는 것:** 고가용성, 저지연 제어, 오프라인 복원력 / **감수해야 할 것:** 엣지-서버 데이터 일관성 보장 복잡도, 이중 관리 포인트(엣지+서버) 발생, 제어기(600) 하드웨어 비용 증가                                                                                                                    |

### ADR-002: 양액 처방 데이터의 서버 중앙화 및 모바일 기반 사용자 인터페이스 채택

| 항목                     | 내용                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 적물 관련 정보(작물 종류, 생육 단계)와 사용자 양액 정보는 서버(300)로 전송되어 서대 양액 처방이 결정된다. 농업인(사용자)은 현장 상주 없이 모바일(200)로 원격 관리를 원하며, 양액 처방 오류는 작물 피해로 직결된다.                             |
| **결정(Decision)**       | 양액 처방 알고리즘 및 작물 관리 데이터를 서버(300)에 중앙화하고, 모바일 앱(200)을 주요 HMI(Human-Machine Interface)로 채택한다. 제어기(600)는 서버로부터 처방값을 수신하여 양액 장치(400)를 구동한다.                       |
| **근거(Rationale)**      | 양액 처방은 작물 종류·생육 단계·환경 데이터를 복합적으로 고려하는 고연산 작업으로, 제한된 엣지 리소스보다 서버에서 처리하는 것이 정확도와 확장성 면에서 유리하다. 모바일 앱은 농업인의 이동성을 보장하며, 서버 중앙화는 처방 이력 관리와 감사(Audit) 추적을 용이하게 한다. |
| **결과(Consequences)**   | ✅ 정밀 양액 처방 및 이력 추적 가능 / ✅ 작물별 처방 모델 중앙 업데이트 용이 / ❌ 서버 장애 시 처방 업데이트 불가(기존 처방값으로 동작) / ❌ 모바일-서버 간 통신 보안 취약점 노출 가능성                                             |
| **트레이드오프(Trade-offs)** | **얻는 것:** 처방 정확도 향상, 중앙 데이터 거버넌스, 다중 농장 확장 용이 / **감수해야 할 것:** 서버 의존성 증가, 모바일 앱 UX 품질이 운영 효율에 직접 영향                                                           |

⚠️ 잠재적 위험 분석
------------

### 1. 서버(300) 단일 장애점(SPOF) 및 양액 처방 중단

* **설명:** 서버(300)가 다운되거나 네트워크가 단절될 경우, 최신 양액 처방값이 제어기(600)에 전달되지 않는다. 제어기가 이전 처방값으로 양액 장치(400)를 구동하면, 작물 생육 단계 변화에 대응하지 못해 과공급 또는 결핍이 발생하여 작물 피해로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 제어기(600)에 최후 수신 처방값 캐싱 및 로컬 폴백(Fallback) 로직 구현. 서버는 Active-Standby 이중화 구성. 헬스체크 기반 자동 알람을 모바일(200)에 즉시 발송하는 모니터링 파이프라인 구축.

### 2. 제어기(600)-양액 장치(400) 간 통신 오류로 인한 과공급/단수 사고

* **설명:** 제어기(600)와 양액 펌프(400) 간 유선/무선 통신 오류 또는 액추에이터 고장 시, 양액이 과다 공급되거나 완전히 차단될 수 있다. 특히 밀폐형 수직농장에서 과공급은 뿌리 질식과 병해 확산을 유발하고, 단수는 식물체 고사로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 양액 장치(400)에 유량 센서 및 이상 감지 인터럭(Interlock) 회로 추가. 제어기(600)에 워치독(Watchdog) 타이머 적용. 설정값 대비 실제 유량 편차 임계치 초과 시 자동 차단 및 경보 발령.

### 3. 모바일 앱(200)과 서버(300) 간 통신 보안 취약점

* **설명:** 사용자 양액 정보 및 적물 관련 정보가 평문 또는 취약한 암호화로 전송될 경우, 중간자 공격(MITM)에 의해 처방값이 위변조될 수 있다. 공격자가 양액 농도를 조작하면 작물 전체 피해가 발생하며, 농장 운영 데이터 유출도 수반된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 구간(앱↔서버, 서버↔제어기) TLS 1.3 이상 암호화 적용. 모바일 앱 API 호출에 JWT 기반 인증 및 만료 토큰 갱신 정책 적용. 서버 측 입력값 검증(양액 농도 허용 범위 화이트리스트) 로직 필수 구현.

### 4. LED 조명(110/120) 제어 오류로 인한 광주기 교란 및 작물 생리장애

* **설명:** 제어기(600)의 소프트웨어 버그나 서버로부터의 잘못된 스케줄 명령으로 인해 LED 조명(110: 적색, 120: 녹색 추정)의 광주기가 교란될 경우, 광형태형성(Photomorphogenesis) 이상이 발생한다. 특히 단일성 또는 장일성 작물에서 개화 시기 오류나 도장(웃자람) 현상이 나타나 상품성이 손실된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 조명 스케줄에 대한 서버-제어기 간 명령 확인응답(ACK) 프로토콜 적용. 제어기(600) 내 독립 RTC(Real-Time Clock) 모듈을 탑재하여 서버 장애 시에도 설정된 광주기를 자율 유지. 조명 상태 이상 감지 시 모바일(200) 알림 발송.

### 5. 제어기(600) 펌웨어 OTA 업데이트 실패로 인한 현장 브릭(Brick) 및 운영 중단

* **설명:** 서버(300)에서 제어기(600)로 원격 펌웨어 업데이트(OTA) 수행 중 네트워크 단절이나 전원 이상이 발생하면 제어기가 부팅 불가 상태(브릭)에 빠진다. 현장 방문 없이는 복구가 불가능하여, 양액 공급과 조명 제어가 동시에 중단되는 전면 운영 마비가 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:** A/B 파티션 이중화 펌웨어 저장 구조 채택(업데이트 실패 시 이전 버전 자동 롤백). OTA 업데이트는 유지보수 시간대(야간)에 단계적 배포(Canary Release) 적용. 업데이트 전 체크섬(SHA-256) 검증 및 전원 안정성 확인 후 진행 강제화.

### 6. 센서 데이터 부재로 인한 오픈루프(Open-loop) 제어 위험

* **설명:** 시스템 개념도상 온습도·EC·pH 등 환경 센서가 명시적으로 도시되지 않았다. 센서 없이 시간 기반 오픈루프 제어만 수행할 경우, 계절 변화·장비 노화·작물 밀도 변화에 따른 실제 환경 편차를 감지하지 못해 양액 처방의 정확도가 급격히 저하된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 재배 환경(100) 내 EC·pH·온습도·CO₂ 센서를 제어기(600)에 연동하는 클로즈드루프(Closed-loop) 제어 구조로 확장. 센서 데이터를 서버(300)에 실시간 전송하여 처방 피드백 루프를 구성. 센서 이상값 감지 시 알람 및 안전 모드 전환 로직 구현.

⚠️ 잠재적 위험 분석

### 1. 서버(300) 단일 장애점(SPOF) 및 양액 처방 중단

* **설명:** 서버(300)가 다운되거나 네트워크가 단절될 경우, 최신 양액 처방값이 제어기(600)에 전달되지 않는다. 제어기가 이전 처방값으로 양액 장치(400)를 구동하면, 작물 생육 단계 변화에 대응하지 못해 과공급 또는 결핍이 발생하여 작물 피해로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 제어기(600)에 최후 수신 처방값 캐싱 및 로컬 폴백(Fallback) 로직 구현. 서버는 Active-Standby 이중화 구성. 헬스체크 기반 자동 알람을 모바일(200)에 즉시 발송하는 모니터링 파이프라인 구축.

### 2. 제어기(600)-양액 장치(400) 간 통신 오류로 인한 과공급/단수 사고

* **설명:** 제어기(600)와 양액 펌프(400) 간 유선/무선 통신 오류 또는 액추에이터 고장 시, 양액이 과다 공급되거나 완전히 차단될 수 있다. 특히 밀폐형 수직농장에서 과공급은 뿌리 질식과 병해 확산을 유발하고, 단수는 식물체 고사로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 양액 장치(400)에 유량 센서 및 이상 감지 인터럭(Interlock) 회로 추가. 제어기(600)에 워치독(Watchdog) 타이머 적용. 설정값 대비 실제 유량 편차 임계치 초과 시 자동 차단 및 경보 발령.

### 3. 모바일 앱(200)과 서버(300) 간 통신 보안 취약점

* **설명:** 사용자 양액 정보 및 적물 관련 정보가 평문 또는 취약한 암호화로 전송될 경우, 중간자 공격(MITM)에 의해 처방값이 위변조될 수 있다. 공격자가 양액 농도를 조작하면 작물 전체 피해가 발생하며, 농장 운영 데이터 유출도 수반된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 구간(앱↔서버, 서버↔제어기) TLS 1.3 이상 암호화 적용. 모바일 앱 API 호출에 JWT 기반 인증 및 만료 토큰 갱신 정책 적용. 서버 측 입력값 검증(양액 농도 허용 범위 화이트리스트) 로직 필수 구현.

### 4. LED 조명(110/120) 제어 오류로 인한 광주기 교란 및 작물 생리장애

* **설명:** 제어기(600)의 소프트웨어 버그나 서버로부터의 잘못된 스케줄 명령으로 인해 LED 조명(110: 적색, 120: 녹색 추정)의 광주기가 교란될 경우, 광형태형성(Photomorphogenesis) 이상이 발생한다. 특히 단일성 또는 장일성 작물에서 개화 시기 오류나 도장(웃자람) 현상이 나타나 상품성이 손실된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 조명 스케줄에 대한 서버-제어기 간 명령 확인응답(ACK) 프로토콜 적용. 제어기(600) 내 독립 RTC(Real-Time Clock) 모듈을 탑재하여 서버 장애 시에도 설정된 광주기를 자율 유지. 조명 상태 이상 감지 시 모바일(200) 알림 발송.

### 5. 제어기(600) 펌웨어 OTA 업데이트 실패로 인한 현장 브릭(Brick) 및 운영 중단

* **설명:** 서버(300)에서 제어기(600)로 원격 펌웨어 업데이트(OTA) 수행 중 네트워크 단절이나 전원 이상이 발생하면 제어기가 부팅 불가 상태(브릭)에 빠진다. 현장 방문 없이는 복구가 불가능하여, 양액 공급과 조명 제어가 동시에 중단되는 전면 운영 마비가 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:** A/B 파티션 이중화 펌웨어 저장 구조 채택(업데이트 실패 시 이전 버전 자동 롤백). OTA 업데이트는 유지보수 시간대(야간)에 단계적 배포(Canary Release) 적용. 업데이트 전 체크섬(SHA-256) 검증 및 전원 안정성 확인 후 진행 강제화.

### 6. 센서 데이터 부재로 인한 오픈루프(Open-loop) 제어 위험

* **설명:** 시스템 개념도상 온습도·EC·pH 등 환경 센서가 명시적으로 도시되지 않았다. 센서 없이 시간 기반 오픈루프 제어만 수행할 경우, 계절 변화·장비 노화·작물 밀도 변화에 따른 실제 환경 편차를 감지하지 못해 양액 처방의 정확도가 급격히 저하된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 재배 환경(100) 내 EC·pH·온습도·CO₂ 센서를 제어기(600)에 연동하는 클로즈드루프(Closed-loop) 제어 구조로 확장. 센서 데이터를 서버(300)에 실시간 전송하여 처방 피드백 루프를 구성. 센서 이상값 감지 시 알람 및 안전 모드 전환 로직 구현.
