## 📋 ADR (Architecture Decision Record)

### ADR-001: 계층별 데이터 수집 및 중앙 집중식 제어 아키텍처 수립

| 항목 | 내용 |
|------|------ |
| **상황(Context)** | 스마트팜 양액 관리 시스템에서 원수탱크(110), 양액탱크(130), 배액탱크(140) 등 다양한 물리 자원을 연결하고 제어해야 하는 환경입니다. 각 탱크별 센서 데이터가 수집되고, 이를 기반으로 밸브드레이션 등의 제어가 이루어져야 합니다. |
| **결정(Decision)** | 이미지의 구조적 흐름에 따라, 각 탱크별 독립적인数据采集 모듈과 센서를 배치하고, 이를 우측의 중앙 제어 장치(150) 가 수집하여 통합 관리하는 계층형 아키텍처를 채택합니다. 데이터 플로우와 제어 플로우를 분리하여 안정성을 확보합니다. |
| **근거(Rationale)** | 이미지의 선 연결 구조는 분산 센서와 중앙 제어기의 관계를 명확히 보여줍니다. 또한 관련 문서 (ISO/IEC 30141:2024) 에 언급된 IoT 참조 아키텍처 표준은 분산된 디바이스 통합 관리를 권장하고 있어 적합합니다. |
| **결과(Consequences)** | **긍정:** 개별 탱크 고장 시 시스템 전체 파산 방지, 중앙 장치에서의 실시간 모니터링 가능.<br>**부정:** 중앙 제어장치(150) 의 부하가 집중될 수 있음. |
| **트레이드오프(Trade-offs)** | 중앙 집중식 관리의 편리성 대신 네트워크 지연 시의 데이터 무결성 문제를 감수해야 합니다. 따라서 에지 컴퓨팅 (국부 탱크 내 간단한 로직) 이 병행됩니다. |

### ADR-002: IoT 보안 표준 및 데이터 보호 프레임워크 적용

| 항목 | 내용 |
|------|------ |
| **상황(Context)** | 스마트팜과 같은 IoT 시스템은 외부 네트워크 연결이 필수적이므로 사이버 공격 (DDoS, 데이터 유출) 에 매우 취약합니다. 특히 배액탱크나 원수탱크와 같은 물리적 리소스 제어는 공격 시 물리적 재해로 이어질 수 있습니다. |
| **결정(Decision)** | 관련 문서 (ITU-T X.1352, ETSI EN 303 645) 에 명시된 대로 암호화 통신, 인증, 접근 제어 정책을 아키텍처 수준에서 강제합니다. 양액 제어장치 (150) 와 탱크 (110, 130 등) 간 통신을 위한 보안 계층을 설정합니다. |
| **근거(Rationale)** | 국내 연구진이 ITU-T 에서 국제표준으로 승인된 보안 인증 기준 (KISA) 이 있다는 점 (문서 참조) 과 ISO/IEC 27030 가이드라인 준수를 통해 글로벌 시장 진출 대비 및 시스템 신뢰도 확보가 필요합니다. |
| **결과(Consequences)** | **긍정:** 데이터 무결성 보장, 해킹 시 물리적 피해 최소화.<br>**부정:** 보안 오버헤드로 인한 시스템 응답 속도 저하 가능성. |
| **트레이드오프(Trade-offs)** | 보안 강화를 위해 사용하는 암호화 프로토콜 (MQTT over TLS 등) 과 성능 간의 균형을 맞춥니다. |

### ADR-003: 확장성을 고려한 모듈형 탱크 아키텍처 설계

| 항목 | 내용 |
|------|------ |
| **상황(Context)** | 스마트팜 규모는 초기부터 크게 늘어나거나 (예: 배액탱크 140 과 같은 추가 탱크), 필요에 따라 감소할 수 있습니다. 예비탱크 (120) 나 배액탱크 (140) 가 복수 개 존재하는 것이 이미지와 문맥에서 확인됩니다. |
| **결정(Decision)** | 탱크 (110, 120, 130, 140 등) 를 독립적인 모듈로 정의하여, 새로운 탱크가 추가될 때마다 아키텍처의 핵심 부분 (중앙 제어 장치 150, 통신 게이트웨이 등) 을 변경하지 않도록 확장성을 설계합니다. |
| **근거(Rationale)** | TTA 표준 목록 중 '무인항공기 활용', '스마트 온실' 등 다양한 규모의 시스템 규격을 개발 중이라는 점 (문서 참조) 이 유연성을 필요로 함을 시사합니다. 또한 oneM2M 표준의 상호운용성 원칙을 준수합니다. |
| **결과(Consequences)** | **긍정:** 시스템 확장성 (Scalability) 극대화, 비용 절감.<br>**부정:** 초기 표준 설계 비용 증가. |
| **트레이드오프(Trade-offs)** | 일회성 구축보다 장기적인 운영 비용과 유연성을 중시하는 트레이드오프입니다. |

## ⚠️ 잠재적 위험 분석

### 1. 중앙 제어 장치 단일 장애 지점 (SPOF) 문제
- **설명:** 이미지 우측에 있는 센서의 자동 밸브드레이션이 가능한 양액 제어장치(150) 가 시스템의 유일한 중앙 허브처럼 보입니다. 이 장치가 고장나거나 네트워크 단절되면 전체 탱크 제어 (원수, 양액, 배액 등) 가 마비될 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 제어 장치 (150) 에 대한 이중화 (Redundancy) 를 적용하거나, 제어 명령 로직을 분산된 로컬 게이트웨이로 분리하여 제어 장치 고장 시에도 로컬 탱크가 기본적인 동작 (예: 펌프 정지) 을 유지하도록 설계합니다.

### 2. 물리적 리소스 제어에 의한 사이버 보안 위협
- **설명:** IoT 표준 (ITU-T X.1352 등) 에서 강조하듯, 원격으로 배액탱크 (140) 나 원수탱크 (110) 의 밸브를 조작당할 경우, 농작물에 해를 입거나 유해 화학물질이 누출될 수 있는 치명적인 리스크가 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 물리적 제어 명령 (밸브 개폐 등) 은 암호화 및 다단계 인증 (MFA) 을 거치게 합니다. 또한, 이상적인 제어 명령 패턴 (갑작스러운 과대 배출 등) 을 감지하여 네트워크가 침입당했을 때 즉시 물리적으로 차단하는 Emergency Stop 기능을 구현합니다.

### 3. 대용량 센서 데이터 처리 및 저장부족
- **설명:** 원수, 양액, 배액, 예비탱크 등 다양한 탱크에서 실시간으로 수집되는 센서 데이터 (pH, 전도도, 수분 등) 가 방대해질 수 있습니다. 관련 문서에서 언급된 '스마트팜 데이터 상호운용 프레임워크'에서 강조하듯, 데이터 양에 대비한 저장 및 처리 인프라가 부재할 경우 성능 저하가 발생합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 수집 주기를 최적화하고 (필요 없는 고빈도 샘플링 제거), 실시간 처리 (Stream Processing) 와 장기 저장 (Time-Series Database) 을 분리하는 아키텍처를 적용합니다.

### 4. 표준화 및 상호운용성 문제
- **설명:** 관련 문서에 따르면 TTA, oneM2M, ISO 등 다양한 표준이 존재합니다. 만약 시스템 내 구성 요소가 서로 다른 표준 프로토콜 (MQTT, CoAP 등) 을 사용하여 상호운용성을 확보하지 못하면, 향후 시스템 확장 시 호환성 문제가 발생합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:** 설계 단계에서 oneM2M 또는 IEEE 2413과 같은 표준 아키텍처 프레임워크를 명확히 적용하고, 모든 센서와 액추에이터가 표준 API 를 준수하도록 강제합니다.

### 5. 네트워크 단절 시 오프라인 운영 불가
- **설명:** 스마트팜은 네트워크에 의존하는 시스템입니다. 관련 문서에서도 언급되는 것처럼 표준화된 통신 프로토콜 사용은 필수적이지만, 네트워크 단절 시 시스템이 멈추는 '오프라인 문제'는 심각한 운영 리스크입니다.
- **심격도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 로컬 에지 컴퓨팅 능력을 강화하여, 네트워크 연결이 끊겨도 일정 기간 동안 탱크 모니터링 및 기본 제어 로직이 로컬에서 실행되도록 (Edge Computing) 아키텍처를 구성합니다.
