## 📋 ADR (Architecture Decision Record)

### ADR-001: 통합 관리 서버의 기능적 모듈화

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 다양한 기능(회원 관리, 양봉 계약, 모니터링, 시뮬레이션, 통계 등)을 동시에 수행해야 함. (그림 1 참고: 통합관리서버 내부 구성) 복잡한 비즈니스 로직과 시스템 관리를 하나의 코드로 합치면 유지보수가 어려울 수 있음. |
| **결정(Decision)** | **통합 관리 서버 (701) 내부에 기능별 서브 모듈화를 적용한다.** (그림 1 내 702~710 영역 분리) 각 모듈(회원관리부, 양봉계약부, 시뮬레이션부 등)은 독립적인 비즈니스 로직을 담당하되, 통합된 서버 환경 아래서 데이터를 공유한다. |
| **근거(Rationale)** | **관심사 분리 (Separation of Concerns):** 회원 관리 (702), 생산 관리 (709) 등의 독립된 모듈화는 코드의 재사용성을 높이고 변경 사항의 영향을 제한한다.<br>**표준 준수:** TTA 개발 중인 단체표준 목록 ([별표 26] 참조) 에서 요구하는 '데이터 관리 요구 사항' 및 '시스템 인터페이스'를 모듈화하여 쉽게 준수할 수 있게 된다. |
| **결과(Consequences)** | <br>✅ **긍정:** 특정 기능(예: 시뮬레이션 부)의 로직 변경이 다른 기능(예: 쇼핑몰 관리)에 영향을 주지 않아 안정성이 확보됨.<br>❌ **부정:** 모듈 간 통신을 위한 API 설계가 복잡해지고, 트래픽 증가에 따른 서버 부하 관리가 추가될 수 있음. |
| **트레이드오프(Trade-offs)** | **복잡성 감소 vs 통신 오버헤드:** 기능 분리 (모듈화) 로 개발 효율성은 증가하지만, 모듈 간의 데이터 동기화를 위한 네트워크 오버헤드는 발생한다. |

### ADR-002: 데이터 엔티티의 독립적 저장 전략

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 다양한 유형의 데이터를 처리해야 함. (그림 1 내 DB 영역 참조: 위탁소비자 DB, 양봉가 DB, 일반소비자 DB, 생산관리부 DB 등). 데이터의 성격이 전혀 다르다. |
| **결정(Decision)** | **논리적 데이터 분리 저장 (Logical Data Partitioning)** <br>서버 내부 DB를 물리적/논리적으로 분리하여 저장한다. (702: 소비자와 계약, 709: 생산 관리, 710: 쇼핑몰 판매 정보) |
| **근거(Rationale)** | **데이터 무결성 보장:** 일반 소비자 데이터와 양봉가 데이터는 접근 권한과 데이터 모델이 달라 분리해야 한다. <br>**보안 표준 준수:** KISA 제안한 IoT 보안 시험·인증 기준 (ITU-T X.1352) 을 준수하기 위해 민감 데이터 (계약 정보 등) 를 분리 저장하여 접근 통제 범위를 좁힌다. |
| **결과(Consequences)** | <br>✅ **긍정:** 특정 데이터 (예: 판매 정보) 의 대용량 로그가 전체 시스템 성능을 저하시키는 것을 방지함.<br>❌ **부정:** 단일 서버 리소스 사용량이 증가할 수 있어 클라우드 확장성 설계가 필요함. |
| **트레이드오프(Trade-offs)** | **관리 편의성 감소:** 데이터가 여러곳에 흩어져 있어 통합 분석을 위해 ETL 프로세스가 필요해 관리 비용이 증가함. |

## ⚠️ 잠재적 위험 분석

### 1. 단일 장애점 (SPOF) 취약성
- **설명:** 모든 데이터 수집, 분석, 제어가 '통합관리서버' (701) 에 집중되어 있다. 이 서버가 다운되면 양봉 계약, 모니터링, 시뮬레이션 등 모든 서비스가 마비된다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** **Redundancy (복제) 구조 도입.** 통합관리서버를 2 개 이상 (Active-Standby) 배치하거나, 클라우드 기반의 HA(Cluster) 구성을 적용하여 서버 고장 시 서비스 연속성을 확보한다.

### 2. 데이터 무결성 및 동기화 실패
- **설명:** 시스템에는 위탁소비자 DB, 양봉가 DB, 생산관리 DB 등 다양한 DB (그림 1 내 702, 709, 710 등) 가 존재한다. 이 데이터들이 실시간으로 동기화되지 않거나, 일관성 없는 데이터가 유입될 경우 (예: 양봉 계약 정보와 실제 생산 정보가 불일치) 오류가 발생한다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **Transactional Consistency (ACID) 및 Event Sourcing 적용.** 변경 사항이 발생했을 때 (예: 양봉 계약 부 703) 다른 시스템으로 변경 로그를 발행하여 실시간으로 데이터를 동기화하는 이벤트 기반 아키텍처를 사용한다.

### 3. 상호운용성 및 호환성 이슈
- **설명:** IoT 기기, 센서, 게이트웨이 등 외부 디바이스들을 연결해야 한다. 국제 표준 (ISO/IEC 30141, ITU-T X.1352) 이나 TTA 표준 ([별표 26]) 을 준수하더라도, 실제 하드웨어 제조사마다 프로토콜 (MQTT, CoAP 등) 이 달라 연동 실패가 발생할 수 있다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **게이트웨이 레이어 (Gateway Layer) 도입.** 표준 프로토콜 (MQTT, CoAP) 변환을 담당하는 별도의 게이트웨이 계층을 배치하거나, 아키텍처 단계에서 oneM2M 규격과 같은 상호운용성 프레임을 표준 프로토콜로 고정한다.

### 4. 시스템 가용성 및 모니터링 지연
- **설명:** '모니터링부' (704) 에 '이상검출부' (705) 와 '환경제어부' (706) 가 있으나, 네트워크 통신 지연이나 센서 자체 오류로 인해 실시간 모니터링이 지연되거나 잘못된 이상을 보고받을 경우 (False Positive/Negative) 문제가 발생한다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 High
- **대응 방안:** **Edge Computing 전략 병행.** 모든 분석을 중앙 서버 (701) 로 보내지 않고, 주요 센서 측에서 기본 필터링과 이상 감지를 수행하여 (에지 노드) 서버로 가는 데이터만 집계하도록 하거나, 지연 시간(TTL)을 고려한 로직을 적용한다.

### 5. 보안 위협 (데이터 유출 및 무단 접근)
- **설명:** 양봉 계약 정보 (703), 위탁소비자 DB (702), 통계분석 정보 (708) 등 민감하고 귀중한 비즈니스 데이터가 하나의 통합 서버에 저장되어 있다. 해킹 시 모든 자산이 노출될 위험이 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **다중 인증 (MFA) 및 암호화 통신 적용.** 데이터 전송 시 TLS/SSL 사용, 저장 시 데이터 암호화 (Encryption at Rest) 적용. 또한, TTA 또는 ITU-T 보안 표준 (X.1352) 에 따라 정기적인 침투 테스트 (Penetration Test) 를 수행한다.
