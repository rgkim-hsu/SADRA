### ADR-001: **모듈화된 스마트팜 시스템 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 실시간 환경 모니터링, 자동 제어, 및 데이터 관리를 통해 농작물 생산성을 최적화해야 합니다. 시스템 개념도에서 **모니터링모듈**, **제어모듈**, **결과관리모듈**로 구분된 구조는 각 기능이 독립적으로 운영되도록 설계되었습니다. 이는 시스템의 확장성, 유지보수성, 및 장애 격리를 위해 필수적입니다.                     |
| **결정(Decision)**       | 시스템을 **모니터링**, **제어**, **결과관리**의 3개 핵심 모듈로 분리하고, 각 모듈 내에서도 세부 기능(예: 환경 모니터링의 경우 온도, 습도, 조도 등)을 독립적인 서브모듈로 구현합니다. 데이터는 중앙 **데이터베이스**에 저장되며, **데이터페이스**를 통해 각 모듈 간 데이터 공유가 이루어집니다.                          |
| **근거(Rationale)**      | 1. **모듈화**로 인해 각 기능의 독립적인 개발, 테스트, 배포가 가능해집니다. 2. **장애 격리**: 한 모듈의 장애가 전체 시스템에 영향을 미치지 않습니다. 3. **확장성**: 새로운 센서나 제어 로직 추가 시 해당 모듈만 수정하면 됩니다. 4. **스마트팜 표준**: ISO 25237(스마트팜 표준) 등에서 권장하는 모듈화 아키텍처와 일치합니다. |
| **결과(Consequences)**   | **장점**: 유지보수 비용 감소, 시스템 안정성 향상, 새로운 기능 추가 용이. **단점**: 모듈 간 통신 오버헤드 발생, 데이터 일관성 관리 복잡성 증가.                                                                                                                 |
| **트레이드오프(Trade-offs)** | 모듈화로 인한 유연성을 얻는 대신, 모듈 간 인터페이스 정의 및 데이터 동기화 메커니즘(예: 메시지 큐, API 호출) 구현이 필요합니다.                                                                                                                             |

### ADR-002: **중앙집중식 데이터베이스(DB) 구축**

| 항목                     | 내용                                                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 모니터링모듈(21~~25번)과 제어모듈(41~~44번), 결과관리모듈(51~52번)에서 생성된 데이터를 실시간으로 공유하고 분석해야 합니다. 분산된 데이터 저장 시 데이터 일관성 및 접근성 문제가 발생할 수 있습니다.                                              |
| **결정(Decision)**       | 모든 모듈에서 생성된 데이터를 **중앙 데이터베이스**에 저장하고, **데이터페이스**를 통해 접근합니다. 데이터베이스는 관계형 데이터베이스(RDBMS) 또는 시계열 데이터베이스(Time-Series DB)로 구축합니다.                                            |
| **근거(Rationale)**      | 1. **데이터 일관성**: 모든 모듈에서 동일 데이터에 접근 가능. 2. **실시간 분석**: 중앙에서 데이터 집계 및 분석이 용이합니다. 3. **스마트팜 트렌드**: IoT 기반 농업 시스템에서 중앙 DB는 필수적입니다(예: AWS IoT Core + DynamoDB, InfluxDB 등). |
| **결과(Consequences)**   | **장점**: 데이터 중복 최소화, 분석 효율성 향상. **단점**: 단일 장애점(SPOF) 발생 가능성, 대용량 데이터 처리 시 성능 병목 현상.                                                                                     |
| **트레이드오프(Trade-offs)** | 데이터 접근성 향상을 위해 DB 이중화 또는 클러스터링이 필요하며, 이를 위해 추가 인프라 비용이 발생합니다.                                                                                                          |

### ADR-003: **실시간 제어 루프 구현**

| 항목                     | 내용                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 제어모듈(41~44번)은 스케줄 관리, 작업 추적, 작업 지시, 작업 관리 기능을 통해 농장 환경(예: 온도, 습도, 조도)을 실시간으로 제어해야 합니다. 지연이 발생하면 농작물에 손상이 발생할 수 있습니다.                                      |
| **결정(Decision)**       | **실시간 운영 체제(RTOS)** 또는 **메시지 큐(예: RabbitMQ, Kafka)**를 활용하여 제어모듈과 모니터링모듈 간 지연 없는 통신을 보장합니다.                                                                |
| **근거(Rationale)**      | 1. **실시간성**: 스마트팜에서 제어 지연은 생산성 저하로 직결됩니다. 2. **신뢰성**: RTOS는 결정적(deterministic) 시간 내에 작업을 완료합니다. 3. **산업 표준**: ISO 25119(농업 기계 안전 표준)에서 실시간 제어 시스템을 권장합니다. |
| **결과(Consequences)**   | **장점**: 제어 정밀도 및 반응성 향상. **단점**: RTOS 구현 복잡성, 하드웨어 비용 증가.                                                                                                 |
| **트레이드오프(Trade-offs)** | 실시간성을 얻기 위해 하드웨어 성능(예: PLC, Edge 컴퓨터) 투자가 필요합니다.                                                                                                          |

⚠️ 잠재적 위험 분석
------------

### 1. **데이터베이스 단일 장애점(SPOF)**

* **설명:** 중앙 데이터베이스에 장애가 발생하면 모든 모듈에서 데이터 접근이 불가능해져 시스템 전체가 마비됩니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **DB 이중화** 및 **자동 Failover** 메커니즘 구축(예: PostgreSQL + Patroni).
  * **백업 시스템**을 통해 주기적 데이터 백업 및 복구 테스트 수행.

* * *

### 2. **모듈 간 통신 지연**

* **설명:** 모니터링모듈에서 수집된 데이터가 제어모듈로 전달되는 과정에서 네트워크 지연이 발생하면 실시간 제어가 실패할 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **메시지 큐(예: Kafka)**를 통해 비동기식 통신 구축.
  * **Edge Computing**을 활용하여 모니터링모듈에서 로컬로 일부 제어 로직 실행.

* * *

### 3. **보안 취약점(데이터 유출)**

* **설명:** 중앙 데이터베이스에 저장된 농장 환경 데이터가 해커에 의해 유출되면 농장 운영에 치명적인 영향을 미칠 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **암호화**: 데이터 저장 시 **AES-256** 적용, 전송 시 **TLS 1.3** 사용.
  * **접근 제어**: **RBAC(Role-Based Access Control)** 및 **MFA(다중 인증)** 도입.

* * *

### 4. **센서 데이터 오류**

* **설명:** 모니터링모듈(21~25번)의 센서(예: 온도, 습도)에서 오류가 발생하면 잘못된 데이터로 인해 제어모듈에서 잘못된 제어 명령을 내릴 수 있습니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **데이터 검증 로직** 구현(예: 이상치 탐지 알고리즘).
  * **이중 센서** 설치로 교차 검증 수행.

* * *

### 5. **시스템 확장성 한계**

* **설명:** 농장의 규모가 커질 경우(예: 100ha 이상), 현 시스템 아키텍처가 처리할 수 있는 데이터 양의 한계에 도달할 수 있습니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **클라우드 기반 아키텍처**로 마이그레이션(예: AWS IoT + Lambda).
  * **마이크로서비스 아키텍처**로 전환하여 각 모듈을 독립적으로 스케일링.

* * *

### 6. **소프트웨어 호환성 문제**

* **설명:** 각 모듈에서 사용되는 소프트웨어(예: 모니터링모듈의 데이터 수집 라이브러리)가 버전 충돌로 인해 호환성 문제가 발생할 수 있습니다.
* **심각도:** 🟢 Low
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **컨테이너화(Docker)**를 통해 각 모듈의 실행 환경 표준화.
  * **CI/CD 파이프라인** 구축으로 자동화된 테스트 및 배포 수행.
