📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트팜 거래 데이터의 블록체인 네트워크 기반 분산 원장 저장 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 생태계에서는 복수의 농가(노드), 유통업자, 소비자, 인증기관 등 다수의 이해관계자가 농산물 생산·유통·거래 데이터를 공유해야 한다. 기존 중앙집중형 DB 구조에서는 단일 장애점(SPOF), 데이터 위·변조, 신뢰 부재 문제가 발생한다. 이미지의 시스템(300)은 다수의 노드(농장 단말기)가 블록체인 네트워크에 참여하고, 사용자(93)로부터 발생한 거래 내역을 외부 블록(310)과 연계하여 분산 저장하는 구조를 채택하고 있다. |
| **결정(Decision)**       | 스마트팜의 생산 이력, 환경 센서 데이터, 농산물 거래 내역을 퍼블릭/컨소시엄 블록체인 네트워크(300) 위에 분산 원장으로 저장하고, 각 농장 노드가 P2P 방식으로 합의 알고리즘(PoA 또는 PBFT)을 통해 블록을 검증·기록하도록 결정한다. 거래 내역(93)은 오프체인 전처리 후 온체인 해시 앵커링 방식을 병행한다.                                                                  |
| **근거(Rationale)**      | ① 농산물 이력 추적의 신뢰성 확보: 생산→유통→판매 전 단계를 불변 원장에 기록하여 위·변조 방지. ② 다수 노드(농장) 간 합의를 통한 데이터 무결성 보장. ③ 외부 블록(310) 연계를 통해 공공 인증 및 감사 추적 가능. ④ 스마트 계약(Smart Contract)을 통한 자동화된 대금 정산 및 인증 프로세스 구현 가능. ⑤ 글로벌 농식품 공급망 블록체인 표준(GS1, IBM Food Trust 등) 트렌드에 부합.        |
| **결과(Consequences)**   | ✅ 긍정적: 농산물 원산지·이력 데이터의 신뢰성 확보, 스마트 계약 기반 자동 정산, 중개자 제거로 농가 수익성 향상, 감사 및 규제 대응 용이. ❌ 부정적: 블록체인 노드 운영을 위한 각 농장의 IT 인프라 요구 증가, 트랜잭션 처리 지연(실시간 IoT 데이터 처리 한계), 초기 구축 비용 및 운영 복잡도 상승.                                                                      |
| **트레이드오프(Trade-offs)** | 🔼 얻는 장점: 데이터 불변성, 탈중앙화 신뢰, 투명한 공급망 추적, 자동화 정산. 🔽 감수할 단점: 높은 레이턴시(합의 과정), 스케일아웃 시 네트워크 부하 증가, 농촌 환경의 낮은 네트워크 인프라와의 충돌 가능성, 스마트 계약 버그 발생 시 롤백 불가.                                                                                                     |

⚠️ 잠재적 위험 분석
------------

### 1. 농촌 네트워크 인프라 불안정으로 인한 노드 이탈 및 합의 장애

* **설명:** 스마트팜은 지리적으로 분산된 농촌 지역에 위치하여, 불안정한 인터넷 연결 환경에서 블록체인 노드가 일시적으로 네트워크에서 이탈할 수 있다. 다수 노드 이탈 시 PBFT·PoA 합의 정족수 미달로 블록 생성이 중단되고 거래 내역(93) 기록이 불가능해진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 엣지 컴퓨팅 기반 로컬 캐싱 레이어 도입(오프라인 시 임시 저장 후 재동기화), 위성 또는 LTE 백업 통신 회선 이중화, 합의 알고리즘을 네트워크 파티션 허용(AP) 방향으로 튜닝(예: Raft 기반 변형), 노드 수 기준 동적 정족수 조정 메커니즘 적용.

### 2. IoT 센서 데이터의 온체인 직접 저장으로 인한 네트워크 과부하 및 확장성 한계

* **설명:** 스마트팜에서 발생하는 온도·습도·CO₂·토양 센서 데이터는 초당 수백~수천 건의 고빈도 데이터다. 이를 모두 블록체인 온체인에 직접 기록할 경우, 블록 크기 초과 및 트랜잭션 처리 병목이 발생하여 시스템 전체 응답속도가 저하된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 오프체인 저장소(IPFS, AWS S3, 로컬 Time-series DB)에 원본 데이터를 저장하고 온체인에는 해시값·메타데이터만 앵커링하는 하이브리드 아키텍처 적용. 데이터 집계(Aggregation) 후 배치 트랜잭션 처리, Layer-2 솔루션(State Channel, Rollup) 도입 검토.

### 3. 스마트 계약(Smart Contract) 취약점으로 인한 거래 자동화 오류 및 자산 손실

* **설명:** 농산물 대금 자동 정산, 인증 발급 등을 처리하는 스마트 계약에 재진입(Reentrancy) 공격, 정수 오버플로우, 접근 제어 미흡 등의 취약점이 존재할 경우, 배포 후 수정이 불가능한 블록체인 특성상 농가 자산 손실이나 잘못된 인증 발급이 발생하고 롤백이 불가능하다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 배포 전 전문 보안 감사(Audit) 필수 수행(CertiK, OpenZeppelin 등 활용), 업그레이더블 프록시 패턴(Transparent Proxy / UUPS) 적용으로 긴급 패치 가능 구조 설계, 스테이징 환경에서의 퍼즈 테스팅(Fuzzing) 및 형식 검증(Formal Verification) 도입, 거래 한도 제한 및 긴급 정지(Circuit Breaker) 기능 내장.

### 4. 블록체인 노드 접근 키(Private Key) 분실 및 탈취로 인한 신원 위협

* **설명:** 각 농장 노드 및 사용자(93)는 거래 서명을 위한 개인키를 보유한다. 농촌 환경 특성상 IT 보안 인식이 낮아 개인키가 평문 저장되거나 피싱 공격에 노출될 경우, 공격자가 정상 노드로 위장하여 허위 거래 데이터를 블록체인에 주입하거나 타인의 자산을 탈취할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** HSM(Hardware Security Module) 또는 TEE(Trusted Execution Environment) 기반 키 관리 시스템 도입, 다중 서명(Multi-sig) 트랜잭션 정책 적용, DID(Decentralized Identity) 기반 노드 인증 체계 구축, 농가 대상 정기 보안 교육 및 키 복구 절차(Shamir Secret Sharing) 마련.

### 5. 외부 블록(310) 연계 지점의 단일 장애점(SPOF) 및 데이터 위변조 위협

* **설명:** 이미지에서 외부 블록(310)은 블록체인 네트워크(300)의 특정 노드와 단일 화살표로 연결되어 있어, 해당 연계 지점이 단일 장애점으로 작동할 가능성이 있다. 외부 시스템과의 API 연동 구간에서 중간자 공격(MITM) 또는 데이터 조작이 발생하면 외부로 전달되는 인증 정보나 이력 데이터가 왜곡될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 외부 블록 연계를 위한 오라클(Oracle) 노드를 다중화(최소 3개 이상)하여 단일 장애점 제거, TLS 1.3 상호 인증(mTLS) 적용, 연계 데이터에 블록체인 서명 및 타임스탬프 검증 레이어 추가, 정기적인 외부 연계 감사 로그 모니터링 체계 구축.

### 6. 규제 및 개인정보보호법(GDPR·개인정보보호법) 준수 충돌

* **설명:** 블록체인의 불변성(Immutability)은 GDPR의 '잊혀질 권리(Right to be Forgotten)' 및 국내 개인정보보호법상 정보 삭제 의무와 원천적으로 충돌한다. 농가 생산자 정보, 사용자(93)의 거래 내역 등 개인 식별 데이터가 온체인에 기록될 경우 법적 리스크가 발생한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 개인 식별 데이터는 반드시 오프체인 저장 후 익명화된 해시값만 온체인 기록, 영지식 증명(ZKP) 기술을 활용한 프라이버시 보존형 검증 도입, 법률 전문가와 협력하여 데이터 최소화 원칙 기반의 온체인 데이터 설계 기준 수립, 컨소시엄 블록체인 선택 시 데이터 거버넌스 정책을 참여 기관 간 계약으로 명문화.

* **대응 방안:** 오프체인 저장소(IPFS, AWS S3, 로컬 Time-series DB)에 원본 데이터를 저장하고 온체인에는 해시값·메타데이터만 앵커링하는 하이브리드 아키텍처 적용. 데이터 집계(Aggregation) 후 배치 트랜잭션 처리, Layer-2 솔루션(State Channel, Rollup) 도입 검토.

### 3. 스마트 계약(Smart Contract) 취약점으로 인한 거래 자동화 오류 및 자산 손실

* **설명:** 농산물 대금 자동 정산, 인증 발급 등을 처리하는 스마트 계약에 재진입(Reentrancy) 공격, 정수 오버플로우, 접근 제어 미흡 등의 취약점이 존재할 경우, 배포 후 수정이 불가능한 블록체인 특성상 농가 자산 손실이나 잘못된 인증 발급이 발생하고 롤백이 불가능하다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 배포 전 전문 보안 감사(Audit) 필수 수행(CertiK, OpenZeppelin 등 활용), 업그레이더블 프록시 패턴(Transparent Proxy / UUPS) 적용으로 긴급 패치 가능 구조 설계, 스테이징 환경에서의 퍼즈 테스팅(Fuzzing) 및 형식 검증(Formal Verification) 도입, 거래 한도 제한 및 긴급 정지(Circuit Breaker) 기능 내장.

### 4. 블록체인 노드 접근 키(Private Key) 분실 및 탈취로 인한 신원 위협

* **설명:** 각 농장 노드 및 사용자(93)는 거래 서명을 위한 개인키를 보유한다. 농촌 환경 특성상 IT 보안 인식이 낮아 개인키가 평문 저장되거나 피싱 공격에 노출될 경우, 공격자가 정상 노드로 위장하여 허위 거래 데이터를 블록체인에 주입하거나 타인의 자산을 탈취할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** HSM(Hardware Security Module) 또는 TEE(Trusted Execution Environment) 기반 키 관리 시스템 도입, 다중 서명(Multi-sig) 트랜잭션 정책 적용, DID(Decentralized Identity) 기반 노드 인증 체계 구축, 농가 대상 정기 보안 교육 및 키 복구 절차(Shamir Secret Sharing) 마련.

### 5. 외부 블록(310) 연계 지점의 단일 장애점(SPOF) 및 데이터 위변조 위협
