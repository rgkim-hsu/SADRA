# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 분산된 IoT 데이터의 통합 및 실시간 처리를 위한 Event-Driven Microservices 아키텍처 채택

| 항목 | 내용 |
| :--- | :--- |
| **상황(Context)** | 본 시스템은 물리적 환경에서 발생하는 방대한 양의 비정형 데이터(센서 측정값, 환경 센서 데이터 등)를 수집하고, 이를 회원/계약/생산/모니터링 등 복잡하고 다양한 비즈니스 영역(회원관리부, 양봉계약부, 생산관리부 등)과 연계하여 실시간으로 가공하고 분석해야 합니다. 전통적인 모놀리식(Monolithic) 아키텍처는 이러한 이기종 데이터 소스 및 다양한 기능 모듈의 독립적인 진화와 확장을 지원하기 어렵습니다. |
| **결정(Decision)** | **Event-Driven Microservices Architecture (MSA)** 기반의 플랫폼을 채택합니다. 모든 IoT 데이터는 **Message Broker (예: Kafka)**를 통해 메시지 스트림으로 표준화되어 유입되며, 각 기능 모듈(모니터링, 이상검출, 시뮬레이션 등)은 이 메시지 스트림을 소비하는 독립적인 마이크로서비스로 구현합니다. |
| **근거(Rationale)** | 1. **탄력성 및 확장성:** 개별 서비스 단위로 배포 및 확장(Scale)이 가능하여, 특정 부하가 집중되는 모듈(예: 실시간 모니터링)에 대해 독립적인 자원 할당이 용이합니다. 2. **실시간 처리:** Event Stream을 중심으로 데이터를 처리함으로써, 데이터 입력(Ingestion) 지연 시간을 최소화하고 즉각적인 의사결정이 필요한 이상 감지(Anomaly Detection)에 최적화됩니다. 3. **표준 준수:** MSA는 ISO/IEC 30141과 같은 참조 아키텍처에서 제시하는 ‘컴포넌트 기반’ 및 ‘재사용 가능한 서비스 인터페이스’의 개념을 구현하는 데 가장 적합합니다. |
| **결과(Consequences)** | **긍정적:** 높은 확장성, 장애 격리(Failure Isolation) 능력 확보, 최신 기술(예: ML 모델)을 모듈 단위로 빠르게 통합 및 배포 가능. **부정적:** 서비스 간의 상호 의존성 관리 복잡도가 극도로 높아지며, 운영 오버헤드(Observability, 트랜잭션 관리)가 증가합니다. |
| **트레이드오프(Trade-offs)** | **장점:** 시스템의 **유연성(Flexibility)**과 **확장성(Scalability)**을 극대화하여, 미래에 추가될 새로운 기능(예: 원격 제어 API 추가)에 대한 대응 속도가 빠릅니다. **감수할 점:** 아키텍처의 복잡성(Complexity)이 매우 높아지므로, 초기 설계 단계에서 강력한 API 게이트웨이와 통합 관측성(Observability) 시스템 구축에 대규모 투자가 필수적입니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 상호운용성 부족 위험 (Interoperability Failure Risk)
- **설명:** 시스템은 다양한 제조사 및 환경(센서, 구동기, 계약 시스템 등)에서 수집된 이기종 데이터(Zigbee, LoRa, MQTT 등 다양한 프로토콜)를 처리해야 합니다. 만약 데이터 파싱 계층이나 게이트웨이에서 표준 프로토콜(예: oneM2M, JSON/XML 스키마)을 통일적으로 처리하지 못하면, 데이터 불일치 및 누락이 발생하여 분석 결과의 신뢰성이 훼손됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 모든 IoT 데이터는 전용 **Data Ingestion Layer (Data Normalizer)**를 통해 단일하고 강제된 메시지 스키마(Canonical Data Model)로 변환해야 합니다. 인터페이스 레벨에서 TTA 등 국내 표준을 기반으로 한 데이터 모델을 의무적으로 적용하고, 상호운용성 테스트 플랫폼을 구축해야 합니다.

### 2. OT/IT 경계 보안 취약점 위험 (OT/IT Boundary Security Risk)
- **설명:** 물리적 환경을 제어하는 OT(Operational Technology) 영역(현장 센서, 제어 장치)이 IT(Information Technology) 영역(API 서버, DB)과 연결되면서, 해커가 비교적 취약한 엔드포인트를 통해 시스템 전체에 접근하는 경로가 생길 수 있습니다. 특히 원격 제어 기능이 포함된 경우 위험도가 매우 높습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** ISA/IEC 62443과 같은 산업제어시스템 보안 표준을 준용하여, 네트워크를 **Zone and Conduit** 개념으로 분리합니다. 데이터 흐름의 모든 경계(Boundary)에는 **One-way Data Diode** 또는 강력한 인증/인가를 갖춘 **IoT 보안 게이트웨이**를 필수로 배치해야 합니다.

### 3. 실시간 이상 감지 성능 저하 위험 (Real-time Anomaly Detection Latency Risk)
- **설명:** 모니터링부와 이상검출부는 실시간 데이터 스트림을 바탕으로 즉시 반응해야 합니다. 시스템 부하가 급증하거나 데이터 스트림의 전처리 과정(필터링, 집계 등)에 지연이 발생할 경우, 중요한 이상 상황(예: 가축 질병 초기 징후, 온도 급변)을 놓치거나 대응 시간이 길어지게 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 처리를 위한 **Stream Processing Engine (예: Apache Flink)**을 사용하고, 반드시 엣지 컴퓨팅(Edge Computing)을 활용하여 데이터 전처리와 1차 필터링을 현장 게이트웨이 레벨에서 수행해야 합니다. 클라우드 기반의 중앙 처리와 엣지 기반의 현장 대응을 계층적으로 분리해야 합니다.

### 4. 데이터 사일로 및 분석 모델화 위험 (Data Silo & Modeling Risk)
- **설명:** 시스템이 관리하는 데이터가 회원 정보(개인정보), 계약 정보(재무정보), 환경 데이터(물리정보) 등 성격이 완전히 다른 여러 DB에 파편화(Silo)되어 존재할 경우, 통합적인 통계 분석(통계분석부)이나 최적화 시뮬레이션(시뮬레이션부)을 수행할 때 데이터 연결과 정합성 확보가 극도로 어려워집니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 데이터를 통합 분석을 위한 **Data Lake** 구조로 취합하고, 데이터 웨어하우징 아키텍처를 도입해야 합니다. 특히 비즈니스 로직과 물리 데이터를 통합하는 **데이터 모델링 중심의 서비스 레이어(BLL)**를 구축하여, 데이터 소스에 관계없이 일관된 데이터 뷰(View)를 제공하도록 설계해야 합니다.

### 5. 운영 및 유지보수 복잡성 위험 (Operational Complexity Risk)
- **설명:** MSA를 채택함에 따라 수십 개 이상의 독립적인 마이크로서비스가 존재하게 되며, 이는 배포(Deployment), 로깅(Logging), 모니터링(Monitoring)의 복잡성을 기하급수적으로 증가시킵니다. 서비스 A의 오류가 서비스 B의 의존성을 간접적으로 건드리면서 전체 시스템 장애를 유발하는 사일런트 오류(Silent Failure)가 발생할 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **DevOps 파이프라인(CI/CD)**을 자동화하여 모든 배포 프로세스를 표준화하고, 중앙 집중식 **Observability Platform (Logging + Metrics + Tracing)**을 구축해야 합니다. 서비스 간의 의존성 맵(Dependency Map)을 시각화하고, 모든 API 호출에 대해 트레이싱 ID를 할당하여 근본 원인 분석(Root Cause Analysis) 시간을 단축해야 합니다.
