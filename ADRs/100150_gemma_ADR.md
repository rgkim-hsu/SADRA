# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 표준 기반의 이벤트 주도형 마이크로서비스 아키텍처(Event-Driven Microservices) 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 토양, 기상, 운영 등 극도로 이질적(Heterogeneous)이며 시공간적(Spatio-Temporal)인 데이터를 실시간으로 수집하여 고도의 정밀한 의사결정(재배 방법 추천)을 내려야 합니다. 데이터 출처가 센서, 외부 API, 레거시 시스템 등 매우 다양하며, 향후 다양한 작물, 환경, 기술이 추가될 수 있어 상호운용성(Interoperability)과 확장성이 가장 중요한 아키텍처적 과제입니다. |
| **결정(Decision)** | 데이터 수집, 전처리, 추천 로직 등 각 기능을 독립적인 마이크로서비스로 분리하고, 이 서비스 간의 데이터 흐름 및 이벤트 발생을 메시지 브로커(Message Broker)를 통해 비동기적으로 처리하는 **이벤트 주도형 아키텍처(EDA)**를 채택합니다. 데이터 모델링은 ISO/IEC 30141과 같은 국제 참조 아키텍처 표준을 준수합니다. |
| **근거(Rationale)** | **1. 확장성 및 독립성:** 각 서비스가 독립적이므로, 특정 기능(예: 기상 데이터 수집)에 장애가 발생해도 전체 시스템이 마비되지 않습니다. 새로운 센서나 분석 로직을 서비스 단위로 쉽게 추가할 수 있습니다. **2. 이질 데이터 처리:** 이벤트 브로커(Kafka 등)는 다양한 형태의 데이터를 표준화된 이벤트 형태로 받아 처리할 수 있게 하여, 데이터 통합의 복잡성을 낮춥니다. **3. 표준 준수:** 국제 표준을 반영하여 설계함으로써, 글로벌 시장 진출 및 다양한 공급업체(Vendor Lock-in 방지)와의 연동 가능성을 극대화합니다. |
| **결과(Consequences)** | **긍정적:** 높은 트랜잭션 처리량(Throughput) 확보, 뛰어난 확장성, 기술적 표준 준수로 인한 장기적 유지보수 용이성 및 유연성. **부정적:** 초기 시스템 구축 복잡도와 개발 난이도가 높고, 서비스 간의 트랜잭션 일관성(Consistency) 관리가 복잡해집니다. |
| **트레이드오프(Trade-offs)** | **[장점]** 최고의 확장성 및 높은 수준의 내결함성(Fault Tolerance)을 확보합니다. **[감수사항]** 상대적으로 높은 초기 설계 비용과 아키텍트 수준의 통합 관리가 필수적입니다. 단순한 모놀리식(Monolithic) 구조 대비 운영 복잡도가 증가합니다. |

## ⚠️ 잠재적 위험 분석

### 1. 센서 데이터의 이질성 및 신뢰성 부족 (Data Integrity & Heterogeneity)
- **설명:** 토양 센서(pH, EC), 기상 센서(온습도), 그리고 운영 기록 등 데이터의 측정 주기가 다르고, 센서의 오작동, 통신 오류, 데이터 손실 등이 발생하여 입력 데이터의 신뢰성 자체가 무너질 수 있습니다.
- **심각도:** 🔴 High (추천 방법 자체가 잘못될 수 있음)
- **발생 가능성:** 🔴 High (현장 환경의 특성상 불가피)
- **대응 방안:** **데이터 전처리 계층(Data Quality Layer) 의 필수화:** 이상치 탐지(Outlier Detection), 결측치 보간법(Imputation)을 적용하는 검증 모듈을 도입하고, 모든 센서 데이터에 메타데이터(측정 시간, 센서 ID, 보정 계수)를 첨부하여 데이터 출처를 명확히 합니다.

### 2. 사이버 공격을 통한 시스템 무결성 위협 (Cybersecurity Threat)
- **설명:** IoT 환경은 수많은 게이트웨이와 센서 노드를 포함하므로, 해커가 단일 노드를 탈취하여 시스템 데이터 수집 파이프라인을 오염시키거나, 추천 로직을 조작하여 농작물에 피해를 주는 방향으로 제어 명령을 송신할 위험이 존재합니다.
- **심각도:** 🔴 High (물리적 피해 및 경제적 손실 직결)
- **발생 가능성:** 🟡 Medium (보안 체계가 불충분할 경우)
- **대응 방안:** **제로 트러스트(Zero Trust) 모델 적용:** 모든 데이터 입력 지점(센서, 게이트웨이)에 대한 인증(Authentication)과 권한 부여(Authorization)를 의무화합니다. 또한, 통신 채널 전체에 대해 종단 간 암호화(End-to-End Encryption)를 적용하고, 입력 데이터에 대한 무결성 검사(MAC/HMAC)를 수행합니다.

### 3. 추천 모델의 과적합(Overfitting) 및 환경 변화 대응 실패 (Model Degradation)
- **설명:** 추천 시스템(ML/AI)이 학습한 데이터셋에 편향되거나 특정 환경(예: 비정상적인 장마, 기록적인 폭염)의 데이터가 발생했을 때, 학습된 모델이 일반화에 실패하여 비현실적이거나 위험한 재배 방법(추천)을 내보낼 수 있습니다.
- **심각도:** 🔴 High (농작물 실패, 막대한 경제적 손실)
- **발생 가능성:** 🟡 Medium (환경 변화의 예측 불가성)
- **대응 방안:** **지속 학습 파이프라인(Continuous Learning Pipeline) 구축:** 시스템을 배포한 후에도 실제 운영 데이터를 주기적으로 수집하고, 전문가의 검토(Human-in-the-loop)를 거쳐 모델을 재학습(Retraining)시키는 자동화된 MLOps 파이프라인을 구축해야 합니다.

### 4. 시스템 부하에 의한 실시간 처리 지연 (Real-time Latency Failure)
- **설명:** 축적된 대용량의 시공간 데이터(Historical Data)와 복잡한 다변수 분석(Multi-variate Analysis)이 실시간으로 발생할 경우, 추천 로직(S1003)이 과부하를 받아 지연(Latency)되면서, 실제 작물에 필요한 즉각적인 제어 결정(Critical Action)이 늦게 이루어질 수 있습니다.
- **심각도:** 🔴 High (생명 유지/제어에 치명적)
- **발생 가능성:** 🟡 Medium (데이터 양의 폭발적 증가 시)
- **대응 방안:** **계층적 데이터 처리 아키텍처:** 실시간 데이터는 스트림 처리 엔진(Stream Processing, 예: Apache Flink)을 사용하여 경량화된 지표만 즉시 분석합니다. 장기적이고 복잡한 패턴 분석은 배치(Batch) 처리에 위임하고, 경고(Alert) 레벨에 따른 적절한 처리 경로를 분리하여 성능을 최적화합니다.

### 5. 표준 부재로 인한 상호운용성 격차 (Interoperability Gap)
- **설명:** 현재 시장에 나와 있는 다양한 스마트팜 기자재 및 IoT 기기들이 각기 다른 비표준 프로토콜이나 독자적인 API를 사용하고 있어, 시스템의 여러 모듈(S1001, S1002)이 모든 외부 기기와 원활하게 통신할 수 없을 위험이 있습니다.
- **심각도:** 🟡 Medium (시스템 확장에 제약 발생)
- **발생 가능성:** 🔴 High (현장 기기의 다양성으로 인해)
- **대응 방안:** **표준화 계층(Adaptor Layer) 도입:** 모든 외부 인터페이스는 표준화된 데이터 포맷(예: JSON Schema, XML Schema)으로 변환하는 적응기(Adaptor/Gateway) 서비스를 거치도록 강제합니다. 이 계층에서 데이터를 추출하고 표준 데이터 모델(예: OCF, ISO/IEC 30141의 개념 모델)에 매핑(Mapping)해야 합니다.
