📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 작물모형(Crop Model) 중심의 데이터 통합 파이프라인 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 벼 재배 스마트팜 시스템은 기상DB, 예측기상, 품종DB라는 이종(異種) 데이터 소스와 사용자 입력(지역·품종·이양기)을 실시간으로 통합하여 예측수량 및 생육상태를 도출해야 한다. 데이터 소스별 갱신 주기·포맷·신뢰도가 상이하며, 최종 출력(수량예측·조치사항·생육상황)의 정확도가 농가 의사결정에 직결되는 고신뢰성 도메인이다.                     |
| **결정(Decision)**       | 기상입력자료·품종자료·재배자료를 단일 **작물모형(Crop Model)** 컴포넌트로 수렴시키는 허브-앤-스포크(Hub-and-Spoke) 통합 아키텍처를 채택한다. 작물모형은 예측수량과 생육상태를 병렬 산출하고, 생육진단 모듈을 경유하여 영농정보 DB와 연계한 후 출력 인터페이스로 전달한다.                                       |
| **근거(Rationale)**      | ① 작물 생육 시뮬레이션(ORYZA, DSSAT 계열)은 기상·품종·재배 인자를 동시에 고려해야 예측 정확도가 확보됨. ② 단일 모델 진입점 구조는 데이터 정합성 검증 로직을 중앙화하여 유지보수 비용을 절감함. ③ 생육진단을 별도 분기(다이아몬드 노드)로 분리하면 진단 알고리즘 교체 시 작물모형 코어에 영향을 주지 않아 변경 격리(Isolation)가 달성됨. |
| **결과(Consequences)**   | (+) 출력 일관성 확보, 모델 교체·업그레이드 용이성, 영농정보 DB 재사용 가능. (-) 작물모형이 단일 장애점(SPOF)이 되어 해당 컴포넌트 장애 시 전체 서비스 중단 위험 존재. 모형 연산 지연이 전체 응답 지연으로 직결됨.                                                                         |
| **트레이드오프(Trade-offs)** | **얻는 것:** 데이터 통합 단순화, 진단 로직 독립 교체 가능, 출력 품질 일관성. **감수해야 할 것:** 작물모형의 고가용성(HA) 설계 필수, 모형 입력 전처리 실패 시 전 기능 마비, 스케일아웃 복잡도 증가.                                                                                 |

### ADR-002: 입력-출력 인터페이스 분리(Input/Output Interface Segregation) 설계

| 항목                     | 내용                                                                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 사용자 입력(지역·품종·이양기)과 DB 기반 자동 수집 데이터(기상DB, 예측기상, 품종DB)가 혼재하며, 출력 역시 수량예측·조치사항·생육상황의 세 가지 이질적 정보 유형을 포함한다. 인터페이스 미분리 시 입력 오류가 출력 전체에 전파되고, 채널별 SLA 관리가 불가능하다.     |
| **결정(Decision)**       | 시스템 경계를 `<<input interface>>`와 `<<output interface>>`로 명시적으로 이분화한다. 입력 측은 사용자 입력과 DB Pull을 분리된 레인(Lane)으로 처리하고, 출력 측은 출력사항 컴포넌트를 통해 소비자(농가·관리자)에게 단일 창구로 제공한다. |
| **근거(Rationale)**      | ① 입출력 경계 명확화는 시스템 테스트 용이성과 외부 연동 확장성을 높임. ② 출력 인터페이스 단일화로 수량예측·생육상태·생육진단 결과의 정렬 및 포맷 통일이 가능함. ③ 향후 모바일 앱·웹 대시보드 등 다중 채널 확장 시 출력 인터페이스만 확장하면 내부 모델 변경 불필요.      |
| **결과(Consequences)**   | (+) 채널 독립 배포 가능, 입력 유효성 검증 레이어 집중화, API 버전 관리 용이. (-) 인터페이스 레이어 추가로 초기 개발 공수 증가, 인터페이스 계약(Schema) 변경 시 양단 동시 수정 필요.                                            |
| **트레이드오프(Trade-offs)** | **얻는 것:** 외부 시스템 연동 유연성, 보안 정책 집중 적용 가능 지점 확보. **감수해야 할 것:** 인터페이스 레이어 자체의 가용성 관리 부담, 스키마 버전 드리프트(drift) 위험.                                                   |

⚠️ 잠재적 위험 분석
------------

### 1. 작물모형(Crop Model) 단일 장애점(SPOF) 위험

* **설명:** 작물모형 컴포넌트는 기상입력자료·품종자료·재배자료 세 가지 입력을 동시에 수신하여 예측수량과 생육상태를 모두 산출한다. 해당 컴포넌트에 메모리 누수, 연산 오류, 또는 프로세스 크래시가 발생할 경우 예측수량·생육상태·생육진단·출력사항에 이르는 전체 다운스트림 파이프라인이 동시에 중단되어 농가에 어떠한 정보도 제공되지 않는다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Standby 이중화 또는 컨테이너 오케스트레이션(Kubernetes) 기반 자동 재시작 정책 적용. 작물모형을 마이크로서비스로 분리하고 헬스체크 엔드포인트를 통한 Circuit Breaker 패턴 도입. 최소한의 캐시 기반 최근 예측값 제공 폴백(Fallback) 메커니즘 구현.

* * *

### 2. 기상DB·예측기상 데이터 품질 저하에 따른 예측 오류 전파

* **설명:** 기상DB(과거 관측치)와 예측기상(수치예보 모델 출력)은 출처와 갱신 주기가 상이하다. 기상청 API 장애, 센서 결측, 수치예보 모델 오류 등으로 입력 데이터에 이상값(outlier) 또는 결측값(NaN)이 포함될 경우, 작물모형이 이를 그대로 처리하여 수량예측 오류가 출력사항(조치사항 포함)으로 전파된다. 농가가 잘못된 조치사항을 신뢰하고 이행할 경우 실질적 영농 피해가 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 기상입력자료 수신 단계에서 범위 검증(Range Validation), 결측 보간(Interpolation), 이상값 탐지(Z-score/IQR 기반) 로직을 포함하는 데이터 품질 게이트웨이(DQ Gateway) 레이어를 <<input interface>> 직후에 삽입. 데이터 품질 점수(DQ Score)를 출력사항에 함께 제공하여 사용자에게 신뢰도를 명시.

* * *

### 3. 품종DB 버전 불일치 및 신품종 미반영 위험

* **설명:** 품종DB는 작물모형의 핵심 파라미터(생육계수, 기본영양생장기간 등)를 공급한다. 농촌진흥청 등 외부 기관의 신품종 등록 주기와 시스템 내 품종DB 갱신 주기가 불일치할 경우, 신품종으로 재배하는 농가가 구품종 파라미터 기반의 잘못된 생육예측을 수신하게 된다. 품종 오매핑(wrong variety mapping) 발생 시 수량예측 오차가 20% 이상 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 품종DB에 버전 관리(Versioning) 및 유효기간(Validity Period) 속성 추가. 외부 품종 등록 기관 API와의 자동 동기화 배치 프로세스 구현. 작물모형 내에서 품종 파라미터 조회 시 버전 미스매치 경고 알림 발송 및 감사 로그(Audit Log) 기록.

* * *

### 4. 사용자 입력(지역·품종·이양기) 유효성 미검증으로 인한 모델 오작동

* **설명:** 사용자가 입력하는 지역 코드, 품종명, 이양기(移秧期) 정보는 작물모형의 초기 조건을 결정한다. 입력 인터페이스에 유효성 검증 로직이 부재하거나 불충분할 경우, 존재하지 않는 지역 코드·품종명 오기(誤記)·미래 날짜의 이양기 입력 등이 그대로 작물모형에 전달되어 Garbage-In-Garbage-Out(GIGO) 문제가 발생한다. 특히 고령 농업인의 경우 모바일 입력 오류 빈도가 높다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** <<input interface>> 레이어에 입력 스키마 검증(JSON Schema Validation), 지역 코드 화이트리스트, 이양기 논리적 범위 검증(농력 기준 4~6월) 로직 구현. UI 수준에서 자동완성(Autocomplete) 및 입력 가이드 제공. 입력 오류 발생 시 즉각적인 피드백 메시지와 함께 재입력 유도.

* * *

### 5. 영농정보DB 접근 집중 및 생육진단 병목(Bottleneck) 위험

* **설명:** 생육진단 모듈은 작물모형의 출력을 받아 영농정보DB를 조회한 뒤 최종 출력사항을 구성한다. 다수 농가가 동일한 생육 시기(예: 이삭 출수기)에 동시 조회할 경우, 영농정보DB에 대한 Read 요청이 집중되어 응답 지연이 발생한다. 또한 생육진단이 동기(Synchronous) 방식으로 설계된 경우, 영농정보DB 응답 지연이 전체 출력 지연으로 직결된다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 영농정보DB 앞단에 캐싱 레이어(Redis 등) 도입 — 생육 단계별 조치사항은 갱신 빈도가 낮아 캐싱 효과가 높음. 생육진단 결과 조회를 비동기(Async) 방식으로 전환하여 작물모형 결과를 먼저 반환하고 영농정보를 후속 푸시(Push) 방식으로 제공. DB 읽기 복제본(Read Replica) 구성으로 조회 부하 분산.

* * *

### 6. 출력 인터페이스 보안 취약점 — 농가 데이터 무단 접근

* **설명:** <<output interface>>를 통해 제공되는 수량예측·조치사항·생육상황 데이터는 특정 농가의 경작지·품종·수확량 정보를 포함한 민감 영농 데이터다. 인증·인가(AuthN/AuthZ) 메커니즘이 미흡할 경우, 타 농가 또는 외부 경쟁자가 특정 농가의 수확 예측 정보를 탈취하여 농산물 가격 담합 등에 악용할 수 있다. 또한 API 키 유출 시 대량 데이터 스크래핑이 가능하다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 출력 인터페이스에 OAuth 2.0 / JWT 기반 사용자별 토큰 인증 적용. 농가 단위 데이터 접근 권한(Row-Level Security) 구현. 전송 구간 TLS 1.3 암호화 필수 적용. API 게이트웨이에서 Rate Limiting 및 비정상 접근 패턴 탐지(SIEM 연계) 설정.
