## 📋 ADR (Architecture Decision Record)

### ADR-001: 비즈니스 로직 분리 및 단계별 프로세스 최적화

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 제공된 시스템 개념도(그림 5-1)에서 보듯 스마트팜 운영 요청과 컨설팅 요청이 병렬 혹은 순차적으로 처리되는 복잡한 비즈니스 로직이 존재함. 초기 요청 단계에서 컨설팅 유무를 즉시 판단하고, 해당 여부에 따라 데이터 수집 흐름이 달라져야 함. 또한 전문가 시스템 연동, 전자계약, 데이터 수집, 스케줄 전송 등 여러 단계가 순차적으로 연동되어야 함. |
| **결정(Decision)** | 시스템의 진입점 (Entry Point) 을 명확히 분리하고, 컨설팅 요청 유무에 따른 조건 분기 (Conditional Branching) 로직을 적용함. 컨설팅 요청이 '아니오'인 경우 운영 요청으로 회귀시키고, '예'인 경우 전문가 시스템 연동 단계로 직행하도록 프로세스 분할함. |
| **근거(Rationale)** | 복잡한 비즈니스 규칙 (스마트팜 운영 vs 컨설팅) 을 한 번의 흐름에 처리하면 코드 복잡도가 급증하고 유지보수가 어려워짐. 조건 분기 구조 (이미지의 다이아몬드 형태) 를 사용하면 각 시나리오의 로직을 독립적으로 관리할 수 있음. 또한, TTA 등의 표준에서 강조하는 상호운용성을 위해 모듈화된 흐름 설계가 필수적임. |
| **결과(Consequences)** | **긍정적**: 시스템 확장성이 높아져 향후 새로운 서비스(예: 자동화 제어 등) 를 추가하기 쉬워짐.<br>**부정적**: 초기 개발 단가 상승 및 단위 테스트 시나리오 수 증가 (테스트 코버리지 관리 필요). |
| **트레이드오프(Trade-offs)** | 코드 복잡도 증가 vs 비즈니스 로직의 명확성 및 유지보수성 향상 사이의 균형 추구. |

### ADR-002: 전문가 시스템 연동 및 데이터 수집 보안 강화

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템의 S6 단계('전문가 시스템에 자료입력') 와 S12 단계('디지털 Data 수집 시작') 에서 외부 시스템 및 IoT 디바이스와 연동해야 함. 이때 S6 단계의 자료입력은 시스템의 논리적 오류를 유발할 수 있으며, S12 단계의 데이터 수집 시 IoT 기기의 사생활 보호와 데이터 무결성이 중요함. |
| **결정(Decision)** | **전문가 시스템 연동 API 게이트웨이 도입**: 외부 전문가 시스템과의 연동을 직접 연결하는 대신, API 게이트웨이를 두고 인증, 유효성 검사, 로깅을 집중 관리함. **엔드-투-엔드(End-to-End) 암호화**: 데이터 수집 과정에서 전송 중인 데이터는 TLS 1.3 또는 그 이상의 암호화 프로토콜을 사용하여 암호화함. |
| **근거(Rationale)** | 관련 문서에서 언급된 ITU-T X.1352(보안요구) 와 ISO/IEC 27030(보안 가이드라인) 을 준수하여 보안 위협으로부터 시스템을 보호해야 함. 외부 시스템 연동 시 API 레벨에서 통합 관리를 하면 시스템 내 코드가 외부 변경에 덜 영향을 받음. |
| **결과(Consequences)** | **긍정적**: 외부 시스템 변경 시 시스템 영향 최소화 및 보안 취약점 감소.<br>**부정적**: API 게이트웨이 도입으로 인한 네트워크 오버헤드 소량 발생. |
| **트레이드오프(Trade-offs)** | 시스템 성능 미세 저하 vs 보안 강화 및 외부 의존성 관리 용이성. |

### ADR-003: 실시간 데이터 동기화 및 스케줄 관리 아키텍처

| 항목 | 내용 |
|------|------|
| **상황(Context)** | S10 단계('점검표 제공 일/월/년') 와 S14 단계('관리스케줄 전송') 에서는 시간 기반의 이벤트 처리와 데이터 동기화가 중요함. 스마트팜 환경은 환경 변화에 따라 실시간으로 대응해야 하므로 데이터 지연이 발생하면 관리 효율이 떨어짐. |
| **결정(Decision)** | 이벤트 기반 아키텍처 (Event-Driven Architecture, EDA) 를 채택함. S10 단계의 점검표 정보를 메신저 또는 메시지 큐 (MQTT 등) 를 통해 실시간으로 구독하고, S14 단계의 스케줄 변경 사항은 즉시 구독자 (관리자 시스템) 에게 브로드캐스트 함. |
| **근거(Rationale)** | 스마트팜 및 IoT 환경은 상태 변화가 빈번하므로 MQTT 와 같은 경량 프로토콜 및 실시간 메시징 시스템 사용이 적합함. ISO/IEC 30141:2024에서 제시하는 IoT 참조 아키텍처의 원칙인 효율적인 데이터 흐름 관리를 반영함. |
| **결과(Consequences)** | **긍정적**: 지연된 데이터 처리로 인한 환경 제어 실패 예방.<br>**부정적**: 실시간 메시징 인프라 구축 비용 발생. |
| **트레이드오프(Trade-offs)** | 실시간 처리 능력 향상 vs 인프라 복잡도 및 비용 증가. |

## ⚠️ 잠재적 위험 분석

### 1. [IoT 디바이스 사생활 침해 위협]
- **설명:** S12 단계에서 디지털 데이터를 수집할 때 센서에서 수집된 위치 정보나 식별 가능한 데이터가 탈취되거나 제 3 자에 유출될 경우 스마트팜 농가의 사생활이 침해될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (해킹 시나리오 증가, 기기 인증 부재 시)
- **대응 방안:** **기기 인증 강화**: IoT 기기 연결 시 고유 인증키 (Certificate) 를 적용하고, 데이터 수집 시 익명화 처리 (Anonymization) 를 적용함. 보안 표준 (ISO/IEC 27030 등) 을 준수하여 데이터 암호화 및 전송 보안 절차를 만듦.

### 2. [데이터 무결성 훼손 위험]
- **설명:** S6 단계에서 전문가 시스템에 자료입력 시, 사용자 실수로 잘못된 값을 입력하거나 악의적인 조작이 이루어져 시스템 전체의 데이터 신뢰도가 떨어질 경우 관리 스케줄 전송 (S14) 이 제대로 작동하지 않을 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **유효성 검사 로직 강화**: 데이터 입력 단계에서 범위 확인 및 논리적 오류를 검증하는 로직을 적용함. 또한 입력된 데이터의 변경 이력을 로깅하고, 백업 데이터를 통해 복구할 수 있도록 함.

### 3. [외부 시스템 연동 장애로 인한 가용성 저하]
- **설명:** S6 단계의 전문가 시스템이나 S8 단계의 전자계약 시스템 등 외부 3rd party 와 연동 시, 해당 외부 시스템이 다운되거나 API 가 변경되면 전체 서비스 가용성이 급격히 떨어질 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (외부 의존성 존재)
- **대응 방안:** **회복성 설계 (Resilience)**: 외부 시스템 연동에 대해 재시도 로직 (Retry Logic) 및 폴백 (Fallback) 시스템 (예: 오프라인 모드에서 일정 시간 데이터 로컬에 저장 후 연결 회복시 동기화) 을 구현함.

### 4. [실시간 데이터 전송 지연으로 인한 제어 실패]
- **설명:** S14 단계의 관리스케줄 전송 시 네트워크 불안정이나 처리 지연으로 인해 실시간으로 필요한 환경 제어가 실패할 경우 작물이나 가축에게 피해가 갈 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (네트워크 환경에 의존)
- **대응 방안:** **edge computing 활용**: 주요 제어 로직을 엣지 디바이스 또는 로컬 게이트웨이에서 처리하고, 클라우드 전송은 비동기로 처리하여 네트워크 지연에 덜 민감한 아키텍처를 설계함.

### 5. [보안 표준 미준수로 인한 규제 리스크]
- **설명:** 제공된 문서에서 언급된 TTA, ITU-T, ETSI 등의 보안 표준 (예: ITU-T X.1352, ETSI EN 303 645) 을 제대로 준수하지 않으면, 향후 서비스 제공 시 규제 제재나 인증 불합격 리스크가 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low (현재 설계 단계이므로 사전 예방 가능)
- **대응 방안:** **규제 준수 체크리스트 수립**: 아키텍처 설계 단계에서 각 표준 (ISO/IEC 30141:2024, oneM2M 등) 을 체크리스트로 활용하여 보안 요구사항 (암호화, 인증 등) 을 명시적으로 반영함.
