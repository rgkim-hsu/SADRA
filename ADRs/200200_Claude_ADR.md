### ADR-001: 모듈형 IoT 컨트롤러 기반 엣지-클라우드 하이브리드 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 거적제어, 환기제어(측면/상단), 관수제어 등 다수의 물리 액추에이터를 실시간으로 제어해야 한다. 농촌 인구 고령화와 노동력 감소로 인해 원격·자동 제어가 필수적이며, 비닐하우스와 같은 열악한 네트워크 환경에서도 안정적으로 동작해야 한다. 단일 중앙 집중형 컨트롤러로는 각 액추에이터의 독립적 장애 격리와 확장이 어렵다.                  |
| **결정(Decision)**       | 각 제어 대상(거적, 환기 측면, 환기 상단, 관수)마다 독립적인 IoT 컨트롤러를 할당하는 모듈형 엣지 아키텍처를 채택한다. 무선공유기를 게이트웨이로 두어 로컬 네트워크를 구성하고, 스마트폰 앱 플랫폼을 통해 원격 제어 및 모니터링(CCTV, 환경센서)을 제공한다. 정보 서비스(귀농지원, 농사정보, 시세정보, 정보공유)는 클라우드 레이어에서 별도 제공한다.       |
| **근거(Rationale)**      | 모듈형 구조는 특정 컨트롤러 장애 시 타 액추에이터에 영향을 주지 않는 장애 격리(Fault Isolation)를 보장한다. 엣지 처리를 통해 네트워크 단절 상황에서도 로컬 자동화 로직 실행이 가능하다. 또한 신규 제어 대상 추가 시 컨트롤러 모듈 하나만 추가하면 되므로 수평 확장성이 높다. 스마트폰 앱은 농가 사용자의 접근성을 극대화한다.                 |
| **결과(Consequences)**   | (+) 개별 모듈 교체·유지보수가 용이하고, 시스템 부분 장애 시 전체 운영 중단을 방지한다. (+) 추가 모듈(수평 확장) 도입이 아키텍처 변경 없이 가능하다. (-) IoT 컨트롤러 수 증가에 따라 펌웨어 버전 관리, OTA 업데이트 복잡도가 상승한다. (-) 무선공유기라는 단일 게이트웨이가 전체 통신의 SPOF(Single Point of Failure)가 된다. |
| **트레이드오프(Trade-offs)** | 【얻는 것】 높은 모듈 독립성, 점진적 확장 용이성, 엣지 자율 운영 가능성 / 【감수할 것】 분산된 디바이스 관리 복잡성 증가, 게이트웨이 이중화 미적용 시 단일 장애점 위험, 각 컨트롤러별 보안 패치 관리 부담                                                                                         |

### ADR-002: 무선(Wi-Fi) 기반 단일 게이트웨이 통신 레이어 채택

| 항목                     | 내용                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 비닐하우스 환경은 유선 배선이 어렵고, 농업 현장 특성상 먼지·수분·온도 변화가 심하다. 다수의 IoT 컨트롤러와 모니터링 장비(CCTV, 환경센서)를 하나의 네트워크로 연결해야 하며, 스마트폰 앱과의 실시간 연동이 필요하다.                                               |
| **결정(Decision)**       | 무선공유기(Wi-Fi 게이트웨이) 1대를 중심으로 모든 IoT 컨트롤러, 모니터링 장비, 스마트폰 앱을 단일 무선 네트워크로 연결하는 Star Topology를 채택한다.                                                                              |
| **근거(Rationale)**      | Wi-Fi는 별도 통신 모듈 없이 범용 스마트폰 앱과 직접 연동 가능하며, 농가의 기존 인터넷 인프라 활용이 용이하다. CCTV 영상 스트리밍과 같은 고대역폭 요구사항도 충족 가능하다. LoRa/Zigbee 대비 구축 비용과 기술 진입장벽이 낮아 고령 농업인도 운영 가능하다.                   |
| **결과(Consequences)**   | (+) 구축 비용 절감 및 운영 단순화. (+) 스마트폰과의 네이티브 연동으로 앱 개발 복잡도 감소. (-) 무선공유기 장애 시 전체 제어·모니터링 기능 마비. (-) Wi-Fi 커버리지 한계로 대규모 농장 확장 시 추가 AP 필요. (-) 2.4/5GHz 대역 혼선 및 농업 환경 특유의 RF 간섭 가능성. |
| **트레이드오프(Trade-offs)** | 【얻는 것】 범용성·저비용·고대역폭 / 【감수할 것】 단일 게이트웨이 SPOF, 실외·원거리 확장 한계, 전력 소비량이 LoRa 대비 높아 배터리 기반 센서 적용 불리                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. 무선공유기 단일 장애점(SPOF) 으로 인한 전체 시스템 마비

* **설명:** 현재 아키텍처에서 무선공유기는 모든 IoT 컨트롤러, 모니터링 장비, 스마트폰 앱 간 통신의 유일한 허브다. 공유기 전원 장애, 펌웨어 크래시, 물리적 파손 발생 시 거적·환기·관수 등 전체 원격 제어가 즉시 불가능해진다. 여름철 고온기에 환기제어가 중단될 경우 작물 피해로 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 무선공유기 이중화(Active-Standby 구성) 도입. IoT 컨트롤러 펌웨어 레벨에서 게이트웨이 미응답 시 로컬 자동화 로직(예: 온도 임계값 초과 시 자동 환기 개방)을 실행하는 오프라인 페일세이프(Fail-Safe) 로직 구현 필수.

### 2. IoT 컨트롤러 펌웨어 보안 취약점 및 무단 접근

* **설명:** 다수의 IoT 컨트롤러가 Wi-Fi 네트워크에 연결되어 있으나, 인증·암호화 메커니즘이 명시되지 않았다. 공유기 Wi-Fi 비밀번호 탈취 또는 기본 자격증명(default credential) 미변경 시 외부 공격자가 네트워크에 침투하여 거적·환기·관수 액추에이터를 임의 조작할 수 있다. 농업 시설 파괴 또는 작물 고사를 유발하는 물리적 피해로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** IoT 컨트롤러와 앱 간 통신에 TLS/DTLS 암호화 및 디바이스 인증서(X.509) 기반 상호 인증 적용. 컨트롤러 관리 네트워크와 모니터링 네트워크를 VLAN으로 분리. OTA 펌웨어 업데이트에 코드 서명(Code Signing) 적용 및 정기 보안 감사 실시.

### 3. 스마트폰 앱 플랫폼의 단일화로 인한 서비스 연속성 위험

* **설명:** 스마트폰 앱이 원격 제어(환기개폐, 거적개폐, 관수제어)와 모니터링의 유일한 인터페이스로 동작한다. 앱 스토어 정책 변경으로 인한 앱 강제 업데이트·배포 중단, OS 버전 비호환, 또는 서버 측 API 장애 발생 시 농업인이 시스템을 전혀 제어할 수 없게 된다. 고령 농업인의 경우 스마트폰 분실·파손 시 대체 접근 수단이 없다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 웹 브라우저 기반 보조 관리 콘솔(반응형 Web UI) 병행 제공. 물리적 비상 제어 버튼(Local Override Switch)을 각 IoT 컨트롤러에 탑재하여 앱 없이도 현장 수동 조작 가능하도록 설계. 앱 API 서버에 대한 SLA 및 DR(재해복구) 계획 수립.

### 4. 환경센서 데이터 신뢰성 저하로 인한 오작동 자동화

* **설명:** 환경센서가 수집한 온도·습도·CO₂ 데이터를 기반으로 환기·관수 자동 제어가 수행될 경우, 센서 드리프트(calibration 오류), 물리적 오염(먼지·결로), 또는 통신 패킷 손실로 인해 부정확한 값이 컨트롤러에 전달될 수 있다. 이로 인해 불필요한 과잉 환기나 관수 중단 같은 오작동이 발생하고 작물 피해 및 에너지 낭비로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 동일 측정 항목에 대해 센서 이중화(Redundant Sensing) 적용 및 이상값 필터링(Moving Average, 3-Sigma 이상값 제거) 로직 구현. 센서 정기 캘리브레이션 스케줄링 기능을 운영 플랫폼에 내장. 임계값 초과 시 자동 제어 실행 전 농업인에게 알림 후 확인을 요구하는 Confirmation Gate 옵션 제공.

### 5. 다수 IoT 컨트롤러의 펌웨어 버전 파편화 및 유지보수 복잡성

* **설명:** 거적, 환기(측면), 환기(상단), 관수 등 4종 이상의 컨트롤러가 독립 운영되며, 향후 "추가 모듈" 확장이 명시되어 있다. 각 컨트롤러의 펌웨어 버전이 상이하게 유지될 경우, 버그 수정·기능 업데이트 배포 시 일부 컨트롤러만 업데이트되는 파편화가 발생한다. 구형 펌웨어 컨트롤러가 보안 취약점에 노출된 채 방치되거나, 앱-컨트롤러 간 API 비호환으로 제어 불능 상태가 될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 중앙화된 디바이스 관리 플랫폼(Device Management Platform) 도입으로 모든 컨트롤러의 펌웨어 버전 현황을 단일 대시보드에서 관리. 무선 OTA(Over-The-Air) 일괄 업데이트 기능 구현 및 롤백(Rollback) 메커니즘 필수 탑재. 컨트롤러-앱 간 API 버전 호환성을 Semantic Versioning으로 명세화하고 하위 호환성 정책 수립.

### 6. 농촌 네트워크 인프라 의존성으로 인한 원격 제어 불가

* **설명:** 스마트폰 앱을 통한 원격 제어는 농가 인터넷 회선(ISP)과 모바일 데이터 망에 동시에 의존한다. 농촌 지역 특성상 ISP 회선 장애, 정전, 또는 태풍·폭설 등 자연재해 시 인터넷 연결이 수 시간~수일 단절될 수 있다. 이 기간 동안 외부 원격 제어가 전혀 불가능하며, 긴급 상황(폭염 시 환기 제어)에 대응하지 못한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 엣지 레벨 자율 운영 로직(Edge Autonomy) 강화: 인터넷 단절 상황에서도 로컬 Wi-Fi 네트워크 내에서 스마트폰-컨트롤러 직접 통신(LAN 모드) 지원. 4G/LTE 백업 회선(USB 모뎀)을 무선공유기에 연결하는 이중화 회선 구성 검토. 주요 자동화 룰(온도 X℃ 초과 시 환기 개방 등)을 컨트롤러 로컬에 저장하여 클라우드 의존 없이 실행 가능하도록 설계.

### ADR-002: 무선(Wi-Fi) 기반 단일 게이트웨이 통신 레이어 채택

| 항목                     | 내용                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 비닐하우스 환경은 유선 배선이 어렵고, 농업 현장 특성상 먼지·수분·온도 변화가 심하다. 다수의 IoT 컨트롤러와 모니터링 장비(CCTV, 환경센서)를 하나의 네트워크로 연결해야 하며, 스마트폰 앱과의 실시간 연동이 필요하다.                                               |
| **결정(Decision)**       | 무선공유기(Wi-Fi 게이트웨이) 1대를 중심으로 모든 IoT 컨트롤러, 모니터링 장비, 스마트폰 앱을 단일 무선 네트워크로 연결하는 Star Topology를 채택한다.                                                                              |
| **근거(Rationale)**      | Wi-Fi는 별도 통신 모듈 없이 범용 스마트폰 앱과 직접 연동 가능하며, 농가의 기존 인터넷 인프라 활용이 용이하다. CCTV 영상 스트리밍과 같은 고대역폭 요구사항도 충족 가능하다. LoRa/Zigbee 대비 구축 비용과 기술 진입장벽이 낮아 고령 농업인도 운영 가능하다.                   |
| **결과(Consequences)**   | (+) 구축 비용 절감 및 운영 단순화. (+) 스마트폰과의 네이티브 연동으로 앱 개발 복잡도 감소. (-) 무선공유기 장애 시 전체 제어·모니터링 기능 마비. (-) Wi-Fi 커버리지 한계로 대규모 농장 확장 시 추가 AP 필요. (-) 2.4/5GHz 대역 혼선 및 농업 환경 특유의 RF 간섭 가능성. |
| **트레이드오프(Trade-offs)** | 【얻는 것】 범용성·저비용·고대역폭 / 【감수할 것】 단일 게이트웨이 SPOF, 실외·원거리 확장 한계, 전력 소비량이 LoRa 대비 높아 배터리 기반 센서 적용 불리                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. 무선공유기 단일 장애점(SPOF) 으로 인한 전체 시스템 마비

* **설명:** 현재 아키텍처에서 무선공유기는 모든 IoT 컨트롤러, 모니터링 장비, 스마트폰 앱 간 통신의 유일한 허브다. 공유기 전원 장애, 펌웨어 크래시, 물리적 파손 발생 시 거적·환기·관수 등 전체 원격 제어가 즉시 불가능해진다. 여름철 고온기에 환기제어가 중단될 경우 작물 피해로 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 무선공유기 이중화(Active-Standby 구성) 도입. IoT 컨트롤러 펌웨어 레벨에서 게이트웨이 미응답 시 로컬 자동화 로직(예: 온도 임계값 초과 시 자동 환기 개방)을 실행하는 오프라인 페일세이프(Fail-Safe) 로직 구현 필수.

### 2. IoT 컨트롤러 펌웨어 보안 취약점 및 무단 접근

* **설명:** 다수의 IoT 컨트롤러가 Wi-Fi 네트워크에 연결되어 있으나, 인증·암호화 메커니즘이 명시되지 않았다. 공유기 Wi-Fi 비밀번호 탈취 또는 기본 자격증명(default credential) 미변경 시 외부 공격자가 네트워크에 침투하여 거적·환기·관수 액추에이터를 임의 조작할 수 있다. 농업 시설 파괴 또는 작물 고사를 유발하는 물리적 피해로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** IoT 컨트롤러와 앱 간 통신에 TLS/DTLS 암호화 및 디바이스 인증서(X.509) 기반 상호 인증 적용. 컨트롤러 관리 네트워크와 모니터링 네트워크를 VLAN으로 분리. OTA 펌웨어 업데이트에 코드 서명(Code Signing) 적용 및 정기 보안 감사 실시.

### 3. 스마트폰 앱 플랫폼의 단일화로 인한 서비스 연속성 위험

* **설명:** 스마트폰 앱이 원격 제어(환기개폐, 거적개폐, 관수제어)와 모니터링의 유일한 인터페이스로 동작한다. 앱 스토어 정책 변경으로 인한 앱 강제 업데이트·배포 중단, OS 버전 비호환, 또는 서버 측 API 장애 발생 시 농업인이 시스템을 전혀 제어할 수 없게 된다. 고령 농업인의 경우 스마트폰 분실·파손 시 대체 접근 수단이 없다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 웹 브라우저 기반 보조 관리 콘솔(반응형 Web UI) 병행 제공. 물리적 비상 제어 버튼(Local Override Switch)을 각 IoT 컨트롤러에 탑재하여 앱 없이도 현장 수동 조작 가능하도록 설계. 앱 API 서버에 대한 SLA 및 DR(재해복구) 계획 수립.

### 4. 환경센서 데이터 신뢰성 저하로 인한 오작동 자동화

* **설명:** 환경센서가 수집한 온도·습도·CO₂ 데이터를 기반으로 환기·관수 자동 제어가 수행될 경우, 센서 드리프트(calibration 오류), 물리적 오염(먼지·결로), 또는 통신 패킷 손실로 인해 부정확한 값이 컨트롤러에 전달될 수 있다. 이로 인해 불필요한 과잉 환기나 관수 중단 같은 오작동이 발생하고 작물 피해 및 에너지 낭비로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 동일 측정 항목에 대해 센서 이중화(Redundant Sensing) 적용 및 이상값 필터링(Moving Average, 3-Sigma 이상값 제거) 로직 구현. 센서 정기 캘리브레이션 스케줄링 기능을 운영 플랫폼에 내장. 임계값 초과 시 자동 제어 실행 전 농업인에게 알림 후 확인을 요구하는 Confirmation Gate 옵션 제공.

### 5. 다수 IoT 컨트롤러의 펌웨어 버전 파편화 및 유지보수 복잡성

* **설명:** 거적, 환기(측면), 환기(상단), 관수 등 4종 이상의 컨트롤러가 독립 운영되며, 향후 "추가 모듈" 확장이 명시되어 있다. 각 컨트롤러의 펌웨어 버전이 상이하게 유지될 경우, 버그 수정·기능 업데이트 배포 시 일부 컨트롤러만 업데이트되는 파편화가 발생한다. 구형 펌웨어 컨트롤러가 보안 취약점에 노출된 채 방치되거나, 앱-컨트롤러 간 API 비호환으로 제어 불능 상태가 될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 중앙화된 디바이스 관리 플랫폼(Device Management Platform) 도입으로 모든 컨트롤러의 펌웨어 버전 현황을 단일 대시보드에서 관리. 무선 OTA(Over-The-Air) 일괄 업데이트 기능 구현 및 롤백(Rollback) 메커니즘 필수 탑재. 컨트롤러-앱 간 API 버전 호환성을 Semantic Versioning으로 명세화하고 하위 호환성 정책 수립.

### 6. 농촌 네트워크 인프라 의존성으로 인한 원격 제어 불가

* **설명:** 스마트폰 앱을 통한 원격 제어는 농가 인터넷 회선(ISP)과 모바일 데이터 망에 동시에 의존한다. 농촌 지역 특성상 ISP 회선 장애, 정전, 또는 태풍·폭설 등 자연재해 시 인터넷 연결이 수 시간~수일 단절될 수 있다. 이 기간 동안 외부 원격 제어가 전혀 불가능하며, 긴급 상황(폭염 시 환기 제어)에 대응하지 못한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 엣지 레벨 자율 운영 로직(Edge Autonomy) 강화: 인터넷 단절 상황에서도 로컬 Wi-Fi 네트워크 내에서 스마트폰-컨트롤러 직접 통신(LAN 모드) 지원. 4G/LTE 백업 회선(USB 모뎀)을 무선공유기에 연결하는 이중화 회선 구성 검토. 주요 자동화 룰(온도 X℃ 초과 시 환기 개방 등)을 컨트롤러 로컬에 저장하여 클라우드 의존 없이 실행 가능하도록 설계.
