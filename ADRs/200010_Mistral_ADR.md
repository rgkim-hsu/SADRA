📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **다중 데이터 소스 통합을 위한 dataPARC 중심 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                                                                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서 MES, ERP, LIMS, Data Historian, MDE/Shift Logs, Excel/WIS 등 다양한 데이터 소스가 존재하며, 이들 간의 원활한 데이터 연동과 실시간 모니터링이 요구됨. 각 시스템은 SQL, API, OPC, 수동 입력 등 다양한 인터페이스를 통해 데이터를 제공하며, 통합 플랫폼 없이 각각의 시스템이 독립적으로 운영될 경우 데이터 일관성, 가시성, 분석 효율성이 저하됨.               |
| **결정(Decision)**       | **dataPARC**를 중심으로 모든 데이터 소스를 통합하는 허브 앤 스포크(Hub-and-Spoke) 아키텍처를 채택. dataPARC는 OPC 인터페이스를 통해 DCS, QCS, PLC 등 실시간 제어 시스템과 연결하며, SQL/API 인터페이스를 통해 MES, ERP, LIMS와 연결. 수동 데이터(MDE/Shift Logs)와 기타 소스(Excel, WIS)는 dataPARC의 데이터 수집 메커니즘을 통해 통합.            |
| **근거(Rationale)**      | dataPARC는 제조 현장(특히 반도체, 바이오, 스마트팜 등)에서 실시간 데이터 수집, 저장, 분석을 위한 플랫폼으로 입증된 솔루션. OPC UA/DA, SQL, API 등 다양한 프로토콜을 지원하여 이기종 시스템과의 연동이 용이하며, 데이터 히스토리안 기능을 통해 시간 축 데이터 저장 및 분석을 지원. 또한, OSIsoft, GE, AspenTech, Honeywell, Siemens, ABB 등 주요 공정 제어 시스템과 호환성 보장. |
| **결과(Consequences)**   | **장점**: 데이터 중앙집중화로 인한 일관성 향상, 실시간 모니터링 및 분석 가능, 시스템 간 연동 효율성 증가, 운영 비용 절감. **부정적 결과**: dataPARC에 대한 의존도 증가로 인한 단일 장애점(Single Point of Failure) 위험, 인터페이스 복잡성 증가로 인한 유지보수 비용 상승.                                                                          |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 통합된 데이터 뷰, 실시간 의사결정 지원, 시스템 확장성 향상. **감수해야 할 단점**: 초기 구축 비용 증가, dataPARC 플랫폼에 대한 전문성 요구, 인터페이스 관리 복잡성.                                                                                                                                        |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. **단일 장애점(Single Point of Failure) 발생**

* **설명:** dataPARC 서버 또는 핵심 모듈에 장애가 발생할 경우, 모든 데이터 수집 및 분석 기능이 중단되어 스마트팜 운영에 치명적 영향 미칠 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** dataPARC의 고가용성(HA) 구성(클러스터링, 이중화) 적용, 정기적인 장애 복구 테스트(DR Test) 수행, 백업 시스템 구축.

* * *

### 2. **데이터 인터페이스 호환성 문제**

* **설명:** 각 데이터 소스(MES, ERP, LIMS 등)에서 제공하는 SQL/API/OPC 인터페이스의 버전 또는 프로토콜 불일치로 인한 연동 실패 가능성.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 인터페이스 표준화 가이드라인 수립, 미들웨어(Middleware) 또는 어댑터(Adapter) 레이어 도입, 각 시스템과의 호환성 테스트 자동화.

* * *

### 3. **실시간 데이터 동기화 지연**

* **설명:** 대용량 데이터가 동시에 유입될 경우(dataPARC → Data Historian, MES, ERP 등), 네트워크 대역폭 부족 또는 dataPARC의 처리 지연으로 인해 실시간성이 저하될 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 네트워크 대역폭 확장, 데이터 스트리밍 최적화(예: Kafka, RabbitMQ 사용), dataPARC의 성능 튜닝(예: 인메모리 캐시 적용).

* * *

### 4. **보안 취약점 노출**

* **설명:** dataPARC를 통해 통합된 데이터가 외부 공격(예: SQL Injection, API Abuse, OPC Exploit)으로 노출될 경우, 스마트팜의 민감한 생산 데이터(예: 환경 설정, 수확량, 품질 데이터)가 유출될 위험.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 데이터 암호화(End-to-End), 인증/인가 강화(예: OAuth 2.0, MFA), 네트워크 세그먼테이션(DMZ 구성), 정기적인 보안 패치 및 침투 테스트 수행.

* * *

### 5. **수동 데이터 입력 오류**

* **설명:** MDE/Shift Logs와 같은 수동 데이터 입력이 dataPARC로 전달될 때, 인적 오류(예: 잘못된 값 입력, 누락)로 인해 데이터 품질 저하.
* **심각도:** 🟢 Low
* **발생 가능성:** 🔴 High
* **대응 방안:** 입력 유효성 검사(Validation) 자동화, 사용자 교육 강화, 오류 검출을 위한 AI 기반 이상 탐지 시스템 도입.

* * *

### 6. **스마트팜 도메인 특화 기능 부족**

* **설명:** dataPARC는 제조업(특히 반도체, 화학) 중심으로 설계되어 스마트팜의 특수 요구사항(예: 환경 센서 데이터, 작물 성장 모델링, 자동 관개 시스템 연동)을 충족하지 못할 가능성.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 커스텀 플러그인 또는 모듈 개발, 스마트팜 특화 데이터 모델링 도구(예: Agri-ERP 연동) 추가, 농업 IoT 표준(예: ISO 11783) 준수.
