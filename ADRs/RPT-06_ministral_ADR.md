## 📋 ADR (Architecture Decision Record)

### **ADR-001: 중앙 집중형 위치 기반 관로 정보 관리 시스템 구축 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **지하 관로(지진/재난 현장, 국가지원지방도, 시설물 관리)**의 위치 정보와 상태 데이터를 실시간으로 수집·통합하여 관리자(국가지원지방도 관리기관, 시설물 관리기관) 및 응급대응팀(119)에 제공해야 함. 기존 분산된 센서 데이터와 NFC/태깅 기반 수동 입력 데이터를 통합하여 **단일 플랫폼에서 관리**하고, **이용자별 접근 제어**와 **이상 감지 기능**을 지원해야 함. |
| **결정(Decision)** | 1. **중앙 서버 기반 아키텍처** 채택 (클라우드 또는 온프레미스 서버에서 위치 정보 통합 처리)
2. **NFC/태깅 기반 데이터 입력**과 **모바일 앱을 통한 실시간 정보 조회** 지원
3. **Web API 기반 정보 제공** (관리자용 대시보드, 119용 응급 정보 제공)
4. **이중화 및 백업 시스템** 도입 (데이터 유실 방지)
5. **OAuth 2.0 기반 접근 제어** (이용자별 권한 관리) |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준에 따라 **중앙 집중형 참조 아키텍처**를 채택하여 상호운용성을 보장
- **ITU-T X.1352** 보안 요구사항 준수 (데이터 암호화, 접근 통제)
- **oneM2M** 프레임워크에 따라 **API 기반 정보 공유**를 지원하여 다양한 클라이언트(모바일, 웹) 호환성 확보
- **ETSI EN 303 645** 준수하여 **사이버 보안 강화** (데이터 무결성, 인증/인가) |
| **결과(Consequences)** | ✅ **장점**: 중앙 관리로 데이터 일관성 및 실시간 모니터링 가능, 보안 강화, 다양한 클라이언트 지원
❌ **단점**: 중앙 서버 의존성 증가 (단일 장애점), 네트워크 latency 가능성, 초기 구축 비용 증가 |
| **트레이드오프(Trade-offs)** | - **중앙화 vs 분산화**: 중앙화로 관리 효율성 향상但 단일 장애점 리스크 존재 → **이중화 시스템**으로 대응
- **실시간성 vs 비용**: 실시간 처리 요구로 클라우드 서버 비용 증가 → **에지 컴퓨팅**과 조합하여 최적화 |

### **ADR-002: 모바일 앱 및 태깅 기반 데이터 입력 방식 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 현장 작업자(국가지원지방도 관리기관)가 **NFC 태그 스캔** 또는 **모바일 앱을 통해 관로 정보**를 입력/수정해야 함. 또한, **태깅 정보**를 통해 위치 기반 데이터 조회를 지원해야 함. |
| **결정(Decision)** | 1. **NFC 기반 자동 데이터 입력** (현장 센서와 연동)
2. **모바일 앱을 통한 수동 입력 및 태깅 정보 조회** (Android/iOS 지원)
3. **Offline-first 디자인** (네트워크 불량 시 데이터 로컬 저장 후 동기화)
4. **QR/Barcode 태깅 지원** (NFC 미지원 장치 호환성) |
| **근거(Rationale)** | - **ISO/IEC 27030:2020** 보안 가이드라인 준수 (데이터 암호화, 안전한 입력 처리)
- **IEEE 2413** 프레임워크에 따라 **모바일 클라이언트 아키텍처** 설계
- **Matter/OCF** 상호운용성 표준 준수 (다양한 IoT 디바이스 지원) |
| **결과(Consequences)** | ✅ **장점**: 현장 작업자 사용성 향상, 오프라인 지원으로 신뢰성 증가
❌ **단점**: 태깅 데이터 관리 복잡성, 앱 유지보수 비용 증가 |
| **트레이드오프(Trade-offs)** | - **NFC vs QR/Barcode**: NFC로 높은 보안성 but 하드웨어 의존성 → **QR/Barcode 지원**으로 호환성 확보
- **Offline-first vs 실시간 동기화**: 오프라인 지원으로 신뢰성 향상 but 동기화 로직 복잡성 증가 |

### **ADR-003: 데이터 저장 및 처리 방식 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 관로 정보(위치, 상태, 재난 데이터)는 **실시간 처리** 및 **장기 보관**이 필요함. 또한, **이상 감지** 기능(예: 지진/재난 시 자동 경보)을 지원해야 함. |
| **결정(Decision)** | 1. **NoSQL(MongoDB) + 관계형 DB(PostgreSQL) 하이브리드 저장소** 채택
   - NoSQL: 위치 기반 데이터(지리정보, 태깅 데이터)
   - 관계형 DB: 관리자 정보, 접근 로그
2. **실시간 스트리밍 처리** (Apache Kafka 사용)
3. **이상 감지 AI 모델** (Edge 및 서버에서 실행) |
| **근거(Rationale)** | - **ISO/IEC 30141:2024**에 따른 **데이터 모델링** 최적화
- **IETF CoAP/MQTT** 프로토콜 지원으로 **경량 통신** 가능
- **ETSI EN 303 645** 준수하여 **데이터 무결성** 보장 |
| **결과(Consequences)** | ✅ **장점**: 유연한 데이터 모델링, 실시간 처리 가능, AI 기반 이상 감지 지원
❌ **단점**: 하이브리드 DB 관리 복잡성, AI 모델 유지보수 비용 |
| **트레이드오프(Trade-offs)** | - **NoSQL vs 관계형 DB**: 유연성 vs 구조화된 쿼리 성능 → **하이브리드**로 최적화
- **서버-side vs Edge AI**: 중앙 처리로 정확성 향상 but latency 증가 → **Edge에서 사전 필터링**으로 대응 |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 서버 단일 장애점 (Single Point of Failure)**
- **설명**: 중앙 서버 장애 시 **전체 시스템 마비** 발생. 네트워크 장애나 사이버 공격 시 데이터 접근 불가.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이중화 서버** 및 **지리적 분산 배포** (예: 서울 + 부산 데이터 센터)
  - **자동 failover 메커니즘** 구현 (서버 장애 시 3초 이내 복구)
  - **백업 서버 주기적 동기화** (RPO/RTO 기준: 15분 이내 복구)

### **2. 데이터 보안 및 개인정보 유출 위험**
- **설명**: 관로 정보 및 관리자 데이터가 **사이버 공격** 또는 **내부 누출**로 노출될 가능성. 특히, **NFC/태깅 데이터**가 탈취되면 위·변조 가능.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **KISA 기준**에 따른 **데이터 암호화** (AES-256, TLS 1.3)
  - **OAuth 2.0 + JWT** 기반 **세분화된 접근 통제** (역할별 권한: 관리자/119/현장 작업자)
  - **정기 보안 감사** 및 **침입 탐지 시스템(IDS)** 배포
  - **ITU-T X.1352** 준수하여 **디바이스 인증** 강화

### **3. 네트워크 latency 및 오프라인 처리 실패**
- **설명**: **현장 환경**에서 네트워크 불량 시 모바일 앱 **오프라인 데이터 동기화 실패**로 정보 손실 발생. 실시간 응답 요구에 미달.
- **심각도**: 🟡 Medium | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **Offline-first 디자인** 강화 (데이터 로컬 저장 + 자동 동기화)
  - **Edge Computing** 도입 (현장 서버에서 사전 처리)
  - **MQTT 프로토콜** 사용 (경량 통신, 재연결 지원)
  - **네트워크 모니터링 도구** 배포 (latency 자동 감지 및 경고)

### **4. 다중 이용자 권한 관리 복잡성**
- **설명**: **관리자, 119, 현장 작업자** 등 다양한 이용자 그룹이 존재할 때 **권한 오류** 또는 **부적절한 접근** 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **RBAC(Role-Based Access Control)** 구현 (역할: 관리자/읽기전용/수정권한)
  - **정기 권한 감사** 및 **로그 추적** 시스템 도입
  - **Multi-Factor Authentication(MFA)** 강제 적용 (SMS + 하드웨어 토큰)

### **5. AI 기반 이상 감지 모델 오류**
- **설명**: **지진/재난 감지 AI 모델**이 **오 false positive/negative** 발생 시 **불필요한 경보** 또는 **재난 미감지**로 이어질 수 있음.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **인간 감독 시스템** 도입 (AI 경보 시 관리자 수동 확인)
  - **다중 모델 ensemble** (여러 AI 모델 투표 기반 결정)
  - **정기 모델 재학습** 및 **실제 데이터로 검증**
  - **ETSI EN 303 645** 준수하여 **모델 보안 검증**

### **6. 표준 호환성 문제**
- **설명**: **국내외 표준(ISO, ITU-T, oneM2M)**과의 호환성 미준수 시 **기존 시스템과의 연동 실패** 발생.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **oneM2M Core Platform** 연동 테스트 수행
  - **ISO/IEC 30141:2024** 준수 확인을 위한 **제3자 인증**
  - **API 버전 관리** (백워드 호환성 유지)

### **7. 유지보수 및 확장성 한계**
- **설명**: 시스템이 **확장될 때** (예: 새로운 센서 유형 추가) **아키텍처 수정 비용**이 증가할 수 있음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **Microservices 아키텍처** 채택 (모듈별 독립적 업데이트)
  - **Kubernetes** 기반 컨테이너화 (자동 스케일링 지원)
  - **TTA 표준** 준수하여 **모듈화 설계** 적용
