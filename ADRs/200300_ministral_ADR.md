## 📋 ADR (Architecture Decision Record)

### **ADR-001: OSHP(Optimal Smart Horticulture Platform) 기반 모듈러 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 **환경 제어, 영양 관리, 데이터 분석, 사용자 인터페이스** 등 다중 기능이 통합되어야 하며, **모듈화와 확장성**이 필수적이다. 또한 **국내외 IoT 표준(ISO/IEC 30141, oneM2M, Matter)**과의 호환성을 확보해야 한다. |
| **결정(Decision)** | 1. **모듈별 분리 아키텍처** 채택: 환경 제어, 영양 관리, UI/UX, 서버 개발을 독립적으로 설계하여 **재사용성과 유지보수성** 향상
2. **OSHP(Optimal Smart Horticulture Platform) 표준 기반**으로 시스템 통합: **TTA 표준**과 **ISO/IEC 30141**을 준수하여 **보안 및 상호운용성** 강화
3. **Edge Computing 기반 데이터 처리**: 센서 데이터는 **지능형 에지 노드**에서 전처리하여 **클라우드 서버 부하** 감소 및 **실시간 응답성** 확보
4. **MQTT/CoAP 프로토콜** 채택: **경량 통신**을 위한 표준 프로토콜 사용으로 **IoT 디바이스 간 효율적 데이터 전송** 보장 |
| **근거(Rationale)** | - **모듈화**: TTA의 스마트팜 표준과 ISO/IEC 30141이 **모듈별 설계**를 권장
- **OSHP 표준 준수**: 국내외 상호운용성 확보 및 **보안 인증(KC 등급)**을 위한 필수 조건
- **Edge Computing**: KISA가 권장하는 **IoT 보안 가이드라인(ISO/IEC 27030)**에 따라 **지역별 데이터 처리**로 네트워크 취약성 감소
- **MQTT/CoAP**: IETF 표준으로 **저전력 IoT 디바이스**에 최적화된 프로토콜 |
| **결과(Consequences)** | ✅ **장점**:
- **유연성**: 모듈별 업데이트 가능 → 신기술 적용 용이
- **보안성**: OSHP 표준 준수 → **KISA 인증** 가능
- **효율성**: 에지 처리 → **클라우드 비용 절감** 및 **실시간 모니터링** 가능
❌ **단점**:
- **초기 구축 비용**: 모듈별 개발 및 표준 준수에 따른 추가 비용 발생
- **복잡성**: 다중 프로토콜(OSHP, MQTT, CoAP) 통합 관리 필요 |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 통합**: 모듈화로 유연성 얻지만, 통합 관리가 복잡해짐
- **Edge vs. Cloud**: 에지 처리로 실시간성 향상하지만, 초기 하드웨어 비용 증가
- **표준 준수 vs. 커스터마이징**: 표준 준수로 보안성 얻지만, 일부 기능 커스터마이징이 제한될 수 있음 |

### **ADR-002: 사용자 인터페이스 및 웹/앱 개발 표준화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **농부, 연구자, 일반 사용자** 등 다채널 사용자를 지원해야 하며, **UI/UX 일관성**과 **접근성**이 필수적이다. 또한 **모바일 및 웹** 환경에서 동일 경험 제공이 요구된다. |
| **결정(Decision)** | 1. **TTA 스마트팜 UI 표준** 준수: **국내 표준화된 UI 패턴** 적용
2. **React.js + Flutter** 기반 크로스플랫폼 개발: **웹 및 모바일** 동시 개발 지원
3. **실시간 대시보드** 구현: **WebSocket**을 활용한 **생육 상태 실시간 업데이트**
4. **접근성 가이드라인(WCAG 2.1)** 준수: **장애인 포함성** 보장 |
| **근거(Rationale)** | - **TTA 표준**: 국내 스마트팜 시스템의 **일관된 사용자 경험**을 위한 필수 조건
- **크로스플랫폼**: React.js(웹) + Flutter(모바일)로 **개발 비용 절감** 및 **유지보수 용이성** 향상
- **WebSocket**: 실시간 데이터 전송을 위한 **최적화된 프로토콜** |
| **결과(Consequences)** | ✅ **장점**:
- **일관성**: 모든 채널에서 동일한 UI/UX 제공
- **확장성**: 새로운 디바이스 지원 용이
❌ **단점**:
- **성능 오버헤드**: WebSocket 및 크로스플랫폼 프레임워크로 인한 **메모리 사용량 증가** 가능 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 개발 효율성**: 크로스플랫폼으로 개발 효율성 향상하지만, 네이티브 앱보다 성능이 떨어질 수 있음
- **실시간성 vs. 복잡성**: WebSocket으로 실시간성 확보하지만, 서버 측 복잡성 증가 |

### **ADR-003: 데이터 관리 및 분석 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **대량의 센서 데이터**를 처리하여 **영양 관리, 생육 상태 분석**을 수행해야 하며, **데이터 보안**과 **가용성**이 critical하다. |
| **결정(Decision)** | 1. **Time-Series DB(InfluxDB)** 채택: **시계열 데이터** 효율적 저장 및 분석
2. **AI/ML 모델 통합**: **생육 상태 예측**을 위한 **TensorFlow Lite** 기반 에지 모델 배포
3. **데이터 암호화(ISO/IEC 27030 준수)**: **REST API 및 DB 레벨 암호화** 적용
4. **백업 및 복구 시스템**: **3-2-1 백업 규칙** (3개 복사본, 2개 미디어, 1개 오프사이트) 적용 |
| **근거(Rationale)** | - **InfluxDB**: IoT 시계열 데이터에 최적화된 DB
- **TensorFlow Lite**: 에지 디바이스에서 **저전력 AI 추론** 가능
- **ISO/IEC 27030**: KISA가 권장하는 **IoT 보안 가이드라인** |
| **결과(Consequences)** | ✅ **장점**:
- **분석 효율성**: 시계열 DB로 **고성능 쿼리** 가능
- **보안성**: 암호화 및 백업으로 **데이터 유실 방지**
❌ **단점**:
- **초기 설정 복잡성**: AI 모델 및 DB 튜닝에 시간 소요 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 보안**: 암호화로 성능 저하 가능성 존재
- **에지 AI vs. 클라우드**: 에지 모델로 저전력 처리 가능하지만, 클라우드보다 정확도가 떨어질 수 있음 |

## ⚠️ 잠재적 위험 분석

### **1. 표준 호환성 문제**
- **설명**: OSHP 및 TTA 표준이 **국내외 표준(ISO, oneM2M, Matter)**과 **완전 호환되지 않을 경우**, 시스템이 **글로벌 시장에서 배제**될 위험이 있다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **표준화 기관(TTA, KISA)과 협력**하여 **호환성 테스트** 수행
  - **Matter 및 oneM2M 프로토콜 지원**을 위한 **미들웨어 개발**

### **2. 센서 데이터 오류 및 노이즈**
- **설명**: **센서 이상**이나 **환경 노이즈**로 인해 **오류 데이터**가 발생하여 **영양 관리 및 생육 분석**에 영향을 줄 수 있다.
- **심각도**: 🔴 High | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **에지 노드에서 데이터 클리닝**을 위한 **AI 기반 이상치 검출 모델** 배포
  - **다중 센서 교차 검증** 시스템 구현 (예: 온도 + 습도 센서 상호 확인)

### **3. 보안 취약성 (IoT 디바이스 공격)**
- **설명**: **IoT 디바이스**가 **DDoS 공격**이나 **데이터 도난**의 대상이 될 경우, 시스템 **가용성 및 기밀성**이 위협받는다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **ETSI EN 303 645 준수**로 **디바이스 인증 및 암호화** 강화
  - **네트워크 세그먼테이션**을 통해 **디바이스 격리** 적용

### **4. 시스템 확장성 제한**
- **설명**: **모듈화 아키텍처**임에도 **클라우드 리소스 부족**이나 **네트워크 병목**으로 인해 **확장성**이 제한될 수 있다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **Kubernetes 기반 오토스케일링** 구현
  - **에지 노드 분산 처리**로 **클라우드 부하 분산**

### **5. 사용자 교육 및 채택 저항**
- **설명**: **농부 및 연구자**가 **신기술에 익숙하지 않아** 시스템 **채택 저항**이 발생할 수 있다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low
- **대응 방안**:
  - **TTA 표준화된 UI 가이드**를 기반으로 **간편한 튜토리얼** 제공
  - **현장 교육 프로그램**을 통해 **사용자 지원** 강화

| **트레이드오프(Trade-offs)** | - **성능 vs. 개발 효율성**: 크로스플랫폼으로 개발 효율성 향상하지만, 네이티브 앱보다 성능이 떨어질 수 있음
- **실시간성 vs. 복잡성**: WebSocket으로 실시간성 확보하지만, 서버 측 복잡성 증가 |

### **ADR-003: 데이터 관리 및 분석 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **대량의 센서 데이터**를 처리하여 **영양 관리, 생육 상태 분석**을 수행해야 하며, **데이터 보안**과 **가용성**이 critical하다. |
| **결정(Decision)** | 1. **Time-Series DB(InfluxDB)** 채택: **시계열 데이터** 효율적 저장 및 분석
2. **AI/ML 모델 통합**: **생육 상태 예측**을 위한 **TensorFlow Lite** 기반 에지 모델 배포
3. **데이터 암호화(ISO/IEC 27030 준수)**: **REST API 및 DB 레벨 암호화** 적용
4. **백업 및 복구 시스템**: **3-2-1 백업 규칙** (3개 복사본, 2개 미디어, 1개 오프사이트) 적용 |
| **근거(Rationale)** | - **InfluxDB**: IoT 시계열 데이터에 최적화된 DB
- **TensorFlow Lite**: 에지 디바이스에서 **저전력 AI 추론** 가능
- **ISO/IEC 27030**: KISA가 권장하는 **IoT 보안 가이드라인** |
| **결과(Consequences)** | ✅ **장점**:
- **분석 효율성**: 시계열 DB로 **고성능 쿼리** 가능
- **보안성**: 암호화 및 백업으로 **데이터 유실 방지**
❌ **단점**:
- **초기 설정 복잡성**: AI 모델 및 DB 튜닝에 시간 소요 |
| **트레이드오프(Trade-offs)** | - **성능 vs. 보안**: 암호화로 성능 저하 가능성 존재
- **에지 AI vs. 클라우드**: 에지 모델로 저전력 처리 가능하지만, 클라우드보다 정확도가 떨어질 수 있음 |
