## 📋 ADR (Architecture Decision Record)

### ADR-001: 다변수 통합 진단 모델 (Diagnostic Model with Multi-Variable Context) 적용

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 단순한 에러 카운트 (Error Count) 와 기초 진단 결과만으로는 농기계의 고장을 정확하게 예측하거나 원인 분석하기 어려울 수 있다. 특히 농기계는 온도, 습도, 부품 수명 등 다양한 외부 환경 요인의 영향을 받는다. 따라서 초기 데이터 분석을 넘어선 더 정밀한 진단이 필요하다. |
| **결정(Decision)** | 진단 모듈 (110) 내부에 '고장 여부 재판정부 (112)'를 도입하여, 기초 진단 결과 외에도 '환경적 요인', '부품의 부품 각각의 특징 관련 요인', '농기계 주행시의 추가 연료 소모량 발생 관련 요인' 등의 정보를 종합적으로 고려하여 최종 진단 결과를 도출하도록 한다. |
| **근거(Rationale)** | - **정확도 향상**: ISO/IEC 30141 및 IEEE 2413 등 IoT 시스템 아키텍처 표준에서 강조하는 맥락 기반 서비스 제공 (Context-aware Service) 의 원리에 부합한다.<br>- **가변성 대응**: 농작업 환경은 날씨, 지형, 기계 노후화 등으로 변동성이 크기 때문에 고정된 규칙이나 단순 카운트만으로 한계가 있다.<br>- **시스템 안정성**: 사용자가 단말 (300) 에 잘못된 정보를 제공하여 사용자를 혼란에 빠뜨리는 것을 방지한다. |
| **결과(Consequences)** | **긍정적**: 농기계 고장의 정확도 향상, 예방 유지보수 주기 최적화, 농작업 중단 시간 최소화.<br>**부정적**: 진단 모듈의 복잡도 증가, 다양한 데이터 수집 및 연동 비용 상승, 알고리즘 업데이트 필요성 증가. |
| **트레이드오프(Trade-offs)** | 단순하고 빠른 '기초 진단' 과 정밀하고 느린 '최종 진단' 간의 균형 필요. 복잡성 증가를 감수하면서도 시스템의 신뢰성을 확보해야 하는 선택. |

### ADR-002: 진단 및 제어의 분리 및 협업 아키텍처 설계

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 농기계 (200) 는 진단 데이터를 보내고, 제어 명령을 받아서 작동해야 한다. 하지만 진단과 제어가 완전히 독립적이게 되면 신속한 대응이 어렵다. 반면 진단 모듈이 직접 제어까지 담당하면 진단 알고리즘의 안정성 확보가 어렵다. |
| **결정(Decision)** | '진단 모듈 (110)'은 진단 알고리즘과 데이터 처리에만 집중하고, '제어 모듈 (120)'은 별도의 프로세스나 모듈로 분리되어 최종 진단 결과에 기반하여 농기계에 대한 제어 명령을 생성하도록 한다. 하지만 진단 모듈에서 직접 진단 결과를 생성할 수 있는 경로도 제공하여 시스템의 유연성을 확보한다. |
| **근거(Rationale)** | - **가용성 (Availability)**: 진단 로직 오작동이 발생해도 제어 기능을 독립적으로 유지할 수 있다.<br>- **보안성 (Security)**: 진단 모듈의 권한은 진단에만 국한하고, 제어 명령 생성은 별도의 제어 모듈이 수행하여 권한 분리 (Separation of Duty) 를 구현.<br>- **확장성**: 향후 진단 엔진을更换 시 제어 로직의 수정 없이 진단 모듈만 교체 가능. |
| **결과(Consequences)** | **긍정적**: 시스템의 내결함성 강화, 보안 위험도 감소, 모듈별 독립적인 개발 및 배포 용이.<br>**부정적**: 모듈 간 통신 오버헤드 증가, 동기화 문제 발생할 수 있음. |
| **트레이드오프(Trade-offs)** | 통신 지연 시간 증가를 감수해야 하지만 시스템의 견고함과 보안성을 확보하는 대신. |

## ⚠️ 잠재적 위험 분석

### 1. 📊 데이터 무결성 및 전송 지연 위험
- **설명**: 농기계 (200) 에서 에러 카운트 데이터를 진단 모듈 (110) 로 전송하는 과정에서 네트워크 불안정이나 간섭으로 인해 데이터 지연이나 손실이 발생할 경우, 진단 모듈이 과거의 상황을 바탕으로 진단하여 실제 현재 상태와 다른 결과(거짓阴性 또는 거짓阳性) 를 출력할 수 있습니다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**: 데이터 전송 프로토콜 (예: MQTT) 에 QoS(Quality of Service) 를 적용하여 데이터 손실 방지 및 재전송 메커니즘 도입. 핵심 데이터는 에지 노드에서 로컬로도暂存하도록 설계.

### 2. 🌦️ 외부 환경 변수 데이터 누락 위험
- **설명**: 최종 진단 결과 도출에 '환경적 요인'이나 '농기계 주행시의 추가 연료 소모량' 데이터가 중요하나, 해당 데이터가 실시간으로 수집되지 않거나 센서 정합 (Calibration) 이 제대로 되지 않은 경우, 진단 모듈 (110) 이 잘못된 요소를 판단하게 됩니다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**: 환경 센서 데이터의 정규화 표준 준수 (ISO/IEC 30141 참조). 진단 모듈 내부에서 데이터가 누락된 경우 기본값 또는 이전 데이터로 대체하는 로직 구현 및 로그 기록.

### 3. 🔒 보안 취약점 (API 또는 통신 계층)
- **설명**: 농기계 (200) 와 진단 모듈 (110), 사용자 단말 (300) 간 통신 과정에서 인증되지 않은 요청이 들어오거나, 제어 모듈 (120) 을 통한 제어 신호가 무단으로 조작될 경우 농기계가 원격으로 조작될 수 있습니다.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**: ITU-T X.1352 및 ETSI EN 303 645 기준에 따라 통신 암호화 (TLS/SSL) 적용. 제어 모듈의 권한 접근 로그 실시간 모니터링 및 비정상 접근 시 자동 차단.

### 4. 🧠 알고리즘 편향 및 일반화 불가
- **설명**: 진단 모듈 (110) 이 학습하거나 규칙 기반을 적용할 때 특정 부품이나 특정 환경 (예: 특정 농기계 모델, 특정 기후) 에만 최적화되어 있다면, 다른 조건에서 고장 징후를 놓치거나 오히려 오류를 일으킬 수 있습니다.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟠 High (장기적)
- **대응 방안**: 진단 모듈 알고리즘의 정기적 검증 및 테스트. 다양한 환경 데이터셋 (Stress Test) 을 포함하여 훈련. 모델 버전 관리 및 A/B 테스트를 통한 안정성 확인.

### 5. 🛠️ 단일 지점 장애 (Single Point of Failure)
- **설명**: 진단 모듈 (110) 또는 제어 모듈 (120) 등 핵심 컴포넌트 (1xx) 가 고장 나거나 전원 공급이 중단되면, 농기계 (200) 의 상태를 파악할 수 없거나 제어를 할 수 없는 상황 (시스템 다운) 이 발생할 수 있습니다.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**: 핵심 모듈 (110, 112, 120) 에 대한 중복 설계 (Redundancy) 또는 클러스터링 고려. 제어 모듈 (120) 은 진단 모듈과 물리적/논리적 분리를 통해 독립적인 실행 가능하도록 설계 (Fail-safe 설계).
