🏗️ 아키텍처 분석 보고서

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 중앙 집중형 모니터링 서버를 허브로 하는 다중 액터 이벤트 기반 시퀀스 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 사료 잔량 감시 장치(10)는 원격 센서부(120)와 제어부(140)로 구성되며, 사료 공급기(30), 사료 잔량 모니터링 서버(20), 관리자 단말(40)이라는 이질적인 4개 액터가 장치 등록, 관리지침 수수, 빈 급이기통 측정, 사료 잔량 측정, 결과 분석·활용이라는 복잡한 시퀀스를 수행해야 한다. 각 액터 간 메시지 순서와 상태 일관성을 보장하면서도 현장 IoT 장치의 네트워크 불안정성을 극복하는 것이 핵심 아키텍처 과제다.                                                      |
| **결정(Decision)**       | 사료 잔량 모니터링 서버(20)를 중앙 허브로 두고, 모든 주요 이벤트(장치등록 S200~S204, 관리지침 전달 S210~S216, 빈 급이기통 측정 S220~S234, 사료 잔량 측정 S250~S295)가 서버를 경유하는 Star Topology 기반 이벤트 브로커 구조를 채택한다. 제어부(140)는 명령 발행자(Command Issuer), 원격 센서부(120)는 실행자(Executor), 서버(20)는 상태 수집·분석·저장의 책임을 전담한다.                                           |
| **근거(Rationale)**      | 현장 IoT 기기(원격 센서부·사료 공급기)는 처리 능력과 저장 용량이 제한적이므로, 복잡한 비즈니스 로직(사료 공급 정보 갱신 S275, 측정결과 분석·활용 S290)을 서버로 집중시키는 것이 현실적이다. 관리자 단말(40)이 관리지침 변경(S240)을 서버(20)를 통해 제어부(140)에 전파하는 구조는 지침의 단일 진실 공급원(Single Source of Truth)을 보장한다. 또한 서버가 빈 급이기통 측정 결과(S234)와 사료 잔량 측정 결과(S285)를 통합 수집함으로써 교차 분석 및 이력 관리가 가능해진다. |
| **결과(Consequences)**   | 긍정적: 모든 측정 이력의 중앙 집중 관리로 감사 추적 및 데이터 분석 용이, 관리자 단말이 단일 엔드포인트(서버)만 관리하면 되는 운영 단순화, 장치별 독립적 펌웨어 업데이트 가능. 부정적: 모니터링 서버(20)가 SPOF(단일 장애점)가 되어 서버 장애 시 전체 시스템 마비, 서버 경유로 인한 메시지 레이턴시 증가, 서버 처리 용량이 연결 장치 수에 비례하여 확장 필요.                                                                                      |
| **트레이드오프(Trade-offs)** | 얻는 장점: 데이터 일관성 보장 용이, 중앙 모니터링·알람 체계 구축 간편, 관리지침 변경의 즉각적 전파 가능(S245). 감수할 단점: 서버 가용성에 전체 시스템 의존, 대규모 농장 확장 시 서버 수평 확장 전략 별도 설계 필요, 엣지 컴퓨팅 활용도 저하로 인한 실시간 대응 지연 가능성.                                                                                                                                      |

⚠️ 잠재적 위험 분석
------------

### 1. 모니터링 서버(20) 단일 장애점으로 인한 전체 서비스 중단

* **설명:** S200 장치 등록부터 S295 사료 잔량 결과 열람까지 모든 주요 시퀀스가 모니터링 서버(20)를 경유한다. 서버 장애·점검·네트워크 단절 시 제어부(140)의 관리지침 수신(S216), 사료 공급기(30)의 공급 정보 갱신(S275), 관리자 단말(40)의 결과 열람(S295)이 동시에 불가능해져 가축 사료 공급에 직접적 차질이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Active 또는 Active-Standby 이중화 서버 구성, 제어부(140)에 마지막 수신 관리지침을 로컬 캐시(S216 관리지침 저장 기능 활용)하여 서버 단절 시 자율 운영 모드 전환, 서버 헬스체크 및 자동 페일오버(Failover) 메커니즘 구현.

### 2. 원격 센서부(120)와 제어부(140) 간 측정 명령·완료 신호 유실

* **설명:** 빈 급이기통 측정(S225 명령 → S230 완료) 및 사료 잔량 측정(S255 명령 → S260 완료) 과정에서 현장 무선 네트워크 불안정으로 명령 또는 완료 신호가 유실될 경우, 제어부(140)는 측정 완료를 인지하지 못한 채 이후 시퀀스(S232 결과 취득, S265 결과 취득)를 실행하거나 무한 대기 상태에 빠질 수 있다. 측정 결과 없이 사료 공급 정보가 갱신(S275)되면 실제 사료 잔량과 시스템 데이터 간 불일치가 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 측정 명령에 타임아웃 및 재시도(Retry) 로직 적용, 멱등성(Idempotency) 보장을 위한 측정 요청 고유 ID 부여, 측정 완료 신호에 대한 ACK 기반 확인 프로토콜 구현, 측정 미완료 시 관리자 단말(40)로 알림 발송.

### 3. 관리지침 변경(S240~S245) 미동기화로 인한 부적절한 사료 공급

* **설명:** 관리자 단말(40)에서 관리지침 변경(S240)이 발생하면 모니터링 서버(20)를 거쳐 제어부(140)로 전파(S245)되어야 한다. 전파 지연 또는 실패 시 구버전 지침으로 사료가 공급되며, 특히 수의사 처방에 따른 사료량 긴급 변경이나 계절별 급이 조정이 현장에 반영되지 않으면 가축 건강에 직접적 피해가 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 관리지침 변경 시 버전 관리(Version Numbering) 적용 및 제어부(140)의 현재 지침 버전을 서버가 주기적으로 확인하는 폴링 메커니즘 병행, 지침 변경 전파 성공 여부를 관리자 단말(40)에 실시간 확인 메시지로 피드백, 미전파 시 재전송 및 관리자 알림 자동화.

### 4. 사료 잔량 측정 데이터 위·변조 및 무단 접근

* **설명:** 원격 센서부(120)에서 제어부(140)로 전달되는 사료 잔량 측정 결과(S260~S265), 서버로 전달되는 측정 결과(S280~S285), 관리자 단말(40)의 결과 열람(S295) 구간 모두에서 통신 패킷이 암호화되지 않을 경우 중간자 공격(MITM)에 의한 데이터 위·변조가 가능하다. 또한 장치 등록(S200~S204) 과정에서 인증이 취약하면 비인가 장치가 시스템에 등록되어 허위 측정값을 주입할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 전 구간 TLS/DTLS 암호화 적용(IoT 환경 고려 시 DTLS 우선), 장치 등록(S200) 시 디바이스 인증서 기반 상호 인증(Mutual TLS) 구현, 측정 데이터에 디지털 서명 또는 HMAC 적용으로 무결성 검증, 관리자 단말(40) 접근에 MFA(다중 인증) 적용.

### 5. 사료 공급기(30) 공급 정보 갱신(S275) 실패로 인한 과공급·과소공급

* **설명:** 사료 잔량 측정 결과 처리(S270) 후 사료 공급기(30)로의 공급 정보 갱신(S275)이 실패하거나 지연될 경우, 공급기는 이전 기준으로 사료를 공급하게 된다. 측정 결과상 사료가 부족함에도 공급 명령이 전달되지 않으면 가축이 굶는 상황이, 반대로 충분함에도 갱신이 실패하면 과잉 공급으로 인한 사료 낭비 및 비용 손실이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** S275 갱신 요청에 대한 사료 공급기(30)의 응답 확인(ACK) 필수화 및 미응답 시 재전송 로직 구현, 공급기 자체에 마지막 수신 공급 기준값 로컬 저장으로 통신 단절 시 안전 모드 운영, 갱신 실패 이벤트를 모니터링 서버(20)가 감지하여 관리자 단말(40)에 즉시 알림 발송.

### 6. 대규모 장치 동시 측정 요청 시 서버 처리 과부하

* **설명:** 대형 축산 농장에서 수십~수백 개의 사료 잔량 감시 장치(10)가 동일 시간대(예: 새벽 급이 전 일괄 점검)에 빈 급이기통 측정(S220~S234) 및 사료 잔량 측정(S250~S285) 결과를 동시에 모니터링 서버(20)로 전송하면, 서버의 동시 처리 한계를 초과하여 응답 지연 또는 데이터 유실이 발생할 수 있다.

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 메시지 큐(MQTT Broker 또는 Kafka)를 서버 전단에 배치하여 측정 결과 수신 버퍼링 처리, 장치별 측정 스케줄을 시간 분산(Jitter) 적용으로 동시 집중 방지, 서버 수평 확장(Scale-out) 및 부하 분산(Load Balancer) 구성, 처리량 기반 자동 스케일링 정책 수립.
