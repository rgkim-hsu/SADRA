### ADR-001: 명령(Command) 생명주기 기반 상태 머신(State Machine) 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 관수, 환기, 조명 등 다수의 액추에이터 제어 명령이 동시다발적으로 발생하며, 각 명령은 자동제어(Auto Control), 센서 트리거(A-Sensor), 수동 중단(Stop Command) 등 다양한 외부 이벤트에 의해 중단되거나 종료될 수 있다. 명령의 현재 상태를 추적하지 않으면 명령 충돌, 중복 실행, 미완료 명령 잔류 등의 문제가 발생한다. |
| **결정(Decision)**       | 모든 제어 명령에 대해 NEW → WAITING → SENT → WORKING → (STOPPING/FINISHED) 단계의 명시적 상태 머신을 적용하고, 각 전이(Transition) 조건을 이벤트 유형(Auto Control, New Command, A-Sensor, Stop Command)별로 분기하여 관리한다.                               |
| **근거(Rationale)**      | 상태 머신은 명령의 현재 위치를 항상 단일 진실 공급원(Single Source of Truth)으로 유지하며, 비정상 전이를 원천 차단한다. 스마트팜의 실시간 제어 요구사항과 다중 종료 경로(IGNORED, FINISHED, STOPPING 계열)를 명확히 모델링할 수 있다.                                                      |
| **결과(Consequences)**   | 긍정: 명령 충돌 방지, 감사 추적(Audit Trail) 용이, 장애 발생 시 정확한 상태 복구 가능. 부정: 상태 수가 증가할수록 전이 로직의 복잡도가 증가하며, 상태 저장소(DB/메모리)에 대한 의존성이 생긴다.                                                                                        |
| **트레이드오프(Trade-offs)** | 얻는 것: 예측 가능한 명령 실행 흐름, 디버깅 용이성, 운영자 모니터링 지원. 감수할 것: 상태 전이 로직 유지보수 비용 증가, 분산 환경에서의 상태 동기화 오버헤드.                                                                                                                   |

### ADR-002: 명령 무시(IGNORED) 경로의 조기 분기 처리 설계

| 항목                     | 내용                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | WAITING 또는 SENT 단계에서 자동제어 시스템이 새로운 정책을 적용하거나 후속 명령이 도착할 경우, 기존 명령을 계속 실행하면 작물 피해나 장치 충돌이 발생할 수 있다. 이 시점에서의 명령 폐기 처리가 명확히 정의되어야 한다.                                                   |
| **결정(Decision)**       | WAITING 상태에서 Auto Control 이벤트 수신 시 IGNORED BY AUTO CONTROL로, New Command 수신 시 IGNORED BY NEW COMMAND로 즉시 전이하여 해당 명령을 종료 처리한다. SENT 이후 단계에서는 IGNORED 경로 대신 STOPPING 경로를 통해 안전하게 종료한다. |
| **근거(Rationale)**      | 이미 장치에 전송(SENT)된 명령은 물리적 액추에이터가 동작 중일 수 있으므로 강제 종료 대신 STOPPING 중간 상태를 두어 안전 정지 절차를 보장한다. WAITING 단계는 아직 장치에 전달되지 않았으므로 즉시 폐기가 안전하다.                                                  |
| **결과(Consequences)**   | 긍정: 명령 우선순위 충돌 시 시스템 보호, 액추에이터 과부하 방지. 부정: IGNORED 처리된 명령에 대한 원인 분석 로깅이 없으면 운영자가 명령 누락을 인지하지 못할 수 있다.                                                                                |
| **트레이드오프(Trade-offs)** | 얻는 것: 시스템 안전성 및 자원 보호. 감수할 것: 폐기된 명령에 대한 재시도 정책 부재 시 제어 누락 발생 가능성.                                                                                                                   |

### ADR-003: 이중 종료 경로(A-Sensor / Stop Command) 기반 STOPPING 중간 상태 도입

| 항목                     | 내용                                                                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | WORKING 중인 명령은 센서값 도달(A-Sensor)이나 운영자의 수동 중단(Stop Command) 두 가지 경로로 종료될 수 있다. 종료 원인을 구분하지 않으면 사후 분석 및 자동화 재학습에 필요한 데이터가 손실된다.                                           |
| **결정(Decision)**       | WORKING에서 종료 이벤트 발생 시 STOPPING BY A-SENSOR 또는 STOPPING BY STOP COMMAND 중간 상태를 경유하여 각각 FINISHED BY A-SENSOR, FINISHED BY STOP COMMAND, FINISHED NORMALLY로 전이하는 구조를 채택한다. |
| **근거(Rationale)**      | 중간 STOPPING 상태는 액추에이터의 안전 정지 시퀀스(예: 펌프 잔압 해소, 밸브 닫힘 확인)를 수행할 시간을 확보하며, 종료 원인별 데이터 분류를 통해 Farm-as-a-Service의 분석 고도화를 지원한다.                                               |
| **결과(Consequences)**   | 긍정: 종료 원인 추적성 확보, 안전 정지 절차 보장, 운영 데이터 품질 향상. 부정: STOPPING 상태에서 장애 발생 시 명령이 영구적으로 해당 상태에 머무는 Dead State 위험 존재.                                                           |
| **트레이드오프(Trade-offs)** | 얻는 것: 운영 데이터 품질 및 안전성. 감수할 것: 상태 전이 타임아웃 관리 로직 추가 구현 필요.                                                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. Dead State — STOPPING 상태 교착(Deadlock)

* **설명:** STOPPING BY A-SENSOR 또는 STOPPING BY STOP COMMAND 상태에서 네트워크 단절, 장치 응답 불능, 또는 소프트웨어 예외로 인해 FINISHED 상태로 전이되지 못하고 해당 상태에 영구 잔류하는 시나리오. 이 경우 동일 장치에 대한 후속 명령이 차단되어 작물 관리 공백이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 각 STOPPING 상태에 최대 체류 시간(TTL, Time-To-Live) 타임아웃을 설정하고, 초과 시 강제로 FINISHED(ERROR) 상태로 전이하는 Watchdog 스레드를 구현한다. 또한 Dead State 감지 시 운영자에게 즉시 알림을 발송하는 모니터링 파이프라인을 구축한다.

### 2. 명령 유실 — WAITING 큐 오버플로우

* **설명:** 다수의 센서 이벤트나 스케줄러가 동시에 명령을 생성할 경우 WAITING 상태의 명령이 급격히 누적되고, 시스템 재시작이나 메모리 부족 시 큐에 적재된 명령이 일괄 유실될 수 있다. 특히 스마트팜의 일출·일몰 시간대에 조명, 환기, 관수 명령이 동시에 발생하는 경우 집중된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** WAITING 큐를 인메모리 구조 대신 Kafka, RabbitMQ 등 내구성 있는 메시지 브로커로 외재화하여 명령의 영속성을 보장한다. 큐 깊이(Queue Depth) 임계값 모니터링과 백프레셔(Backpressure) 정책을 적용한다.

### 3. 보안 위협 — 비인가 Stop Command 주입

* **설명:** WORKING 중인 명령에 대해 외부 공격자 또는 내부 권한 없는 사용자가 임의로 STOP COMMAND를 전송할 경우, 진행 중인 관수·가온 작업이 부적절하게 중단되어 작물 피해가 발생할 수 있다. IoT 환경의 특성상 MQTT 등 경량 프로토콜을 사용할 경우 인증 우회 가능성이 높다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 명령 전이 요청에 대해 역할 기반 접근 제어(RBAC)를 적용하고, Stop Command는 서명된 토큰(JWT 또는 mTLS) 기반 인증을 필수화한다. 명령 발신자 정보를 상태 로그에 기록하여 감사 추적을 보장한다.

### 4. 센서 오작동 — A-Sensor 오탐에 의한 조기 종료

* **설명:** 온도·습도·토양수분 센서의 고장, 노이즈, 또는 캘리브레이션 오차로 인해 A-Sensor가 목표값 도달을 잘못 감지하면, WORKING 명령이 실제 작업 완료 전에 STOPPING BY A-SENSOR로 조기 전이된다. 이 경우 관수 부족, 가온 미달 등 작물 생육 환경이 목표치에 도달하지 못한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 단일 센서값이 아닌 복수 센서의 앙상블 판정(다수결 또는 평균값 기반)을 통해 A-Sensor 이벤트를 발생시키는 센서 퓨전 로직을 도입한다. 센서값 이상 탐지(Anomaly Detection) 모듈을 별도 구성하여 오탐 필터링을 수행한다.

### 5. 운영 위험 — IGNORED 명령 무음 폐기에 의한 제어 누락

* **설명:** WAITING 단계에서 Auto Control 또는 New Command에 의해 IGNORED 처리된 명령이 운영자에게 통보되지 않을 경우, 관리자는 명령이 정상 실행된 것으로 오인할 수 있다. 이로 인해 특정 구역의 관수 또는 환기 작업이 반복적으로 누락되어도 인지하지 못하는 운영 공백이 발생한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** IGNORED BY AUTO CONTROL 및 IGNORED BY NEW COMMAND 전이 발생 시 반드시 이벤트 로그를 기록하고, 일정 시간 내 동일 장치·동일 유형 명령의 IGNORED 빈도가 임계값을 초과할 경우 운영자 알림 및 자동 재스케줄링 정책을 적용한다.

### 6. 분산 환경 위험 — 상태 불일치(State Inconsistency)

* **설명:** 클라우드 기반 Farm-as-a-Service 환경에서 서버 인스턴스가 다중화(Scale-out)된 경우, 동일 명령의 상태가 서로 다른 인스턴스에서 상이하게 관리될 수 있다. 예를 들어 인스턴스 A는 명령을 WORKING으로, 인스턴스 B는 SENT로 인식하여 중복 전송이 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 명령 상태를 각 인스턴스의 로컬 메모리가 아닌 Redis 또는 분산 데이터베이스(PostgreSQL with row-level locking)에 단일 원본으로 저장하고, 상태 전이 시 낙관적 잠금(Optimistic Locking) 또는 분산 락(Distributed Lock)을 적용하여 동시성 충돌을 방지한다.

| **상황(Context)**        | WORKING 중인 명령은 센서값 도달(A-Sensor)이나 운영자의 수동 중단(Stop Command) 두 가지 경로로 종료될 수 있다. 종료 원인을 구분하지 않으면 사후 분석 및 자동화 재학습에 필요한 데이터가 손실된다.                                           |
| **결정(Decision)**       | WORKING에서 종료 이벤트 발생 시 STOPPING BY A-SENSOR 또는 STOPPING BY STOP COMMAND 중간 상태를 경유하여 각각 FINISHED BY A-SENSOR, FINISHED BY STOP COMMAND, FINISHED NORMALLY로 전이하는 구조를 채택한다. |
| **근거(Rationale)**      | 중간 STOPPING 상태는 액추에이터의 안전 정지 시퀀스(예: 펌프 잔압 해소, 밸브 닫힘 확인)를 수행할 시간을 확보하며, 종료 원인별 데이터 분류를 통해 Farm-as-a-Service의 분석 고도화를 지원한다.                                               |
| **결과(Consequences)**   | 긍정: 종료 원인 추적성 확보, 안전 정지 절차 보장, 운영 데이터 품질 향상. 부정: STOPPING 상태에서 장애 발생 시 명령이 영구적으로 해당 상태에 머무는 Dead State 위험 존재.                                                           |
| **트레이드오프(Trade-offs)** | 얻는 것: 운영 데이터 품질 및 안전성. 감수할 것: 상태 전이 타임아웃 관리 로직 추가 구현 필요.                                                                                                                |

⚠️ 잠재적 위험 분석
------------

### 1. Dead State — STOPPING 상태 교착(Deadlock)

* **설명:** STOPPING BY A-SENSOR 또는 STOPPING BY STOP COMMAND 상태에서 네트워크 단절, 장치 응답 불능, 또는 소프트웨어 예외로 인해 FINISHED 상태로 전이되지 못하고 해당 상태에 영구 잔류하는 시나리오. 이 경우 동일 장치에 대한 후속 명령이 차단되어 작물 관리 공백이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 각 STOPPING 상태에 최대 체류 시간(TTL, Time-To-Live) 타임아웃을 설정하고, 초과 시 강제로 FINISHED(ERROR) 상태로 전이하는 Watchdog 스레드를 구현한다. 또한 Dead State 감지 시 운영자에게 즉시 알림을 발송하는 모니터링 파이프라인을 구축한다.

### 2. 명령 유실 — WAITING 큐 오버플로우

* **설명:** 다수의 센서 이벤트나 스케줄러가 동시에 명령을 생성할 경우 WAITING 상태의 명령이 급격히 누적되고, 시스템 재시작이나 메모리 부족 시 큐에 적재된 명령이 일괄 유실될 수 있다. 특히 스마트팜의 일출·일몰 시간대에 조명, 환기, 관수 명령이 동시에 발생하는 경우 집중된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** WAITING 큐를 인메모리 구조 대신 Kafka, RabbitMQ 등 내구성 있는 메시지 브로커로 외재화하여 명령의 영속성을 보장한다. 큐 깊이(Queue Depth) 임계값 모니터링과 백프레셔(Backpressure) 정책을 적용한다.

### 3. 보안 위협 — 비인가 Stop Command 주입

* **설명:** WORKING 중인 명령에 대해 외부 공격자 또는 내부 권한 없는 사용자가 임의로 STOP COMMAND를 전송할 경우, 진행 중인 관수·가온 작업이 부적절하게 중단되어 작물 피해가 발생할 수 있다. IoT 환경의 특성상 MQTT 등 경량 프로토콜을 사용할 경우 인증 우회 가능성이 높다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 명령 전이 요청에 대해 역할 기반 접근 제어(RBAC)를 적용하고, Stop Command는 서명된 토큰(JWT 또는 mTLS) 기반 인증을 필수화한다. 명령 발신자 정보를 상태 로그에 기록하여 감사 추적을 보장한다.

### 4. 센서 오작동 — A-Sensor 오탐에 의한 조기 종료

* **설명:** 온도·습도·토양수분 센서의 고장, 노이즈, 또는 캘리브레이션 오차로 인해 A-Sensor가 목표값 도달을 잘못 감지하면, WORKING 명령이 실제 작업 완료 전에 STOPPING BY A-SENSOR로 조기 전이된다. 이 경우 관수 부족, 가온 미달 등 작물 생육 환경이 목표치에 도달하지 못한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 단일 센서값이 아닌 복수 센서의 앙상블 판정(다수결 또는 평균값 기반)을 통해 A-Sensor 이벤트를 발생시키는 센서 퓨전 로직을 도입한다. 센서값 이상 탐지(Anomaly Detection) 모듈을 별도 구성하여 오탐 필터링을 수행한다.

### 5. 운영 위험 — IGNORED 명령 무음 폐기에 의한 제어 누락

* **설명:** WAITING 단계에서 Auto Control 또는 New Command에 의해 IGNORED 처리된 명령이 운영자에게 통보되지 않을 경우, 관리자는 명령이 정상 실행된 것으로 오인할 수 있다. 이로 인해 특정 구역의 관수 또는 환기 작업이 반복적으로 누락되어도 인지하지 못하는 운영 공백이 발생한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** IGNORED BY AUTO CONTROL 및 IGNORED BY NEW COMMAND 전이 발생 시 반드시 이벤트 로그를 기록하고, 일정 시간 내 동일 장치·동일 유형 명령의 IGNORED 빈도가 임계값을 초과할 경우 운영자 알림 및 자동 재스케줄링 정책을 적용한다.

### 6. 분산 환경 위험 — 상태 불일치(State Inconsistency)

* **설명:** 클라우드 기반 Farm-as-a-Service 환경에서 서버 인스턴스가 다중화(Scale-out)된 경우, 동일 명령의 상태가 서로 다른 인스턴스에서 상이하게 관리될 수 있다. 예를 들어 인스턴스 A는 명령을 WORKING으로, 인스턴스 B는 SENT로 인식하여 중복 전송이 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 명령 상태를 각 인스턴스의 로컬 메모리가 아닌 Redis 또는 분산 데이터베이스(PostgreSQL with row-level locking)에 단일 원본으로 저장하고, 상태 전이 시 낙관적 잠금(Optimistic Locking) 또는 분산 락(Distributed Lock)을 적용하여 동시성 충돌을 방지한다.
