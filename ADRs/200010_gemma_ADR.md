# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 데이터 통합을 위한 스트리밍 기반의 디커플링 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 MES, ERP, LIMS, Historian, 그리고 레거시 OT 시스템(PLC, DCS) 등 근본적으로 이질적이고 상이한 프로토콜(SQL, API, OPC, Fieldbus 등)을 사용하는 다양한 지점의 데이터를 수집하고 통합해야 하는 상황에 놓여 있습니다. 데이터 소스(Sources)의 수와 다양성, 그리고 데이터의 실시간성(Velocity) 요구가 높아 전통적인 ETL/바스(Bus) 방식으로는 확장성(Scalability)과 복원력(Resilience)을 보장하기 어렵습니다. |
| **결정(Decision)** | 데이터 통합의 핵심 계층을 **스트리밍 메시징 아키텍처(Streaming Messaging Architecture)** 기반의 데이터 메시(Data Mesh) 형태로 설계하고, 시스템의 경계 지점(Edge/Protocol Gateway)에 물리적/논리적 분리층을 도입합니다. 모든 원천 데이터는 비동기 메시지 큐(Message Queue)를 통해 중앙 통합 플랫폼(dataPARC)으로 흐르게 합니다. |
| **근거(Rationale)** | 1. **디커플링(Decoupling):** 메시지 큐를 사용함으로써 원천 시스템과 중앙 통합 플랫폼 간의 시간적, 공간적 종속성(Temporal/Spatial Coupling)을 제거합니다. 어느 한쪽 시스템에 장애가 발생하더라도 전체 데이터 흐름이 멈추지 않고 메시지를 큐에 남아 있다가 재연결될 수 있습니다. 2. **확장성 및 처리량:** 카프카(Kafka) 같은 분산 스트리밍 플랫폼을 활용하면 수십만 건 이상의 데이터가 초당 유입되는 대규모 산업 환경의 트래픽을 효율적으로 처리할 수 있습니다. 3. **다중 프로토콜 처리:** OPC UA 게이트웨이와 같은 전문 게이트웨이를 도입하여, 다양한 레거시 프로토콜을 표준화된 이진(Binary) 또는 메시지 포맷으로 변환하는 레이어(Protocol Translation Layer)를 구축합니다. |
| **결과(Consequences)** | **긍정적:** 시스템의 결합도가 극도로 낮아져(Loose Coupling) 향후 새로운 원천 시스템이나 프로토콜(예: 새로운 센서 유형)이 추가되어도 통합 로직을 전면 수정할 필요가 없습니다. 실시간 데이터 스트림 처리가 가능해져 지연 시간이 최소화됩니다. **부정적:** 아키텍처의 복잡도가 매우 높고, 메시지 흐름 관리를 위한 전문적인 운영 인력(DevOps, Streaming Architect)이 필수적으로 요구됩니다. |
| **트레이드오프(Trade-offs)** | **[전통적 방식 (ETL/DB-centric)]**의 단순한 구조와 직관성을 포기하고, **[스트리밍/메시지 기반]**의 높은 초기 구현 복잡도와 운영 난이도를 감수합니다. 그러나 이 트레이드오프를 통해 **최대 수준의 확장성(Scalability)**과 **고가용성(High Availability)**을 확보하여, 산업 현장의 24/7 무중단 가동 요구사항을 충족시킬 수 있습니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 의미론적 불일치 위험 (Semantic Drift Risk)
- **설명:** MES 시스템에서는 '공정비율'을 A라는 단위로 정의하고, LIMS 시스템에서는 동일한 데이터를 B라는 물리적 기준으로 기록하는 등, 같은 개념이라도 각 시스템이 데이터의 정의(Definition)와 구조(Structure)를 다르게 사용하는 경우입니다. 이는 데이터 통합 플랫폼의 상위 계층에서 심각한 분석 오류를 초래합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 통합 계층에 **메타데이터 레이어(Metadata Layer)**와 **지식 그래프(Knowledge Graph)**를 구축해야 합니다. 모든 통합 데이터 필드에 대해 표준화된 온톨로지(Ontology)를 정의하고, 데이터 매핑 및 트랜슬레이션 서비스(Data Mapping Service)를 강제 적용하여 의미론적 통일성을 확보해야 합니다.

### 2. 레거시 OT 시스템 인터페이스 고장 위험 (Legacy Interface Failure)
- **설명:** 현장의 제어기(PLC/DCS)와 같은 레거시 OT 장비는 현대적인 통신 규격이나 안정적인 API를 제공하지 못하는 경우가 많습니다. 이 장비의 네트워크 장애나 프로그램 오류가 발생하면, 통합 플랫폼의 핵심 데이터 수집 경로가 마비되어 공정 모니터링 및 제어가 불가능해질 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 수집 아키텍처를 '엣지 컴퓨팅(Edge Computing)' 중심으로 재설계해야 합니다. 원천 현장과 통합 플랫폼 사이에 자체 데이터 정제, 필터링, 로컬 버퍼링(Local Buffering) 기능을 가진 엣지 게이트웨이를 배치하고, 통신 실패 시 데이터를 로컬에 백업하고 네트워크 복구 후 자동 전송(Store-and-Forward)하는 메커니즘을 구현해야 합니다.

### 3. 사이버 보안 및 OT-IT 격리 실패 위험 (Cybersecurity & Air Gap Failure)
- **설명:** OT(제어 및 물리 프로세스) 영역과 IT(사무 및 정보 처리) 영역을 하나의 네트워크로 통합하거나, 외부 네트워크와 연결하는 과정에서 보안 경계(Perimeter)가 허술해질 경우, 해킹 공격자가 IT 시스템을 통해 물리적인 제어 시스템(PLC)에 접근하여 공정을 오작동시키거나 장비를 손상시킬 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **진정한 네트워크 분리(Segmentation)**와 **방화벽 기반의 접근 제어(ACL)**를 최우선으로 적용해야 합니다. 산업용 프로토콜 게이트웨이에는 OT 전문 방화벽(Industrial Firewall)을 설치하고, 데이터 전송은 반드시 일방향 통신(Data Diode) 원칙을 준수하는 것이 이상적입니다.

### 4. 데이터 볼륨 및 처리 부하 병목 현상 위험 (Scalability Bottleneck Risk)
- **설명:** 제조 공정이 정상 상태가 아닌, 비상 정지 해제(Restart) 상황이나 대량의 배치 데이터(Batch Data)가 한꺼번에 처리될 때, 중앙 통합 플랫폼의 메시지 큐, 저장소, 또는 데이터 처리 엔진이 설계 용량을 초과하여 순간적으로 부하가 몰리는 병목 현상이 발생할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 메시지 큐와 데이터 처리 모듈(Consumer)을 오토 스케일링(Auto-Scaling) 그룹으로 구성하여 처리 가능한 워커 노드 수를 동적으로 늘려야 합니다. 또한, 대용량 배치 데이터는 스트리밍 방식으로 처리하되, 시간적 순서를 보장(Ordering Guarantee)하는 명확한 키(Key)와 파티셔닝 전략을 수립해야 합니다.

### 5. 데이터 품질 관리 부재 위험 (Data Quality Governance Failure)
- **설명:** 수집된 데이터가 측정 노이즈, 센서의 드리프트(Drift), 측정 장비의 보정 주기 누락 등 다양한 이유로 인해 잘못되거나 불완전할 수 있음에도 불구하고, 시스템이 이를 '정확한 데이터'로 인식하고 상위 분석 로직에 사용하게 될 위험입니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 파이프라인의 핵심 단계마다 **데이터 유효성 검사(Validation)** 및 **품질 게이트(Quality Gate)**를 필수로 도입해야 합니다. 이상치 탐지(Anomaly Detection), 누락 값 처리(Imputation), 그리고 데이터의 출처(Provenance)와 신뢰 점수(Confidence Score)를 기록하는 메커니즘을 아키텍처 깊숙이 내장해야 합니다.
