## 100230

# 🏗️ 아키텍처 분석 보고서

## ADR (Architecture Decision Record)

### ADR-001: 중앙 집중식 데이터 버스 기반의 모듈 간 느슨한 결합(Loose Coupling) 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 모니터링(310), 제어(320), 모델링(350), 네트워크 구축(340), 플랫폼(360) 등 이기종 기능 모듈들이 유기적으로 데이터를 교환하고 명령을 전달해야 하는 복합 시스템임. 기존 점대점(P2P) 통합 방식은 모듈 추가 시 기존 코드 수정이 불가피하고 시스템 결합도가 높아져 유지보수가 어려운 아키텍처적 과제가 존재함.                                                           |
| **결정(Decision)**       | 모든 기능 모듈을 단일 중앙 통신 라인(중앙의 양방향 화살표)에 연결하는 **중앙 집중식 데이터 버스(Central Data Bus) 아키텍처**를 채택함. 모듈 간 통신은 직접적인 호출이 아닌, 중앙 버스를 통한 메시지 발행/구독(Pub/Sub) 또는 데이터 공유 방식으로 구현하여 상호 작용을 중계하도록 설계함.                                                                   |
| **근거(Rationale)**      | 1. **모듈 독립성:** 모니터링부(310)나 제어부(320)와 같은 핵심 모듈이 내부 로직 변경 시 다른 모듈(예: 커스텀부 390)에 영향을 주지 않음.<br>2. **확장성:** 새로운 분석 모듈이나 외부 시스템 연동 시 중앙 버스에만 연결하면 되므로 시스템 확장이 용이함.<br>3. **데이터 통합:** 모델링부(350)나 반복필지운용부(380)가 필요로 하는 데이터를 중앙 버스를 통해 일관되게 수집 및 분배할 수 있음. |
| **결과(Consequences)**   | 시스템의 모듈성이 극대화되어 기능 추가 및 수정이 용이해지며, 특정 모듈의 장애가 전체 시스템으로 전파되는 것을 최소화함. 다만, 중앙 버스 트래픽이 포화될 경우 전체 시스템의 지연(Latency)이 발생할 수 있으며, 버스 자체의 장애가 전체 시스템 중단으로 이어질 수 있는 리스크가 존재함.                                                                               |
| **트레이드오프(Trade-offs)** | 모듈 간 결합도 최소화 및 유연성 확보 vs. 중앙 통신 인프라의 병목 현상 가능성 및 단일 장애점(SPOF) 관리의 복잡성 증가.                                                                                                                                                                          |

---

## ⚠️ 잠재적 위험 분석

### 1. 중앙 버스 트래픽 포화에 의한 시스템 전체 지연

- **설명:** 모니터링부(310)에서 초당 대량의 센서 데이터가 유입되거나, 반복필지운용부(380)가 배치 작업을 수행하는 동안 중앙 버스의 대역폭이 포화됨. 이 경우 제어부(320)의 실시간 명령 전달이 지연되어 시스템 응답성이 저하됨.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 중요도에 따른 QoS(Quality of Service) 큐잉 정책 적용, 고빈도 데이터는 별도의 고속 채널로 분리, 버스 분할(Sharding) 또는 다중 버스 아키텍처 도입 검토.
  
  ### 2. 중앙 버스 장애에 의한 전체 시스템 마비 (SPOF)
- **설명:** 모든 모듈이 단일 중앙 라인에 의존하므로, 이 라인을 제어하는 메시지 브로커나 물리적 통신선에 장애가 발생하면 모니터링부터 제어, 모델링까지의 모든 프로세스가 즉시 중단됨.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 메시지 브로커 클러스터링 및 고가용성(HA) 구성(예: Active-Active), 물리적 통신 경로 이중화(Redundancy), 로컬 캐싱 기능을 통한 일시적 독립 동작 모드 지원.
  
  ### 3. 모듈 간 보안 경계 모호성 및 무단 접근
- **설명:** 중앙 버스를 통해 모든 모듈이 통신하므로, 권한이 낮은 모듈(예: 커스텀부 390)이 핵심 제어 모듈(제어부 320)에 접근하거나 데이터를 조작할 수 있는 보안 허점이 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 버스 레벨에서의 세분화된 접근 제어(ACL) 및 암호화 적용, 모듈별 인증서 기반 Mutual TLS(mTLS) 구현, 메시지 무결성 검증 로직 도입.
  
  ### 4. 비동기 처리로 인한 데이터 순서 보장 실패
- **설명:** 중앙 버스를 통한 비동기 통신 환경에서, 모니터링부(310)에서 전송된 데이터의 순서가 뒤바뀌어 모델링부(350)나 제어부(320)에 도달할 경우, 시계열 데이터 기반의 분석이나 제어 로직이 왜곡될 수 있음.
- **심각도:**  Medium
- **발생 가능성:**  High
- **대응 방안:** 메시지 시퀀싱(Sequencing) 및 오셋 관리 로직 구현, 데이터 생성 타임스프 기반 재정렬(Reordering) 버퍼 도입, 순서가 중요한 트랜잭션에 대한 순차적 처리 보장 옵션 제공.
  
  ### 5. 이기종 모듈 간 데이터 포 불일치
- **설명:** 네트워크구축부(340)와 플랫폼부(360) 등 각 모듈이 사용하는 내부 데이터 구조가 상이할 경우, 중앙 버스에서 데이터 변환(Transformation) 지연이 발생하거나 해석 오류로 인한 통신 실패가 빈번해질 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 중앙 버스 수준에서 표준 데이터 스키마(예: JSON Schema, Protobuf) 정의 및 강제 적용, 어댑터(Adapter) 패턴을 활용한 레거시 모듈 호환성 유지, 데이터 변환 미들웨어 도입.
