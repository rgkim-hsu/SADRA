# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: [분산 신원 관리 아키텍처 (Decentralized Identity Architecture) 도입 결정]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 기존 IoT 및 디지털 서비스 환경은 중앙집중식 서버(Identity Provider)가 모든 인증 정보를 관리하여, 해킹 시 데이터 유출 위험이 크고 단일 고장 포인트(SPOF)가 존재합니다. 또한, GDPR 등 개인정보 보호 규정 하에서 데이터 주권(Data Sovereignty)과 프라이버시 보호가 필수적입니다. 제공된 시스템 개념도는 "사용자(Holder)", "발행자(Issuer)", "검증자(Verifier)"가 참여하는 분산 신원 모델의 흐름을 보여줍니다. |
| **결정(Decision)** | 시스템 아키텍처는 **Self-Sovereign Identity (SSI)** 또는 **Decentralized Identity (DID)** 방식을 채택합니다.<br>1. **신원정보 (Credential)**는 암호화되어 사용자의 지갑 (Wallet) 에 저장됩니다.<br>2. **신원정보발행자 (Issuer)**는 권한을 증명하고 크레덴셜을 발행합니다.<br>3. **서비스제공자 (Verifier)**는 발급된 정보를 요청시 검증하며, **분산ID저장소 (Verifiable Data Registry)**는 공개키나 상태 변경 (revocation) 정보를 보관합니다. |
| **근거(Rationale)** | 1. **보안성 향상**: 중앙 서버를 탈취하는 대신, 사용자의 개인키 (Private Key) 가 보안된 지갑에 보관되므로 사용자 통제력이 강화됩니다.<br>2. **상호운용성**: 제공된 문서 (ISO/IEC 30141, oneM2M 등) 에서 언급되는 IoT 표준과 호환되며, 다양한 벤더 간의 데이터 공유 장벽을 허물 수 있습니다.<br>3. **민첩성**: 사용자는 최소한의 정보 (예: 이름 없이 나이만) 만 선택하여 제공함으로써 프라이버시를 보호할 수 있습니다. |
| **결과(Consequences)** | **긍정적**: 시스템의 신뢰도 향상, 해킹 시 피해 면도 최소화, 사용자 프라이버시 보호.<br>**부정적**: 사용자 측의 키 관리 난이도 증대, 기존 중앙집중식 DB 구조를 따르는 레거시 시스템과의 통합 비용 증가, 개발 초기 복잡도 상승. |
| **트레이드오프(Trade-offs)** | **복잡성 vs 보안/프라이버시**: 단순한 로그인 (계정 ID/PW) 보다 복잡한 지갑 및 DLT 기반 기술이 필요하므로 사용 진입 장벽이 높아질 수 있으나, 장기적인 보안과 규제 준수 측면에서는 명확한 이득이 있습니다. |

## ⚠️ 잠재적 위험 분석

### 1. [개인키 분실 및 키 관리 위험]
- **설명:** SSI 아키텍처에서 사용자의 신원은 개인키 (Private Key) 로 보호됩니다. 만약 사용자가 지갑이 손상되거나 개인키를 분실하면, 해당 신원정보를 복구할 수 없는 영구적인 데이터 손실이 발생합니다. 또한 IoT 디바이스가 리소스가 부족하여 키를 안전하게 저장 (HSM) 하는 것이 어렵습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
    1. **재covery 메커니즘 구현:** 분산 지갑 시스템 도입 (Backup Seed Phrase) 또는 기관 기반의 키 관리 서비스 (KMS) 를 통해 백업 키를 안전하게 분산 저장합니다.
    2. **다중 서명 (MFA):** 인증에 단일 키뿐만 아니라 생체정보나 2단계 인증 등을 결합하여 접근성을 높입니다.

### 2. [분산 ID 저장소 (Registry) 가용성 위험]
- **설명:** 개념도 (6) 번 단계에서 검증자 (Verifier) 가 발행자 (Issuer) 가 발급한 신원정보의 유효성을 확인하기 위해 '분산ID저장소'에 접근합니다. 만약 이 저장소 (DB 또는 블록체인 노드) 가 네트워크 문제나 고장으로 인해 다운되면, 검증자가 신원정보를 검증하지 못해 서비스가 마비될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:** 
    1. **P2P 또는 샤딩 아키텍처:** 단일 저장소 대신 여러 노드가 분산된 네트워크 구조 (예: Hyperledger Aries, ION) 를 사용하여 단일 노드 장애 시에도 서비스 가용성을 유지합니다.
    2. **오프라인 모드 지원:** 네트워크가 끊긴 상황에서 최소한의 검증 기능만 제한적으로 허용하도록 아키텍처를 설계합니다.

### 3. [유효하지 않은 신원정보 (Revocation) 검증 실패]
- **설명:** 사용자가 신원정보를 삭제하거나 발급자를 변경하는 경우 (재voke), 해당 상태를 외부에서 즉시 인지해야 합니다. 개념도에서 '분산ID저장소'가 이 역할을 하지만, 저장소에 등록되지 않은 삭제 정보나 해킹된 저장소 시, 검증자는 유효하지 않은 정보를 유효하다고 승인하여 보안 사고가 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
    1. **재voke 리스트 최적화:** 모든 사용자의 상태를 저장하는 방식 대신, Merkle Tree 와 같은 구조를 사용하여 변경 사항을 효율적으로 관리합니다.
    2. **다중 출처 검증:** 저장소 정보뿐만 아니라, 발급자가 직접 서명한 상태 정보를 검증하는 논리를 추가합니다.

### 4. [신원정보 제시 (Presentation) 과정의 도청 위험]
- **설명:** 개념도 (5) 번 단계에서 사용자가 검증자에게 신원정보 (Credential) 를 제공하는 과정입니다. 만약 이 전송 과정에서 제 3 자가 중간에서 데이터를 가로챈다면 (MITM 공격), 민감한 인증 정보가 유출될 수 있습니다. 특히 ZKP (Zero-Knowledge Proof) 를 사용하지 않을 경우, 검증자는 불필요한 개인정보까지 알게 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
    1. **端到端 암호화:** TLS/DTLS 등 전송 계층 암호화를 필수로 적용합니다.
    2. **선택적 공개 (Selective Disclosure):** DIF 표준에 따른 ZKP 기술 적용을 통해 검증자는 '만 20 세 미만'이라는 사실만 확인하도록 하고, 실제 '생년월일'은 노출되지 않도록 데이터를 가공하여 전송합니다.

### 5. [발행자 (Issuer) 신뢰성 및 사기 위험]
- **설명:** 시스템은 '신원정보발행자'에게 절대적인 권한을 부여합니다. 만약 이 발행자가 해킹당하거나, 사칭 사이트 (Phishing) 를 통해 권한을 획득하면, 불법적인 인증 정보를 발행할 수 있습니다. 검증자 (Verifier) 는 이를 신뢰하고 받아들일 수 있게 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 
    1. **발행자 인증 (Authentication):** 발급자가 누구인지 확실하게 확인하는 DID (Decentralized Identifier) 명목하에서의 인증 절차를 강요합니다.
    2. **발행자 평가 모델:** 검증자 측에서 신뢰할 수 있는 발급자 리스트를 유지 관리하고, 신뢰도가 낮은 발급자에게 발급된 증명서는 기본적으로 거부하는 정책을 수립합니다.
