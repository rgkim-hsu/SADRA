## 📋 ADR (Architecture Decision Record)

### ADR-001: 사료 잔량 관리를 위한 중앙 제어 기반의 능동형 폴링(Polling) IoT 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 사료 창고 및 사료 탱크의 잔량을 실시간으로 모니터링하여 사료 부족 상황을 예방하고, 관리자가 원격으로 상태를 확인해야 함. 다수의 센서(원격 센서부 120)가 비동기적으로 데이터를 전송할 경우 네트워크 트래픽 과부하 및 데이터의 불일치(예: 빈 사료통과 사료 크의 시간차 데이터)가 발생할 수 있는 아키텍처적 과제가 존재함.                                                                                    |
| **결정(Decision)**       | `원격 센서부(120)`를 수동적인 데이터 송신 장치가 아닌, `제어부(140)`의 명령(`빈 급이기동 측정명령`, `사료잔량측정명령`)에 따라 측정하고 보고하는 **능동형 폴링(Active Polling) 방식**의 IoT 아키텍처를 채택함. `제어부(140)`를 엣지 게이트웨이로 하여 센서 데이터를 집계한 후 `사료 잔량 모니터링 서버(20)`로 일괄 전송하도록 설계함.                                                        |
| **근거(Rationale)**      | 1. **데이터 동기화:** 제어부가 명령을 통해 특정 시점의 빈 사료통과 사료 탱크의 잔량을 동시에 측정(S230, S260)함으로써, 사료 공급 로직(S275)에 일관된 기준 데이터를 제공함.<br>2. **전력 및 네트워크 효율:** 센서가 상시 대기 및 전송하지 않고 요청 시에만 동작하므로 에너지를 절약하고 불필요한 네트워크 패킷을 줄임.<br>3. **중앙 집중식 관리:** 제어부가 센서 상태를 모니터링하고 이상 유무를 1차적으로 판단하여 서버의 부하를 분산함. |
| **결과(Consequences)**   | 사료 잔량 데이터의 신뢰도가 높아지며, 관리 시스템(서버, 관리자 단말)에서 정확한 상황을 파악할 수 있음. 또한, 제어부의 장애 시 하위 센서 전체의 모니터링이 중단되는 단일 장애점(SPOF) 리스크가 발생할 수 있음.                                                                                                                                               |
| **트레이드오프(Trade-offs)** | 데이터 일관성 확보 및 네트워크 효율성 향상 vs. 제어부 장애 시 전체 센서 네트워크 마비 가능성 및 제어부 구현 복잡도 증가.                                                                                                                                                                                                  |

---

## ⚠️ 잠재적 위험 분석

### 1. 원격 센서부(120)의 측정 오차 및 드리프트(Drift)

- **설명:** `원격 센서부(120)`가 측정하는 빈 사료통 무게(S230)나 사료 잔량(S260)이 시간이 지남에 따라 센서 노후화, 진동, 또는 환경 요인으로 인해 오차가 발생하거나 기준점이 흔들리는 드리프트 현상이 발생할 수 있음. 이로 인해 실제 사료는 부족함에도 시스템은 '충분'하다고 판단하여 급이 중단되는 치명적 오류가 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 제어부(140)에 주기적인 영점 조정(Zero Calibration) 로직 내장, 이동 평균(Moving Average) 필터 적용으로 순간적 오차 제거, 센서 상태 진단 알고리즘을 통한 이상 신호 감지 시 관리자 경고 발송.

### 2. 제어부(140)와 서버(20) 간 통신 두절

- **설명:** `제어부(140)`가 `사료 잔량 모니터링 서버(20)`로 측정 결과를 전송(S280)하는 과정에서 네트워크 장애가 발생하면, 관리자는 실시간 현황을 확인할 수 없으며, 사료 공급기(30)에 대한 공급 정보 갱신(S275)이 지연되어 사료 공급이 끊길 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 제어부에 'Store-and-Forward' 기능 도입(통신 복구 시 미전송 데이터 일괄 전송), 통신 두절 시 로컬 메모리에 저장된 마지막 유효 설정값으로 사료 공급기(30)를 기본 모드로 운전하는 Fail-safe 로직 적용, 통신 상태 하트비트(Heartbeat) 모니터링.

### 3. 장치 등록 과정에서의 보안 및 식별 오류

- **설명:** `장치등록요청(S200)` 및 `관리지점 등록/확인(S210)` 과정에서 고유 식별 정보(Hardware ID 등) 검증 없이 장치 등록이 이루어지면, 악의적인 제3자가 가짜 센서 데이터를 주입하거나 다른 관리자의 장치 정보를 탈취하여 사료 공급을 방해하는 보안 사고가 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:** 장치 등록 시 물리적 인증(예: QR 코드 스캔 또는 근거리 무선 인증) 병행, 통신 구간 암호화(TLS/SSL) 적용, 고유 디바이스 시리얼 번호 기반의 화이트리스트 관리.

### 4. 사료 공급기(30) 제어 로직의 불일치

- **설명:** `사료 공급 정보 갱신(S275)` 단계에서 서버의 데이터와 실제 사료 공급기의 제어 로직 간에 동기화 문제가 발생할 수 있음. 예를 들어, 서버는 '공급 중지' 명령을 내렸으나 공급기가 이를 수신하지 못하고 계속 사료를 공급하여 사료 탱크가 넘치는(Oversupply) 사고가 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 사료 공급기(30)에 독립적인 과충전 방지 센서(Overfill Sensor)를 하드웨어적으로 설치하여 네트워크 제어와 별개로 물리적 차단 기능 제공, 명령어 전달 시 ACK(Acknowledgement) 기반의 신뢰성 있는 전송 프로토콜 사용.

### 5. 관리자 단말(40) 알림 지연으로 인한 대응 실패

- **설명:** `사료 잔량 측정결과 알림(S295)`이 관리자에게 실시간으로 전달되지 않고 지연될 경우, 관리자가 현장에 도착하기 전에 가축이 굶주리는 상황이 발생할 수 있음. 특히 네트워크 트래픽이 많을 때 알림 메시지가 큐에 밀릴 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 알림 메시지에 우선순위(Priority) 부여(위기 상황 알림은 최상위 전송), 푸시 알림(Push Notification)과 SMS 문자 메시지를 병행하여 전달 보장, 관리자가 알림을 확인하지 않았을 경우 에스컬레이션(Escalation) 로직(상급 관리자 알림) 적용.
