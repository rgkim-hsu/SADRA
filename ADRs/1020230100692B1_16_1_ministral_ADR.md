## 📋 ADR (Architecture Decision Record)

### **ADR-001: 모듈별 기능 분리와 이중 처리 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 기반 스마트팜/축산 시스템은 실시간 모니터링, 예측 모델링, 자동 제어 및 플랫폼 통합이 필수적이다. 기존 모놀리식 아키텍처는 확장성, 유지보수성, 실시간 처리 요구사항을 충족하지 못한다. 또한, **국내외 표준(ISO/IEC 30141, oneM2M, ETSI EN 303 645)**에 따른 보안 및 상호운용성 요구사항을 고려해야 한다. |
| **결정(Decision)** | 1) **모듈별 기능 분리**: 모니터링부(310), 제어부(320), 모델링부(350), 플랫폼부(340/380) 등 8개 모듈로 분할하여 **마이크로서비스 아키텍처**를 채택한다.
2) **이중 처리 구조**: 모니터링부 ↔ 제어부, 모델링부 ↔ 플랫폼부 등 **대칭적 데이터 동기화**를 통해 결함 허용성(Fault Tolerance)을 보장한다.
3) **표준 준수**: oneM2M API 프레임워크와 ETSI 보안 표준을 기반으로 모듈간 통신을 설계한다. |
| **근거(Rationale)** | - **확장성**: 모듈별 배포로 수평적 스케일링이 가능 (예: 모델링부만 독립적으로 확장).
- **유지보수성**: 기능별 코드베이스 분리로 CI/CD 파이프라인 적용이 용이.
- **실시간 처리**: 모니터링부와 제어부 간 **이중 큐(Queue) 기반 통신**으로 지연 시간 최소화.
- **표준 준수**: ISO/IEC 30141의 "재사용 가능한 설계" 원칙과 oneM2M의 "API 일관성" 요구사항을 충족.
- **보안**: ETSI EN 303 645의 "기기 사이버보안" 요구사항을 모듈별로 적용 (예: 플랫폼부에서 TLS 1.3 강제). |
| **결과(Consequences)** | ✅ **장점**:
- 모듈별 업데이트가 시스템 전체에 미치는 영향 최소화.
- 실시간 데이터 처리 latency **<100ms** 달성 가능.
- 보안 인증(예: KISA 기준) 모듈별로 독립적 처리 가능.
❌ **단점**:
- 모듈간 통신 오버헤드 발생 (대응: gRPC 대신 CoAP 프로토콜 사용).
- 초기 개발 비용 증가 (대응: TTA 표준 가이드북 참조하여 템플릿 재사용). |
| **트레이드오프(Trade-offs)** | - **성능 vs. 복잡성**: 이중 처리 구조로 성능 향상但 모듈간 동기화 로직 추가 필요.
- **표준 준수 vs. 유연성**: oneM2M API 강제 적용으로 개발 속도 저하 가능但 글로벌 상호운용성 보장. |

### **ADR-002: 에지 컴퓨팅 기반 모델링부 배포**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 모델링부(350)는 AI/ML 기반 예측 모델을 실행해야 하며, **클라우드 전송 지연**으로 실시간 제어가 어려울 수 있다. 또한, **국내 표준(TTAK.KO-10.1170)**은 에지 컴퓨팅을 스마트팜 시스템의 필수 요소로 규정한다. |
| **결정(Decision)** | 모델링부를 **에지 서버(On-Premise 또는 로컬 게이트웨이)**에 배포하고, 클라우드와 하이브리드 동기화 구조를 채택한다.
- **모델 업데이트**: 클라우드에서 사전 학습된 모델을 에지 서버로 **OTA(Over-The-Air) 업데이트** 지원.
- **데이터 처리**: 모니터링부로부터 수집된 데이터는 **로컬에서 80% 처리**, 나머지 20%만 클라우드로 전송. |
| **근거(Rationale)** | - **지연 시간 최소화**: 에지 처리로 제어부까지의 latency **<50ms** 달성.
- **네트워크 비용 절감**: 불필요한 데이터 클라우드 전송 방지.
- **오프라인 지원**: 네트워크 단절 시에도 로컬 모델링이 가능.
- **TTA 표준 준수**: "에지 기반 스마트 온실 서비스" 관련 가이드라인 참조. |
| **결과(Consequences)** | ✅ **장점**:
- 실시간 제어 성능 향상.
- 네트워크 대역폭 절약 (예: 100Mbps → 20Mbps).
❌ **단점**:
- 에지 서버 유지보수 비용 발생 (대응: KISA 보안 인증 받은 하드웨어 사용).
- 모델 업데이트 복잡성 증가 (대응: Docker 컨테이너화 및 CI/CD 자동화). |
| **트레이드오프(Trade-offs)** | - **중앙 집중식 vs. 분산식**: 클라우드 모델링보다 에지 모델링으로 유연성 증가但 단일 장애점(SPOF) 위험 존재 (대응: 이중 에지 노드 구성). |

### **ADR-003: 보안 플랫폼부 통합**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 플랫폼부(340/380)는 **데이터 저장 및 서비스 제공**을 담당하며, **ITU-T X.1352**와 **ISO/IEC 27030**의 보안 요구사항을 충족해야 한다. 또한, **Matter/OCF 표준**과 상호운용성이 필요하다. |
| **결정(Decision)** | 플랫폼부를 **보안 강화형 마이크로서비스**로 설계하고, 다음 기능을 통합한다:
1. **데이터 암호화**: REST API 및 데이터베이스 레벨에서 **AES-256** 적용.
2. **인증/인가**: OAuth 2.1 + JWT 토큰 기반 **Fine-Grained Access Control**.
3. **로그 관리**: SIEM 통합을 위한 **Kafka 기반 로그 스트리밍**.
4. **표준 준수**: Matter의 **Pairing Protocol**과 OCF의 **Resource Model**을 지원한다. |
| **근거(Rationale)** | - **보안 표준 준수**: ITU-T X.1352의 "IoT 기기 보안 요구사항" 충족.
- **상호운용성**: Matter/OCF 표준으로 스마트홈 및 스마트팜 기기 통합 가능.
- **감사 가능성**: SIEM 통합으로 ETSI EN 303 645의 "사이버보안 감사" 요구사항 만족. |
| **결과(Consequences)** | ✅ **장점**:
- 글로벌 보안 인증(예: KISA, ETSI) 용이.
- 스마트홈 기기와의 상호운용성 확보.
❌ **단점**:
- 초기 개발 복잡성 증가 (대응: OpenMatter 라이브러리 재사용).
- 성능 오버헤드 발생 (대응: Redis 캐시 사용). |
| **트레이드오프(Trade-offs)** | - **보안 vs. 성능**: JWT 토큰 검증으로 latency 증가 가능 (대응: 토큰 캐싱). |

## ⚠️ 잠재적 위험 분석

### **1. 모듈간 통신 장애 (Cascading Failure)**
- **설명**: 모듈간 통신 실패(예: 네트워크 단절, API 타임아웃)로 **제어부 장애**가 전체 시스템에 전파될 수 있다. 특히, 모니터링부 ↔ 제어부 간 이중 처리 구조가 실패하면 실시간 제어가 중단된다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **서킷 브레이커 패턴** 적용 (Hystrix 또는 Resilience4j 사용).
  - 모듈간 **비동기 통신**으로 fallback 메커니즘 구현 (예: 모니터링 데이터 로컬 캐싱).
  - **헬스 체크** 주기적 수행 (5초 간격).

### **2. 에지 모델링부 모델 드리프트 (Model Drift)**
- **설명**: 에지 서버에서 실행되는 AI 모델이 **데이터 분포 변화**로 성능이 저하될 수 있다. 예를, 기후 변화로 모니터링 데이터 분포가 변하면 예측 정확도가 떨어진다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **온라인 학습 지원**: 에지 서버에서 **부분적 모델 업데이트** 가능하게 설계.
  - **성능 모니터링**: 모델 정확도 저하 시 **자동 알림** 시스템 구축 (예: Prometheus + AlertManager).
  - **A/B 테스트**: 새로운 모델을 에지 서버의 일부 노드에서만 테스트한 후 롤아웃.

### **3. 보안 취약점 노출 (Security Vulnerability)**
- **설명**: 플랫폼부에서 사용되는 **OAuth 2.1 또는 JWT**에 취약점이 발견되면 전체 시스템이 위협받을 수 있다. 특히, **토큰 탈취**로 불법 접근이 가능해진다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **정기적 보안 스캔**: Dependabot 또는 Snyk를 사용하여 의존성 취약점 모니터링.
  - **토큰 단축 시간**: JWT 유효 기간을 **15분 이하**로 설정하고, refresh token은 **1시간**으로 제한.
  - **KISA 인증**: 플랫폼부를 **KISA 보안 인증 프로세스**에 적용하여 글로벌 표준 준수 확인.

### **4. 데이터 일관성 문제 (Data Inconsistency)**
- **설명**: 이중 처리 구조로 인해 **모니터링부와 제어부 간 데이터 불일치**가 발생할 수 있다. 예를, 모니터링 데이터가 제어부에 늦게 반영되면 오류 제어가 발생한다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 소싱 패턴** 적용: 모든 상태 변경을 이벤트로 기록하고, 재생산성 보장.
  - **트랜잭션 로그**: 분산 트랜잭션을 위한 **Saga 패턴** 구현.
  - **데이터 검증 체크섬**: 모듈간 데이터 전송 시 **SHA-256 체크섬**으로 일관성 확인.

### **5. 표준 변경으로 인한 재작업 (Standard Evolution Risk)**
- **설명**: **ISO/IEC 30141:2024** 또는 **Matter 표준**이 변경되면 시스템을 재작업해야 한다. 예를, API 스펙 변경으로 모듈간 호환성 문제가 발생할 수 있다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기적으로)
- **대응 방안**:
  - **표준 모니터링**: ISO/IEC 및 IEEE 표준 변경 사항을 **자동 알림** 시스템으로 모니터링 (예: RSS 피드 + 웹훅).
  - **추상화 레이어**: 모듈간 통신을 위한 **어댑터 패턴** 적용하여 표준 변경에 대한 영향 최소화.
  - **백워드 호환성**: 새로운 표준 버전 지원 시 **기존 API와 병행 실행** 가능하게 설계.

**참고 사항**:
- 모든 모듈은 **TTA 표준 가이드북** 및 **KISA 보안 가이드라인**을 준수하여 개발한다.
- 에지 컴퓨팅 환경은 **ETRI의 스마트팜 표준**을 참조하여 하드웨어 요구사항을 정의한다.
- 보안 관련 결정은 **ETSI EN 303 645**와 **ISO/IEC 27030**을 기준으로 한다.
