# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 서비스 계층의 디커플링 및 상호운용성을 위한 표준 데이터 모델 기반 API 게이트웨이 도입

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 관측 환경 데이터(온도, pH, EC 등)와 같이 이질적이고 다양한 프로토콜(Modbus, Zigbee, LoRa 등)을 통해 수집되는 다종(Multi-modal)의 센서 데이터를 기반으로 합니다. 이 데이터를 기반으로 Web/Mobile 등 수많은 서비스(Application)가 데이터를 필요로 하므로, 데이터의 출처(Source)와 소비(Consumption)가 복잡하게 얽히는 'Spaghetti Architecture'가 될 위험이 매우 높습니다. |
| **결정(Decision)** | 데이터 저장소(Data Module)와 서비스 계층(Service Layer) 사이에 **표준화된 추상화 계층(Abstraction Layer)**을 필수적으로 도입합니다. 이 계층은 API Gateway 패턴을 활용하여 모든 내부 데이터를 통일된 Semantic Data Model (예: OCF, oneM2M 기반의 통합 모델)로 변환하여 외부에 노출하고, 모든 서비스 요청은 오직 이 게이트웨이를 통해서만 접근하도록 강제합니다. |
| **근거(Rationale)** | 1. **상호운용성(Interoperability):** 시스템의 핵심은 다양한 기기와 서비스를 연결하는 것입니다. 표준 모델을 채택함으로써 특정 서비스가 특정 데이터 모델에 종속되는 것을 막고, 새로운 디바이스나 서비스를 추가하더라도 기존 서비스에 미치는 영향을 최소화할 수 있습니다. 2. **관심사 분리(Separation of Concerns):** 데이터 수집(Ingestion), 데이터 분석(Analytics), 서비스 제공(API)의 경계를 명확히 분리하여, 각 컴포넌트가 독립적으로 개발, 배포, 확장될 수 있게 합니다 (마이크로 서비스 원칙). 3. **보안 강화:** API 게이트웨이를 통해 모든 진입점을 중앙 집중화함으로써, 접근 제어(Authentication/Authorization) 및 부하 분산(Throttling) 등 보안 정책을 일관되게 적용할 수 있습니다. |
| **결과(Consequences)** | **긍정적:** 시스템의 유연성(Flexibility)과 확장성(Scalability)이 극대화됩니다. 기술 부채(Technical Debt)가 누적되는 것을 방지하여 장기적인 유지보수 비용을 절감합니다. **부정적:** 초기 아키텍처 설계 및 데이터 모델 구축(Semantic Modeling)에 막대한 시간과 노력이 필요하며, 데이터 변환(Transformation) 과정에서 성능 병목(Bottleneck)이 발생할 가능성이 있습니다. |
| **트레이드오프(Trade-offs)** | **(장점)** 높은 상호운용성과 장기적 유지보수 용이성 확보 $\rightarrow$ **(감수해야 할 단점)** 초기 개발 복잡도(Complexity) 증가 및 데이터 변환 과정에서의 오버헤드 발생. |

## ⚠️ 잠재적 위험 분석

### 1. 이기종 센서 데이터의 신뢰성 및 시맨틱 오류 (Data Drift & Semantic Error)
- **설명:** 현장 관측 환경 데이터는 센서 노화, 외부 환경 변화, 무선 통신 간섭 등으로 인해 데이터가 비정상적이거나 부정확한(out-of-range) 값으로 수집될 수 있습니다. 만약 이 오류 데이터를 분석 엔진이 신뢰하고, 이것이 다시 자동 제어 명령(Actuator)으로 피드백되면, 농장/축사 환경에 치명적인 손상을 입힐 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    1. **엣지(Edge) 레벨 검증 강화:** 물리적 제어기(PLC) 단계에서 데이터의 유효성 검사(Range Check, Rate of Change Check)를 수행하고, 비정상 데이터는 즉시 플래그를 지정하고 경고를 발생시켜 상위 시스템에 전파해야 합니다.
    2. **데이터 정합성 검증 모듈:** 중앙 플랫폼에 통계적 이상 감지(Anomaly Detection) 모듈을 배치하여, 센서 간의 상호 상관관계(예: 온도가 높을 때 습도가 높아져야 함)를 분석하고 데이터의 의미적 오류(Semantic Error)를 감지해야 합니다.

### 2. 보안 경계의 취약점 (Edge/Device Level Security Breach)
- **설명:** 시스템의 가장 취약한 부분은 무선으로 연결된 수많은 센서 노드(IoT Things)입니다. 공격자가 낮은 보안 수준의 센서 노드를 장악할 경우, 이를 교두보(Jump Point) 삼아 네트워크 전체로 확산시키거나, 악성 데이터를 주입(Data Spoofing)하여 시스템 오작동을 일으킬 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:**
    1. **제로 트러스트(Zero Trust) 모델 적용:** 모든 디바이스와 사용자, 트래픽을 기본적으로 불신(Don't Trust)하고, 접근 시마다 최소 권한 원칙(Principle of Least Privilege)에 따라 인증 및 인가(AuthN/AuthZ)를 수행해야 합니다.
    2. **암호화 및 인증:** 센서-게이트웨이 간 모든 통신 구간(LORA, Zigbee 등)은 최소한 TLS/DTLS와 같은 강력한 암호화 프로토콜을 사용하며, 디바이스에 고유 인증서(Certificate)를 탑재해야 합니다.

### 3. 데이터 파이프라인의 단일 실패 지점 (Single Point of Failure - SPOF)
- **설명:** 데이터 수집(Ingestion) 모듈과 데이터베이스(DB)가 물리적으로 또는 논리적으로 단일 실패 지점으로 작용할 경우, 해당 모듈이 다운되면 시스템의 모든 데이터가 중단되어 농장/축사 관리가 불가능해집니다. 특히 실시간성이 중요한 제어 시스템에서 치명적입니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    1. **고가용성(High Availability, HA) 아키텍처 구축:** 데이터 수집, 메시지 큐(Message Queue), DB 등 핵심 백엔드 컴포넌트를 최소 3개 이상의 Zone/Region에 분산 배포하고, 활성-활성(Active-Active) 또는 활성-대기(Active-Standby) 복제 구조를 유지해야 합니다.
    2. **메시지 큐의 영속성(Persistence) 확보:** 데이터 수집 과정에서 발생하는 데이터 스트림은 Kafka와 같은 메시지 큐를 사용하여 영속적으로 저장하고, 백엔드 모듈이 일시적으로 실패하더라도 데이터를 잃지 않고 복구할 수 있도록 설계해야 합니다.

### 4. 비즈니스 로직의 표준화 부족 (Non-Standardized Business Logic)
- **설명:** 'AI-In-One Platform'의 분석 기능이나 '서비스'에 포함될 제어 로직(예: 온도가 25도 초과 시, 환기팬을 켜고, 난방기를 끄는)이 각 서비스별로 독립적으로 구현될 경우, 제어 로직이 분산되고 일관성 있는 거버넌스를 확보하기 어렵습니다. 이는 A 서비스와 B 서비스가 같은 환경 데이터를 가지고도 서로 다른 방식으로 해석하고 충돌하는 결과를 낳을 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    1. **제어 로직 레이어 표준화:** 핵심 제어 로직(Orchestration Logic)을 플랫폼 레벨의 전용 서비스(Rule Engine Service)로 분리하고, 모든 서비스는 이 엔진을 통해 환경 제어 명령을 요청하도록 통일해야 합니다.
    2. **업무 흐름(Workflow) 모델 정의:** 스마트팜의 핵심 업무 프로세스(예: 성장 주기별 환경 관리)를 BPMN(Business Process Model and Notation) 등 표준화된 방식으로 모델링하고, 이를 아키텍처 문서로 관리해야 합니다.

### 5. 데이터 거버넌스 및 사생활 침해 위험 (Data Governance and Privacy Risk)
- **설명:** 수집된 데이터에는 단순히 환경 정보 외에도 특정 시설의 운영 패턴, 가축의 생체 데이터, 또는 사용자(농업 종사자)의 접속 기록 등 민감한 운영 정보가 포함될 수 있습니다. 이러한 데이터가 적절히 익명화되거나 접근 통제되지 않을 경우, 데이터 유출 및 비즈니스 기밀 침해, 개인정보 침해의 법적/운영적 위험을 초래합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟢 Low
- **대응 방안:**
    1. **데이터 분류 및 접근 통제:** 데이터 수집 단계부터 데이터를 민감도(Severity Level)별로 분류하고, 각 데이터 타입별로 엄격한 접근 제어 목록(ACL)을 적용해야 합니다.
    2. **익명화 및 가명화(Pseudonymization):** 운영/사용자 데이터를 백엔드에 저장하거나 분석에 활용할 때는 반드시 식별자가 포함된 민감 정보는 가명화 또는 익명화 처리를 거쳐야 하며, 이를 위한 별도의 프라이버시 보호 계층(Privacy Layer)을 도입해야 합니다.
