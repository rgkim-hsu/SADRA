📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 이미지 기반 생육정보 산출을 위한 중앙 집중형 파이프라인 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서 작물의 생육 상태를 정량적으로 판단하려면 카메라/센서로부터 수집된 이미지 데이터를 실시간으로 분석하고, 기준정보(품종별 생육 기준치)와 대조하여 의미 있는 생육지표를 산출해야 한다. 이미지 제공모듈(100), 생육정보 산출모듈(200), 기준정보 데이터베이스(300), 영농정보 데이터베이스(400), 사용자단말(400)이라는 5개 컴포넌트가 존재하며, 이를 어떤 토폴로지로 연결하느냐가 전체 시스템의 확장성과 신뢰성을 결정한다. |
| **결정(Decision)**       | 생육정보 산출모듈(200)을 허브(Hub)로 삼는 중앙 집중형 스타(Star) 토폴로지를 채택한다. 이미지 제공모듈(100)은 원시 이미지를 단방향으로 산출모듈에 전송하고, 기준정보 DB(300)와는 양방향 참조·갱신, 영농정보 DB(400)에는 산출 결과를 단방향 저장, 사용자단말과는 양방향 인터랙션(조회·알림)을 수행하도록 인터페이스를 정의한다.                                                       |
| **근거(Rationale)**      | ① 생육정보 산출이라는 단일 핵심 비즈니스 로직을 한 모듈에 집중시켜 책임 분리(SoC)를 달성한다. ② 이미지 전처리·AI 추론·기준값 비교·결과 저장의 순차적 파이프라인을 하나의 오케스트레이터가 제어하므로 트랜잭션 일관성 유지가 용이하다. ③ 스마트팜 현장 특성상 이미지 제공 디바이스(카메라, 드론 등)가 다양하게 추가될 수 있어, 허브 교체 없이 엣지 노드만 추가하는 수평 확장이 가능하다.                             |
| **결과(Consequences)**   | 긍정적: 각 컴포넌트의 역할이 명확히 분리되어 유지보수성이 향상되고, 산출모듈의 버전 업그레이드(모델 교체 등)가 독립적으로 가능하다. 부정적: 생육정보 산출모듈(200)이 단일 장애점(SPOF)이 되어, 해당 모듈 장애 시 전체 서비스가 중단된다. 또한 모든 데이터가 산출모듈을 경유하므로 처리량(Throughput) 병목이 발생할 수 있다.                                                           |
| **트레이드오프(Trade-offs)** | 얻는 것: 단순한 제어 흐름, 명확한 책임 경계, 빠른 초기 개발 속도. 감수할 것: 산출모듈의 고가용성(HA) 구성 필수, 수평 스케일 아웃 시 상태 공유 문제(세션/캐시 동기화) 발생 가능성, 기준정보 DB와의 빈번한 양방향 통신으로 인한 레이턴시 누적 위험.                                                                                                        |

⚠️ 잠재적 위험 분석
------------

### 1. 생육정보 산출모듈(200) 단일 장애점(SPOF) 위험

* **설명:** 모든 컴포넌트가 생육정보 산출모듈(200)에 의존하는 스타 토폴로지 구조상, 해당 모듈의 프로세스 크래시·메모리 부족·AI 추론 엔진 오류 발생 시 이미지 수집부터 사용자 조회까지 전체 서비스가 즉시 중단된다. 스마트팜 특성상 생육 임계 시점(개화기, 착과기 등)에 장애가 발생하면 농업적 피해가 직접적으로 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Standby 또는 Active-Active 이중화 구성(컨테이너 오케스트레이션 기반 Kubernetes Deployment + HPA 적용), 헬스체크 및 자동 재시작 정책 수립, 장애 발생 시 사용자단말에 즉시 알림을 전송하는 Fallback 메커니즘 구현.

### 2. 기준정보 데이터베이스(300) 데이터 정합성 및 동시성 충돌 위험

* **설명:** 생육정보 산출모듈(200)이 추론 결과를 기준정보 DB(300)에 쓰는 동시에 읽기도 수행하는 양방향 구조에서, 다수의 카메라 이미지가 동시에 유입될 경우 읽기-쓰기 경합(Race Condition)이 발생할 수 있다. 잘못된 기준값을 참조한 생육 판정 결과가 영농정보 DB(400)에 저장되면 이후 의사결정(시비량, 관수량 산정 등)에 연쇄적 오류를 초래한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 기준정보 DB 접근 시 읽기 전용 레플리카(Read Replica)와 쓰기 마스터 분리, 트랜잭션 격리 수준(Isolation Level) 명시적 설정(최소 Repeatable Read), 기준값 변경 이력을 버전 관리(Optimistic Locking)하여 롤백 가능하도록 설계.

### 3. 이미지 제공모듈(100) 데이터 품질 저하로 인한 오추론 위험

* **설명:** 스마트팜 현장의 카메라·드론·RGB-D 센서 등은 조도 변화, 렌즈 오염, 네트워크 패킷 손실로 인해 블러·노이즈·누락 프레임이 발생하기 쉽다. 생육정보 산출모듈(200)이 저품질 이미지를 그대로 AI 모델에 투입하면 생육지표가 실제보다 과대·과소 산출되어 영농 의사결정에 오류를 유발한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 이미지 수신 시 품질 검증 게이트(해상도, 조도 히스토그램, 블러 스코어 임계값) 전처리 파이프라인 삽입, 품질 미달 이미지는 큐(Queue)에 보류 후 재촬영 요청 또는 직전 정상 프레임으로 대체하는 정책 수립, 이상 이미지 비율 모니터링 대시보드 구축.

### 4. 영농정보 데이터베이스(400) 누적 데이터 폭증 및 성능 저하 위험

* **설명:** 이미지 기반 생육정보는 수집 주기(분·시간 단위)에 따라 대용량 레코드가 지속적으로 적재된다. 파티셔닝·아카이빙 전략 없이 운영할 경우 수개월 내 테이블 풀스캔 응답 시간이 급격히 증가하며, 사용자단말의 생육 이력 조회 및 통계 분석 기능이 사실상 마비될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 시계열 특성을 고려한 시간 기반 파티셔닝(월별/분기별) 적용, 원시 이미지는 오브젝트 스토리지(S3 호환)에 분리 저장하고 DB에는 메타데이터·인덱스만 보관, 콜드 데이터 자동 아카이빙 정책 수립, 조회용 OLAP 레플리카 분리 운영.

### 5. 사용자단말 인증·인가 부재로 인한 데이터 무단 접근 및 조작 위험

* **설명:** 개념도상 사용자단말(400)과 생육정보 산출모듈(200) 간의 양방향 통신 경로에 인증·인가 메커니즘이 명시되어 있지 않다. 외부 공격자 또는 권한 없는 내부 사용자가 생육 파라미터 조작, 기준정보 DB 간접 변조, 영농정보 무단 열람 등을 시도할 경우 농장 운영 전체가 위협받는다. 특히 스마트팜 시스템은 물리적 액추에이터(관수 밸브, 냉난방 장치)와 연동될 가능성이 높아 보안 취약점의 파급 효과가 물리 세계까지 확장된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** API Gateway 계층에 OAuth 2.0 + JWT 기반 인증 적용, 역할 기반 접근 제어(RBAC)로 농장주·관리자·열람자 권한 분리, 통신 구간 전체 TLS 1.3 암호화 적용, 주요 조작 이벤트에 대한 감사 로그(Audit Log) 불변 저장 및 이상 행위 탐지(SIEM) 연동.
