# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: IoT 데이터와 엔터프라이즈 비즈니스 로직을 위한 서비스 주도 아키텍처(Service-Oriented Architecture) 및 데이터 계층화 적용

| 항목 | 내용 |
| :--- | :--- |
| **상황(Context)** | 본 시스템은 102A와 같은 이질적이고 이질적인(Heterogeneous) 다수의 IoT 장치(센서, 액추에이터)로부터 실시간, 대용량의 시계열 데이터(Time-Series Data)를 수집해야 한다. 또한, 이 원시 데이터는 단순 모니터링을 넘어, 주문 처리, 공급망 관리(SCM), 재고 관리 등 복잡한 엔터프라이즈 비즈니스 프로세스(ERP)와 통합되어 활용되어야 한다. 이 두 영역(물리적 세계의 데이터 흐름과 논리적 비즈니스 흐름)을 하나의 경직된 구조로 통합할 경우, 시스템의 확장성(Scalability)과 유지보수성(Maintainability)이 급격히 저하되고, 새로운 표준(예: Matter, ISO/IEC 30141)에 대한 대응 속도가 느려지는 문제가 발생한다. |
| **결정(Decision)** | 시스템의 핵심 데이터 처리 영역(Data Ingestion $\to$ Data Abstraction $\to$ Service Layer)에 반드시 **이벤트 기반(Event-Driven)**의 **마이크로서비스(Microservices)** 아키텍처를 도입하고, 전용 **IoT 플랫폼 계층**을 분리하여 구축한다. 이 플랫폼 계층은 공통된 표준화된 메시지 포맷(예: JSON/Avro)과 표준 프로토콜(MQTT, Kafka)을 통해 물리적 데이터와 논리적 서비스 호출을 분리하여 중개하는 역할을 수행한다. |
| **근거(Rationale)** | 1. **느슨한 결합(Loose Coupling):** 마이크로서비스 도입으로 인해, 계측기 시스템이나 공급망 관리 시스템을 개별적으로 업데이트하거나 확장할 때, 다른 핵심 모듈에 미치는 영향(Ripple Effect)을 최소화할 수 있다. 2. **확장성 및 탄력성(Elasticity):** 데이터 유입량이 갑작스럽게 폭증하는 시나리오(예: 재난 모니터링, 대규모 수확 데이터)에도 플랫폼 계층이 탄력적으로 부하를 분산하고 처리할 수 있게 한다. 3. **표준 준수:** 이 방식은 ISO/IEC 30141 등 국제 아키텍처 표준에서 권장하는 **관점 기반(View-Based)** 아키텍처를 구현하기 용이하며, 특정 컴포넌트가 전체 시스템의 병목 지점(Bottleneck)이 되는 것을 방지한다. |
| **결과(Consequences)** | **긍정적:** 높은 확장성, 컴포넌트별 독립적 개발 및 배포(CI/CD), 미래 표준 변화에 대한 높은 유연성 확보. **부정적:** 초기 시스템 구축 난이도가 매우 높고, 분산 트랜잭션 관리(Distributed Transaction Management)를 위한 복잡한 오케스트레이션(Orchestration) 로직 설계 및 운영 역량이 필수적으로 요구된다. |
| **트레이드오프(Trade-offs)** | **[획득 장점]** 높은 기술적 유연성과 확장성 (Scalability & Resilience) $\leftrightarrow$ **[감수할 단점]** 복잡한 운영 환경 및 높은 초기 구축 비용 (Complexity & Overhead). 초기 단계에서 기술 부채(Technical Debt)를 최소화하고 장기적인 시장 적응성을 확보하는 방향으로 트레이드오프한다. |

## ⚠️ 잠재적 위험 분석

### 1. 제로 트러스트 기반의 보안 취약점 위험
- **설명:** 시스템이 너무 많은 외부 요소(다양한 벤더의 102A 장치, 외부 포털, 공급망 파트너)와 연결되어 있어, 만약 저수준 장치(Edge Device, 107A/107B) 중 단 하나라도 취약점(예: 기본 비밀번호, 패킷 조작)이 발견되거나 해킹될 경우, 전체 플랫폼(100)으로의 진입점을 제공하여 전체 시스템의 기밀성과 무결성을 위협할 수 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** '제로 트러스트 네트워크(Zero Trust Network)' 원칙을 적용한다. 모든 통신(Edge $\to$ Gateway, Gateway $\to$ Platform) 구간에 대해 강력한 인증(Mutual TLS, X.509 Certificate) 및 인가(Policy Engine)를 의무화하고, 네트워크 분할(Microsegmentation)을 통해 하나의 컴포넌트가 피해를 입더라도 시스템 전반으로 전파되지 않도록 격리한다.

### 2. 데이터 의미론적 불일치(Semantic Inconsistency) 위험
- **설명:** 다양한 출처(107A, 107B)의 장비는 각기 다른 제조사, 다른 측정 원리, 다른 데이터 명명 규칙을 사용한다. 이로 인해 '온도(Temperature)'라는 같은 속성이라도 A 장비에서는 섭씨를, B 장비에서는 화씨를 사용하거나, 측정 단위 자체가 명확하게 정의되지 않을 경우, 상위 데이터 분석 시스템이나 SCM 시스템에서 잘못된 비즈니스 결정을 내리게 할 수 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 수집 단계(Ingestion Layer)에서 **데이터 표준화/정규화 모듈(Data Normalization Module)**을 필수로 도입하고, 모든 데이터를 공통의 **산업 표준 데이터 모델(예: CIM, ISA-95 기반)**에 맞춰 강제 변환한다. 초기 단계에서 모든 데이터 포맷에 대한 엄격한 데이터 사전(Data Dictionary)을 구축하고 관리한다.

### 3. 실시간 데이터 처리 병목 현상(Ingestion Bottleneck) 위험
- **설명:** IoT 장비가 초당 수백, 수천 건에 달하는 대용량의 시계열 데이터를 순간적으로 대량 전송할 경우, 게이트웨이(102B)나 플랫폼 계층의 데이터 수집 버퍼(Kafka/MQ)에서 병목 현상이 발생할 수 있다. 이로 인해 데이터 손실이 발생하거나, 시스템 전체가 과부하로 인해 응답 지연(Latency)이 발생할 수 있다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 수집 계층(Data Ingestion)에 **버스트 방지(Burst Prevention)** 및 **Scale-Out** 전략을 적용한다. 데이터 메시징 큐는 반드시 분산형 메시지 브로커(예: Apache Kafka Cluster)를 사용하고, 장치 측에서는 데이터 전송 주기를 최적화하는 게이팅 알고리즘(Duty Cycling)을 적용하여 과부하를 예측하고 분산 처리한다.

### 4. 공급망 프로세스와 IoT 데이터의 결합 실패 위험
- **설명:** 본 시스템의 핵심 목표 중 하나인 '데이터 분석'과 '공급 체인 관리'의 통합이 실패할 경우, 현장에서 측정된 데이터(예: 사료 온도 변화, 재고 위치)가 단순히 보고서로 남는 데 그치고, 이것이 실제 주문, 발주, 경로 최적화와 같은 비즈니스 액션으로 이어지지 못하는 지능화 사일로(Intelligence Silo)가 발생한다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 데이터 분석 시스템을 단순한 리포팅 도구로 구축하지 않고, 분석 결과를 기반으로 **자동화된 워크플로우(Workflow)** 및 **의사결정 엔진(Decision Engine)**과 연결한다. 예를 들어, '사료 온도 경고' 발생 $\to$ '자동 발주 요청' $\to$ '공급망 시스템에 작업 티켓 생성'의 흐름을 정의하여 자동화된 비즈니스 피드백 루프를 구축한다.

### 5. 기술 표준 변화에 대한 시스템 비호환성 위험
- **설명:** IoT 및 스마트홈 분야는 Matter, OCF 등 새로운 개방 표준이 매우 빠르게 제정된다. 만약 시스템의 핵심 게이트웨이나 플랫폼이 특정 시대의 폐쇄적 프로토콜이나 레거시 기술에 너무 강하게 종속될 경우, 국제 표준으로 승인된 신기술(예: 2025년의 Matter 프로토콜)을 도입하거나 특정 시장에 진출하는 순간 심각한 비호환성(Incompatibility) 문제에 직면하게 된다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모든 외부 인터페이스와 통신 계층은 반드시 **플러그 앤 플레이(Plug-and-Play)** 원칙을 준수하고, **API 게이트웨이**를 통해 모든 표준화된 추상화 계층(Abstraction Layer)을 거치도록 강제한다. 모든 하드웨어/소프트웨어 결정을 할 때, 최소 3년 이상 유효할 것으로 예상되는 미래 표준 로드맵을 검토하고, 모듈화된 설계 원칙을 최우선으로 삼는다.
