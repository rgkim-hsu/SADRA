# ️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 확장 가능한 모듈형 환경 지수 산출 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜 또는 축사 환경 관리 시스템에서 일별 온습도지수(THI)와 같은 기본 환경 지수를 산출하는 동시에, 향후 추가될 수 있는 다양한 환경 요인(조도, 암모니아 농도 등)에 대한 영향도 지수를 유연하게 계산해야 하는 요구사항이 존재함. 단일 모놀리식 구조로는 새로운 지수 추가 시 시스템 전체의 재배포가 필요하여 유지보수 비용이 증가하는 아키텍처적 과제가 발생함.                                                                                                      |
| **결정(Decision)**       | `제어부(130)`를 중심으로 기본 기능을 담당하는 `디폴트 모듈(150)`과 추가 기능을 담당하는 `확장 모듈(160)`을 분리하는 **모듈형 플러그인 아키처**를 채택함. `제어부(130)`는 `환경 정보 입력부(110)`의 데이터를 수신하여 각 모듈로 라우팅하고, 각 모듈은 독립적인 계산 로직(`일별 온습도지수 계산부(152)`, `일별 추가영향지수 계산부(162)`) 및 전용 데이터베이스(`온습도 영향도 데이터베이스부(154)`, `추가 영향도 데이터베이스부(164)`)를 보유하도록 설계함.                          |
| **근거(Rationale)**      | 1. **확장성(Extensibility):** `확장 모듈(160)`을 도입함으로써 새로운 환경 변수가 추가되더라도 `제어부(130)`나 `디폴트 모듈(150)`의 수정 없이 독립적으로 기능을 추가할 수 있음.<br>2. **관심사의 분리(Separation of Concerns):** 기본 지수 산출 로직과 추가 지수 산출 로직을 물리적으로 분리하여 코드 복잡도를 낮추고 테스트 용이성을 높임.<br>3. **데이터 격리:** 영향도 데이터베이스를 분리(154, 164)하여 데이터 접근 권한 관리 및 성능 최적화를 모듈 단위로 수행 가능함. |
| **결과(Consequences)**   | 시스템의 유지보수성과 기능 확장성이 획기적으로 향상됨. 새로운 센서나 분석 알고리즘 도입 시 전체 시스템 중단 없이 `확장 모듈(160)`만 업데이트하면 됨. 반면, `제어부(130)`의 라우팅 로직이 복잡해지고, 모듈 간 데이터 일관성을 유지하기 위한 추가적인 오버헤드가 발생할 수 있음.                                                                                                                                                 |
| **트레이드오프(Trade-offs)** | 높은 확장성 및 모듈 독립성 확보 vs. 중앙 제어부의 복잡도 증가 및 분산 데이터 관리에 따른 일관성 유지 비용 상승.                                                                                                                                                                                                                                                |

---

## ⚠️ 잠재적 위험 분석

### 1. 제어부(130)의 중앙 집중식 병목 현상

- **설명:** `환경 정보 입력부(110)`로부터 들어오는 모든 데이터가 `제어부(130)`를 거쳐 `디폴트 모듈(150)`과 `확장 모듈(160)`로 분배됨. 데이터 입력 빈도가 높거나 모듈의 계산 부하가 증가할 경우, `제어부(130)`가 단일 장애점(SPOF)이 되어 전체 시스템의 응답 속도가 저하될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** `제어부(130)`에 비동기 메시지 큐(Message Queue) 도입하여 데이터 수신과 처리를 분리, `제어부`의 수평적 확장(Horizontal Scaling) 가능하도록 상태 비저장(Stateless) 설계 적용.
  
  ### 2. 확장 모듈(160) 인터페이스 불일치 및 통합 패
- **설명:** `확장 모듈(160)`이 `제어부(130)`와 통신하기 위한 표준 인터페이스(API)가 명확히 정의되지 않을 경우, 새로운 모듈 추가 시 데이터 형식 불일치나 프로토콜 오류로 인해 `제어부`가 데이터를 제대로 처리하지 못할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 모듈 간 통신을 위한 엄격한 계약(Contract) 정의 및 SDK 제공, 모듈 로딩 시 자동 유효성 검증(Validation) 로직 구현, 인터페이스 버전 관리 체계 도입.
  
  ### 3. 다중 데이터베이스 간 데이터 일관성 훼손
- **설명:** `환경 정보 데이터베이스부(120)`, `온습도 영향도 데이터베이스부(154)`, `추가 영향도 데이터베이스부(164)`가 물리적으로 분리되어 있을 때, `제어부(130)`의 트랜잭션 관리 패로 인해 일부 DB는 업데이트되고 일부는 실패하는 데이터 불일치 현상이 발생할 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 분산 트랜잭션 관리 프로토콜(2PC 또는 Saga 패턴) 적용, 또는 이벤트 소싱(Event Sourcing) 방식을 도입하여 최종 일관성(Eventual Consistency) 보장 및 롤백 메커니즘 구축.
  
  ### 4. 계산 로직 오류에 의한 잘못된 환경 제어 신호 출력
- **설명:** `일별 온습도지수 계산부(152)` 또는 `일별 추가영향지수 계산부(162)`의 알고리즘에 결함이 있거나 입력 데이터(`110`)의 센서 값이 왜곡된 경우, `출력부(140)`를 통해 잘못된 제어 신호(예: 환기 장치 오작동)가 전송되어 작물 또는 가축에 피해를 줄 수 있음.
- **심각도:**  High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 계산 결과에 대한 범위 검증(Range Check) 및 이상치 탐지(Anomaly Detection) 로직 추가, `출력부(140)` 전송 전 인간 승인(Human-in-the-loop) 또는 시뮬레이션 검증 단계 도입.
  
  ### 5. 추가 영향도 데이터베이스(164)의 스키마 변경 어려움
- **설명:** `확장 모듈(160)`의 특성상 다양한 종류의 추가 지수가 저장될 것으로 예상됨. 관계형 데이터베이스(RDBMS)를 사용할 경우, 새로운 지수 유형 추가마다 테이블 스키마를 변경해야 하여 유연성이 떨어질 수 있음.
- **심각도:**  Medium
- **발생 가능성:**  High
- **대응 방안:** `추가 영향도 데이터베이스부(164)`로 NoSQL(Document-store) 데이터베이스 활용을 검토하거나, EAV(Entity-Attribute-Value) 모델 적용하여 동적인 속성 저장 지원.
