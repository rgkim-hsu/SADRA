📋 ADR (Architecture Decision Record)

### ADR-001: 클라우드 기반 스마트팜 통합 데이터 파이프라인 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 다수의 농장(Farm)에서 센서(G/W 게이트웨이 경유)를 통해 외부기상정보, 내부환경정보(온도·습도·풍속·강수 등), 양액정보(EC·PH·급액량 등)가 이기종 프로토콜로 수집된다. 이 데이터를 농가용 스마트폰 앱(300), 농업데이터 관제시스템(200), 클라우드 AI 분석 엔진(100)이 동시에 소비해야 하므로, 단일 수집 경로로는 확장성과 실시간성을 동시에 충족하기 어렵다.                            |
| **결정(Decision)**       | G/W(게이트웨이) 계층에서 MQTT/REST 표준 프로토콜로 데이터를 정규화한 뒤, 클라우드 스트리밍 버스(Kafka 또는 AWS Kinesis 계열)를 중심으로 농업데이터 관제시스템(200)·AI 추론 엔진·병발생 예측 모듈이 독립적으로 구독하는 **이벤트 드리븐(Event-Driven) + 멀티 컨슈머 파이프라인** 구조를 채택한다. 데이터 수집 표준은 농촌진흥원 스마트팜 데이터 표준을 준수하며 스마트필코리아에 제공한다. |
| **근거(Rationale)**      | ① 센서 종류·농장 수 증가 시 G/W 계층만 수평 확장하면 되므로 파이프라인 전체를 재설계할 필요가 없다. ② AI 추론(이상현상 분석, 수확량 예측)과 병해 예측은 배치·스트림 혼합 처리가 필요하며, 이벤트 버스는 두 처리 모드를 동시에 지원한다. ③ 농촌진흥원 표준 준수로 공공 데이터 연계 및 인증 취득이 용이하다.                                                             |
| **결과(Consequences)**   | (+) 농가 앱·관제 대시보드·AI 모듈이 느슨하게 결합되어 독립 배포 가능. (+) 데이터 재처리(replay)로 모델 재학습 지원. (-) 이벤트 버스 운영 복잡도 증가. (-) 스키마 버전 관리 및 하위 호환성 유지 필요.                                                                                                                  |
| **트레이드오프(Trade-offs)** | **얻는 것:** 실시간 모니터링과 배치 AI 학습의 동시 처리, 컴포넌트 독립 확장. **감수할 것:** 메시지 브로커 인프라 추가 비용, 운영 엔지니어의 스트리밍 플랫폼 전문성 요구, 네트워크 지연 시 메시지 순서 보장 로직 필요.                                                                                                              |

### ADR-002: AI 기반 병해충 예측 모듈의 엣지-클라우드 하이브리드 추론 전략

| 항목                     | 내용                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 병발생 예측(도미노 병 발생 예측, 딸기 병 발생 예측)은 환경 변화 알고리즘·병발생 예측 모델·SW기술을 결합한다. 농촌 네트워크는 간헐적 단절이 빈번하고, 클라우드 전송 지연이 발생할 경우 골든타임(초기 방제 시점)을 놓칠 수 있다.                                            |
| **결정(Decision)**       | 경량화된 추론 모델(TFLite / ONNX Runtime)을 G/W 또는 현장 엣지 디바이스에 배포하여 **1차 로컬 추론**을 수행하고, 클라우드에서는 전체 데이터를 활용한 **2차 정밀 추론 및 모델 재학습**을 담당하는 하이브리드 구조를 채택한다. 알림은 농가용 스마트폰 앱(300)을 통해 푸시 제공한다. |
| **근거(Rationale)**      | ① 네트워크 단절 시에도 핵심 경보 기능 유지 가능(가용성 확보). ② 클라우드 전송 데이터량 감소로 통신 비용 절감. ③ 개인 농장 환경 데이터의 클라우드 전송 최소화로 데이터 주권 보호.                                                                      |
| **결과(Consequences)**   | (+) 오프라인 내성(Resilience) 확보. (+) 응답 지연 최소화. (-) 엣지 모델과 클라우드 모델 간 버전 동기화 관리 필요. (-) 엣지 디바이스 하드웨어 스펙 제약으로 모델 경량화 품질 손실 가능.                                                         |
| **트레이드오프(Trade-offs)** | **얻는 것:** 고가용성, 저지연 경보, 통신비 절감. **감수할 것:** 이중 모델 유지보수 부담, MLOps 파이프라인 복잡도 증가, 엣지 디바이스 보안 패치 관리 필요.                                                                              |

### ADR-003: 농업데이터 관제시스템(200)의 멀티테넌트 마이크로서비스 분리

| 항목                     | 내용                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 관제시스템(200)은 대시보드, 통계, 사용자관리, 회원관리, 센서관리, 외부기상데이터 연계, 농가용 스마트폰 앱 제공(정보관리·커뮤니티·모니터링 등) 등 이질적인 기능을 포함한다. 농장 수 증가 시 단일 모놀리식 구조는 특정 서비스의 부하가 전체 시스템에 영향을 준다.      |
| **결정(Decision)**       | 관제시스템을 **도메인별 마이크로서비스**(데이터 수집 서비스, 사용자/회원 서비스, 센서 관리 서비스, 통계/분석 서비스, 알림 서비스)로 분리하고, API Gateway를 단일 진입점으로 구성한다. 각 서비스는 독립 DB(Database per Service 패턴)를 가진다. |
| **근거(Rationale)**      | ① 통계 조회 폭증 시 해당 서비스만 스케일아웃 가능. ② 서비스별 독립 배포로 장애 격리(Fault Isolation) 실현. ③ 스마트폰 앱(300)과 웹 관제 UI가 동일 API를 공유하여 개발 중복 최소화.                                      |
| **결과(Consequences)**   | (+) 서비스별 독립 기술 스택 선택 자유도. (+) CI/CD 파이프라인 병렬화. (-) 분산 트랜잭션 처리(Saga 패턴 등) 필요. (-) 서비스 간 네트워크 홉 증가로 전체 응답 지연 가능성.                                              |
| **트레이드오프(Trade-offs)** | **얻는 것:** 탄력적 확장, 장애 격리, 팀별 독립 개발. **감수할 것:** 운영 복잡도, 분산 추적(Distributed Tracing) 도구 도입 필요, 초기 설계 비용 증가.                                                      |

⚠️ 잠재적 위험 분석
------------

### 1. G/W 단일 장애점(Single Point of Failure) 위험

* **설명:** 농장과 클라우드 사이의 G/W(게이트웨이)가 물리적 고장, 전원 차단, 펌웨어 오류로 중단될 경우 해당 농장의 모든 센서 데이터 수집이 완전히 중단된다. 특히 온실 내 고온·고습 환경에서 하드웨어 수명이 단축될 가능성이 높으며, 장애 발생 시 농가가 즉각적으로 인지하기 어렵다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** G/W 이중화(Active-Standby) 구성 및 하트비트 모니터링 구현. G/W 자체에 로컬 버퍼 스토리지(SD카드/SSD)를 탑재하여 네트워크 단절 시에도 데이터를 로컬 저장 후 복구 시 일괄 업로드(Store-and-Forward)하는 메커니즘 적용. 농가 앱(300)에 G/W 상태 실시간 알림 기능 추가.

### 2. AI 병해 예측 모델의 오탐(False Positive) / 미탐(False Negative) 위험

* **설명:** 병발생 예측 모듈이 학습 데이터의 지역적·품종적 편향으로 인해 실제 병해를 미탐(방치)하거나 정상 상태를 병해로 오탐(불필요한 방제 조치)할 수 있다. 미탐 시 작물 피해가 확산되고, 오탐이 반복되면 농가 신뢰도가 하락하여 시스템 자체를 사용하지 않게 되는 이탈 위험이 존재한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 예측 결과에 신뢰도 점수(Confidence Score)와 근거 데이터를 함께 제공하는 설명 가능한 AI(XAI) 적용. 농가별 피드백 루프(실제 병해 발생 여부 입력)를 앱(300)에 탑재하여 지속적 모델 재학습(MLOps) 파이프라인 구축. 초기에는 AI 단독 자동 조치를 지양하고 농가 확인 후 실행하는 Human-in-the-Loop 구조 유지.

### 3. 농가 센서 데이터 및 개인정보 유출 보안 위험

* **설명:** 농가의 생산량, 양액 정보(EC·PH), 수확 일정 등은 경쟁 농가 또는 유통 업체에 유출될 경우 직접적인 경제적 피해를 야기한다. G/W와 클라우드 간 통신이 암호화되지 않거나, 농가용 앱(300)의 인증 토큰이 탈취될 경우 제3자가 타 농장 데이터에 무단 접근할 수 있다. 특히 회원관리·사용자관리 서비스는 개인정보보호법 적용 대상이다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** G/W~클라우드 전 구간 TLS 1.3 암호화 및 디바이스 인증서 기반 mTLS 적용. 앱(300) 인증에 OAuth 2.0 + JWT(짧은 만료시간) 적용 및 Refresh Token Rotation 구현. 데이터 접근 제어를 농장 단위 RBAC(역할 기반 접근제어)로 설계하고, 개인정보 최소 수집 원칙 준수 및 정기 보안 감사 실시.

### 4. 클라우드 의존성 심화로 인한 서비스 가용성 위험

* **설명:** AI 추론, 병해 예측, 통계 분석, 앱 데이터 조회가 모두 클라우드(100)에 집중되어, 클라우드 사업자의 리전 장애 또는 네트워크 단절 시 농가의 모든 모니터링·제어 기능이 일시에 중단된다. 스마트팜 특성상 온도 관리 실패는 단시간 내 작물 고사로 이어질 수 있어 다운타임 허용 범위가 극히 짧다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 핵심 제어 로직(온도·습도 임계값 기반 자동화)은 G/W 또는 엣지 디바이스에 오프라인 실행 가능하도록 구현. 클라우드는 멀티 가용 영역(Multi-AZ) 배포 및 RTO/RPO 목표를 명확히 정의한 DR(재해복구) 계획 수립. 중요 알람은 클라우드 우회 SMS/LTE 직접 발송 경로 확보.

### 5. 데이터 수집 표준 미준수 및 이기종 센서 통합 위험

* **설명:** 개념도에서 농촌진흥원 스마트팜 데이터 수집 표준을 준수한다고 명시되어 있으나, 실제 현장에서는 제조사별로 센서 데이터 포맷, 단위, 샘플링 주기가 상이하다. 표준 미준수 센서가 연결될 경우 데이터 품질 저하, 파싱 오류, AI 모델 입력 오염이 발생하여 예측 정확도가 급격히 저하될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** G/W 계층에 데이터 정규화 어댑터(Adapter Pattern)를 구현하여 이기종 센서 데이터를 표준 스키마로 변환. 수집 단계에서 범위 검증·이상값 필터링·결측값 처리 로직을 포함한 데이터 품질 파이프라인 구축. 신규 센서 등록 시 표준 적합성 자동 검증 테스트 절차 의무화 및 인증된 센서 목록(Approved Device List) 관리.

### 6. 농가 디지털 리터러시 격차로 인한 시스템 활용도 저하 위험

* **설명:** 스마트폰 앱(300)이 대시보드, 통계, 모니터링, 커뮤니티, 정보관리 등 다양한 기능을 제공하지만, 고령 농업인의 경우 인터페이스 복잡성으로 인해 핵심 알림을 인지하지 못하거나, 잘못된 설정으로 오작동을 유발할 수 있다. 이는 시스템 투자 효과를 무력화하는 운영적 위험이다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 앱 UX를 핵심 알림 중심의 간소화된 기본 모드와 전문가용 상세 모드로 이원화. 음성 알림 및 큰 글씨 접근성 옵션 제공. 농촌진흥원 또는 지역 농업기술센터와 연계한 초기 온보딩 교육 프로그램 및 현장 지원 체계 구축. 앱 사용 패턴 분석을 통해 미활용 기능 식별 및 UI 지속 개선.
