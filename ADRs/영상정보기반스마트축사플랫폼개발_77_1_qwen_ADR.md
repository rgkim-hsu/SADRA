# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: [계층별 맞춤형 기능 서비스 아키텍처 (Tiered Functional Architecture)]

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 다양한 크기와 운영 특성을 가진 농가 (대형 5,000두 이상, 소규모 5,000두 미만, 종돈) 에 동일한 기능 세트만 제공하면 비용 효율성이 떨어집니다. 또한, 대형 농가의 고급 분석 기능 (질병 조기 감지 등) 과 소규모 농가의 기본 제어 기능이 혼재되어 유지보수 복잡도가 발생합니다.<br><br>시스템이 직면한 핵심 과제는 농가별 필요성 차이를 유연하게 수용하면서도 서비스 품질을 균일하게 유지하는 것입니다. |
| **결정 (Decision)** | 농가 유형과 규모에 따라 시스템 기능을 **Level 1 ~ Level 3**으로 계층화하고, 각 계층에 필수 기능과 선택 기능을 배정하는 아키텍처를 채택합니다.<br><br>- **대형 농가 (Level 3)**: 모든 기능 포함 (고급 분석, 자동화 제어 등)<br>- **중간/소규모 농가 (Level 1/2)**: 핵심 기능 위주로 제한 적용<br>- **종돈 농장**: 특정 기능 (임신률, 유전자 등) 강화 적용 |
| **근거 (Rationale)** | - **비용 효율성**: 초기 도입 비용을 최소화하면서도 확장성 확보.<br>- **유연성**: 농가별 실제 필요 (Need) 에 맞춘 서비스 제공 가능.<br>- **표준 준수**: TTA 등 국내 표준에서 제시된 데이터 수집 지침과 인터페이스 요구사항을 계층별로 적용하여 호환성 확보. |
| **결과 (Consequences)** | <ul><li><b>긍정적:</b> 초기 도입 장벽 감소, 농가별 맞춤형 솔루션 제공 가능.</li><li><b>부정적:</b> 각 계층의 기능 결합 로직 관리가 복잡해지고, 고수준 계층에서만 작동하는 API 개발 오버헤드가 발생할 수 있음.</li></ul> |
| **트레이드오프 (Trade-offs)** | **장점 (Pros):** 초기 비용 절감, 농가 수요에 대한 유연한 대응.<br>**단점 (Cons):** 모든 기능을 한 번에 제공하지 못해 일부 고급 분석 기능은 제한적일 수 있음. 표준화 가이드 (예: ISO/IEC 30141) 에서 권장하는 재사용 가능한 설계 원칙을 따르되, 비즈니스 요구사항에 따라 기능을 자르는 것이나 균형을 찾아야 함. |

### ADR-002: [IoT 표준 기반 상호운용성 프레임워크 (IoT Standard-based Interoperability Framework)]

| 항목 | 내용 |
|------|------|
| **상황 (Context)** | 스마트돈사는 다양한 센서 (온습도, 이불, 사료 등) 와 제어기를 사용해야 하며, 하드웨어 교체나 벤더 변경 시 시스템이 작동하지 않는 경우를 막아야 합니다. 문서에 언급된 ISO/IEC 30141:2024 와 oneM2M 표준은 상호운용성을 위해 필수적입니다.<br><br>또한, 데이터 수집과 전송 시 보안 (ETSI EN 303 645 등) 이 필수적입니다. |
| **결정 (Decision)** | 시스템 설계 시 **ISO/IEC 30141:2024 참조 아키텍처** 및 **TTA 단체표준**을 기반으로 통신 프로토콜 (MQTT, CoAP) 과 데이터 포맷 (JSON/XML) 을 표준화합니다.<br><br>- **에지 계층**: 표준화된 게이트웨이 인터페이스 사용.<br>- **플랫폼 계층**: 표준화된 API (RESTful, oneM2M) 노출.<br>- **보안 계층**: 인증 및 암호화 필수 구현. |
| **근거 (Rationale)** | - **재사용성**: 표준화된 설계 요소는 향후 시스템 확장 시 재사용 가능.<br>- **보안**: 국제 표준 (ITU-T X.1352 등) 을 준수하여 농가 데이터 유출 방지.<br>- **확장성**: 새로운 센서나 기기 유형을 추가할 때 별도의 아키텍처 변경 없이 플러그인 가능. |
| **결과 (Consequences)** | <ul><li><b>긍정적:</b> 하드웨어 벤더 변경 시 시스템 연동 비용 최소화, 타 플랫폼과의 연동 용이성 확보.</li><li><b>부정적:</b> 표준 프로토콜 준수에 따른 개발 시간 증가, 비표준 저가 기기는 지원 불가 가능성.</li></ul> |
| **트레이드오프 (Trade-offs)** | **장점 (Pros):** 장기적인 유지보수 비용 절감, 생태계 형성.<br>**단점 (Cons):** 초기 개발 속도 저하, 일부 구형或非표준 장비와의 연동 불가 (브릿지 필요). |

## ⚠️ 잠재적 위험 분석

### 1. [농가 데이터 프라이버시 및 보안 위험]
- **설명:** 스마트돈사 서비스는 농가별 생체 데이터 (질병, 출하량 등) 와 시설 제어 데이터를 수집합니다. 이 데이터가 제 3 자나 해커에게 유출될 경우 농가의 경쟁력 하락 및 법적 문제가 발생할 수 있습니다. 특히 종돈 농장의 유전 정보는 매우 민감합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **데이터 암호화:** 수집된 데이터를 전송 및 저장 시 모두 AES-256 등 강固한 암호화 적용.
    - **접근 제어:** 역할 기반 접근 제어 (RBAC) 를 적용하여 최소 권한 원칙 준수.
    - **규정 준수:** 개인정보보호법 및 농촌진흥청 관련 데이터 보호 가이드라인 준수.

### 2. [대형 농가의 시스템 가용성 및 확장성 위험]
- **설명:** 대형 양돈농가 (5,000 두 이상) 는 수많은 센서와 카메라가 연동됩니다. 센서 수량이 급증하거나 네트워크 트래픽이 폭주할 경우 시스템 지연 (Latency) 이 발생하거나 서비스가 마비될 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **에지 컴퓨팅 (Edge Computing):** 대용량 데이터 (CCTV 영상 등) 는 에지 장비를 통해 전처리 (필터링, 압축) 후만 전송하도록 설계.
    - **무중단 아키텍처 (HA):** 서버 및 DB 클러스터링을 적용하여 고가용성 (High Availability) 확보.
    - **로드 밸런싱:** 트래픽 분산 및 자동 스케일링 (Auto-scaling) 기능 구현.

### 3. [기능 간소화 (Tiering)에 따른 운영 효율성 저하 위험]
- **설명:** Level 1/2 계층 농가는 일부 고급 기능 (예: AI 질병 감지, 자동 사료 배급) 을 누릴 수 없습니다. 이로 인해 농가는 수동으로 작업을 해야 하거나 시스템의 한계를 우회해야 할 수 있으며, 이는 운영 효율성을 떨어뜨릴 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low
- **대응 방안:**
    - **확장성 있는 모듈 설계:** 기본 기능은 무조건 제공하며, 고급 기능은 '추가 패키지' 형태로 제공하는 유연한 아키텍처 적용.
    - **사용자 경험 (UX) 최적화:** 기능 없이도 기본 운영이顺畅하도록 UI/UX 단순화 및 자동화 로직 강화.

### 4. [센서 데이터 품질 및 상호운용성 위험]
- **설명:** 다양한 벤더의 센서를 지원해야 하지만, 표준화 (ISO/IEC 30141 등) 가 완벽하게 이루어지지 않을 경우 데이터 포맷이나 통신 프로토콜 호환성 문제가 발생할 수 있습니다. 이는 데이터 분석의 정확도를 떨어뜨립니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **정규화된 데이터 형식:** 모든 센서 데이터는 표준 포맷 (예: JSON Schema) 으로 변환 후 저장.
    - **브릿지 솔루션:** 비표준 장비에 대한 오픈소스 또는 자체 개발 게이트웨이 (Bridge) 를 활용하여 표준 프로토콜로 변환.

### 5. [공급망 의존성 (Vendor Lock-in) 위험]
- **설명:** 시스템이 특정 통신 모듈, 센서 프로토콜, 또는 클라우드 플랫폼 (e.g., AWS, Azure 등) 에 깊이 의존하게 되면, 해당 벤더의 정책 변경이나 가격 인상에 대응하기 어려울 수 있습니다.
- **심각도:** 🟢 Low
- **발생 가능성:** 🟢 Low
- **대응 방안:**
    - **멀티 클라우드 전략:** 핵심 데이터를 여러 클라우드나 온프레미스에 분산 저장.
    - **오픈소스 선호:** 가능한 경우 오픈소스 소프트웨어 활용하여 벤더 의존성 최소화.
    - **API 우선 설계:** 벤더 특정 기능보다는 오픈 API 를 사용하여 외부 시스템 연동 용이성 확보.
