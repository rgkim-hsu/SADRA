## 📋 ADR (Architecture Decision Record)

### **ADR-001: 중앙 집중형 데이터 저장소 및 모듈화 기능 설계 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 농업 데이터(환경, 로그, 전문가 데이터)를 실시간으로 수집·분석하여 재배 계획 및 예측 서비스를 제공해야 함. 분산된 데이터 소스와 다양한 분석 요구사항을 통합 관리해야 하며, 확장성 및 상호운용성을 보장해야 함. |
| **결정(Decision)** | 1) **중앙 집중형 Agricultural Information Repository**를 도입하여 모든 데이터 수집 및 저장을 단일화
2) **모듈화 기능 엔티티** (예: Prediction Functional Entity, Calculation Functional Entity)를 독립적으로 설계하여 재사용성 및 유지보수성을 높임
3) **이중 데이터 흐름** (Measured Data → Environment Monitoring Functional Entity → Repository → Data Analysis Function)을 채택하여 실시간 분석을 지원 |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준의 참조 아키텍처에서 중앙 집중형 데이터 저장소가 IoT 시스템의 확장성과 상호운용성을 보장하는 핵심 요소로 지정됨
- **oneM2M** 표준의 모듈화 원칙에 따라 기능별 엔티티를 분리하면 API 기반 통합이 용이해짐
- **ETSI EN 303 645** 보안 표준과 연계하여 중앙 저장소에 접근 제어를 강화할 수 있음 |
| **결과(Consequences)** | ✅ **장점**: 데이터 일관성 향상, 기능 재사용성 증가, 확장성 및 보안 강화
❌ **단점**: 초기 구축 비용 증가, 중앙 저장소의 단일 장애점(SPOF) 위험, 네트워크 병목 가능성 |
| **트레이드오프(Trade-offs)** | - **중앙화 vs 분산화**: 중앙 저장소로 인한 단일 장애점 위험을 감수하되, **KISA의 ITU-T X.1352 보안 기준**을 적용하여 미연방지
- **모듈화 vs 통합**: 기능별 엔티티 분리로 유지보수성을 높였으나, **API 관리 복잡성** 증가 |

### **ADR-002: 실시간 데이터 수집 및 이벤트 기반 처리 아키텍처**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 환경 데이터(온도, 습도 등)와 로그 데이터가 실시간으로 수집되어야 하며, 예측 모델은 지연 없이 분석 결과를 제공해야 함. 기존 배치 처리 방식으로는 요구사항을 충족할 수 없음. |
| **결정(Decision)** | 1) **이벤트 기반 데이터 수집** (MQTT/CoAP 프로토콜)을 채택하여 센서 데이터 실시간 전송
2) **스트리밍 처리** (예: Apache Kafka 또는 AWS Kinesis)를 도입하여 데이터 분석 지연 시간 최소화
3) **Prediction Functional Entity**는 **미들웨어 기반 호출** (예: RESTful API 또는 gRPC)으로 설계하여 실시간 응답 지원 |
| **근거(Rationale)** | - **IETF CoAP/MQTT** 표준이 IoT 환경의 경량 통신을 위한 공통 프로토콜로 지정됨
- **ISO/IEC 27030:2020** 보안 가이드라인에서 실시간 데이터 전송 시 암호화 및 인증이 필수적으로 요구됨
- **Matter/OCF** 표준의 상호운용성 원칙에 따라 프로토콜 선택이 유연하게 가능함 |
| **결과(Consequences)** | ✅ **장점**: 저지연 데이터 처리, 확장성 높은 아키텍처, 센서 데이터 손실 최소화
❌ **단점**: 네트워크 대역폭 증가, 이벤트 처리 복잡성, 보안 인증 오버헤드 |
| **트레이드오프(Trade-offs)** | - **MQTT vs CoAP**: MQTT의 pub/sub 모델로 확장성이 우수하나, CoAP의 RESTful 특성이 API 통합에 유리함
- **스트리밍 처리 vs 배치 처리**: 실시간 분석으로 지연 시간 감소하나, **자원 사용량 증가** |

### **ADR-003: 보안 및 접근 제어 모델**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 농업 데이터는 민감한 정보(예: 토지 데이터, 재배 계획)로서 보안이 필수적임. 또한, **ETSI EN 303 645** 및 **ITU-T X.1352** 표준을 준수해야 함. |
| **결정(Decision)** | 1) **역할 기반 접근 제어 (RBAC)**를 도입하여 Service Users 및 Service Provider의 권한을 세분화
2) **데이터 암호화** (TLS 1.3, AES-256) 및 **인증** (OAuth 2.0 + JWT)를 필수적으로 적용
3) **Agricultural Information Repository**에 대한 **API 게이트웨이**를 두어 모든 접근을 중앙 관리 |
| **근거(Rationale)** | - **ISO/IEC 27030:2020**에서 RBAC와 데이터 암호화가 필수적으로 요구됨
- **KISA의 ITU-T X.1352** 표준과 연계하여 글로벌 보안 인증 기준을 충족함
- **oneM2M** 표준의 보안 프레임워크에서 API 게이트웨이가 접근 제어의 핵심 요소로 지정됨 |
| **결과(Consequences)** | ✅ **장점**: 데이터 유출 위험 최소화, 글로벌 표준 준수, 유연한 권한 관리
❌ **단점**: 인증/인가 프로세스 복잡성 증가, 성능 오버헤드 |
| **트레이드오프(Trade-offs)** | - **JWT vs 세션 기반 인증**: JWT로 Stateless 설계 가능하나, 토큰 관리 복잡성 증가
- **API 게이트웨이 vs 마이크로서비스 직접 접근**: 보안 강화로 인한 성능 저하 |

## ⚠️ 잠재적 위험 분석

### **1. 중앙 저장소의 단일 장애점 (SPOF) 위험**
- **설명**: Agricultural Information Repository가 다운되면 전체 시스템의 데이터 수집 및 분석이 중단됨. 특히, 실시간 예측 서비스에 critical path로 작용함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **주/백업 저장소**를 구축하여 데이터 동기화 (예: AWS Multi-AZ 배포)
  - **데이터 캐싱 계층** (Redis) 도입으로 읽기 요청 분산
  - **자동 복구 메커니즘** (Kubernetes Self-Healing)을 적용

### **2. 네트워크 병목 및 대역폭 과부하**
- **설명**: 실시간 센서 데이터 수집과 스트리밍 처리가 네트워크 대역폭을 초과하여 시스템 지연 발생. 특히, 대량의 로그 데이터가 수집될 경우 문제 발생 가능성 높음.
- **심각도**: 🟡 Medium | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **Edge Computing** 도입으로 지역별 데이터 전처리 (예: 로컬 게이트웨이에서 필터링)
  - **MQTT QoS 레벨 조절** (QoS 1 대신 QoS 0 사용으로 오버헤드 감소)
  - **네트워크 모니터링 도구** (Prometheus + Grafana)로 병목 분석 및 예방

### **3. 모듈화 기능 간의 API 호환성 문제**
- **설명**: Prediction Functional Entity와 Calculation Functional Entity 간의 API 스키마 불일치로 통합 테스트 실패 또는 데이터 손실 발생 가능성.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **공통 API 스펙** (OpenAPI/Swagger)을 정의하고 CI/CD 파이프라인에 통합 테스트 자동화
  - **백워드 호환성 정책** 적용 (예: API 버전 관리)
  - **oneM2M 표준 API**를 참조하여 인터페이스 설계

### **4. 보안 인증 오버헤드 및 성능 저하**
- **설명**: RBAC와 JWT 기반 인증이 추가되면 API 호출마다 암호화/복호화 및 토큰 검증 과정이 발생하여 시스템 성능 저하.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (설계 시 고려 가능)
- **대응 방안**:
  - **캐싱된 토큰** (예: Redis에 저장된 JWT) 재사용
  - **성능 테스트** (Load Testing)를 통해 인증 오버헤드 측정 및 최적화
  - **하이브리드 인증** (예: 세션 기반 인증 + JWT) 도입

### **5. 데이터 일관성 및 동기화 지연**
- **설명**: 분산된 센서 데이터와 중앙 저장소 간의 동기화 지연으로 실시간 분석 결과의 신뢰성 저하. 특히, 예측 모델은 최신 데이터에 의존함.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 소싱 패턴** 도입으로 데이터 변경 이력을 추적
  - **CDC (Change Data Capture)** 도구 (Debezium)를 사용하여 실시간 동기화
  - **트랜잭션 일관성** 보장 (예: Saga 패턴 또는 분산 트랜잭션 관리)
