## 📋 ADR (Architecture Decision Record)

### ADR-001: 작업자-기계-IoT 데이터 통합을 위한 정규화된 관계형 데이터 모델 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 운영 환경에서 인적 자원(작업자 할당, 작업 계획 및 실적)과 물적 자원(농기계, IoT 태그 기반 이벤트)이 이질적인 데이터 소스로 분산 관리될 경우, 자원 활용 효율성 분석 및 작업 이력 추적(Traceability)에 구조적 한계가 발생함. 운영 계획과 실제 실행 데이터 간의 참조 무결성을 보장할 단일 진실 공급원(Single Source of Truth)이 요구됨.                                                                                  |
| **결정(Decision)**       | `sf_worker`, `sf_workplan`, `sf_machine`, `sf_msevent`, `sf_tag` 엔티티를 명시적 외래키(`WKCODE`, `WTCODE`, `TAG CODE`)로 연계한 정규화된 관계형(Relational) 데이터 모델을 핵심 운영 데이터 저장소로 채택함.                                                                                                                                     |

| **결과(Consequences)**   | **긍정적:** 데이터 일관성 및 참조 무결성 극대화, 운영 보고 및 규제 감사 추적 용이, 인적/물적 자원 연계 분석 인프라 즉시 마련.<br>**부정적:** 고빈도 IoT 이벤트(`sf_msevent`) 유입 시 관계형 DB의 쓰기 성능 병목 가능성 존재, 스키마 변경 시 마이그레이션 복잡도 및 운영 중단 리스크 발생.                                                                                                                   |
| **트레이드오프(Trade-offs)** | 높은 데이터 무결성 및 구조적 분석 효율성 vs. 실시간 대용량 시계열 데이터 처리 유연성 및 스키마 확장성. 향후 IoT 데이터 폭증 시 `sf_msevent`를 시계열 DB(Time-Series DB) 또는 데이터 레이크로 오프로딩하는 하이브리드 아키텍처로 진화할 수 있도록 핵심 트랜잭션 경로만 관계형에 유지하는 설계 유보 전략 적용.                                                                                                          |

## ⚠️ 잠재적 위험 분석

### 1. IoT 이벤트 집중 유입으로 인한 데이터베이스 쓰기 병목

* **설명:** `sf_msevent` 테이블은 기계 센서 및 태그(`sf_tag`)에서 발생하는 주기적 또는 이벤트 기반 데이터를 저장함. 스마트팜 확대 또는 센서 샘플링 주기 단축 시 초당 수천 건 이상의 INSERT/UPDATE가 집중될 경우, 관계형 DB의 로그 쓰기 및 인덱스 갱신 병목으로 인해 `sf_workplan` 업데이트 등 핵심 트랜잭션이 지연됨.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** `sf_msevent` 전용 쓰기 최적화 스토리지 엔진(InnoDB 버퍼 풀 튜닝, 파티셔닝) 적용. 장기적으로는 CDC(Change Data Capture) 또는 메시지 큐(Kafka/Pulsar)를 도입하여 IoT 이벤트를 비동기적으로 수집하고, 집계 후 배치로 관계형 DB에 적재하는 람다/카파 아키텍처 패턴 도입 검토.

### 2. 작업 계획(Workplan)과 실제 기계 이벤트(Msevent) 간 동기화 지연 및 불일치

* **설명:** `sf_workplan`은 사전 계획된 작업 일정 및 요구사항을 관리하나, 현장 기계의 실제 가동 상태(`sf_msevent`)는 예측 불가능한 변수(기상, 고장, 작업 지연)에 의해 변동됨. 실시간 상태 반영 지연 시 작업자(`sf_worker`) 할당 계획과 실제 기계 가동 간 미스매치가 발생하여 생산성 저하 및 리소스 낭비 초래.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** `sf_msevent` 스트림과 `sf_workplan` 상태를 비교 검증하는 실시간 동기화 에이전트 도입. 임계치 기반 알림(Webhook/SMS) 및 동적 재스케줄링 알고리즘 적용. 데이터 정합성 검증을 위한 주기적 배치 reconciliation job 운영.

### 3. 외래키 의존성으로 인한 단일 장애점(SPOF) 및 시스템 종속성 확대

* **설명:** `WKCODE`, `TAG CODE`, `WTCODE` 등 명시적 외래키로 모든 엔티티가 강결합되어 있음. 중앙 데이터베이스 장애 시 작업 계획 수립, 기계 상태 모니터링, 태그 기반 이력 조회 등 모든 스마트팜 운영 기능이 동시에 마비되며, 장애 복구 시 참조 무결성 검증 절차로 인해 RTO(Recovery Time Objective)가 길어질 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 읽기 전용 Replica DB 구성으로 모니터링 및 조회 트래픽 분리. 핵심 `sf_worker`, `sf_workplan` 테이블은 캐시 레이어(Redis)에热点 데이터 유지하여 DB 장애 시 제한적 운영 가능하도록 설계. 정기적 장애 복구(DR) drill 및 외래키 제약 조건 일시 해제 프로토콜 수립.

### 4. 농업 현장 네트워크 불안정으로 인한 태그 데이터 수집 손실 및 무결성 훼손

* **설명:** 스마트팜은 광활한 야외 환경에 배치되므로 LTE/LoRaWAN/Wi-Fi 연결이 불안정함. `sf_tag` 기반 기계 이벤트 전송 중 네트워크 단절 시 데이터 유실이 발생하며, 재전송 로직 부재 시 `sf_msevent`와 실제 물리적 작업 이력 간 갭(Gap)이 발생하여 품질 관리 및 작업자 성과 평가 정확도 저하.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 엣지 게이트웨이(Edge Gateway)에 로컬 버퍼링 및 오프라인 큐잉 메커니즘 도입. 네트워크 복구 시 시퀀스 번호 기반 중복 제거 및 순서 보장 재전송 구현. 데이터 수집 에이전트 헬스체크 및 자동 복구 스크립트 운영.

### 5. 권한 관리 부재로 인한 작업자/기계 제어 데이터 무단 접근 및 조작 위험

* **설명:** 현재 다이어그램에는 인증/인가 계층이 명시되지 않음. `sf_worker` 정보나 `sf_machine` 제어 이력이 평문 또는 무차별 접근 가능한 엔드포인트로 노출될 경우, 악의적 작업 계획 변조, 기계 원격 조작, 또는 작업자 개인정보 유출로 이어져 운영 안전성 및 법적 준수성(GDPR/개인정보보호법) 위반 가능성 존재.
* **심각도:** 🔴 High
* **발생 가능성:**  Medium
* **대응 방안:** RBAC(Role-Based Access Control) 기반 세분화된 접근 제어 정책 적용. 모든 API 호출에 OAuth2.0/JWT 인증 강제. `sf_worker` 개인정보 및 `sf_machine` 제어 명령은 전송 중(TLS 1.3) 및 저장 시(AES-256) 암호화. 접근 로그 감사(`sf_msevent` 확장 또는 별도 Audit 테이블) 및 이상 징후 탐지(SIEM) 연동.
