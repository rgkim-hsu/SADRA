## 📋 ADR (Architecture Decision Record)

### **ADR-001: 상태 기반 비동기 작업 처리 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | IoT 시스템에서 센서 기반 작업 처리 및 명령 실행 시 실시간 상태 관리와 비동기 처리 요구가 발생. 시스템은 작업의 생성부터 완료까지의 상태 전이를 명확히 관리해야 하며, 외부 명령(STOP COMMAND) 또는 센서 이벤트(A-SENSOR)에 따라 유연하게 대응해야 한다. |
| **결정(Decision)** | 1. **상태 기반 작업 처리 모델** 채택: 작업은 `NEW` → `WAITING` → `SENT` → `WORKING` → `STOPPING`으로 상태 전이를 통해 관리한다.<br>2. **이벤트 기반 종료 조건** 도입: `A-SENSOR` 또는 `STOP COMMAND`에 따라 작업이 비동기적으로 종료된다.<br>3. **자동 제어 및 명령 우선순위** 정의: `AUTO CONTROL` 또는 `NEW COMMAND`에 의한 작업 중단이 가능하도록 설계한다. |
| **근거(Rationale)** | - **IoT 표준 준수**: ISO/IEC 30141:2024의 참조 아키텍처에서 상태 관리와 이벤트 기반 처리 방식을 권장.<br>- **유연성 확보**: oneM2M 및 ETSI EN 303 645의 보안 및 상호운용성 요구를 충족하기 위해 센서/명령 기반 비동기 처리가 필수.<br>- **실시간 대응**: 스마트팜/축산 시스템에서 센서 데이터에 따른 즉각적인 제어가 요구되므로 상태 전이 모델이 적합. |
| **결과(Consequences)** | - **장점**: 시스템의 투명성과 디버깅 용이성 향상, 실시간 제어 가능.<br>- **단점**: 상태 관리 로직의 복잡성 증가, 이벤트 처리 지연 가능성.<br>- **트레이드오프**: 복잡성 증가로 인한 개발 비용 vs. 유연성 및 실시간성 요구 충족. |
| **트레이드오프(Trade-offs)** | - **상태 관리 오버헤드** vs. **실시간 제어 요구**: 상태 전이 로직을 최적화하여 오버헤드를 최소화.<br>- **이벤트 처리 지연** vs. **신뢰성**: 우선순위 큐를 도입하여 중요한 이벤트를 우선 처리. |

### **ADR-002: 센서 및 명령 기반 종료 조건 구현**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 작업 중 `A-SENSOR` 또는 `STOP COMMAND`에 따라 종료되어야 하는 경우, 시스템은 이러한 조건을 실시간으로 감지하고 처리해야 한다. |
| **결정(Decision)** | 1. **센서 이벤트 수신 모듈** 도입: `A-SENSOR`로부터의 데이터는 실시간으로 처리되어 작업 종료 신호로 변환.<br>2. **명령 우선순위 규칙** 정의: `STOP COMMAND`는 즉시 처리되며, `NEW COMMAND`는 현재 작업이 완료되면 적용.<br>3. **종료 상태 코드** 표준화: `FINISHED BY A-SENSOR`, `FINISHED BY STOP COMMAND`, `FINISHED NORMALLY` 등 명확한 상태 코드를 정의. |
| **근거(Rationale)** | - **보안 및 안정성**: ITU-T X.1352 및 ETSI EN 303 645의 보안 요구사항에 따라 명령 및 센서 데이터의 무결성을 보장.<br>- **스마트팜/축산 시스템 요구**: 생체 데이터나 환경 센서에 따른 즉각적인 제어가 필수.<br>- **국내 표준 준수**: TTA의 스마트팜 데이터 상호운용 프레임워크와 일치. |
| **결과(Consequences)** | - **장점**: 시스템의 안정성 및 신뢰성 향상, 보안 이슈 최소화.<br>- **단점**: 센서 및 명령 처리 로직의 복잡성 증가.<br>- **트레이드오프**: 보안 강화 vs. 시스템 복잡성. |
| **트레이드오프(Trade-offs)** | - **센서 데이터 처리 지연** vs. **신뢰성**: 에지 컴퓨팅을 활용하여 지역 처리 지연을 줄임.<br>- **명령 충돌** vs. **안정성**: 우선순위 큐와 락 메커니즘을 도입하여 명령 충돌 방지. |

## ⚠️ 잠재적 위험 분석

### **1. 상태 전이 로직 오류**
- **설명**: 상태 전이 로직의 버그로 인해 작업이 예상치 못한 상태로 전이되어 시스템 장애 발생 (예: `WORKING` 상태에서 `WAITING`으로 잘못 전이).
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **단위 테스트 강화**: 상태 전이 로직에 대한 자동화된 테스트 케이스 추가.
  - **로그 및 모니터링**: 모든 상태 전이를 로그로 기록하고 실시간 모니터링 시스템 구축.
  - **rollback 메커니즘**: 오류 발생 시 이전 상태로 자동 복구.

### **2. 센서 데이터 오류 또는 지연**
- **설명**: `A-SENSOR`로부터의 데이터 오류 또는 네트워크 지연으로 인해 작업 종료가 지연되거나 오류 발생.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **데이터 유효성 검사**: 센서 데이터에 대한 체크섬 및 유효성 검사 추가.
  - **재시도 메커니즘**: 데이터 수신 실패 시 자동 재시도 및 경고 알림.
  - **에지 처리**: 센서 데이터 지역 처리(에지 컴퓨팅)하여 네트워크 지연 최소화.

### **3. 명령 충돌 및 우선순위 문제**
- **설명**: 동시에 수신된 `STOP COMMAND`와 `NEW COMMAND`로 인해 작업 처리 순서가 혼선되어 시스템 불일치 발생.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **우선순위 큐**: 명령에 우선순위를 부여하고 FIFO/우선순위 기반 처리.
  - **락 메커니즘**: 작업 처리 중인 동안 다른 명령이 중복 실행되지 않도록 락 적용.
  - **명령 큐 모니터링**: 실시간으로 명령 큐 상태를 모니터링하고 병목 현상 방지.

### **4. 보안 취약성 (외부 명령 위조)**
- **설명**: 네트워크 공격으로 인해 위조된 `STOP COMMAND` 또는 `NEW COMMAND`가 실행되어 시스템이 비정상 종료.
- **심각도**: 🔴 High
- **발생 가능성**: 🟢 Low (보안 강화 시)
- **대응 방안**:
  - **인증 및 암호화**: 모든 명령과 센서 데이터에 대해 TLS/SSL 및 디지털 서명 적용.
  - **접근 제어**: 명령 발행에 대한 RBAC(역할 기반 접근 제어) 구현.
  - **이상행동 감지**: AI 기반 이상행동 감지 시스템 도입.

### **5. 시스템 확장성 문제**
- **설명**: 작업 처리량이 증가함에 따라 상태 관리 및 이벤트 처리 로직이 병목 현상을 일으켜 시스템 성능 저하.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🔴 High (장기적)
- **대응 방안**:
  - **미들웨어 분리**: 상태 관리 로직을 독립적인 미들웨어로 분리하여 확장성 확보.
  - **마이크로서비스 아키텍처**: 작업 처리 모듈을 독립적인 서비스로 분할하여 수평 확장 가능.
  - **로드 테스트**: 시스템 부하 테스트를 통해 병목 지점 식별 및 최적화.

  - **명령 큐 모니터링**: 실시간으로 명령 큐 상태를 모니터링하고 병목 현상 방지.
