📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 센서-모니터링-클라우드 연계를 위한 경량 IoT 기반 3계층 아키텍처

| 항목                     | 내용                                                                                                                                                                                            |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 시스템은 센서 측정장치(100), 모니터링 장치(300), 정보 제공 서버(400), 사용자 기기(20)로 구성된다. 센서 데이터는 모니터링 장치를 통해 수집 및 1차 처리되고, 이후 서버로 전달되어 사용자에게 제공된다. 핵심 과제는 저전력 IoT 환경에서 안정적인 데이터 수집과 사용자 전달까지의 효율적인 데이터 흐름을 구축하는 것이다. |
| **결정(Decision)**       | 센서 계층 → 엣지(모니터링 장치) → 클라우드(정보 제공 서버) → 사용자 계층으로 구성된 3계층 IoT 아키텍처를 채택한다. 엣지 계층에서 데이터 필터링 및 1차 분석을 수행하고, 클라우드에서는 데이터 저장 및 서비스 제공을 담당하도록 역할을 분리한다.                                               |
| **근거(Rationale)**      | IoT 환경에서는 센서 데이터의 양이 많고 네트워크 자원이 제한적이므로, 엣지에서 사전 처리하는 것이 효율적이다. 클라우드는 확장성과 접근성을 제공하며, 사용자 기기는 다양한 인터페이스로 데이터를 소비할 수 있다.                                                                       |
| **결과(Consequences)**   | 네트워크 부하 감소 및 응답 속도 개선 효과가 있으며, 확장 가능한 구조를 확보한다. 그러나 엣지와 클라우드 간 데이터 동기화 및 관리 복잡성이 증가한다.                                                                                                        |
| **트레이드오프(Trade-offs)** | 효율적인 데이터 처리(장점) vs 아키텍처 복잡성 증가(단점), 확장성 확보(장점) vs 운영 관리 비용 증가(단점)                                                                                                                             |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 센서 데이터 신뢰성 문제

* **설명:** 센서 측정장치(100)의 오작동 또는 노이즈로 인해 부정확한 데이터 수집

* **심각도:** 🔴 High

* **발생 가능성:** 🔴 High

* **대응 방안:** 센서 보정, 다중 센서 적용, 데이터 필터링

### 2. 엣지 장치 장애

* **설명:** 모니터링 장치(300) 장애 시 데이터 수집 및 전달 중단

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 장치 이중화, 로컬 저장 및 재전송 기능

### 3. 네트워크 연결 불안정

* **설명:** 엣지와 서버 간 무선 통신 장애로 데이터 전송 실패

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 재전송 메커니즘, 데이터 버퍼링, 다중 통신 채널

### 4. 서버 과부하

* **설명:** 정보 제공 서버(400)에 데이터 요청이 집중되어 성능 저하

* **심각도:** 🟡 Medium

* **발생 가능성:** 🔴 High

* **대응 방안:** 오토스케일링, 캐싱, CDN 적용

### 5. 보안 취약점 (IoT 및 클라우드)

* **설명:** 데이터 전송 구간 또는 서버에서 해킹으로 데이터 유출 가능성

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 암호화 통신(TLS), 디바이스 인증, 접근 제어 강화

### 6. 사용자 서비스 지연

* **설명:** 사용자 기기(20)에서 데이터 조회 시 응답 지연 발생

* **심각도:** 🟡 Medium

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 캐싱 전략, API 최적화, 데이터 압축 전송
