===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 영상 기반 스마트팜 모니터링을 위한 중앙 처리형 스트리밍 아키텍처

| 항목                     | 내용                                                                                                                                                                                                                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 시스템은 카메라(316, 414)를 통해 촬영된 영상을 중앙 프로세서(421)로 전달하고, 이를 디스플레이 제어기(449), 단일-와식 입력 선택부(435), 사진 콘텐츠 펌프(428), 비디오 콘텐츠 펌프(426, 442) 등으로 분배하는 구조이다. 스마트팜 환경에서는 작물 상태, 병충해, 생육 상황을 실시간 영상으로 분석하고 사용자에게 제공해야 하며, 다양한 출력 장치와 콘텐츠 처리 모듈 간의 효율적인 데이터 흐름 관리가 핵심 과제이다. |
| **결정(Decision)**       | 중앙 프로세서 기반의 스트리밍 허브 아키텍처를 채택하고, 영상 데이터 처리는 파이프라인 방식(ingest → processing → distribution)으로 구성한다. 카메라 입력은 표준화된 인터페이스로 수집하고, 콘텐츠 펌프 모듈을 통해 영상/이미지를 분리 처리하며, 디스플레이 및 외부 인터페이스로는 이벤트 기반으로 전달하는 구조를 적용한다.                                                      |
| **근거(Rationale)**      | 영상 데이터는 대역폭과 처리량 요구가 높기 때문에 중앙에서 일관된 파이프라인으로 관리하는 것이 효율적이다. 콘텐츠 펌프 구조는 확장성과 재사용성을 높이며, 다양한 출력 장치(디스플레이, 저장소 등)에 유연하게 대응할 수 있다.                                                                                                                           |
| **결과(Consequences)**   | 영상 처리 흐름이 명확해지고 확장성이 향상된다. 그러나 중앙 프로세서 부하가 증가하며, 고성능 하드웨어 요구사항이 발생한다.                                                                                                                                                                                    |
| **트레이드오프(Trade-offs)** | 처리 일관성 및 관리 용이성(장점) vs 중앙 집중 부하 증가(단점), 확장성 확보(장점) vs 초기 구축 비용 증가(단점)                                                                                                                                                                                    |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 중앙 프로세서 과부하

* **설명:** 다수의 카메라 영상이 동시에 입력되면서 중앙 프로세서(421)의 CPU/GPU 자원이 부족해지는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🔴 High

* **대응 방안:** GPU 가속, 분산 처리 도입, 스트림 샤딩 및 로드 밸런싱 적용

### 2. 영상 데이터 지연 및 프레임 손실

* **설명:** 네트워크 대역폭 부족 또는 처리 지연으로 인해 영상이 끊기거나 지연되는 문제

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 압축 코덱 최적화(H.264/H.265), QoS 적용, 엣지 캐싱 도입

### 3. 카메라 장치 장애

* **설명:** 카메라(316, 414) 또는 카메라 제어기(414) 고장 시 영상 수집 불가

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 카메라 이중화, 상태 모니터링, 장애 감지 및 자동 전환

### 4. 콘텐츠 처리 모듈 간 데이터 불일치

* **설명:** 사진 콘텐츠 펌프(428)와 비디오 콘텐츠 펌프(426, 442) 간 처리 타이밍 차이로 데이터 싱크 불일치 발생

* **심각도:** 🟡 Medium

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 타임스탬프 기반 동기화, 버퍼링 전략 적용

### 5. 보안 취약점 (영상 데이터 유출)

* **설명:** 카메라 스트림이 외부로 유출되거나 무단 접근되는 경우

* **심각도:** 🔴 High

* **발생 가능성:** 🟡 Medium

* **대응 방안:** 스트림 암호화(RTSP over TLS), 접근 제어, 네트워크 분리

### 6. 디스플레이 출력 오류

* **설명:** 디스플레이 제어기(449) 오류로 인해 사용자에게 잘못된 영상 또는 정보 제공

* **심각도:** 🟡 Medium

* **발생 가능성:** 🟢 Low

* **대응 방안:** 출력 검증 로직, UI 상태 모니터링, 장애 시 재시작 메커니즘 적용
