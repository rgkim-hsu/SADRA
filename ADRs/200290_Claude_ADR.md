📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트팜 통합 관리를 위한 All-In-One 클라우드 플랫폼 채택

| 항목                     | 내용                                                                                                                                                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 양액 농도(EC, pH), 배액량, 무게 등 다양한 근권·배지·농업기상 환경 데이터가 MW0~MW8 등 복수의 수집 모듈에서 실시간으로 생성된다. 이 이기종 데이터를 단일 시스템에서 수집·분석·서비스로 연결하는 통합 아키텍처가 필요하다.                                                                 |
| **결정(Decision)**       | 데이터 수집(MW 모듈) → 스마트 재배환경 시스템 → All-In-One 플랫폼(데이터 보안·수집·분석 기능 + 근관광정 DBMS + 수집 DBMS) → Cloud 플랫폼(Open API 서비스) → Application/WEB/Mobile 서비스 계층으로 이어지는 계층형 통합 아키텍처를 채택한다.                                        |
| **근거(Rationale)**      | ① UI/UX 지시 모듈과 DATA 처리 모듈의 명확한 분리로 관심사 분리(SoC) 실현 ② 클라우드 기반 플랫폼화로 일반농가 S/W, WEB S/W, Mobile 등 다채널 서비스 일원화 ③ Open API(공공API, ML API, 부석API) 제공으로 외부 연계 확장성 확보 ④ 근관광정 DBMS와 수집 DBMS 분리로 운영 데이터와 분석 데이터의 I/O 경합 방지 |
| **결과(Consequences)**   | (+) 농가·농업 컨설턴트·시스템 관리자가 단일 플랫폼에서 모든 재배 데이터에 접근 가능 / (+) Open API를 통한 제3자 서비스 생태계 구성 용이 / (-) 플랫폼 단일 장애점(SPOF) 발생 시 전 계층 서비스 중단 위험 / (-) MW 모듈 수 증가에 따른 수집 미들웨어 병목 가능성                                           |
| **트레이드오프(Trade-offs)** | 【얻는 것】 운영 단순화, 데이터 일관성, 다채널 서비스 확장성 / 【감수할 것】 플랫폼 복잡도 증가, 클라우드 의존성 심화, 초기 구축 비용 및 마이그레이션 리스크                                                                                                                    |

### ADR-002: 엣지-클라우드 하이브리드 데이터 수집 구조 채택

| 항목                     | 내용                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | MW0~MW8 수집 모듈은 농장 현장(엣지)에 위치하며, 양액 중량·EC·pH·온습도·광량 등 고빈도 센서 데이터를 실시간으로 처리해야 한다. 네트워크 불안정 구간에서도 재배 제어의 연속성이 보장되어야 한다.           |
| **결정(Decision)**       | 현장 MW 모듈에서 1차 수집 및 로컬 저장(수집플릭터 DB)을 수행하고, 클라우드라인드 서버 통신 제어 프로그램을 통해 Cloud 플랫폼의 수집 DBMS로 배치 또는 스트리밍 동기화하는 엣지-클라우드 이중화 구조를 채택한다. |
| **근거(Rationale)**      | ① 농업 환경 특성상 농촌 인터넷 회선 불안정 빈번 → 엣지 버퍼링으로 데이터 유실 방지 ② 중량 기반 양액 제어는 ms 단위 응답이 필요하므로 엣지 로컬 처리가 필수 ③ 클라우드 전송은 분석·통계 목적으로 지연 허용 가능   |
| **결과(Consequences)**   | (+) 네트워크 단절 시에도 현장 제어 연속성 유지 / (+) 클라우드 부하 감소 / (-) 엣지-클라우드 간 데이터 정합성 관리 복잡도 증가 / (-) MW 펌웨어 및 로컬 DB 유지보수 비용 발생                |
| **트레이드오프(Trade-offs)** | 【얻는 것】 현장 제어 가용성, 네트워크 장애 내성 / 【감수할 것】 데이터 동기화 충돌 처리 로직 필요, 이중 인프라 운영 부담                                                       |

### ADR-003: 기능별 DBMS 분리 설계 (수집 DBMS / 근관광정 DBMS)

| 항목                     | 내용                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 실시간 센서 데이터 수집(고빈도 쓰기)과 생육 이력·환경 분석(복잡한 읽기 쿼리)이 동일 DB에서 수행될 경우 I/O 경합으로 양쪽 성능이 모두 저하된다.                                                |
| **결정(Decision)**       | 수집 DBMS(생육정보·농업지동물·공공DB)와 근관광정 DBMS(시물생장정보·환경정보·분석정보·통계/미래정보)를 물리적으로 분리하고, 외부정보 수집 기능(외부연도 DB IF, 변동 관리, 환경관리, 압락관리)을 별도 수집 경로로 구성한다. |
| **근거(Rationale)**      | CQRS(Command Query Responsibility Segregation) 패턴 적용으로 쓰기 최적화 DB와 읽기 최적화 DB를 분리, 각각의 인덱싱·파티셔닝 전략을 독립적으로 최적화 가능                        |
| **결과(Consequences)**   | (+) 분석 쿼리가 수집 성능에 영향 미치지 않음 / (+) 각 DBMS 독립 스케일아웃 가능 / (-) 두 DBMS 간 데이터 일관성 보장을 위한 동기화 파이프라인 필요                                       |
| **트레이드오프(Trade-offs)** | 【얻는 것】 수집·분석 성능 독립 최적화 / 【감수할 것】 운영 DBMS 수 증가, ETL 파이프라인 관리 부담                                                                        |

⚠️ 잠재적 위험 분석
------------

### 1. All-In-One 플랫폼 단일 장애점(SPOF) 위험

* **설명:** 데이터 보안 기능·수집 기능·분석 기능이 단일 All-In-One 플랫폼에 집중되어 있어, 해당 플랫폼의 장애 발생 시 일반농가 S/W, WEB S/W, Mobile 서비스가 동시에 중단되고 현장 양액 제어 명령 전달이 불가능해지는 전면 서비스 장애가 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 플랫폼 핵심 컴포넌트(데이터 수집·제어 기능)를 Active-Active 이중화 구성으로 배포하고, 현장 MW 모듈의 엣지 자율 제어 모드(클라우드 단절 시 로컬 룰 기반 제어)를 의무 구현한다. Circuit Breaker 패턴을 적용하여 장애 전파를 차단한다.

* * *

### 2. MW 모듈 펌웨어 보안 취약점 및 물리적 훼손 위험

* **설명:** 농장 현장에 설치된 MW0~MW8 수집 모듈은 물리적 접근이 용이한 환경에 노출되어 있다. 펌웨어 업데이트 채널이 암호화되지 않거나, 디바이스 인증 없이 통신할 경우 공격자가 허위 양액 중량 데이터를 주입하여 작물 고사 또는 과잉 양액 공급을 유발할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 각 MW 모듈에 디바이스 고유 인증서(X.509) 기반 mTLS 통신을 적용하고, 펌웨어 서명 검증(Secure Boot) 메커니즘을 도입한다. 데이터 수집 계층에서 이상치 탐지(Anomaly Detection) 로직을 적용하여 물리 센서값과 통계적으로 이탈된 값을 자동 격리한다.

* * *

### 3. 엣지-클라우드 데이터 동기화 정합성 오류 위험

* **설명:** 네트워크 단절 후 MW 로컬 DB(수집플릭터)와 클라우드 수집 DBMS 간 재동기화 과정에서 타임스탬프 충돌, 중복 레코드 삽입, 또는 순서 역전이 발생할 경우 근관광정 DBMS의 생육 이력 분석 결과가 왜곡되어 잘못된 시비·관수 처방으로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 이벤트 소싱(Event Sourcing) 패턴을 적용하여 모든 수집 이벤트에 단조 증가 시퀀스 번호를 부여하고, 재동기화 시 Last-Write-Wins가 아닌 시퀀스 기반 머지 전략을 사용한다. 동기화 후 체크섬 검증 프로세스를 자동화한다.

* * *

### 4. Open API 남용 및 농업 데이터 무단 유출 위험

* **설명:** Cloud 플랫폼의 Open API(공공API, ML API, 부석API)가 외부에 공개될 경우, API 키 관리 미흡이나 인증 우회 취약점을 통해 특정 농가의 생육 데이터, 생산량 정보, 재배 노하우가 경쟁사 또는 악의적 제3자에게 유출될 수 있다. 농업 데이터는 농가 경쟁력과 직결되는 민감 자산이다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** API Gateway 계층에서 OAuth 2.0 + RBAC(역할 기반 접근 제어)를 강제 적용하고, 농가별 데이터 테넌시(Multi-tenancy) 격리를 DB 스키마 레벨에서 구현한다. API 호출 로그를 SIEM에 연동하여 비정상 접근 패턴을 실시간 탐지한다.

* * *

### 5. 미들데이터 관리 프로그램 병목으로 인한 실시간 제어 지연 위험

* **설명:** MW0~MW8 전 모듈의 데이터가 단일 미들데이터 관리 프로그램과 데이터 관리 프로그램을 통해 처리될 경우, 영농 최성수기(모종 이식, 수확기)에 수집 데이터량이 급증하면 처리 큐 포화로 양액 제어 명령 응답이 수 초~수십 초 지연되고 중량 제어 정밀도가 저하되어 작물 피해가 발생할 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 미들웨어 계층을 제어 경로(Control Path, 저지연 우선)와 데이터 경로(Data Path, 처리량 우선)로 분리한다. 제어 메시지는 MQTT QoS 2 또는 전용 메시지 큐(경량 브로커)로 처리하고, 수집 데이터는 Kafka 등 고처리량 스트리밍 플랫폼으로 분기하여 상호 영향을 차단한다.

* * *

### 6. 외부 공공 DB 연계 의존성으로 인한 서비스 불안정 위험

* **설명:** 외부정보 수집 기능이 기상청·농촌진흥청 등 공공 DB에 의존하는 구조에서, 공공 API 서비스 장애·스펙 변경·폐기 발생 시 농업 기상 환경 데이터 수집이 중단되어 기상 연계 양액 처방 알고리즘이 오작동하거나 비활성화될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 외부 공공 API 호출부에 Adapter 패턴을 적용하여 인터페이스 변경 시 내부 코드 수정을 최소화한다. 최근 72시간 기상 데이터를 로컬 캐시에 보관하는 폴백(Fallback) 전략을 구현하고, 공공 API 헬스체크 모니터링 및 대체 데이터 소스(민간 기상 API)를 사전 계약으로 확보한다.
