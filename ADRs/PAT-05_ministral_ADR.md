## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 센서 및 제어 데이터 통합 플랫폼 구축 방식 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **스마트팜/농업 IoT 환경**에서 센서 및 제어 장치로부터 실시간 데이터를 수집하여 작물 관리, 마케팅 전략 반영, 지역별 데이터 생성까지 처리해야 함. 기존 시스템은 데이터 수집과 처리 과정이 분리되어 있어 **데이터 일관성 저하** 및 **지연 시간 증가** 문제가 발생함. 또한, **오류 탐지 및 사용자 입력 반영**이 실시간으로 이루어지지 않아 운영 효율성이 떨어짐. |
| **결정(Decision)** | 1. **통합 데이터 수집 레이어** 구축: 센서/제어 데이터 수신(S21)과 오류 탐지(S22)를 단일 모듈로 통합하여 **실시간 데이터 처리**를 보장함.
2. **이중 데이터 검증 메커니즘** 도입: 오류 데이터 탐지(S22)에서 **ML 기반 이상치 탐지 모델**을 적용하여 신뢰성 향상.
3. **모듈형 아키텍처** 채택: 사용자 입력(S23), 모델링 데이터 생성(S24), 마케팅 전략 반영(S25)을 **독립적 마이크로서비스**로 설계하여 확장성 및 유지보수성을 높임.
4. **지역별 데이터 생성 모듈(S26)** 별도 구축: **지리적 분산 처리**를 통해 지역별 최적화된 관리 데이터를 생성함. |
| **근거(Rationale)** | - **ISO/IEC 30141:2024** 표준에 따라 **재사용 가능한 설계**와 **모듈형 아키텍처**를 적용하여 상호운용성을 보장함.
- **oneM2M** 및 **ETSI EN 303 645** 표준을 준수하여 **보안 및 데이터 무결성**을 강화함.
- **TTA 스마트팜 표준**에 따라 **데이터 상호운용 프레임워크**를 구축하여 국내외 표준과의 호환성을 확보함.
- **KISA 보안 기준**을 적용하여 **IoT 기기 보안**을 강화함. |
| **결과(Consequences)** | ✅ **장점**:
- 실시간 데이터 처리 및 오류 탐지를 통해 **시스템 신뢰성** 향상.
- 모듈형 설계로 **확장성** 및 **유지보수성** 개선.
- 지역별 데이터 생성으로 **관리 효율성** 증가.
- 표준 준수로 **글로벌 상호운용성** 확보. |
| **트레이드오프(Trade-offs)** | ❌ **단점**:
- 초기 구축 비용 증가 (통합 레이어 및 보안 강화).
- 모듈간 통신 지연 가능성 (이중 검증 메커니즘으로 완화). |

### **ADR-002: 작물 모델링 데이터 생성 방식 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 작물 모델링 데이터(S24)는 **사용자 입력**과 **센서 데이터**를 기반으로 생성되어야 함. 그러나 현재 시스템은 **정적 모델**을 사용하고 있어 **실시간 환경 변화 반영**이 어려움. 또한, **마케팅 전략(S25)**과 연계되지 않아 **출하 계획 최적화**가 어려움. |
| **결정(Decision)** | 1. **실시간 ML 모델** 도입: **LSTM/Transformer 기반** 예측 모델을 사용하여 **동적 작물 모델링**을 지원함.
2. **피드백 루프 통합**: 마케팅 전략 반영(S25)에서 생성된 데이터를 **모델 학습에 재사용**하여 지속적 개선.
3. **에지 컴퓨팅 활용**: 지역별 관리 데이터 생성(S26)에서 **로컬 처리**를 통해 지연 시간 최소화. |
| **근거(Rationale)** | - **ISO/IEC 27030:2020** 보안 가이드라인 준수하여 **데이터 무결성** 보장.
- **IEEE 2413** 표준에 따라 **IoT 시스템 아키텍처 프레임워크**를 적용함.
- **TTA 스마트팜 데이터 표준**에 따라 **데이터 포맷 및 인터페이스**를 정의함. |
| **결과(Consequences)** | ✅ **장점**:
- 실시간 예측 모델로 **관리 효율성** 향상.
- 피드백 루프로 **지속적 학습** 가능.
- 에지 컴퓨팅으로 **지연 시간 감소**. |
| **트레이드오프(Trade-offs)** | ❌ **단점**:
- ML 모델 학습에 **추가 컴퓨팅 리소스** 필요.
- 모델 업데이트 시 **데이터 재학습** 비용 발생. |

### **ADR-003: 마케팅 및 출하 전략 반영 메커니즘 결정**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 현재 시스템은 **마케팅 전략(S25)**이 **정적**으로 적용되어 **시장 동향 반영**이 어려움. 또한, **지역별 데이터(S26)**와 연계되지 않아 **지역별 최적화**가 불가능함. |
| **결정(Decision)** | 1. **실시간 마케팅 API** 통합: **외부 시장 데이터**를 실시간으로 수집하여 전략 반영.
2. **지역별 가중치 적용**: S26에서 생성된 데이터에 따라 **출하 우선순위** 동적으로 조정.
3. **블록체인 기반 데이터 무결성**: 마케팅 데이터 변조 방지를 위해 **블록체인 로깅** 적용. |
| **근거(Rationale)** | - **oneM2M API 표준** 준수하여 **외부 시스템 연동** 가능.
- **ETSI EN 303 645** 보안 표준을 적용하여 **데이터 무결성** 보장. |
| **결과(Consequences)** | ✅ **장점**:
- 실시간 시장 데이터 반영으로 **경쟁력 강화**.
- 지역별 최적화로 **출하 효율성** 향상.
- 블록체인으로 **데이터 신뢰성** 증가. |
| **트레이드오프(Trade-offs)** | ❌ **단점**:
- 블록체인 적용으로 **처리 지연** 가능성.
- 외부 API 연동으로 **보안 취약점** 증가 (추가 인증 필요). |

## ⚠️ **잠재적 위험 분석**

### **1. 데이터 일관성 저하**
- **설명**: 센서 및 제어 데이터 수신(S21)에서 **네트워크 지연** 또는 **장치 오류**로 인해 데이터 불일치 발생. 특히, **오류 탐지(S22)**가 실패하면 **모델링 데이터 오류**로 이어짐.
- **심각도**: 🔴 High | **발생 가능성**: 🔴 High
- **대응 방안**:
  - **이중 데이터 검증 메커니즘** 강화 (ML 기반 이상치 탐지 모델 적용).
  - **데이터 버전 관리** 시스템 도입 (블록체인 또는 데이터베이스 트랜잭션 로그 사용).

### **2. 실시간 처리 지연**
- **설명**: 모듈간 통신 지연으로 인해 **실시간 데이터 처리**가 실패할 경우, **작물 모델링(S24)**과 **마케팅 전략(S25)**이 지연됨.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **에지 컴퓨팅**을 통해 **로컬 처리**를 강화.
  - **우선순위 기반 큐** 시스템 도입 (예: Kafka 또는 RabbitMQ 사용).

### **3. 보안 취약점**
- **설명**: IoT 장치 및 네트워크가 **외부 공격**에 노출될 경우, **데이터 유출** 또는 **시스템 마비** 발생 가능.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **ITU-T X.1352** 및 **ETSI EN 303 645** 표준 준수하여 **기기 보안** 강화.
  - **제로 트러스트 아키텍처** 도입 (예: BeyondCorp 모델 적용).
  - **정기 보안 패치** 및 **침입 탐지 시스템(IDS)** 배포.

### **4. 시스템 확장성 한계**
- **설명**: 모듈형 아키텍처로 설계되었으나, **사용자 증가** 또는 **데이터 양 증가**로 인해 **성능 저하** 발생 가능.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **클라우드 네이티브 아키텍처** (Kubernetes + Auto-scaling) 적용.
  - **데이터 샤딩**을 통해 **DB 부하 분산**.

### **5. 표준 호환성 문제**
- **설명**: 국내외 표준(ISO, oneM2M, Matter 등)이 **상호 배타적**인 경우, **데이터 상호운용성**이 저하됨.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **중립적 데이터 포맷** (예: JSON Schema, Protobuf) 사용.
  - **API 게이트웨이**를 통해 **표준 변환** 지원 (예: Kong 또는 Apigee 사용).

### **6. 사용자 오류 및 입력 오류**
- **설명**: **사용자 입력(S23)**이 잘못되거나 **오류가 발생**할 경우, **모델링 데이터 오류**로 이어짐.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **입력 유효성 검사** 강화 (예: 정규 표현식, 범위 검사).
  - **사용자 가이드라인** 및 **오류 메시지 자동화** 제공.

### **7. 지역별 데이터 생성 오류**
- **설명**: **지역별 관리 데이터(S26)**가 **오류로 생성**될 경우, **관리 결정에 영향을 미침**.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **지역별 데이터 검증 프로토콜** 도입 (예: 체크섬, 디지털 서명).
  - **인공감각(AI) 기반 오류 검출** 모델 적용.
