📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트팜 통합 플랫폼의 계층형 양방향 버스 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경은 다수의 이질적 장치(센서, 액추에이터, 제어기)와 다양한 운영 주체(단일/복수 필지 운용자)가 공존한다. 모니터링부(310), 제어부(320), 완료부(330), 망구축부(340), 모델링부(350), 플랫폼부(360), 연결부(370), 복수필지운용부(380), 커스텀부(390)라는 9개의 이질적 컴포넌트가 단일 시스템 내에서 실시간 데이터를 교환해야 하며, 각 컴포넌트는 독립적으로 진화 가능해야 한다.                                |
| **결정(Decision)**       | 중앙 수직 양방향 데이터 버스를 중심축으로, 좌측(모니터링·완료·모델링·연결·커스텀)과 우측(제어·망구축·플랫폼·복수필지운용) 컴포넌트가 수평 양방향 채널로 연결되는 **이중 레인 계층형 메시지 버스(Dual-Lane Hierarchical Message Bus)** 아키텍처를 채택한다. 각 컴포넌트는 독립 마이크로서비스로 구현하며, 버스는 이벤트 브로커(예: Apache Kafka 또는 MQTT 브로커)로 구현한다.                                  |
| **근거(Rationale)**      | ① 스마트팜 특성상 센서 데이터의 실시간성과 제어 명령의 신뢰성이 동시에 요구됨. ② 복수필지운용부(380)의 존재는 다중 테넌시(Multi-tenancy) 지원 필요성을 시사하며, 중앙 버스 구조가 테넌트 간 데이터 격리와 공유를 동시에 지원하기 용이함. ③ 커스텀부(390)와 모델링부(350)의 분리는 AI/ML 모델 교체 및 사용자 정의 로직의 무중단 배포를 가능하게 함. ④ IEC 61850, FIWARE NGSI-LD 등 스마트팜 국제 표준과의 정합성 확보에 유리함. |
| **결과(Consequences)**   | 긍정적: 컴포넌트 단위 독립 배포 및 확장 가능, 장애 격리(Fault Isolation) 용이, 복수 필지 동시 운용 지원. 부정적: 중앙 버스가 단일 장애점(SPOF)이 될 수 있으며, 컴포넌트 간 계약(API/스키마) 관리 복잡도 증가, 초기 인프라 구축 비용 상승.                                                                                                                     |
| **트레이드오프(Trade-offs)** | 얻는 것: 유연한 확장성, 멀티 테넌트 지원, 컴포넌트 독립 진화. 감수해야 할 것: 버스 레이턴시로 인한 제어 응답 지연 가능성, 운영 복잡도 증가, 버스 장애 시 전체 시스템 영향.                                                                                                                                                                      |

### ADR-002: 모델링부(350)와 플랫폼부(360) 분리를 통한 AI 추론 계층 독립화

| 항목                     | 내용                                                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜의 작물 생장 예측, 병해충 탐지, 환경 최적화 등 AI/ML 기능은 빠르게 진화하는 반면, 하드웨어 플랫폼(플랫폼부, 360)의 교체 주기는 길다. 두 계층을 결합하면 모델 업그레이드 시 플랫폼 전체를 재배포해야 하는 리스크가 발생한다. |
| **결정(Decision)**       | 모델링부(350)를 독립된 AI 추론 서비스 계층으로 분리하고, 플랫폼부(360)와는 표준화된 REST/gRPC 인터페이스로 통신한다. 모델 버전 관리는 MLflow 등 모델 레지스트리를 통해 별도 운영한다.                      |
| **근거(Rationale)**      | AI 모델의 재학습 및 배포 주기(수일~수주)와 플랫폼 펌웨어 업데이트 주기(수개월)가 상이하므로 계층 분리가 운영 효율을 극대화한다. 또한 커스텀부(390)를 통한 사용자 정의 모델 주입 시나리오를 안전하게 지원할 수 있다.            |
| **결과(Consequences)**   | 긍정적: 모델 A/B 테스트 가능, 플랫폼 무중단 모델 교체. 부정적: 인터페이스 버전 관리 부담 증가, 네트워크 홉 추가로 인한 추론 레이턴시 소폭 증가.                                                   |
| **트레이드오프(Trade-offs)** | 얻는 것: 기술 부채 감소, 빠른 모델 이터레이션. 감수해야 할 것: 인터페이스 계약 유지 비용, 분산 트레이싱 필요성 증가.                                                                    |

⚠️ 잠재적 위험 분석
------------

### 1. 중앙 데이터 버스 단일 장애점(Single Point of Failure) 위험

* **설명:** 시스템 개념도 중앙의 수직 버스가 물리적/소프트웨어 장애를 일으킬 경우, 모니터링부(310)·제어부(320)·완료부(330) 등 모든 컴포넌트 간 통신이 동시에 단절되어 스마트팜 전체의 제어 불능 상태가 발생한다. 특히 온실 환경에서는 온도·습도 제어 실패가 수분 내 작물 피해로 직결된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 메시지 브로커(Kafka/MQTT)의 클러스터링 및 리플리케이션 구성(최소 3-노드), 버스 우회 비상 제어 경로(로컬 엣지 컨트롤러) 마련, 헬스체크 기반 자동 페일오버 구현.

* * *

### 2. 복수필지운용부(380) 멀티 테넌트 데이터 혼용 위험

* **설명:** 복수의 농가(필지)가 단일 플랫폼을 공유할 때 테넌트 간 데이터 격리가 불완전하면, A 농가의 센서 데이터나 제어 명령이 B 농가에 잘못 전달되는 크로스 테넌트 오염이 발생할 수 있다. 이는 잘못된 관개·시비 제어로 인한 작물 손실과 법적 분쟁을 초래한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 테넌트별 토픽 네임스페이스 격리(예: `farm/{tenantId}/sensor/#`), API 게이트웨이 레벨 JWT 기반 테넌트 검증, 데이터베이스 Row-Level Security(RLS) 적용, 정기적 테넌트 격리 침투 테스트 수행.

* * *

### 3. 모델링부(350) AI 모델 드리프트로 인한 오제어 위험

* **설명:** 스마트팜 환경 데이터(기온, 일조량, 토양 상태)는 계절·기후 변화에 따라 분포가 변동한다. 모델 재학습 없이 구 모델을 장기 운용하면 예측 정확도가 저하되어 모델링부가 부적절한 제어 신호를 제어부(320)에 전달, 과잉 관개나 과열 등 실질적 피해가 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 모델 성능 모니터링 파이프라인 구축(PSI·KL Divergence 기반 드리프트 탐지), 드리프트 임계치 초과 시 자동 재학습 트리거, 모델 예측값과 실제 센서값 간 편차 임계 초과 시 규칙 기반 폴백(fallback) 제어 모드 전환.

* * *

### 4. 연결부(370) 네트워크 단절 시 엣지-클라우드 동기화 충돌 위험

* **설명:** 농촌 지역 특성상 LTE/5G 네트워크가 불안정하여 연결부(370)가 일시 단절될 경우, 엣지 측과 클라우드 측이 각각 독립적으로 상태를 변경한다. 네트워크 복구 후 양측 상태를 병합할 때 충돌(conflict)이 발생하며, 잘못된 버전의 제어 파라미터가 적용될 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 오프라인 우선(Offline-First) 아키텍처 적용, CRDT(Conflict-free Replicated Data Type) 기반 상태 동기화, 연결 복구 시 타임스탬프 기반 Last-Write-Wins 정책 또는 관리자 수동 충돌 해소 UI 제공, 엣지 디바이스 로컬 큐잉 버퍼 확보.

* * *

### 5. 커스텀부(390) 사용자 정의 코드 실행으로 인한 보안 취약점 위험

* **설명:** 커스텀부(390)가 농가 또는 제3자 개발자의 사용자 정의 스크립트·플러그인을 실행할 경우, 검증되지 않은 코드가 악의적 페이로드를 포함하거나 시스템 자원을 과점할 수 있다. 이는 전체 플랫폼의 가용성 저하(DoS) 또는 타 테넌트 데이터 탈취로 이어질 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 커스텀 코드를 격리된 샌드박스(WebAssembly 또는 gVisor 기반 컨테이너)에서만 실행, 코드 서명(Code Signing) 및 정적 분석(SAST) 필수화, CPU·메모리·네트워크 사용량 리소스 쿼터 적용, 플랫폼 내부 API 접근 최소 권한 원칙(PoLP) 적용.

### 6. 망구축부(340) IoT 디바이스 펌웨어 미업데이트로 인한 취약점 누적 위험

* **설명:** 스마트팜에 배포된 수백~수천 개의 IoT 센서·액추에이터 펌웨어가 장기간 업데이트되지 않으면 알려진 CVE(공통 취약점)를 통한 침해가 발생할 수 있다. 망구축부(340)가 이를 통제하지 못할 경우 공격자가 센서 데이터를 조작하거나 제어 명령을 가로챌 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** OTA(Over-The-Air) 펌웨어 업데이트 파이프라인 구축, 디바이스 인벤토리 자동 스캔 및 취약점 매핑(CVE DB 연동), 네트워크 세그멘테이션(IoT DMZ 구성)으로 감염 확산 차단, 디바이스 상호 인증(mTLS/X.509) 적용.
