📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **실시간 환경 모니터링을 위한 IoT 센서 네트워크 및 중앙 서버 통합 아키텍처**

| 항목                     | 내용                                                                                                                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 실시간으로 온실 내 환경(온도, 습도, 조도 등)을 모니터링하고, 사용자(농업인)에게 모바일 앱을 통해 데이터를 제공해야 합니다. 이미지 상에서 110, 120번으로 표시된 센서 배열이 환경 데이터를 수집하며, 400번으로 표시된 중앙 서버가 데이터를 처리하고, 200번 모바일 기기(사용자)로 데이터를 전달합니다. 또한, 500번(외부 네트워크), 600번(게이트웨이), 300번(서버 애플리케이션)으로 연결된 구조로, 데이터의 실시간성과 신뢰성이 핵심 과제입니다. |
| **결정(Decision)**       | IoT 센서 네트워크를 통해 수집된 데이터를 **게이트웨이(600번)를 거치도록 하며**, 중앙 서버(400번)에서 데이터를 집계·처리한 후, 모바일 앱(200번)으로 실시간 전송하는 **계층적 아키텍처**를 채택합니다. 또한, 서버 애플리케이션(300번)은 데이터베이스와 연동하여 역사적 데이터를 저장하고, 사용자 요청 시 분석 결과 제공합니다.                                                                              |
| **근거(Rationale)**      | 1. **실시간성**: 센서에서 게이트웨이를 거치면 데이터 전송 지연을 최소화할 수 있습니다. 2. **확장성**: 게이트웨이가 중계역할을 하면 센서 노드 추가가 용이합니다. 3. **안정성**: 중앙 서버에서 데이터를 집계·처리하면 데이터 무결성과 일관성을 보장합니다. 4. **사용자 접근성**: 모바일 앱을 통해 언제 어디서나 환경 데이터를 확인할 수 있습니다.                                                                   |
| **결과(Consequences)**   | **장점**: 실시간 모니터링 가능, 시스템 확장 용이, 데이터 중앙 관리로 분석 및 의사결정 지원. **단점**: 게이트웨이와 서버의 단일 장애점이 발생 시 전체 시스템에 영향을 미칠 수 있습니다.                                                                                                                                                                 |
| **트레이드오프(Trade-offs)** | **장점**: 실시간 데이터 처리, 시스템 유연성, 사용자 편의성. **단점**: 네트워크 인프라 구축 비용 증가, 게이트웨이/서버의 단일 장애점 위험, 데이터 전송 지연 가능성(네트워크 환경에 따라).                                                                                                                                                               |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. **게이트웨이(600번) 단일 장애점(Single Point of Failure)**

* **설명:** 게이트웨이에 장애가 발생하면 모든 센서에서 서버로의 데이터 전송이 중단되어 실시간 모니터링이 불가능해집니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 이중화 게이트웨이 구축 또는 클라우드 기반의 로드 밸런싱을 통해 장애 복구 시간 최소화.

* * *

### 2. **네트워크 지연 및 데이터 손실**

* **설명:** 센서에서 게이트웨이, 또는 게이트웨이에서 서버로 데이터 전송 중 네트워크 지연이나 패킷 손실로 인해 실시간성이 저하될 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** QoS(Quality of Service) 정책 적용, 데이터 전송 프로토콜 최적화(예: MQTT 사용), 에지 컴퓨팅을 통한 지역적 데이터 처리.

* * *

### 3. **보안 취약점(데이터 탈취 또는 변조)**

* **설명:** 센서-게이트웨이-서버 간 전송되는 데이터가 해킹 또는 스푸핑 공격으로 탈취 또는 변조될 위험이 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 끝단간 암호화(End-to-End Encryption), 인증 메커니즘(예: TLS/SSL), 정기적인 보안 패치 및 모니터링.

* * *

### 4. **서버 과부하로 인한 성능 저하**

* **설명:** 동시 접속 사용자 증가 또는 센서 노드 대량 추가로 서버(400번)가 과부하 상태에 빠질 경우, 시스템 응답 시간이 지연됩니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 서버 클러스터링 또는 오토스케일링(Auto-scaling) 도입, 캐싱 메커니즘 적용.

* * *

### 5. **모바일 앱(200번) 호환성 및 성능 이슈**

* **설명:** 다양한 모바일 기기에서 앱이 원활히 동작하지 않거나, 실시간 데이터 수신 지연이 발생할 수 있습니다.
* **심각도:** 🟢 Low
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 크로스 플랫폼 개발 프레임워크(예: Flutter) 사용, 앱 성능 최적화, 사용자 기기 호환성 테스트 강화.

* * *

### 6. **센서 노드(110, 120번) 배터리 및 유지보수**

* **설명:** 장시간 운영 시 센서 노드의 배터리 소모 또는 하드웨어 고장으로 인해 데이터 수집이 중단될 수 있습니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 에너지 효율적인 프로토콜(예: LoRaWAN) 사용, 정기적인 유지보수 스케줄 수립, 태양광 등 자가 발전 시스템 도입.
