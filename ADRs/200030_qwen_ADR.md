## 📋 ADR (Architecture Decision Record)

### ADR-001: 초기화면에서의 로컬라이제이션 우선 전략 적용

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **이미지 참조**: 시스템 흐름의 첫 번째 단계는 '1. 언어 및 국가 설정'으로 시작됨. <br> 이 단계는 사용자가 스캔을 진행하기 전, 앱의 언어와 지역 정보를 확정하는 과정임. <br> 이를 통해 이후 QR 코드(Barcode) 해석 시 문자 인코딩 오류나 지역 설정을 기반으로 한 데이터 형식 불일치를 방지할 수 있음. |
| **결정(Decision)** | 앱의 런처 (Launcher) 활동과 동일한 시점에 또는 앱 첫 실행 시, 반드시 '언어 및 국가 설정' 단계에서 사용자가 언어와 국가를 선택하도록 강제 (Mandatory) 함. |
| **근거(Rationale)** | - **QR Code 데이터 해석**: 바코드 내부에 포함된 문자열은 지역 설정 (Locale) 에 따라 인코딩이나 문자 해석 방식이 다를 수 있음.<br>- **사용자 경험 (UX) 일관성**: 사용자가 이후 서비스 연결 시 본국어를 볼 수 있어 혼란을 줄임.<br>- **스마트폰 OS 설정 차이**: 사용자의 휴대폰 설정과 앱 내 설정을 동기화하여, 특정 기기에서 서비스명이 깨지는 현상을 방지. |
| **결과(Consequences)** | **긍정적**: 언어 관련 버그 발생 감소, 글로벌 서비스 접근성 향상.<br>**부정적**: 사용자 설정 변경 시 앱 재설치나 설정 강요로 인한 초기 진입 장벽 소소 증가. |
| **트레이드오프(Trade-offs)** | **장점**: 데이터 무결성 보장, UI 일관성 확보.<br>**단점**: 사용자 편의성 일부 제한 (예: 앱 설정에서 나중에 바꾸는 것보다 앱 실행 시마다 선택해야 함). |

### ADR-002: 멀티-프로토콜 기반 하이브리드 디스커버리 아키텍처

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **이미지 참조**: '2. Data Matrix Scan', '2-1 Bluetooth Scan', '2-3 WiFi Scan' 세 가지 경로가 존재함.<br> IoT 기기는 블루투스 센서, WiFi 네트워크, QR 코드 등 다양한 방식으로 제어될 수 있음. <br> 앱은 이들 모두를 하나의 UI 로 통합하여 제공해야 함. |
| **결정(Decision)** | 블루투스 (BLE), WiFi (SSID), 데이터 매트릭스 (QR Code) 세 가지 디스커버리 프로토콜을 동시 혹은 병렬 처리할 수 있도록 멀티스레드 혹은 비동기 로직으로 구현. |
| **근거(Rationale)** | - **프로토콜 독립성**: 스마트팜이나 IoT 환경에서 블루투스만 쓰는 센서와 WiFi 를 쓰는 게이트웨이, 그리고 QR 코드를 통한 초기 설정 기기가 공존함.<br>- **최적의 경로 발견**: 가장 가까이 있는 기기 (BLE) 나 가장 쉬운 설정 방법 (QR) 을 먼저 찾도록 하여 사용자 편의를 극대화.<br>- **IoT 표준 준수**: TTA, ISO/IEC 30141 등에서 언급된 IoT 상호운용성을 위한 필수 요소인 다양한 계층 (물리/네트워크) 지원. |
| **결과(Consequences)** | **긍정적**: 다양한 IoT 기기를 하나의 앱으로 통합 제어 가능.<br>**부정적**: 배터리 소모 증가 및 시스템 리소스 경쟁 발생 가능성. |
| **트레이드오프(Trade-offs)** | **장점**: 유비쿼터스 환경 구축, 기기 호환성 극대화.<br>**단점**: 배터리 수명 단축, 복잡한 백그라운드 프로세스 관리 필요. |

### ADR-003: WebView 기반의 동적 서비스 렌더링 전략

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **이미지 참조**: '3. Service 리스트 출력' 후 '4. Service 연결' 단계에서 웹뷰 (WebView) 화면으로 이동하는 경로가 존재함. <br> "같은 url 일 경우"라는 조건부 로직이 존재함. |
| **결정(Decision)** | IoT 기기의 기본 제어 인터페이스 (Web UI) 가 HTTPS 로 제공된다면, 이를 앱 내부의 WebView 로 렌더링하여 보여주는 방식을 표준 아키텍처로 채택. |
| **근거(Rationale)** | - **신속한 개발 및 유지보수**: IoT 기기 제조사가 웹 기반 UI 를 제공하고 있으므로, 별도의 네이티브 UI 로 다시 구현하지 않아도 됨.<br>- **상호운용성**: 표준 웹 기술 (HTML/CSS/JS) 이므로, 기기 제조사의 UI 변경에 대한 앱 수정 비용이 적음.<br>- **보안 및 인증**: 기기 본래의 인증 페이지 (예: 관리자 페이지) 가 WebView 를 통해 재현됨. |
| **결과(Consequences)** | **긍정적**: 개발 기간 단축, 웹 UI 업데이트 자동 적용.<br>**부정적**: 네이티브 앱의 성능 (예: 카메라, Bluetooth 제어) 을 직접 제어할 수 있는 부분의 제약. |
| **트레이드오프(Trade-offs)** | **장점**: 개발 효율성, UI 동적 업데이트 용이.<br>**단점**: 네이티브 기능 접근성 제한, 앱 내 웹뷰 보안 설정 (CSP 등) 필요. |

## ⚠️ 잠재적 위험 분석

### 1. [IoT 기기 간 상호운용성 저하 위험]
- **설명:** 블루투스, WiFi, 바코드 등 서로 다른 프로토콜을 동시에 스캔하는 과정에서, 특정 기기 드라이버나 프로토콜 버전 (예: Bluetooth 4.2 vs 5.0) 이 앱 지원 목록에 포함되지 않아 기기 발견에 실패하는 경우. 이는 시스템의 핵심 목적인 '상호운용성'을 떨어뜨림.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - 핵심 프로토콜만 지원하고, 비표준 프로토콜은 로그 메시지 등으로 피하기 (Fail-fast 전략).
    - 기기 제조사와 API 명세서를 매칭하여 지원 목록을 정기적으로 업데이트.
    - '같은 url 일 경우' 로직처럼 URL 기반 fallback 을 통해 웹 브라우징 방식으로 우회하는 경로 확보.

### 2. [스캔 과정에서의 보안 노출 위험]
- **설명:** 'Bluetooth Scan' 또는 'WiFi Scan' 과정에서 스캔된 기기 목록 (MAC 주소, SSID) 이 앱의 메모리나 로깅 시스템에 남을 경우, 사용자 사생활 (위치 추정 등) 이 유출될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High (백그라운드 스캔 시 빈번히 발생)
- **대응 방안:**
    - 스캔 완료 후 불필요한 스캔 데이터는 즉시 메모리에서 제거.
    - 민감한 기기 정보 (MAC 등) 로깅을 제한하고 암호화.
    - 앱 권한 (블루투스, 네트워크 위치 접근) 최소한의 범위만 요구.

### 3. [WebView 을 통한 악성 콘텐츠 Injection 위험]
- **설명:** '4. Service 연결' 단계에서 WebView 를 통해 IoT 기기의 웹 대시보드에 접속하지만, IoT 기기가 취약한 웹 서버일 경우 XSS(교차 사이트 스크립팅) 나 악성 스크립트 injection 되어 사용자의 앱 내 데이터가 탈취될 수 있음.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - WebView 의 `JavaScript` 실행을 기본값으로 금지하고 필요 시만 활성화.
    - 서버 측 Content Security Policy (CSP) 적용.
    - WebView 의 `allowFileAccess`, `allowUniversalLinks` 등 보안 속성 최소화.

### 4. [네트워크 연결 불안정성으로 인한 서비스 거부 (DoS)]
- **설명:** IoT 환경은 무선 신호 간섭이 잦은 곳 (스마트팜, 공장) 에 배치됨. 스캔 단계에서 네트워크 불안정으로 인해 'Service 리스트' 로직이 멈추거나, 'WebView' 로 연결되지 않아 사용자가 서비스를 이용할 수 없는 경우 발생.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High (무선 환경 특성상)
- **대응 방안:**
    - 스캔 시간이 제한적 (예: 10 초) 으로 제한 후 자동으로 재시도 로직 추가.
    - WiFi 스캔 시 백그라운드 스캔 주기를 적절히 줄이고, 활성 모드에서만 수행.
    - 오프라인 상태에서도 로컬 캐시 (기존에 스캔한 기기 정보) 를 활용하여 기본 기능 제공.

### 5. [데이터 무결성 위협: 멀티-스캔 시 충돌]
- **설명:** '2-1 Bluetooth Scan'과 '2-3 WiFi Scan'이 동시 진행 중일 때, 동일한 기기에 대해 두 프로토콜에서 중복된 정보가 입력되는 경우. 이로 인해 'Service 리스트' 에서 중복된 항목이 생성되어 사용자가 혼란을 겪거나, 잘못된 기기에 연결될 위험 발생.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - 'Service 리스트' 에 고유 ID (UUID) 를 기반으로 중복 필터링 로직 구현.
    - 블루투스 스캔 시 해당 기기에 WiFi 신호가 없으면 필터링.
    - 리스트 출력 시 사용자가 중복된 항목을 수동으로 선택할 수 있도록 UI 로직 강화.
