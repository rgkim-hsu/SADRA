📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **이벤트 드리븐 아키텍처(EDA) 기반 실시간 데이터 동기화 시스템 채택**

| 항목                     | 내용                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 빅데이터부(310), 학습부(330), 예측부(350), 연동학습부(370)와 제공부(320), 진행관리부(340), 분석학습부(360), 미러링부(380) 간의 실시간 데이터 교환이 필수적입니다. 각 컴포넌트 간 양방향 통신이 필요하며, 특히 IoT 센서로부터 수집된 데이터를 실시간으로 분석하고, 학습 및 예측 모델에 반영해야 합니다. 기존 Batch 처리 방식은 실시간성 요건을 충족하지 못합니다.          |
| **결정(Decision)**       | **이벤트 드리븐 아키텍처(EDA)**를 채택하여, 각 컴포넌트(빅데이터부, 학습부, 예측부 등) 간 **비동기식 메시지 큐(Kafka, RabbitMQ 등)**를 통한 실시간 데이터 스트리밍을 구현합니다. 또한, **CQRS(Command Query Responsibility Segregation)** 패턴을 도입하여 읽기/쓰기 작업을 분리하고, **이벤트 소싱(Event Sourcing)**을 통해 데이터 변경 이력을 추적합니다. |
| **근거(Rationale)**      | 1) **실시간성**: EDA는 이벤트가 발생하면 즉시 처리하여 실시간 데이터 동기화를 보장합니다. 2) **확장성**: 메시지 큐를 통해 컴포넌트 간 결합도를 낮추고, 수평적 확장을 용이하게 합니다. 3) **신뢰성**: 이벤트 소싱을 통해 데이터 일관성을 유지하며, 장애 발생 시 복구가 가능합니다. 4) **스마트팜 트렌드**: IoT 및 실시간 모니터링이 핵심인 스마트팜 분야에서 EDA는 표준 아키텍처로 인정받고 있습니다.    |
| **결과(Consequences)**   | **장점**: 실시간 데이터 처리 가능, 시스템 확장성 향상, 장애 복구 용이성. **단점**: 시스템 복잡도 증가, 이벤트 순서 보장 및 중복 처리 방지 메커니즘 필요.                                                                                                                                                      |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 실시간 데이터 동기화, 유연성, 확장성. **감수해야 할 단점**: 아키텍처 복잡도 증가, 모니터링 및 디버깅 어려움, 이벤트 처리 지연 가능성.                                                                                                                                                         |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. **실시간 데이터 처리 지연**

* **설명:** IoT 센서에서 대량의 데이터가 유입될 때, 메시지 큐의 처리 용량 한계로 인해 데이터 처리 지연이 발생할 수 있습니다. 특히, 학습부(330)와 예측부(350)에서 AI 모델 추론 시간이 길어질 경우, 전체 시스템의 실시간성이 저하될 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **메시지 큐 파티셔닝**을 통해 병렬 처리 성능 향상.
  * **에지 컴퓨팅** 도입을 통해 센서 데이터의 사전 처리(필터링, 집계) 수행.
  * **AI 모델 최적화** (예: Quantization, Pruning) 및 **GPU 가속** 적용.

* * *

### 2. **데이터 일관성 손상**

* **설명:** EDA에서 이벤트가 비동기적으로 처리될 경우, 빅데이터부(310)와 미러링부(380) 간 데이터 동기화 시점 차이로 인해 일시적인 데이터 불일치가 발생할 수 있습니다. 예를 들어, 진행관리부(340)에서 상태가 업데이트된 후, 예측부(350)에서 구식 데이터를 사용해 잘못된 예측을 내릴 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **이벤트 소싱 + 스냅샷**을 통해 데이터 일관성을 주기적으로 검증.
  * **Saga 패턴**을 도입해 분산 트랜잭션 관리.
  * **Conflict-free Replicated Data Types(CRDTs)** 사용을 고려.

* * *

### 3. **보안 취약점 (데이터 유출 및 무단 접근)**

* **설명:** 실시간 데이터가 메시지 큐를 통해 전송될 때, 인증/권한이 미비한 상태에서 노출될 위험이 있습니다. 특히, 스마트팜 시스템은 농작물 재배 데이터, 환경 제어 정보 등 민감한 데이터를 다루며, 외부 공격에 노출될 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **End-to-End 암호화** (TLS 1.3 + 메시지 수준 암호화).
  * **Zero Trust 아키텍처** 도입: 모든 컴포넌트 간 통신에 **mTLS(Mutual TLS)** 적용.
  * **API 게이트웨이**를 통해 인증/인가 통일 관리.

* * *

### 4. **시스템 장애 전파(Cascading Failure)**

* **설명:** 특정 컴포넌트(예: 빅데이터부 310)가 장애를 일으키면, 의존하는 다른 컴포넌트(예: 학습부 330, 예측부 350)도 연쇄적으로 장애를 겪을 수 있습니다. 예를 들어, 빅데이터부에서 데이터가 지연되면, 학습부에서 모델 학습이 중단될 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **회로 차단기(Circuit Breaker) 패턴** (Hystrix, Resilience4j) 도입.
  * **재시도 메커니즘** (Exponential Backoff) 및 **Dead Letter Queue(DLQ)** 구축.
  * **마이크로서비스별 독립적 스케일링** 및 **Health Check** 자동화.

* * *

### 5. **AI 모델 편향성 및 예측 오류**

* **설명:** 학습부(330)에서 훈련된 AI 모델이 편향된 데이터로 학습될 경우, 예측부(350)에서 잘못된 예측(예: 온도/습도 조절 실패)을 내릴 수 있습니다. 이는 농작물 손실로 이어질 수 있습니다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **데이터 품질 관리**: 이상치 탐지(Outlier Detection) 및 데이터 클렌징 자동화.
  * **모델 설명 가능성(XAI)** 도구(예: SHAP, LIME) 도입하여 예측 결과 해석.
  * **A/B 테스팅**을 통해 새로운 모델과 기존 모델의 성능 비교.

* * *

### 6. **미러링부(380) 동기화 실패**

* **설명:** 미러링부(380)는 분석학습부(360) 및 다른 컴포넌트와 데이터를 동기화해야 합니다. 네트워크 지연 또는 장애로 인해 동기화가 실패하면, 백업 데이터가 최신 상태가 아닌 경우 장애 복구 시 데이터 손실이 발생할 수 있습니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **다중화(Multi-Region) 배포**를 통해 지역별로 미러링부 복제.
  * **체크섬(Checksum)** 기반 동기화 검증.
  * **증분 동기화(Delta Sync)**를 통해 대용량 데이터 동기화 효율성 향상.****

* **설명:** 미러링부(380)는 분석학습부(360) 및 다른 컴포넌트와 데이터를 동기화해야 합니다. 네트워크 지연 또는 장애로 인해 동기화가 실패하면, 백업 데이터가 최신 상태가 아닌 경우 장애 복구 시 데이터 손실이 발생할 수 있습니다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **다중화(Multi-Region) 배포**를 통해 지역별로 미러링부 복제.
  * **체크섬(Checksum)** 기반 동기화 검증.
  * **증분 동기화(Delta Sync)**를 통해 대용량 데이터 동기화 효율성 향상.****
