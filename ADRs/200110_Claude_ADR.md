===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 정책 기반 분리형 데이터 검증 파이프라인 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 환경정보·제어정보·생육정보·기타정보 등 이종(異種) 센서 데이터가 실시간으로 수집된다. 각 데이터 유형마다 오류 패턴이 상이하며(통신 단절에 의한 결측, 센서 노후화에 의한 갱신 정체, 물리적 범위 초과값 등), 단일 검증 로직으로 모든 이상치를 처리할 경우 검증 정확도 저하 및 유지보수 복잡도가 급증하는 문제가 존재한다.                                                                 |
| **결정(Decision)**       | 데이터 검증 시스템을 ① 오류데이터 처리, ② 갱신주기 이상치 처리, ③ 범위 이상치 처리의 세 개 독립 처리 모듈로 분리하고, 각 모듈에 대응하는 정책(오류데이터 검증 정책 / 갱신주기 이상치 정책 / 범위 이상치 정책)을 외부화하여 데이터 검증 정책 저장소에서 런타임에 주입하는 정책 주도(Policy-Driven) 파이프라인 아키텍처를 채택한다. 최종 단계에서 데이터 클렌징 처리를 통합 수행하여 정제 데이터를 생성하며, 처리결과 이력을 별도 저장한다. |
| **근거(Rationale)**      | 관심사 분리(SoC) 원칙에 따라 이상치 유형별 처리 로직을 독립 모듈화함으로써 개별 정책의 변경이 타 모듈에 영향을 주지 않는다. IQR(사분위수 범위) 기반 연관성 매핑 등 통계적 기법을 범위 이상치 정책에 독립 적용할 수 있으며, 작물(벼·밀·양파) 및 생육 단계별로 임계값이 상이한 스마트팜 도메인 특성에 최적화된다. 정책 외부화는 코드 재배포 없이 정책 갱신을 가능하게 하여 운영 민첩성을 확보한다.                             |
| **결과(Consequences)**   | 긍정적: 작물·시즌별 검증 정책의 독립적 업데이트 가능, 검증 단계별 처리결과 이력 추적성 확보, 데이터 클렌징 품질 향상으로 하위 분석 모델의 정확도 제고. 부정적: 모듈 간 데이터 전달 인터페이스 설계 복잡도 증가, 정책 저장소가 단일 장애점(SPOF)이 될 위험, 파이프라인 단계 증가로 인한 처리 지연(latency) 발생 가능.                                                                     |
| **트레이드오프(Trade-offs)** | 얻는 장점: 높은 유지보수성·확장성, 정책 버전 관리 가능, 이상치 유형별 독립 튜닝. 감수할 단점: 파이프라인 오케스트레이션 복잡도 증가, 정책 저장소 가용성 확보를 위한 추가 인프라 비용, 검증 데몬(Daemon) 프로세스의 지속적 모니터링 필요.                                                                                                                     |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 데이터 검증 정책 저장소 단일 장애점(SPOF) 위험

* **설명:** 오류데이터 검증 정책·갱신주기 이상치 정책·범위 이상치 정책이 단일 정책 저장소에 집중되어 있어, 해당 저장소 장애 발생 시 세 개 처리 모듈 모두가 정책을 조회하지 못해 검증 파이프라인 전체가 중단된다. 노지 환경의 네트워크 불안정 구간에서 발생 가능성이 높다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 정책 저장소를 Active-Standby 이중화 구성으로 전환하고, 각 처리 모듈에 마지막으로 로드된 정책의 로컬 캐시(Last-Known-Good Policy Cache)를 유지하여 저장소 장애 시에도 최신 캐시 정책으로 Fallback 운영이 가능하도록 설계한다. 정책 변경 이벤트는 메시지 큐를 통해 비동기 전파한다.

### 2. 갱신주기 이상치 오탐(False Positive)으로 인한 정상 데이터 손실

* **설명:** 네트워크 지연, 센서 절전 모드, 일시적 통신 혼잡 등 정상 운영 상황에서도 갱신주기 이상치 처리 모듈이 해당 데이터를 이상치로 분류할 수 있다. 생육정보 등 타이밍에 민감한 데이터가 오탐으로 제거될 경우, 후속 AI 분석 모델의 학습 데이터 편향이 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 갱신주기 판단 임계값을 작물 유형·센서 종류·계절별로 다층화하고, 이상치 판정 시 즉시 삭제가 아닌 '의심 플래그(Suspect Flag)' 처리 후 일정 기간 보류 큐에 보관한다. 처리결과 이력을 활용해 오탐율 KPI를 주기적으로 모니터링하고 임계값 자동 조정 피드백 루프를 구현한다.

### 3. 데이터 클렌징 처리 단계의 병목(Bottleneck) 및 처리 지연

* **설명:** 세 개의 독립 처리 모듈(오류·갱신주기·범위) 결과가 단일 데이터 클렌징 처리 컴포넌트로 집약되는 구조상, 수확 시즌 등 대량 데이터 유입 구간에서 클렌징 단계가 병목이 되어 정제 데이터 생성 지연이 발생한다. 실시간 제어 피드백이 필요한 스마트팜 환경에서 치명적일 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 데이터 클렌징 처리 컴포넌트를 수평 확장(Scale-Out) 가능한 Worker Pool 구조로 설계하고, 상위 세 모듈과의 연결에 메시지 큐(예: Kafka, RabbitMQ)를 도입하여 비동기 버퍼링을 적용한다. 환경정보·제어정보 등 긴급도 높은 데이터 스트림에 우선순위 큐를 부여한다.

### 4. 처리결과 이력 데이터의 무결성 및 감사 추적 미흡 위험

* **설명:** 처리결과 이력이 별도로 저장되나, 어떤 정책 버전에 의해 어떤 원본 데이터가 어떻게 변환·제거되었는지에 대한 상세 감사 로그가 부재할 경우, 정제 데이터의 신뢰성 검증이 불가능하다. 농업 연구 데이터로 활용 시 재현성(Reproducibility) 문제가 발생한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 처리결과 이력에 원본 데이터 스냅샷, 적용된 정책 ID·버전, 처리 타임스탬프, 처리 모듈 식별자를 포함하는 불변(Immutable) 감사 로그 스키마를 설계한다. 이력 저장소에 Write-Once 정책을 적용하고, 정기적인 데이터 계보(Data Lineage) 검증 프로세스를 운영 절차에 포함한다.

### 5. 스마트팜 수집정보와 검증 시스템 간 인터페이스 보안 취약점

* **설명:** 환경정보·제어정보·생육정보·기타정보가 스마트팜 현장 장치에서 검증 시스템으로 전송되는 구간에 대한 인증·암호화 메커니즘이 명시되어 있지 않다. 노지 환경의 무선 네트워크 특성상 중간자 공격(MITM)에 의한 데이터 위변조나, 악의적 허위 센서 데이터 주입(Data Poisoning)으로 정책 오작동을 유발할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 센서 게이트웨이와 검증 시스템 간 통신에 TLS 1.3 이상의 전송 암호화를 의무화하고, 디바이스 인증서 기반의 상호 TLS(mTLS)를 적용한다. 데이터 수신 단계에서 서명 검증을 통해 데이터 출처를 확인하며, 단시간 내 비정상적 데이터 볼륨 급증을 탐지하는 이상 트래픽 감지 룰을 검증 데몬에 추가 구현한다.

### 6. 검증 데몬(Daemon) 단일 프로세스 의존에 따른 가용성 위험

* **설명:** 개념도 상 데이터 검증 데몬이 전체 파이프라인의 오케스트레이터 역할을 수행하는 단일 프로세스로 표현되어 있다. 데몬 프로세스 크래시, 메모리 누수, OS 패치 재기동 등의 상황에서 검증 파이프라인 전체가 중단되며, 그 동안 수집되는 스마트팜 원시 데이터는 미검증 상태로 누적되거나 유실된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 검증 데몬을 컨테이너(Docker/Kubernetes) 기반으로 배포하여 자동 재시작(Restart Policy) 및 헬스체크를 적용한다. Active-Active 또는 Active-Standby 이중화를 구성하고, 데몬 장애 구간 동안 수집된 원시 데이터는 내구성 있는 메시지 큐에 보존하여 복구 후 재처리(Replay)가 가능하도록 설계한다.
