# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 데이터 거버넌스 및 ML/AI 파이프라인 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 업무 정의 단계에서 획득된 다양한 원시 데이터를 다중 단계(정제 $\rightarrow$ 라벨링 $\rightarrow$ 모델 개발)를 거쳐 최종적으로 활용하는 AI 기반 서비스입니다. 데이터의 출처(Source)가 다르고, 데이터의 특성(Raw, Clean, Labeled)이 계층적으로 변화하며, 이러한 과정에서 데이터의 신뢰성(Provenance)과 연속적인 변환 추적(Data Lineage)을 유지하는 것이 가장 큰 아키텍처적 과제입니다. |
| **결정(Decision)** | **스트리밍 기반의 모듈화된 데이터 메시(Data Mesh) 아키텍처를 채택하고, 모든 데이터 변환 단계를 전문적인 데이터 파이프라인 오케스트레이션 도구(예: Apache Airflow, Kubeflow)로 관리합니다.** 각 데이터 스테이지(Raw Store, Staging, Feature Store, Labeled Store)를 독립적 서비스로 분리하고, 이들 간의 통신은 표준화된 메시지 브로커(Message Broker)를 통해 비동기적으로 처리합니다. |
| **근거(Rationale)** | **1. 데이터 분산 및 독립성 확보:** 데이터 메시는 중앙 집중식 데이터 레이크가 아닌, 도메인별로 소유권을 가진 데이터 제품(Data Product)을 관리하게 하여 확장성과 고가용성을 극대화합니다. **2. 처리의 투명성 및 이중화:** 오케스트레이션을 통해 데이터 획득, 정제, 라벨링 등 각 변환 단계의 실행 기록(Execution Log)과 성공 여부를 완벽하게 추적할 수 있습니다. **3. 실시간 처리 능력:** 메시지 브로커 사용은 센서 등 실시간으로 유입되는 원시 데이터의 백프레셔(Backpressure) 문제를 해소하고, 지연 시간(Latency)을 최소화하여 실시간 활용을 지원합니다. |
| **결과(Consequences)** | **[긍정적]** 시스템의 각 부분이 독립적으로 발전할 수 있어, 특정 도메인이나 기술 변화에 대한 영향을 최소화합니다 (기술 부채 관리 용이). 데이터 제품화(Data Productization)가 가능하여 재사용률이 높고, 시스템의 확장성이 수평적, 수직적으로 보장됩니다. **[부정적]** 초기 구축 및 구현 복잡도가 매우 높고, 전문적인 데이터 엔지니어링 역량(Stream Processing, Orchestration)이 필수적입니다. |
| **트레이드오프(Trade-offs)** | **복잡도(Complexity) vs. 확장성 및 유연성(Scalability & Flexibility):** 초기 설계 및 구현 단계에서의 복잡성과 비용은 증가하지만, 장기적으로는 다양한 이기종 데이터 소스(IoT, Legacy DB 등)의 연결과 비즈니스 로직의 추가가 용이하여 시장 변화에 민첩하게 대응할 수 있습니다. |

## ⚠️ 잠재적 위험 분석

### 1. 데이터 파이프라인 오염 및 데이터 드리프트 (Data Pollution & Drift)
- **설명:** 시간이 지남에 따라 실제 운영 환경의 데이터 패턴(분포, 스키마, 물리적 변화)이 초기 학습 데이터나 정제 과정의 가정을 벗어나 변화(Data Drift)할 경우, AI 모델의 성능이 급격히 저하될 수 있습니다. 예를 들어, 계절 변화나 센서 교체로 원시 데이터의 측정 단위나 간격이 변할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** **1. 모니터링 시스템 구축:** 모델 서빙 단계(Inference)에서 예측 성능(Performance Degradation)뿐만 아니라, 입력 데이터의 통계적 특성(Feature Drift, Schema Validation)을 실시간으로 모니터링하는 Drift Detection 모듈을 구축하고, 이상 감지 시 자동으로 경고 및 모델 재학습 파이프라인을 트리거해야 합니다. **2. 버전 관리:** 모든 데이터 스키마와 모델은 반드시 버전(Version)을 관리하고, 데이터 소스 변경 시 백그라운드에서 영향도 분석을 수행합니다.

### 2. 엣지 디바이스 보안 취약점 및 데이터 위변조 (Edge Security Vulnerability & Tampering)
- **설명:** 원시데이터가 획득되는 '엣지(Edge)' 레벨의 IoT 디바이스나 게이트웨이가 해킹되거나 물리적으로 손상될 경우, 시스템에 유입되는 데이터가 위변조(Data Tampering)되거나 유출될 수 있습니다. 이는 최종적인 AI 활용의 신뢰도를 근본적으로 훼손합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **1. 종단 간 암호화(End-to-End Encryption):** 센서-게이트웨이-클라우드 전송 구간 전체에서 TLS/DTLS와 같은 강력한 암호화 프로토콜을 의무적으로 사용해야 합니다. **2. 경량 보안 모듈:** 엣지 게이트웨이에 최소한의 무결성 검사(Integrity Check) 및 접근 제어(Access Control) 기능을 갖춘 하드웨어 보안 모듈(HSM)을 탑재하여 데이터의 출처와 무결성을 보장해야 합니다.

### 3. 라벨링 편향 및 지식 격차 (Labeling Bias & Knowledge Gap)
- **설명:** 데이터 라벨링 단계는 사람의 주관적 판단(Domain Knowledge)에 의존하므로, 라벨링 수행자 간의 합의 부족이나 특정 관점(Bias)에 치우친 라벨링이 발생할 위험이 높습니다. 만약 라벨링 데이터가 실제 발생 가능한 모든 예외 상황(Edge Cases)을 포괄하지 못한다면, 모델은 해당 예외 상황에 취약합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **1. 전문가 그룹 활용 (Ground Truth):** 라벨링 작업에 반드시 여러 도메인 전문가(Subject Matter Experts, SME)의 합의 메커니즘(Consensus Mechanism)을 적용해야 하며, 데이터셋에 포함되어야 할 예외 케이스를 목록화하고 관리해야 합니다. **2. 능동 학습(Active Learning) 적용:** 모델이 자신감이 낮은 데이터 포인트(Uncertainty Sampling)를 자동으로 식별하여, 이를 라벨링 전문가에게 우선적으로 검토 요청함으로써 라벨링 효율성과 정확도를 동시에 높여야 합니다.

### 4. 컴포넌트 간 인터페이스 비호환성 및 종속성 (Interoperability & Dependency Failure)
- **설명:** 시스템이 데이터 획득, 정제, 모델링 등 여러 계층에 걸쳐 외부 상용 솔루션(Commercial Off-The-Shelf, COTS)이나 표준화된 프로토콜(MQTT, REST API 등)을 다수 사용합니다. 이들 컴포넌트 간의 API 스키마가 변경되거나 버전이 맞지 않을 경우, 전체 파이프라인이 멈추는 '시스템 연쇄 고장'이 발생할 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **1. 인터페이스 규격화 및 계약:** 모든 내부 및 외부 컴포넌트 간의 인터페이스는 엄격하게 API 계약(API Contract)을 정의하고 문서화해야 하며, 이 계약을 자동화된 테스트(Contract Testing)로 주기적으로 검증해야 합니다. **2. 메시지 인터페이스 강제:** 컴포넌트 간의 결합도를 낮추기 위해 직접적인 API 호출보다는 표준화된 메시지 브로커를 통한 비동기 통신을 메인 방식으로 채택하여, 한 컴포넌트의 장애가 다른 컴포넌트에 직접 영향을 미치는 것을 방지해야 합니다.

### 5. 데이터 저장소의 성능 및 병목 현상 (Data Store Performance Bottleneck)
- **설명:** 데이터 정제(Preprocessing) 및 피처 엔지니어링(Feature Engineering) 과정은 대용량의 원시 데이터를 메모리에 로드하고 복잡한 계산을 요구합니다. 만약 데이터 저장소(Storage)나 데이터 파이프라인 오케스트레이터의 컴퓨팅 자원이 병목현상을 일으킬 경우, 실시간에 가까운 고빈도의 데이터 처리 요청을 처리하지 못하게 됩니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium

## ⚠️ 잠재적 위험 분석

### 1. 데이터 파이프라인 오염 및 데이터 드리프트 (Data Pollution & Drift)
- **설명:** 시간이 지남에 따라 실제 운영 환경의 데이터 패턴(분포, 스키마, 물리적 변화)이 초기 학습 데이터나 정제 과정의 가정을 벗어나 변화(Data Drift)할 경우, AI 모델의 성능이 급격히 저하될 수 있습니다. 예를 들어, 계절 변화나 센서 교체로 원시 데이터의 측정 단위나 간격이 변할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** **1. 모니터링 시스템 구축:** 모델 서빙 단계(Inference)에서 예측 성능(Performance Degradation)뿐만 아니라, 입력 데이터의 통계적 특성(Feature Drift, Schema Validation)을 실시간으로 모니터링하는 Drift Detection 모듈을 구축하고, 이상 감지 시 자동으로 경고 및 모델 재학습 파이프라인을 트리거해야 합니다. **2. 버전 관리:** 모든 데이터 스키마와 모델은 반드시 버전(Version)을 관리하고, 데이터 소스 변경 시 백그라운드에서 영향도 분석을 수행합니다.

### 2. 엣지 디바이스 보안 취약점 및 데이터 위변조 (Edge Security Vulnerability & Tampering)
- **설명:** 원시데이터가 획득되는 '엣지(Edge)' 레벨의 IoT 디바이스나 게이트웨이가 해킹되거나 물리적으로 손상될 경우, 시스템에 유입되는 데이터가 위변조(Data Tampering)되거나 유출될 수 있습니다. 이는 최종적인 AI 활용의 신뢰도를 근본적으로 훼손합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium

### 3. 라벨링 편향 및 지식 격차 (Labeling Bias & Knowledge Gap)
- **설명:** 데이터 라벨링 단계는 사람의 주관적 판단(Domain Knowledge)에 의존하므로, 라벨링 수행자 간의 합의 부족이나 특정 관점(Bias)에 치우친 라벨링이 발생할 위험이 높습니다. 만약 라벨링 데이터가 실제 발생 가능한 모든 예외 상황(Edge Cases)을 포괄하지 못한다면, 모델은 해당 예외 상황에 취약합니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **1. 전문가 그룹 활용 (Ground Truth):** 라벨링 작업에 반드시 여러 도메인 전문가(Subject Matter Experts, SME)의 합의 메커니즘(Consensus Mechanism)을 적용해야 하며, 데이터셋에 포함되어야 할 예외 케이스를 목록화하고 관리해야 합니다. **2. 능동 학습(Active Learning) 적용:** 모델이 자신감이 낮은 데이터 포인트(Uncertainty Sampling)를 자동으로 식별하여, 이를 라벨링 전문가에게 우선적으로 검토 요청함으로써 라벨링 효율성과 정확도를 동시에 높여야 합니다.

### 4. 컴포넌트 간 인터페이스 비호환성 및 종속성 (Interoperability & Dependency Failure)
- **설명:** 시스템이 데이터 획득, 정제, 모델링 등 여러 계층에 걸쳐 외부 상용 솔루션(Commercial Off-The-Shelf, COTS)이나 표준화된 프로토콜(MQTT, REST API 등)을 다수 사용합니다. 이들 컴포넌트 간의 API 스키마가 변경되거나 버전이 맞지 않을 경우, 전체 파이프라인이 멈추는 '시스템 연쇄 고장'이 발생할 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** **1. 인터페이스 규격화 및 계약:** 모든 내부 및 외부 컴포넌트 간의 인터페이스는 엄격하게 API 계약(API Contract)을 정의하고 문서화해야 하며, 이 계약을 자동화된 테스트(Contract Testing)로 주기적으로 검증해야 합니다. **2. 메시지 인터페이스 강제:** 컴포넌트 간의 결합도를 낮추기 위해 직접적인 API 호출보다는 표준화된 메시지 브로커를 통한 비동기 통신을 메인 방식으로 채택하여, 한 컴포넌트의 장애가 다른 컴포넌트에 직접 영향을 미치는 것을 방지해야 합니다.
