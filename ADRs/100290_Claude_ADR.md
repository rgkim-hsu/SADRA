🏗️ 아키텍처 분석 보고서
===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트팜 병충해 감지를 위한 모듈형 실시간 모니터링-제어 분리 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서 병충해를 실시간으로 감지하고 자동 방제 작업을 수행하기 위해, 환경정보 수집(21), 객체식별(22), 병충해판단(23), 음영분석(24), 객체매칭(25) 등 다수의 감지 기능과 스케줄관리(41), 작업추천(42), 작업접수(43), 작업관리(44) 등의 제어 기능이 동시에 운영되어야 한다. 단일 모놀리식 구조로 설계할 경우 특정 모듈의 장애가 전체 시스템 다운으로 이어질 위험이 존재한다. |
| **결정(Decision)**       | 시스템을 모니터링모듈(2), 제어모듈(4), 결과관리모듈(5), 공유 데이터베이스(6)의 4개 독립 모듈로 분리하고, 모듈 간 양방향 인터페이스를 통해 느슨한 결합(Loose Coupling)을 구현한다. 결과관리모듈은 추적부(51)와 갱신부(52)로 분리하여 피드백 루프를 구성한다.                                                                        |
| **근거(Rationale)**      | 병충해 감지(모니터링)와 방제 작업 실행(제어)은 책임과 변경 주기가 상이하므로 분리가 타당하다. 공유 DB(6)를 중심으로 각 모듈이 비동기적으로 데이터를 교환함으로써, 모듈별 독립 배포 및 확장이 가능하다. 결과관리모듈의 갱신부(52)가 DB를 통해 모니터링모듈에 피드백을 제공함으로써 AI 모델의 지속적 학습 기반을 마련한다.                                              |
| **결과(Consequences)**   | ✅ 긍정적: 모듈별 독립 장애 격리, 기능 단위 확장성 확보, 병충해 판단 모델 교체 시 모니터링모듈만 수정하면 됨. ❌ 부정적: 모듈 간 인터페이스 정의 복잡도 증가, 공유 DB가 단일 장애점(SPOF)이 될 수 있음, 분산 환경에서의 데이터 정합성 관리 필요.                                                                                    |
| **트레이드오프(Trade-offs)** | 🟢 얻는 것: 유지보수성, 모듈별 독립 스케일링, 피드백 기반 모델 개선 루프. 🔴 감수할 것: 모듈 간 통신 오버헤드, 공유 DB 의존성으로 인한 병목 가능성, 운영 복잡도 증가.                                                                                                                                |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. 공유 데이터베이스(DB) 단일 장애점(SPOF) 위험

* **설명:** 모니터링모듈(2), 제어모듈(4), 결과관리모듈(5) 모두가 단일 데이터베이스(6)에 의존하는 구조로, DB 서버 장애 발생 시 병충해 감지 데이터 저장, 작업 스케줄 조회, 결과 추적 등 전체 시스템 기능이 동시에 마비되는 시나리오.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** DB 이중화(Active-Standby 또는 Active-Active 클러스터) 구성, 자동 Failover 메커니즘 도입. 각 모듈에 로컬 캐시 레이어(Redis 등)를 두어 DB 단절 시에도 최근 데이터 기반으로 제한적 운영 지속. 정기적인 백업 및 복구 훈련 실시.

### 2. 음영분석부(24) 및 객체식별부(22) 실시간 처리 성능 병목

* **설명:** 스마트팜 내 다수의 카메라 센서로부터 고해상도 영상 데이터가 동시에 유입될 때, 음영분석부(24)와 객체식별부(22)의 AI 추론 처리 지연으로 병충해 판단(23)까지의 응답 시간이 임계치를 초과하여 방제 골든타임을 놓치는 시나리오.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** GPU 가속 기반 엣지 컴퓨팅 노드를 현장에 배치하여 영상 전처리를 분산 수행. 모니터링모듈 내 처리 파이프라인에 메시지 큐(Kafka, RabbitMQ)를 도입하여 부하 분산. 처리 지연 발생 시 자동 알림을 트리거하는 SLA 모니터링 체계 구축.

### 3. 병충해 판단 모델의 오탐(False Positive) 및 미탐(False Negative) 위험

* **설명:** 병충해판단부(23)의 AI/머신러닝 모델이 조도 변화, 계절적 식물 형태 변화, 유사 해충 혼동 등으로 인해 정상 작물을 병충해로 오판하거나(오탐) 실제 병충해를 감지하지 못하는(미탐) 시나리오. 결과관리모듈의 갱신부(52)가 잘못된 데이터로 피드백되면 모델 품질이 점진적으로 저하될 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 신뢰도 임계값(Confidence Threshold) 기반의 인간 검토(Human-in-the-loop) 프로세스 도입. 결과관리모듈의 추적부(51)에서 판단 결과를 누적 분석하여 정기적인 모델 재학습 파이프라인 구성. 작업추천부(42)에서 고위험 작업은 자동 실행 전 관리자 승인 단계 추가.

### 4. 모듈 간 인터페이스 버전 비호환 및 통신 장애 위험

* **설명:** 모니터링모듈(2)과 제어모듈(4) 사이의 양방향 인터페이스에서, 어느 한쪽 모듈이 업데이트되어 API 스펙이 변경될 경우 상대 모듈이 예외 처리 없이 통신에 실패하는 시나리오. 이로 인해 작업접수부(43)가 모니터링 이벤트를 수신하지 못해 방제 작업이 자동으로 생성되지 않을 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모듈 간 인터페이스에 API 버전 관리(Semantic Versioning) 정책 수립. 하위 호환성(Backward Compatibility)을 보장하는 계약 기반 테스트(Contract Testing, Pact 등) 자동화. 통신 실패 시 재시도(Retry) 및 회로 차단기(Circuit Breaker) 패턴 적용.

### 5. 농장 현장 네트워크 불안정으로 인한 실시간 데이터 유실 위험

* **설명:** 스마트팜은 농촌 지역에 위치한 경우가 많아 LTE/5G 네트워크 불안정 구간에서 환경정보수집부(21)의 센서 데이터 및 영상 스트림이 간헐적으로 단절되는 시나리오. 데이터 유실 구간 동안 병충해가 확산되어도 모니터링모듈이 탐지하지 못함.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 엣지 게이트웨이에 로컬 데이터 버퍼링 기능 구현하여 네트워크 복구 시 자동 재전송(Store-and-Forward). 네트워크 단절 감지 시 현장 엣지 노드에서 독립적으로 기본 병충해 판단 및 알람 발생이 가능한 오프라인 동작 모드 설계. 이중화 통신망(유선 + 무선) 구성 검토.

### 6. 작업관리부(44) 자동 방제 명령의 보안 취약점 위험

* **설명:** 제어모듈(4)의 작업관리부(44)가 드론, 자동 살포 장치 등 물리적 액추에이터에 방제 명령을 전송하는 과정에서 외부 공격자가 통신을 가로채거나 위조 명령을 주입하여 과다 농약 살포 또는 작물 손상을 유발하는 시나리오. DB(6)에 대한 SQL 인젝션 공격으로 스케줄 데이터가 위변조될 수도 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 모든 모듈 간 통신에 TLS 1.3 암호화 및 상호 인증(mTLS) 적용. 액추에이터 제어 명령에 전자서명 기반 무결성 검증 도입. DB 접근에 최소 권한 원칙(Principle of Least Privilege) 적용 및 입력값 파라미터 바인딩으로 인젝션 방지. 이상 명령 패턴 감지를 위한 보안 이벤트 모니터링(SIEM) 구축.
