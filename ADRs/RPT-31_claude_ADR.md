📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 클라우드 중앙집중형 학습 관리와 엣지 모니터링의 하이브리드 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 다수의 사용자(User 1 ~ User n)가 실시간으로 농장 데이터를 모니터링해야 하며, 동시에 AI/ML 기반 학습 모델을 통해 영농 의사결정을 지원해야 한다. 단일 아키텍처로는 실시간 저지연 모니터링과 대규모 학습 연산을 동시에 충족하기 어렵다.                                                                                                                                                                 |
| **결정(Decision)**       | 사용자 대면 모니터링(Monitoring Function)과 학습 검증(Learning Screening Function)은 엣지/온프레미스 레이어에 배치하고, 핵심 학습 모델 관리(LMS), 농장 관리 제어(FMCF), 스마트팜 관리 기능(Smart Farming Management Function)은 클라우드에 집중 배치하는 하이브리드 2-티어 아키텍처를 채택한다. 클라우드와 엣지 간 인터페이스는 Learning Information Connection Function이 담당하며 Farming Information 채널로 단방향 데이터를 수신한다. |
| **근거(Rationale)**      | 모니터링 기능을 엣지에 배치하면 네트워크 장애 시에도 현장 가시성을 유지할 수 있다. LMS(Learning Management System)와 FMCF(Farm Management Control Function)를 클라우드에 집중함으로써 컴퓨팅 자원의 탄력적 확장이 가능하고, 다수 농장의 데이터를 통합 학습하여 모델 품질을 향상시킬 수 있다. Learning Screening Function이 클라우드 학습 결과를 검증·필터링함으로써 부적합 모델이 현장에 배포되는 것을 방지한다.                                         |
| **결과(Consequences)**   | (+) 클라우드 장애 시에도 로컬 모니터링 지속 가능 / (+) 학습 자원의 중앙 집중으로 규모의 경제 실현 / (+) Learning Screening을 통한 모델 품질 게이트 확보 / (-) 클라우드-엣지 간 데이터 동기화 복잡도 증가 / (-) Learning Information Connection Function이 단일 장애점(SPOF)이 될 위험 존재                                                                                                             |
| **트레이드오프(Trade-offs)** | 【획득】 운영 탄력성·확장성·모델 품질 보증 / 【감수】 아키텍처 복잡도 증가, 클라우드-엣지 간 네트워크 레이턴시 및 동기화 오버헤드, 이중 인프라 운영 비용                                                                                                                                                                                                                               |

### ADR-002: LMS-FMCF 직접 연동을 통한 폐쇄 루프(Closed-Loop) 농장 제어 설계

| 항목                     | 내용                                                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 클라우드 내 LMS가 생성한 학습 결과(모델 추론값, 처방 등)를 실제 농장 설비 제어에 반영하기 위한 실행 경로가 필요하다. 학습과 제어가 분리되면 의사결정 지연이 발생하고 자동화 수준이 저하된다.                                                    |
| **결정(Decision)**       | 클라우드 내부에서 LMS와 FMCF를 양방향 직접 연결(↔)하여, 학습 모델의 추론 결과가 즉시 농장 관리 제어 명령으로 전환되는 폐쇄 루프 구조를 설계한다. Smart Farming Management Function은 데이터 저장소(DB)를 공유하며 두 컴포넌트의 상태를 통합 관리한다. |
| **근거(Rationale)**      | 작물 생육 환경(온·습도, CO₂, 관개 등)은 시간에 민감하므로, 학습-추론-제어의 사이클 타임을 최소화해야 한다. 동일 클라우드 내 직접 연동은 외부 API 호출 대비 레이턴시를 대폭 절감한다. 공유 DB를 통해 이력 기반 학습과 실시간 제어 상태를 일관되게 유지할 수 있다.       |
| **결과(Consequences)**   | (+) 학습→제어 사이클 단축으로 농장 자동화 수준 향상 / (+) 단일 DB로 데이터 일관성 확보 / (-) LMS 또는 FMCF 중 하나의 장애가 전체 제어 루프에 영향 / (-) 두 컴포넌트 간 강결합으로 독립 배포·버전 관리 어려움                              |
| **트레이드오프(Trade-offs)** | 【획득】 저지연 자동 제어, 데이터 일관성 / 【감수】 컴포넌트 간 강결합, 장애 전파 위험, 마이크로서비스 전환 시 리팩토링 비용                                                                                          |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. Learning Information Connection Function 단일 장애점(SPOF) 위험

* **설명:** 클라우드의 Farming Information를 엣지의 Learning Screening Function으로 전달하는 유일한 경로인 Learning Information Connection Function이 장애·과부하·네트워크 단절 시, 클라우드 학습 결과가 엣지로 전혀 전달되지 않아 모델 갱신이 중단되고 현장은 구버전 모델로 계속 운영된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** Active-Standby 이중화 구성 적용, 메시지 큐(Kafka/RabbitMQ) 도입으로 비동기 버퍼링 처리, 헬스체크 및 자동 페일오버 메커니즘 구현, 엣지 측 마지막 유효 모델 캐싱 정책 수립

* * *

### 2. 클라우드-엣지 간 네트워크 단절 시 모니터링 데이터 유실

* **설명:** 농촌 지역 특성상 네트워크 불안정이 빈번하게 발생할 수 있으며, Monitoring Function에서 수집된 실시간 센서 데이터가 클라우드 전송 실패 시 로컬 버퍼 없이 유실될 경우, 학습 데이터셋의 연속성이 깨지고 모델 품질이 저하된다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** 엣지 레이어에 로컬 시계열 데이터베이스(InfluxDB 등) 배치로 오프라인 버퍼링 구현, 네트워크 복구 시 자동 재전송(Store-and-Forward) 로직 적용, 데이터 중요도 기반 우선순위 전송 정책 수립

* * *

### 3. LMS-FMCF 강결합에 의한 오작동 제어 명령 전파

* **설명:** LMS가 이상 학습 데이터 또는 과적합(Overfitting) 모델을 기반으로 잘못된 추론 결과를 생성할 경우, FMCF와의 직접 연동 구조로 인해 검증 없이 농장 설비(관개 시스템, 온도 제어 등)에 오제어 명령이 즉시 전달되어 작물 피해가 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** FMCF 실행 전 추론값 신뢰도 임계값(Confidence Threshold) 검증 레이어 삽입, 제어 명령의 변화율(Rate of Change) 한계값 설정으로 급격한 변동 차단, Shadow Mode 운영으로 신규 모델 검증 후 단계적 적용, 롤백 가능한 제어 이력 관리

* * *

### 4. 다중 사용자(User 1~n) 접근 제어 및 권한 관리 부재 위험

* **설명:** 개념도상 Monitoring Function이 불특정 다수 사용자(User 1 ~ User n)에게 개방된 구조로 표현되어 있으며, 사용자별 역할 기반 접근 제어(RBAC)나 인증 체계가 명시되지 않았다. 악의적 사용자 또는 내부자가 농장 제어 명령을 무단으로 발행하거나 타 농가 데이터에 접근할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** OAuth 2.0/OpenID Connect 기반 인증 체계 도입, 사용자-농장 단위 RBAC 정책 구현, API Gateway를 통한 접근 단일화, 모든 제어 명령에 대한 감사 로그(Audit Log) 기록 의무화, 농가 간 데이터 격리(Tenant Isolation) 적용

* * *

### 5. Smart Farming Management Function DB 단일화로 인한 데이터 병목 및 손실 위험

* **설명:** LMS와 FMCF가 단일 Smart Farming Management DB를 공유하는 구조에서, 대규모 학습 쿼리와 실시간 제어 트랜잭션이 동시에 발생할 경우 DB 락 경합·응답 지연이 발생한다. DB 장애 시 학습과 제어 기능이 동시에 마비되며, 장기 농업 이력 데이터의 영구 손실 가능성도 존재한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** CQRS 패턴 적용으로 학습용 Read Replica와 제어용 Write DB 분리, 실시간 제어 트랜잭션용 인메모리 캐시(Redis) 레이어 추가, 다중 가용 영역(Multi-AZ) DB 클러스터 구성, 정기 스냅샷 및 Point-in-Time Recovery 정책 수립

* * *

### 6. Learning Screening Function의 모델 검증 기준 모호성으로 인한 부적합 모델 배포

* **설명:** Learning Screening Function이 클라우드로부터 수신한 학습 모델을 '검증'한다고 가정하나, 검증 기준(정확도 임계값, 데이터 드리프트 감지, 편향성 검사 등)이 명시되지 않은 경우 형식적 검증에 그칠 수 있다. 계절·기후 변화로 데이터 분포가 달라진 상황에서 구 기준으로 통과된 모델이 현장 적용 후 예측 실패를 유발할 수 있다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** 모델 성능 지표(정확도, F1, MAE 등) 기반 자동화된 게이트 기준 정의 및 문서화, 데이터 드리프트 감지 알고리즘(PSI, KS-test) 통합, 계절별·지역별 모델 평가 데이터셋 분리 관리, MLOps 파이프라인(MLflow 등) 도입으로 모델 버전 및 실험 이력 추적
