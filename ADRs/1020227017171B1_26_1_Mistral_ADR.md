📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: **이벤트 기반 아키텍처를 통한 실시간 데이터 통합**

| 항목                     | 내용                                                                                                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜 시스템은 배송, 운송, 공장, 컴플라이언스, 노동 관리 등 다양한 서브시스템 간에 실시간으로 데이터를 동기화해야 함. 특히, 101(배송 기기 시스템), 107(운송 시스템), 111(배송 및 조율 트래킹 시스템), 113(공장 관리 시스템), 115(컴플라이언스 처리 시스템) 등에서 발생하는 데이터를 실시간으로 통합하여 효율적인 의사결정을 지원해야 함. |
| **결정(Decision)**       | **이벤트 기반 아키텍처(EDA, Event-Driven Architecture)**를 채택하여, 각 서브시스템에서 발생하는 이벤트(예: 배송 상태 변경, 공장 생산 완료, 컴플라이언스 검증 결과)를 실시간으로 발행하고, 필요한 시스템에서 구독하여 처리하도록 설계.                                                         |
| **근거(Rationale)**      | 스마트팜 시스템은 실시간성이 중요하며, 각 시스템이 독립적으로 운영되면서도 유기적으로 연결되어야 함. EDA는 시스템 간의 느슨한 결합(loose coupling)을 보장하며, 실시간 데이터 흐름과 확장성을 동시에 지원함. 또한, 117(공장 체인 관리) 및 121A/B/C(제3자 컴플라이언스 시스템)와 같은 외부 시스템과의 통합도 용이함.              |
| **결과(Consequences)**   | 실시간 데이터 동기화로 인한 운영 효율성 향상, 시스템 확장성 증가. 그러나 이벤트 중복 처리, 이벤트 순서 보장 등 복잡성이 증가할 수 있음.                                                                                                                             |
| **트레이드오프(Trade-offs)** | **장점**: 실시간성, 유연성, 확장성. **단점**: 이벤트 처리 로직의 복잡성 증가, 디버깅 어려움, 이벤트 스토리지 및 관리 오버헤드.                                                                                                                              |

### ADR-002: **마이크로서비스 기반 모듈화 설계**

| 항목                     | 내용                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 시스템은 배송, 운송, 공장, 컴플라이언스, 노동 관리 등 다양한 기능 영역을 포함하며, 각 영역이 독립적으로 개발, 배포, 운영되어야 함. 특히, 103(외부/내부 프론트엔드 시스템), 109(판매자 포털), 119(창고 관리 시스템) 등 사용자 인터페이스와 비즈니스 로직이 혼재되어 있음. |
| **결정(Decision)**       | **마이크로서비스 아키텍처**를 채택하여, 각 기능 영역(예: 배송, 운송, 컴플라이언스)을 독립적인 마이크로서비스로 분리. 각 마이크로서비스는 자체적인 데이터베이스와 API를 가지며, API 게이트웨이(117, 115 등)를 통해 통신.                               |
| **근거(Rationale)**      | 마이크로서비스는 시스템의 유연성, 확장성, 그리고 장애 격리를 보장함. 각 팀이 독립적으로 서비스 개발 및 배포가 가능하며, 특정 서비스 장애가 전체 시스템에 미치는 영향을 최소화할 수 있음.                                                         |
| **결과(Consequences)**   | 독립적인 개발 및 배포가 가능해져 개발 속도가 향상됨. 그러나 서비스 간 통신 오버헤드, 데이터 일관성 관리, 모니터링 복잡성 등이 증가함.                                                                                      |
| **트레이드오프(Trade-offs)** | **장점**: 유연성, 확장성, 장애 격리. **단점**: 운영 복잡성 증가, 분산 트랜잭션 관리 어려움, 네트워크 지연 가능성.                                                                                            |

### ADR-003: **에지 컴퓨팅을 통한 로컬 데이터 처리 최적화**

| 항목                     | 내용                                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템은 공장(113, 115), 창고(119), 노동 관리(125) 등에서 대량의 센서 데이터와 트랜잭션 데이터를 실시간으로 처리해야 함. 특히, 200(장비) 및 107A/B/C(장치) 등에서 발생하는 데이터는 네트워크 지연을 최소화해야 함.          |
| **결정(Decision)**       | **에지 컴퓨팅**을 도입하여, 공장 및 창고 등에서 발생하는 데이터를 로컬에서 미리 처리하고, 필요한 정보만 중앙 시스템(101, 103 등)으로 전송. 예를 들어, 115(컴플라이언스 처리 시스템)는 로컬에서 데이터 검증 후, 117(공장 체인 관리)로 결과만 전송. |
| **근거(Rationale)**      | 에지 컴퓨팅은 네트워크 대역폭 사용량을 줄이고, 실시간 처리 속도를 향상시킴. 특히, IoT 장비(200, 107A/B/C)에서 발생하는 대용량 데이터를 효율적으로 처리할 수 있음.                                                   |
| **결과(Consequences)**   | 네트워크 트래픽 감소, 실시간 처리 성능 향상. 그러나 에지 노드 관리 및 보안이 복잡해질 수 있음.                                                                                                |
| **트레이드오프(Trade-offs)** | **장점**: 실시간성 향상, 네트워크 효율성. **단점**: 에지 노드 관리 복잡성, 보안 취약점 증가.                                                                                             |

⚠️ 잠재적 위험 분석
------------

### 1. **실시간 데이터 동기화 실패**

* **설명:** 이벤트 기반 아키텍처에서 이벤트 발행/구독 시스템(예: 117, 115)에 장애가 발생하여, 배송(101) 및 운송(107) 시스템 간 데이터가 동기화되지 못하는 경우. 예를 들어, 배송 상태가 업데이트되지 않아 창고(119)에서 재고 관리에 오류가 발생할 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * 이벤트 브로커(예: Kafka, RabbitMQ)의 클러스터링 및 복제 구성.
  * 이벤트 처리 모니터링 및 재시도 메커니즘 도입.
  * 데이터 일관성을 보장하기 위한 SAGA 패턴 또는 2PC(Two-Phase Commit) 적용.

* * *

### 2. **컴플라이언스 데이터 위변조**

* **설명:** 제3자 컴플라이언스 시스템(121A/B/C)에서 전송된 데이터가 위변조되어, 공장(113) 또는 배송 시스템(101)에서 잘못된 의사결정을 내리는 경우. 예를 들어, 컴플라이언스 인증서가 조작되어 불량 제품이 유통될 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * 블록체인 기술을 활용한 데이터 무결성 검증.
  * 디지털 서명 및 암호화를 통한 데이터 보안 강화.
  * 정기적인 컴플라이언스 시스템 감사 및 로그 분석.

* * *

### 3. **에지 노드 보안 취약점**

* **설명:** 에지 컴퓨팅 노드(예: 200, 107A/B/C)가 물리적/네트워크 공격에 노출되어, 로컬 데이터가 유출 또는 조작되는 경우. 예를 들어, 공장 내 에지 노드가 해킹당해 생산 데이터가 유출될 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * 에지 노드에 보안 패치 및 인증 메커니즘(예: TPM, Secure Boot) 적용.
  * 네트워크 분리(Network Segmentation) 및 방화벽 구성.
  * 정기적인 보안 감사 및 침해 탐지 시스템(IDS) 도입.

* * *

### 4. **마이크로서비스 간 통신 장애**

* **설명:** 마이크로서비스 간 API 호출(예: 103 ↔ 101, 119 ↔ 123)이 지연 또는 실패하여, 시스템 전체 성능이 저하되는 경우. 예를 들어, 노동 관리 시스템(125)이 배송 시스템(101)과 통신 실패로 인해 인력 배치가 지연될 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * API 게이트웨이(117, 115)에 로드 밸런싱 및 재시도 메커니즘 도입.
  * 서비스 메시(Service Mesh, 예: Istio)를 통한 트래픽 관리 및 장애 복구.
  * 서킷 브레이커(Circuit Breaker) 패턴을 통한 장애 격리.

* * *

### 5. **IoT 장비 호환성 문제**

* **설명:** 다양한 IoT 장비(200, 107A/B/C)가 서로 다른 프로토콜(예: MQTT, CoAP)을 사용하여, 시스템 통합 시 호환성 문제가 발생하는 경우. 예를 들어, 107A 장비에서 발생한 데이터가 101(배송 기기 시스템)에서 인식되지 못함.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * 표준화된 프로토콜(예: OPC UA, MQTT 5.0) 채택 및 어댑터 패턴 적용.
  * 장비 제조사와의 협업을 통한 호환성 테스트 및 인증.
  * 에지 게이트웨이를 통한 프로토콜 변환 및 데이터 표준화.

* * *

### 6. **시스템 확장성 한계**

* **설명:** 시스템 트래픽이 급증(예: seasonal demand)하여, 기존 인프라(101, 103, 117 등)가 처리 능력을 초과하는 경우. 예를 들어, 추수 시즌에 배송 요청이 급증하여 시스템이 다운될 수 있음.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * 클라우드 기반 오토스케일링(Auto-scaling) 도입.
  * 컨테이너화(Docker) 및 오케스트레이션(Kubernetes)을 통한 유연한 리소스 관리.
  * 캐싱 메커니즘(Redis, CDN)을 통한 성능 최적화.
