===============

📋 ADR (Architecture Decision Record)
-------------------------------------

### ADR-001: 스마트팜 작업 관리 중심의 코드 기반 참조 무결성 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 환경에서는 작업자(sf_worker), 작업계획(sf_workplan), 작업기(sf_machine), 작업유형(sf_wtype), 센서/이벤트(sf_msevent), TAG(sf_tag) 등 다수의 도메인 엔티티가 상호 연관되어 운영된다. 작업자의 일/시간별 작업요청·결과를 추적하고, 작업기의 TAG CODE를 통해 센서 이벤트와 연계해야 하며, 작업유형(수확, 적엽, 방제, 유식 등)에 따른 분류가 필요하다. 이기종 데이터(인적 자원, 기계 자원, 센서 데이터)를 하나의 통합 스키마로 관리해야 하는 구조적 과제가 존재한다. |
| **결정(Decision)**       | WKCODE(작업자 식별), WTCODE(작업유형 식별), TAG CODE(작업기-이벤트 연계), MCCODE(기계 식별)를 핵심 참조 키로 삼아, sf_workplan을 중심 허브 테이블로 구성하는 Star Schema 기반의 관계형 데이터 모델을 채택한다. sf_msevent는 sf_machine과 sf_tag를 TAG CODE로 연결하는 브릿지 역할을 수행한다.                                                                                                 |
| **근거(Rationale)**      | 작업계획(sf_workplan)이 작업자·작업유형·작업기 정보를 모두 참조하는 중심점이므로, 이를 Fact 테이블로 두고 나머지를 Dimension으로 구성하면 조회 성능과 데이터 정합성을 동시에 확보할 수 있다. TAG CODE 기반 연계는 IoT 센서 표준 식별 체계와 호환되며, 확장 시 새로운 센서/기기 추가가 용이하다.                                                                                                                        |
| **결과(Consequences)**   | (긍정) 작업자별·기기별·작업유형별 다차원 분석이 가능하며, 이력 추적과 감사(Audit)가 명확해진다. sf_workplan 단일 조회로 전체 작업 맥락 파악이 가능하다. (부정) sf_workplan 테이블에 대한 쓰기/읽기 집중으로 병목 발생 가능성이 있으며, 엔티티 간 외래키 제약이 많아 스키마 변경 시 연쇄 영향이 크다.                                                                                                                      |
| **트레이드오프(Trade-offs)** | (장점) 데이터 정합성 보장, 중복 최소화, 표준 SQL 기반 분석 용이. (단점) 수평 확장(Scale-out) 어려움, 실시간 대용량 센서 데이터 처리 시 RDBMS 한계 노출 가능, 스키마 마이그레이션 비용 증가.                                                                                                                                                                                     |

* * *

### ADR-002: TAG CODE 기반 IoT 이벤트-기기 연계 브릿지 구조 채택

| 항목                     | 내용                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | sf_machine(작업기)과 sf_msevent(기계 센서 이벤트) 사이의 연계를 TAG CODE로 수행하며, sf_tag는 TAG 메타 정보를 별도 관리한다. 스마트팜 환경에서는 다수의 작업기에 복수의 센서가 부착되어 지속적으로 이벤트를 발생시키므로, 이벤트-기기-TAG 3자 관계를 효율적으로 표현해야 한다. |
| **결정(Decision)**       | sf_msevent를 MCCODE(기계코드)와 TAG CODE를 동시에 보유하는 이벤트 로그 테이블로 설계하고, sf_tag를 TAG 마스터로 분리하여 TAG의 물리적 속성과 이벤트 데이터를 구분 관리하는 구조를 채택한다.                                                    |
| **근거(Rationale)**      | TAG CODE를 공통 식별자로 사용함으로써 신규 센서 추가 시 sf_tag 마스터 등록만으로 확장이 가능하다. MCCODE와 TAG CODE의 복합 참조는 특정 기계의 특정 센서 이벤트를 정밀하게 필터링할 수 있게 한다.                                                    |
| **결과(Consequences)**   | (긍정) 센서 종류 확장 시 코드 변경 최소화, 기기-이벤트 간 명확한 추적 경로 확보. (부정) sf_msevent에 이벤트가 대량 적재될 경우 테이블 크기 급증, 아카이빙 전략 부재 시 성능 저하.                                                                |
| **트레이드오프(Trade-offs)** | (장점) 유연한 TAG 확장성, 명확한 이벤트 출처 추적. (단점) MCCODE + TAG CODE 복합 인덱스 관리 부담, 실시간 스트리밍 처리 미지원 시 이벤트 유실 위험.                                                                              |

* * *

⚠️ 잠재적 위험 분석
------------

### 1. sf_workplan 단일 허브 테이블 병목(Single Point of Contention)

* **설명:** sf_workplan이 sf_worker, sf_wtype, sf_machine을 모두 참조하는 중심 테이블로 기능하므로, 작업자 수·작업기 수 증가에 따라 동시 INSERT/UPDATE 트랜잭션이 집중된다. 수확철 등 피크 시즌에 수백 명의 작업자와 수십 대의 기계가 동시에 작업 결과를 기록할 경우 Lock 경합 및 응답 지연이 발생할 수 있다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 테이블 파티셔닝(날짜 기반), 작업계획 이력과 실시간 상태를 분리하는 CQRS 패턴 도입, 쓰기 부하 분산을 위한 큐(Queue) 기반 비동기 처리(예: Kafka, RabbitMQ) 적용.

* * *

### 2. TAG CODE 불일치로 인한 센서 이벤트 유실 또는 미매핑

* **설명:** sf_msevent에 기록되는 TAG CODE가 sf_tag 또는 sf_machine에 등록되지 않은 코드일 경우, 참조 무결성 위반으로 이벤트가 거부되거나, 무결성 검사를 우회하면 고아(Orphan) 레코드가 누적된다. 현장에서 새 센서를 임시 부착하고 마스터 등록을 지연하는 운영 패턴에서 빈번히 발생한다.
* **심각도:** 🔴 High
* **발생 가능성:** 🔴 High
* **대응 방안:** TAG 자동 등록(Auto-provisioning) 워크플로우 구축, 미등록 TAG 이벤트에 대한 격리 큐(Dead Letter Queue) 운영, TAG CODE 등록 현황 실시간 모니터링 대시보드 제공.

* * *

### 3. 작업자 인증·권한 관리 부재로 인한 데이터 위변조 위험

* **설명:** 현재 개념도에서 sf_worker는 WKCODE로만 식별되며, 인증(Authentication) 및 권한(Authorization) 계층이 명시되어 있지 않다. 악의적 사용자 또는 실수로 타인의 WKCODE를 사용하여 작업 결과를 기록하거나, 관리자 권한 없이 작업계획을 변경하는 시나리오가 가능하다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** WKCODE와 연계된 JWT/OAuth 2.0 기반 인증 레이어 추가, Role-Based Access Control(RBAC) 적용(작업자/관리자/분석자 역할 분리), 작업 결과 기록 시 전자서명 또는 타임스탬프 기반 감사 로그 의무화.

* * *

### 4. 실시간 센서 데이터 대용량 처리 시 RDBMS 확장 한계

* **설명:** sf_msevent는 작업기에 부착된 다수의 센서로부터 지속적으로 이벤트를 수신하는 구조다. 스마트팜 규모 확대(온실 수 증가, 센서 밀도 증가)에 따라 초당 수천 건 이상의 이벤트가 발생할 수 있으며, 현재 아키텍처가 전통적 RDBMS 기반일 경우 수평 확장이 어려워 성능 한계에 도달한다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:** sf_msevent에 TimescaleDB, InfluxDB 등 시계열 특화 DB를 도입하거나, 핫/콜드 데이터 티어링 전략 수립. 실시간 스트리밍 처리를 위해 Apache Kafka + Flink 조합의 이벤트 파이프라인 구성 검토.

* * *

### 5. 작업유형(sf_wtype) 코드 체계의 경직성으로 인한 도메인 확장 장애

* **설명:** 현재 sf_wtype은 수확, 적엽, 방제, 유식(coffee) 등 고정 분류를 WTCODE로 관리한다. 새로운 작물 도입이나 작업 방식 변경(예: 드론 방제 추가, 자동화 수확 분리) 시 코드 체계 재설계가 필요하며, 이미 적재된 sf_workplan 이력 데이터와의 하위 호환성 유지가 어려워진다.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:** sf_wtype에 계층형 분류(부모-자식 코드) 구조 도입(예: 대분류/소분류), 코드 폐기 시 이력 보존을 위한 Soft Delete + 유효기간(valid_from/valid_to) 컬럼 추가, 작업유형 변경 이력 관리 테이블 별도 운영.

* * *

### 6. 개인정보 및 작업자 행동 데이터 보호 미흡

* **설명:** sf_workplan은 작업자의 일/시간별 작업요청 및 결과를 상세히 기록하므로, 사실상 작업자의 노동 행태를 정밀하게 추적하는 데이터가 누적된다. 이는 개인정보보호법(PIPA) 및 근로 관련 법규 상 민감 정보에 해당할 수 있으며, 데이터 유출 시 작업자 프라이버시 침해로 이어진다.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:** 작업자 개인 식별 정보의 암호화 저장(AES-256), 데이터 접근 로그 의무화, 분석 목적 시 WKCODE 익명화(pseudonymization) 처리, 데이터 보유 기간 정책 수립 및 자동 삭제 스케줄러 구현.
