# 🏗️ 아키텍처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: [모듈화된 다단계 데이터 검증 파이프라인 도입]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜과 같은 IoT 환경에서 발생하는 원시 데이터(raw data)는 센서 오류, 통신 지연, 환경적 요인에 의해 노이즈가 포함될 가능성이 높습니다. 단순한 필터링이 불가능하고, 비즈니스 로직과 연관된 의미론적 검증이 필요합니다. |
| **결정(Decision)** | **다단계 검증 로직 분리**: 원시 데이터 입력 -> 오류 데이터 처리 -> 갱신주기 검증 -> 범위 이상치 검증 -> 클리닝 처리 -> 정제 데이터 저장 순으로 명확한 단계적 파이프라인을 구축합니다. 각 단계별 정의를 별도의 정책(정책 저장소)과 연결합니다. |
| **근거(Rationale)** | 1. **유연성**: 특정 검증 규칙 (예: 농사철별 온도 범위) 이 변경되어도 해당 모듈만 수정하면 됩니다.<br>2. **추적성**: 각 데이터 포인트가 어떤 검증 단계를 통과했는지 이력(처리결과이력)을 남길 수 있습니다.<br>3. **확장성**: 새로운 데이터 소스가 추가될 때 기존 파이프라인에 병렬로 연결 가능 (e.g., 환경정보, 제어정보 등). |
| **결과(Consequences)** | **긍정**: 데이터 신뢰성 극대화. 분석용 정제 데이터에 대한 확신을 줌.<br>**부정**: 초기 설계가 복잡하고, 데이터 흐름 지연(latency) 발생 가능성. |
| **트레이드오프(Trade-offs)** | 검증 정밀도(정밀하게 걸러냄) 과 처리 속도/데이터 양 간의 균형이 필요함. 과도한 검증은 데이터 부족으로 이어질 수 있으므로 각 단계별 민감도 조정이 필수적임. |

## ⚠️ 잠재적 위험 분석

### 1. [과도한 데이터 손실 위험 (False Positive Risk)]
- **설명:** 스마트팜의 특수한 상황 (예: 급격한 기상 변화, 축사 환기 시점의 급격한 온도 하강) 에서 발생하는 정상적이지만 통계적으로 극단적인 데이터를 '범위 이상치'로 잘못 판단하여 삭제하거나 클리닝하는 경우.
- **심각도:** 🟠 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 검증 정책에 '임계치 완화 구간' (Dead Band) 도입 및 수동 리뷰 절차 마련. 시계열 분석 기법 적용하여 단일 데이터 포인트의 이상으로 인접 데이터 급변화 패턴인지 판단하여 오검출 방지.

### 2. [검증 정책 갱신 누락 위험 (Configuration Drift)]
- **설명:** 계절적 변화에 따른 센서 오차 한도나 기기 교체 시 적용해야 하는 검증 정책 (Range, Period) 을 유지보스 팀이 업데이트하지 않아 시스템이 구형 데이터 기준에 맞춰 데이터를 삭제하는 경우.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 정책 변경 시 변경 로그 남김 및 자동화된 시나리오 테스트 (Regression Test) 를 통해 정책 변경 전후 데이터 일관성 검증.

### 3. [대규모 데이터 처리 병목 위험 (Performance Bottleneck)]
- **설명:** 수천 개의 센서에서 밀리초 단위 간격으로 수집된 대용량 데이터가 '오류데이터 처리' 및 '갱신주기 이상치 처리' 단계를 통과하며 실시간성이 저하되어 실시간 제어가 불가능해지는 경우.
- **심각도:** 🟠 Medium
- **발생 가능성:** 🔴 High (IoT 데이터 양 증가 시)
- **대응 방안:** 배치 처리와 실시간 처리를 분리 (Stream/Batch Architecture). 검증 로직을 C/C++ 등 고성능 언어나 RPA (Rule Processing Architecture) 로 구현하여 성능 최적화.

### 4. [데이터 클리닝 로직의 투명성 부재 위험 (Black Box Risk)]
- **설명:** '데이터 클리핑 처리' 단계를 경과한 데이터가 어떻게 수정되었는지 로그가 명확하지 않아, 문제 발생 시 원인을 파악하거나 데이터를 복원하기 어려운 경우.
- **심각도:** 🟠 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** '처리결과이력' 테이블에 수정 전 값, 수정 후 값, 적용된 규칙 ID, 수정 사유 코드를 상세히 기록 (Audit Trail).

### 5. [다양한 센서 제조사 데이터 포맷 호환성 위험 (Interoperability Issue)]
- **설명:** 스마트팜은 다양한 벤더의 센서를 사용하는데, 각 벤더마다 데이터 단위 (예: 온도는 섭씨/화씨), 정밀도, 전달 주기 (Sampling Rate) 가 다르며, 이 차이를 검증 로직에 반영하지 못해 특정 벤더 데이터만 필터링되는 경우.
- **심각도:** 🟠 Medium
- **발생 가능성:** 🔴 High
- **대응 방안:** 표준화 노력 (oneM2M, ISO/IEC 30141 참조) 기반의 표준 포맷 정의 및 각 벤더별 매핑 테이블을 구축하여 변환 후 검증 수행.
