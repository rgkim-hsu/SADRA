### ADR-001: **마이크로서비스 기반 모듈화 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 도메인에서 대형 농가, 소규모 농가, 전문 농가 등 다양한 사용자 유형에게 맞춤형 스마트 도사 서비스를 제공해야 함. 각 농가 유형별로 요구되는 기능(총입/사업 관리, 생산 관리, 출하 관리 등)이 상이하며, 실시간 데이터 수집(온습도, 화재/전기누전, CCTV 등)과 분석이 필요함.                                                               |
| **결정(Decision)**       | **마이크로서비스 아키텍처**를 채택하여 각 기능(예: 온습도 정보수집, CCTV 화면 대시보드, 출하 패치 수 카운팅 등)을 독립적인 서비스로 분리하고, API 게이트웨이를 통해 통합 관리.                                                                                                                        |
| **근거(Rationale)**      | 1) 각 기능의 독립적인 배포 및 확장성 보장(예: 대형 농가는 CCTV와 패치 최신화 기능 강조, 소규모 농가는 출하 예보 기능 강조). 2) 특정 서비스 장애 시 다른 서비스에 미치는 영향 최소화. 3) IoT 센서(온습도, 화재 감지 등)에서 수집된 데이터를 실시간으로 처리하고, 각 서비스에서 필요한 데이터만 선택적으로 활용 가능. 4) 사용자 유형별로 필요한 기능만 패키지화하여 제공할 수 있음. |
| **결과(Consequences)**   | **장점**: 유연성과 확장성 향상, 장애 격리, 사용자 맞춤형 서비스 제공 용이. **부정적 결과**: 서비스 간 통신 오버헤드 증가, 데이터 일관성 관리 복잡성, 모니터링 및 로깅 시스템 구축 필요.                                                                                                                  |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 빠른 기능 추가/수정, 사용자 요구사항에 유연한 대응, 시스템 가용성 향상. **감수하는 단점**: 분산 시스템의 복잡성, 네트워크 지연 가능성, 데이터 동기화 이슈.                                                                                                                           |

### ADR-002: **실시간 데이터 스트리밍 및 이벤트 드리븐 아키텍처(EDA) 도입**

| 항목                     | 내용                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | IoT 센서(온습도, 화재, 전기누전 등)에서 실시간으로 데이터가 생성되며, 이 데이터를 기반으로 즉시 알림(예: 화재 발생 시 알림) 또는 대시보드 업데이트가 필요함.                     |
| **결정(Decision)**       | **Apache Kafka** 또는 **AWS Kinesis**와 같은 메시지 브로커를 도입하여 실시간 데이터 스트리밍 파이프라인을 구축. 이벤트 드리븐 방식으로 데이터 변화에 즉시 반응하는 시스템 설계. |
| **근거(Rationale)**      | 1) 실시간 데이터 처리 요구사항(예: 화재 감지 시 즉시 알림) 충족. 2) 데이터 손실 최소화 및 순서 보장. 3) 여러 서비스(예: CCTV 화면 대시보드, 패치 최신화 기능)에서 동시 접근 가능.  |
| **결과(Consequences)**   | **장점**: 실시간 데이터 처리 가능, 시스템 반응성 향상, 데이터 손실 방지. **부정적 결과**: 메시지 브로커 운영 비용, 시스템 복잡성 증가.                               |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 실시간성 보장, 확장성 높은 데이터 파이프라인. **감수하는 단점**: 인프라 비용 증가, 장애 시 데이터 유실 가능성(예: 브로커 장애 시).                        |

### ADR-003: **클라우드 기반 인프라 및 하이브리드 배포 전략**

| 항목                     | 내용                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 대형 농가의 경우 대용량 데이터(예: CCTV 영상, 5,000두 이상의 사육 규모) 저장 및 처리 필요, 소규모 농가는 저비용 인프라 요구.                                                       |
| **결정(Decision)**       | **하이브리드 클라우드 인프라** 채택: 1) 대형 농가용 서비스는 클라우드(예: AWS, Azure)에 배포하여 확장성 보장. 2) 소규모 농가용 서비스는 엣지 컴퓨팅(예: 라즈베리파이) 또는 로컬 서버에서 운영하여 비용 절감.      |
| **근거(Rationale)**      | 1) 대형 농가의 경우 클라우드의 무한 확장성을 활용하여 대용량 데이터 처리. 2) 소규모 농가의 경우 로컬에서 데이터 전처리 후 클라우드로 전송하여 네트워크 비용 절감. 3) 농장 환경(인터넷 연결 불안정 지역)에서 오프라인 동작 지원. |
| **결과(Consequences)**   | **장점**: 비용 효율성, 유연한 인프라 관리, 오프라인 동작 지원. **부정적 결과**: 하이브리드 환경의 복잡한 관리, 데이터 동기화 이슈.                                                     |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 비용 최적화, 지역적 제약 극복. **감수하는 단점**: 인프라 관리 복잡성, 보안 취약점 증가.                                                                     |

### ADR-004: **API 게이트웨이를 통한 사용자 맞춤형 서비스 라우팅**

| 항목                     | 내용                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 각 농가 유형(대형/소규모/전문)별로 필요한 기능이 다름(예: 대형 농가는 CCTV와 패치 최신화, 소규모 농가는 출하 예보).                          |
| **결정(Decision)**       | **API 게이트웨이**를 통해 사용자 유형에 따라 요청을 적절한 마이크로서비스로 라우팅. 예를 들어, 대형 농가 사용자는 CCTV 서비스와 패치 관리 서비스로 우선 연결. |
| **근거(Rationale)**      | 1) 사용자 경험 최적화(불필요한 기능 노출 방지). 2) 서비스 간 의존성 최소화. 3) 인증/인가(예: 농가 유형 인증)를 통한 보안 강화.                 |
| **결과(Consequences)**   | **장점**: 맞춤형 서비스 제공, 보안 강화, 트래픽 최적화. **부정적 결과**: API 게이트웨이 단일 장애점(Single Point of Failure) 가능성.   |
| **트레이드오프(Trade-offs)** | **얻는 장점**: 사용자 편의성 향상, 보안 강화. **감수하는 단점**: API 게이트웨이 장애 시 시스템 전체 장애 가능성.                         |

⚠️ 잠재적 위험 분석
------------

### 1. **실시간 데이터 처리 지연**

* **설명:** IoT 센서에서 발생한 이벤트(예: 화재 감지)가 메시지 브로커(Kafka)를 통해 처리되는 도중 네트워크 지연 또는 브로커 과부하로 인해 알림이 지연되는 경우.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * 메시지 브로커의 클러스터링을 통해 고가용성 보장.
  * 이벤트 우선순위 지정(예: 화재 알림 > 온습도 데이터) 및 Priority Queue 적용.
  * 엣지 컴퓨팅을 통해 로컬에서 즉각적인 알림 처리(예: 화재 감지 시 로컬 알림 발송 후 클라우드로 동기화).

* * *

### 2. **마이크로서비스 간 데이터 일관성 문제**

* **설명:** 예시로, "출하 패치 수 카운팅" 서비스와 "출하 예보 계절 기능" 서비스에서 동일한 출하 데이터를 사용하지만, 데이터 동기화 실패로 인해 각 서비스에서 상이한 데이터를 표시하는 경우.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **Saga 패턴** 또는 **2PC(2-Phase Commit)** 프로토콜을 통해 분산 트랜잭션 관리.
  * 이벤트 소싱(Event Sourcing)을 통해 데이터 변경 이력을 추적 및 복구.
  * 주기적인 데이터 동기화 검증 스크립트 자동화.

* * *

### 3. **클라우드 인프라 비용 초과**

* **설명:** 대형 농가의 CCTV 영상 저장 또는 5,000두 이상 사육 규모에서 발생하는 대용량 데이터로 인해 클라우드 스토리지 및 컴퓨팅 비용이 예산 초과하는 경우.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:**
  * **Cold Storage** (예: AWS S3 Glacier) 활용하여 오래된 CCTV 영상 아카이빙.
  * **데이터 압축** 및 **증분 백업** 전략 도입.
  * 사용량 모니터링 및 자동 스케일링 정책 수립(예: 사용량 저조 시 리소스 축소).

* * *

### 4. **보안 취약점(데이터 유출 또는 무단 접근)**

* **설명:** 농장의 민감한 데이터(예: CCTV 영상, 생산량 정보)가 외부로 유출되거나, 무단으로 API에 접근하여 서비스 오용(예: 출하 패치 수 조작)하는 경우.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **Zero Trust 보안 모델** 적용: 모든 API 요청에 대해 엄격한 인증/인가(예: JWT 토큰 + OAuth 2.0).
  * **데이터 암호화**: 저장 시(AES-256) 및 전송 시(TLS 1.3) 암호화 적용.
  * **API 게이트웨이에 WAF(Web Application Firewall)** 설치 및 정기적인 보안 감사.

* * *

### 5. **엣지 디바이스(라즈베리파이 등) 장애**

* **설명:** 소규모 농가에서 사용되는 엣지 디바이스(예: 라즈베리파이)가 하드웨어 고장 또는 소프트웨어 오류로 인해 데이터 수집 및 전송이 중단되는 경우.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🔴 High
* **대응 방안:**
  * **이중화 구성**: 주요 엣지 디바이스에 백업 디바이스 연결.
  * **자동 복구 메커니즘**: 디바이스 장애 시 자동 재시작 또는 클라우드로 알림 전송.
  * **로컬 캐시**: 일시적인 장애 시 데이터를 로컬에 저장 후 복구 시 동기화.

* * *

### 6. **사용자 인터페이스(UI) 복잡성 증가**

* **설명:** 대형 농가, 소규모 농가, 전문 농가 등 각 사용자 유형별로 제공되는 기능이 증가함에 따라 UI가 복잡해져 사용자 경험(UX) 저하.
* **심각도:** 🟢 Low
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **역할 기반 UI 맞춤화**: 사용자 유형에 따라 필요한 기능만 노출(예: 대형 농가는 CCTV 대시보드 강조).
  * **프로그레시브 웹 앱(PWA)** 도입으로 모바일 환경 최적화.
  * **사용자 피드백 수집**을 통한 지속적인 UI/UX 개선.
