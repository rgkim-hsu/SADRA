## 📋 ADR (Architecture Decision Record)

### **ADR-001: 분산형 데이터 처리 아키텍처 채택 및 모듈화 설계**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **예측수량, 생육상태 분석, 작물모형 처리** 등 농업 IoT 데이터 처리 요구사항을 충족해야 하며, **기상DB, 품종DB, 예측기상 데이터** 등 다중 데이터 소스 통합과 실시간 처리 능력을 필요로 함. 또한 사용자 입력(지역, 품종, 이앙기)에 따라 동적으로 처리 로직이 변해야 함. |
| **결정(Decision)** | 1. **모듈화 아키텍처** 채택: 예측수량, 생육상태, 작물모형 등 기능별로 독립적인 모듈로 분리하여 재사용성과 유지보수성을 높임.
2. **이벤트 기반 처리** 도입: 사용자 입력 및 실시간 데이터 수신 시 이벤트 트리거를 통해 각 모듈이 병렬 처리되도록 설계.
3. **데이터 중복 최소화**를 위한 **공유 DB 레이어** 구축: 기상DB, 품종DB 등 공통 데이터는 중앙 집중식으로 관리하고, 예측 결과는 별도 저장소(예: 영용정보)에 기록.
4. **에지 컴퓨팅 지원**을 위한 **지역별 처리 노드** 배포: 지역별로 데이터 전처리를 수행하여 네트워크 부하를 줄임. |
| **근거(Rationale)** | - **모듈화**: ISO/IEC 30141:2024 표준에서 권장하는 재사용 가능한 설계 원칙에 부합.
- **이벤트 기반 처리**: oneM2M 및 ETSI EN 303 645 표준에서 권장하는 실시간 처리 및 보안 요구사항을 충족.
- **공유 DB 레이어**: 데이터 일관성과 접근 효율성을 높임(ITU-T X.1352 표준 준수).
- **에지 컴퓨팅**: IoT 시스템에서 네트워크 지연과 대역폭 문제를 해결하기 위한 IEEE 2413 표준과 일치. |
| **결과(Consequences)** | - **장점**: 모듈별 업데이트가 용이하며, 시스템 확장성이 높음. 실시간 처리 성능 향상.
- **단점**: 모듈 간 통신 오버헤드 발생 가능. 중앙 DB가 단일 장애 지점이 될 수 있음. |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 성능**: 모듈 간 통신 오버헤드 vs. 유지보수성 향상.
- **중앙 DB vs. 분산 처리**: 데이터 일관성 vs. 네트워크 부하 분산. |

### **ADR-002: 보안 및 데이터 무결성 강화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **예측 데이터 및 생육 상태 정보** 등 민감한 농업 데이터를 처리하며, **외부 공격 및 데이터 변조** 위험에 노출될 수 있음. 또한, **사용자 인증 및 권한 관리**가 필요함. |
| **결정(Decision)** | 1. **데이터 암호화**: DB 레벨(기상DB, 품종DB) 및 통신 레벨(REST/CoAP 프로토콜)에서 AES-256 암호화 적용.
2. **접근 통제**: 사용자별 RBAC(Role-Based Access Control) 구현. 예: 재배자료 조회는 "재배자" 역할만 가능.
3. **블록체인 기반 로그 관리**: 영용정보 저장소에 기록된 데이터 변경 이력을 불변성 보장 위해 블록체인 기술 적용.
4. **IoT 기기 인증**: ETSI EN 303 645 표준 준수하여 기기 인증 및 통신 암호화 강제. |
| **근거(Rationale)** | - **ETSI EN 303 645** 및 **ISO/IEC 27030:2020** 표준 준수.
- **블록체인**: 데이터 무결성을 보장하기 위한 KISA 권장 기술.
- **RBAC**: oneM2M 표준에서 권장하는 접근 통제 메커니즘. |
| **결과(Consequences)** | - **장점**: 데이터 보안 강화 및 규제 준수 가능.
- **단점**: 암호화 및 블록체인 처리 오버헤드 발생 가능. |
| **트레이드오프(Trade-offs)** | - **보안 vs. 성능**: 암호화 및 인증 오버헤드 vs. 데이터 보안.
- **중앙화된 로그 vs. 분산 처리**: 블록체인 처리 비용 vs. 데이터 무결성. |

### **ADR-003: 상호운용성 및 표준 준수**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 시스템은 **다양한 농업 장비 및 플랫폼**과 통합되어야 하며, **국내외 표준**을 준수해야 함. 특히, **스마트팜 데이터 상호운용 프레임워크**와 호환성을 확보해야 함. |
| **결정(Decision)** | 1. **oneM2M 표준 준수**: API 및 데이터 포맷을 oneM2M Core Service Layer와 호환되도록 설계.
2. **OCF/Matter 프로토콜 지원**: 스마트홈/스마트팜 장비와의 상호운용성을 위해 OCF 프레임워크 적용.
3. **TTA 표준 준수**: 국내 스마트팜 데이터 관리 요구 사항(TTAK.KO-10.1170) 준수하여 데이터 구조 및 인터페이스 표준화.
4. **MQTT/CoAP 프로토콜 지원**: 경량 통신을 위한 IETF 표준 프로토콜 채택. |
| **근거(Rationale)** | - **oneM2M**: 글로벌 IoT 상호운용성 표준.
- **OCF/Matter**: 스마트팜 장비와의 호환성 강화.
- **TTA 표준**: 국내 법적 요구사항 준수 및 시장 경쟁력 강화. |
| **결과(Consequences)** | - **장점**: 다중 플랫폼 호환성 및 글로벌 시장 진출 가능.
- **단점**: 프로토콜 변환 오버헤드 발생 가능. |
| **트레이드오프(Trade-offs)** | - **표준 준수 vs. 개발 복잡성**: 다중 프로토콜 지원 vs. 시스템 복잡성 증가. |

## ⚠️ 잠재적 위험 분석

### **1. 데이터 일관성 문제**
- **설명**: 중앙 DB와 모듈별 캐시 간 데이터 불일치 발생 가능. 예: 예측수량 모듈과 생육상태 모듈이 동일한 기상 데이터를 다른 버전으로 처리할 경우.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 소싱 패턴** 도입: 모든 데이터 변경 이벤트를 로그로 기록하고 재생하여 일관성 유지.
  - **DB 트랜잭션 관리**: 분산 트랜잭션을 위한 Saga 패턴 적용.

### **2. 성능 병목점**
- **설명**: 중앙 DB가 예측수량 및 생육상태 모듈로부터의 동시 요청으로 과부하 발생 가능.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **읽기 복제본** 도입: 기상DB 및 품종DB에 읽기 전용 복제본 배포.
  - **캐시 계층** 추가: Redis를 사용하여 빈번히 접근하는 데이터 캐시화.

### **3. 보안 취약점**
- **설명**: IoT 기기 간 통신에서 **MITM 공격** 또는 **데이터 변조** 위험 발생 가능.
- **심각도**: 🔴 High
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **TLS 1.3** 강제 적용 및 주기적 인증서 갱신.
  - **기기 인증**을 위한 **X.509 인증서** 사용(ITU-T X.1352 준수).

### **4. 모듈 간 결합도 증가**
- **설명**: 이벤트 기반 처리로 인해 모듈 간 의존성이 증가하여 유지보수성이 저하될 수 있음.
- **심각도**: 🟡 Medium
- **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **이벤트 스키마 표준화**: Avro 또는 Protobuf를 사용하여 이벤트 구조 표준화.
  - **모니터링 도구** 도입: Prometheus 및 Grafana를 사용하여 모듈 간 의존성 추적.

### **5. 규제 준수 실패**
- **설명**: 국내외 표준(예: TTA, ISO/IEC 30141) 변경에 따라 시스템이 준수하지 못할 경우 법적 위험 발생.
- **심각도**: 🔴 High
- **발생 가능성**: 🟢 Low (단기적으로)
- **대응 방안**:
  - **표준 모니터링 팀** 구성: 표준 변경 사항을 실시간으로 추적.
  - **자동화된 준수 검사 도구** 도입: 시스템 코드에 대한 표준 준수 자동 검사 스크립트 작성.
