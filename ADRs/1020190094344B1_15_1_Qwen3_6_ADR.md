# 🏗️ 아키처 분석 보고서

## 📋 ADR (Architecture Decision Record)

### ADR-001: 중앙 공유 버스 기반의 모듈 간 느슨한 결합(Loose Coupling) 아키텍처 채택

| 항목                     | 내용                                                                                                                                                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 빅데이터 수집(310), 데이터 검증(330), 예측(350), 연동 학습(370), 결과 제공(320), 진행 관리(340), 분석 학습(360), 미러링(380) 등 8개의 이기종 모듈이 유기적으로 데이터를 주고받아야 하는 복잡한 시스템임. 각 모듈의 처리 속도, 데이터 형식, 업데이트 주기가 상이하여 직접적인 점대점(P2P) 연결 시 유지보수 및 확장성이 현저히 저하되는 문제가 발생함.                                      |
| **결정(Decision)**       | 모든 모듈을 단일 중앙 버스(화살표 표시된 중앙 통신선)에 연결하는 **중앙 집중식 데이터 버스(Central Data Bus) 아키텍처**를 채택함. 모듈 간 통신은 직접적인 호출이 아닌, 중앙 버스를 통한 메시지 발행/구독(Pub/Sub) 또는 데이터 공유 방식으로 구현함.                                                                                                       |
| **근거(Rationale)**      | 1. **확장성:** 새로운 분석 모듈이나 학습 모듈이 추가되더라도 기존 모듈의 인터페이스 수정 없이 중앙 버스에만 연결하면 됨.<br>2. **모듈 독립성:** 각 부서(모듈)가 자체적인 생명주기와 기술 스택을 가질 수 있으며, 장애가 다른 모듈로 전파되는 것을 최소화함.<br>3. **데이터 통합:** 빅데이터부(310)에서 수집된 데이터가 검증(330), 학습(360, 370), 예측(350) 등 다양한 경로를 통해 재사용될 수 있는 효율적인 구조임. |
| **결과(Consequences)**   | 시스템의 모듈성이 극대화되어 기능 추가 및 수정이 용이해짐. 다만, 중앙 버스 트래픽이 포화될 경우 전체 시스템의 지연(Latency)이 발생할 수 있으며, 버스 자체의 장애가 전체 시스템 중단으로 이어질 수 있는 단일 장애점(SPOF) 리스크가 존재함.                                                                                                                    |
| **트레이드오프(Trade-offs)** | 모듈 간 결합도 최소화 및 유연성 확보 vs. 중앙 통신 인프라의 병목 현상 가능성 및 단일 장애점 관리의 복잡성 증가.                                                                                                                                                                                               |

---

## ⚠️ 잠재적 위험 분석

### 1. 중앙 버스 트래픽 포화에 의한 시스템 전체 지연

- **설명:** 빅데이터부(310)에서 초당 대량의 데이터 스트림이 유입되거나, 미러링부(380)가 전체 데이터를 실시간으로 복제하려는 시나리오에서 중앙 버스의 대역폭이 포화됨. 이 경우 예측부(350)나 제공부(320)의 실시간 응답이 심각하게 지연됨.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:** 데이터 중요도에 따른 QoS(Quality of Service) 큐잉 정책 적용, 고빈도 데이터는 별도의 고속 채널로 분리, 버스 분할(Sharding) 또는 다중 버스 아키처 도입 검토.
  
  ### 2. 중앙 버스 장애에 의한 전체 시스템 마비 (SPOF)
- **설명:** 모든 모듈이 단일 중앙 라인에 의존하므로, 이 라인을 제어하는 메시지 브로커나 물리적 통신선에 장애가 발생하면 빅데이터 수집부터 결과 제공까지의 모든 프로세스가 즉시 중단됨.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 메시지 브로커 클러스터링 및 고가용성(HA) 구성(예: Active-Active), 물리적 통신 경로 이중화(Redundancy), 로컬 캐싱 기능을 통한 일시적 독립 동작 모드 지원.
  
  ### 3. 학습 모듈 간 모델 버전 불일치 (Model Drift)
- **설명:** 분석학습부(360)와 연동학습부(370)가 각각 독립적으로 모델을 학습하고 업데이트할 경우, 예측부(350)가 참조하는 모델 버전이 혼재되어 일관성 없는 예측 결과를 제공하거나, 학습 데이터의 왜곡이 발생할 수 있음.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:** 중앙 모델 레지스트리(Model Registry) 도입을 통한 버전 관리 강제, 학습 완료 시 검증부(330)를 통한 모델 품질 승인 프로세스 필수화, A/B 테스트 환경 분리.
  
  ### 4. 비동기 처리로 인한 데이터 순서 보장 실패
- **설명:** 중앙 버스를 통한 비동기 통신 환경에서, 빅데이터부(310)에서 전송된 데이터의 순서가 뒤바뀌어 확인부(330)에 도달할 경우, 시계열 데이터 기반의 분석이나 예측 로직이 왜곡될 수 있음.
- **심각도:**  Medium
- **발생 가능성:**  High
- **대응 방안:** 메시지 시퀀싱(Sequencing) 및 오프셋 관리 로직 구현, 데이터 생성 타임스탬프 기반 재정렬(Reordering) 버퍼 도입, 순서가 중요한 트랜잭션에 대한 순차적 처리 보장 옵션 제공.
  
  ### 5. 미러링부 지연으로 인한 재해 복구(RDR) 데이터 손실
- **설명:** 미러링부(380)가 중앙 버스의 트래픽을 실시간으로 복제하지 못하고 지연(Lag)이 발생할 경우, 시스템 장애 발생 시 최신 데이터(특히 진행관리부(340)의 상태 정보)가 유실되어 복구 시점(Recovery Point Objective) 목표 미달성.
- **심각도:**  Medium
- **발생 가능성:**  Medium
- **대응 방안:** 미러링 전용 고속 채널 할당, 비동기 복제에서 동기 복제(Synchronous Replication)로 전환 옵션 제공(성능 저하 감수), 정기적인 무결성 체크섬(Checksum) 검증 수행.
