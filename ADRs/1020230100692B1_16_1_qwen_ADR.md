## 📋 ADR (Architecture Decision Record)

### ADR-001: [모듈화된 기능 단위와 중앙 허브 간의 양방향 통합 아키텍처 도입]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **스마트팜 및 IoT 생태계 내 복잡한 기능 통합:**<br>주어진 이미지와 텍스트를 분석한 결과, 이 시스템은 센서 데이터 수집(모니터링부 310), 모델링(모델링부 350), 제어(제어부 320), 및 네트워크 구축(망구축부 340) 등 다양한 기능을 수행해야 합니다. 텍스트에서 언급된 TTA(한국정보통신기술협회) 표준과 ISO/IEC 30141 등 국제 표준은 각 기능의 독립적 정의와 상호 운용성을 요구합니다. 시스템이 단일 하드웨어 환경에서 다수의 센서, 액추에이터, 네트워크, 보안 모듈을 통합해야 하며, 데이터의 실시간 처리와 제어 명령 전달이 필수적입니다. |
| **결정(Decision)** | **양방향 중추 아키텍처 (Bidirectional Hub Architecture) 도입:**<br>시스템의 모든 기능 단위 (모니터링부, 완료부, 모델링부, 연결부, 커스텀부 등) 를 좌측 열에 배치하고, 제어 및 플랫폼 관련 기능 (제어부, 망구축부, 플랫폼부, 복수필지원부 등) 을 우측 열로 구분하되, 중앙에 있는 큰 양방향 화살표를 통해 전체 시스템을 하나의 통합된 로직으로 연동합니다. 즉, 중앙 허브를 통해 각 단위 간의 실시간 데이터 동기화와 명령 전달을 수행합니다. |
| **근거(Rationale)** | **유연성과 확장성 확보:**<br>이미지의 좌측 열 (310~390) 을 통해 '커스텀부 (390)', '모델링부 (350)' 등 유연한 기능 모듈이 추가될 수 있습니다. 우측 열 (320~380) 을 통해 보안 (380), 플랫폼 (360) 등 핵심 인프라를 집중 관리합니다. 이는 TTA 표준 목록 (별표 26) 에서나 '스마트 온실 서비스 데이터 관리', '가상 센서' 등을 언급할 때 요구되는 재사용 가능한 설계 (ISO/IEC 30141:2024 기준) 에 부합합니다. 또한, 양방향 통신은 모니터링 데이터를 즉시 제어 로직에 반영하여 스마트팜의 자동화 수준을 높입니다. |
| **결과(Consequences)** | **긍정적:** 시스템의 모듈화가 가능해져 표준별 (예: TTA 표준 vs ISO 표준) 요구사항을 독립 모듈로 지원할 수 있습니다.<br>**부정적/도전 과제:** 중앙 연결부 (370 연결부) 와 우측 열의 모든 노드 (320~380) 가 단일 통신 버스 (화살표) 를 통해 연결되므로, 이 채널의 부하가 심해지면 전체 시스템의 응답 속도가 저하될 수 있습니다. |
| **트레이드오프(Trade-offs)** | **장점:** 각 모듈 (예: 모니터링부 310) 을 독립적으로 개발하고 표준화할 수 있음.<br>**단점:** 중앙 통신 프로토콜 (예: MQTT, CoAP 등 텍스트 기반 문서 언급) 의 복잡성이 증가하고, 중앙 처리 로직 (플랫폼부 360) 의 성능이 병목 지점이 될 수 있음. |

### ADR-002: [IoT 보안 표준에 기반한 별도의 보안 및 대응 지원 모듈 격리]

| 항목 | 내용 |
|------|------|
| **상황(Context)** | **IoT 환경의 민감한 보안 요구사항:**<br>시스템은 ITU-T X.1352 (IoT 기기 보안), ETSI EN 303 645 (사이버보안) 등 국제 보안 표준을 준수해야 합니다. 텍스트에서는 특히 '가축 질병 조기 감지', '환경 데이터 모니터링' 등 데이터의 정확성과 기밀성이 생명 농업을 위한 핵심 자산임을 강조합니다. 따라서 네트워크 구축부 (340) 나 제어부 (320) 가 직결되는 보안 위협으로부터 시스템을 보호해야 합니다. |
| **결정(Decision)** | **보안 전용 모듈 격리 (Isolation):**<br>우측 열 하단에 위치한 '복수필지원부 (380)'를 최상위 보안 경계로 기능하도록 설계합니다. 모든 외부 데이터 (좌측 열 입력) 가 우측 열의 제어 시스템 (320) 으로 들어가기 전, 이 '복수필지원부 (380)'를 통과하여 위협 여부, 인증, 암호화 상태를 검증하도록 합니다. |
| **근거(Rationale)** | **공격 표면 축소를 통한 신뢰성 확보:**<br>보안 표준 (ITU-T X.1352) 에 따르면 '보안 요구사항'은 시스템의 핵심 로직 (제어부 320) 과 분리되어야 합니다. 이미지의 화살표 흐름에 따라 380 번 노드가 360(플랫폼) 과 340(망구축) 과 직접 연결되어 있으므로, 이를 통해 모든 통신을 암호화 및 인증된 경로를 사용하여 필터링할 수 있습니다. |
| **결과(Consequences)** | **긍정적:** 외부 해커의 네트워크 침입 시, 가장 하위의 보안 모듈 (380) 에서 차단되어 제어 시스템 (320) 이 감염되지 않습니다.<br>**부정적:** 보안 모듈 (380) 의 오동작 (예: 합법적인 트래픽 과도 차단) 이 시스템 가용성에 영향을 줄 수 있습니다. |
| **트레이드오프(Trade-offs)** | **장점:** 시스템의 취약점을 최소화하고, TTA 및 국제 보안 인증 획득 시 유리한 구조.<br>**단점:** 보안 모듈의 처리 속도가 느려져 전체 데이터 전달 속도가 제한될 수 있음. |

## ⚠️ 잠재적 위험 분석

### 1. [중앙 통신 채널의 병목 및 지연 위험]
- **설명:** 이미지의 중앙에 있는 대형 양방향 화살표는 시스템 내 모든 데이터 흐름의 주 통로입니다. 모니터링부 (310), 모델링부 (350), 커스텀부 (390) 등 수많은 좌측 단위에서 우측 제어/플랫폼 단위 (320~380) 로 데이터를 보내고, 제어 명령을 받습니다. 데이터량이 방대하거나 실시간 제어가 필요한 경우 (예: 가축 급식 제어), 이 채널의 대역폭이 부족하거나 처리 지연이 발생할 수 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🔴 High
- **대응 방안:**
    - **QoS (Quality of Service) 정책 적용:** 제어 명령 (Critical Data) 과 모니터링 데이터 (Non-Critical Data) 를 QoS 등급으로 분류하여 우선순위를 설정합니다.
    - **에지 컴퓨팅 (Edge Computing) 도입:** 이미지 중앙의 대역폭을 줄이기 위해, 일부 필터링과 초기 처리 (모델링부 350 관련 로직) 를 엣지 노드에서 수행하도록 분산 아키텍처를 고려합니다.

### 2. [보안 모듈 (복수필지원부) 의 단일 장애점 (Single Point of Failure) 위험]
- **설명:** 우측 열의 모든 데이터 흐름이 '복수필지원부 (380)'를 통과합니다. 이 모듈이 고장나거나 소프트웨어 버그로 인해 기능을 상실할 경우, 시스템의 보안 장벽이 사라지거나 정상 데이터 흐름이 차단되어 전체 시스템이 마비될 수 있습니다. 텍스트에서 언급된 '복수필지원부'는 아마도 Countermeasure Support Unit 로, 보안 정책 실행부이므로 이 부분이 고장 나면 시스템은 무방비 상태가 됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium (단일 모듈이지만 모든 트래픽을 관리하므로 중요도 높음)
- **대응 방안:**
    - **Redundancy (중복화) 구조 설계:** 복수필지원부 (380) 기능에 대한 백업 모듈 (Active-Standby) 을 도입하여 한쪽이 장애가 발생해도 트래픽이 정상 처리되도록 합니다.
    - **분산 보안 정책:** 380 이 아닌 다른 모듈 (예: 각 노드 자체의 보안 모듈) 에서도 기본 인증을 수행하여 부하를 분산하고, 380 은 심층 분석에만 집중하도록 합니다.

### 3. [표준화 및 커스터마이징 간의 균형 붕괴 위험]
- **설명:** 시스템은 TTA(한국정보통신기술협회) 및 ISO/IEC 표준을 준수하려는 목적이 강해 보이나, 좌측 열 하단의 '커스텀부 (390)'가 존재합니다. 이 커스텀부가 표준 프로토콜 (oneM2M, MQTT 등) 과 호환되지 않는 비표준 데이터를 생성하면, 우측의 '플랫폼부 (360)'나 '연결부 (370)'가 정상적으로 처리할 수 없게 됩니다. 이는 텍스트에서 강조한 '상호 운용성' 문제를 야기합니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **API 게이트웨이 필터링:** 커스텀부 (390) 에서 생성된 데이터를 플랫폼부 (360) 로 전달할 때, 표준 준수 여부를 API 게이트웨이에서 검증 (Validate) 후 재포맷합니다.
    - **타입 시스템 (Type System) 사용:** 메시지 프로토콜 (JSON 등) 에 엄격한 스키마를 정의하여 데이터 구조가 표준에 맞는지 강제합니다.

### 4. [모델링부 (350) 와 실제 센서 데이터의 불일치 위험]
- **설명:** 시스템에는 '모델링부 (350)'가 있고 '완료부 (330)', '모니터링부 (310)'가 있습니다. 스마트팜이나 디지털 트윈 시스템에서 모델링부 (가상 데이터) 는 실제 센서 데이터 (모니터링부 310) 와 동기화되어야 합니다. 텍스트의 '디지털 트윈 기반 스마트 축사' 문맥을 고려할 때, 모델링부의 데이터가 업데이트되지 않아 제어부 (320) 가 잘못된 판단 (예: 온도 데이터가 모델링 데이터 기준이 아니라 실제 온도가 낮음으로 판단) 을 할 수 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟡 Medium
- **대응 방안:**
    - **실시간 시계 동기화 (Clock Sync):** 모델링부와 모니터링부 간 시간 동기화를 유지하여 데이터 갱신 주기를 일치시킵니다.
    - **오차 보정 알고리즘:** 실제 센서 데이터와 모델링 데이터의 차이를 모니터링하여, 편차가 일정 수준 이상이면 '연결부 (370)'를 통해 경고하거나 모델을 재학습하도록 트리거합니다.

### 5. [네트워크 구축부 (340) 와 환경 변화에 대한 취약성]
- **설명:** 우측 열의 '망구축부 (340)'는 네트워크를 구축하는 역할을 합니다. 그러나 IoT 환경 (특히 스마트팜) 은 온도, 습도, 물리적 장애물에 의해 네트워크 상태가 쉽게 변화합니다. 망구축부가 이러한 환경 변화를 실시간으로 감지하지 못해 네트워크 연결이 끊어지거나 불안정해질 수 있습니다. 특히 TTA 표준 목록 중 '노지 관수·관비제어기' 등 야외 환경용 장비와 연동될 경우 이 위험이 커집니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🟢 Low (Network Resilience 이 잘 작동한다면) / 🟡 Medium (IoT 특성상)
- **대응 방안:**
    - **멀티 경로 네트워킹:** 망구축부 (340) 가 단일 Wi-Fi/Zigbee 를 사용하는 것이 아닌, 이더넷/무선/LoRaWAN 등 여러 경로를 사용하여 네트워크 연결을 유지합니다.
    - **Self-healing 네트워크:** 연결부 (370) 와 연동하여 네트워크 연결이 끊어지면 자동으로 대체 경로를 찾아 연결을 복구하는 로직을 구현합니다.
