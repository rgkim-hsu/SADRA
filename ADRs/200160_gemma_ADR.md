## 📋 ADR (Architecture Decision Record)

### ADR-001: 계층적 모듈화 및 표준화 기반의 서비스 지향 아키텍처 채택

| 항목 | 내용 |
|------|------|
| **상황(Context)** | 본 시스템은 기후 데이터, 품종 특성, 사용자 입력 등 **성격이 이질적이고(Heterogeneous)**, 변화가 잦은 외부 요인들(기상, 환경)을 통합하여 복잡한 생물학적 모델링(작물모형)을 거쳐 예측을 수행해야 합니다. 이 과정에서 데이터 소스의 이질성, 모델의 복잡성, 그리고 미래의 확장성(예: 새로운 센서, 새로운 작물 도입) 확보가 핵심 아키텍처적 과제입니다. |
| **결정(Decision)** | 데이터 수집, 모델링, 예측 서비스를 독립적인 모듈(Service)로 분리하고, 모든 인터페이스는 ISO/IEC 30141 등의 국제 표준 아키텍처 참조 모델을 따르는 **서비스 지향 아키텍처(SOA) 또는 마이크로서비스 아키텍처(MSA)**로 설계합니다. |
| **근거(Rationale)** | 1. **이질적 데이터 통합:** `<<input interface>>`를 경계로 설정하고, 데이터 표준화 계층(Data Standardization Layer)을 도입하여 기상, DB 등 모든 데이터를 공통 모델(Common Model)로 변환함으로써, 데이터 출처에 관계없이 작물모형이 처리할 수 있도록 보장합니다. 2. **확장성 및 재사용성:** `작물모형`과 `생육상태`를 독립 서비스로 분리하면, 특정 작물/환경 변화 시 모델만 업데이트하거나 교체할 수 있어 유지보수 비용과 시간을 획기적으로 절감합니다. 3. **상호운용성 확보:** 국제 표준(e.g., oneM2M, ISO/IEC 30141)에 따른 명세화된 API를 사용함으로써, 추후 다른 농업 관련 시스템과의 연동이 용이합니다. |
| **결과(Consequences)** | **긍정적:** 높은 유연성, 확장성, 강한 결합도(Loose Coupling)를 갖춘 시스템 구현. 예측 결과를 시각화하고 다양한 대시보드에 재사용하기 용이해집니다. **부정적:** 시스템 초기 설계 복잡도가 매우 높아지고, 서비스 간의 데이터 일관성(Transaction Consistency) 관리가 어려워집니다. |
| **트레이드오프(Trade-offs)** | **획득 장점 (Interoperability & Scalability):** 표준화된 모듈과 API를 통해 시스템 전체의 유연성을 극대화하여 시장 변화에 빠르게 대응할 수 있습니다. **감수 단점 (Complexity & Latency):** 모듈 간의 통신(Service Mesh) 오버헤드와 초기 개발 복잡도 증가로 인해, 단일 단일화 시스템 대비 초기 구축 비용 및 운영 복잡도가 증가할 수 있습니다. |

## ⚠️ 잠재적 위험 분석

### 1. 기상/환경 데이터 신뢰성 의존 위험 (Data Reliability Risk)
- **설명:** 예측의 핵심 입력인 `기상DB` 및 환경 데이터(토양, 기온 등)가 데이터 공백, 부정확한 측정, 또는 예측 오류를 포함할 경우, 시스템의 모든 출력(`예측수량`, `생육상태`)이 신뢰도를 상실하게 됩니다. 농업 분야의 특성상 데이터 오류가 곧바로 경제적 손실로 이어집니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **다중 출처 교차 검증(Cross-Validation):** 기상 데이터 외에 위성 데이터, 지상 관측소 데이터, 과거 통계 등을 조합하여 데이터 불일치 시 경고(Confidence Score)를 발행하고, 모델 계산 시 가중 평균(Weighted Average) 방식을 적용하여 신뢰도를 보정합니다.

### 2. 작물 모형의 블랙박스 및 해석 가능성 위험 (Model Interpretability Risk)
- **설명:** `작물모형`이 매우 복잡한 머신러닝(ML) 또는 심층 신경망(Deep Learning)을 기반으로 할 경우, 예측 결과(예: 수량 급감)가 나온 근본적인 원인(어떤 변수가 문제인지)을 사용자가 이해하기 어렵습니다. 이로 인해 사용자가 모델 결과를 신뢰하지 않거나, 오류 발생 시 대응이 불가능해집니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **설명 가능한 AI(XAI, Explainable AI) 도입:** LIME(Local Interpretable Model-agnostic Explanations)이나 SHAP(SHapley Additive exPlanations) 등 모델 해석 기법을 적용하여, 예측 결과와 함께 "이 예측이 낮은 이유는 '지난주 급격한 기온 변화'와 '사용자 입력의 품종 특성' 때문입니다"와 같은 해석 보고서를 함께 제공해야 합니다.

### 3. 인터페이스 비표준화 및 상호운용성 위험 (Interoperability Risk)
- **설명:** 시스템이 여러 외부 디바이스(IoT 센서), 다양한 현장 수집 시스템, 그리고 여러 DB를 통합합니다. 이들 컴포넌트 간의 물리적/논리적 인터페이스가 표준(e.g., MQTT, OPC UA, ISO/IEC 30141)을 따르지 못할 경우, 데이터 전송 과정에서 오류가 발생하거나, 특정 제조사나 환경에 종속(Vendor Lock-in)되는 위험이 있습니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **API Gateway 구축 및 표준화 계층 강제:** 모든 외부 데이터 수집 경로는 API 게이트웨이를 통과하도록 강제하고, 데이터를 수집하는 즉시 메시지 브로커(Message Broker, 예: Kafka)를 통해 표준화된 토픽(Topic)으로 발행하는 파이프라인을 구축하여 데이터 포맷을 일관되게 유지해야 합니다.

### 4. 사이버보안 및 데이터 무결성 위험 (Security & Integrity Risk)
- **설명:** 시스템은 외부 인터넷(기상 정보)과 현장 IoT 센서(사용자 입력, DB)를 연결하며 민감한 농업 생산 정보(수량, 품종, 최적 환경)를 처리합니다. 만약 외부 공격이나 내부 시스템 오류로 인해 데이터 무결성이 훼손되거나 시스템이 마비되면, 예측 및 제어 기능이 완전히 상실됩니다.
- **심각도:** 🔴 High
- **발생 가능성:** 🟡 Medium
- **대응 방안:** **제로 트러스트 아키텍처(Zero Trust Architecture) 구현:** 모든 컴포넌트와 사용자 요청을 신뢰하지 않고, 접근할 때마다 강력한 인증 및 권한 검사(Authentication & Authorization)를 수행해야 합니다. 특히, 물리적 제어와 관련된 출력을 통제하는 모듈에 대해서는 WAF(Web Application Firewall)와 IDS(Intrusion Detection System)를 필수적으로 적용합니다.

### 5. 대규모 시뮬레이션 및 계산 부하 위험 (Computational Load Risk)
- **설명:** `생육상태` 및 `예측수량`을 계산하는 과정은 작물의 성장 단계별로 다양한 변수를 반복적으로 시뮬레이션해야 합니다. 시스템 사용자가 대규모 데이터셋(수십 개 작물, 수년치 기상 데이터)으로 한 번에 예측을 요청할 경우, 서버에 과부하가 걸려 응답 시간이 극도로 느려지거나(Latency), 서비스가 중단될 위험이 있습니다.
- **심각도:** 🟡 Medium
- **발생 가능성:** 🔴 High
