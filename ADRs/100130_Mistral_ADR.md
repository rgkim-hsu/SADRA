### ADR-001: **데이터베이스 중심 아키텍처 채택**

| 항목                     | 내용                                                                                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 스마트팜 시스템에서 환경 정보(온습도 등)를 실시간으로 수집, 저장, 분석하여 최적의 재배 조건을 제공해야 함. 시스템은 **환경 정보 입력부**, **환경 정보 데이터베이스부**, **제어부**, **저장부**로 구성되어 있으며, **디폴트 모델**과 **학습 모델**을 통해 온습도 지수와 영향도를 계산함. |
| **결정(Decision)**       | 모든 환경 데이터와 계산 결과를 **중앙 집중식 데이터베이스**에 저장하고, 디폴트 모델(일별 온습도 지수 계산, 온습도 영향도 DB)과 학습 모델(일별 추가 영향 지수 계산, 추가 영향도 DB)을 분리하여 운영.                                                       |
| **근거(Rationale)**      | 1. **데이터 일관성**: 중앙 DB를 통해 모든 컴포넌트가 동일한 데이터를 공유하여 일관성 유지. 2. **모듈성**: 디폴트 모델과 학습 모델을 분리하여 각 모델의 독립적인 업데이트와 테스트 가능. 3. **확장성**: 새로운 환경 센서 또는 영향도 계산 로직을 추가하기 용이.                |
| **결과(Consequences)**   | **장점**: 데이터 관리 간소화, 모델별로 성능 최적화 가능, 시스템 유지보수 용이. **단점**: 중앙 DB에 의존하여 단일 장애점이 발생할 수 있으며, 대용량 데이터 처리 시 성능 병목 현상이 발생할 수 있음.                                                      |
| **트레이드오프(Trade-offs)** | **장점**: 데이터 통합 관리, 모듈별 독립성, 확장성. **단점**: 중앙 DB의 성능과 가용성이 시스템 전체에 영향을 미침.                                                                                                      |

### ADR-002: **이중 모델(디폴트 + 학습) 구조 도입**

| 항목                     | 내용                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **상황(Context)**        | 스마트팜에서는 실시간 환경 데이터를 기반으로 재배 조건을 최적화해야 하며, 초기 단계에서는 디폴트 규칙 기반 모델로 운영하고, 장기적으로는 기계학습 모델로 전환해야 함.                           |
| **결정(Decision)**       | **디폴트 모델**(일별 온습도 지수 계산, 온습도 영향도 DB)과 **학습 모델**(일별 추가 영향 지수 계산, 추가 영향도 DB)을 병렬로 운영하고, 제어부에서 두 모델의 결과를 종합하여 최종 제어 신호를 생성. |
| **근거(Rationale)**      | 1. **안정성**: 디폴트 모델은 규칙 기반으로 안정적인 결과를 제공. 2. **정확성 향상**: 학습 모델은 데이터 축적에 따라 정확도가 향상됨. 3. **유연성**: 두 모델을 병행하여 점진적 전환 가능.    |
| **결과(Consequences)**   | **장점**: 초기 안정적 운영 가능, 장기적으로는 학습 모델을 통해 정확도 향상. **단점**: 시스템 복잡성 증가, 두 모델의 결과 통합 로직이 필요.                                   |
| **트레이드오프(Trade-offs)** | **장점**: 안정성 + 정확성 동시 달성. **단점**: 아키텍처 복잡성, 추가 리소스 필요.                                                                    |

### ADR-003: **계층적 데이터 처리 파이프라인 구축**

| 항목                     | 내용                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **상황(Context)**        | 환경 정보는 실시간으로 입력되며, 저장부와 제어부에서 동시에 접근해야 함. 데이터의 흐름(입력 → DB 저장 → 계산 → 제어)을 효율적으로 관리해야 함.                                                |
| **결정(Decision)**       | **환경 정보 입력부** → **환경 정보 데이터베이스부** → **제어부** → **저장부**로 데이터가 순차적으로 흐르도록 설계. 디폴트/학습 모델은 제어부에서 호출되어 계산 결과를 반환.                           |
| **근거(Rationale)**      | 1. **데이터 흐름 명확화**: 각 컴포넌트의 역할과 책임 분리. 2. **오류 추적 용이**: 데이터가 각 단계에서 어떻게 처리되는지 로그로 추적 가능. 3. **성능 최적화**: 병목 현상을 최소화하기 위해 데이터 처리 단계를 분리. |
| **결과(Consequences)**   | **장점**: 시스템의 투명성 및 유지보수성 향상. **단점**: 데이터 처리 지연 가능성, 컴포넌트 간 의존성 증가.                                                                    |
| **트레이드오프(Trade-offs)** | **장점**: 명확한 역할 분리, 오류 추적 용이. **단점**: 지연 시간 증가 가능성, 컴포넌트 간 결합도 관리 필요.                                                                  |

⚠️ 잠재적 위험 분석
------------

### 1. **중앙 데이터베이스 단일 장애점(SPOF)**

* **설명:** 중앙 데이터베이스에 장애가 발생하면 전체 시스템이 마비될 수 있음. 환경 정보와 계산 결과가 실시간으로 필요하기 때문에, DB 장애 시 제어부에서 올바른 결정을 내릴 수 없음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **이중화**: 주 DB와 백업 DB를 구축하여 장애 시 자동 Failover.
  * **캐싱**: 자주 접근하는 데이터는 In-Memory DB(예: Redis)에 캐시하여 DB 부하 감소.
  * **로컬 백업**: 제어부에서 일정 시간 동안 로컬로 데이터를 저장하여 임시 운영 가능하도록 설계.

* * *

### 2. **학습 모델의 정확도 저하**

* **설명:** 학습 모델은 초기 데이터가 부족하거나, 환경 변화(예: 계절 변화, 새로운 작물)에 적응하지 못하면 오류가 발생할 수 있음. 디폴트 모델에 비해 예측 정확도가 떨어질 경우, 시스템 전체의 신뢰성이 하락.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **지속적 학습**: 새로운 데이터를 주기적으로 학습 모델에 반영(Online Learning).
  * **모델 모니터링**: 학습 모델의 출력과 디폴트 모델의 출력을 비교하여 이상 징후를 감지하는 시스템 도입.
  * **A/B 테스트**: 디폴트 모델과 학습 모델의 결과를 병행 운영하여 성능을 비교하고, 학습 모델이 우수할 때만 전환.

* * *

### 3. **실시간 데이터 처리 지연**

* **설명:** 환경 정보가 대량으로 유입될 경우, 데이터베이스 쓰기/읽기 지연 또는 모델 계산 지연으로 인해 제어부에서 실시간 제어가 어려워질 수 있음. 스마트팜에서는 실시간성이 매우 중요함.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **스트리밍 처리**: Apache Kafka 또는 AWS Kinesis와 같은 스트리밍 플랫폼을 도입하여 데이터 실시간 처리.
  * **에지 컴퓨팅**: 센서 근접에서 부분 계산 수행(예: 온습도 기본 계산)하여 중앙 시스템의 부하 감소.
  * **우선순위 큐**: 실시간성이 중요한 데이터(예: 급격한 온도 변화)는 우선 처리.

* * *

### 4. **보안 취약점(데이터 변조 및 무단 접근)**

* **설명:** 중앙 데이터베이스에 저장된 환경 정보나 모델 계산 결과가 해킹 또는 내부자에 의해 변조될 경우, 잘못된 제어 신호가 발생하여 작물 손실로 이어질 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **암호화**: 데이터 저장 시 암호화(예: AES-256) 적용.
  * **접근 제어**: 역할 기반 접근 제어(RBAC) 및 다단계 인증을 통해 무단 접근 방지.
  * **감사 로그**: 모든 데이터 접근 및 수정을 로그로 기록하여 추적 가능하도록 함.

* * *

### 5. **시스템 확장성 한계**

* **설명:** 스마트팜 시스템이 대규모로 확장될 경우(예: 다수 농장 관리), 현재 아키텍처는 데이터베이스와 제어부에서 성능 병목이 발생할 수 있음. 특히, 학습 모델의 경우 계산 리소스가 많이 필요함.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **마이크로서비스 아키텍처**: 각 컴포넌트를 컨테이너화(예: Docker)하여 독립적으로 확장 가능하도록 함.
  * **클라우드 기반 인프라**: AWS 또는 Azure와 같은 클라우드 서비스에서 자동 스케일링을 활용.
  * **분산 데이터베이스**: NoSQL(예: MongoDB) 또는 분산 SQL(예: CockroachDB)을 도입하여 수평 확장 가능.

### 1. **중앙 데이터베이스 단일 장애점(SPOF)**

* **설명:** 중앙 데이터베이스에 장애가 발생하면 전체 시스템이 마비될 수 있음. 환경 정보와 계산 결과가 실시간으로 필요하기 때문에, DB 장애 시 제어부에서 올바른 결정을 내릴 수 없음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **이중화**: 주 DB와 백업 DB를 구축하여 장애 시 자동 Failover.
  * **캐싱**: 자주 접근하는 데이터는 In-Memory DB(예: Redis)에 캐시하여 DB 부하 감소.
  * **로컬 백업**: 제어부에서 일정 시간 동안 로컬로 데이터를 저장하여 임시 운영 가능하도록 설계.

* * *

### 2. **학습 모델의 정확도 저하**

* **설명:** 학습 모델은 초기 데이터가 부족하거나, 환경 변화(예: 계절 변화, 새로운 작물)에 적응하지 못하면 오류가 발생할 수 있음. 디폴트 모델에 비해 예측 정확도가 떨어질 경우, 시스템 전체의 신뢰성이 하락.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **지속적 학습**: 새로운 데이터를 주기적으로 학습 모델에 반영(Online Learning).
  * **모델 모니터링**: 학습 모델의 출력과 디폴트 모델의 출력을 비교하여 이상 징후를 감지하는 시스템 도입.
  * **A/B 테스트**: 디폴트 모델과 학습 모델의 결과를 병행 운영하여 성능을 비교하고, 학습 모델이 우수할 때만 전환.

* * *

### 3. **실시간 데이터 처리 지연**

* **설명:** 환경 정보가 대량으로 유입될 경우, 데이터베이스 쓰기/읽기 지연 또는 모델 계산 지연으로 인해 제어부에서 실시간 제어가 어려워질 수 있음. 스마트팜에서는 실시간성이 매우 중요함.
* **심각도:** 🔴 High
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **스트리밍 처리**: Apache Kafka 또는 AWS Kinesis와 같은 스트리밍 플랫폼을 도입하여 데이터 실시간 처리.
  * **에지 컴퓨팅**: 센서 근접에서 부분 계산 수행(예: 온습도 기본 계산)하여 중앙 시스템의 부하 감소.
  * **우선순위 큐**: 실시간성이 중요한 데이터(예: 급격한 온도 변화)는 우선 처리.

* * *

### 4. **보안 취약점(데이터 변조 및 무단 접근)**

* **설명:** 중앙 데이터베이스에 저장된 환경 정보나 모델 계산 결과가 해킹 또는 내부자에 의해 변조될 경우, 잘못된 제어 신호가 발생하여 작물 손실로 이어질 수 있음.
* **심각도:** 🔴 High
* **발생 가능성:** 🟢 Low
* **대응 방안:**
  * **암호화**: 데이터 저장 시 암호화(예: AES-256) 적용.
  * **접근 제어**: 역할 기반 접근 제어(RBAC) 및 다단계 인증을 통해 무단 접근 방지.
  * **감사 로그**: 모든 데이터 접근 및 수정을 로그로 기록하여 추적 가능하도록 함.

### 5. **시스템 확장성 한계**

* **설명:** 스마트팜 시스템이 대규모로 확장될 경우(예: 다수 농장 관리), 현재 아키텍처는 데이터베이스와 제어부에서 성능 병목이 발생할 수 있음. 특히, 학습 모델의 경우 계산 리소스가 많이 필요함.
* **심각도:** 🟡 Medium
* **발생 가능성:** 🟡 Medium
* **대응 방안:**
  * **마이크로서비스 아키텍처**: 각 컴포넌트를 컨테이너화(예: Docker)하여 독립적으로 확장 가능하도록 함.
  * **클라우드 기반 인프라**: AWS 또는 Azure와 같은 클라우드 서비스에서 자동 스케일링을 활용.
  * **분산 데이터베이스**: NoSQL(예: MongoDB) 또는 분산 SQL(예: CockroachDB)을 도입하여 수평 확장 가능.
