## 📋 **ADR (Architecture Decision Record)**

### **ADR-001: 중앙제어 시스템 기반 모듈화 제어 아키텍처 채택**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 **환풍기, 스프링클러, 조명, 관수밸브, 난방** 등 **5개 이상 독립적 제어 모듈**을 통합 관리해야 하며, **실시간 모니터링 및 원격 제어**가 필수적이다. 기존 중앙집중식 제어 시스템은 확장성 및 유지보수성에서 한계가 존재하며, **IoT 표준 준수**와 **보안 요구사항**을 충족해야 한다. |
| **결정(Decision)** | 1. **모듈화 제어 아키텍처** 채택: 각 제어기(환풍기, 스프링클러 등)는 **독립적 에지 디바이스**로 구현하며, **스마트팜 시스템 컨트롤러**를 통해 중앙 집중식으로 관리한다.<br>2. **oneM2M/ISO/IEC 30141:2024 표준** 준수: 통신 프로토콜은 **MQTT/CoAP**를 기본으로 하며, API는 **RESTful**로 설계한다.<br>3. **보안 레이어 추가**: 각 제어기는 **TLS 1.3** 암호화와 **ITU-T X.1352** 기반 인증 메커니즘을 적용한다. |
| **근거(Rationale)** | - **모듈화**: TTA의 *"스마트팜 데이터 상호운용 프레임워크"* 표준과 일치하며, **확장성**과 **장애 격리**를 보장한다.<br>- **oneM2M 표준**: 글로벌 상호운용성을 위해 필수적이며, **ETSI EN 303 645** 보안 요구사항을 충족한다.<br>- **MQTT/CoAP**: IoT 환경의 **저용량 통신**과 **실시간 제어**에 최적화되어 있다. |
| **결과(Consequences)** | ✅ **장점**:<br>• **유연성**: 새로운 제어기 추가 시 시스템 변경 최소화.<br>• **보안**: 중앙 컨트롤러와 에지 디바이스 간 **엔드투엔드 암호화** 적용 가능.<br>• **표준 준수**: 국제 표준과 국내 TTA 표준 호환성 확보.<br>❌ **단점**:<br>• **초기 구축 비용**: 모듈별 보안 및 통신 인프라 구축 필요.<br>• **복잡성**: 다중 프로토콜 관리(MQTT, CoAP, REST) 요구. |
| **트레이드오프(Trade-offs)** | - **모듈화 vs. 중앙집중식**: 모듈화는 확장성 ↑, 단일 장애점 ↑(중앙 컨트롤러 장애 시 전체 영향)<br>- **MQTT vs. HTTP**: MQTT는 실시간성 ↑, HTTP는 디버깅 용이성 ↑<br>- **보안 강화 vs. 성능 오버헤드**: TLS 1.3 적용으로 **~10% latency 증가** 가능. |

### **ADR-002: 에지 디바이스 기반 로컬 처리 및 클라우드 동기화**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 **실시간 제어**와 **오프라인 운영**을 지원해야 하며, 네트워크 장애 시에도 **최소한의 기능**을 유지해야 한다. 클라우드 의존도는 최소화하여 **지연 시간**과 **가용성**을 최적화해야 한다. |
| **결정(Decision)** | 1. **에지 디바이스에 로컬 처리 로직** 구현: 센서 데이터는 **로컬에서 전처리** 후 중앙 컨트롤러로 전송.<br>2. **클라우드 동기화**: 비즈니스 로그 및 이벤트만 클라우드로 전송하며, **오프라인 모드** 지원.<br>3. **데이터 버전 관리**: 중앙 컨트롤러와 에지 디바이스 간 **Conflict-Free Replicated Data Types (CRDT)** 사용. |
| **근거(Rationale)** | - **로컬 처리**: TTA의 *"에지 기반 스마트 온실 서비스의 데이터 관리"* 표준과 일치.<br>- **CRDT**: 네트워크 분할 시 **데이터 일관성** 유지 가능.<br>- **오프라인 지원**: 농업 현장 환경의 **불안정 네트워크**에 대응. |
| **결과(Consequences)** | ✅ **장점**:<br>• **저지연 제어**: 로컬 처리로 **<50ms** 응답 시간 보장.<br>• **고가용성**: 네트워크 장애 시 **로컬 제어 유지**.<br>❌ **단점**:<br>• **에지 디바이스 복잡성**: 로컬 처리 로직 구현으로 **메모리/CPU 사용량 ↑**.<br>• **동기화 오버헤드**: CRDT 적용으로 **~15% 대역폭 증가**. |
| **트레이드오프(Trade-offs)** | - **로컬 처리 vs. 클라우드 처리**: 로컬 처리로 **지연 시간 ↓**, 클라우드 처리로 **스케일러블 저장소 ↑**.<br>- **CRDT vs. 전통적 동기화**: CRDT는 **일관성 ↑**, 전통적 동기화는 **구현 간소화**. |

### **ADR-003: 보안 아키텍처 - 제로 트러스트 모델 적용**
| 항목 | 내용 |
|------|------|
| **상황(Context)** | 스마트팜 시스템은 **사이버 공격**에 취약하며, **기밀성**, **무결성**, **가용성**을 보장해야 한다. 기존의 **방화벽 중심 보안**은 IoT 환경의 **다중 디바이스**에 적합하지 않다. |
| **결정(Decision)** | 1. **제로 트러스트 아키텍처** 적용: 모든 디바이스와 통신은 **인증/인가**를 필수적으로 요구.<br>2. **디바이스 인증**: **ITU-T X.1352** 기반 **공개키 인증서** 사용.<br>3. **통신 암호화**: **TLS 1.3** + **AES-256-GCM** 적용.<br>4. **로그 모니터링**: 중앙 컨트롤러에 **SIEM 통합** (예: ELK 스택). |
| **근거(Rationale)** | - **제로 트러스트**: ETSI EN 303 645와 **ISO/IEC 27030:2020** 가이드라인 준수.<br>- **공개키 인증서**: 디바이스 간 **신뢰성** 확보.<br>- **SIEM**: **이상행동 감지**를 위한 필수 요소. |
| **결과(Consequences)** | ✅ **장점**:<br>• **고급 보안**: **MITM 공격**, **데이터 변조** 방지.<br>• **규제 준수**: **GDPR**, **K-ISMS** 요구사항 충족.<br>❌ **단점**:<br>• **구현 복잡성**: 인증서 관리 및 SIEM 설정 필요.<br>• **성능 오버헤드**: TLS 핸드셰이크로 **~20% latency 증가**. |
| **트레이드오프(Trade-offs)** | - **제로 트러스트 vs. 전통적 보안**: 제로 트러스트는 **보안성 ↑**, 전통적 보안은 **구현 간소화**.<br>- **AES-256 vs. ChaCha20**: AES는 **보안성 ↑**, ChaCha20은 **속도 ↑**. |

## ⚠️ **잠재적 위험 분석**

### **1. 네트워크 장애로 인한 제어 시스템 마비**
- **설명**: 중앙 컨트롤러와 에지 디바이스 간 네트워크 장애 시 **실시간 제어 실패**로 작물 손실 또는 시설 파손 발생 가능. 특히 **스프링클러/환풍기** 제어 실패 시 **물리적 피해**로 이어질 수 있다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **다중 네트워크 인터페이스** 지원 (예: 4G + LoRaWAN).
  - **로컬 폴백 메커니즘** 구현 (예: 에지 디바이스에 사전 정의된 제어 로직 저장).
  - **정기 네트워크 테스트** (예: 주간 네트워크 장애 시뮬레이션).

### **2. 보안 취약점으로 인한 디바이스 해킹**
- **설명**: 에지 디바이스에 **기본 비밀번호**나 **미패치 취약점**이 존재할 경우, 해커가 **원격 제어**를 획득하여 시스템 마비 또는 데이터 유출을 유도할 수 있다.
- **심각도**: 🔴 High | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **디바이스 인증 강제**: 모든 디바이스에 **TOTP 기반 2FA** 적용.
  - **자동 패치 시스템**: 중앙 컨트롤러가 **오버더에어 업데이트(OTA)**를 통해 취약점 패치 강제.
  - **정기 보안 감사**: **KISA 기준**에 따라 분기별 보안 평가 실시.

### **3. 데이터 일관성 문제 (네트워크 분할 시)**
- **설명**: 네트워크 분할 시 **CRDT 동기화 실패**로 에지 디바이스와 중앙 컨트롤러 간 **데이터 불일치** 발생. 특히 **관수밸브 제어**에서 **중복 작동**으로 물 낭비가 발생할 수 있다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **데이터 버전 로그** 유지: 모든 변경 사항에 **timestamp + transaction ID** 할당.
  - **동기화 재시도 메커니즘**: 네트워크 복구 후 **자동 재동기화** 스크립트 실행.
  - **오프라인 모드 제어 제한**: 네트워크 분할 시 **읽기 전용 모드**로 강제 전환.

### **4. 확장성 한계로 인한 시스템 과부하**
- **설명**: 제어 모듈이 **100개 이상**으로 확장될 경우, 중앙 컨트롤러의 **CPU/메모리 과부하**로 시스템 다운 발생 가능. 특히 **MQTT 브로커**가 병목 현상을 유발할 수 있다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟢 Low (단기적으로)
- **대응 방안**:
  - **미들웨어 분산 처리**: **Kafka** 또는 **NATS**를 통해 MQTT 메시지 큐잉.
  - **로드 밸런싱**: 중앙 컨트롤러를 **클러스터링** (예: Kubernetes 기반).
  - **에지 디바이스 필터링**: 디바이스별 **QoS 레벨** 조절 (예: 비紧急 데이터는 QoS 1 사용).

### **5. 표준 호환성 문제으로 인한 상호운용성 실패**
- **설명**: 제3자 디바이스 (예: 다른 벤더의 **환풍기 제어기**)가 **oneM2M 표준**을 준수하지 않을 경우, **통신 실패**로 이어질 수 있다. 특히 **스마트팜 생태계**가 다양해질수록 위험이 증가한다.
- **심각도**: 🟡 Medium | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **어댑터 레이어 구현**: 표준 미준수 디바이스용 **프로토콜 변환기** 개발.
  - **공통 API 스펙 정의**: TTA 표준과 **Matter 프로토콜** 호환성 확보.
  - **벤더 협업**: 주요 디바이스 제조사와 **표준화 MoU** 체결.

### **6. 에너지 관리 실패로 인한 비용 증가**
- **설명**: **조명/난방 제어**가 비효율적으로 작동할 경우, **전력 비용**이 급격히 증가할 수 있다. 특히 **스프링클러**의 과도한 사용은 **물 낭비**로 이어진다.
- **심각도**: 🟢 Low | **발생 가능성**: 🟡 Medium
- **대응 방안**:
  - **AI 기반 예측 제어**: **ML 모델**을 통해 에너지 최적화 (예: 온도/습도 예측).
  - **사용량 모니터링**: 중앙 컨트롤러에 **실시간 에너지 사용량 대시보드** 통합.
  - **사용자 알림**: 비정상 사용량 발생 시 **SMS/이메일 알림** 자동 발송.

### **7. 유지보수성 저하로 인한 장기적 운영 실패**
- **설명**: 모듈화 아키텍처가 **과도하게 복잡**해질 경우, **유지보수 비용**이 증가하고 **기능 추가**가 어려워질 수 있다. 특히 **다양한 프로토콜(CoAP, MQTT, REST)** 관리가 어려울 수 있다.
- **심각도**: 🟢 Low | **발생 가능성**: 🟡 Medium (장기적)
- **대응 방안**:
  - **문서화 자동화**: **Swagger/OpenAPI**를 통해 API 문서화 자동 생성.
  - **모듈별 테스트**: **CI/CD 파이프라인** 구축 (예: GitHub Actions).
  - **트레이닝 프로그램**: 개발자 및 운영자 대상 **아키텍처 워크샵** 정기 개최.
